# 11.3 Skill 注入策略

> 技能注入（Skill Injection）是将 SKILL.md 定义的"专业知识+行为模式"注入到 Agent 推理上下文中的技术过程。根据注入的时机、位置和执行方式，可以分为 Inline 展开、Fork 子 Agent 和 Remote 加载三种策略，它们在 token 成本、延迟、隔离性和能力边界上存在本质差异。

---

## 一、注入策略的本质：上下文的"搬运"问题

在深入分析三种策略之前，需要理解一个核心矛盾：**Skill 的知识与 Agent 的上下文窗口之间的矛盾**。

一个中等复杂度的 SKILL.md 文件大约需要 1500-3000 个 token。当 Agent 活跃的技能数量从 3 个增长到 20 个时：

```
3个技能 × 2000 tokens = 6000 tokens（可接受）
10个技能 × 2000 tokens = 20000 tokens（吃紧）
20个技能 × 2000 tokens = 40000 tokens（大多数模型已无法承受）
```

三种注入策略本质上是对这个问题的不同权衡：

```
                     Token 成本  ←→  推理质量
                          │              │
              Inline ── 高(in)         高(Agent直接理解)
              Fork   ── 中(只调度)    中(子Agent质量)
              Remote ── 低(只索引)    低(受网络/API限制)
```

每种策略没有绝对的好坏，关键在于场景匹配。

---

## 二、策略一：Inline 展开

### 2.1 原理

Inline 展开是直接将 SKILL.md 的 Body 内容嵌入到主 Agent 的 System Prompt 或对话上下文中。这是最直接的注入方式，也是目前大多数 Agent 框架的默认做法。

```
         ┌─────────────────────────────────┐
         │        主 Agent 上下文            │
         │                                 │
         │  [System Prompt]                │
         │  你是一个有用的AI助手...          │
         │                                 │
         │  [Skill: code-reviewer]         │
         │  你是一个代码审查专家...          │
         │  1. 安全性分析                   │
         │  2. 性能评估                     │
         │  3. ...                         │
         │                                 │
         │  [Skill: database-architect]    │
         │  数据库架构设计原则...            │
         │  ...                            │
         │                                 │
         │  [对话历史]                      │
         │  User: 审查这段代码               │
         └─────────────────────────────────┘
```

### 2.2 适用场景

- **核心技能**：Agent 必须始终具备的基础能力
- **高频触发的技能**：每次对话几乎都会用到的技能
- **小型轻量技能**：Body 内容少于 500 token 的技能
- **对话全程技能**：贯穿整个对话的技能（如"安全助手"）

### 2.3 Token 成本模型

Inline 展开的成本由以下公式决定：

```
C_inline = Σ(skill_i.body_tokens) × N_turns
```

其中 `N_turns` 是对话轮次。由于所有技能在每个推理步骤都存在于上下文中，成本随对话轮次线性增长。

**成本明细**：

| 项目 | 计算方式 | 示例值 |
|------|----------|--------|
| 初始注入成本 | 所有激活技能的 Body token 总和 | 10 × 2000 = 20000 tokens |
| 每次推理固定成本 | 技能上下文固定不变 | 20000 tokens（每次推理都要"携带"） |
| 10 轮对话总成本 | 20000 × 10 = 200000 tokens | ~200K tokens |
| 100 轮对话总成本 | 20000 × 100 = 2000000 tokens | ~2M tokens |

### 2.4 优势

1. **零额外延迟**：技能内容已在上下文中，模型可直接使用
2. **全局可见**：主 Agent 在推理的任何阶段都能"感知"技能知识
3. **实现简单**：只需要字符串拼接，不需要路由逻辑
4. **一致性强**：Agent 的推理在统一的上下文中进行，不会出现 Agent 间不一致

### 2.5 劣势

1. **Token 消耗大**：上下文窗口被大量技能定义占据（见上文成本公式）
2. **注意力稀释**：如第 6.3 节所述，过长的 System Prompt 会导致模型注意力分散，核心指令被淹没在大量泛泛的技能描述中
3. **上下文窗口溢出**：当技能数量超过模型上下文限制时，部分技能被截断，行为不可预测
4. **更新困难**：运行中添加或移除技能需要重建整个上下文

## 三、策略二：Fork 子 Agent

### 3.1 原理

Fork 策略在主 Agent 需要执行特定任务时，派生出**一个独立的子 Agent 进程**来处理该任务。主 Agent 只保留"调度指令"（该找谁干），实际技能内容只在子 Agent 的上下文中加载。

```
         ┌──────────────────────────────┐
         │        主 Agent              │
         │                              │
         │  用户: 审查这段代码            │
         │  主Agent思考:                 │
         │    "我需要代码审查能力。        │
         │      → Fork code-reviewer    │
         │      子Agent 的结果: {...}    │
         │  "                          │
         └──────────┬───────────────────┘
                    │ "审查 tools/api.py"
                    ▼
         ┌──────────────────────────────┐
         │    子 Agent (code-reviewer)   │
         │                              │
         │  [Skill: code-reviewer]      │
         │  - 安全性分析                 │
         │  - 性能评估                   │
         │  - 代码质量                    │
         │                              │
         │  工具: read_file, search     │
         │  输出: structured_review     │
         └──────────┬───────────────────┘
                    │ 审查结果 JSON
                    ▼
         ┌──────────────────────────────┐
         │        主 Agent              │
         │  汇总结果并回复用户            │
         └──────────────────────────────┘
```

**Fork 的核心思想**：将"技能知识"从主 Agent 的上下文中剥离，只在需要时才在子 Agent 中加载。主 Agent 只需要知道"哪个技能处理什么类型的问题"。

### 3.2 适用场景

- **复杂专业技能**：Body 超过 1000 token 的重度技能
- **低频触发技能**：偶尔才会用到的技能（如"论文排版"）
- **需要专用工具的技能**：子 Agent 可以挂载不同的工具集
- **需要长上下文推理的技能**：避免主 Agent 上下文被"撑爆"

### 3.3 Token 成本模型

Fork 策略的成本由三部分组成：

```
C_fork = C_schedule + C_result + P_active × C_skill

其中：
- C_schedule = 主 Agent 调用子 Agent 的调度开销（约 200-500 tokens）
- C_result = 子 Agent 返回结果的开销（约 200-1000 tokens）
- P_active = 该技能被激活的概率（0~1）
- C_skill = 完整加载该技能 Body 的 token 数
```

**成本明细**（对比 Inline）：

| 项目 | Inline | Fork |
|------|--------|------|
| 10 个技能初始加载 | 20000 tokens（全部加载） | 0 tokens（技能不在主上下文） |
| "代码审查"触发 1 次 | 20000（所有技能仍在） | C_schedule(300) + C_skill(2000) + C_result(500) = 2800 |
| "数据库"触发 1 次 | 20000 | 2800（同上，复用公式） |
| 总共 10 轮对话 | ~200000 tokens | ~56000 tokens |
| **节省比例** | 基准 | **~72% token 节省** |

### 3.4 子 Agent 通信协议

Fork 策略需要定义主 Agent 和子 Agent 之间的接口协议：

```json
// 主 Agent → 子 Agent 的调度请求
{
  "skill": "code-reviewer",
  "task": "审查 tools/api.py",
  "context": {
    "project_root": "/path/to/project",
    "files": ["tools/api.py", "tools/db.py"],
    "branch": "feature/new-api",
    "user_intent": "检查安全漏洞和性能问题"
  },
  "tools_allowed": [
    "read_file",
    "search_code",
    "grep",
    "list_directory"
  ],
  "max_tokens": 8000,
  "timeout_ms": 30000
}
```

```json
// 子 Agent → 主 Agent 的响应
{
  "status": "completed",
  "summary": "发现 2 个安全问题、1 个性能问题",
  "findings": [
    {
      "file": "tools/api.py",
      "line": 45,
      "severity": "critical",
      "description": "SQL 注入风险: 未使用参数化查询"
    }
  ],
  "tokens_used": 4520,
  "confidence": "high"
}
```

### 3.5 优势

1. **Token 效率高**：只在需要时加载技能内容，主 Agent 上下文干净
2. **注意力集中**：子 Agent 可以专注于特定技能，不受其他上下文干扰
3. **隔离性好**：子 Agent 的推理错误不会污染主 Agent 的上下文
4. **可扩展性强**：理论上可以支持任意数量的技能，技能增加不会撑爆主上下文

### 3.6 劣势

1. **额外延迟**：每个 Fork 调用需要 1-3 秒（子 Agent 初始化 + 推理）
2. **调度开销**：主 Agent 需要判断"什么时候 Fork 什么技能"，这本身也是推理成本
3. **信息损耗**：子 Agent 看不到主 Agent 的完整对话上下文，可能做出与整体语境不符的判断
4. **实现复杂**：需要子 Agent 管理、通信协议、超时处理等基础设施
5. **级联结果出错**：极端情况下子 Agent 可能产生严重错误，主 Agent 全盘采信

## 四、策略三：Remote 加载

### 4.1 原理

Remote 加载将技能的执行完全委托给**远程服务**，主 Agent 只向远程服务发送调用请求并接收返回结果。技能的知识和执行都在远程完成，主 Agent 的上下文中只保留一个"函数签名"。

```
         ┌──────────────────────────────────┐
         │        主 Agent                   │
         │                                  │
         │  [轻量级技能索引]                  │
         │  code-reviewer → api.example.com  │
         │  database-architect → ...          │
         │  security-auditor → ...            │
         │                                  │
         │  用户: 审查这段代码                │
         │                                  │
         │  主Agent调度:                     │
         │  POST /skills/code-reviewer       │
         │  { file: "api.py" }              │
         │                                  │
         │  ← 远程服务返回结果                │
         │  { findings: [...] }              │
         │                                  │
         └──────────────────────────────────┘
                      │
                      │ HTTP / gRPC
                      ▼
         ┌──────────────────────────────────┐
         │       Remote Skill Service        │
         │                                  │
         │  ┌─ code-reviewer ─────────────┐ │
         │  │  LLM + SKILL.md             │ │
         │  │  + 专用工具集               │ │
         │  └─────────────────────────────┘ │
         │                                  │
         │  ┌─ database-architect ────────┐ │
         │  │  LLM + SKILL.md             │ │
         │  └─────────────────────────────┘ │
         └──────────────────────────────────┘
```

### 4.2 适用场景

- **计算密集型技能**：需要大量计算资源（如代码分析、大型文档处理）
- **需要领域专用模型的技能**：技能背后是特化的微调模型而非通用 LLM
- **技能即服务（Skill-as-a-Service）**：商业化的专业技能，按调用计费
- **数据敏感性技能**：需要在特定安全环境中执行（如内部网络中的代码审计）
- **资源受限客户端**：客户端无法承载完整推理，将技能执行卸载到云端

### 4.3 Token 成本模型

Remote 加载的成本分离为客户端和服务器端两部分：

```
C_remote_client = C_index + P_active × (C_request + C_response)
C_remote_server = P_active × C_skill_execution

其中:
- C_index = 技能索引开销（约 50-200 tokens）
- C_request = 请求序列化开销（约 100-300 tokens）
- C_response = 响应解析开销（约 200-800 tokens）
- C_skill_execution = 远程端执行该技能的完整 token 消耗
```

**三种策略综合对比**（10 个技能、10 轮对话的场景）：

| 指标 | Inline | Fork | Remote |
|------|--------|------|--------|
| **主上下文平均占用** | 20000 tokens | 500 tokens（仅索引） | 200 tokens（仅索引） |
| **每次技能调用增加** | 0（已在上下文中） | 2800 tokens | 500 tokens（仅传参+收结果） |
| **10 轮总 token** | ~200K | ~56K | ~35K（客户端） |
| **额外延迟** | 0 | 1-3s/次调用 | 2-8s/次调用（含网络） |
| **客户端计算需求** | 高 | 高 | 低 |
| **技能隔离性** | 无 | 好 | 最好 |
| **实现复杂度** | 低 | 中 | 高 |
| **离线可用** | 是 | 是 | 否 |
| **技能权限控制** | 无 | 中 | 强 |

### 4.4 Remote 服务 API 规范

建议的 RESTful API 标准：

```yaml
POST /api/v1/skills/{skill_name}/execute
Content-Type: application/json

Request:
{
  "task": "审查 tools/api.py 的安全问题",
  "context": {
    "project_language": "python",
    "framework": "fastapi",
    "files": [
      {
        "path": "tools/api.py",
        "content": "from fastapi import ..."
      }
    ]
  },
  "options": {
    "focus_areas": ["security"],
    "max_findings": 10
  }
}

Response:
{
  "request_id": "req_abc123",
  "status": "completed",
  "result": { ... },
  "usage": {
    "tokens_in": 4532,
    "tokens_out": 1287,
    "latency_ms": 3420
  },
  "confidence": 0.92
}
```

### 4.5 优势

1. **最小的客户端 token 占用**：主 Agent 只需维护技能索引
2. **最强的隔离性**：技能执行在独立环境中，安全可控
3. **可商业化**：可以作为 API 产品或服务提供
4. **资源优化**：远程服务可以使用更适合该任务的模型或硬件
5. **实时更新**：服务端技能可以随时更新，客户端无需变更

### 4.6 劣势

1. **网络延迟**：每次调用增加 1-5s 的网络往返时间
2. **离线不可用**：依赖网络连接
3. **服务依赖**：远程服务宕机 = 技能不可用
4. **数据隐私**：发送的请求中可能包含敏感数据
5. **额外成本**：同时支付客户端推理 + 远程服务调用费用
6. **复杂度高**：需要认证、限流、计费、监控等基础设施

## 五、混合策略：在实践中组合使用

大多数生产级 Agent 系统不会只用一种策略，而是**混合使用**：

### 5.1 混合策略配置示例

```yaml
# .skills.json 中的注入策略配置
skills:
  # 高频、轻量技能 → Inline（无额外延迟）
  default_injection: inline
  always_active:
    - name: security-guard
      strategy: inline
      priority: 100
    
  # 中低频、复杂技能 → Fork（按需加载）
  fork_strategy:
    enabled: true
    max_concurrent_forks: 3
    fork_timeout_ms: 30000
    skills:
      - code-reviewer
      - database-architect
      - performance-analyzer
    
  # 外部依赖、商业技能 → Remote
  remote_strategy:
    enabled: true
    endpoint: "https://skills.example.com"
    api_key: "${SKILLS_API_KEY}"
    skills:
      - compliance-checker
      - legal-review
      - patent-search
```

### 5.2 推荐的策略选择矩阵

| 技能特征 | 推荐策略 | 理由 |
|----------|----------|------|
| Body < 500 tokens，每次对话都触发 | Inline | 无额外延迟，小成本 |
| Body > 1500 tokens，偶尔触发 | Fork | 节省主上下文，按需加载 |
| 需要专用模型/计算资源 | Remote | 资源卸载，特化处理 |
| Body < 500 tokens，极少触发 | Fork | 比 Remote 更快，离线可用 |
| 涉及敏感数据（PII、密钥） | Fork（本地）或 Remote（私有部署） | 数据不出环境 |
| 技能来自第三方/商业服务 | Remote | 按调用计费，自动更新 |
| Agent 在边缘设备上运行 | Remote | 客户端计算资源不足 |
| 需要实时性（< 500ms 响应） | Inline 或 Fork（预热） | Remote 网络延迟不可接受 |

## 六、注入时机：Lazy vs Eager

除了注入方式，还有注入时机的问题：

### 6.1 Eager Loading（预加载）

```python
# Agent 启动时，将所有 Inline 策略的技能加载到上下文
def eager_load(registry: SkillRegistry):
    context = []
    for skill in registry.get_skills_by_strategy('inline'):
        context.append(skill.body)
    return "\n\n".join(context)
```

**优点**：零延迟激活，随时可用。
**缺点**：即使该技能从未被使用，也占用上下文。

### 6.2 Lazy Loading（按需加载）

```python
# 只有在 when_to_use 匹配时才注入
def lazy_load(registry: SkillRegistry, user_input: str):
    matched_skills = registry.match_skills(user_input)
    context = []
    for skill in matched_skills:
        if skill.strategy in ('fork', 'remote'):
            # Fork/Remote 策略创建子 Agent 或远程调用
            continue
        context.append(skill.body)
    return context
```

**优点**：只加载匹配的技能，节省上下文空间。
**缺点**：匹配过程需要时间，首次使用有延迟。

### 6.3 Hybrid 策略

实践中推荐的做法：

- **Inline + Eager**：少量（≤3 个）核心技能始终加载
- **Inline + Lazy**：中等数量的 Inline 技能匹配后注入
- **Fork/Remote + Lazy**：按需调用，通过 when_to_use 匹配

---

## 关键概念速查

| 术语 | 解释 |
|------|------|
| Inline 展开 | 将 SKILL.md Body 直接嵌入主 Agent 上下文，零额外延迟但消耗大 |
| Fork 子 Agent | 主 Agent 调度子 Agent 执行技能，节省主上下文但有调度延迟 |
| Remote 加载 | 将技能执行委托给远程服务，最小化客户端 token 但依赖网络 |
| C_schedule | Fork 策略中主 Agent 调度子 Agent 的 token 开销 |
| Lazy Loading | 技能在匹配触发时才注入上下文 |
| Eager Loading | 技能在 Agent 启动时预先加载 |
| 混合策略 | 根据技能特征选择不同的注入策略，实践中通常组合使用 |
| 子 Agent 通信协议 | Fork 策略中主/子 Agent 间的结构化数据交换格式 |
