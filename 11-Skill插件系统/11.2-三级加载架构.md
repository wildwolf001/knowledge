# 11.2 三级加载架构

> 三级加载架构将技能来源划分为 Bundled（内置）、User（用户）和 Project（项目）三个层级，通过优先级和覆盖规则决定最终生效的技能组合。这套架构解决了"技能从哪里来、谁覆盖谁、冲突怎么办"的核心问题。

---

## 一、为什么需要三级加载架构？

当 Agent 管理的 Skill 数量从个位数增长到成百上千时，以下问题就会浮现：

1. **来源混乱**：Agent 的出厂技能和用户自己添加的技能混在一起，无法区分
2. **版本冲突**：用户自定义的技能和内置技能定义了相同的行为，谁说了算？
3. **项目隔离**：在 A 项目配置的技能不应该在 B 项目中自动生效
4. **加载效率**：每次启动时查找多少个目录？从哪里加载？搜索路径如何配置？

**三级加载架构**用"分层 + 覆盖"的朴素思路解决了这些问题：

```
层级越高，优先级越高
       ▲
       │    Project 技能（项目特定）
       │    └─ 项目目录下 .skills/
       │
       │    User 技能（用户全局）
       │    └─ ~/.agent/skills/
       │
       │    Bundled 技能（出厂内置）
       │    └─ 安装目录下 skills/
       └───▶ 加载顺序：自底向上扫描，上层覆盖下层
```

## 二、三级加载架构详解

### 2.1 第一级：Bundled（内置）技能

**定义**：随 Agent 发行包一起安装的出厂技能。由 Agent 框架的维护团队发布和维护。

**存储位置**：
```
<agent-install-dir>/skills/
├── code-reviewer/
│   └── SKILL.md
├── database-architect/
│   ├── SKILL.md
│   └── templates/
│       └── schema-review.json
├── security-auditor/
│   └── SKILL.md
├── docker-helper/
│   └── SKILL.md
└── git-workflow/
    └── SKILL.md
```

**特点**：
- 基础覆盖面广：覆盖通用场景（编码、数据库、Docker、Git 等）
- 经过官方测试和验证
- 不可删除（但可以被上层覆盖）
- 随 Agent 版本一起更新
- 通常以 `bundled/` 命名空间标识

**内置 Skill 的更新策略**：
```
Agent v1.0 → 附带内置技能 v1.0
Agent v1.1 → 内置技能可能升级到 v1.1
    用户如果未自定义，自动跟随升级
    用户如果已覆盖，保留用户的版本
```

**典型的内置 Skill 列表**：

| 技能名称 | 功能 | 优先级（默认） |
|----------|------|----------------|
| `code-reviewer` | 代码审查 | 0 |
| `database-architect` | 数据库设计 | 0 |
| `security-auditor` | 安全审计 | 0 |
| `docker-helper` | Docker 操作 | 0 |
| `git-workflow` | Git 工作流 | 0 |
| `prompt-engineer` | Prompt 工程协助 | 0 |
| `debug-helper` | 调试辅助 | 0 |

### 2.2 第二级：User（用户）技能

**定义**：用户自定义或从社区安装的全局技能。对当前设备上的所有项目生效。

**存储位置**：
```
~/.agent/skills/
├── my-code-style/
│   └── SKILL.md
├── company-api-helper/
│   └── SKILL.md
├── custom-commit-formatter/
│   └── SKILL.md
└── installed/
    ├── terraform-helper@1.2.0/
    │   └── SKILL.md
    └── k8s-troubleshoot@0.8.0/
        └── SKILL.md
```

**特点**：
- 用户自定义的工作流偏好（如代码风格的个性化要求）
- 从社区安装的第三方 Skill（类似 VSCode 的扩展市场）
- 跨项目共享，适用于用户日常工作流
- 优先级高于 Bundled 技能

**获取来源**：

| 来源 | 说明 | 更新机制 |
|------|------|----------|
| 用户自建 | 用户按 SKILL.md 标准自行编写 | 手动管理 |
| 社区市场 | Skill 注册中心，类似 npm/GitHub Marketplace | 自动更新 |
| 团队仓库 | 企业内部的 Skill 仓库，通过 git 分发 | git pull |
| AI 生成 | Agent 根据用户行为分析自动生成 | Agent 管理 |

### 2.3 第三级：Project（项目）技能

**定义**：绑定到特定项目的技能。只在该项目的上下文中生效。

**存储位置**（位于项目根目录下）：
```
<project-root>/
├── src/
├── tests/
├── docs/
├── .skills/                    ← 项目技能目录
│   ├── project-rules/
│   │   └── SKILL.md            ← 项目的编码规范
│   ├── api-schema-validator/
│   │   └── SKILL.md
│   └── deployment-workflow/
│       └── SKILL.md
├── .skills.json                ← 项目技能配置文件
└── README.md
```

**.skills.json 配置文件示例**：

```json
{
  "version": "1.0",
  "project": "my-backend-service",
  "skills": {
    "enabled": [
      "project-rules",
      "api-schema-validator",
      "deployment-workflow"
    ],
    "disabled": [
      "code-reviewer",
      "database-architect"
    ],
    "overrides": {
      "code-reviewer": {
        "priority": 100,
        "config": {
          "focus_areas": ["security", "error_handling"],
          "ignore_patterns": ["generated/", "vendor/"]
        }
      }
    }
  },
  "extends": [
    "~/.agent/skills/company-api-helper"
  ]
}
```

**特点**：
- 最高优先级：项目配置覆盖用户和内置配置
- 环境隔离：不同项目可以有完全不同的技能组合
- 团队共享：`.skills/` 目录应纳入版本控制
- 可禁用内置技能：当项目不需要某些内置技能时，在 `disabled` 中声明

## 三、优先级与覆盖规则

### 3.1 基础覆盖规则

**核心原则：上层覆盖下层，具体覆盖通用**

```
  名称层级                  优先级
  ┌─────────────────────┐
  │  Project Skill      │  最高 (200)
  ├─────────────────────┤
  │  User Skill         │  中等 (100)
  ├─────────────────────┤
  │  Bundled Skill      │  最低 (0)
  └─────────────────────┘
```

**覆盖规则示例**：

```
场景：Agent 自带内置技能 docker-helper，但用户自定义了同名的用户级技能

加载后生效的是 → 用户的 docker-helper（覆盖内置版本）

原因：User 层级（优先级 100）> Bundled 层级（优先级 0）
```

### 3.2 详细覆盖规则

#### 规则 1：同名覆盖

当不同层级存在同名（`name` 相同）的 Skill 时，高优先级层级的版本完全取代低优先级版本。

```
生效技能 = 具有最高优先级的同名技能
```

#### 规则 2：配置合并

对于不同名的技能，各层级之间是叠加关系——同一层级内不能有同名技能，但不同层级的技能互相补充。

```yaml
# 生效技能集合 = Bundled ∪ User ∪ Project
# 冲突时按规则1处理
```

#### 规则 3：优先级数值

在同一个层级内，`priority` 字段决定加载顺序。优先级高的技能在 Agent 的上下文中"更靠前"：

```yaml
# 在 Project 层级中
- name: security-critical
  priority: 200    # 高优先级 → 在 System Prompt 中靠前注入
- name: nice-to-have
  priority: -10    # 低优先级 → 在靠后位置，可能被上下文截断
```

#### 规则 4：禁用指令

项目或用户层可以显式禁用某个技能。禁用的技能在任何层级都不会被加载：

```yaml
# .skills.json
"disabled": ["database-architect", "docker-helper"]
```

#### 规则 5：部分覆盖（Override）

不替换整个技能，只覆盖技能的某些字段：

```yaml
# .skills.json 中的 overrides 配置
"overrides": {
  "code-reviewer": {
    "priority": 150,
    "config": {
      "strictness": "high",     # 提升代码审查的严格度
      "languages": ["python"]   # 只审查 Python 代码
    }
  }
}
```

### 3.3 加载流程

Agent 启动时的完整技能加载流程：

```
加载开始
   │
   ├── 1. 扫描 Bundled 目录
   │       └── 读取所有 SKILL.md → 构建内置技能索引
   │
   ├── 2. 扫描 User 目录
   │       ├── 读取所有 SKILL.md → 构建用户技能索引
   │       └── 同名覆盖：用户技能替换内置版本
   │
   ├── 3. 扫描 Project 目录
   │       ├── 读取 .skills/.skills.json → 构建项目技能索引
   │       ├── 同名覆盖：项目技能替换下层版本
   │       └── 处理 disabled 列表：从索引中移除
   │
   ├── 4. 解析依赖树
   │       ├── 构建所有已启用技能的 DAG
   │       ├── 自动加载依赖技能
   │       └── 检测循环依赖并报错
   │
   ├── 5. 应用 Overrides
   │       └── 合并 config、调整 priority
   │
   ├── 6. 优先级排序
   │       └── 按 priority 降序排列技能
   │
   └── 7. 构建最终技能注册表
           └── 注入 Agent 上下文（详见 11.3 节）
```

### 3.4 依赖处理的特殊规则

当 A 技能依赖 B 技能时的处理逻辑：

```
加载 A（name: api-tester）
  │
  ├── 检查 A.depends_on = ["http-client"]
  │
  ├── 在注册表中查找 http-client
  │     ├── 如果找到 → 使用已加载的版本
  │     └── 如果未找到 →
  │           ├── 在三级目录中搜索 http-client
  │           ├── 如果找到 → 加载
  │           └── 如果未找到 → 报错：缺少依赖
  │
  └── 依赖满足 → 完成 A 的加载
```

依赖查找的顺序也是自底向上（Bundled → User → Project），确保项目层级的依赖优先加载。

## 四、加载决策的工程实现

### 4.1 技能注册表（Skill Registry）

技能注册表是 Agent 运行时维护的内存数据结构，保存所有已加载技能的信息：

```typescript
interface SkillRegistry {
  skills: Map<string, LoadedSkill>;
  layers: {
    bundled: Set<string>;  // 技能名称集合
    user: Set<string>;
    project: Set<string>;
  };
  disabled: Set<string>;
  overrides: Map<string, SkillOverride>;
}

interface LoadedSkill {
  name: string;
  version: string;
  source: 'bundled' | 'user' | 'project';
  priority: number;
  frontmatter: SkillFrontmatter;
  body: string;
  config: Record<string, any>;
  dependsOn: string[];
  resolvedDeps: string[];  // 解析后的依赖列表
}
```

### 4.2 覆盖算法实现

```python
class SkillManager:
    def __init__(self):
        self.registry = SkillRegistry()
    
    def load_all(self, project_root: str):
        """三级加载入口"""
        # Step 1: 加载 Bundled
        bundled_skills = self._scan_directory(BUNDLED_DIR)
        self._register_bulk(bundled_skills, layer='bundled')
        
        # Step 2: 加载 User
        user_skills = self._scan_directory(USER_SKILL_DIR)
        self._register_bulk(user_skills, layer='user')
        
        # Step 3: 加载 Project
        project_skills = self._scan_directory(
            os.path.join(project_root, '.skills')
        )
        project_config = self._read_project_config(project_root)
        self._register_bulk(project_skills, layer='project')
        
        # Step 4: 处理禁用和覆盖
        self._apply_disabled(project_config.disabled)
        self._apply_overrides(project_config.overrides)
        
        # Step 5: 依赖解析
        self._resolve_dependencies()
        
        # Step 6: 优先级排序
        return self._sort_by_priority()
    
    def _register_bulk(self, skills: list, layer: str):
        """注册技能，处理同名覆盖"""
        for sk in skills:
            existing = self.registry.skills.get(sk.name)
            layer_order = {'bundled': 0, 'user': 1, 'project': 2}
            
            if existing is None:
                # 新技能，直接注册
                self.registry.skills[sk.name] = sk
            elif layer_order[layer] > layer_order[existing.source]:
                # 上层覆盖下层
                self.registry.skills[sk.name] = sk
            
            # 记录来源
            self.registry.layers[layer].add(sk.name)
```

### 4.3 调试和诊断

当技能加载出现预期之外的行为时，诊断表格可以提供快速排查线索：

| 现象 | 可能原因 | 排查方法 |
|------|----------|----------|
| 技能未生效 | 被上层同名技能覆盖 | 检查 User/Project 层是否有同名技能 |
| 技能冲突 | 依赖解析错误 | 使用 `skill-manager --debug` 查看依赖图 |
| 加载失败 | 依赖缺失或循环依赖 | 检查 depends_on 声明是否正确 |
| 行为异常 | 优先级排序错误 | 检查 priority 字段 |
| "技能不存在" | 在 disabled 列表中 | 查看 .skills.json 的 disabled 配置 |

推荐提供 CLI 诊断命令：

```bash
# 查看当前加载的所有技能
agent skills list

# 查看技能加载详情（来源、优先级）
agent skills inspect code-reviewer

# 查看技能依赖图
agent skills deps --graph

# 查看层级覆盖关系
agent skills layers
```

## 五、跨设备与团队同步

### 5.1 技能目录的版本控制

| 层级 | 是否纳入版本控制 | 建议 |
|------|-----------------|------|
| Bundled | 否 | 随 Agent 版本管理 |
| User - 自建 | 用户自行决定 | 建议用 dotfiles 管理 |
| User - 安装 | 否 | 通过 Skill Manager 安装/更新 |
| Project | 是 | 纳入项目 git 仓库 |

### 5.2 多环境一致性

在 CI/CD 和多人协作场景中，需要确保所有开发者使用相同的技能配置：

```json
// skills.lock.json — 锁定所有技能的精确版本
{
  "generated_at": "2026-05-20T10:30:00Z",
  "agent_version": "2.1.0",
  "bundled_skills": {
    "code-reviewer": "1.3.0",
    "database-architect": "2.1.0"
  },
  "user_skills": {
    "company-api-helper": "3.2.1",
    "my-code-style": "1.0.0"
  },
  "project_skills": {
    "project-rules": "0.5.0",
    "api-schema-validator": "0.2.0"
  }
}
```

这个锁定文件类似于 `package-lock.json` 或 `Gemfile.lock`，确保团队成员加载的**完全相同版本**的技能。

## 关键概念速查

| 术语 | 解释 |
|------|------|
| Bundled Skill | Agent 出厂内置的基础技能，不可删除 |
| User Skill | 用户全局技能，对所有项目生效 |
| Project Skill | 项目限定技能，仅在该项目范围内生效 |
| 层级覆盖 | 上层（Project）覆盖下层（Bundled），同名冲突时高优先级胜出 |
| 技能注册表 | Agent 运行时的内存数据结构，保存所有已加载技能 |
| 依赖解析 | 根据 depends_on 声明构建依赖 DAG，自动加载依赖技能 |
| Disabled 列表 | 显式禁用的技能集合，在任何层级都不会被加载 |
| Override 配置 | 不替换整个技能，只覆盖特定字段（如 priority、config） |
| skills.lock.json | 锁定所有技能精确版本的配置文件，保证多环境一致性 |

## 六、2026年生态发展

### 6.1 OpenClaw Skill市场

OpenClaw的Skill市场在2026年上半年迎来爆发式增长：

- **半年积累超过13,700个Skill**，涵盖从代码开发到金融分析的各个领域
- 每个Skill包含**触发条件、标准流程和可执行脚本**的完整封装
- 行业Know-how首次以标准化Skill形式被系统性整理和分发

### 6.2 行业Know-how的Skill标准化

2026年最重要的趋势之一，是垂直行业的专业知识开始以Skill形式标准化：

| 行业 | Skill示例 | 价值 |
|------|----------|------|
| 金融合规 | 反洗钱交易审查、KYC文档验证 | 将监管合规经验转化为可复用的Agent能力 |
| 医疗诊断辅助 | 影像报告生成、用药相互作用检查 | 降低医疗AI应用的门槛 |
| 法律文书 | 合同审查、案例法检索 | 将律师的审查流程标准化 |
| 制造业 | 设备故障诊断、质量检测流程 | 维护经验不再是"老师傅的脑子" |

这一趋势的深远影响在于：**行业专业知识首次以可编程、可版本控制、可审计的形式存在**，而不再依赖于个人经验或非结构化文档。
