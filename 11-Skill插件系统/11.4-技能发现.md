# 11.4 技能发现

> 技能发现（Skill Discovery）是 Agent 在运行时"决定该激活哪些技能"的过程。它的核心矛盾是：**激活得太积极 → 上下文被无关技能撑爆；激活得太保守 → 该用的技能没用到，回答质量下降**。本章讨论三种发现机制——关键词匹配、AI 分类和用户显式调用——以及它们的组合策略。

---

## 一、为什么要做技能发现？

在三级加载架构（11.2 节）完成了技能的**静态注册**后，Agent 面临的问题是：在一个 100 个技能的注册表中，面对用户的一句话，**该把哪些技能注入到当前上下文中**？

```
技能注册表（100 个技能）
    │
    ├── 全部注入 → 上下文爆炸（200K tokens×）
    ├── 不注入 → Agent 没有专业能力（和普通 Chat 无异）
    └── 选择性注入 → 核心问题：选哪些？选几个？怎么选？
```

技能发现解决的就是这个"选择性注入"的问题。它的输入是"用户输入 + 当前上下文状态"，输出是"应该激活的技能列表"。

```
用户输入 + 上下文状态
       │
       ▼
┌──────────────────────────────────┐
│        技能发现引擎               │
│                                  │
│  1. 关键词匹配（快速预筛）          │
│  2. AI 分类（深度语义理解）         │
│  3. 上下文推断（隐式需求）          │
│  4. 优先级排序（限制激活数量）       │
│                                  │
└──────────────┬───────────────────┘
               │ 激活的技能列表
               ▼
          Skill 注入（11.3 节）
```

## 二、三种发现机制

### 2.1 关键词匹配（Keyword Matching）

**原理**：将用户输入与 SKILL.md Frontmatter 中的 `when_to_use` 字段进行字符串匹配。

**这是最快速、最确定的发现方式**——不涉及模型推理，纯规则引擎。

**匹配算法**：

```python
from typing import List
import re

class KeywordMatcher:
    def __init__(self):
        # 技能名 → 触发词列表
        self.trigger_index: dict[str, List[str]] = {}
    
    def register_skill(self, skill_name: str, triggers: List[str]):
        """注册技能的触发词"""
        self.trigger_index[skill_name] = triggers
    
    def match(self, user_input: str, top_k: int = 5) -> List[str]:
        """
        在用户输入中查找触发词，返回匹配的技能名称列表
        """
        input_lower = user_input.lower()
        scores = {}
        
        for skill_name, triggers in self.trigger_index.items():
            score = 0
            for trigger in triggers:
                # 精确匹配
                if trigger.lower() in input_lower:
                    score += 10
                # 正则匹配（支持通配符）
                if re.search(self._to_regex(trigger), input_lower):
                    score += 5
                # 词级别匹配（处理复合词）
                trigger_words = set(trigger.lower().split())
                input_words = set(input_lower.split())
                overlap = len(trigger_words & input_words)
                if overlap > 0:
                    score += overlap * 2
            
            if score > 0:
                scores[skill_name] = score
        
        # 按匹配分数排序，取 top_k
        sorted_skills = sorted(
            scores.items(), 
            key=lambda x: x[1], 
            reverse=True
        )
        return [s[0] for s in sorted_skills[:top_k]]
    
    def _to_regex(self, trigger: str) -> str:
        """将通配符触发词转为正则"""
        pattern = re.escape(trigger)
        pattern = pattern.replace(r'\*', '.*')
        pattern = pattern.replace(r'\?', '.')
        return pattern
```

**匹配模式举例**：

| 用户输入 | 匹配的 when_to_use | 技能 |
|----------|---------------------|------|
| "帮我审查这段代码" | `"代码审查"`, `"code review"` | code-reviewer |
| "分析一下数据库Schema" | `"数据库设计"`, `"schema设计"` | database-architect |
| "数据库慢查询怎么优化" | `"慢查询"`, `"索引优化"` | database-architect |
| "用Docker部署这个服务" | `"docker"`, `"docker部署"` | docker-helper |
| "这个API安全吗" | `"安全审计"`, `"security"` | security-auditor |

**局限性**：

1. **语义盲区**：无法理解同义表达。"数据库性能瓶颈在哪"可能匹配不到 `"慢查询"`
2. **上下文缺失**：只做单轮匹配，不考虑对话历史。"继续"——继续什么？
3. **多义词误触发**：`"security"` 可能同时匹配安全审计和网络安全
4. **一词多技能**：同一个关键词可能匹配多个技能，难以区分

**为了解决语义盲区，需要引入第二种机制**。

### 2.2 AI 分类（AI Classification）

**原理**：使用 LLM 或专用分类模型理解用户输入的语义，然后根据语义匹配最适合的技能。

```
    用户输入："这段代码的数据库查询很慢，怎么优化？"
                    │
                    ▼
     ┌─────────────────────────────┐
     │    AI 分类模型               │
     │                             │
     │  语义理解层:                 │
     │  - 主领域: 数据库            │
     │  - 子领域: 查询优化          │
     │  - 意图: 寻求优化建议        │
     │                             │
     │  技能映射层:                 │
     │  1. database-architect  (92%)│  ← 选中
     │  2. performance-analyzer(75%)│
     │  3. code-reviewer      (30%)│
     └─────────────────────────────┘
```

#### 2.2.1 语义分类（Semantic Classification）

使用文本嵌入模型（Embedding Model）将用户输入和技能描述映射到同一个向量空间：

```python
import numpy as np
from typing import List

class SemanticSkillMatcher:
    def __init__(self, embedding_model):
        self.embedding_model = embedding_model
        self.skill_embeddings = {}  # skill_name → embedding
    
    def index_skills(self, skills: List[dict]):
        """将技能描述转为向量索引"""
        for skill in skills:
            # 合并技能用于语义匹配的文本
            search_text = f"{skill['name']}: {skill['description']}. " \
                          f"Triggers: {', '.join(skill['when_to_use'])}. " \
                          f"Tags: {', '.join(skill.get('tags', []))}"
            self.skill_embeddings[skill['name']] = \
                self.embedding_model.encode(search_text)
    
    def match(self, user_input: str, top_k: int = 5, threshold: float = 0.6) -> List[str]:
        """语义匹配：计算余弦相似度"""
        input_embedding = self.embedding_model.encode(user_input)
        
        similarities = []
        for skill_name, skill_emb in self.skill_embeddings.items():
            # 余弦相似度
            cos_sim = np.dot(input_embedding, skill_emb) / \
                      (np.linalg.norm(input_embedding) * np.linalg.norm(skill_emb))
            if cos_sim >= threshold:
                similarities.append((skill_name, cos_sim))
        
        # 按相似度排序
        similarities.sort(key=lambda x: x[1], reverse=True)
        return [s[0] for s in similarities[:top_k]]
```

#### 2.2.2 LLM 路由（LLM Routing）

使用 LLM 本身来做技能选择的"路由器"。这比嵌入分类更准确，但成本也更高：

```python
SKILL_ROUTER_PROMPT = """
你是一个技能路由专家。你的任务是根据用户的输入，从以下技能列表中选择最合适的技能。

技能列表：
{skill_list}

用户输入：{user_input}

请选择最匹配的 1-3 个技能，并以 JSON 数组格式输出：
["skill_name_1", "skill_name_2"]

要求：
- 只选择与用户输入**高度相关**的技能
- 如果用户输入明显不涉及任何技能，输出空数组 []
- 优先选择语义匹配度高的技能，而非字面匹配
- 考虑对话历史中的上下文
"""

def llm_router(user_input: str, skill_registry: dict, llm) -> List[str]:
    """使用 LLM 进行技能路由"""
    skill_list = "\n".join([
        f"- {s['name']}: {s['description']} [{', '.join(s['tags'])}]"
        for s in skill_registry.values()
    ])
    
    prompt = SKILL_ROUTER_PROMPT.format(
        skill_list=skill_list,
        user_input=user_input
    )
    
    response = llm.generate(prompt)
    # 解析 JSON 响应
    import json
    try:
        return json.loads(response)
    except:
        return []
```

**两种 AI 分类方式的对比**：

| 维度 | 嵌入分类 | LLM 路由 |
|------|----------|----------|
| 模型大小 | 小型（100M-300M 参数） | 大型（数十亿参数） |
| 延迟 | 5-20ms | 200-2000ms |
| 成本 | ~1/1000 的 LLM 调用成本 | 每次调用也需要 LLM 推理 |
| 准确性 | 中等，依赖嵌入质量 | 高，能理解复杂语义 |
| 上下文感知 | 单轮 | 可结合对话历史 |
| 技能数量扩展 | 良好（向量检索可扩展到百万级） | 受 Prompt 长度限制 |
| 离线可用 | 可以（小模型本地运行） | 通常需要 API 调用 |

### 2.3 用户显式调用（Explicit Invocation）

**原理**：用户直接告诉 Agent 要使用什么技能。这是三种方式中最确定、最不可疑的。

**调用方式**：

```
方式一：斜杠命令（Slash Command）
  /code-review tools/api.py
  /database-architect 帮忙设计订单表
  /security-auditor --full

方式二：自然语言显式指定
  "请使用代码审查技能审查这段代码"
  "启动数据库架构师模式"
  "切换到安全审计模式"

方式三：API 参数指定（程序化调用）
  POST /agent/chat
  {
    "message": "审查这段代码",
    "skills": ["code-reviewer", "security-auditor"]
  }

方式四：UI 切换（图形界面）
  [技能选择器]
  ☑ 代码审查
  ☑ 数据库设计
  ☐ Docker 助手
```

**用户显式调用的优势**：
- **零误判**：用户明确指定，没有匹配错误的可能
- **最高优先级**：用户的显式指令应覆盖任何自动匹配结果
- **适合"模式切换"**：用户知道当前任务需要什么技能

**用户显式调用的劣势**：
- **用户负担**：用户需要知道有哪些技能可用、叫什么名字
- **发现成本**：用户不知道"原来还有这个技能"（可通过 `/skills` 命令解决）
- **不适合新手**：新手用户可能不知道应该显式调用

## 三、什么时候自动激活，什么时候等待指令？

这就是技能发现的决策边界问题。以下是一个决策树：

```
用户输入到达
    │
    ├── 用户是否显式指定了技能？
    │       ├── 是 → 无条件执行该技能（最高优先级）
    │       └── 否 → 进入自动匹配流程
    │
    ├── 关键词匹配是否命中？
    │       ├── 是 && 匹配分数 > HIGH_THRESHOLD →
    │       │       自动激活（无需用户确认）
    │       ├── 是 && 匹配分数在 MEDIUM 范围 →
    │       │       建议激活（等待用户确认）
    │       └── 否 → 进入 AI 分类
    │
    ├── AI 分类的置信度如何？
    │       ├── 置信度 > 0.85 →
    │       │       自动激活
    │       ├── 0.60 ≤ 置信度 < 0.85 →
    │       │       建议激活（"我可以用XXX技能帮你，需要吗？"）
    │       └── 置信度 < 0.60 →
    │              不激活任何技能，以通用能力回答
    │
    └── 用户补充输入？
            └── 结合补充信息重新匹配
```

### 3.1 自动激活条件

以下情况应该**自动激活**技能（不询问用户）：

1. **高置信度匹配**：关键词匹配分数 > 阈值，或 AI 分类置信度 > 0.85
2. **安全/合规类技能**：安全审计、数据脱敏等应始终自动激活
3. **用户历史偏好**：用户在过去类似场景中多次确认使用某个技能
4. **显式指定**：用户直接要求使用某个技能

### 3.2 建议激活（等待确认）条件

以下情况应该**建议激活**（询问用户是否启用）：

1. **中等置信度匹配**：0.60 ≤ 置信度 < 0.85
2. **高 Token 成本的技能**：该技能注入后消耗大量上下文，确认后再注入更合理
3. **首次使用的技能**：Agent 不确定用户是否希望使用该技能
4. **容易误触发的技能**：如"部署"类技能，误触发可能导致意外操作

**建议激活的交互示例**：

```
用户: 这个数据库查询很慢
Agent: 我可以用"数据库架构设计"技能来帮你分析查询性能，
       是否需要激活这个技能？(/yes 或 /no)
```

### 3.3 不激活条件

以下情况**不激活任何技能**：

1. **低置信度匹配**：没有任何技能的匹配分数超过阈值
2. **通用聊天场景**：用户只是闲聊或提出简单问题
3. **冲突场景**：多个技能竞争但都不够明确，等待用户澄清

## 四、上下文感知发现

除了分析"当前这一句话"，技能发现还应该考虑**对话上下文**：

### 4.1 对话历史分析

```python
def context_aware_discovery(
    current_input: str,
    conversation_history: List[str],
    active_skills: List[str],
    skill_registry: dict
) -> List[str]:
    """
    结合对话上下文进行技能发现
    """
    new_matches = []
    
    # 1. 在当前输入中匹配
    current_matches = match_skills(current_input, skill_registry)
    new_matches.extend(current_matches)
    
    # 2. 检查对话历史中的"未闭合"技能引用
    #    如果上一轮提到了"review this code"，这一轮说"继续"
    #    应该保持 code-reviewer 技能的激活状态
    if any(word in current_input.lower() for word in ["继续", "接着", "同上", "还是"]):
        new_matches.extend(active_skills)  # 保持已有技能
    
    # 3. 检查是否有新信息补充了之前的匹配
    combined = " ".join(conversation_history[-3:] + [current_input])
    combined_matches = match_skills(combined, skill_registry)
    new_matches.extend(combined_matches)
    
    # 4. 去重和优先级排序
    return deduplicate_and_sort(new_matches)
```

### 4.2 技能激活的"粘性"

某些技能一旦激活，应该在当前对话中保持活跃（"粘性"）：

```
用户: 帮我审查这段代码
Agent: 使用 code-reviewer → 激活（粘性开始）

用户: 第45行看起来有点问题
Agent: 仍在使用 code-reviewer（粘性保持）

用户: 好的，谢谢，这个审查结束了 → code-reviewer 解除（粘性结束）
```

粘性规则：

| 规则 | 说明 |
|------|------|
| 技能保持 | 一旦激活，后续对话默认保持激活状态 |
| 显式解除 | 用户说"结束审查"、"换一个话题"等时解除 |
| 话题转移 | 当新的用户输入匹配了完全不同的技能域时，解除旧技能 |
| 超时解除 | 连续 N 轮对话未引用该技能相关内容，自动解除 |

## 五、多技能冲突与优先级裁决

当多个技能同时被匹配时，需要裁决机制：

```
    用户: "这段代码的数据库查询有安全问题"
                    │
    同时匹配的技能：
    ├── code-reviewer      (匹配: "代码", "审查")  → 通用
    ├── database-architect (匹配: "数据库查询")     → 领域特定
    └── security-auditor   (匹配: "安全问题")       → 领域特定
```

**裁决规则**：

| 规则 | 优先级 | 说明 |
|------|--------|------|
| 用户显式指定 | 最高 | 用户说用哪个就用哪个 |
| 特有词匹配 | 高 | "慢查询"特有匹配 database-architect |
| 领域深度 | 中高 | 3 个及以上触发词匹配优于 1 个 |
| 技能 specificity | 中 | specifics 高的技能优先（"安全审计" > "代码助手"） |
| 历史偏好 | 中低 | 用户在过去相似场景中经常使用的技能 |
| 默认顺序 | 低 | 按注册表顺序 |

## 六、技能发现的工程架构

### 6.1 两阶段匹配流水线

为了平衡速度和精度，推荐采用"两阶段匹配"架构：

```
阶段一：快速预筛（关键词 + 嵌入）        阶段二：精确排序（LLM 裁决）
├─────────────── 5-50ms ───────────────┤├────────── 200-1000ms ──────────┤

用户输入 → 关键词匹配 → 嵌入语义匹配 → 候选技能池(5-10个) → LLM 排序 → 最终激活(1-3个)
              │              │                      │
          确定性匹配      语义相似度            综合考量上下文
         < 1ms          5-20ms                和历史偏好
```

**设计要点**：
- 阶段一的目标是从 100+ 个技能中快速筛选出候选集（5-10 个）
- 阶段二对候选集做精确排序（LLM 评估上下文、历史、冲突），选出最终激活的 1-3 个
- 阶段二只在候选集 > 上限时执行，如果阶段一的结果已经满足需求（如只匹配到 2 个技能），则跳过阶段二

### 6.2 可观测性

技能发现过程需要完整的日志记录：

```json
{
  "timestamp": "2026-06-01T10:30:00Z",
  "user_input": "这段代码的数据库查询很慢",
  "discovery_result": ["database-architect"],
  "phase1_candidates": [
    {"skill": "database-architect", "keyword_score": 25, "embedding_score": 0.91},
    {"skill": "code-reviewer", "keyword_score": 10, "embedding_score": 0.65},
    {"skill": "performance-analyzer", "keyword_score": 5, "embedding_score": 0.72}
  ],
  "phase2_ranking": [
    {"skill": "database-architect", "final_score": 0.92, "reason": "领域强匹配+用户历史偏好"},
    {"skill": "performance-analyzer", "final_score": 0.74, "reason": "部分匹配但非主要意图"}
  ],
  "activation_mode": "auto",
  "latency_ms": 312
}
```

### 6.3 冷启动问题

当用户首次使用 Agent（没有历史数据）时，技能发现的准确率会下降。缓解策略：

1. **默认激活少量核心技能**：如安全审计、通用代码助手
2. **主动提示**：在对话开始时提示用户可用的技能列表
3. **基于任务的渐进学习**：随着用户不断使用，逐步学习用户的技能偏好

## 关键概念速查

| 术语 | 解释 |
|------|------|
| 技能发现 | Agent 运行时确定"该激活哪些技能"的过程 |
| 关键词匹配 | 基于字符串匹配的快速发现，零延迟，但语义盲区 |
| AI 分类 | 使用嵌入模型或 LLM 进行语义匹配，精度高但成本高 |

| 建议激活 | 中等置信度匹配时询问用户是否启用 |
| 技能粘性 | 已激活的技能在当前对话中保持活跃 |
| 两阶段匹配 | 快速预筛 → 精确排序的流水线架构 |
| 嵌入分类 | 用文本嵌入模型计算语义相似度的分类方式 |
| LLM 路由 | 用 LLM 本身做技能选择的"路由器" |

### 7.2 三合一发现策略

2026年，最佳实践的技能发现策略是**三合一**：

1. **关键词匹配**：快速预筛，毫秒级响应，覆盖所有已注册的Skill
2. **AI分类**：深度语义匹配，处理同义表达和复杂意图
3. **MCP Server注册表发现**：运行时动态查询已连接的MCP Server，发现其捆绑的Skills

```python
class DiscoveryStrategy2026:
    """
    2026年三合一技能发现策略
    """

    def discover(self, user_input: str, active_mcp_servers: list) -> List[str]:
        candidates = set()

        # 1. 关键词匹配（本地）
        candidates.update(self.keyword_match(user_input))

        # 2. AI分类（本地 + 语义）
        candidates.update(self.ai_classify(user_input))

        # 3. MCP Server注册表发现（动态）
        for server in active_mcp_servers:
            server_skills = server.discover_skills(user_input)
            candidates.update(server_skills)

        return self.rank_and_filter(candidates)
```

这一策略使得技能发现的覆盖范围从"本地注册表"扩展到"整个MCP生态"，同时保持了关键词匹配的快速性和AI分类的准确性。
