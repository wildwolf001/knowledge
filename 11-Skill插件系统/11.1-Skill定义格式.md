# 11.1 Skill 定义格式

> Skill（技能）是 Agent 可加载的专业能力模块，通过标准化的 SKILL.md 文件定义。一个 Skill 包含元数据（Frontmatter）、行为描述（Body）、触发器（when_to_use）和可选配置（Config），共同构成 Agent 的最小可扩展能力单元。

---

## 一、为什么需要标准化 Skill 定义？

在 Agent 工程中，**技能（Skill）** 是指 Agent 完成特定任务的**专业知识 + 行为模式**的封装。不同于传统的 API 或插件——它们提供的是外部功能调用接口——Skill 的本质是**一种 Prompt 注入单元**：它告诉 Agent"当遇到 X 场景时，你应该知道 Y，并按 Z 的方式行事"。

在没有标准化之前，Agent 的"技能"通常是硬编码在 System Prompt 中的一段话：

```
你是一个代码审查专家。审查代码时要关注安全性、性能、可维护性...
```

这种做法的缺陷显而易见：
- **不可复用**：同样的"代码审查"知识在每个 Prompt 中重复编写
- **不可组合**：无法精确控制什么时候注入什么技能
- **不可管理**：随着技能增多，System Prompt 膨胀失控（如第 6 章所述，过长的 System Prompt 会导致注意力稀释）
- **不可发现**：Agent 无法知道自己拥有哪些技能

**SKILL.md 标准**就是为了解决这些问题而设计的——它让技能的定义、加载、触发和注入都有了统一的协议。

---

## 二、SKILL.md 文件格式标准

SKILL.md 使用 **Frontmatter + Body** 的双段结构。Frontmatter 是 YAML 格式的元数据块，Body 是 Markdown 格式的行为描述。

```
┌─────────────────────────────────────────────────┐
│  SKILL.md 结构                                   │
│                                                  │
│  ┌─ Frontmatter (YAML) ──────────────────────┐   │
│  │  ---                                       │   │
│  │  name: code-reviewer                       │   │
│  │  version: 1.2.0                            │   │
│  │  description: 专业的代码审查技能             │   │
│  │  when_to_use: [代码审查, code review, ...]  │   │
│  │  model_recommendation: claude-3.5-sonnet   │   │
│  │  ---                                       │   │
│  └────────────────────────────────────────────┘   │
│                                                  │
│  ┌─ Body (Markdown) ─────────────────────────┐   │
│  │  # Code Reviewer                          │   │
│  │                                            │   │
│  │  ## 审查维度                               │   │
│  │  1. 安全性分析...                          │   │
│  │  2. 性能评估...                            │   │
│  │  ...                                      │   │
│  └────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────┘
```

### 2.1 Frontmatter 字段详解

Frontmatter（前置元数据）是 SKILL.md 的"身份证"，使用 YAML 格式，位于文件最顶部，由 `---` 包裹。

| 字段 | 必填 | 类型 | 说明 |
|------|------|------|------|
| `name` | 是 | string | 技能名称，全局唯一标识符 |
| `version` | 是 | string | 语义化版本号，遵循 SemVer 2.0 |
| `description` | 是 | string | 一句话描述技能功能 |
| `when_to_use` | 是 | string[] | 触发关键词/短语列表 |
| `author` | 否 | string | 技能作者 |
| `model_recommendation` | 否 | string | 推荐的模型（如 claude-3.5-sonnet, gpt-4o） |
| `min_model_capability` | 否 | string[] | 最低模型能力要求 |
| `depends_on` | 否 | string[] | 依赖的其他技能 |
| `tags` | 否 | string[] | 分类标签 |
| `priority` | 否 | integer | 加载优先级（默认 0，越大越优先） |
| `injection_strategy` | 否 | string | 注入策略：`inline` / `fork` / `remote` |
| `max_tokens_reserved` | 否 | integer | 保留的最大 token 数 |
| `requires_confirmation` | 否 | boolean | 是否需要用户确认后激活 |

**关键字段详解**：

**`when_to_use`（触发器）**：这是 Skill 最核心的元数据。它是一个字符串数组，每个元素是一个触发词或短语。当用户的输入或 Agent 的当前上下文匹配这些触发词时，Skill 管理器决定是否加载此技能。

```yaml
when_to_use:
  - "代码审查"
  - "code review"
  - "pull request review"
  - "审查代码质量"
  - "代码规范检查"
```

匹配策略在 11.4 节详细讨论，这里只需知道：`when_to_use` 是技能发现的"入口索引"。

**`depends_on`（依赖声明）**：Skill 可以依赖其他 Skill。例如，"技术架构评审"技能可能依赖"安全审查"和"性能评估"两个子技能：

```yaml
depends_on:
  - security-auditor@1.x
  - performance-analyzer@>=2.0
```

依赖声明中的版本号支持 SemVer 范围（`@1.x`, `@>=2.0`, `@^1.2.3`），技能管理器在加载时会解析依赖树并自动处理。

**`injection_strategy` 与 `max_tokens_reserved`**：这两个字段控制技能注入的"成本预算"。详见 11.3 节。

### 2.2 Body 结构规范

Body 是 SKILL.md 的主体部分，使用 Markdown 格式编写。它描述的是"当这个技能被激活时，Agent 应该知道什么、怎么做"。

**推荐的 Body 结构**：

```markdown
# Code Review Expert

## Overview
本技能赋予 Agent 专业的代码审查能力，适用于 Python、TypeScript、Go 等主流语言的 Pull Request 审查场景。

## Core Principles
- 安全性优先：发现潜在的安全漏洞和攻击面
- 性能意识：识别性能瓶颈和资源泄漏
- 可维护性：评估代码的可读性、可测试性和可扩展性
- 一致性：确保代码符合项目的编码规范和最佳实践

## Review Dimensions

### 1. Security Analysis
对以下安全风险进行逐项检查：
- 注入漏洞（SQLi, XSS, Command Injection）
- 认证授权缺陷（RBAC 缺失、权限提升）
- 敏感数据泄露（硬编码密钥、日志泄漏 PII）
- 依赖漏洞（已知 CVE 的第三方库）

### 2. Performance Assessment
- 算法复杂度：是否存在 O(n^2) 以上的不必要循环
- 资源管理：连接池、文件句柄、内存泄漏
- 缓存策略：是否需要引入或优化缓存
- 并发安全：race condition、死锁、事务隔离级别

### 3. Code Quality
- 代码重复度：提取公共逻辑为函数或类
- 错误处理：是否有未捕获的异常或静默吞异常
- 测试覆盖：是否有对应的单元测试 / 集成测试
- 命名规范：变量/函数/类命名是否清晰一致

## Output Format
审查结果需按以下 JSON Schema 输出：
```json
{
  "summary": "总体评价",
  "severity": "critical" | "major" | "minor" | "info",
  "findings": [
    {
      "file": "文件路径",
      "line": 行号,
      "type": "security" | "performance" | "quality" | "style",
      "description": "问题描述",
      "suggestion": "修复建议",
      "severity": "critical" | "major" | "minor" | "info"
    }
  ]
}
```

## Interaction Guidelines
- 发现 critical 级别问题，立即通知用户并阻塞合并
- 对于 subjective 的风格问题，标注为建议而非强制
- 提供修复代码示例，而非仅指出问题
- 不确定时标注置信度
```

**Body 的撰写原则**：

1. **行为驱动**：告诉 Agent"做什么"而非"是什么"。不要写"代码审查很重要"，而要写"逐行检查以下安全风险..."
2. **结构清晰**：使用二级标题（##）划分主要章节，三级标题（###）划分子章节。Header 结构应与技能调用的思维流程一致。
3. **提供决策树**：当 Agent 面临多种选择时，给出明确的判断逻辑。
4. **指定输出格式**：Agent 对结构化输出的理解能力远强于自由格式。给出明确的 JSON Schema 或模板。
5. **包含示例**：尤其是边界情况和异常处理。
6. **避免过度约束**：不要在 Body 中加入大量无意义的规则填充 token，这会稀释核心技能的效能。

## 三、一个完整的 SKILL.md 示例

以下是一个生产级 Skill 的完整定义。该技能赋予 Agent 数据库 Schema 设计咨询能力。

```yaml
---
name: database-architect
version: 2.1.0
description: >
  数据库架构设计专家，提供 Schema 设计、索引优化、查询性能调优建议。
  支持关系型（PostgreSQL, MySQL）和 NoSQL（MongoDB, Redis）数据库。

author: ARG Knowledge Team
model_recommendation: claude-3.5-sonnet
min_model_capability:
  - tool_use
  - vision
  - 100k_context

when_to_use:
  - "数据库设计"
  - "schema设计"
  - "表结构"
  - "索引优化"
  - "慢查询"
  - "数据库选型"
  - "DDL"
  - "数据库迁移"
  - "数据建模"
  - "ER图"

depends_on:
  - sql-syntax-helper@^1.0

tags:
  - database
  - architecture
  - backend
  - data-modeling

priority: 50
injection_strategy: inline
max_tokens_reserved: 2000
requires_confirmation: false
---
```

```markdown
# Database Architect

## Overview
你是一个资深的数据库架构师。你的任务是在用户询问数据库设计问题时，提供专业、具体的架构建议。遵循以下原则和流程。

## Core Principles
1. **从需求出发**：永远先理解业务场景和数据访问模式，再设计 Schema
2. **Trade-off 思维**：没有完美的设计，只有适合的——明确指出每个选择的利弊
3. **未来导向**：考虑 6-12 个月后的数据量和查询模式变化
4. **可量化建议**：避免"建立索引"这种笼统建议，应具体到"在 orders.user_id 上建 B-tree 索引"以及"预估可减少 80% 的查询时间"

## Analysis Workflow

### Step 1: 需求澄清
在给出任何设计建议前，先确认：
- 数据规模：当前量级和预期增长速率
- 读写比例：读密集还是写密集？
- 一致性要求：强一致性还是最终一致性？
- 查询模式：主要的查询路径是什么？
- 可用性要求：RTO / RPO 是多少？

如果用户未提供以上信息，先逐一询问。

### Step 2: 数据库选型
基于 Step 1 的需求，给出数据库选型建议：

| 场景 | 推荐 | 不推荐 |
|------|------|--------|
| 强事务、复杂关联查询 | PostgreSQL | MongoDB |
| 高写入吞吐、简单查询 | Cassandra / ScyllaDB | MySQL |
| KV 缓存、会话存储 | Redis | PostgreSQL |
| 文档存储、快速迭代 | MongoDB | 传统 RDBMS |
| 时序数据（监控/指标） | TimescaleDB / InfluxDB | 通用 RDBMS |
| 全文搜索 | Elasticsearch | MySQL LIKE |

### Step 3: Schema 设计审查
逐项检查用户的表结构设计：

**规范化检查**：
- 是否存在不必要的冗余？
- 是否达到 3NF（第三范式）？如有意反范式化，理由是否充分？
- 主键选择是否合理？自增 ID vs UUID vs 业务主键的权衡

**索引策略**：
- 覆盖索引：查询需要的列是否被索引覆盖以避免回表
- 复合索引的列序：高选择性列在前，范围查询列在后
- 索引代价：写频繁的表上索引数控制在 5 个以内
- 避免冗余索引：(a, b) 和 (a) 同时存在时，(a) 是冗余的

**数据类型优化**：
- 避免使用 TEXT 存储短字符串（VARCHAR(255) 足够时）
- 避免使用 BIGINT 当 INT 足够时
- 时间字段使用 TIMESTAMP 而非字符串
- IP 地址使用 INET 类型而非 VARCHAR(15)

### Step 4: 查询 & 性能评估
- 慢查询分析：是否可以通过索引优化？
- N+1 查询检测：ORM 使用中的常见陷阱
- JOIN 深度：超过 3 表 JOIN 的表征 Schema 可能有问题
- EXPLAIN 计划解读能力

### Step 5: 迁移策略
- 大表 DDL 的在线迁移工具（gh-ost, pt-online-schema-change）
- 零停机迁移的最佳实践（蓝绿部署、双写）
- 数据一致性验证：checksum 核对

## Output Format
结论以"问题-影响-建议"格式输出：

```markdown
### [数据库选型]
- **当前**：用户计划用 MongoDB 存储订单数据
- **影响**：MongoDB 不支持跨文档事务，订单场景需要强一致性
- **建议**：改为 PostgreSQL，配合 pg_partition 做订单分表

### [索引优化]
- **当前**：`orders` 表在 `user_id` 上无索引
- **影响**：按用户查询订单需要全表扫描（预计 50 万行）
- **建议**：创建复合索引 `(user_id, created_at DESC)` 覆盖 90% 的查询
```

## Interaction Guidelines
- 当用户的设计存在安全隐患时（如明文存储密码），提升告警级别
- 对于不确定的数据库版本特性差异，标注"请参考官方文档确认"
- 如果用户的问题涉及成本优化（RDS 费用、预留实例），主动提供成本估算
```

## 四、Frontmatter 高级用法

### 4.1 条件依赖

依赖声明支持逻辑表达式，用于复杂的依赖关系：

```yaml
depends_on:
  - controller-helper  # 基础依赖
  - one-of:            # 或关系：至少满足一个
      - gcp-sdk@^2.0
      - aws-sdk@^3.0
  - not:               # 互斥关系：不能与以下技能共存
      - legacy-toolkit
```

### 4.2 环境约束

限定 Skill 的生效环境：

```yaml
environment:
  runtime: nodejs >= 18
  tools:
    - git
    - docker
  features:
    - mcp
    - filesystem-read
  forbidden:
    - network-write  # 禁止该技能发起网络写操作
```

### 4.3 多策略注入

为同一个技能定义多种注入策略（参见 11.3 节）：

```yaml
injection_strategies:
  primary: fork        # 默认使用 fork 策略
  fallback: inline     # 当 fork 不可用时回退到 inline
  max_cost_tokens: 8000
  timeout_ms: 30000
```

### 4.4 国际化和多语言

```yaml
i18n:
  default: zh-CN
  supported:
    - zh-CN
    - en-US
    - ja-JP
locales:
  zh-CN:
    description: 数据库架构设计专家
    when_to_use:
      - "数据库设计"
      - "表结构"
  en-US:
    description: Database Architecture Expert
    when_to_use:
      - "database design"
      - "table schema"
```

## 五、SKILL.md 的校验与最佳实践

### 5.1 校验规则

一个合法的 SKILL.md 必须满足：

1. **Frontmatter 完整性**：`name`, `version`, `description`, `when_to_use` 四项必填
2. **版本号合规**：遵循 SemVer 2.0（`MAJOR.MINOR.PATCH`）
3. **Body 非空**：至少包含一个二级标题
4. **名称唯一性**：在整个技能仓库中 `name` 不能重复
5. **Depends On 无循环依赖**：依赖图必须是有向无环图（DAG）

### 5.2 常见反模式

| 反模式 | 问题 | 正确做法 |
|--------|------|----------|
| when_to_use 过于宽泛 | "帮助"、"工具"——匹配几乎所有输入 | 精确描述触发场景 |
| Body 写成论文 | "数据库设计的 50 个原则..." agent 无法有效消化 | 结构化、分层、使用列表和表格 |
| 缺少输出格式 | Agent 输出难以解析的自由文本 | 给出明确的 JSON Schema 或模板 |
| 依赖循环 | A 依赖 B，B 又依赖 A | 重构为公共依赖 C |
| 版本号不变但内容修改 | 无法追踪技能演化 | 每次修改升级版本号 |

### 5.3 技能设计清单

在设计一个新的 Skill 时，逐项检查：

- [ ] when_to_use 是否覆盖了最常见的触发场景？
- [ ] Body 是否提供了明确的决策逻辑？（if-then 结构）
- [ ] 是否有输出格式规范？
- [ ] 是否需要依赖其他 Skill？（如 "deploy" 可能依赖 "docker"）
- [ ] 是否声明了推荐的模型和 token 预算？
- [ ] 是否有边界条件处理？（用户输入缺失信息时如何处理）
- [ ] 是否包含示例？（尤其是边界场景）
- [ ] 是否有安全考虑？（该技能可能被滥用于哪些恶意用途）

## 六、2026年Skills生态关键更新

### 6.1 MCP + Skills：手与脑的明确分工

2026年4月，Anthropic正式定义了MCP（Model Context Protocol）与Skills的关系：

> **MCP = "手"**：连接外部工具和数据源，提供执行能力
> **Skills = "脑"**：封装程序性知识，提供决策和行动模式

这一区分为Agent工程提供了清晰的架构指导——MCP负责"如何连接到外部世界"，Skills负责"如何在特定场景下思考和行动"。两者互补而非替代。

### 6.2 experimental-ext-skills：MCP Server直接分发Skills

2026年Anthropic推出的实验性扩展协议 `experimental-ext-skills`，允许MCP Server在提供工具和数据的同时，**直接分发捆绑的Skills**。这意味着：

- 安装一个MCP Server = 同时获得一组相关的专业Skills
- Skill的发现和安装从"用户主动搜索"变为"工具即技能"
- MCP生态与Skill生态开始深度融合

### 6.3 主流MCP Server + Skills捆绑案例

| 产品 | MCP Server能力 | 捆绑Skills |
|------|---------------|-----------|
| **Canva** | 设计资源访问、模板操作 | 设计规范审查、品牌一致性检查、自动布局建议 |
| **Notion** | 数据库查询、页面管理 | 笔记整理工作流、项目跟踪模板、知识库构建指南 |
| **Sentry** | 错误事件检索、性能数据 | 错误排查流程、性能优化建议、告警响应SOP |

这些案例表明，2026年Skills的生态已从"独立的Prompt注入单元"演变为"与工具深度绑定的专业知识包"。

*下一节：11.2 三级加载架构 —— Bundled（内置）→ User（用户）→ Project（项目），优先级与覆盖规则*
