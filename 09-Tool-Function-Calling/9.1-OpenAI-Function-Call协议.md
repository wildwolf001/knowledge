# 9.1 OpenAI Function Call 协议

> Function Calling（函数调用）是 LLM 与外部工具交互的基础协议。它通过让模型输出结构化的 JSON 来调用预定义的函数，使 Agent 能够操作外部系统、查询数据库、执行代码等。本章深入剖析 OpenAI Function Call 协议的 JSON Schema 设计规范、参数 description 对模型行为的影响，以及最佳实践。

---

## 一、Function Calling 协议概述

### 1.1 什么是 Function Calling？

Function Calling 是 OpenAI 在 2023 年 6 月引入的 API 能力，随后被 Anthropic、Google、Mistral 等厂商广泛采用，成为 LLM 工具调用的**事实标准协议**。

其核心思想是：开发者向模型注册一组"工具"（tools），每个工具通过 **JSON Schema** 描述其名称、描述和参数结构。当模型判断需要调用某个工具时，它不直接执行代码，而是输出一个结构化的 JSON 对象，包含工具名称和参数。由开发者端（Agent 框架）负责解析并执行该工具。

```
┌─────────────────┐          ┌─────────────────┐          ┌─────────────────┐
│                  │  tools   │                  │  function_call  │                  │
│   开发者         │ ──────── │     LLM          │ ────────────── │   Agent 运行时   │
│   (定义工具)     │          │   (选择工具)     │                │   (执行工具)     │
│                  │          │                  │                │                  │
│ 注册工具 Schema  │          │ 输出 JSON 格式   │                │ 解析、执行、返回  │
└─────────────────┘          └─────────────────┘                └─────────────────┘
```

### 1.2 Function Calling 与传统 Prompt 工程的区别

| 维度 | 传统 Prompt 方式 | Function Calling 方式 |
|------|-----------------|---------------------|
| **输出格式** | 自然语言，模型自行决定 | 强制结构化 JSON，Schema 约束 |
| **解析难度** | NLP 解析，容易出错 | JSON.parse，确定性解析 |
| **参数校验** | 依赖模型"自觉" | Schema 级别的强校验 |
| **重试机制** | 重新生成文本 | 结构化错误 + 参数修正 |
| **组合能力** | 难以多工具组合 | 原生支持并行工具调用 |

## 二、JSON Schema 设计规范

### 2.1 Function Call Schema 完整示例

一个标准的 Function Call Schema 遵循 JSON Schema Draft 2020-12 规范。以下是一个真实场景的完整示例——一个电商 Agent 的订单查询和发货接口：

```json
{
  "type": "function",
  "function": {
    "name": "query_order",
    "description": "根据订单ID查询订单的当前状态、物流信息和商品明细",
    "strict": true,
    "parameters": {
      "type": "object",
      "properties": {
        "order_id": {
          "type": "string",
          "description": "订单唯一标识符，格式为 ORD-YYYYMMDD-NNNNNN，例如 ORD-20250601-000123"
        },
        "include_items": {
          "type": "boolean",
          "description": "是否在返回结果中包含商品明细。默认为 false。设置为 true 时额外返回商品列表、单价和数量"
        },
        "date_range": {
          "type": "object",
          "description": "按下单时间范围筛选。如果不提供则返回订单最新状态",
          "properties": {
            "start": {
              "type": "string",
              "description": "起始日期，ISO 8601 格式，例如 2025-01-01"
            },
            "end": {
              "type": "string",
              "description": "结束日期，ISO 8601 格式，例如 2025-12-31"
            }
          },
          "additionalProperties": false
        },
        "status_filter": {
          "type": "string",
          "enum": ["pending", "processing", "shipped", "delivered", "cancelled"],
          "description": "按订单状态筛选，仅当 order_id 未提供时生效"
        }
      },
      "required": ["order_id"],
      "additionalProperties": false
    }
  }
}
```

### 2.2 Schema 核心字段详解

#### (1) `name` —— 工具名称

**命名规范**：
- 使用蛇形命名法（snake_case），如 `query_order`、`send_email`
- 长度控制在 3-64 字符
- 使用动词开头（`get_`、`create_`、`update_`、`delete_`）
- 避免使用空格、特殊字符、大写字母（部分模型对大小写敏感）

**一个有趣的发现**：工具名称对模型的选择有隐式影响。名为 `delete_all_users` 的工具，即使描述写得再"无害"，模型也会更谨慎地调用——说明名称中的语义信息会影响模型的决策。

#### (2) `description` —— 工具描述

这是**对模型行为影响最大的字段**。模型通过 description 理解"什么时候该调用这个工具"。具体设计原则见第三节。

#### (3) `strict` —— 严格模式

OpenAI 在 2024 年 11 月引入了 `strict: true` 参数。启用后，模型将严格遵循 Schema 定义的参数结构，不会输出 Schema 之外的字段。这极大地提高了工具调用的可靠性：

| 特性 | strict = false | strict = true |
|------|---------------|--------------|
| 参数类型保证 | 可能类型错误 | 强制类型匹配 |
| 额外字段 | 可能添加 Schema 外字段 | 禁止额外字段 |
| 必填字段 | 可能遗漏 | 强制填充（可能填充空值） |
| 枚举值 | 可能输出非枚举值 | 严格限制在枚举内 |

#### (4) `parameters.properties` —— 参数定义

每个参数必须明确定义 `type`。支持的类型体系：

```
JSON Schema 类型  →  Python 映射
──────────────────────────────────────
string           →  str
number           →  float
integer          →  int
boolean          →  bool
array            →  list
object           →  dict
enum (扩展)      →  Literal[...]
```

#### (5) `required` —— 必填参数

明确标注哪些参数是必需的。经验法则：**只把真正必需的参数设为 required**。如果某参数有合理的默认值，让其作为 optional 更好——这给了模型更大的灵活性。

#### (6) `additionalProperties` —— 额外属性控制

**强烈建议设置 `additionalProperties: false`**。不设置此字段时，模型可能会"创造"不存在的参数。这在 strict 模式下会自动强制。

### 2.3 嵌套对象与复杂类型

对于复杂参数，使用嵌套对象而非扁平化参数列表：

```json
{
  "name": "send_email",
  "description": "发送电子邮件",
  "strict": true,
  "parameters": {
    "type": "object",
    "properties": {
      "to": {
        "type": "array",
        "items": { "type": "string" },
        "description": "收件人邮箱列表"
      },
      "content": {
        "type": "object",
        "properties": {
          "subject": { "type": "string", "description": "邮件主题" },
          "body": { "type": "string", "description": "邮件正文，支持 Markdown 格式" },
          "attachments": {
            "type": "array",
            "items": {
              "type": "object",
              "properties": {
                "filename": { "type": "string" },
                "mime_type": { "type": "string" },
                "content_b64": { "type": "string" }
              },
              "required": ["filename", "mime_type", "content_b64"],
              "additionalProperties": false
            }
          }
        },
        "required": ["subject", "body"],
        "additionalProperties": false
      }
    },
    "required": ["to", "content"],
    "additionalProperties": false
  }
}
```

## 三、参数 description 对模型行为的影响

### 3.1 description 就是"隐式 Prompt"

Function Calling 的参数 description 实际上被拼接到发给模型的 System Prompt 中。这意味着 **description 的质量直接影响模型选择工具和填充参数的准确性**。

```python
# 内部构造（简化）
system_message = f"""
您有以下工具可用：

工具: query_order
描述: {tool_description}
参数:
  - order_id (string): {order_id_description}
  - include_items (boolean): {include_items_description}
...
"""
```

这个内部构造机制意味着：
- **description 越长，占用的上下文窗口越多**（见 9.6 节工具描述膨胀）
- **description 的措辞影响模型的行为偏好**
- **description 中的示例值提高参数填充准确率**

### 3.2 description 最佳实践

**原则一：提供具体示例值**

```python
# 差 ❌
"order_id": {
  "type": "string",
  "description": "订单ID"
}

# 好 ✅
"order_id": {
  "type": "string",
  "description": "订单唯一标识符，格式为 ORD-YYYYMMDD-NNNNNN，例如 ORD-20250601-000123"
}
```

带有格式示例的描述，模型填充正确率约提升 30-50%。

**原则二：明确什么情况下使用该参数**

```python
# 差 ❌
"status_filter": {
  "type": "string",
  "description": "订单状态筛选"
}

# 好 ✅
"status_filter": {
  "type": "string",
  "enum": ["pending", "processing", "shipped", "delivered", "cancelled"],
  "description": "按订单状态筛选。仅当 order_id 未提供时生效。如果提供了 order_id 则此参数被忽略"
}
```

**原则三：描述边界条件和副作用**

```python
# 好 ✅
"delete_order": {
  "type": "object",
  "properties": {
    "order_id": {
      "type": "string",
      "description": "要删除的订单ID。注意：此操作不可逆，删除后订单数据将永久丢失。建议在删除前先调用 query_order 确认订单信息"
    }
  }
}
```

**原则四：使用一致的措辞风格**

所有 description 保持一致的语态和风格。不要一部分用"请提供..."，另一部分用"需要输入..."。推荐的风格是**陈述句 + 被动语态**，客观中立：

```
字段说明的推荐风格：

创建工具：描述工具的用途和副作用
参数说明：描述参数的格式、约束和行为
返回值：描述返回数据的结构和可能的状态
```

### 3.3 参数 description 长度与准确率的关系

根据多项实验，参数 description 长度与模型准确率存在非线性关系：

```
准确率 (%)
 100 │                                          ●
  90 │                              ●
  80 │                   ●
  70 │        ●
  60 │  ●
  50 │
     └────────────────────────────────────────────
       0    20    40    60    80   100   120   140
                    description 字数

● 经验数据点
```

**关键发现**：
- **0-20 字**：描述过于简洁，模型对参数含义理解不足，准确率约 60%
- **20-80 字**：描述包含了足够的信息，准确率快速上升到约 85-92%
- **80-150 字**：加入示例值和边界说明，准确率可达到 95%+
- **150+ 字**：过度描述开始引入噪声，准确率出现下降趋势（约 1-3%）

**建议**：每个参数 description 控制在 **30-100 字**之间，包含：字段含义 + 格式说明 + 一个示例值。

## 四、Multi-Tool Calling（并行工具调用）

### 4.1 并行调用的 Schema 设计

OpenAI 支持在一次响应中调用多个工具。这对 Schema 设计提出了新要求——**工具之间不要产生隐式的执行顺序依赖**：

```json
// 模型可以一次输出多个 function_call
{
  "choices": [{
    "message": {
      "content": null,
      "tool_calls": [
        {
          "id": "call_1",
          "type": "function",
          "function": {
            "name": "get_weather",
            "arguments": "{\"city\": \"北京\"}"
          }
        },
        {
          "id": "call_2",
          "type": "function",
          "function": {
            "name": "get_weather",
            "arguments": "{\"city\": \"上海\"}"
          }
        }
      ]
    }
  }]
}
```

**Schema 设计对并行调用的影响**：

1. **独立的工具比组合工具更利于并行**：将 `get_weather`（查天气）和 `get_traffic`（查路况）分开定义，模型可以并行调用。如果合为一个 `get_weather_and_traffic`，则只能串行。
2. **避免全局状态依赖**：如果一个工具的输出会影响另一个工具的参数，要明确在 description 中说明调用顺序。

### 4.2 强制调用特定工具

```python
response = client.chat.completions.create(
    model="gpt-4o",
    messages=[...],
    tools=tools,
    tool_choice={"type": "function", "function": {"name": "query_order"}}
    # tool_choice="auto"       # 让模型决定（默认）
    # tool_choice="required"   # 强制必须调一个工具
    # tool_choice="none"       # 禁止调用工具
)
```

## 五、不同厂商的 Function Calling 协议对比

| 特性 | OpenAI | Anthropic (Claude) | Google (Gemini) |
|------|--------|-------------------|-----------------|
| **API 参数名** | `tools` | `tools` | `tools` |
| **Schema 格式** | JSON Schema Draft 2020-12 | JSON Schema (子集) | JSON Schema (子集) |
| **并行调用** | 原生支持 | 原生支持 | 不支持 |
| **strict 模式** | 支持 (2024.11+) | 不支持 | 不支持 |
| **Tool Choice** | `auto/required/none/function:{name}` | `auto/any/tool:{name}` | `auto/none/function:{name}` |
| **流式 tool_calls** | delta 模式 | 完整 JSON 逐块 | 完整 JSON |
| **多模态工具** | code_interpreter, file_search 内置 | 无内置工具 | Google Search 内置 |

## 六、最佳实践清单

### 6.1 Schema 设计清单

```
□ 所有工具使用 snake_case 命名
□ 每个参数都有清晰、具体的 description
□ required 字段只包含真正必需的参数
□ 所有对象都设置 additionalProperties: false
□ 枚举值使用 enum 而非 description 描述
□ 启用 strict: true（支持时）
□ 参数 description 包含格式示例
□ 避免过长的 description（每个参数 30-100 字）
□ 工具描述中说明可能调用的其他工具关系
□ 副作用（删除、修改）在 description 中显式标注
```

### 6.2 常见的 Schema 设计错误

| 错误 | 后果 | 修复 |
|------|------|------|
| 缺少 `additionalProperties: false` | 模型可能创造不存在参数 | 显式设置 |
| 过度嵌套对象 | 模型填充深层字段困难 | 保持嵌套 ≤ 3 层 |
| 参数含义不明确 | 模型跳过此工具或填错值 | 加示例值 |
| 遗漏必填参数 | 执行时报错 | 加 exhaustive 测试 |
| enum 值与实际 API 不匹配 | 枚举转换错误 | 保持同步 |
| 使用 `anyOf`/`oneOf` | 部分模型不支持 | 改用独立工具 |

### 6.3 Function Call 协议与 MCP 的关系

MCP（Model Context Protocol，详见第 10 章）是 Anthropic 提出的标准化工具协议，而 Function Calling 是 OpenAI 的 API 级协议。两者关系如下：

```
MCP Server (标准化工具)
     │
     ▼ MCP 协议 (统一接口描述)
     │
┌────────────────────────────────────┐
│         MCP Client → Function Call 转换层      │
│  MCP 工具描述 → JSON Schema                │
│  执行请求 → Function Call 响应            │
└────────────────────────────────────┘
     │
     ▼ OpenAI / Claude / Gemini API
```

在 Agent 框架中，通常通过一个适配层（Adapter）将 MCP 的工具描述转换为不同厂商的 Function Call 格式。

## 关键概念速查表

| 概念 | 定义 | 重要性 |
|------|------|--------|
| **Function Calling** | LLM 输出结构化 JSON 调用预定义函数的协议 | 工具交互的基础 |
| **JSON Schema** | 描述函数参数结构的标准格式 | 决定工具调用的准确性 |
| **strict 模式** | 强制模型严格遵循 Schema 定义的模式 | 高 |
| **tool_choice** | 控制模型是否/如何选择调用工具的机制 | 高 |
| **Multi-Tool Calling** | 单次响应中调用多个工具的并行能力 | 中 |
| **description 注入** | 参数描述被拼接进模型 Prompt 的机制 | 影响准确率的关键 |
| **additionalProperties** | 控制是否允许额外字段的 Schema 属性 | 防止模型创造参数 |
