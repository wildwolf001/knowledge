# 9.4 流式工具执行 vs 批量执行

> 当 Agent 一次需要调用多个工具时，有两种执行策略：**流式执行**（Streaming Execution）——一边接收模型的工具调用序列，一边立即执行已就绪的工具；**批量执行**（Batch Execution）——等模型输出全部工具调用后再统一执行。两种策略在延迟、顺序保证和用户体验上有本质差异。

---

## 一、问题的起源

### 1.1 模型输出工具调用的时间线

在 Multi-Tool Calling 场景中，模型并不是瞬间输出所有工具调用的。尤其是复杂场景下，模型可能需要数百毫秒甚至数秒才能完成全部工具调用的推理和生成。

```
时间线（逐 token 输出）:

t=0ms    模型开始输出
t=50ms   输出：{"tool_calls": [{"id": "call_1", "name": "get_weather", ...
t=150ms  输出：{"id": "call_2", "name": "get_stock", ...
t=300ms  输出：{"id": "call_3", "name": "send_email", ...
t=400ms  模型输出完成
```

**批量执行**会等到 t=400ms 才开始执行任何工具。而**流式执行**可以在 t=50ms 时就开始执行 `get_weather`，在 t=150ms 开始执行 `get_stock`，实现工具执行和模型推理的"流水线并行"。

---

## 二、流式执行（Streaming Execution）

### 2.1 流式执行的工作原理

流式执行的核心思想是：**只要一个工具调用的信息已经完整，就立即开始执行，不必等待其他工具**。

```
流式执行的时间线:

模型推理                       工具执行
┌──────────────┐             ┌──────────────┐
│ 输出 call_1  │ ──→ 检测完成 ──→ 执行 get_weather  │  ← t=50ms 启动
│  (get_weather)│             │              │
├──────────────┤             ├──────────────┤
│ 输出 call_2  │ ──→ 检测完成 ──→ 执行 get_stock    │  ← t=150ms 启动
│  (get_stock) │             │              │
├──────────────┤             ├──────────────┤
│ 输出 call_3  │             │              │
│  (send_email)│             │  ← 需等待模型输出完成 │
└──────────────┘             └──────────────┘

时间节约：400ms 的模型输出时间与工具执行时间重叠
```

### 2.2 流式执行的关键问题

**问题一：如何判断一个工具调用已经完整？**

在流式模式下，模型的输出是以 **delta**（增量）形式逐块到达的。OpenAI 的流式 API 中，工具调用以 `tool_calls` delta 形式返回：

```python
# 流式响应中的工具调用 delta
# Chunk 1:
{
    "choices": [{
        "delta": {
            "tool_calls": [{
                "index": 0,
                "id": "call_1",
                "type": "function",
                "function": {
                    "name": "get_weather",
                    "arguments": ""
                }
            }]
        }
    }]
}

# Chunk 2:
{
    "choices": [{
        "delta": {
            "tool_calls": [{
                "index": 0,
                "function": {
                    "arguments": "{\"city\":"
                }
            }]
        }
    }]
}

# Chunk 3:
{
    "choices": [{
        "delta": {
            "tool_calls": [{
                "index": 0,
                "function": {
                    "arguments": " \"北京\"}"
                }
            }]
        }
    }]
}
```

关键判断点：当一个 tool_call 的 index 第一次出现时伴随着 `id` 字段，说明这是一个新的工具调用的开始。当检测到 `id` 和 `name` 都非空时，可以确认工具名称。

但参数（arguments）是逐步到达的，需要累积到完整的 JSON 才能执行。**不等参数接收完就无法执行**——这限制了流式执行的提前量。

**问题二：不完整的参数怎么办？**

流式执行面临的核心矛盾：模型可能需要多步才能完成参数的输出，而参数从输出的第一块开始就是 JSON 片段，只有拼接完整的 JSON 后才能解析执行。

### 2.3 流式执行的实现

```python
import json
import asyncio
from typing import AsyncGenerator, Optional


class StreamingToolCallAccumulator:
    """
    流式工具调用累加器。
    将流式 delta 片段累加成完整的工具调用，并在完成后立即派发执行。
    """

    def __init__(self, executor):
        self._executor = executor
        # key: tool_call index, value: 累积的片段
        self._accumulators: dict[int, dict] = {}
        self._pending_executions: list[asyncio.Task] = []

    async def process_chunk(self, chunk: dict) -> Optional[dict]:
        """
        处理一个流式 chunk。
        如果该 chunk 使得某个工具调用完整，返回该工具调用。
        否则返回 None。
        """
        choices = chunk.get("choices", [])
        if not choices:
            return None

        delta = choices[0].get("delta", {})
        tool_calls = delta.get("tool_calls", [])

        completed_tool = None

        for tc_delta in tool_calls:
            index = tc_delta.get("index")

            # 初始化累加器
            if index not in self._accumulators:
                self._accumulators[index] = {
                    "id": None,
                    "name": None,
                    "arguments": ""
                }

            acc = self._accumulators[index]

            # 累积 id
            if "id" in tc_delta and tc_delta["id"]:
                acc["id"] = tc_delta["id"]

            # 累积 name
            function = tc_delta.get("function", {})
            if "name" in function and function["name"]:
                acc["name"] = function["name"]

            # 累积 arguments
            if "arguments" in function:
                acc["arguments"] += function["arguments"]

            # 检查是否已经完整（通过尝试解析 JSON 参数）
            if self._is_complete(acc):
                completed_tool = {
                    "id": acc["id"],
                    "name": acc["name"],
                    "arguments": json.loads(acc["arguments"])
                }
                # 从累加器中移除已完成的工具
                del self._accumulators[index]

        return completed_tool

    def _is_complete(self, acc: dict) -> bool:
        """判断一个工具调用是否已经完整"""
        if not acc["id"] or not acc["name"] or not acc["arguments"]:
            return False
        # 尝试解析 JSON——解析成功说明参数完整
        try:
            json.loads(acc["arguments"])
            return True
        except json.JSONDecodeError:
            return False

    def get_remaining(self) -> list[dict]:
        """获取所有剩余未完成的工具调用（用于超时处理）"""
        return list(self._accumulators.values())


class StreamingExecutor:
    """流式执行器"""

    def __init__(self, tool_registry):
        self._registry = tool_registry

    async def execute_streaming(
        self, llm_stream: AsyncGenerator[dict, None]
    ):
        """
        流式执行入口：
        一边接收 LLM 的流式输出，一边执行已完成的工具调用。
        """
        accumulator = StreamingToolCallAccumulator(self)
        all_results = []

        async for chunk in llm_stream:
            completed = await accumulator.process_chunk(chunk)
            if completed:
                # 立即执行——不等待后续工具
                result = await self._execute_tool(completed)
                all_results.append({
                    "tool_call_id": completed["id"],
                    "tool_name": completed["name"],
                    "result": result,
                    "execution_mode": "streaming"
                })

        # 处理所有剩余的工具调用
        remaining = accumulator.get_remaining()
        for acc in remaining:
            try:
                tool_call = {
                    "id": acc["id"],
                    "name": acc["name"],
                    "arguments": json.loads(acc["arguments"])
                }
                result = await self._execute_tool(tool_call)
                all_results.append({
                    "tool_call_id": tool_call["id"],
                    "tool_name": tool_call["name"],
                    "result": result,
                    "execution_mode": "streaming"
                })
            except json.JSONDecodeError:
                # 参数无法解析——标记失败
                all_results.append({
                    "tool_call_id": acc.get("id", "unknown"),
                    "tool_name": acc.get("name", "unknown"),
                    "error": "参数不完整",
                    "execution_mode": "streaming"
                })

        return all_results

    async def _execute_tool(self, tool_call: dict):
        """执行单个工具"""
        tool_meta = self._registry.get(tool_call["name"])
        if not tool_meta:
            raise ValueError(f"未知工具: {tool_call['name']}")

        # 实际执行逻辑
        ...
```

### 2.4 流式执行的发送进度消息

流式执行的一个重要优势是可以在工具执行期间向用户发送**进度消息**（Progress Message），提升用户体验：

```python
async def execute_with_progress(
    self, llm_stream, websocket
):
    """流式执行并发送进度消息"""
    accumulator = StreamingToolCallAccumulator(self)
    step_count = 0

    async for chunk in llm_stream:
        completed = await accumulator.process_chunk(chunk)

        if completed:
            step_count += 1
            # 发送进度消息
            await websocket.send(json.dumps({
                "type": "tool_execution_start",
                "step": step_count,
                "tool_name": completed["name"],
                "status": "running"
            }))

            result = await self._execute_tool(completed)

            await websocket.send(json.dumps({
                "type": "tool_execution_complete",
                "step": step_count,
                "tool_name": completed["name"],
                "status": "completed",
                "summary": _generate_summary(result)
            }))

    # 全部完成
    await websocket.send(json.dumps({
        "type": "all_tools_completed",
        "total_steps": step_count
    }))
```

## 三、批量执行（Batch Execution）

### 3.1 批量执行的工作原理

批量执行是最简单、最可靠的执行方式。它等待模型输出**全部**工具调用后，再统一执行。

```
批量执行的时间线:

模型推理
┌─────────────────────────────────────────────┐
│ 输出 call_1 │ 输出 call_2 │ 输出 call_3     │
│ (50ms)      │ (150ms)     │ (400ms)          │
└─────────────────────────────────────────────┘
                                              等待 400ms
                                              ▼
工具执行
┌─────────────────────────────────────────────┐
│ 执行 call_1 → 执行 call_2 → 执行 call_3     │
│ (开始于 t=400ms)                              │
└─────────────────────────────────────────────┘

总延迟 = 模型输出时间 (400ms) + 工具执行时间
```

### 3.2 批量执行的实现

```python
class BatchExecutor:
    """批量执行器"""

    def __init__(self, tool_registry):
        self._registry = tool_registry

    async def execute_batch(
        self, final_tool_calls: list[dict]
    ) -> list[dict]:
        """
        批量执行所有工具调用。
        先等待所有工具调用收集完毕，再统一执行。
        """
        results = []

        for tool_call in final_tool_calls:
            result = await self._execute_tool(tool_call)
            results.append({
                "tool_call_id": tool_call["id"],
                "tool_name": tool_call["name"],
                "result": result,
                "execution_mode": "batch"
            })

        return results

    async def execute_batch_parallel(
        self, final_tool_calls: list[dict]
    ) -> list[dict]:
        """
        批量并行执行（结合 9.3 节的读写分离策略）。
        """
        read_tools = []
        write_tools = []

        for call in final_tool_calls:
            meta = self._registry.get(call["name"])
            if meta and meta.concurrency_safe:
                read_tools.append(call)
            else:
                write_tools.append(call)

        results = []

        # 读工具并行
        if read_tools:
            read_results = await asyncio.gather(
                *[self._execute_tool(t) for t in read_tools],
                return_exceptions=True
            )
            for tool, result in zip(read_tools, read_results):
                results.append({
                    "tool_call_id": tool["id"],
                    "tool_name": tool["name"],
                    "result": result,
                    "execution_mode": "batch_parallel"
                })

        # 写工具串行
        for tool in write_tools:
            result = await self._execute_tool(tool)
            results.append({
                "tool_call_id": tool["id"],
                "tool_name": tool["name"],
                "result": result,
                "execution_mode": "batch_serial"
            })

        return results
```

## 四、流式执行 vs 批量执行的对比

### 4.1 全面对比表

| 维度 | 流式执行 | 批量执行 |
|------|---------|---------|
| **延迟** | 更低（执行与推理重叠） | 更高（等待全部输出后再执行） |
| **实现复杂度** | 高（需要累加器、状态管理） | 低（简单的收集-执行模式） |
| **顺序保证** | 弱（工具可能按完成顺序而非模型输出顺序完成） | 强（严格按模型输出顺序） |
| **错误处理** | 复杂（部分工具提前成功，部分失败） | 简单（统一处理） |
| **依赖管理** | 困难（DAG 依赖只能识别已完成的工具） | 容易（完整 DAG 可见） |
| **进度可见性** | 好（可以发送进度消息） | 差（用户需等待全部完成） |
| **资源利用** | 高（CPU/IO 时间重叠） | 低（串行等待） |
| **适用场景** | 用户等待实时交互的场景 | 后台批量处理、依赖复杂的场景 |
| **Token 开销** | 无额外开销 | 无额外开销 |

### 4.2 延迟对比分析

```
延迟差异可视化：

批量执行:
模型输出 ████████████████████ 工具执行 ████████
          ← 400ms →            ← 300ms →
总延迟: 700ms

流式执行:
模型输出 ████████████████████
工具执行         ████░░░░████████
                 重叠时间 ← 200ms →
总延迟: 500ms

节约: 200ms (约 28.6%)
```

**节约的延迟取决于**：
1. **模型输出时间**：输出越长，流式优势越大
2. **工具执行时间**：如果工具执行时间远大于模型输出时间，流式优势明显
3. **工具数量**：工具越多，流式可能提前启动的机会越多

### 4.3 场景决策矩阵

| 场景 | 推荐模式 | 原因 |
|------|---------|------|
| 实时对话 Agent | 流式执行 | 用户等待响应，延迟敏感 |
| 后台数据处理 | 批量执行 | 依赖关系复杂，需要完整性保证 |
| 工具间有 DAG 依赖 | 批量执行 + DAG 分析 | 需要完整的依赖图才能优化 |
| 只读工具集（无依赖） | 流式执行 + 并行执行 | 最大化吞吐量 |
| 混合读写工具集 | 流式执行 + 写工具序列化 | 兼顾延迟和安全 |
| 工具数量 > 10 个 | 批量执行（先分析再执行） | 流式累加器管理复杂 |

## 五、混合执行策略

### 5.1 流式+批量的混合模式

实际生产系统中，通常采用混合策略——既不是纯粹的流式，也不是纯粹的批量。

```python
class HybridExecutor:
    """
    混合执行器：
    - 流式识别可提前执行的独立工具
    - 批量执行有依赖关系的工具
    - 写工具始终串行化
    """

    def __init__(self, registry):
        self._registry = registry
        self._accumulator = StreamingToolCallAccumulator(self)
        self._early_tools = []   # 可提前执行的工具
        self._dependent_tools = []  # 需要等待全部依赖的工具
        self._batch_executor = BatchExecutor(registry)

    async def execute_hybrid(self, llm_stream):
        """混合执行"""
        # 第一阶段：流式接收，识别可提前执行的工具
        async for chunk in llm_stream:
            completed = await self._accumulator.process_chunk(chunk)
            if completed:
                meta = self._registry.get(completed["name"])
                if meta and meta.concurrency_safe and not self._has_pending_deps():
                    # 无依赖的只读工具——提前执行
                    asyncio.create_task(
                        self._execute_early(completed)
                    )
                    self._early_tools.append(completed)
                else:
                    # 有依赖或写工具——加入等待队列
                    self._dependent_tools.append(completed)

        # 第二阶段：执行等待队列中的工具（含 DAG 分析）
        if self._dependent_tools:
            dag = build_runtime_dag(self._dependent_tools)
            plan = dag.get_execution_plan()
            for level in plan.levels:
                # 执行该层级的所有工具
                ...

    def _has_pending_deps(self):
        """检查是否有尚未接收的依赖工具"""
        return False  # 简化实现

    async def _execute_early(self, tool_call):
        """提前执行工具"""
        result = await self._batch_executor._execute_tool(tool_call)
        # 缓存结果供后续工具使用
        self._result_cache[tool_call["id"]] = result
```

### 5.2 顺序保证策略

关于顺序保证，一个实用的权衡方案是：

```python
class OrderedStreamingExecutor:
    """带顺序保证的流式执行器"""

    def __init__(self, registry):
        self._registry = registry
        self._pending_results = {}  # 已完成但未到输出顺序的结果

    async def execute_ordered(self, tool_calls_stream, output_queue):
        """
        流式执行但严格保证输出顺序。

        策略：
        - 工具按流式顺序执行（不等全部收集）
        - 但结果按原始顺序排列输出
        - 如果 call_2 先于 call_1 完成，缓存 call_2 的结果
        - 等到 call_1 的结果也到了，按顺序输出
        """
        expected_order = []  # 原始顺序
        next_to_output = 0  # 下一个应该输出的位置

        async for completed_tool in self._accumulate(tool_calls_stream):
            position = len(expected_order)
            expected_order.append(completed_tool["id"])

            # 异步执行
            task = asyncio.create_task(
                self._execute_tool(completed_tool)
            )
            self._running_tasks[completed_tool["id"]] = {
                "task": task,
                "position": position
            }

        # 等待并按要求顺序输出
        while next_to_output < len(expected_order):
            expected_id = expected_order[next_to_output]

            if expected_id in self._pending_results:
                # 结果已缓存——输出
                result = self._pending_results.pop(expected_id)
                await output_queue.put(result)
                next_to_output += 1
            else:
                # 等待指定任务完成
                task_info = self._running_tasks.get(expected_id)
                if task_info:
                    result = await task_info["task"]
                    self._pending_results[expected_id] = result
```

## 关键概念速查表

| 概念 | 定义 | 重要性 |
|------|------|--------|
| **流式执行** | 一边接收模型输出一边执行已就绪的工具 | P0（延迟优化） |
| **批量执行** | 等待全部工具调用输出后再统一执行 | P0（可靠性） |
| **Delta 累加器** | 将流式增量片段累积为完整工具调用的组件 | P1（流式核心） |
| **进度消息** | 工具执行期间向用户发送的状态更新 | P1（用户体验） |
| **混合执行** | 同时使用流式和批量策略的执行模式 | P1（最佳实践） |
| **顺序保证** | 确保工具结果按模型输出顺序返回的机制 | P1 |
| **延迟重叠** | 模型输出时间与工具执行时间的重叠效应 | P2（性能分析） |
