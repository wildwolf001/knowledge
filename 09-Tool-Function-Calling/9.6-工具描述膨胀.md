# 9.6 工具描述膨胀

> "114 个工具说 hello 耗 46,000 token"——这不是一个夸张的比喻，而是一个真实发生的生产事故。当工具数量增长时，工具描述（Tool Descriptions）在上下文窗口中占用的 Token 数量呈线性增长，但工具的实际利用率却并不随之增长。这就是**工具描述膨胀**（Tool Description Bloat）问题。

---

## 一、问题的发现

### 1.1 真实案例分析：114 工具 46K Token

某 SaaS 公司的 Agent 系统集成了 114 个工具，覆盖 CRM、ERP、邮件、项目管理、数据分析等多个领域。在生产环境中，团队发现每次 LLM 调用的 Token 消耗异常高：

```
实际 Token 消耗分析（单次调用）：

┌────────────────────────────────────────────┐
│  System Prompt (固定部分)    2,300 tokens    │
│                                              │
│  工具定义 (114 个工具)      45,600 tokens    │  ← 问题在这里！
│    ├─ get_user              380 tokens       │
│    ├─ create_lead           520 tokens       │
│    ├─ update_contact        410 tokens       │
│    ├─ send_email            350 tokens       │
│    ├─ ... (110 个其他工具)   43,940 tokens   │
│                                              │
│  对话历史                    3,200 tokens    │
│  ────────────────────────────────────        │
│  总计                       51,100 tokens   │
│                                              │
│  其中工具定义占比            89.3%           │
└────────────────────────────────────────────┘
```

**这意味着每次用户说"hello"，系统就要消耗约 46,000 token 来传输工具定义**——而实际上这些工具可能只有 2-3 个与"hello"相关。

### 1.2 膨胀的代价

工具描述膨胀带来的代价是多维度的：

| 代价维度 | 具体影响 | 量化估算 |
|---------|---------|---------|
| **Token 成本** | 每次调用支付不必要的 Token 费用 | 46,000 token × 请求次数 × 价格 |
| **延迟增加** | 大输入量的预处理和注意力计算 | TTFT 增加约 200-500ms |
| **注意力稀释** | 大量不相关工具干扰模型注意力 | 选型准确率下降约 15-25% |
| **上下文窗口压力** | 工具定义挤占了对话和指令的空间 | 有效上下文减少 50-80% |
| **缓存效率下降** | 每个对话的上下文都不同，难以复用 KV Cache | 缓存命中率下降 |

**成本量化示例**（以 GPT-4o 为例）：

```
单次调用额外 Token: 45,600 (工具定义)
单次调用额外成本: 45,600 × $2.50/1M = $0.114
日均请求: 100,000
日均额外成本: $0.114 × 100,000 = $11,400
月均额外成本: $11,400 × 30 = $342,000
年化额外成本: $342,000 × 12 = $4,104,000

→ 这还只是直接 Token 成本，不包括延迟增加导致的用户体验损失
```

## 二、膨胀的根因分析

### 2.1 工具定义的 Token 构成

一个典型工具的 Token 消耗分布在以下字段：

```json
{
  "type": "function",                          // 2 tokens
  "function": {                                 // 1 token
    "name": "get_user_info",                    // 3 tokens
    "description": "根据用户 ID 查询用户的完 整个人信息",  // 10 tokens
    "strict": true,                              // 2 tokens
    "parameters": {                              // 2 tokens
      "type": "object",                          // 2 tokens
      "properties": {                            // 2 tokens
        "user_id": {                             // 2 tokens
          "type": "string",                      // 3 tokens
          "description": "用户唯一标识，UUID 格式，例如 a1b2c3d4-e5f6-7890-abcd-ef1234567890"  // 18 tokens
        },
        "include_details": {                     // 3 tokens
          "type": "boolean",                     // 3 tokens
          "description": "是否返回详细信息，包括地址、电话、历史订单等。开启后响应时间会增加 200ms",  // 20 tokens
          "default": false                       // 3 tokens
        }
      },
      "required": ["user_id"],                   // 5 tokens
      "additionalProperties": false              // 3 tokens
    }
  }
}
```

一个工具约 **80-100 tokens**。但仅凭这个数据，还不至于 114 个工具就用掉 46K token。**问题在于描述字段的膨胀**。

### 2.2 膨胀的具体模式

分析真实案例，发现描述信息中存在四种典型的膨胀模式：

**模式一：过度描述参数含义**

```python
# 过度描述 ❌
"user_id": {
  "type": "string",
  "description": "用户的唯一标识符（User Identifier），这是一个用于唯一确定某个用户在系统中的身份的 ID 字符串，通常由系统自动生成，格式为 UUID v4，例如 a1b2c3d4-e5f6-7890-abcd-ef1234567890。在调用此接口时，用户 ID 是必填参数，如果不提供将无法查询到用户信息"
}
# → 约 45 tokens（其中大量冗余信息）

# 精简描述 ✅
"user_id": {
  "type": "string",
  "description": "用户 UUID，例如 a1b2c3d4-e5f6-7890-abcd-ef1234567890"
}
# → 约 10 tokens（减少了 78%）
```

**模式二：在 description 中重复工具名称**

```python
# 重复 ❌
"description": "获取用户信息的工具，通过此工具可以获取用户的详细信息，包括用户的基本信息、联系方式等。注意：此工具用于获取用户信息，不用于修改用户信息"

# 精简 ✅
"description": "查询用户基本信息（姓名、邮箱、电话）。只读，不修改数据"
```

**模式三：过度使用枚举值描述**

```python
# 膨胀 ❌
"status": {
  "type": "string",
  "enum": ["active", "inactive", "pending", "suspended", "deleted"],
  "description": "用户账号的当前状态。active 表示账号正常使用；inactive 表示账号未激活或已禁用；pending 表示等待审核；suspended 表示临时冻结；deleted 表示已删除。注意：deleted 状态的用户无法恢复"
}
# → 约 25 tokens（枚举描述冗余）

# 精简 ✅
"status": {
  "type": "string",
  "enum": ["active", "inactive", "pending", "suspended", "deleted"],
  "description": "账号状态：active=正常, inactive=未激活, pending=审核中, suspended=冻结, deleted=已删除"
}
# → 约 15 tokens
```

**模式四：描述中包含实现细节**

```python
# 包含实现细节 ❌
"description": "查询用户信息。该接口通过调用内部微服务 user-service 的 /api/v2/users/{id} 端点，经过 API Gateway 认证后，从 PostgreSQL 数据库的 users 表中读取数据，并缓存到 Redis 中 5 分钟"

# 精简 ✅
"description": "查询用户基本信息。缓存 5 分钟"
```

### 2.3 膨胀的累积效应

单个工具的膨胀看似微小，但累加起来造成巨大的浪费：

```
每个工具平均节约: 200 → 60 tokens = 140 tokens
114 个工具: 140 × 114 = 15,960 tokens/次
日均 100K 请求: 15,960 × 100,000 = 1.6B tokens/天
月均节约: 1.6B × $2.50/1M × 30 = $120,000/月
```

## 三、工具描述优化的方法论

### 3.1 描述效率的度量：Token 密度

定义 **Token 密度**（Token Density）指标来衡量工具描述的信息效率：

```
Token 密度 = 有用信息量 / Token 消耗

其中"有用信息量"通过模型对工具理解的准确率来间接度量。

一个高质量的工具描述应该满足:
- Token 密度高（信息紧凑）
- 语义清晰（模型一次理解）
- 无冗余（没有重复信息）
```

### 3.2 具体的优化规则

**规则一：移除语义冗余**

```python
# 优化前: 37 tokens
"description": "这是一个用于发送电子邮件的工具函数，它可以帮助用户发送各种类型的电子邮件，包括文本邮件和 HTML 邮件"

# 优化后: 12 tokens
"description": "发送文本或 HTML 格式的电子邮件"
# 节约: 68%
```

**规则二：使用标准化的描述模板**

```python
DESCRIPTION_TEMPLATES = {
    "query": "查询{entity}的{fields}。只读操作",
    "create": "创建新的{entity}记录。需要{fields}参数",
    "update": "更新{entity}的{fields}。只修改提供的字段",
    "delete": "删除{entity}。不可逆操作",
    "list": "列出符合条件的{entity}列表，支持{filter_criteria}"
}

# 使用模板:
# "查询用户的基本信息（姓名、邮箱、角色）。只读操作"
# 而不是:
# "这个工具可以用来查看用户的信息，比如用户名、邮箱地址和用户角色"
```

**规则三：参数 description 统一格式化**

```python
# 格式: [含义]。[格式/示例]。[边界条件，可选]
"description": "用户 UUID。格式: a1b2c3d4-...。必须提供"
"description": "页面大小。1-100，默认 20"
"description": "排序方向。可选: asc, desc"
```

**规则四：按使用频率动态调整描述长度**

```python
class AdaptiveDescriptionManager:
    """根据工具使用频率动态调整描述长度"""

    def __init__(self):
        self._call_count: dict[str, int] = {}
        self._full_descriptions: dict[str, str] = {}
        self._short_descriptions: dict[str, str] = {}

    def record_call(self, tool_name: str):
        """记录工具被调用"""
        self._call_count[tool_name] = self._call_count.get(tool_name, 0) + 1

    def get_adaptive_description(
        self, tool_name: str,
        min_calls_for_short: int = 100
    ) -> str:
        """
        高频工具 → 短描述（模型已熟悉）
        低频工具 → 全描述（模型需要更多上下文）
        """
        calls = self._call_count.get(tool_name, 0)

        if calls > min_calls_for_short:
            return self._short_descriptions.get(
                tool_name,
                self._full_descriptions.get(tool_name, "")
            )
        return self._full_descriptions.get(tool_name, "")
```

### 3.3 优化的实际效果

在一家 Saas 公司实施了上述优化后，效果显著：

```
优化前:
  工具平均描述长度: 约 400 tokens

优化后:
```

## 四、Token 压缩与复用

### 4.1 系统级 Token 压缩方案

除了优化描述文本本身，还可以从系统层面减少 Token 消耗：

**方案一：工具定义预缓存（Prefix Caching）**

许多 LLM API 提供商（如 OpenAI、Anthropic）支持提示词缓存（Prompt Caching）。如果系统提示（包含工具定义）在多轮对话中保持不变，可以只传输一次并缓存：

```python
# OpenAI: 系统消息被自动缓存（2024+）
# Anthropic Claude: 显式缓存标记
response = client.messages.create(
    model="claude-3-5-sonnet-20241022",
    system=[
        {
            "type": "text",
            "text": tools_definition,  # 被自动缓存
            "cache_control": {"type": "ephemeral"}
        }
    ],
    messages=[user_message]
)
```

**缓存效果**：
- 首次请求：完整 Token 费用
- 后续请求（缓存命中）：只需支付约 10% 的缓存读取费用
- 如果工具定义不变，每次对话只有第一条消息会消耗工具定义的 Token

**方案二：工具描述的压缩传输**

```python
def compress_tool_descriptions(tools: list[dict]) -> list[dict]:
    """
    压缩工具描述：
    1. 移除可选参数的默认值描述（模型已知默认行为）
    2. 简化枚举值的 description（枚举值本身已说明含义）
    3. 移除 superfluous 字段（"type": "function" 等冗余）
    """
    compressed = []
    for tool in tools:
        func = tool.get("function", tool)
        params = func.get("parameters", {})

        for prop_name, prop_def in params.get("properties", {}).items():
            # 枚举值：不再重复描述每个值的含义
            if "enum" in prop_def and "description" in prop_def:
                prop_def["description"] = _simplify_enum_desc(
                    prop_def["description"],
                    prop_def["enum"]
                )

            # 布尔参数：精简描述
            if prop_def.get("type") == "boolean":
                prop_def["description"] = _simplify_bool_desc(
                    prop_def.get("description", "")
                )

        compressed.append(tool)

    return compressed
```

### 4.2 工具描述的分层投递

不同的 Agent 阶段只需要看到相关工具（详见 9.5 节），这本身就是对抗工具描述膨胀的最有效手段：

```
无分层（全部投递）:
  System: 114 个工具定义 → 45,600 tokens
  → 浪费

有分层（按需展开）:
  Round 1: 5 个分类导航工具 → ~400 tokens
  Round 2: 1 个分类展开，15 个子工具 → ~2,000 tokens
  Round 3: 1 个子工具选中执行 → ~200 tokens
  
  总计: ~2,600 tokens（减少了 94%）
```

### 4.3 描述自动压缩工具

可以开发一个自动化工具来分析并压缩工具描述：

```python
import tiktoken  # OpenAI 的 token 计数器


class DescriptionCompressor:
    """工具描述自动压缩器"""

    def __init__(self):
        self._tokenizer = tiktoken.get_encoding("cl100k_base")

    def analyze(self, tools: list[dict]) -> dict:
        """分析工具描述的 Token 消耗"""
        total_tokens = 0
        tool_stats = []

        for tool in tools:
            text = json.dumps(tool, ensure_ascii=False)
            tokens = len(self._tokenizer.encode(text))
            total_tokens += tokens

            func = tool.get("function", tool)
            name = func.get("name", "unknown")
            desc = func.get("description", "")
            desc_tokens = len(self._tokenizer.encode(desc))

            tool_stats.append({
                "name": name,
                "total_tokens": tokens,
                "description_tokens": desc_tokens,
                "description_pct": desc_tokens / tokens * 100 if tokens else 0
            })

        # 按描述占比排序（越高越值得优先优化）
        tool_stats.sort(
            key=lambda x: x["description_pct"], reverse=True
        )

        return {
            "total_tools": len(tools),
            "total_tokens": total_tokens,
            "ranked_by_bloat": tool_stats[:10]  # 膨胀最严重的 Top 10
        }

    def suggest_compression(
        self, description: str, max_tokens: int = 30
    ) -> str:
        """对描述文本提出压缩建议"""
        current_tokens = len(self._tokenizer.encode(description))

        if current_tokens <= max_tokens:
            return description  # 已经够精简

        # 压缩策略：
        # 1. 移除"这是一个..."引导语
        desc = re.sub(r'^(这是一个|该工具用于|此函数).*?[，,]', '', description)

        # 2. 移除括号内的冗余说明
        desc = re.sub(r'[（(].{0,20}?[）)]', '', desc)

        # 3. 合并重复信息
        # (简化实现)

        return desc.strip()
```

## 五、监控与告警

### 5.1 Token 消耗监控

```python
class ToolTokenMonitor:
    """工具 Token 消耗监控器"""

    def __init__(self, threshold: int = 10000):
        self._threshold = threshold  # Token 告警阈值
        self._history: list[dict] = []

    def check(self, tools: list[dict]) -> dict:
        """检查工具是否超过 Token 阈值"""
        total_tokens = self._count_tokens(tools)
        alert = total_tokens > self._threshold

        result = {
            "timestamp": time.time(),
            "tool_count": len(tools),
            "total_tokens": total_tokens,
            "threshold": self._threshold,
            "exceeded": alert
        }

        self._history.append(result)

        if alert:
            self._raise_alert(result)

        return result

    def _count_tokens(self, tools: list[dict]) -> int:
        text = json.dumps(tools, ensure_ascii=False)
        return len(self._tokenizer.encode(text))

    def _raise_alert(self, result: dict):
        print(
            f"[ALERT] 工具定义 Token 消耗 {result['total_tokens']} "
            f"超过阈值 {self._threshold}。"
            f"工具数量: {result['tool_count']}"
        )

    def get_daily_report(self) -> dict:
        """生成日报"""
        if not self._history:
            return {"no_data": True}

        max_token = max(h["total_tokens"] for h in self._history)
        min_token = min(h["total_tokens"] for h in self._history)
        avg_token = sum(h["total_tokens"] for h in self._history) / len(
            self._history
        )

        return {
            "samples": len(self._history),
            "max_tokens": max_token,
            "min_tokens": min_token,
            "avg_tokens": avg_token,
            "alerts_triggered": sum(1 for h in self._history if h["exceeded"])
        }
```

### 5.2 最佳实践清单

```
工具描述优化 Checklist：

□ 每个工具的 description 控制在 15-30 字以内
□ 移除"这是一个"、"该工具用于"等引导语
□ 参数 description 统一格式：[含义]。[格式/示例]
□ 枚举值不需要在 description 中重复说明（enum 字段已包含）
□ 不要在描述中写实现细节（调用了哪个 API、哪种数据库）
□ 布尔参数的 description 控制在 10 字以内
□ 高频使用工具 → 更短的 description
□ 启用 Prompt Caching
□ 部署层级工具菜单（见 9.5 节）
□ 设置 Token 消耗告警阈值（建议 10,000 tokens）
□ 每周检查工具描述膨胀报告
□ 新工具注册时自动检查描述长度
```

## 关键概念速查表

| 概念 | 定义 | 重要性 |
|------|------|--------|
| **工具描述膨胀** | 工具描述占用的 Token 过多导致效率下降的现象 | P0 |
| **Token 密度** | 有用信息量与 Token 消耗的比值 | P1 |
| **Prompt Caching** | 缓存系统提示（含工具定义）减少重复 Token 消耗 | P1 |
| **Prefix Caching** | LLM API 提供的提示前缀缓存功能 | P1 |
| **描述压缩** | 通过移除冗余来减少工具描述 Token 的技术 | P1 |
| **分层投递** | 按需展开工具而非一次性全部投递（见 9.5 节） | P0 |
| **自适应描述** | 根据工具使用频率动态调整描述长度 | P2 |
