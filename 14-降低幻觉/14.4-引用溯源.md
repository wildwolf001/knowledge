# 14.4 引用溯源

> 引用溯源（Citation & Attribution）要求 Agent 为其生成的每一个事实陈述标注来源。这不仅是降低幻觉的技术手段，也是建立用户信任和满足合规要求的必要条件。核心理念：**"每一个断言都需要一份出生证明"**。

---

## 一、为什么引用溯源重要？

### 1.1 技术层面

- **可验证性**：用户（或下游系统）可以快速核实 Agent 的陈述是否准确
- **幻觉检测**：无法标注来源的陈述很可能就是幻觉
- **RAG 质量反馈**：如果某个来源从未被引用，可能说明检索质量有问题

### 1.2 用户信任层面

研究表明，展示引用信息可以显著提升用户对 AI 系统的信任度：
- 用户可以通过追溯来源来**自行验证**关键信息
- 即使不实际点击每个引用，**引用的存在本身**就给用户一种"透明可查"的安心感
- 当 Agent 说"我不确定"并附带来源时，用户信任度高于说"答案是 X"但无来源

### 1.3 合规层面

- EU AI Act 等法规要求 AI 系统的输出具有可追溯性
- 企业内部的审计和合规流程需要记录决策依据
- 法律和医疗等领域，无来源的陈述可能构成责任风险

## 二、引用溯源的实现架构

### 2.1 来源标注流水线

```
用户问题
    │
    ▼
检索阶段 ─────→ 检索到的文档 + metadata（URL、标题、段落ID）
    │
    ▼
生成阶段 ─────→ LLM 基于检索文档生成回答 + 标注引用
    │
    ▼
验证阶段 ─────→ Cross-Encoder 验证：引用段落是否真的支持该断言
    │
    ▼
输出阶段 ─────→ 带引用标记的回答（claims + citations）
```

### 2.2 引用粒度控制

| 粒度 | 描述 | 示例 | 优点 | 缺点 |
|------|------|------|------|------|
| **文档级** | 标注引用的文档 | "参见《2024年行业报告》" | 简单 | 文档可能很长，难以定位具体信息 |
| **段落级** | 标注引用的段落 | "参见[doc_3 §4]" | 平衡了精确性和可用性 | 段落仍可能包含多个独立断言 |
| **句子级** | 标注引用的具体句子 | "参见[doc_3 第4段第2句]" | 非常精确 | 实现复杂，token 开销大 |
| **Span 级** | 标注原文的具体文本范围 | "原文:'2024年增长率为42%'" | 最精确 | 实现最复杂，UI 展示困难 |

**工程推荐**：段落级引用作为默认，对高风险断言（数据、法律条款）使用句子级或 Span 级引用。

### 2.3 上下文注入策略

在 Prompt 中，为每个可引用的内容块分配唯一的引用 ID：

```json
{
  "sources": [
    {
      "id": "src_01",
      "title": "2024年行业报告",
      "paragraph": "根据国家统计局数据，2024年AI市场规模达到580亿美元...",
      "url": "https://example.com/report2024",
      "access_time": "2025-06-15"
    },
    {
      "id": "src_02",
      "title": "AI Index Report 2024",
      "paragraph": "AI investment in 2024 surpassed $100 billion globally...",
      "url": "https://aiindex.stanford.edu/report/",
      "access_time": "2025-06-15"
    }
  ]
}
```

对应的 System Prompt 指令：
```
在生成回答时：
1. 每个事实陈述后面标注来源 ID，格式为 [src_XX]
2. 如果你使用了多个来源的信息来得出一个结论，标注所有相关来源
3. 如果某个陈述是你自己的推理（而非直接来自来源），标注 [推理]
4. 不要编造来源 ID——只使用提供的来源
```

## 三、Cross-Encoder 验证引用一致性

### 3.1 问题定义

标注了引用不代表引用正确。模型可能出现以下错误：
- **弱相关引用**：引用的段落确实提到了相关主题，但不足以支持具体的断言
- **矛盾引用**：引用的段落实际上说的是相反的意思
- **幻觉引用**：来源 ID 是编造的，对应的文档中根本找不到该信息

### 3.2 Cross-Encoder 的工作原理

Cross-Encoder 是一种将两个文本**联合编码**后进行分类的模型架构，区别于 Bi-Encoder（分别编码后计算相似度）：

```
Bi-Encoder（向量相似度）:
  Text_A → Encoder → Vector_A  ─┐
                                  ├→ cosine_similarity → Score
  Text_B → Encoder → Vector_B  ─┘
  
  特点：可预计算向量，检索快，但精度较低

Cross-Encoder（联合编码）:
  [Text_A, Text_B] → Encoder → Classifier → Score
  
  特点：无法预计算（必须每次联合编码），检索慢，但精度高
```

Cross-Encoder 适合作为 Reranker（重排序）和引用验证器，因为它能捕捉文本间的**细粒度语义关系**。

### 3.3 引用验证流程

```python
from sentence_transformers import CrossEncoder

# 使用专门训练用于事实验证的 Cross-Encoder 模型
model = CrossEncoder('vectara/hallucination_evaluation_model')

def verify_citation(claim: str, cited_paragraph: str) -> dict:
    """
    验证一个断言是否被引用的段落支持
    """
    score = model.predict([claim, cited_paragraph])
    
    # 该模型输出三个类别的概率
    # [hallucination_score, entailed_score, neutral_score]
    
    if score > THRESHOLD_SUPPORTED:  # 通常阈值设在 0.5
        return {"verdict": "SUPPORTED", "score": float(score)}
    else:
        return {"verdict": "NOT_SUPPORTED", "score": float(score)}

# 完整验证流程
def verify_answer_with_citations(answer_text, sources):
    claims = extract_claims(answer_text)  # 把回答拆解为多个独立断言
    results = []
    
    for claim in claims:
        claim_results = []
        for citation in claim.citations:
            source_text = sources[citation.source_id].paragraph
            result = verify_citation(claim.text, source_text)
            claim_results.append(result)
        results.append({
            "claim": claim.text,
            "citations": claim_results,
            "all_supported": all(r["verdict"] == "SUPPORTED" 
                                for r in claim_results)
        })
    
    return results
```

### 3.4 常用引用验证模型

| 模型 | 特点 | 适用场景 |
|------|------|---------|
| vectara/hallucination_evaluation_model | 专为幻觉检测训练，基于 deberta-v3-base | RAG 输出的事实性验证 |
| AlignScore | 评估两个文本是否在事实上一致 | 通用的事实验证 |
| TrueTeacher | 基于 FLAN-T5，通过自然语言推理判断支持/矛盾 | 需要细粒度分析的场景 |
| MiniCheck | 轻量级，适合高吞吐场景 | 大规模实时验证 |

### 3.5 性能考量

- Cross-Encoder 的推理成本与引用对的数量成正比
- 对于一个 3 条断言、每条 2 个引用、共 6 个 claim-citation 对的回答，约为 100-300ms
- 如果成本过高，可以只对高风险断言（数据、法律声明、医疗建议）使用 Cross-Encoder，其余的仅做格式检查（是否有引用 ID 标注）

## 四、事实核查流水线（完整架构）

```
                       用户问题
                          │
                          ▼
              ┌─────────────────────┐
              │     检索阶段         │
              │  用语义搜索找到相关文档 │
              └──────────┬──────────┘
                         │
                         ▼
              ┌─────────────────────┐
              │     生成阶段         │
              │  LLM基于文档生成回答  │
              │  并标注引用 [src_XX] │
              └──────────┬──────────┘
                         │
                         ▼
              ┌─────────────────────┐
              │     提取阶段         │
              │  将回答拆解为独立断言  │
              │  claim_1, claim_2... │
              └──────────┬──────────┘
                         │
                         ▼
              ┌─────────────────────┐
              │     验证阶段         │
              │  每个claim × 对应    │
              │  引用段落 → CE验证   │
              └──────────┬──────────┘
                         │
                    ┌────┴────┐
                    ▼         ▼
                 通过率≥80%   通过率<80%
                    │         │
                    ▼         ▼
                直接输出    标记不可验证的断言
                           "关于X的说法需要进一步核实"
```

## 五、引用溯源的工程设计要点

### 5.1 来源元数据管理

每个来源应携带足够的元数据：

```python
@dataclass
class Source:
    id: str                    # 唯一标识符
    title: str                 # 文档/页面标题
    content: str               # 引用的具体内容
    url: str | None            # 来源 URL
    access_time: datetime      # 访问时间
    source_type: str           # "official_doc" | "academic" | "news" | "forum" | "unknown"
    authority_score: float     # 权威性评分 0-1
    snippet_start: int | None  # 原文起始位置
    snippet_end: int | None    # 原文结束位置
```

### 5.2 UI 设计考量

- 引用角标使用数字或图标（如 [1] [2]），点击展开原文
- 高风险断言使用不同颜色的引用标记（如红色角标表示"需要验证"）
- 为移动端提供引用折叠/展开的交互
- 在引用列表底部显示"访问时间"，提示内容的时效性

### 5.3 检索质量闭环

引用溯源系统可以反向评估检索质量：

```python
# 统计每个来源的引用频率
citation_stats = defaultdict(int)
for session in sessions:
    for citation in session.citations:
        citation_stats[citation.source_id] += 1

# 从未被引用的来源 → 可能是检索噪声
unused_sources = [s for s in all_retrieved_sources 
                  if s.id not in citation_stats]
unused_rate = len(unused_sources) / len(all_retrieved_sources)

# unused_rate > 50% → 检索精度需要优化
```

## 关键概念速查

| 术语 | 解释 |
|------|------|
| 引用溯源 | 为每个断言标注信息来源的过程 |
| Cross-Encoder | 联合编码两个文本后分类，适合验证引用相关性 |
| Bi-Encoder | 分别编码后计算相似度，适合大规模检索 |
| 引用粒度 | 引用精确到文档/段落/句子/文本范围的级别 |
| 事实核查流水线 | 检索→生成→提取→验证的完整引用溯源架构 |
