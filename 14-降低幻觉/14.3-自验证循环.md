# 14.3 自验证循环

> 自验证循环（Self-Verification Loop）是让 Agent 对自己的每步输出进行二次确认的机制。其核心理念借鉴图书馆学的"Librarian Check"：任何断言在成为下一步的输入之前，必须经过一个独立的验证节点。

---

## 一、为什么需要自验证？

### 1.1 单一模型的结构性弱点

同一个模型既是"生成者"又是"验证者"时，存在一个根本问题：

> **如果模型有能力在生成时就知道某件事是错的，那它为什么还会生成错误内容？**

答案在于 LLM 的**非对称能力**：
- 模型在**辨别（Verification）**任务上的表现通常优于**生成（Generation）**任务
- 给定一个陈述判断其对错（二元判断），比从头生成正确的陈述更容易
- 这类似于人类"我看别人写的东西能看出错误，但自己写的时候会犯相同的错误"

**实验证据**：多项研究表明，让 LLM 审查自己的输出，它能够识别出约 60-80% 的自己产生的幻觉——尽管无法识别全部。如果使用更强大的模型来验证较弱模型的输出，识别率更高（详见 20.3 节 LLM-as-Judge）。

### 1.2 自验证在 Agent 中的特殊价值

常规的 Chatbot 场景中，模型只需要在最终输出时做一次验证。但 Agent 场景不同：

- Agent 的每一步输出都会**反馈为下一步的输入**（Observation → Next Thought）
- 第 3 步的幻觉污染第 4 步的决策，第 5 步可能已经不可挽回
- 因此需要在**每一步**都进行验证，而不是只在最后一步

这就是自验证循环的核心设计目标：**在幻觉造成级联效应之前截获它**。

## 二、Librarian Check 模式

### 2.1 基本架构

Librarian Check 是自验证循环中的一种经典设计模式，将验证角色从生成角色中分离：

```
┌──────────────────────────────────────────────────┐
│                  Agent 主循环                       │
│                                                    │
│   Thought ─→ Action ─→ Observation ─→ Thought      │
│       │        │           │                        │
│       └────────┼───────────┘                        │
│                │                                    │
│         验证节点（Librarian）                        │
│         - 检查 Action 是否合理                      │
│         - 检查 Observation 是否被误解               │
│         - 检查 Thought 是否与 Observation 一致      │
│         - 如发现问题 → 标记、纠正或重新生成        │
└──────────────────────────────────────────────────┘
```

### 2.2 验证节点的职责

**对 Thought（思考）的验证**：
- 推理链路是否连贯？前一步的 Observation 是否支持当前 Thought？
- 是否引入了与上下文无关的新假设？
- 是否无依据地改变了之前的结论？

**对 Action（行动）的验证**：
- 工具名称是否存在？（避免工具调用幻觉，见 24.8 节）
- 参数是否符合 Schema？必填参数是否完整？
- 该 Action 在当前上下文是否合理？（例如：还没查询价格就要下单购买）

**对 Observation（观察）的验证**：
- 工具返回值是否与预期一致？
- 是否误解了工具输出的含义？
- 是否有隐式的错误信号？（如 API 返回了错误但模型将其当作正常结果）

### 2.3 实现方式

**方式一：同模型自检（Self-Check）**

用同一个模型在验证模式下运行：
```python
def librarian_check(step_type, content, context):
    prompt = f"""你是一名严格的审核员。请检查以下 Agent {step_type} 是否存在问题。

    上下文：
    {context}
    
    待检查的 {step_type}：
    {content}
    
    请判断：
    1. 是否有事实错误？
    2. 推理是否连贯？
    3. 是否有无依据的假设？
    
    返回 JSON：
    {{"pass": true/false, "issues": ["问题1", "问题2"], "confidence": 0.0-1.0}}
    """
    return llm.generate(prompt, temperature=0.0)  # 用 temperature=0 增加确定性
```

**方式二：Cross-Model Check（交叉验证）**

使用不同的模型进行验证（更可靠但成本更高）：
- 用 Claude 生成，用 GPT-4o 验证
- 用大模型生成，用小模型验证（检测明显错误）
- 优势是避免了"同一个模型犯同样错误"的系统性盲区

**方式三：工具辅助验证**

用确定性工具/代码验证（零幻觉）：
- 数学计算：用 Python 执行并对比结果
- JSON 格式：用 JSON Schema 验证器
- 代码语法：用 AST 解析器或 linter
- 日期/时间：用 datetime 库验证合法性

## 三、Reflexion：带记忆的自验证

Reflexion（Shinn et al., 2023）模式将自验证与长期记忆相结合。它是 2.4 节提到的 Reflexion 模式的一种实现角度，此处从"降低幻觉"的维度来理解：

### 3.1 核心机制

```
Episode 结束
    │
    ▼
LLM 回顾完整轨迹
    │
    ├── 成功 → 提取成功经验 → 存入长期记忆
    │
    └── 失败 → 分析失败原因 → 生成"反思笔记" → 存入长期记忆
                                              │
                                   下次类似任务时注入上下文
                                   作为"教训"指导行为
```

### 3.2 反思笔记（Reflexion Note）的结构

```
反思笔记：
- 任务：[原始任务描述]
- 失败节点：步骤 4 的 Action "search_product"
- 失败类型：工具选择错误
- 根因分析：应使用 "search_inventory" 而非 "search_product"，
  因为用户问的是库存状态而非产品信息
- 经验教训：查询库存状态时应使用 search_inventory 工具
- 触发条件：当用户提到"有没有货""库存""还剩多少"时
```

### 3.3 Reflexion 的幻觉预防效果

- **避免重复错误**：第一次犯了某个幻觉错误后，反思笔记确保了后续不会犯相同类型的错误
- **长期学习**：通过多次反思的积累，Agent 逐渐建立"什么情况下容易出错"的元认知
- **成本考量**：Reflexion 需要额外的 LLM 调用来生成反思，在长周期任务中是值得的投入

## 四、Self-Consistency（自一致性验证）

Self-Consistency 是一种轻量级的自验证方法（Wang et al., 2023）：

### 4.1 基本思想

> 对一个问题的回答如果是正确的，那么多次独立生成的结果应该是一致的。
> 如果不一致，说明模型在该问题上信心不足，回答可能不可靠。

### 4.2 实现

```python
def self_consistency_check(prompt, n=5, temperature=0.7):
    """生成 n 个独立回答，取多数一致的作为最终答案"""
    responses = []
    for _ in range(n):
        response = llm.generate(prompt, temperature=temperature)
        responses.append(response)
    
    # 聚类：找到最一致的答案群
    clusters = semantic_cluster(responses)
    largest_cluster = max(clusters, key=len)
    
    consistency_score = len(largest_cluster) / n
    
    if consistency_score >= 0.6:  # 60% 以上一致
        return largest_cluster[0], consistency_score
    else:
        return None, consistency_score  # 不一致，标记为不可靠
```

### 4.3 适用场景

- 答案有明确对错之分的问题（数学题、事实查询）
- 不适用于开放性的创意任务（创意写作本身就期望多样性）

### 4.4 Social Sampling

Self-Consistency 的变体：不仅比较答案文本，还在 Prompt 中要求模型"给出推理过程"，然后比较的是**推理路径**的一致性而非最终答案的一致性。

## 五、Agent 自我纠错流程

### 5.1 检测-修正循环

```
         生成输出
            │
            ▼
    ┌──────────────┐
    │   自验证检查   │
    └──────┬───────┘
           │
    ┌──────┴───────┐
    ▼              ▼
  通过          未通过
    │              │
    ▼              ▼
 继续下一步    ┌──────────┐
              │ 错误分类  │
              └─────┬────┘
                    │
        ┌───────────┼───────────┐
        ▼           ▼           ▼
    可自动修复   需重新生成   需转人工
        │           │           │
        ▼           ▼           ▼
    修正后重新   带着反馈    HITL
    提交验证     重新生成     升级流程
```

### 5.2 纠错反馈（Corrective Feedback）

当检测到错误时，给模型的具体反馈比笼统的"你的回答有误"更有效：

```python
# 好的纠错反馈
feedback = """你的回答中有以下问题：
1. 第3段提到的"2023年发布"与检索结果[doc_3]中的"2024年发布"矛盾
2. 结论中使用的增长率42%在源数据中未找到依据

请基于以下正确的信息重新生成：
- 发布时间为2024年（来源：[doc_3]）
- 增长率数据请使用[doc_5]中提供的官方数据
"""

# 避免的笼统反馈
feedback = "你的回答有错误，请重新生成。"  # 模型可能再次犯相同的错误
```

### 5.3 最大重试与降级

- 同一问题的重新生成不应超过 **3 次**
- 3 次后仍不通过 → 降级处理（标注不确定部分 / 转人工 / 回复"我无法提供准确回答"）
- 这是基于经验数据：如果连续 3 次生成的答案都未能通过验证，第 4 次通过的概率极低

## 六、自验证的工程权衡

### 6.1 成本

| 方法 | Token 增量 | 延迟增量 | 幻觉降低效果 |
|------|-----------|---------|-------------|
| 单次 Self-Check | +50-100% | +30-80% | 额外识别 60-70% 的幻觉 |
| Cross-Model Check | +100-150% | +50-100% | 额外识别 75-85% 的幻觉 |
| Self-Consistency (n=5) | +400% | +300-400% | 大幅提升数学/事实类准确性 |
| Reflexion | +20-30%（均摊） | 几乎无影响 | 降低重复性错误 |

### 6.2 何时开启自验证

建议的策略：

```
if task.criticality == "high":  # 医疗、法律、金融
    开启 Cross-Model Check
elif step.type == "irreversible_action":  # 数据库写入、API 发布
    开启 Self-Check + Human Confirmation
elif task.complexity > 5_steps:
    开启 Self-Check for each step
else:
    仅开启 输出护栏（14.2 节）
```

## 关键概念速查

| 术语 | 解释 |
|------|------|
| Librarian Check | 在每一步后进行验证的节点模式，生成和验证分离 |
| Self-Consistency | 多次独立生成回答，比较一致性来评估可靠性 |
| Reflexion | 将自验证结果保存为长期记忆，避免重复犯同类错误 |
| 纠错反馈 | 包含具体错误位置和正确信息的反馈，比笼统反馈更有效 |
| 最大重试 | 对同一问题的重新生成次数上限（通常为 3 次） |
