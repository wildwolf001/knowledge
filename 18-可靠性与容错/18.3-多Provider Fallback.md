# 18.3 多 Provider Fallback

> "模型 A 挂了怎么办？切换到模型 B。"——听起来简单，但实际 Fallback 涉及成本控制、延迟权衡、模型能力差异等多维度决策。529 Overloaded 更需要专有的处理策略。

---

## 一、为什么需要多 Provider Fallback

### 1.1 单 Provider 的风险

依赖单一 LLM Provider 在可靠性上有明显缺陷：

| 风险类型 | 示例 | 影响 |
|---------|------|------|
| **服务中断** | OpenAI、Anthropic 等曾出现区域性服务中断 | Agent 完全不可用 |
| **限流（Rate Limit）** | 突发流量触发 Provider 的限流策略 | 请求被拒绝 |
| **过载（Overloaded）** | 高峰期 GPU 资源不足，返回 529 | 延迟增加或失败 |
| **模型变更** | Provider 下架旧模型或更新行为 | 行为不一致 |
| **定价变化** | API 价格大幅上涨 | 成本失控 |
| **合规限制** | 某些 Provider 不能在特定地区使用 | 部署受限 |

多 Provider Fallback 的核心思想是：**不要把所有鸡蛋放在一个篮子里**。

### 1.2 Fallback 的层次结构

Fallback 可以在多个层次上实施：

```
层次 1: 服务商内 Fallback（同一 Provider 的不同模型）
  例如: GPT-4 → GPT-4-Turbo → GPT-3.5-Turbo

层次 2: 服务商间 Fallback（不同 Provider 的类似模型）
  例如: GPT-4 → Claude-3-Opus → Gemini-Ultra

层次 3: 模型大小降级 Fallback（大模型 → 小模型）
  例如: GPT-4 → Claude-3-Haiku → Local-7B

层次 4: 非 LLM Fallback（LLM → 确定性系统）
  例如: LLM 生成 → 规则引擎 → 模板填充
```

## 二、Fallback 链路设计

### 2.1 路由与 Fallback 架构

一个完整的 Fallback 系统由三部分组成：

```
用户请求
    │
    ▼
┌─────────────────────────────────────────┐
│           Fallback Router               │
│  ┌──────────┐  ┌──────────┐  ┌────────┐│
│  │ Provider │  │ Provider │  │ Provider││
│  │ A        │  │ B        │  │ C      ││
│  │ (Primary)│  │ (Secondary)│  │ (Tertiary)│
│  └────┬─────┘  └────┬─────┘  └───┬────┘│
│       │              │             │     │
│       ▼              ▼             ▼     │
│  ┌─────────────────────────────────────┐│
│  │        健康检查 & 断路器            ││
│  └─────────────────────────────────────┘│
└─────────────────────────────────────────┘
```

### 2.2 链路优先级定义

```python
from dataclasses import dataclass
from typing import List, Optional, Dict, Any
from enum import Enum

class ModelTier(Enum):
    """模型分级"""
    PREMIUM = "premium"       # 顶级模型，处理复杂任务
    STANDARD = "standard"     # 标准模型，处理常规任务
    ECONOMY = "economy"       # 经济模型，处理简单任务
    FALLBACK = "fallback"     # 最后备选（可能使用本地模型或规则）


@dataclass
class ProviderConfig:
    """Provider 配置"""
    name: str
    model: str
    tier: ModelTier
    base_url: str
    api_key: str
    max_retries: int = 3
    timeout: float = 30.0
    cost_per_1k_tokens: float = 0.0
    weight: int = 10  # 优先级权重，越大越优先


@dataclass
class FallbackChain:
    """Fallback 链路定义"""
    task_type: str  # 任务类型，如 "code_generation", "qa", "tool_call"
    providers: List[ProviderConfig]
    
    def get_primary(self) -> ProviderConfig:
        return self.providers[0] if self.providers else None
    
    def get_fallback(self, failed_provider: str) -> Optional[ProviderConfig]:
        """获取下一个可用的 Fallback Provider"""
        for i, provider in enumerate(self.providers):
            if provider.name == failed_provider:
                if i + 1 < len(self.providers):
                    return self.providers[i + 1]
                return None
        return None
```

### 2.3 链路切换的完整实现

```python
import asyncio
import time
from typing import Optional, Callable

class ProviderRouter:
    """
    多 Provider 路由与 Fallback 引擎
    
    管理一组 Provider 的健康状态，按优先级路由请求，
    在 Provider 失败时自动切换到下一个。
    """
    
    def __init__(self, fallback_chains: List[FallbackChain]):
        self.chains = {chain.task_type: chain for chain in fallback_chains}
        self.circuit_breakers = {}  # provider 名称 → CircuitBreaker
        
    async def call_with_fallback(
        self,
        task_type: str,
        request_func: Callable,
        max_fallback_depth: int = 3,
    ) -> Dict[str, Any]:
        """
        带 Fallback 的请求调用
        
        Args:
            task_type: 任务类型
            request_func: 请求函数，接收 provider_config 参数
            max_fallback_depth: 最大 Fallback 深度
        
        Returns:
            包含结果和元数据的字典
        
        Raises:
            AllProvidersFailedError: 所有 Provider 都失败
        """
        chain = self.chains.get(task_type)
        if not chain:
            raise ValueError(f"未找到任务类型 [{task_type}] 的 Fallback 链路")
        
        errors = []
        attempted_providers = []
        
        for depth, provider in enumerate(chain.providers):
            if depth >= max_fallback_depth:
                break
            
            # 检查断路器
            cb = self.circuit_breakers.get(provider.name)
            if cb and not cb.is_available:
                errors.append(ProviderUnavailableError(
                    f"Provider [{provider.name}] 断路器已断开"
                ))
                attempted_providers.append(provider.name)
                continue
            
            try:
                start_time = time.time()
                result = await request_func(provider)
                elapsed = time.time() - start_time
                
                return {
                    "result": result,
                    "provider": provider.name,
                    "model": provider.model,
                    "tier": provider.tier.value,
                    "elapsed_seconds": elapsed,
                    "fallback_depth": depth,
                    "attempted_providers": attempted_providers,
                }
                
            except ProviderOverloadedError as e:
                # 529 Overloaded → 特殊处理
                errors.append(e)
                attempted_providers.append(provider.name)
                await self._handle_overload(provider, e)
                
            except ProviderRateLimitedError as e:
                # 429 Rate Limited → 等待后重试当前 provider
                errors.append(e)
                attempted_providers.append(provider.name)
                retry_result = await self._retry_with_backoff(
                    provider, request_func
                )
                if retry_result:
                    return retry_result
                    
            except ProviderError as e:
                # 其他 Provider 级别错误 → 记录并继续 Fallback
                errors.append(e)
                attempted_providers.append(provider.name)
                if cb:
                    cb._on_failure()
                    
            except Exception as e:
                # 未知错误 → 记录但继续 Fallback
                errors.append(UnknownProviderError(
                    f"Provider [{provider.name}] 未知错误: {e}"
                ))
                attempted_providers.append(provider.name)
        
        # 所有 Provider 都失败
        raise AllProvidersFailedError(
            f"所有 Provider 都失败失败链路: {chain.providers}",
            errors=errors,
            attempted_providers=attempted_providers,
        )
    
    async def _handle_overload(self, provider, error):
        """处理 529 Overloaded 的专项策略"""
        # 1. 记录过载事件
        print(f"Provider [{provider.name}] 过载: {error}")
        
        # 2. 增加断路器的失败计数
        cb = self.circuit_breakers.get(provider.name)
        if cb:
            cb._on_failure()
        
        # 3. 不需要额外等待，直接让外层切到下一个 Provider
        # （过载通常持续时间较长，等几秒不如切 Provider）
    
    async def _retry_with_backoff(self, provider, request_func):
        """带退避的重试（用于 429 等限流错误）"""
        for attempt in range(1, provider.max_retries + 1):
            delay = min(1.0 * (2 ** attempt), 30.0)
            await asyncio.sleep(delay)
            try:
                return await request_func(provider)
            except (ProviderRateLimitedError, ProviderOverloadedError):
                continue
        return None
```

## 三、模型降级策略

### 3.1 降级的原则

模型降级不是在所有场景都直接用弱模型替代强模型。需要遵守以下原则：

**原则 1：任务类型决定降级方案**

| 任务类型 | 可用降级目标 | 降级可行性 |
|---------|-------------|-----------|
| 简单问答 | GPT-4 → GPT-3.5 → 小模型 | 高（复杂度低） |
| 代码生成 | GPT-4 → Claude → GPT-3.5 | 中（需要特定能力） |
| 工具调用 | GPT-4 → GPT-4-Turbo → 本地模型 | 低（小模型函数调用能力弱） |
| 推理分析 | 必须保持模型能力 | 低（降级后质量不可接受） |

**原则 2：按能力维度评估降级损失**

```python
def evaluate_degradation_impact(
    task_type: str,
    from_model: str,
    to_model: str
) -> Dict[str, float]:
    """
    评估从 from_model 降级到 to_model 的影响
    
    返回一个字典，列出各能力维度的预期质量下降比例
    """
    impact = {}
    
    # 指令遵循能力
    impact["instruction_following"] = {
        ("gpt-4", "gpt-3.5"): 0.15,
        ("gpt-4", "claude-3-haiku"): 0.10,
        ("gpt-4", "llama-7b"): 0.35,
    }.get((from_model, to_model), 0.20)
    
    # 推理能力
    impact["reasoning"] = {
        ("gpt-4", "gpt-3.5"): 0.25,
        ("gpt-4", "claude-3-haiku"): 0.15,
        ("gpt-4", "llama-7b"): 0.40,
    }.get((from_model, to_model), 0.30)
    
    # 工具调用能力
    impact["tool_calling"] = {
        ("gpt-4", "gpt-3.5"): 0.20,
        ("gpt-4", "claude-3-haiku"): 0.05,
        ("gpt-4", "llama-7b"): 0.50,
    }.get((from_model, to_model), 0.25)
    
    return impact
```

### 3.2 自动降级决策

```python
class DegradationDecision:
    """降级决策"""
    
    ALLOWED_TASK_TYPES_FOR_DEGRADATION = {
        "simple_qa", "text_generation", "summarization",
        "classification", "entity_extraction",
    }
    
    CRITICAL_TASK_TYPES = {
        "code_execution", "financial_calculation", "medical_advice",
        "legal_analysis", "tool_call_complex", "data_transformation",
    }
    
    @classmethod
    def should_degrade(
        cls,
        task_type: str,
        fallback_depth: int,
        confidence: float,
        degradation_policy: str = "auto",
    ) -> bool:
        """
        判断是否应该接受模型降级
        
        Args:
            task_type: 任务类型
            fallback_depth: 当前已 Fallback 的深度
            confidence: 置信度分数（参见 14.5 节）
            degradation_policy: auto / conservative / aggressive
        
        Returns:
            是否允许降级
        """
        
        if degradation_policy == "conservative":
            # 保守策略：只对非关键任务降级
            if task_type in cls.CRITICAL_TASK_TYPES:
                return False
        
        if degradation_policy == "aggressive":
            # 激进策略：允许所有降级
            return True
        
        # 默认自动策略
        if task_type in cls.ALLOWED_TASK_TYPES_FOR_DEGRADATION:
            return True
        
        if task_type in cls.CRITICAL_TASK_TYPES:
            # 关键任务只有在确定性降级时才允许
            return False
        
        # 其他任务：根据置信度和 Fallback 深度决策
        if confidence >= 0.7 and fallback_depth <= 1:
            # 高置信度、小降级深度 → 允许
            return True
        
        if fallback_depth >= 3:
            # 已经尝试了 3 个 Provider → 允许进一步降级
            return True
        
        return False
```

### 3.3 降级通知与追踪

降级不是透明的——系统需要知道当前使用的是降级模型：

```python
@dataclass
class DegradationInfo:
    """降级信息记录"""
    original_provider: str
    current_provider: str
    original_model: str
    current_model: str
    fallback_depth: int
    degradation_reason: str
    performance_impact: str  # "low" / "medium" / "high"
    
    def to_metadata(self) -> Dict:
        """转换为元数据，可注入到 Agent 的日志中"""
        return {
            "degraded": True,
            "original_provider": self.original_provider,
            "current_provider": self.current_provider,
            "degradation_depth": self.fallback_depth,
            "reason": self.degradation_reason,
        }


class DegradationTracker:
    """降级追踪器——用于监控和分析降级模式"""
    
    def __init__(self):
        self.degradation_log: List[DegradationInfo] = []
    
    def record(self, info: DegradationInfo):
        self.degradation_log.append(info)
    
    def get_degradation_rate(self, time_window: float = 3600) -> float:
        """计算降级率"""
        now = time.time()
        window_logs = [
            log for log in self.degradation_log
            if now - log.timestamp < time_window
        ]
        if not window_logs:
            return 0.0
        return len([l for l in window_logs if l.fallback_depth > 0]) / len(window_logs)
    
    def get_most_common_reason(self) -> str:
        """获取最常见的降级原因"""
        from collections import Counter
        reasons = Counter(log.degradation_reason for log in self.degradation_log)
        return reasons.most_common(1)[0][0] if reasons else "unknown"
```

## 四、529 Overloaded 专项处理

### 4.1 529 错误的本质

**529 Overloaded** 是 LLM API 服务特有的 HTTP 状态码，表示服务端当前负载过高，无法处理请求。这不是客户端的问题，也不是服务器崩溃——只是服务器"太忙了"。

529 和 429 的关键区别：

| 维度 | 429 Too Many Requests | 529 Overloaded |
|------|----------------------|---------------|
| 原因 | 客户端请求速率超过限流阈值 | 服务器整体负载过高 |
| 责任方 | 客户端 | 服务端 |
| 典型持续时间 | 数百毫秒到数秒 | 数秒到数分钟 |
| 解决方案 | 降低请求速率 | 等待后重试 或 切换到其他 Provider |
| 重试成功率 | 等待后通常成功 | 可能持续失败（服务器仍在过载） |

### 4.2 529 处理策略

由于 529 通常持续数秒到数分钟，**等待重试不如直接切换 Provider**：

```python
class OverloadHandler:
    """
    529 Overloaded 专项处理器
    
    策略：不等待重试，立即可用 Fallback 切换。
    但是如果所有 Provider 都过载，采用渐进式退避。
    """
    
    def __init__(self, backoff_config: Dict = None):
        self.backoff_config = backoff_config or {
            "initial_wait": 2.0,
            "max_wait": 120.0,
            "backoff_factor": 2.0,
        }
        self.global_overload_count = 0
        self.last_all_overload_time = 0.0
    
    async def handle(
        self,
        provider: ProviderConfig,
        router: ProviderRouter,
        task_type: str,
        request_func: Callable,
    ) -> Optional[Dict]:
        """
        处理单个 Provider 的 529 错误
        
        返回值：
            - 成功结果（如果切换到其他 Provider 并成功了）
            - None（如果所有 Provider 都过载）
        """
        try:
            # 直接尝试下一个 Provider，不等待
            return await router.call_with_fallback(
                task_type=task_type,
                request_func=request_func,
                max_fallback_depth=2,  # 只尝试当前的下一个
            )
        except AllProvidersFailedError as e:
            # 所有 Provider 都失败 → 可能全局过载
            return await self._handle_global_overload(
                provider, task_type, request_func
            )
    
    async def _handle_global_overload(
        self,
        last_provider: ProviderConfig,
        task_type: str,
        request_func: Callable,
    ) -> Optional[Dict]:
        """所有 Provider 都过载时的处理"""
        
        self.global_overload_count += 1
        self.last_all_overload_time = time.time()
        
        # 渐进式退避
        wait_time = min(
            self.backoff_config["initial_wait"] * 
            (self.backoff_config["backoff_factor"] ** self.global_overload_count),
            self.backoff_config["max_wait"]
        )
        
        print(f"所有 Provider 过载，等待 {wait_time:.1f}s 后重试 "
              f"(第 {self.global_overload_count} 次全局过载)")
        
        await asyncio.sleep(wait_time)
        
        # 重试（使用 Primary Provider）
        try:
            return await request_func(last_provider)
        except ProviderOverloadedError:
            return None  # 仍然过载，上层会处理
    
    def get_overload_metrics(self) -> Dict:
        """返回过载指标用于监控"""
        return {
            "global_overload_count": self.global_overload_count,
            "last_global_overload": self.last_all_overload_time,
            "is_in_global_overload": (
                time.time() - self.last_all_overload_time < 60.0
            ),
        }
```

### 4.3 529 的历史数据驱动策略

对于生产系统，应基于历史数据制定 529 策略：

```python
class OverloadPredictor:
    """
    基于历史数据的 529 预测
    
    如果某个 Provider 在特定时间段频繁出现过载，
    自动降低其优先级或切换 Primary。
    """
    
    def __init__(self, history_window: float = 3600):
        self.overload_events: List[Dict] = []
        self.history_window = history_window
    
    def record_overload(self, provider: str, model: str):
        self.overload_events.append({
            "provider": provider,
            "model": model,
            "timestamp": time.time(),
        })
        # 清理过期记录
        self._cleanup()
    
    def get_overload_rate(self, provider: str) -> float:
        """计算 Provider 的 529 比率"""
        self._cleanup()
        provider_events = [
            e for e in self.overload_events 
            if e["provider"] == provider
        ]
        return len(provider_events) / max(self.history_window, 1)
    
    def should_demote(self, provider: str, threshold: float = 0.05) -> bool:
        """
        判断是否应该降级 Provider
        
        如果过去 1 小时内有超过 5% 的请求遇到 529，降级
        """
        rate = self.get_overload_rate(provider)
        return rate > threshold
    
    def _cleanup(self):
        now = time.time()
        self.overload_events = [
            e for e in self.overload_events
            if now - e["timestamp"] < self.history_window
        ]
```

## 五、Fallback 的工程最佳实践

### 5.1 优雅降级的用户体验

当发生 Fallback 时，用户通常不应该感知到，但在关键降级场景下应透明通知：

```
正常的 Agent 回复: "根据您的需求，我已经生成了一份数据分析报告..."

降级后的 Agent 回复（用户透明）:
"根据您的需求，我已经生成了一份数据分析报告...

（注：当前使用了备选模型处理您的请求，部分高级功能可能受限）"

完全失败时的回复（用户可见）:
"很抱歉，我目前无法处理这个请求。当前所有 AI 服务都处于过载状态。
请稍后再试，或联系管理员。错误码：ALL_PROVIDERS_OVERLOADED"
```

### 5.2 成本控制

Fallback 切换可能带来意外的成本变化：

```python
@dataclass
class FallbackCostTracker:
    """Fallback 成本追踪"""
    request_count: int = 0
    total_cost: float = 0.0
    fallback_extra_cost: float = 0.0
    
    def record_request(self, provider: ProviderConfig, is_fallback: bool):
        """记录一次请求的成本"""
        cost = provider.cost_per_1k_tokens * self._estimate_tokens(provider)
        self.total_cost += cost
        self.request_count += 1
        if is_fallback:
            # Fallback 请求通常切换到更便宜的模型
            # 但这里记录的是相对于 Primary 的成本差异
            pass
    
    def get_fallback_cost_ratio(self) -> float:
        """Fallback 导致的额外成本比率"""
        if self.total_cost == 0:
            return 0.0
        return self.fallback_extra_cost / self.total_cost
```

### 5.3 健康检查与预热

Fallback 链路需要持续的健康检查，而不是等失败了才发现不可用：

```python
class HealthChecker:
    """Provider 健康检查器"""
    
    def __init__(self, providers: List[ProviderConfig], check_interval: float = 30.0):
        self.providers = providers
        self.check_interval = check_interval
        self.health_status: Dict[str, bool] = {}
        self._stop_event = threading.Event()
    
    async def start_health_check(self):
        """启动周期性健康检查"""
        while not self._stop_event.is_set():
            for provider in self.providers:
                is_healthy = await self._check_provider(provider)
                self.health_status[provider.name] = is_healthy
            
            await asyncio.sleep(self.check_interval)
    
    async def _check_provider(self, provider: ProviderConfig) -> bool:
        """检查单个 Provider 的健康状态"""
        try:
            # 发送一个极简请求来检测服务是否正常
            response = await asyncio.wait_for(
                self._ping(provider),
                timeout=5.0
            )
            return response.status == 200
        except:
            return False
    
    async def _ping(self, provider):
```

## 关键概念速查

| 术语 | 解释 |
|------|------|
| Fallback | 当主要方案失败时切换到备选方案 |
| Provider | LLM 服务提供商（如 OpenAI、Anthropic、Google） |
| 模型降级（Degradation） | 从高能力模型切换到低能力模型 |
| 529 Overloaded | 服务器负载过高，无法处理请求（LLM API 特有） |
| 429 Too Many Requests | 客户端请求速率超过 Provider 的限流阈值 |
| 链路切换 | 按优先级从 Primary → Secondary → Tertiary 切换 |
| 优雅降级 | 降级时尽量不让用户感知，或透明告知但不影响核心功能 |
| 健康检查 | 周期性检测 Provider 可用性，而不是等使用时才发现 |
| 全局过载 | 所有 Provider 同时不可用的极端情况 |
