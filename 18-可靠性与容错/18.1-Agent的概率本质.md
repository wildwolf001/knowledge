# 18.1 Agent 的概率本质

> "Agent 是概率系统，你怎么在不确定性中做出可靠的工程设计？"——这是面试必问题，也是构建生产级 Agent 无法绕过的基础认知。理解 Agent 的概率本质，是后续所有可靠性工程的前提。

---

## 一、Agent 的根本矛盾：概率生成 vs 确定性期望

### 1.1 LLM 是概率机，但用户期望它是确定性系统

大型语言模型本质上是一个**条件概率分布**：给定输入序列 \(x_1, x_2, ..., x_{t-1}\)，模型输出下一个 token 的概率分布 \(P(x_t | x_1, ..., x_{t-1})\)。在 Agent 的语境下，这个"概率生成"被放大为多层决策链：

```
用户请求
  → Agent 理解意图（概率性）
    → Agent 决定调用哪个工具（概率性）
      → Agent 生成工具参数（概率性）
        → 工具返回结果（可能含噪声）
          → Agent 解释结果（概率性）
            → Agent 决定下一步（概率性）
              → ... 循环直到任务结束
```

**每一层都是概率性的**。每一层都可能出错，而且每一层的错误会累积到下一层。这就是 Agent 可靠性问题的数学根源。

### 1.2 "确定性幻觉"——工程师最容易犯的错误

很多 Agent 工程师会有一种潜意识假设："模型大概率会走对的路。" 但用"大概率"来做工程是不行的——你需要的是量化的失败概率。

一个常见的思维陷阱：

```
工程师："模型在工具调用测试中正确率是 95%，可以上线了。"
现实：  20 步的 Agent 任务，总成功率只有 0.95^20 ≈ 35.8%
```

**每步 95% 的正确率听起来很高，但 20 步的累积成功率不到 36%。** 这就是概率爆炸的结果。

## 二、概率爆炸的数学推导

### 2.1 基本模型：独立同分布假设

假设 Agent 的每一步决策失败的概率为 \(p\)，且步骤之间相互独立（这是一个简化的理想假设，实际步骤之间有相关性，下文会讨论）。

Agent 完成一个 \(n\) 步任务的**成功率**为：

\[
P(\text{成功}) = (1 - p)^n
\]

**失败率**为：

\[
P(\text{失败}) = 1 - (1 - p)^n
\]

这就是概率爆炸的核心公式。关键洞察在于：**即使 \(p\) 很小，当 \(n\) 足够大时，失败率趋近于 1。**

### 2.2 数值可视化：失败率随步数增长

| 步数 n | p=1% | p=2% | p=5% | p=10% | p=20% |
|--------|------|------|------|-------|-------|
| 1 | 1.0% | 2.0% | 5.0% | 10.0% | 20.0% |
| 5 | 4.9% | 9.6% | 22.6% | 41.0% | 67.2% |
| 10 | 9.6% | 18.3% | 40.1% | 65.1% | 89.3% |
| 20 | 18.2% | 33.2% | **64.2%** | 87.8% | 98.8% |
| 50 | 39.5% | 63.6% | 92.3% | 99.5% | ≈100% |
| 100 | 63.4% | 86.7% | 99.4% | ≈100% | ≈100% |

**关键观察**：
- p=5%（每步 95% 正确率）时，20 步的累积失败率达到 64.2%——大多数多步任务都会失败
- p=1%（每步 99% 正确率，已经很高了）时，100 步的累积失败率也达到 63.4%
- 要让 100 步 Agent 任务有 90% 的成功率，每步失败率需要低于 0.105%（99.895% 的步级正确率）

### 2.3 期望成功步数的推导

我们可以定义**期望成功步数** \(E[n_{\text{success}}]\)——在失败前期望完成的步数。对于几何分布：

\[
E[n_{\text{success}}] = \frac{1-p}{p}
\]

| 每步失败率 p | 期望成功步数 |
|-------------|-------------|
| 1% | 99 步 |
| 2% | 49 步 |
| 5% | 19 步 |
| 10% | 9 步 |
| 20% | 4 步 |

这意味着，如果每步失败率为 5%，你的 Agent 在期望上只能连续完成 19 步就会遇到一次失败。对于一个需要 50 步的复杂任务，几乎必然会在中途失败。

### 2.4 步骤相关性的影响——更现实的模型

上述模型假设步骤独立，这并不完全准确。实际上，Agent 步骤之间通常存在**正相关**：

1. **错误传播**：第 3 步的误解可能导致第 4-10 步全部基于错误前提
2. **上下文污染**：早期错误输出的 token 会影响后续生成的 token 分布
3. **状态一致性**：Agent 的心理模型（对任务的理解）会持续影响后续决策

当步骤正相关时，实际失败率比独立假设更高：

```
假设 p=5%，n=20，相关性系数 ρ：
- ρ=0（独立）：失败率 64.2%
- ρ=0.2：     失败率 ≈ 72%
- ρ=0.5：     失败率 ≈ 83%
- ρ=1.0（完全相关）：失败率 5%（一步错，后面全错 / 一步对，后面全对）
```

完全相关其实"更好"——要么全对要么全错，而中间程度的正相关是最坏的情况：它在放大错误的同时保留了大量步骤，使得每一步都有独立的出错机会。

另一个极端是**负相关**——虽然在实际 Agent 系统中较少见。负相关的例子是：如果 Agent 在某步出错了，外部监督机制（如验证器）介入并纠正，从而降低后续步骤的失败概率。这就是 18.2 节重试策略和 18.3 节 Fallback 机制的价值所在——它们通过引入负相关来打破概率爆炸。

### 2.5 概率爆炸的直观理解：乘积 vs 最小值

另一种理解概率爆炸的方式是：**系统的可靠性由最弱的环节和最长的链路共同决定**。

对于串联系统（Agent 的步骤是典型的串联）：

\[
P(\text{系统成功}) = \prod_{i=1}^{n} P(\text{步骤 i 成功})
\]

这和"短板效应"不同——短板效应看最小值，而串联系统看乘积：

```
短板效应：系统性能 ≈ min(各步骤性能)
串联系统：系统可靠度 = Π(各步骤可靠度)

示例：5 个步骤，可靠度 [0.99, 0.98, 0.97, 0.99, 0.98]
- 短板效应视角：最差的是 0.97，系统性能 ≈ 0.97
- 串联系统视角：可靠度 = 0.99×0.98×0.97×0.99×0.98 ≈ 0.913
```

**串联系统的可靠性总是低于最不可靠的环节。** 这是 Agent 可靠性的第一性原理。

## 三、概率爆炸在 Agent 各环节的具体表现

### 3.1 工具调用中的概率失效

工具调用是 Agent 最常见的概率失效点。以函数调用（Function Calling）为例：

```
步骤分解：
1. 识别需要哪个工具（意图分类）：P(正确) = 0.96
2. 生成工具参数（参数提取）：P(正确) = 0.94  
3. 参数格式符合 API 规范（格式验证）：P(正确) = 0.98
4. 工具执行成功（外部因素）：P(成功) = 0.99

P(工具调用成功) = 0.96 × 0.94 × 0.98 × 0.99 ≈ 0.875
```

仅仅一个工具调用，就有 12.5% 的失败率。如果 Agent 需要调用 3 个工具来完成一个任务：

\[
P(3\text{个工具都成功}) = 0.875^3 \approx 0.670
\]

这就意味着几乎 1/3 的任务会在工具调用环节出问题。

### 3.2 多步推理中的概率退化

对于需要多步推理的任务（如代码生成、数据分析），Agent 的"推理链"本身就是概率性的：

```
Chain-of-Thought 推理：
步骤1: 理解问题 → 步骤2: 分解子问题 → 步骤3: 分析每个子问题 
→ 步骤4: 综合结论 → 步骤5: 格式化输出

推理中间步骤出错 → 最终答案错误（即使最后几步完全正确）
```

这就是为什么**推理链越长，幻觉和错误越严重**——数学上，它就是一个概率退化过程。

### 3.3 级联失败（Cascading Failure）

级联失败是概率爆炸在 Agent 系统中的放大形式。它不是简单的乘法累积，而是指数级放大：

```
正常链路：A → B → C → D（成功率 0.95^4 ≈ 0.814）
级联链路：A错误 → B基于错误前提 → C继续基于错误 → D输出无用结果
```

级联链路中，失败的不仅是当前步骤，还包括对后续步骤的"污染"。实际工程观察表明，**Agent 系统中约 70% 的失败可以追溯到前 3 步的错误**。

## 四、对抗概率爆炸的策略框架

概率爆炸是数学定律，无法消除，只能管理。18 章的后续小节围绕以下 5 条策略展开：

### 4.1 降低单步失败率（p↓）

每步的失败率 \(p\) 越小，\(n\) 步后的总失败率越低。降低 \(p\) 的方法：

- **更好的模型**：GPT-4 在工具调用上可能比开源 7B 模型错误率低 3-5 倍
- **更好的 Prompt Engineering**：结构化 prompt、few-shot examples 可以降低 30-50% 的错误率
- **约束解码**：通过工具调用约束（如 JSON schema 约束）使生成结果一定符合格式要求

### 4.2 缩短链路长度（n↓）

减少 Agent 的步骤数 \(n\) 可以直接降低概率爆炸效应：

- **合并步骤**：将多个小步骤合并为一个更大的步骤（例如：一次生成完整 JSON 而非逐字段生成）
- **并行执行**：将串行步骤改为并行，把串联系统变为混联系统
- **任务粒度调整**：合理设计 Agent 的"原子操作"粒度，不要太细

### 4.3 引入容错机制

在每一步引入检错和纠正机制，将步骤间的关系从"纯串联"变为"带反馈的串联"：

- **重试**（18.2 节）：失败后自动重试，引入多次尝试提高单步成功率
- **Fallback**（18.3 节）：当一种模型/服务失败时切换到备选
- **降级**（18.6 节）：当置信度不足时降低服务质量目标而不是完全失败

### 4.4 提前检测和止损

- **静默失败检测**（18.4 节）：尽早发现"已经出错但还没有 explicit error"的状况
- **幂等性设计**（18.5 节）：确保重复执行不产生副作用，允许"试了再改"

### 4.5 数学视角：如何量化容错收益

以最简单的重试机制为例。假设每步的失败概率为 \(p\)，最多重试 \(k\) 次（总共尝试 \(k+1\) 次），重试之间独立：

\[
P(\text{步骤失败}) = p^{k+1}
\]

这比单次尝试的 \(p\) 指数级下降。举例：

| p | 无重试 | 1 次重试 | 2 次重试 |
|---|--------|---------|---------|
| 10% | 10.0% | 1.0% | 0.1% |
| 20% | 20.0% | 4.0% | 0.8% |
| 30% | 30.0% | 9.0% | 2.7% |

加入 1 次重试后，每步失败率从 5% 降到 0.25%。对于 20 步任务：

- 无重试：\(P(\text{失败}) = 1 - 0.95^{20} \approx 64.2\%\)
- 1 次重试：\(P(\text{失败}) = 1 - (1 - 0.05^2)^{20} \approx 1 - 0.9975^{20} \approx 4.9\%\)

**一次重试就把 64.2% 的失败率降到了 4.9%。** 这就是容错机制对抗概率爆炸的数学力量。

## 五、概率本质对系统设计的深层影响

### 5.1 从"确定性思维"到"概率思维"

接受 Agent 的概率本质意味着系统设计思维的转变：

| 确定性思维 | 概率思维 |
|-----------|---------|
| "这个功能 95% 准确，可以用了" | "每步 95%，10 步后只有 60% 成功率" |
| "失败了就是 Bug" | "失败是概率的必然结果，需要容错" |
| "测试通过了就上线" | "需要持续的监控和指标反馈" |
| "错误处理是锦上添花" | "容错机制是核心架构的一部分" |
| "反正失败了会报错" | "静默失败最危险，需要主动检测" |

### 5.2 概率系统的工程原则

1. **每一层都要防守**：不能只在顶层做容错，每一层（模型调用、工具执行、业务逻辑）都需要自己的容错机制
2. **可观测性是前提**：不了解实际失败概率，就无法做有依据的工程决策
3. **容错本身也有成本**：重试带来延迟，Fallback 带来成本增加，降级带来体验下降——需要在可靠性和成本之间做 trade-off
4. **失败模式的分布服从帕累托法则**：通常 20% 的失败模式导致了 80% 的失败，优先解决高频失败模式

### 5.3 从概率本质看"面试必问题"

回到章节开头的问题——"Agent 是概率系统，你怎么在不确定性中做出可靠的工程设计？"

一个完整的回答应该覆盖以下维度：

1. **认知层面**：理解概率爆炸的数学原理，认识到每一步都是概率性的，接受失败是必然的而非偶然的
2. **防御层面**：构建多层防御——重试（18.2）、Fallback（18.3）、断路器等
3. **检测层面**：监控隐性失败信号（18.4），在错误蔓延前发现问题
4. **恢复层面**：设计幂等操作（18.5），支持从检查点恢复而非从头重跑
5. **降级层面**：确定何时转人工、何时回退到简单但可靠的方案（18.6）
6. **闭环反馈**：从生产数据中学习，持续降低各环节的失败概率

## 关键概念速查

| 术语 | 解释 |
|------|------|
| 条件概率分布 | LLM 的输出不是确定的，而是下一个 token 的概率分布 |
| 概率爆炸（Probability Explosion） | 串联系统中，多步累积导致失败率随步数指数级增长 |
| 串联系统可靠性 | 系统可靠度 = 各步骤可靠度的乘积，总是低于最弱一环 |
| 级联失败（Cascading Failure） | 前一步的错误污染后续步骤，导致错误被放大 |
| 期望成功步数 | 在失败前期望能连续完成的步数 \(E = (1-p)/p\) |
| 步骤相关性 | 步骤之间的依赖关系，正相关会进一步恶化成功概率 |
| 容错收益 | 通过重试等机制将串联系统变为带反馈的系统，指数级降低失败率 |
| 概率思维 vs 确定性思维 | 接受失败必然性 vs 认为失败是异常，两种根本不同的工程范式 |
