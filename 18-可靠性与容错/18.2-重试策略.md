# 18.2 重试策略

> "失败了就重试"——听起来简单，但生产级 Agent 的重试远不止一个 `while` 循环。不合理的重试会把瞬时失败变成系统性崩溃。本章从指数退避到断路器模式，构建完整的重试工程体系。

---

## 一、重试的基本问题

### 1.1 为什么需要重试

Agent 系统中的大多数失败是**瞬时性（Transient）的**，而不是永久性的：

- **网络抖动**：TCP 连接超时，DNS 解析暂时失败
- **服务端限流**：LLM API 返回 429 Too Many Requests 或 529 Overloaded
- **负载波动**：GPU 推理节点暂时过载，响应变慢导致超时
- **分布式一致性问题**：数据复制延迟导致读取暂时不一致

这些失败不需要"修复"，只需要**等待后重试**。

### 1.2 不合理的重试的危害

如果重试不加控制，会造成比不重试更严重的问题：

```
不加控制的重试 →
1. 客户端瞬间发出大量重试请求 → 给服务器造成更大压力
2. 服务器压力增大 → 更多请求失败 → 更多客户端重试
3. 恶性循环 → 系统雪崩（Cascade Failure）
4. 最终所有 Agent 实例都卡在重试循环中 → 系统完全不可用
```

这就是**重试风暴（Retry Storm）**——不合理的重试使局部失败演变为全局崩溃。

### 1.3 重试策略的三要素

一个完备的重试策略由三个核心要素组成：

1. **何时重试**：哪些错误码/异常需要重试，哪些不需要
2. **如何等待**：两次重试之间的等待时间策略
3. **何时停止**：最大重试次数、超时时间、断路器状态

## 二、指数退避（Exponential Backoff）

### 2.1 基本原理

**指数退避**（Exponential Backoff）是指每次重试的等待时间按指数增长的策略。核心思想是：如果服务忙，给它更多时间恢复。

\[
\text{wait\_time} = \text{base\_delay} \times 2^{(\text{attempt} - 1)}
\]

其中：
- `base_delay`：基础延迟（如 1 秒）
- `attempt`：当前重试次数（从 1 开始计数）

### 2.2 添加随机抖动（Jitter）

单纯的指数退避有一个问题：**多个客户端同时重试时，它们的等待时间完全同步**。这会导致"雷鸣般的羊群"（Thundering Herd）问题——所有的重试在完全相同的时间点发起到服务器。

解决方案是添加**随机抖动（Jitter）**：

```python
import random
import time

def wait_with_jitter(base_delay, attempt, jitter_factor=0.5):
    """指数退避 + 随机抖动"""
    delay = base_delay * (2 ** (attempt - 1))
    
    # 全抖动（Full Jitter）：在 [0, delay] 范围内随机
    actual_delay = random.uniform(0, delay * (1 + jitter_factor))
    
    # 等比例抖动（Equal Jitter）：delay ± 50%
    # actual_delay = delay * (1 + jitter_factor * random.uniform(-1, 1))
    
    return actual_delay
```

常见的抖动策略有三种：

| 策略 | 公式 | 特性 |
|------|------|------|
| 无抖动 | \(d \times 2^{n}\) | 确定性强，但可能引发重试风暴 |
| 全抖动（Full Jitter） | \(\text{random}(0, d \times 2^{n})\) | 最平滑的负载分布，推荐 |
| 等比例抖动（Equal Jitter） | \(d \times 2^{n} \times (1 \pm \text{rand})\) | 折中方案 |
| 去相关抖动（Decorrelated Jitter） | \(\text{random}(d, \text{prev\_delay} \times 3)\) | AWS 推荐，适应性强 |

### 2.3 最大延迟上限

指数增长理论上会无限增长，需要设定上限：

```python
def capped_backoff(base_delay, attempt, max_delay=120):
    """带上限的指数退避"""
    delay = base_delay * (2 ** (attempt - 1))
    return min(delay, max_delay)
```

典型配置：
- 首次延迟：1 秒
- 最大延迟：30-120 秒
- 最大重试次数：3-5 次

## 三、最大重试与超时

### 3.1 最大重试次数

始终设置最大重试次数的上限。无限重试可能导致无限延迟和资源泄漏：

```python
MAX_RETRIES = 3

def call_with_retry(agent_step, max_retries=MAX_RETRIES):
    """带最大重试次数的 Agent 步骤调用"""
    last_error = None
    for attempt in range(1, max_retries + 1):
        try:
            return agent_step()
        except TransientError as e:
            last_error = e
            delay = wait_with_jitter(base_delay=1.0, attempt=attempt)
            time.sleep(delay)
        except PermanentError as e:
            # 永久性错误（如认证失败），不重试
            raise
    
    raise MaxRetriesExceededError(f"重试 {max_retries} 次后仍然失败", last_error)
```

### 3.2 超时保护

重试必须配合超时（Timeout）使用。没有超时的重试是危险的：

```python
import asyncio

async def call_with_retry_and_timeout(
    agent_step, 
    max_retries=3, 
    step_timeout=30.0, 
    total_timeout=120.0
):
    """带超时保护和重试的 Agent 步骤调用"""
    start_time = time.time()
    
    for attempt in range(1, max_retries + 1):
        # 检查总超时
        elapsed = time.time() - start_time
        remaining = total_timeout - elapsed
        if remaining <= 0:
            raise TotalTimeoutError("总超时时间已到")
        
        # 步骤级超时（取剩余时间和步骤超时的较小值）
        current_timeout = min(step_timeout, remaining)
        
        try:
            result = await asyncio.wait_for(
                agent_step(), 
                timeout=current_timeout
            )
            return result
        except asyncio.TimeoutError:
            if attempt < max_retries:
                delay = wait_with_jitter(base_delay=1.0, attempt=attempt)
                await asyncio.sleep(delay)
            else:
                raise MaxRetriesExceededError("重试次数用尽，最终超时")
        except TransientError as e:
            if attempt < max_retries:
                delay = wait_with_jitter(base_delay=1.0, attempt=attempt)
                await asyncio.sleep(delay)
            else:
                raise MaxRetriesExceededError(
                    f"重试 {max_retries} 次后仍然失败", e
                )
```

### 3.3 哪些错误应该重试？

重试不是万能药——有些错误重试 100 次也没用。需要区分可重试和不可重试的错误：

```python
def is_retriable(error) -> bool:
    """判断错误是否应该重试"""
    retriable_status_codes = {
        408,   # Request Timeout
        429,   # Too Many Requests
        500,   # Internal Server Error
        502,   # Bad Gateway
        503,   # Service Unavailable
        504,   # Gateway Timeout
        529,   # Overloaded (LLM API 常见)
    }
    
    non_retriable_status_codes = {
        400,   # Bad Request（请求本身有问题）
        401,   # Unauthorized（认证失败，重试也没用）
        403,   # Forbidden（权限不足）
        404,   # Not Found（资源不存在）
        422,   # Unprocessable Entity
    }
    
    if isinstance(error, HTTPStatusError):
        if error.status in retriable_status_codes:
            return True
        if error.status in non_retriable_status_codes:
            return False
    
    # 网络错误通常是可重试的
    if isinstance(error, ConnectionError):
        return True
    
    # LLM 内容审核拒绝（内容违规），重试通常没用
    if isinstance(error, ContentFilterError):
        return False
    
    # 默认：不重试（安全优先）
    return False
```

## 四、断路器模式（Circuit Breaker）

### 4.1 什么是断路器模式？

**断路器模式**（Circuit Breaker Pattern）是一种防止系统反复尝试可能失败的操作的保护机制。它得名于电路中的断路器：当电流过大时自动断开电路，防止损坏设备。

在 Agent 系统中，断路器的作用是：**如果某个外部服务连续失败，停止对该服务的调用，而不是继续浪费时间的重试**。

### 4.2 断路器的三种状态

```
                    ┌──────────────────────────────┐
                    │                              │
                    ▼                              │
              ┌──────────┐     失败次数 > 阈值     │
         ┌───▶│  CLOSED  │─────────────────────────┤
         │    │  (关闭)   │                        │
         │    └──────────┘                        │
         │          │                             │
         │          │ 成功（重置计数器）            │
         │          │                             │
         │          ▼                             │
         │    ┌──────────┐     超时时间到          │
         │    │   OPEN   │◀───────────────────────┘
         │    │  (断开)  │
         │    └──────────┘
         │          │
         │          │ 超时时间到
         │          ▼
         │    ┌──────────┐
         │    │ HALF_OPEN│──── 尝试请求 ──── 成功 ──▶ CLOSED
         └────│ (半开)   │──── 尝试请求 ──── 失败 ──▶ OPEN (重置超时)
              └──────────┘
```

**三种状态的解释**：

| 状态 | 含义 | 行为 |
|------|------|------|
| **CLOSED（关闭）** | 电路正常工作 | 请求正常通过，记录失败次数 |
| **OPEN（断开）** | 电路已断开 | 请求直接失败（Fast Fail），不调用服务 |
| **HALF_OPEN（半开）** | 试探性恢复 | 允许少量请求通过，判断服务是否恢复 |

### 4.3 断路器完整 Python 实现

```python
import time
import threading
from enum import Enum
from dataclasses import dataclass
from typing import Callable, Optional


class CircuitState(Enum):
    CLOSED = "CLOSED"       # 正常，请求可以通过
    OPEN = "OPEN"           # 断开，请求直接失败
    HALF_OPEN = "HALF_OPEN" # 半开，允许试探性请求


@dataclass
class CircuitBreakerConfig:
    """断路器配置"""
    failure_threshold: int = 5          # 连续失败 N 次后断开
    recovery_timeout: float = 30.0      # 断开后等待多久进入 HALF_OPEN
    half_open_max_requests: int = 3     # HALF_OPEN 状态允许的最大请求数
    consecutive_success_to_close: int = 2  # HALF_OPEN 下连续成功 N 次后恢复


class CircuitBreaker:
    """
    断路器实现
    
    用法：
        breaker = CircuitBreaker(name="LLM API", config=CircuitBreakerConfig())
        
        with breaker:
            result = call_llm_api()
    """
    
    def __init__(self, name: str, config: CircuitBreakerConfig = None):
        self.name = name
        self.config = config or CircuitBreakerConfig()
        self.state = CircuitState.CLOSED
        
        # 计数器和时间戳
        self.failure_count = 0
        self.consecutive_success_count = 0
        self.last_failure_time = 0.0
        self.half_open_request_count = 0
        
        # 线程安全
        self._lock = threading.Lock()
        self._half_open_lock = threading.Lock()
    
    def __enter__(self):
        """上下文管理器入口：检查断路器状态"""
        self._check_state()
        if self.state == CircuitState.OPEN:
            elapsed = time.time() - self.last_failure_time
            remaining = self.config.recovery_timeout - elapsed
            raise CircuitBreakerOpenError(
                f"断路器 [{self.name}] 已断开，"
                f"还需 {remaining:.1f}s 恢复"
            )
        if self.state == CircuitState.HALF_OPEN:
            if not self._try_acquire_half_open():
                raise CircuitBreakerHalfOpenLimitedError(
                    f"断路器 [{self.name}] 半开状态，"
                    f"请求被限流"
                )
        return self
    
    def __exit__(self, exc_type, exc_val, exc_tb):
        """上下文管理器退出：记录成功或失败"""
        if exc_type is None:
            # 请求成功
            self._on_success()
        elif exc_val and self._is_retriable_error(exc_val):
            # 可重试的错误 → 记录失败
            self._on_failure()
        # 不可重试的错误→不记录到断路器（避免把参数错误算成服务不可用）
        return False  # 不抑制异常
    
    def _check_state(self):
        """检查是否需要从 OPEN 切换到 HALF_OPEN"""
        if self.state == CircuitState.OPEN:
            elapsed = time.time() - self.last_failure_time
            if elapsed >= self.config.recovery_timeout:
                with self._lock:
                    # 双重检查
                    if self.state == CircuitState.OPEN:
                        self.state = CircuitState.HALF_OPEN
                        self.half_open_request_count = 0
                        self.consecutive_success_count = 0
                        print(f"断路器 [{self.name}]: OPEN → HALF_OPEN")
    
    def _try_acquire_half_open(self) -> bool:
        """HALF_OPEN 状态下获取请求配额"""
        with self._half_open_lock:
            if self.half_open_request_count < self.config.half_open_max_requests:
                self.half_open_request_count += 1
                return True
            return False
    
    def _on_success(self):
        """处理请求成功"""
        if self.state == CircuitState.HALF_OPEN:
            with self._lock:
                self.consecutive_success_count += 1
                if self.consecutive_success_count >= \
                        self.config.consecutive_success_to_close:
                    self.state = CircuitState.CLOSED
                    self.failure_count = 0
                    self.consecutive_success_count = 0
                    print(f"断路器 [{self.name}]: HALF_OPEN → CLOSED")
        elif self.state == CircuitState.CLOSED:
            # CLOSED 状态下成功→重置失败计数器
            self.failure_count = 0
    
    def _on_failure(self):
        """处理请求失败"""
        with self._lock:
            if self.state == CircuitState.HALF_OPEN:
                # 半开状态下失败→立即回到 OPEN
                self.state = CircuitState.OPEN
                self.last_failure_time = time.time()
                self.half_open_request_count = 0
                self.consecutive_success_count = 0
                print(f"断路器 [{self.name}]: HALF_OPEN → OPEN")
            
            elif self.state == CircuitState.CLOSED:
                self.failure_count += 1
                if self.failure_count >= self.config.failure_threshold:
                    self.state = CircuitState.OPEN
                    self.last_failure_time = time.time()
                    print(f"断路器 [{self.name}]: CLOSED → OPEN "
                          f"(连续失败 {self.failure_count} 次)")
    
    def _is_retriable_error(self, error: Exception) -> bool:
        """判断是否为可重试错误"""
        # 这里应该集成 18.2.3 节的 is_retriable 逻辑
        return True
    
    def force_open(self):
        """手动断开电路（用于运维场景）"""
        with self._lock:
            self.state = CircuitState.OPEN
            self.last_failure_time = time.time()
    
    def force_close(self):
        """手动恢复电路"""
        with self._lock:
            self.state = CircuitState.CLOSED
            self.failure_count = 0
            self.consecutive_success_count = 0

    @property
    def is_available(self) -> bool:
        """判断服务是否可用"""
        if self.state == CircuitState.CLOSED:
            return True
        if self.state == CircuitState.HALF_OPEN:
            return self.half_open_request_count < \
                   self.config.half_open_max_requests
        return False


class CircuitBreakerOpenError(Exception):
    """断路器断开时抛出的异常"""
    pass


class CircuitBreakerHalfOpenLimitedError(Exception):
    """断路器半开时请求被限流"""
    pass


class MaxRetriesExceededError(Exception):
    """超过最大重试次数"""
    pass
```

### 4.4 断路器 + 重试：组合策略

在实际 Agent 系统中，断路器和重试应该协同工作，而不是互斥：

```python
def agent_call_with_circuit_breaker_and_retry(
    call_fn: Callable,
    circuit_breaker: CircuitBreaker,
    max_retries: int = 3,
    base_delay: float = 1.0,
):
    """断路器保护下的重试策略"""
    last_error = None
    
    for attempt in range(1, max_retries + 1):
        try:
            with circuit_breaker:
                return call_fn()
        except CircuitBreakerOpenError as e:
            # 断路器断开→快速失败，不要重试
            raise ServiceUnavailableError(
                f"服务 [{circuit_breaker.name}] 当前不可用"
            ) from e
        except CircuitBreakerHalfOpenLimitedError:
            # 半开被限流→等待后重试
            delay = wait_with_jitter(base_delay, attempt)
            time.sleep(delay)
        except TransientError as e:
            last_error = e
            if attempt < max_retries:
                delay = wait_with_jitter(base_delay, attempt)
                time.sleep(delay)
    
    raise MaxRetriesExceededError(
        f"重试 {max_retries} 次后仍然失败", last_error
    )
```

### 4.5 断路器参数的工程调优

断路器有 4 个关键参数，需要根据实际数据调整：

| 参数 | 推荐值 | 调优原则 |
|------|--------|---------|
| `failure_threshold` | 5-10 | 太大会容忍过多失败，太小会过于敏感 |
| `recovery_timeout` | 30-120s | 取决于服务恢复的典型时间 |
| `half_open_max_requests` | 1-5 | 试探请求数，太多可能导致恢复期间过载 |
| `consecutive_success_to_close` | 2-5 | 太少会导致状态频繁切换（flapping） |

**调优方法论**：
1. 先让断路器处于"只记录不执行"的观察模式，收集失败模式数据
2. 根据 P99 恢复时间设定 `recovery_timeout`
3. 根据正常负载下的平均失败率设定 `failure_threshold`
4. 上线后持续监控"断路器跳闸率"——如果从未跳闸，说明阈值太高；如果频繁跳闸，说明有系统性问题需要解决

## 五、Agent 场景的特殊重试需求

### 5.1 LLM 特有的可重试错误

LLM API 的重试策略需要考虑模型特有的错误类型：

```python
LLM_RETRY_CONFIG = {
    # 限流类错误：等待后重试
    429: {"retry": True, "strategy": "exponential_backoff", "priority": "high"},
    # 过载类错误：等待较长时间后重试
    529: {"retry": True, "strategy": "long_backoff", "base_delay": 5.0, "priority": "high"},
    # 服务端错误：标准指数退避
    500: {"retry": True, "strategy": "exponential_backoff"},
    502: {"retry": True, "strategy": "exponential_backoff"},
    503: {"retry": True, "strategy": "exponential_backoff"},
    # 内容审核拒绝：不重试
    400: {"retry": False, "sub_code_check": "content_filter"},
    # 认证错误：不重试
    401: {"retry": False},
    403: {"retry": False},
}
```

### 5.2 Agent 步骤重试的特殊性

Agent 的步骤重试不同于普通 API 重试——重试时需要**重置上下文**：

```python
def retry_agent_step(agent, step_input, max_retries=3):
    """
    Agent 步骤重试
    
    注意：每次重试需要重置 LLM 的上下文状态，
    避免"刚刚失败了"的信息污染新的生成
    """
    for attempt in range(1, max_retries + 1):
        try:
            # 每次重试用干净的上下文
            clean_context = deepcopy(step_input.context)
            result = agent.execute_step(
                step_input.task, 
                context=clean_context
            )
            return result
        except AgentStepError as e:
            if attempt == max_retries:
                raise
            delay = wait_with_jitter(1.0, attempt)
            time.sleep(delay)
```

### 5.3 语义重试

对于 Agent 系统，有一类特殊的重试——**语义重试**：模型的输出格式正确、没有报错，但内容不符合预期（如产生了幻觉内容）。这种重试不是基于异常，而是基于输出验证：

```python
def semantic_retry(agent, task, max_attempts=3, validator=None):
    """基于语义验证的重试"""
    validator = validator or default_validator
    
    for attempt in range(1, max_attempts + 1):
        result = agent.run(task)
        
        # 验证输出质量
        validation_result = validator(result)
        if validation_result.passed:
            return result
        
        # 如果验证失败，更新 prompt 提示上一轮的不足
        task.update_prompt(
            f"上一轮生成的答案存在以下问题：{validation_result.reasons}\n"
            f"请修正后重新生成。"
        )
    
    # 所有尝试都失败→返回最佳结果（带降级标记）
    return DegradedResult(
        result=result,
        confidence=0.3,
        degradation_reason="语义重试次数用尽"
    )
```

## 关键概念速查

| 术语 | 解释 |
|------|------|
| 指数退避（Exponential Backoff） | 每次重试等待时间按指数增长（1s→2s→4s→8s...） |
| 随机抖动（Jitter） | 在退避时间上添加随机偏移，防止重试风暴 |
| 重试风暴（Retry Storm） | 大量客户端同时重试导致服务崩溃的恶性循环 |
| 断路器模式（Circuit Breaker） | 连续失败 N 次后自动断开，定期试探恢复 |
| CLOSED → OPEN → HALF_OPEN | 断路器的三种状态：正常→断开→半开试探 |
| Fast Fail（快速失败） | 断路器 OPEN 状态下直接拒绝请求，不等待 |
| 语义重试 | 基于输出内容质量（而非异常）触发的重试 |
| 429 Too Many Requests | 客户端请求速率超过服务端限制（限流） |
| 529 Overloaded | LLM API 特有的服务过载错误码 |
