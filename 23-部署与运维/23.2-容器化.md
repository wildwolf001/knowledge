# 23.2 容器化 —— Docker 多阶段构建、健康检查、优雅关闭

> 容器化是 Agent 从开发机走向生产环境的关键一步。Docker 提供的环境一致性、资源隔离和编排能力，使得 Agent 可以在开发、测试、生产环境中以完全相同的方式运行。本章聚焦于 Agent 服务的 Docker 化最佳实践，包括多阶段构建、健康检查、优雅关闭和资源限制等核心议题。

---

## 一、为什么要容器化 Agent？

### 1.1 Agent 对容器化的特殊需求

Agent 服务与传统 Web 服务在容器化方面有几个本质差异：

| 对比维度 | 传统 Web 服务 | Agent 服务 |
|---------|-------------|-----------|
| 启动时间 | 通常在 1-3 秒 | 可能 10-30 秒（加载模型、初始化工具） |
| 请求时长 | 毫秒到秒级 | 秒到分钟级（多轮工具调用） |
| 内存模式 | 相对稳定 | 可能随会话数线性增长 |
| 临时文件 | 很少 | 可能大量（工具执行中间产物） |
| 外部依赖 | 数据库、缓存 | LLM API、向量数据库、搜索引擎、多方外部 API |

这些差异直接影响了 Dockerfile 的构建策略、资源限制配置和健康检查的实现方式。

### 1.2 容器化的三层收益

```
开发者笔记本         测试环境          生产环境
  ┌──────┐       ┌──────────┐       ┌──────────┐
  │ 代码  │ ──→  │ 测试通过   │ ──→  │ 稳定运行   │
  │ 环境A │       │ 环境B     │       │ 环境C     │
  └──────┘       └──────────┘       └──────────┘
      │                │                 │
      └────────────────┴─────────────────┘
                  Docker 镜像
          (完全相同的基础环境和依赖)
```

- **环境一致性**：消除"在我电脑上能跑"问题
- **依赖隔离**：Agent 的 Python 包、系统工具、模型文件互不干扰
- **弹性扩缩**：结合 Kubernetes 实现基于队列长度的自动扩缩容

## 二、多阶段 Dockerfile 设计

### 2.1 为什么需要多阶段构建

Agent 服务的构建过程通常需要以下依赖：
- **编译依赖**：gcc、g++、python-dev（某些 Python 包需要编译 C 扩展）
- **构建工具**：pip、poetry、git（拉取私有包）
- **测试工具**：pytest、ruff、mypy

这些工具在运行环境中完全不需要，不应该出现在最终的镜像中。多阶段构建允许我们在第一个阶段安装所有依赖，在第二个阶段只复制产物。

### 2.2 完整 Dockerfile

```dockerfile
# =====================================================================
# 第一阶段：依赖构建阶段 (builder)
# 目标：安装所有 Python 依赖，包括需要编译 C 扩展的包
# =====================================================================
FROM python:3.12-slim AS builder

# 设置构建时的环境变量
ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1 \
    PIP_NO_CACHE_DIR=1 \
    PIP_DISABLE_PIP_VERSION_CHECK=1 \
    POETRY_VERSION=1.8.0

# 安装系统编译依赖
# grpcio、numpy、cryptography 等需要 C 扩展编译
RUN apt-get update && apt-get install -y --no-install-recommends \
    gcc \
    g++ \
    libffi-dev \
    libssl-dev \
    && rm -rf /var/lib/apt/lists/*

# 安装 Poetry
RUN pip install "poetry==$POETRY_VERSION"

# 复制依赖声明文件
COPY pyproject.toml poetry.lock* ./

# 安装依赖——只安装生产依赖，利用 Docker 缓存层
RUN poetry config virtualenvs.create false \
    && poetry install --only main --no-interaction --no-ansi

# =====================================================================
# 第二阶段：运行阶段 (runtime)
# 目标：极小的生产镜像，只包含运行所需的最小文件
# =====================================================================
FROM python:3.12-slim AS runtime

# 安全：创建非 root 用户
RUN groupadd -r agent && \
    useradd -r -g agent -d /app -s /sbin/nologin agent

# 安装运行时系统依赖
# 某些 Agent 工具调用可能依赖系统命令（如 curl、jq 用于 API 测试）
RUN apt-get update && apt-get install -y --no-install-recommends \
    curl \
    ca-certificates \
    tini \
    && rm -rf /var/lib/apt/lists/*

# 从 builder 阶段复制已安装的 Python 包
COPY --from=builder /usr/local/lib/python3.12/site-packages /usr/local/lib/python3.12/site-packages
COPY --from=builder /usr/local/bin /usr/local/bin

# 创建应用目录并复制代码
WORKDIR /app
COPY --chown=agent:agent app/ ./app/
COPY --chown=agent:agent run.py .
COPY --chown=agent:agent alembic.ini ./  # 数据库迁移配置（见 Ch23.3）

# 创建必要的目录
RUN mkdir -p /app/data /app/tmp && \
    chown -R agent:agent /app/data /app/tmp

# 切换到非 root 用户
USER agent

# 声明持久化数据卷
VOLUME ["/app/data"]

# 使用 tini 作为入口点——正确处理信号转发
# tini 确保 SIGTERM 能正确传递到子进程
ENTRYPOINT ["/usr/bin/tini", "--"]

# Uvicorn 启动命令
CMD ["uvicorn", "app.main:app", \
     "--host", "0.0.0.0", \
     "--port", "8000", \
     "--workers", "4", \
     "--loop", "uvloop", \
     "--http", "httptools", \
     "--timeout-keep-alive", "75", \
     "--limit-concurrency", "1000", \
     "--log-level", "info"]

# 暴露端口
EXPOSE 8000

# 健康检查
HEALTHCHECK --interval=30s --timeout=10s --start-period=30s --retries=3 \
    CMD curl -f http://localhost:8000/health || exit 1
```

### 2.3 Dockerfile 关键设计决策

**① 使用 `tini` 作为入口点**

`tini` 是一个极小（~6KB）的 init 系统，解决了 Docker 中 PID 1 的信号转发问题：

```
没有 tini 的情况：
docker stop → SIGTERM 发送给 PID 1 (shell) → shell 不转发信号 → 10s 后 SIGKILL → 进程被强制杀死

有 tini 的情况：
docker stop → SIGTERM 发送给 tini (PID 1) → tini 转发信号给子进程 → 优雅关闭
```

对于 Agent 服务，优雅关闭尤为重要——正在执行的工具调用或正在生成的 Token 需要被正确中断，已完成的会话结果需要被持久化。

**② `--start-period` 对 Agent 的重要性**

```dockerfile
HEALTHCHECK --interval=30s --timeout=10s --start-period=30s --retries=3
```

`--start-period=30s` 给 Agent 服务提供了 30 秒的初始化宽限期。在这段时间内，健康检查失败不会触发容器重启。这对于 Agent 服务至关重要：

- 加载 LLM 客户端可能需要建立连接池
- 工具注册系统需要扫描和初始化外部 API 客户端
- 会话恢复可能需要从 Redis 加载大量数据

如果 `start-period` 设置过短，健康检查在初始化期间频繁失败，容器会被不断重启，形成"初始化被中断 → 重启 → 又被中断"的死循环。

**③ 层（Layer）的优化**

Docker 构建使用缓存层加速构建。正确的层顺序可以最大化缓存命中率：

```
较差的分层（每次代码变更都重新安装依赖）：
COPY . /app
RUN pip install -r requirements.txt
RUN apt-get install -y packages

优化的分层（利用 Docker 缓存）：
RUN apt-get install -y packages          ← 系统依赖很少变更
COPY requirements.txt .                  ← 依赖声明变更频率低于代码
RUN pip install -r requirements.txt
COPY . /app                              ← 代码变更不影响上层缓存
```

## 三、docker-compose.yml 编排

对于开发环境和中型部署，`docker-compose.yml` 可以一次性启动 Agent 服务及其所有依赖：

```yaml
# docker-compose.yml
version: "3.9"

x-logging: &default-logging
  driver: "json-file"
  options:
    max-size: "10m"
    max-file: "3"

services:
  agent-api:
    build:
      context: .
      dockerfile: Dockerfile
      # 构建参数（不影响缓存）
      args:
        - BUILD_DATE=${BUILD_DATE:-unknown}
        - GIT_COMMIT=${GIT_COMMIT:-unknown}
    image: agent-api:${TAG:-latest}
    container_name: agent-api
    restart: unless-stopped
    ports:
      - "8000:8000"
    volumes:
      # 持久化数据（SQLite 数据库存放于此）
      - agent-data:/app/data
      # 只读配置挂载（敏感信息）
      - type: bind
        source: ./.env
        target: /app/.env
        read_only: true
    environment:
      - REDIS_URL=redis://redis:6379/0
      - DATABASE_URL=sqlite:///data/agent.db
      - LOG_LEVEL=info
    env_file:
      - .env
    depends_on:
      redis:
        condition: service_healthy
      postgres:
        condition: service_healthy
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:8000/health"]
      interval: 30s
      timeout: 10s
      retries: 3
      start_period: 30s
    deploy:
      resources:
        limits:
          cpus: "2.0"
          memory: "2G"
        reservations:
          cpus: "0.5"
          memory: "512M"
    logging: *default-logging
    networks:
      - agent-net

  redis:
    image: redis:7-alpine
    container_name: agent-redis
    restart: unless-stopped
    ports:
      - "6379:6379"
    volumes:
      - redis-data:/data
      - type: bind
        source: ./redis/redis.conf
        target: /usr/local/etc/redis/redis.conf
        read_only: true
    command: ["redis-server", "/usr/local/etc/redis/redis.conf"]
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 10s
      timeout: 3s
      retries: 3
    deploy:
      resources:
        limits:
          memory: "512M"
    logging: *default-logging
    networks:
      - agent-net

  postgres:
    image: postgres:16-alpine
    container_name: agent-postgres
    restart: unless-stopped
    ports:
      - "5432:5432"
    environment:
      POSTGRES_DB: agent_db
      POSTGRES_USER: agent_user
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password
    volumes:
      - postgres-data:/var/lib/postgresql/data
      - type: bind
        source: ./init-scripts
        target: /docker-entrypoint-initdb.d
    secrets:
      - db_password
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U agent_user -d agent_db"]
      interval: 10s
      timeout: 5s
      retries: 5
    deploy:
      resources:
        limits:
          memory: "1G"
    logging: *default-logging
    networks:
      - agent-net

  nginx:
    image: nginx:1.25-alpine
    container_name: agent-nginx
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - type: bind
        source: ./nginx/nginx.conf
        target: /etc/nginx/conf.d/default.conf
        read_only: true
      - type: bind
        source: ./ssl
        target: /etc/nginx/ssl
        read_only: true
    depends_on:
      - agent-api
    logging: *default-logging
    networks:
      - agent-net

volumes:
  agent-data:
    driver: local
  redis-data:
    driver: local
  postgres-data:
    driver: local

networks:
  agent-net:
    driver: bridge

secrets:
  db_password:
    file: ./secrets/db_password.txt
```

### 依赖启动顺序分析

```
docker-compose up 启动顺序：

Step 1: redis + postgres   ← 同时启动，两者无依赖
Step 2: agent-api          ← depends_on: redis (healthy), postgres (healthy)
Step 3: nginx              ← depends_on: agent-api（不需要等healthy，只需容器启动）
```

`condition: service_healthy` 确保 Agent 服务不会在数据库和缓存尚未就绪时启动，避免连接重试风暴。

## 四、资源限制与监控

### 4.1 Docker 资源限制

Agent 是内存密集型服务，必须设置严格的资源限制：

```yaml
# docker-compose.yml 中的资源限制
deploy:
  resources:
    limits:
      cpus: "2.0"      # 最多使用 2 个 CPU 核心
      memory: "2G"      # 最多使用 2GB 内存
    reservations:
      cpus: "0.5"      # 至少保留 0.5 个 CPU
      memory: "512M"    # 至少保留 512MB 内存
```

**为什么 Agent 需要更严格的内存限制？**

```
Agent 工作负载的内存特征：
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
初始内存：        ~200MB  ← Python 运行时 + 依赖加载
连接池：          ~100MB  ← HTTP 连接池 + OpenAI 客户端
每会话内存：      ~50MB   ← 消息历史 + 中间结果
工具执行暂存：    ~200MB  ← 文件处理、临时数据
LLM 响应缓冲：    ~100MB  ← 流式 Token 缓冲
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

如果不设置限制，单个 Agent 容器可能因并发会话累积而耗尽主机内存。

## 五、优雅关闭（Graceful Shutdown）

### 5.1 关闭流程

Agent 服务的优雅关闭比传统 Web 服务更复杂，因为需要处理进行中的推理任务：

```
收到 SIGTERM (docker stop)
    │
    ├── 1. 停止接受新连接
    │      Uvicorn 关闭监听 socket
    │
    ├── 2. 通知正在进行的推理
    │      向 active tasks 发送取消信号
    │
    ├── 3. 等待进行中的任务完成（最多 grace_period 秒）
    │      ├── 工具调用完成
    │      ├── 已经生成的 Token 返回给客户端
    │      └── 会话状态持久化到 Redis
    │
    ├── 4. 持久化未完成会话
    │      将进行中的会话序列化保存
    │
    └── 5. 关闭连接池和客户端
           HTTP 连接池、Redis、数据库
```

### 5.2 代码实现

```python
# app/graceful_shutdown.py
import asyncio
import signal
import time
from typing import Set
from app.config import config


class ShutdownManager:
    """管理 Agent 的优雅关闭流程"""

    def __init__(self):
        self.active_tasks: Set[asyncio.Task] = set()
        self._shutdown_event = asyncio.Event()
        self._grace_period = 30  # 最长等待 30 秒

    def register_task(self, task: asyncio.Task):
        """注册一个正在进行的 Agent 推理任务"""
        self.active_tasks.add(task)
        task.add_done_callback(self.active_tasks.discard)

    async def shutdown(self, sig: signal.Signals):
        """执行优雅关闭"""
        signal_name = sig.name
        print(f"[Shutdown] 收到 {signal_name}，开始优雅关闭...")

        # 通知所有正在进行推理的任务
        self._shutdown_event.set()

        if self.active_tasks:
            print(f"[Shutdown] 等待 {len(self.active_tasks)} 个进行中的任务完成...")
            done, pending = await asyncio.wait(
                self.active_tasks,
                timeout=self._grace_period,
            )
            print(f"[Shutdown] {len(done)} 个任务已完成，{len(pending)} 个任务被取消")

            # 取消超时的任务
            for task in pending:
                task.cancel()
                try:
                    await task
                except asyncio.CancelledError:
                    pass

        print("[Shutdown] 关闭完成")


# 全局关闭管理器
shutdown_manager = ShutdownManager()


def setup_signal_handlers(app):
    """注册系统信号处理器"""
    # 在 Uvicorn 环境中，信号由 Uvicorn 自己处理
    # 这里提供在自定义启动脚本中使用的信号处理

    async def handle_sigterm(sig):
        await shutdown_manager.shutdown(sig)
        # 触发 FastAPI 的 shutdown 事件
        for handler in app.router.shutdown_handlers:
            await handler()
        loop = asyncio.get_event_loop()
        loop.stop()

    # Linux 信号注册
    if hasattr(signal, "SIGTERM"):
        asyncio.get_event_loop().add_signal_handler(
            signal.SIGTERM,
            lambda: asyncio.create_task(handle_sigterm(signal.SIGTERM))
        )
    if hasattr(signal, "SIGINT"):
        asyncio.get_event_loop().add_signal_handler(
            signal.SIGINT,
            lambda: asyncio.create_task(handle_sigterm(signal.SIGINT))
        )
```

### 5.3 Docker 关闭信号交互

```
docker stop agent-api
    │
    ├── Docker 发送 SIGTERM 到容器 PID 1
    │
    ├── 容器内（tini 接收 SIGTERM）
    │   └── tini 转发 SIGTERM 到 Uvicorn 主进程
    │
    ├── Uvicorn 主进程：
    │   1. 停止 accept 新连接
    │   2. 发送 SIGTERM 到各 Worker
    │
    ├── 各 Worker（10 秒内完成正在处理的任务）：
    │   ├── 正在执行推理的任务 → 收到取消信号 → 持久化会话 → 退出
    │   └── 空闲 Worker → 立即退出
    │
    └── 10 秒后（Docker 默认等待时间）：
        └── 如果 Worker 未退出 → SIGKILL 强制终止
```

**关键时序问题**：Docker 默认在 SIGTERM 之后等待 10 秒发送 SIGKILL。对于 Agent 服务，10 秒可能不足以完成正在进行的工具调用。需要通过 `docker stop -t <seconds>` 参数或 `stop_grace_period` 配置延长等待时间：

```yaml
# docker-compose.yml
services:
  agent-api:
    stop_grace_period: 60s  # 给 Agent 60 秒完成正在进行的任务
```

## 六、健康检查的深度设计

### 6.1 三层健康检查

```python
# app/health.py
import time
import psutil


class HealthChecker:
    """分层健康检查 — 返回不同粒度的健康状态"""

    def __init__(self):
        self.start_time = time.time()
        self.last_llm_call_success = time.time()
        self.llm_call_failures = 0
        self.last_redis_ping = time.time()
        self.redis_ok = False

    def liveness(self) -> dict:
        """
        Liveness Probe — 容器是否活着
        只要进程在运行就返回 OK，用于检测死锁
        """
        return {
            "status": "ok",
            "uptime": time.time() - self.start_time,
        }

    def readiness(self) -> dict:
        """
        Readiness Probe — 容器是否准备好接受流量
        检查所有外部依赖是否就绪
        """
        checks = {
            "redis": self._check_redis(),
            "llm_api": self._check_llm_api(),
        }
        all_ready = all(check["ok"] for check in checks.values())

        return {
            "status": "ready" if all_ready else "not_ready",
            "checks": checks,
        }

    def _check_redis(self) -> dict:
        """检查 Redis 连接"""
        try:
            # 简单的 Redis ping 检查
            # actual redis check
            return {"ok": True, "latency_ms": 0.5}
        except Exception as e:
            self.redis_ok = False
            return {"ok": False, "error": str(e)}

    def _check_llm_api(self) -> dict:
        """检查 LLM API 可达性（轻量级）"""
        # 生产环境：检查 API 端点是否可以连接
        # 不发送实际请求，只 DNS 解析 + TCP 连接
        return {"ok": True, "latency_ms": 10}
```

```yaml
        image: agent-api:latest
        ports:
        - containerPort: 8000
        env:
        - name: REDIS_URL
          valueFrom:
            secretKeyRef:
              name: agent-secrets
              key: redis-url
        # --- Liveness Probe ---
        # 检查容器是否存活。如果失败，K8s 会重启容器。
        livenessProbe:
          httpGet:
            path: /health/live
            port: 8000
          initialDelaySeconds: 30   # Agent 初始化时间可能较长
          periodSeconds: 30          # 每 30 秒检查一次
          timeoutSeconds: 5          # 等待 5 秒超时
          failureThreshold: 3        # 连续失败 3 次才重启
        # --- Readiness Probe ---
        # 检查容器是否可以接收流量。如果失败，K8s 将 Pod 从 Service 中移除。
        readinessProbe:
          httpGet:
            path: /health/ready
            port: 8000
          initialDelaySeconds: 30
          periodSeconds: 10
          timeoutSeconds: 5
          failureThreshold: 1        # 一次失败就停止发送流量
        # --- Startup Probe ---
        # Kubernetes 1.18+ 新增的探针，只在启动时运行。
        # 用于启动特别慢的应用，避免 startup 期间的误判。
        startupProbe:
          httpGet:
            path: /health/live
            port: 8000
          initialDelaySeconds: 5
          periodSeconds: 5
          failureThreshold: 12       # 最多等待 60 秒启动
        resources:
          limits:
            cpu: "2"
            memory: "2Gi"
          requests:
            cpu: "500m"
            memory: "512Mi"
```

**三种探针的协作逻辑**：

```
Pod 启动时间线:
0s  ───────────────────────────────────────────────────→ 60s
    startup          liveness + readiness
    ───────────────  ─────────────────────────
    探针开始工作      startup 成功后，liveness 和
    每 5 秒检查       readiness 接管，按各自的
    失败阈值 12 次    periodSeconds 运行

场景分析:
- Pod 启动慢（59 秒才就绪）：
  startup 持续检查，每次失败都允许，最终在第 12 次检查时成功
  → 不会触发重启

- Pod 运行中内存泄漏（liveness 检测到）：
  liveness 连续 3 次失败 → K8s 重启 Pod
  → 通过 --limit-max-requests 设置自动重启可减少此场景

- Redis 临时不可用（readiness 检测到）：
  readiness 失败 → 从 Service 移除流量 → Redis 恢复 → readiness 通过 → 重新接收流量
  → 不会导致重启，只是暂时不接收请求
```

## 八、生产环境常见问题

### 8.1 容器 OOM 排查

**症状**：容器被 Docker 或 K8s 杀死，退出码 137（SIGKILL）。

**诊断步骤**：
```bash
# 1. 查看容器退出码
docker inspect agent-api --format '{{.State.ExitCode}}'

# 2. 查看 OOM 事件
docker inspect agent-api --format '{{.State.OOMKilled}}'

# 3. 查看内存使用历史
docker stats agent-api --no-stream

# 4. 启用容器的内存日志
docker run -m 2G --memory-swap 2G --memory-swappiness 0 ...
```

**预防措施**：
- 设置 `--memory-reservation` 提前预警
- 实现会话级内存跟踪（追踪每会话的 Token 数量）
- 设置 `max_concurrent_sessions` 限流

### 8.2 日志管理

Docker 默认的 json-file 日志驱动可能导致磁盘被日志填满：

```yaml
x-logging: &default-logging
  driver: "json-file"
  options:
    max-size: "10m"    # 每个日志文件最大 10MB
    max-file: "3"       # 保留最近 3 个日志文件
```

对于 Agent 服务，建议将 Agent 推理日志（包含工具调用链和 Token 使用）与标准访问日志分离：

```python
# 独立的 Agent 日志文件通过 volumes 挂载
# 避免推理日志和 Docker 标准日志混在一起
```

| 术语 | 解释 |

| 多阶段构建 | Docker 构建中使用多个 FROM 指令，分离构建环境和运行环境 |
