# 23.4 缓存层 —— Redis 用于 Session Cache / Embedding Cache / Rate Limiter

> 随着 Agent 服务从单用户原型演进到多用户生产系统，缓存层从"可选项"变成了"必需品"。Redis 在 Agent 体系中扮演三个关键角色：会话状态的共享存储、Embedding 向量的高速缓存、以及 API 调用频率的精确控制。本节从这三个场景出发，给出完整的 Redis 配置、数据结构和最佳实践。

---

## 一、Redis 在 Agent 体系中的角色

### 1.1 Agent 为什么需要 Redis？

Agent 的运行时特征决定了它对缓存层的强烈需求：

**特征一：有状态的分布式部署**
Agent 服务在多实例（多 Worker / 多 Pod）部署时，每个请求可能落在不同的实例上。如果会话状态存储在本地内存中，用户会在不同的请求之间丢失上下文。Redis 作为所有 Agent 实例都能访问的共享状态层，解决了两大问题：
- 会话连续性：同一用户的多次请求，无论由哪个 Worker 处理，都可以访问相同的会话历史
- 实例无损：任意 Worker 宕机不影响会话状态，其他 Worker 可以无缝接管

**特征二：计算密集型操作需要结果复用**
Agent 的操作中有大量可以被缓存的计算：
- Embedding 向量化：相同文本反复调用 Embedding API（成本高、延迟高）
- LLM 推理结果：在特定场景下（如确定性工具调用），相同输入可以复用缓存结果
- 检索结果：RAG 检索对同一问题的检索结果可以缓存一段时间

**特征三：多用户场景下的资源保护**
多用户环境下，单个用户（或恶意的批量请求）可能耗尽系统的所有资源：
- LLM API 配额：按 Token 计费，需要精确控制
- 数据库连接池：防止缓存穿透导致数据库过载
- 工具调用频率：某些外部 API 有严格的调用限制

## 二、Session Cache：分布式会话共享

### 2.1 会话数据结构设计

```python
# app/cache/session_cache.py
import json
import hashlib
import time
from typing import Optional

import redis.asyncio as redis
from app.config import config


class SessionCache:
    """
    基于 Redis 的 Agent 会话缓存。

    设计原则：
    - 会话有 TTL：超过 TTL 自动过期，避免内存泄漏
    - 写穿透（Write-Through）：每次更新都同时写入缓存和数据库
    - 读时填充（Read-Through）：缓存未命中时从数据库加载
    """

    def __init__(self, redis_client: redis.Redis):
        self.redis = redis_client
        self.ttl = config.session_ttl  # 默认 3600 秒

    # ========== 会话元数据 ==========

    async def get_session_meta(self, session_id: str) -> Optional[dict]:
        """获取会话元数据"""
        key = f"session:{session_id}:meta"
        data = await self.redis.get(key)
        if data:
            return json.loads(data)
        return None

    async def set_session_meta(self, session_id: str, meta: dict):
        """设置会话元数据，同时刷新 TTL"""
        key = f"session:{session_id}:meta"
        await self.redis.setex(key, self.ttl, json.dumps(meta, default=str))

    # ========== 消息历史 ==========

    async def get_messages(self, session_id: str) -> list[dict]:
        """获取会话的消息历史"""
        key = f"session:{session_id}:msgs"
        data = await self.redis.get(key)
        if data:
            return json.loads(data)
        return []

    async def append_message(self, session_id: str, message: dict):
        """追加消息到会话历史（使用 Lua 脚本保证原子性）"""
        key = f"session:{session_id}:msgs"
        # Lua 脚本：原子地追加消息并刷新 TTL
        lua_script = """
            local key = KEYS[1]
            local ttl = ARGV[1]
            local message = ARGV[2]

            -- 获取现有消息列表，追加新消息
            local existing = redis.call('GET', key)
            if existing then
                local messages = cjson.decode(existing)
                table.insert(messages, cjson.decode(message))
                redis.call('SETEX', key, ttl, cjson.encode(messages))
            else
                redis.call('SETEX', key, ttl, '[' .. message .. ']')
            end
            return 1
        """
        # 注意：Redis 7.0+ 内置了 cjson，但 Lua 脚本方式更通用
        # 这里使用更简单的 Python 级操作
        messages = await self.get_messages(session_id)
        messages.append(message)
        await self.redis.setex(key, self.ttl, json.dumps(messages, default=str))
        return len(messages)

    async def clear_session(self, session_id: str):
        """清除会话的所有缓存"""
        keys = [
            f"session:{session_id}:meta",
            f"session:{session_id}:msgs",
        ]
        await self.redis.delete(*keys)

    async def touch_session(self, session_id: str):
        """刷新会话的 TTL（在 Agent 推理过程中定期调用，防止会话过期）"""
        keys = [
            f"session:{session_id}:meta",
            f"session:{session_id}:msgs",
        ]
        for key in keys:
            await self.redis.expire(key, self.ttl)
```

```python
# app/middleware/session.py
from fastapi import Request, HTTPException
from app.cache.session_cache import SessionCache


class SessionMiddleware:
    """
    会话管理中间件。

    与 Ch21.4 的对应关系：
    - 此处的 Session Cache 实现 Ch21.4 中描述的"缓存层会话存储"
    - Ch21.4 讨论了会话的创建、验证、销毁的完整生命周期
    - 本节聚焦于 Redis 作为缓存层的技术实现
    """

    def __init__(self, cache: SessionCache):
        self.cache = cache

    async def resolve_session(self, request: Request):
        """解析请求中的 Session ID"""
        session_id = request.headers.get("X-Session-Id")
        if not session_id:
            # 从 Cookie 中获取
            session_id = request.cookies.get("session_id")
        if not session_id:
            raise HTTPException(
                status_code=401,
                detail="缺少 Session ID，请参见 Ch21.4 会话管理"
            )
        return session_id

    async def get_or_create_context(self, session_id: str) -> dict:
        """获取或创建会话上下文"""
        meta = await self.cache.get_session_meta(session_id)
        if meta is None:
            # 从持久化存储恢复（数据库）
            # 如果数据库也找不到，创建新会话
            meta = {
                "session_id": session_id,
                "created_at": time.time(),
                "message_count": 0,
                "token_count": 0,
            }
            await self.cache.set_session_meta(session_id, meta)
        return meta
```

### 2.3 消息压缩策略

当会话积累了大量消息，Redis 存储和网络传输的开销会显著增长：

```python
# app/cache/compression.py
import zlib
import json


class MessageCompressor:
    """
    消息压缩器——当会话历史超过阈值时启用压缩。

    压缩效果（实测数据）：
    - 纯文本消息：压缩率 30-40%（JSON 格式的冗余）
    - 含代码块的消息：压缩率 50-60%
    - 含很长 Tool Call Result 的 JSON：压缩率 70-80%
    """

    def __init__(self, threshold_bytes: int = 1024 * 100):  # 100KB 阈值
        self.threshold = threshold_bytes
        self.level = 6  # zlib 压缩级别（0-9，折中速度和压缩率）

    def compress_if_needed(self, messages: list[dict]) -> str | bytes:
        """如果消息序列化后超过阈值，进行压缩"""
        serialized = json.dumps(messages, default=str, ensure_ascii=False)
        if len(serialized.encode()) > self.threshold:
            compressed = zlib.compress(serialized.encode(), self.level)
            return compressed
        return serialized

    def decompress(self, data: str | bytes) -> list[dict]:
        """自动识别并解压"""
        if isinstance(data, bytes):
            try:
                decompressed = zlib.decompress(data).decode()
                return json.loads(decompressed)
            except zlib.error:
                # 不是压缩数据，直接解析
                return json.loads(data.decode())
        return json.loads(data)
```

## 三、Embedding Cache：向量化结果复用

### 3.1 为什么需要 Embedding Cache？

Embedding 是 Agent 系统中最昂贵的操作之一：

```
Embedding 的计算成本：
- API 调用：OpenAI text-embedding-3-small 约 $0.02/1K tokens
- 延迟：单次 Embedding 调用约 200-500ms（取决于文本长度）
- 频率：一个 Agent 推理周期可能调用 10-20 次 Embedding（检索 + 工具输出向量化）

缓存前后的对比（典型场景，100 次 Agent 调用）：
               ┌──────────────┬──────────────┐
               │   无缓存      │  有缓存       │
    ┌──────────┼──────────────┼──────────────┤
    │ API 调用  │ 1,500 次     │ 200 次        │
    │ 延迟累计  │ 5-10 分钟    │ 30-60 秒      │
    │ API 费用  │ $3.0         │ $0.4          │
    │ 数据库负载 │ 高（反复查询）│ 低（高速命中）  │
    └──────────┘              └──────────────┘
```

### 3.2 实现代码

```python
# app/cache/embedding_cache.py
import hashlib
import json
import time
from typing import Optional

import redis.asyncio as redis
import numpy as np


class EmbeddingCache:
    """
    Embedding 向量缓存。

    缓存键设计：
    - 使用文本的 MD5 哈希作为键（固定长度，节省内存）
    - 前缀 + 模型名：区分不同 Embedding 模型的输出
    - 示例键：emb:text-embedding-3-small:a1b2c3d4...

    过期策略：
    - 短期缓存（默认 TTL=86400，1天）：普通文本
    - 长期缓存（TTL=604800，7天）：检索文档、FAQ、知识库条目
    - 无过期（手动管理）：静态知识库的 Embedding

    内存估算：
    - 每个 1536 维向量 ≈ 6KB（JSON 格式）
    - 100 万条缓存 ≈ 6GB Redis 内存
    - 建议设置 maxmemory 策略为 allkeys-lru
    """

    def __init__(self, redis_client: redis.Redis):
        self.redis = redis_client
        self.default_ttl = 86400  # 1 天
        self.persistent_ttl = 604800  # 7 天

    def _make_key(self, text: str, model: str = "default") -> str:
        """生成缓存键"""
        text_hash = hashlib.md5(text.encode("utf-8")).hexdigest()
        return f"emb:{model}:{text_hash}"

    async def get(self, text: str, model: str = "default") -> Optional[list[float]]:
        """获取缓存的 Embedding 向量"""
        key = self._make_key(text, model)
        data = await self.redis.get(key)
        if data:
            # 命中缓存
            return json.loads(data)
        return None

    async def set(
        self,
        text: str,
        embedding: list[float],
        model: str = "default",
        ttl: Optional[int] = None,
    ):
        """缓存 Embedding 向量"""
        key = self._make_key(text, model)
        ttl = ttl or self.default_ttl
        await self.redis.setex(key, ttl, json.dumps(embedding))

    async def get_batch(
        self,
        texts: list[str],
        model: str = "default",
    ) -> tuple[list[int], list[str], list[list[float]]]:
        """
        批量查询缓存。

        返回 (missing_indices, missing_texts, cached_embeddings)
        - missing_indices: 在缓存中未命中的文本索引
        - missing_texts: 需要调用 API 生成 Embedding 的文本
        - cached_embeddings: 已缓存的向量（与输入 texts 顺序一致）
        """
        pipeline = self.redis.pipeline()
        keys = [self._make_key(t, model) for t in texts]
        for key in keys:
            pipeline.get(key)
        results = await pipeline.execute()

        cached = [None] * len(texts)
        missing_indices = []
        missing_texts = []

        for i, (text, result) in enumerate(zip(texts, results)):
            if result:
                cached[i] = json.loads(result)
            else:
                missing_indices.append(i)
                missing_texts.append(text)

        return missing_indices, missing_texts, cached

    async def set_batch(
        self,
        texts: list[str],
        embeddings: list[list[float]],
        model: str = "default",
        ttl: Optional[int] = None,
    ):
        """批量缓存 Embedding 向量"""
        ttl = ttl or self.default_ttl
        pipeline = self.redis.pipeline()
        for text, emb in zip(texts, embeddings):
            key = self._make_key(text, model)
            pipeline.setex(key, ttl, json.dumps(emb))
        await pipeline.execute()

    async def get_or_compute(
        self,
        text: str,
        compute_fn,
        model: str = "default",
        ttl: Optional[int] = None,
    ) -> list[float]:
        """
        获取缓存，如果未命中则调用 compute_fn 生成。
        这是 Embedding Cache 的核心模式——Cache-Aside。
        """
        cached = await self.get(text, model)
        if cached is not None:
            return cached

        # 缓存未命中，计算 Embedding
        embedding = await compute_fn(text)

        # 异步缓存（不阻塞返回）
        ttl = ttl or self.default_ttl
        await self.set(text, embedding, model, ttl)

        return embedding

    async def get_stats(self) -> dict:
        """获取缓存统计信息"""
        # 使用 SCAN 命令统计前缀匹配的键
        cursor = 0
        keys_with_ttl = []
        while True:
            cursor, keys = await self.redis.scan(
                cursor=cursor, match="emb:*", count=1000
            )
            for key in keys:
                ttl = await self.redis.ttl(key)
                keys_with_ttl.append({"key": key, "ttl": ttl})
            if cursor == 0:
                break

        total = len(keys_with_ttl)
        if total == 0:
            return {"total_keys": 0}

        active = sum(1 for k in keys_with_ttl if k["ttl"] > 0)
        return {
            "total_keys": total,
            "active_keys": active,
            "avg_ttl": sum(k["ttl"] for k in keys_with_ttl if k["ttl"] > 0) / active if active else 0,
        }
```

## 四、Rate Limiter：API 调用限流

### 4.1 Agent 场景的限流特殊需求

Agent 的限流与传统 Web 限流有三点本质不同：

**① 双层限流**
传统限流只保护后端服务。Agent 系统需要同时保护两方：
- **下游 API 限流**：LLM 提供商（OpenAI、Anthropic）有严格的 TPM/RPM 限制
- **上游用户限流**：防止单个用户消耗所有 Agent 资源

**② 成本感知限流**
Agent 的每次 LLM 调用成本差异巨大（简单问答 < $0.01，多轮工具调用可能 $0.50+）。限流策略应该考虑 Token 消耗而非仅请求次数：
```
简单限流：每分钟最多 60 次请求
成本限流：每分钟最多 100K prompt tokens
```

**③ 突发容忍 vs 平滑**
Agent 工作负载是突发性的——用户发送一个复杂请求，Agent 在短时间内发起多次 LLM 调用。限流策略需要容忍这类突发行为：
```
Token 桶算法（Token Bucket）比固定窗口更适合 Agent：
- 可以积累突发配额（桶容量）
- 平滑处理长期速率
- 适合 Agent 的"安静一段时间后突然密集调用"模式
```

### 4.2 滑动窗口限流实现（精确版）

```python
# app/cache/rate_limiter.py
import time
import asyncio
from typing import Optional

import redis.asyncio as redis


class SlidingWindowRateLimiter:
    """
    基于 Redis Sorted Set 的滑动窗口限流器。

    算法：滑动窗口日志（Sliding Window Log）
    为每个用户维护一个有序集合，成员是请求时间戳，
    分数也是请求时间戳。每次请求：
    1. 移除窗口外的旧记录（ZREMRANGEBYSCORE）
    2. 统计窗口内的请求数（ZCARD）
    3. 如果超出限制则拒绝，否则添加当前请求

    优势：精确，没有突刺问题（固定窗口算法的缺陷）
    劣势：每个用户需要维护有序集合，内存开销略高
    """

    def __init__(self, redis_client: redis.Redis):
        self.redis = redis_client

    async def check(
        self,
        key: str,
        limit: int = 60,
        window_seconds: int = 60,
        cost: int = 1,
    ) -> bool:
        """
        检查是否允许请求。

        参数：
        - key: 限流键（用户 ID、IP、API Key 等）
        - limit: 窗口内允许的最大数量
        - window_seconds: 滑动窗口大小（秒）
        - cost: 本次请求消耗的配额（用于成本感知限流）

        返回：True=允许，False=拒绝
        """
        redis_key = f"ratelimit:{key}"
        now = time.time()
        window_start = now - window_seconds

        # 使用 Lua 脚本保证原子性
        lua_script = """
            local key = KEYS[1]
            local now = tonumber(ARGV[1])
            local window_start = tonumber(ARGV[2])
            local limit = tonumber(ARGV[3])
            local cost = tonumber(ARGV[4])

            -- 清除窗口外的过期记录
            redis.call('ZREMRANGEBYSCORE', key, '-inf', window_start)

            -- 统计窗口内的请求数
            local current = redis.call('ZCARD', key) or 0

            -- 检查是否超限
            if current + cost > limit then
                return 0  -- 拒绝
            end

            -- 记录本次请求
            for i = 1, cost do
                redis.call('ZADD', key, now + (i * 0.001), now + (i * 0.001) .. ':' .. i)
            end

            -- 设置 TTL 防止内存泄漏
            redis.call('EXPIRE', key, math.ceil(window_seconds * 1.5))
            return 1  -- 允许
        """

        allowed = await self.redis.eval(
            lua_script,
            1,
            redis_key,
            now,
            window_start,
            limit,
            cost,
        )
        return bool(allowed)

    async def get_remaining(self, key: str, limit: int, window_seconds: int) -> int:
        """获取剩余配额"""
        redis_key = f"ratelimit:{key}"
        now = time.time()
        window_start = now - window_seconds

        await self.redis.zremrangebyscore(redis_key, "-inf", window_start)
        current = await self.redis.zcard(redis_key) or 0
        return max(0, limit - current)

    async def get_reset_time(self, key: str, window_seconds: int) -> float:
        """获取配额重置时间（最早过期的记录时间）"""
        redis_key = f"ratelimit:{key}"
        oldest = await self.redis.zrange(redis_key, 0, 0, withscores=True)
        if oldest:
            return oldest[0][1] + window_seconds
        return time.time()


class TokenBucketRateLimiter:
    """
    Token 桶限流器——更适合 Agent 的突发工作负载。

    原理：
    - 桶容量（burst）：最大突发请求数
    - 填充速率（rate）：每秒恢复的 Token 数
    - 每个请求消耗 1 个 Token
    - Token 不够时请求被延迟或拒绝
    """

    def __init__(self, redis_client: redis.Redis):
        self.redis = redis_client

    async def acquire(
        self,
        key: str,
        capacity: int = 100,
        rate: float = 1.0,  # 每秒填充 Token 数
        cost: int = 1,
        max_wait: Optional[float] = None,
    ) -> bool:
        """
        获取 Token。

        参数：
        - capacity: 桶容量（最大突发量）
        - rate: Token 填充速率（个/秒）
        - max_wait: 最大等待时间（秒），None 表示不等待直接拒绝

        使用 Lua 脚本确保原子性。
        """
        lua_script = """
            local key = KEYS[1]
            local now = tonumber(ARGV[1])
            local capacity = tonumber(ARGV[2])
            local rate = tonumber(ARGV[3])
            local cost = tonumber(ARGV[4])

            -- 获取当前桶状态：{tokens, last_refill_time}
            local state = redis.call('GET', key)
            local tokens, last_time

            if state then
                local decoded = cjson.decode(state)
                tokens = decoded[1]
                last_time = decoded[2]
            else
                tokens = capacity
                last_time = now
            end

            -- 计算自上次填充以来应该补充的 Token 数
            local elapsed = now - last_time
            local refill = elapsed * rate
            tokens = math.min(capacity, tokens + refill)

            -- 检查是否有足够的 Token
            if tokens >= cost then
                tokens = tokens - cost
                redis.call('SETEX', key, 86400, cjson.encode({tokens, now}))
                return {1, 0}  -- {允许, 等待时间}
            else
                -- 计算需要等待的时间
                local wait_time = (cost - tokens) / rate
                if tonumber(ARGV[5]) and wait_time > tonumber(ARGV[5]) then
                    return {0, -1}  -- 拒绝，等待时间超过 max_wait
                end
                return {0, wait_time}  -- 拒绝，告知需要等待的时间
            end
        """

        now = time.time()
        result = await self.redis.eval(
            lua_script,
            1,
            f"token_bucket:{key}",
            now,
            capacity,
            rate,
            cost,
            max_wait or -1,
        )
        return bool(result[0])
```

### 4.3 限流中间件

```python
# app/middleware/rate_limit.py
from fastapi import Request, HTTPException
from fastapi.responses import JSONResponse
from app.cache.rate_limiter import SlidingWindowRateLimiter


class RateLimitMiddleware:
    """FastAPI 限流中间件"""

    def __init__(self, limiter: SlidingWindowRateLimiter):
        self.limiter = limiter

    async def check(self, client_ip: str, api_key: str | None = None):
        """
        检查请求是否在限流范围内。
        同时检查 IP 级别和 API Key 级别的限流。
        """
        # IP 级别限流（宽松）
        ip_allowed = await self.limiter.check(
            key=f"ip:{client_ip}",
            limit=100,  # 每分钟 100 次
            window_seconds=60,
        )
        if not ip_allowed:
            raise HTTPException(
                status_code=429,
                detail="IP 级别限流：请求过于频繁，请稍后重试",
                headers={
                    "Retry-After": "30",
                    "X-RateLimit-Type": "ip",
                }
            )

        # API Key 级别限流（严格）
        if api_key:
            key_allowed = await self.limiter.check(
                key=f"key:{api_key}",
                limit=60,  # 每分钟 60 次
                window_seconds=60,
            )
            if not key_allowed:
                raise HTTPException(
                    status_code=429,
                    detail="API Key 级别限流：已超出配额限制",
                    headers={
                        "Retry-After": "30",
                        "X-RateLimit-Type": "api_key",
                    }
                )

    async def check_llm_quota(self, api_key: str, prompt_tokens: int):
        """
        LLM Token 配额检查（成本感知限流）。
        限制每分钟的 Prompt Token 总量。
        """
        # 每分钟最多 100K Prompt Tokens
        token_limit = 100_000
        # 将 Token 量转换为 cost（每 100 Token 算 1 单位）
        cost = max(1, prompt_tokens // 100)

        allowed = await self.limiter.check(
            key=f"llm_tokens:{api_key}",
            limit=token_limit // 100,
            window_seconds=60,
            cost=cost,
        )
        if not allowed:
            raise HTTPException(
                status_code=429,
                detail="LLM Token 配额已用尽，请降低请求频率或升级套餐",
                headers={
                    "X-RateLimit-Type": "llm_tokens",
                    "Retry-After": "30",
                }
            )
```

### 5.3 Redis 监控

```python
# app/cache/monitor.py
import time
from typing import Optional
import redis.asyncio as redis


class RedisMonitor:
    """Redis 性能监控"""

    def __init__(self, redis_client: redis.Redis):
        self.redis = redis_client
        self.metrics = {
            "hits": 0,
            "misses": 0,
            "set_calls": 0,
            "delete_calls": 0,
            "avg_get_latency": 0.0,
            "avg_set_latency": 0.0,
        }

    async def track_get(self, key: str) -> Optional[str]:
        """带性能追踪的 GET 操作"""
        start = time.monotonic()
        result = await self.redis.get(key)
        elapsed = (time.monotonic() - start) * 1000

        if result is not None:
            self.metrics["hits"] += 1
        else:
            self.metrics["misses"] += 1

        # 指数移动平均
        alpha = 0.1
        self.metrics["avg_get_latency"] = (
            (1 - alpha) * self.metrics["avg_get_latency"] + alpha * elapsed
        )

        return result

    async def get_cache_ratio(self) -> float:
        """获取缓存命中率"""
        total = self.metrics["hits"] + self.metrics["misses"]
        if total == 0:
            return 0.0
        return self.metrics["hits"] / total * 100

    async def report(self) -> dict:
        """生成监控报告"""
        info = await self.redis.info()
        return {
            "cache_hit_ratio": f"{await self.get_cache_ratio():.1f}%",
            "used_memory_human": info.get("used_memory_human", "N/A"),
            "total_connections_received": info.get("total_connections_received", 0),
            "evicted_keys": info.get("evicted_keys", 0),
            "avg_get_latency_ms": f"{self.metrics['avg_get_latency']:.2f}",
            "avg_set_latency_ms": f"{self.metrics['avg_set_latency']:.2f}",
        }
```

## 关键概念速查

| 术语 | 解释 |
|------|------|
| Cache-Aside | 应用程序先读缓存，未命中时读数据库并回写缓存 |
| Sliding Window Log | 使用有序集合维护每个请求的时间戳，精确限流 |
| Token Bucket | 允许突发流量的限流算法，桶容量控制最大突发量 |
| Write-Through | 写入时同时更新缓存和数据库，保证一致性 |
| allkeys-lru | Redis 内存淘汰策略，淘汰最近最少使用的键 |
| Sorted Set | Redis 有序集合，成员按分数排序，适合滑动窗口实现 |
| 成本感知限流 | 基于 Token 消耗而非请求次数的限流策略 |
| 连接池预热 | 应用启动时提前创建 Redis 连接，避免首次请求延迟 |
