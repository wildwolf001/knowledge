# 13.5 多模型协同路由 —— B 站生产实践：SQL→Claude / 多模态→Gemini / 中文→DeepSeek

> 多模型协同路由（Multi-Model Routing）是指根据任务类型、输入特征和性能要求，将不同的子任务动态路由到最合适的 LLM 模型上执行。没有单一模型在所有任务上表现最优，通过智能路由可以同时提升系统整体质量、降低成本和延迟。本节以 B 站的 Agent 系统生产实践为案例，详细展开多模型路由的设计与实现。

---

## 一、为什么需要多模型路由？

### 1.1 单一模型的局限性

截至 2026 年，主流 LLM 各有其擅长和薄弱的领域（详见第 1.5 节「模型能力全景图」）：

| 任务类型 | Claude 3.5 Sonnet | GPT-4o | Gemini 2.0 Pro | DeepSeek-V4 | Qwen3-72B |
|---------|------------------|--------|----------------|-------------|-----------|
| **SQL 生成** | ★★★★★ 最佳 | ★★★★ | ★★★ | ★★★★ | ★★★ |
| **代码审查** | ★★★★★ | ★★★★ | ★★★★ | ★★★★ | ★★★ |
| **中文理解** | ★★★★ | ★★★★ | ★★★ | ★★★★★ 最佳 | ★★★★★ |
| **多模态（图/视频）** | ★★★ | ★★★★ | ★★★★★ 最佳 | ★★ | ★★★ |
| **长文档分析** | ★★★★★ | ★★★★ | ★★★★ | ★★★ | ★★★ |
| **数学推理** | ★★★★ | ★★★★ | ★★★ | ★★★★★ 最佳 | ★★★★ |
| **延迟** | 中等 | 中等 | 快 | 快 | 快 |
| **成本/token** | $$ | $$$ | $ | $ | $ |

**核心洞察**：没有任何一个模型在所有维度上都是最优的。如果使用单一模型处理所有子任务：
- 模型强项上的任务质量不错
- 弱项上的任务质量不理想
- 成本上可能浪费（高成本模型处理简单任务）
- 延迟上可能不足（慢模型拖慢整体系统）

### 1.2 路由的价值

```
单模型 vs 多模型路由对比：

单模型（全部用 Claude）:
  总成本: 1000 万 tokens × $15/1M = $15,000
  平均质量: 8.5/10
  平均延迟: 1200ms
  问题: 50% 的简单任务本可以用更便宜的模型

多模型路由:
  SQL 任务 (30%): Claude × $15 = $4,500    质量 9.5/10
  多模态 (10%):  Gemini × $5  = $500        质量 9.5/10
  中文任务 (40%): DeepSeek × $2 = $800      质量 9.5/10
  简单任务 (20%): Qwen × $1    = $200       质量 8.5/10（够了）
  总成本: $6,000（节省 60%）
  平均质量: 9.2/10
  平均延迟: 600ms
```

### 2.2 路由分类器（Routing Classifier）

路由分类器是整个系统的入口，负责将用户请求分类到正确的模型。B 站使用**两级分类策略**：

**第一级：规则引擎**（确定性，零延迟）

```python
class RuleRouter:
    """
    第一级路由：基于规则的确定性路由
    处理 60% 以上的请求，零延迟
    """
    
    # B 站的路由规则
    RULES = [
        # SQL 任务 → Claude
        {
            "name": "sql_query",
            "pattern": r"(查询|统计|分析|SQL|数据库|select|from|where)\s.*(数据|订单|用户|播放|点赞|投币)",
            "target": "claude",
            "priority": 90,
        },
        # 图片/视频处理 → Gemini
        {
            "name": "multimodal",
            "pattern": None,  # 通过检测输入中的媒体类型判断
            "check_fn": lambda req: req.has_image or req.has_video,
            "target": "gemini",
            "priority": 80,
        },
        # 中文内容创作 → DeepSeek
        {
            "name": "chinese_content",
            "pattern": r"(写[一|篇|段|个]|创作|作文|文章|小说|诗歌|剧本)",
            "target": "deepseek",
            "priority": 70,
        },
        # 简单聊天 → Qwen（低成本）
        {
            "name": "simple_chat",
            "pattern": r"^(你好|嗨|在吗|hello|hi|早上好|晚上好)$",
            "target": "qwen",
            "priority": 60,
        },
    ]
    
    def route(self, request: Request) -> Optional[str]:
        """基于规则路由，返回目标模型名"""
        for rule in sorted(self.RULES, key=lambda r: -r["priority"]):
            # 检查正则
            if rule.get("pattern"):
                if re.search(rule["pattern"], request.text, re.IGNORECASE):
                    logger.info(f"规则路由: {rule['name']} → {rule['target']}")
                    return rule["target"]
            # 检查函数
            if rule.get("check_fn"):
                if rule["check_fn"](request):
                    return rule["target"]
        return None  # 无法确定，交给第二级
```

**第二级：分类模型路由**（小模型，5-20ms）

```python
class ModelRouter:
    """
    第二级路由：基于分类模型的路由
    
    使用轻量级 BERT 模型（约 300M 参数）对请求进行分类。
    B 站在内部标注了 50 万条请求-模型匹配数据微调。
    """
    
    def __init__(self):
        # B 站自研的分类器，基于 BERT-base-Chinese 微调
        self.classifier = load_model("bilibili/task-classifier-v2")
        self.labels = [
            "sql_analytics",       # → Claude
            "chinese_creation",    # → DeepSeek
            "multimodal",          # → Gemini
            "code_review",         # → Claude
            "general_chat",        # → Qwen
            "translation",         # → DeepSeek
            "long_document",       # → Claude
        ]
    
    def classify(self, request: Request) -> Tuple[str, float]:
        """
        分类请求，返回（目标模型，置信度）
        """
        # 对输入进行分类
        label, confidence = self.classifier.predict(
            request.text,
            return_confidence=True
        )
        
        # 模型映射
        model_mapping = {
            "sql_analytics": "claude",
            "chinese_creation": "deepseek",
            "multimodal": "gemini",
            "code_review": "claude",
            "general_chat": "qwen",
            "translation": "deepseek",
            "long_document": "claude",
        }
        
        target = model_mapping.get(label, "claude")  # 默认 Claude
        
        logger.info(
            f"模型路由: 标签={label}, "
            f"置信度={confidence:.2f}, 目标={target}"
        )
        
        return target, confidence


# 完整的路由调用链
class BilibiliRouter:
    """B 站多模型路由入口"""
    
    def __init__(self):
        self.rule_router = RuleRouter()
        self.model_router = ModelRouter()
        self.stats = RoutingStats()
    
    async def route(self, request: Request) -> RoutingDecision:
        """
        完整路由决策
        """
        # 第一步：规则路由（零延迟）
        rule_result = self.rule_router.route(request)
        if rule_result:
            self.stats.record("rule", rule_result)
            return RoutingDecision(
                model=rule_result,
                confidence=1.0,
                method="rule"
            )
        
        # 第二步：模型分类路由
        model_target, confidence = self.model_router.classify(request)
        
        # 低置信度降级：使用默认模型
        if confidence < 0.6:
            model_target = "claude"  # 默认用最安全的模型
            method = "fallback"
        else:
            method = "classifier"
        
        self.stats.record(method, model_target)
        
        return RoutingDecision(
            model=model_target,
            confidence=confidence,
            method=method
        )
```

### 2.3 B 站的三条主要路由路径

#### 路径 1：SQL 分析 → Claude

B 站内部有大量的数据分析需求——运营需要查询播放量、创作者需要查看收益数据、推荐系统需要分析用户行为。

```
请求样例: "查询过去 7 天互动率超过 5% 的所有视频标题和 UP 主"

路由决策:
  规则匹配: "查询...播放...视频" → Claude
  原因: Claude 在 SQL 生成上的准确率最高（B 站实测 94.7%）
  
Claude Agent 执行流程:
  1. 解析自然语言 → 识别意图: 多表 JOIN 查询

     FROM video v
     JOIN creator c ON v.creator_id = c.id
```

## 三、路由策略的工程实现

### 3.1 动态路由 + 回退机制

B 站的路由系统采用"主路由 + 回退链"策略，确保在任何模型不可用时系统仍能正常运行：

```python
class FallbackChain:
    """
    回退链：当主模型不可用时，自动降级到备用模型
    
    B 站配置示例:
      SQL: Claude → GPT-4o → DeepSeek
      多模态: Gemini → GPT-4o → Claude
      中文: DeepSeek → Qwen → Claude
    """
    
    FALLBACK_CHAINS = {
        "claude": ["claude", "gpt4o", "deepseek", "qwen"],
        "gemini": ["gemini", "gpt4o", "claude", "qwen"],
        "deepseek": ["deepseek", "qwen", "claude", "gpt4o"],
        "qwen": ["qwen", "deepseek", "claude", "gpt4o"],
    }
    
    def __init__(self):
        self.model_clients = {
            "claude": ClaudeClient(),
            "gemini": GeminiClient(),
            "deepseek": DeepSeekClient(),
            "gpt4o": GPT4oClient(),
            "qwen": QwenClient(),
        }
        self.circuit_breakers = {
            name: CircuitBreaker()
            for name in self.model_clients
        }
    
    async def execute_with_fallback(
        self,
        request: Request,
        primary_model: str,
    ) -> Response:
        """
        带回退链的执行：
        1. 尝试主模型
        2. 主模型失败 → 尝试回退链中的下一个
        3. 所有模型都失败 → 返回错误应答
        """
        chain = self.FALLBACK_CHAINS.get(primary_model, [primary_model])
        
        for model_name in chain:
            # 检查断路器
            if self.circuit_breakers[model_name].is_open():
                logger.warning(f"断路器打开: {model_name}，跳过")
                continue
            
            try:
                client = self.model_clients[model_name]
                response = await client.execute(request)
                
                # 记录成功
                self.circuit_breakers[model_name].record_success()
                
                return response
                
            except Exception as e:
                logger.warning(
                    f"模型 {model_name} 执行失败: {e}，"
                    f"切换到下一个"
                )
                self.circuit_breakers[model_name].record_failure()
                continue
        
        # 所有模型都失败
        logger.error(f"所有回退模型均失败，主路由: {primary_model}")
        return Response(
            content="服务暂时不可用，请稍后重试",
            error=True
        )
```

### 3.2 断路器（Circuit Breaker）模式

```python
class CircuitBreaker:
    """
    断路器：防止对故障模型进行无效的重试
    
    状态机:
      CLOSED (正常) → OPEN (故障) → HALF_OPEN (试探) → CLOSED 或 OPEN
    """
    
    def __init__(
        self,
        failure_threshold: int = 5,      # 连续失败 N 次后打开
        recovery_timeout: float = 30.0,   # 30 秒后进入半开状态
        half_open_max_requests: int = 3,  # 半开状态最多试探 3 次
    ):
        self.failure_threshold = failure_threshold
        self.recovery_timeout = recovery_timeout
        self.half_open_max_requests = half_open_max_requests
        
        self.state = "CLOSED"
        self.failure_count = 0
        self.last_failure_time = 0
        self.half_open_requests = 0
    
    def is_open(self) -> bool:
        """检查断路器是否打开"""
        if self.state == "CLOSED":
            return False
        
        if self.state == "OPEN":
            # 检查是否到了恢复时间
            if time.time() - self.last_failure_time > self.recovery_timeout:
                self.state = "HALF_OPEN"
                self.half_open_requests = 0
                return False
            return True
        
        # HALF_OPEN 状态
        if self.half_open_requests >= self.half_open_max_requests:
            return True
        
        self.half_open_requests += 1
        return False
    
    def record_success(self):
        """记录成功"""
        self.state = "CLOSED"
        self.failure_count = 0
        self.half_open_requests = 0
    
    def record_failure(self):
        """记录失败"""
        self.failure_count += 1
        self.last_failure_time = time.time()
        
        if self.failure_count >= self.failure_threshold:
            self.state = "OPEN"
            logger.warning(
                f"断路器打开: 连续失败 {self.failure_count} 次"
            )
```

## 四、成本和延迟优化

### 4.1 成本优化模型

B 站实现的成本优化模型：

```python
class CostOptimizer:
    """
    成本优化器：在满足质量要求的前提下最小化成本
    """
    
    # B 站实际使用的模型定价（2026）
    MODEL_PRICING = {
        "claude": {"input": 15.0, "output": 75.0},    # $ per 1M tokens
        "gpt4o": {"input": 10.0, "output": 30.0},
        "gemini": {"input": 5.0, "output": 15.0},
        "deepseek": {"input": 2.0, "output": 8.0},
        "qwen": {"input": 1.0, "output": 4.0},
    }
    
    def estimate_cost(
        self,
        model: str,
        input_tokens: int,
        output_tokens: int,
    ) -> float:
        """估算请求成本"""
        pricing = self.MODEL_PRICING[model]
        cost = (
            pricing["input"] * input_tokens / 1_000_000 +
            pricing["output"] * output_tokens / 1_000_000
        )
        return cost
    
    def get_cheapest_qualified_model(
        self,
        task_type: str,
        quality_requirement: float,  # 0.0 ~ 1.0
    ) -> str:
        """
        获取满足质量要求的最便宜模型
        """
        model_qualities = {
            "sql": {"claude": 0.95, "gpt4o": 0.89, "deepseek": 0.85, "qwen": 0.78},
            "chinese": {"deepseek": 0.97, "qwen": 0.96, "claude": 0.92, "gpt4o": 0.90},
            "multimodal": {"gemini": 0.96, "gpt4o": 0.94, "claude": 0.91},
            "general": {"claude": 0.93, "gpt4o": 0.91, "deepseek": 0.88, "qwen": 0.85},
        }
        
        available = model_qualities.get(task_type, {})
        # 按成本升序排序
        sorted_models = sorted(
            available.items(),
            key=lambda x: self.MODEL_PRICING[x[0]]["input"]
        )
        
        for model, quality in sorted_models:
            if quality >= quality_requirement:
                return model
        
        return sorted_models[-1][0]  # 返回质量最高的
```

### 4.2 B 站的月度成本对比

B 站分享的实际数据（2026Q1）：

- 最佳性价比：多模型路由是最优策略

## 五、路由策略的演进路径

B 站的多模型路由系统经历了三个阶段：

```
阶段 1：硬编码路由（2024）
  路由逻辑: if/else 硬编码在业务代码中
  问题: 每次模型更新都要改代码，无法灵活调整

阶段 2：配置化路由（2025）
  路由逻辑: YAML 配置 + 规则引擎
  改进: 运维可调整，无需改代码
  问题: 规则覆盖不全，长尾请求路由不准

阶段 3：智能路由（2026 - 当前）
  路由逻辑: 规则引擎 + 分类模型 + 实时反馈学习
  改进: 
  - 自动检测新的任务类型
  - 根据模型的实际表现动态调整权重
  - A/B 测试框架持续优化路由策略
```

### 当前正在探索的方向

1. **基于 Embedding 的路由**：将用户请求编码为向量，在向量空间中查找最相似的已分类请求
2. **强化学习路由**：根据成功率、用户满意度反馈实时调整路由策略
3. **混合推理**：对高难度请求，同时路由到两个模型并取最佳结果（增加成本但提高可靠性）

## 关键概念速查

| 术语 | 解释 |
|------|------|
| 多模型路由（Multi-Model Routing） | 根据任务特征将请求分配到最合适的模型 |
| 路由分类器（Routing Classifier） | 使用规则或小模型判断请求应路由到哪个模型 |
| 回退链（Fallback Chain） | 主模型不可用时依次尝试备用模型的策略 |
| 断路器（Circuit Breaker） | 防止对故障模型进行无效重试的保护机制 |
| 模型能力全景图 | 不同模型在各种任务上的表现对比（见第 1.5 节） |
| 质量-成本权衡 | 在模型质量和调用成本之间寻找最优平衡点 |
| 智能路由 | 基于实时反馈和模型表现动态调整的路由策略 |

---

*多模型路由是 13.3 节 Coordinator 模式在模型选择层面的具体实现。子任务分配给不同 Agent 时，Agent 背后可以挂载不同的模型——这依赖于 13.4 节讨论的进程内/远程部署能力。模型能力的具体对比数据详见第 1.5 节「模型能力全景图」。Multi-Agent 系统的整体架构框架见第 12 章。*
