# 13.1 任务粒度判定 —— 何时 Fork 子 Agent、何时串行、何时并行

> 任务粒度（Task Granularity）指将一个复杂任务拆分为多个子任务时，每个子任务的大小和复杂度。粒度太粗，子 Agent 无法有效并行或隔离风险；粒度太细，协调开销超过执行收益。本节提供系统化的粒度判定方法和决策框架。

---

## 一、任务分解的三种基本模式

在 Multi-Agent 系统（详见第 12 章 Multi-Agent 架构与协作）中，复杂任务通常以三种方式分配给子 Agent：

```
┌─────────────────────────────────────────────────────┐
│              任务分配的基本模式                        │
├─────────────────────────────────────────────────────┤
│                                                      │
│  串行模式（Sequential）                                │
│  Task → Agent A → Agent B → Agent C → Result         │
│  适用：强依赖链，每步依赖上一步结果                      │
│                                                      │
│  并行模式（Parallel）                                  │
│        ┌→ Agent A ─┐                                 │
│  Task ──┼→ Agent B ─┼→ Merge → Result                │
│        └→ Agent C ─┘                                 │
│  适用：独立子任务，无数据依赖                           │
│                                                      │
│  Fork 模式（子 Agent 独立运行）                         │
│  Task → Coordinator ─┬→ SubAgent A (独立上下文) ─→ ... │
│                       ├→ SubAgent B (独立上下文) ─→ ... │
│                       └→ SubAgent C (独立上下文) ─→ ... │
│  适用：子任务需要在隔离环境中运行，自带完整工具链          │
│                                                      │
└─────────────────────────────────────────────────────┘
```

### 1.1 串行模式

串行模式是最直观的任务分解方式。Agent A 的输出作为 Agent B 的输入，形成处理流水线。

**典型场景**：
- 数据清洗 → 特征提取 → 模型推理 → 结果格式化
- 文档解析 → 摘要生成 → 翻译 → 最终润色

**优势**：实现简单，依赖关系清晰，调试容易。
**劣势**：总耗时 = 各步耗时之和，无法利用并行加速。

### 1.2 并行模式

并行模式将无依赖关系的子任务同时分配给多个 Agent 执行。

**典型场景**：
- 同时查询多个数据源（数据库、API、文件系统）
- 对同一份文档执行多种分析（情感分析、实体提取、摘要）
- 批量处理多条独立记录

**优势**：显著降低总耗时（取决于最慢的子任务）。
**劣势**：需要协调机制来合并结果，可能引入资源竞争。

### 1.3 Fork 模式

Fork 模式是"真正"的子 Agent 创建——每个子 Agent 拥有独立的上下文窗口、工具集和权限范围。这与 13.2 节讨论的上下文隔离密切相关。

**典型场景**：
- 每个子 Agent 负责一个客户的全流程支持
- 安全敏感操作需要隔离执行环境
- 子任务需要使用互斥的工具或资源

**优势**：最强隔离性，错误不会跨 Agent 传播。
**劣势**：开销最大（上下文重新加载、工具初始化）。

## 二、任务粒度的判定维度

判定一个任务应该采用哪种模式，需要从四个核心维度进行评估：

### 2.1 依赖密度（Dependency Density）

依赖密度指子任务之间的数据耦合程度。这是最重要的判定维度。

```python
def assess_dependency_density(subtasks: list) -> str:
    """
    评估任务依赖密度，返回推荐模式
    """
    dependency_graph = build_dependency_graph(subtasks)
    edges = len(dependency_graph.edges)
    nodes = len(dependency_graph.nodes)
    
    if nodes == 0:
        return "single_task"
    
    # 依赖密度 = 实际依赖边数 / 最大可能边数
    max_possible_edges = nodes * (nodes - 1) / 2
    density = edges / max_possible_edges if max_possible_edges > 0 else 0
    
    if density > 0.6:
        return "sequential"   # 高依赖：串行
    elif density > 0.2:
        return "hybrid"       # 中等依赖：混合模式
    else:
        dependencies_per_node = edges / nodes
        if dependencies_per_node == 0:
            return "parallel" # 零依赖：并行
        else:
            return "fork"     # 低密度但有依赖：Fork
```

### 2.2 上下文隔离需求（Isolation Requirement）

某些子任务需要在隔离的环境中执行，以防止信息泄漏或交叉污染。

| 隔离需求级别 | 描述 | 推荐模式 |
|------------|------|---------|
| **无隔离** | 子任务可以共享上下文 | 串行/并行 |
| **轻量隔离** | 需要独立 Context Window，但工具集可共享 | Fork（进程内） |
| **重量隔离** | 需要独立进程/容器，不能有任何共享状态 | Fork（远程 Agent，见 13.4） |

**典型需要隔离的场景**：
- 处理不同客户的敏感数据（数据隔离）
- 使用互斥的 API Key 或身份认证（凭据隔离）
- 运行不受信的第三方代码（安全隔离）

### 2.3 错误传播半径（Error Propagation Radius）

如果一个子任务失败，影响范围有多大？这是决定是否使用 Fork 模式的关键指标。

```
错误传播半径示意图：

串行模式：
  Step A (失败) → Step B (全部错误) → Step C (全部错误)
  传播半径 = 全部后续步骤 ❌

并行模式：
  ┌→ Step A (失败) ─┐
  ├→ Step B (成功) ─┼→ Merge (A 部分缺失)
  └→ Step C (成功) ─┘
  传播半径 = 仅 Step A ✅

Fork 模式：
  SubAgent A (失败) → 重启 SubAgent A
  SubAgent B (成功) → 不受影响
  传播半径 = 仅 A，且可恢复 ✅✅
```

**经验法则**：
- 若单个子任务失败将导致整个任务失败 → 缩小粒度，增加容错点
- 若子任务需要高可靠性（如支付处理）→ 使用 Fork 模式隔离
- 若子任务可以容忍部分失败（如批量数据提取）→ 并行模式即可

### 2.4 执行耗时分布（Execution Time Distribution）

子任务的执行时间分布直接影响模式选择：

```python
def recommend_mode_by_time(subtasks: list) -> str:
    """
    根据子任务耗时分布推荐模式
    """
    times = [estimate_execution_time(t) for t in subtasks]
    total = sum(times)
    max_time = max(times)
    min_time = min(times)
    avg_time = total / len(times)
    
    # 串行总耗时
    serial_time = total
    
    # 并行总耗时（等于最慢子任务）
    parallel_time = max_time
    
    speedup = serial_time / parallel_time if parallel_time > 0 else 1
    
    if speedup < 1.2:
        # 加速比不足 20%，不值得并行
        return "sequential"
    elif speedup > 3.0:
        # 加速比超过 3 倍，强烈推荐并行
        teamplate = "parallel"
    else:
        # 中等加速比，需要结合其他维度判断
        return "needs_further_analysis"
```

**实际案例**：
| 场景 | 串行耗时 | 并行耗时 | 加速比 | 推荐 |
|------|---------|---------|--------|------|
| 3 个 API 调用（各 200ms） | 600ms | 200ms | 3.0x | 并行 |
| 文档翻译 3 段（各 2s） | 6s | 2s | 3.0x | 并行 |
| 链式数据清洗（各 100ms） | 300ms | 300ms | 1.0x | 串行 |
| 复杂报告生成（含依赖） | 10s | 8s | 1.25x | 混合 |

## 三、任务粒度决策树

以下决策树将上述四个维度整合为一个可执行的判定流程：

```
                                         │

                   │  - 中间值：看错误半径 │
                   └──────────────────────┘
```

### 决策细则

1. **先检查依赖**：如果子任务 B 必须等待 A 的结果才能开始，无论其他维度如何，串行是强制选项。
2. **再检查隔离**：如果任务涉及敏感数据或不可信代码，优先选择 Fork 模式（详见 13.2 节）。
3. **最后检查耗时**：加速比超过 2 倍时值得并行，低于 1.5 倍时串行更简单可靠。
4. **混合模式**：实际系统中常将三种模式嵌套使用。例如：外层串行（阶段 1→阶段 2→阶段 3），每个阶段内并行。

## 四、粒度判定的常见陷阱

### 4.1 过度分解（Over-decomposition）

将任务拆解到过于细粒度会导致"协调开销吞噬执行收益"。

**症状**：
- Agent 数量超过可用资源（CPU core、API 并发配额）
- 任务分配 + 结果合并的时间 > 子任务执行时间
- 日志被协调消息淹没，难以定位真实问题

**反面案例**：
```
❌ 错误做法：把 100 行代码的逐行翻译拆成 100 个子 Agent
   - 分配 100 个 Context Window：约 100 × 400ms = 40s 初始化
   - 合并 100 个结果片段：需要额外的格式对齐
   - 总耗时 ≈ 串行执行的 5 倍

✅ 正确做法：按段落/章节拆分为 5-10 个子任务
   - 每个子任务处理 10-20 行，上下文完整
   - 合并结果时只需要拼接，无需调整
```

**经验法则**：子任务数不应超过可用 Worker 数的 2-3 倍。每个子任务的执行时间不低于 200ms（低于此值则协调开销占比过高）。

### 4.2 粒度不一致（Inconsistent Granularity）

同一批次中的子任务执行时间相差超过 10 倍，导致"长尾等待"。

```
问题：并行执行 5 个子任务
  SubTask A: 100ms   ✅
  SubTask B: 150ms   ✅
  SubTask C: 200ms   ✅
  SubTask D: 5000ms  ❌ (瓶颈)
  SubTask E: 120ms   ✅
  
总耗时 = 5000ms（受限于最慢任务）
加速比 = (100+150+200+5000+120) / 5000 = 1.1x ❌ 几乎等于串行
```

**解决方案**：
- 将长任务进一步拆分，或使用"分治"递归分解
- 对短任务进行批处理（Batch），减少 Worker 占用
- 对不同粒度的子任务分配不同的优先级和资源

### 4.3 忽略协调成本

协调（Coordination）不是免费的。每次任务分发、状态同步、结果合并都有成本。

| 协调操作 | 成本 | 说明 |
|---------|------|------|
| 创建子 Agent 上下文 | 100-500ms | 加载系统 Prompt、初始化工具列表 |
| 序列化/反序列化参数 | 10-50ms | 将 Python 对象转 JSON 传输 |
| 跨进程通信（IPC） | 1-10ms | 进程间数据传输（见 13.4 节） |
| 结果合并 | 50-200ms | 格式对齐、冲突消解 |
| 错误处理 | 100-1000ms | 重试、降级、转人工 |

**成本阈值**：当协调总成本 > 子任务执行总成本的 30% 时，说明粒度太细，需要合并子任务。

## 五、生产实践：任务粒度配置化

在生产系统中，任务粒度不应硬编码在代码中，而应通过配置动态调整：

```yaml
# task_decomposition_config.yaml
decomposition:
  strategy: "hybrid"  # sequential | parallel | fork | hybrid
  
  granularity_rules:
    min_subtask_time_ms: 200        # 子任务最小执行时间
    max_subtasks_per_worker: 3      # 每个 Worker 最大子任务数
    coordination_overhead_pct: 0.3  # 协调成本占比上限
    
  dependency:
    auto_detect: true               # 自动检测子任务依赖
    max_sequential_chain: 5         # 最长串行链
    
  isolation:
    auto_isolate_sensitive: true    # 自动为敏感任务启用 Fork
    isolation_keywords:             # 触发隔离的关键词
      - "password"
      - "api_key"
      - "personal_info"
```

```python
# 运行时根据配置动态选择执行模式
class TaskExecutor:
    def execute(self, task: ComplexTask):
        subtasks = self.decompose(task)
        
        for sub in subtasks:
            sub.estimated_time = self.estimator.estimate(sub)
        
        mode = self.select_mode(subtasks)
        
        if mode == "sequential":
            return self._execute_sequential(subtasks)
        elif mode == "parallel":
            return self._execute_parallel(subtasks)
        elif mode == "fork":
            return self._execute_fork(subtasks)
        elif mode == "hybrid":
            return self._execute_hybrid(subtasks)
```

这种设计让运维人员可以在不修改代码的情况下调整任务分解策略，适应不同场景下的性能需求。

## 关键概念速查

| 术语 | 解释 |
|------|------|
| 任务粒度（Task Granularity） | 子任务的大小和复杂度，决定如何分配给 Agent |
| 依赖密度（Dependency Density） | 子任务间数据耦合程度，决定串行还是并行 |
| Fork 模式 | 为子任务创建独立上下文窗口和工具集的执行模式 |
| 并行加速比（Speedup） | 串行耗时 / 并行耗时，衡量并行化收益 |
| 错误传播半径 | 单个子任务失败影响的范围，决定隔离策略 |
| 过度分解 | 任务拆得过细导致协调开销超过执行收益 |
| 协调成本（Coordination Overhead） | 任务分发、状态同步、结果合并的总开销 |
