# 20.4 评估→训练闭环

> 评估本身不是目的，改进 Agent 才是。评估→训练闭环（Evaluation-Training Loop）将每一个评估失败案例转化为改进的养料，形成"发现问题→诊断根因→实施改进→验证效果→部署上线"的持续迭代飞轮。**让每一次失败都让 Agent 变得更强。**

---

## 一、闭环的核心逻辑

### 1.1 为什么需要闭环？

传统的 Agent 开发模式是**瀑布式的**——开发、评估、上线彼此割裂：

```
传统模式：
  开发 → 评估 → 发现 N 个问题 → 手动修复 → 重新评估 → 上线
  
问题：
  - 每次评估后发现问题，但同类问题在下一次迭代中再次出现
  - 失败案例无人追踪，无人分析，知识流失
  - 改进措施的效果无法量化验证
  - 问题修复速度远落后于新功能开发速度
```

评估→训练闭环将这一过程改造为**持续学习的数据飞轮**：

```
闭环模式：
                  ┌──────────────┐
                  │  生产环境     │
                  │  (在线流量)   │
                  └──────┬───────┘
                         │
                    ┌────▼───────┐
                    │ 实时监控    │
                    │ 异常捕获    │
                    └────┬───────┘
                         │ 失败案例
                    ┌────▼───────┐
              ┌────►│ 失败归类    │◄────┐
              │     └────┬───────┘     │
              │          │             │
              │     ┌────▼───────┐     │
              │     │ 根因诊断    │     │ 回归测试不通过
              │     └────┬───────┘     │
              │          │             │
              │     ┌────▼───────┐     │
              │     │ Skill 改进  │─────┘
              │     └────┬───────┘
              │          │
              │     ┌────▼───────┐
              │     │ 回归测试    │
              │     └────┬───────┘
              │          │ 通过
              │     ┌────▼───────┐
              │     │ 灰度部署    │
              │     └────┬───────┘
              │          │
              └──────────┘
```

### 1.2 闭环的核心收益

| 收益 | 量化表现 | 来源 |
|------|---------|------|
| 缺陷率降低 | -70% ~ -90%（3个迭代周期内） | Google MLOps 实践报告 |
| 迭代速度提升 | 2-5 倍 | 自动化归因减少人工分析时间 |
| 改进效果可追溯 | 每一次改进都有量化指标 | 回归测试与 A/B 测试 |
| 团队知识积累 | 失败案例库成为组织知识资产 | 系统化记录与分析 |

## 二、第一步：失败案例自动归类（Failure Classification）

### 2.1 失败类别体系

首先需要建立统一的失败分类法。Agent 失败通常可分为以下类别：

| 大类 | 子类 | 定义 | 示例 |
|------|------|------|------|
| **理解失败** | 意图识别错误 | 未能正确理解用户意图 | 用户问"退款"，Agent 以为要"查询订单" |
| | 歧义未澄清 | 面对模糊指令未请求澄清 | 用户说"删掉它"，Agent 直接删除而非确认 |
| | 上下文丢失 | 未能保持对话上下文 | 用户在第 3 轮提及的信息，第 5 轮忘了 |
| **推理失败** | 逻辑断裂 | 推理步骤中出现了逻辑跳跃 | 从"A > B"和"B > C"推不出"A > C" |
| | 过度自信 | 在证据不足时做出确定结论 | 仅凭一个来源就下结论，如 14.5 节所述 |
| | 目标遗忘 | 多步任务中偏离原始目标 | 本来要订机票，讨论行李后忘了订机票 |
| **执行失败** | 工具选择错误 | 选择了不合适的工具 | 需要查数据库却调用了搜索 API |
| | 参数错误 | 工具调用参数错误 | 传入了错误的日期格式 |
| | 结果解析错误 | 错误解读工具的返回结果 | API 返回 error 却被认为是 success |
| **知识失败** | 幻觉 | 生成不符合事实的内容（见 14.1 节） | 编造不存在的政策条款 |
| | 知识不足 | 缺乏完成任务的必要知识 | 用户问的是内部知识库中不存在的信息 |
| | 时效性错误 | 使用过时的信息 | 参考了 2022 年的定价信息而非 2025 年 |
| **安全失败** | 拒绝不当 | 拒绝合理请求 | 用户问内部电话号码却被拒绝 |
| | 边界违反 | 执行了超出权限的操作 | 试图删除其他部门的数据 |

### 2.2 自动化归类实现

```python
class FailureClassifier:
    """
    失败案例自动归类系统
    
    基于 LLM 对 Agent 的执行轨迹进行自动分类
    """
    
    def __init__(self, llm):
        self.llm = llm
        self.classification_schema = self._build_schema()
    
    def _build_schema(self):
        """构建分类体系"""
        return {
            "understanding": {
                "name": "理解失败",
                "subcategories": ["intent_misunderstanding", "ambiguity", "context_loss"]
            },
            "reasoning": {
                "name": "推理失败",
                "subcategories": ["logic_break", "overconfidence", "goal_forgetting"]
            },
            "execution": {
                "name": "执行失败",
                "subcategories": ["tool_selection", "parameter_error", "result_parsing"]
            },
            "knowledge": {
                "name": "知识失败",
                "subcategories": ["hallucination", "insufficient_knowledge", "timeliness"]
            },
            "safety": {
                "name": "安全失败",
                "subcategories": ["improper_refusal", "boundary_violation"]
            }
        }
    
    def classify(self, trace: dict) -> dict:
        """
        对 Agent 执行轨迹进行失败归类
        
        Args:
            trace: {
                "task": "用户原始任务描述",
                "steps": [...],  # Agent 执行的每一步
                "final_output": "...",
                "expected_output": "...",
                "success": False,
                "error_message": "..."
            }
        
        Returns:
            classification: {
                "primary_category": "execution",
                "primary_subcategory": "tool_selection",
                "confidence": 0.92,
                "all_categories": [...],
                "reasoning": "Agent 选择了 search_products 工具但需要的是 search_orders..."
            }
        """
        prompt = self._build_classification_prompt(trace)
        response = self.llm.generate(prompt)
        classification = self._parse_response(response)
        
        return classification
    
    def _build_classification_prompt(self, trace: dict) -> str:
        """构建分类 prompt"""
        schema_text = json.dumps(self.classification_schema, ensure_ascii=False, indent=2)
        
        prompt = f"""请分析以下 Agent 执行轨迹，判断失败的主要原因类别。

## 分类体系
{schema_text}

## 任务描述
{trace.get('task', 'N/A')}

## Agent 执行步骤
{self._format_steps(trace.get('steps', []))}

## 最终输出
{trace.get('final_output', 'N/A')}

## 期望输出
{trace.get('expected_output', 'N/A')}

## 错误信息
{trace.get('error_message', 'N/A')}

## 要求
1. 从主类别中选择一个最匹配的
2. 从子类别中选择一个最具体的
3. 给出置信度分数 (0-1)
4. 给出分类理由
5. 如果涉及多个失败类型，请标注"次要类别"

## 输出格式（JSON）
{{
    "primary_category": "execution",
    "primary_subcategory": "tool_selection",
    "confidence": 0.92,
    "secondary_categories": [],
    "reasoning": "详细的分析理由..."
}}
"""
        return prompt
    
    def _format_steps(self, steps: list) -> str:
        """格式化步骤供 LLM 分析"""
        formatted = []
        for i, step in enumerate(steps):
            formatted.append(
                f"步骤 {i+1} [{step.get('type', 'unknown')}]: "
                f"输入={step.get('input', 'N/A')}, "
                f"输出={step.get('output', 'N/A')}, "
                f"状态={step.get('status', 'N/A')}"
            )
        return "\n".join(formatted)
    
    def _parse_response(self, response: str) -> dict:
        """解析 LLM 返回的分类结果"""
        try:
            import re
            json_match = re.search(r'\{.*\}', response, re.DOTALL)
            if json_match:
                return json.loads(json_match.group())
        except (json.JSONDecodeError, AttributeError):
            pass
        
        return {
            "primary_category": "unknown",
            "primary_subcategory": "unknown",
            "confidence": 0.0,
            "reasoning": "Failed to parse LLM response"
        }
    
    def batch_classify(self, traces: list) -> list:
        """批量归类失败案例"""
        classifications = []
        
        for trace in traces:
            if not trace.get("success", True):
                classifications.append(self.classify(trace))
        
        return classifications
```

### 2.3 失败分布分析

```python
def analyze_failure_distribution(classifications: list) -> dict:
    """
    分析失败案例的分布
    
    生成失败类别分布报告，用于识别系统性的薄弱环节
    """
    from collections import Counter
    
    primary_dist = Counter()
    subcategory_dist = Counter()
    confidence_sum = Counter()
    
    for c in classifications:
        primary_dist[c["primary_category"]] += 1
        subcategory_dist[c["primary_subcategory"]] += 1
        confidence_sum[c["primary_category"]] += c.get("confidence", 1.0)
    
    total = len(classifications)
    
    report = {
        "total_failures": total,
        "primary_distribution": {
            k: {
                "count": v,
                "percentage": round(v / total * 100, 1)
            }
            for k, v in primary_dist.most_common()
        },
        "subcategory_distribution": {
            k: {
                "count": v,
                "percentage": round(v / total * 100, 1)
            }
            for k, v in subcategory_dist.most_common()
        },
        "avg_confidence_by_category": {
            k: round(v / primary_dist[k], 2)
            for k, v in confidence_sum.items()
        },
        "top_3_failure_types": [
            {"category": k, "count": v, "percentage": round(v / total * 100, 1)}
            for k, v in subcategory_dist.most_common(3)
        ]
    }
    
    return report
```

## 三、第二步：根因诊断（Root Cause Diagnosis）

### 3.1 根因诊断方法论

失败归类告诉"哪里失败了"，根因诊断回答"为什么失败"。常见的根因类型：

| 根因类型 | 说明 | 诊断方法 |
|---------|------|---------|
| **Prompt 缺陷（15.3 节）** | 指令不清晰、示例不充分、约束条件缺失 | 检查 Prompt 中指令的完备性 |
| **上下文缺失** | Agent 推理时缺少关键上下文信息 | 分析步骤间上下文传递链 |
| **工具定义不完整** | 工具描述不准确、参数说明不完整 | 检查 Tool Definition 的清晰度 |
| **模型能力不足** | 当前模型在该类型任务上能力不够 | 与更强模型的结果对比 |
| **数据质量差** | 检索到的文档内容错误或不完整 | 分析检索结果的准确性 |
| **评估标准问题** | 任务被标记为失败但实际是正确的 | 复查评估标准 |

### 3.2 根因诊断实现

```python
class RootCauseAnalyzer:
    """
    根因诊断系统
    
    对归类后的失败案例进行深度分析，定位根因
    """
    
    def __init__(self, llm, prompt_template: str = None):
        self.llm = llm
        self.prompt_template = prompt_template or self._default_template()
    
    def _default_template(self) -> str:
        return """你是 Agent 系统调试专家。请分析以下 Agent 失败的根因。

## 任务
{task}

## Agent 执行轨迹
{trace}

## 失败类别
{category}

## 失败子类别
{subcategory}

## 诊断方向
请分析以下可能的根因（选择最可能的 1-2 个）：
1. 【Prompt 问题】指令是否明确？示例中是否覆盖了该场景？
2. 【工具问题】工具定义是否完整？参数描述是否清晰？
3. 【上下文问题】Agent 推理时是否缺少关键信息？
4. 【模型问题】该场景所需的推理能力是否超出当前模型的能力范围？
5. 【数据问题】检索到的数据是否准确、充分？
6. 【评估问题】失败判定是否合理？

## 输出格式
{{
    "root_causes": [
        {{
            "type": "prompt_issue",
            "confidence": 0.85,
            "description": "...",
            "evidence": ["...", "..."],
            "suggested_fix": "..."
        }}
    ],
    "severity": "high",
    "fix_effort": "medium" 
}}
"""
    
    def diagnose(self, trace: dict, classification: dict) -> dict:
        """诊断单个失败案例的根因"""
        prompt = self.prompt_template.format(
            task=trace.get("task", ""),
            trace=json.dumps(trace.get("steps", []), ensure_ascii=False, indent=2),
            category=classification.get("primary_category", ""),
            subcategory=classification.get("primary_subcategory", "")
        )
        
        response = self.llm.generate(prompt)
        
        try:
            import re
            json_match = re.search(r'\{.*\}', response, re.DOTALL)
            if json_match:
                diagnosis = json.loads(json_match.group())
            else:
                diagnosis = self._fallback_diagnosis(classification)
            
            diagnosis["trace_id"] = trace.get("id", "unknown")
            diagnosis["category"] = classification.get("primary_category")
            return diagnosis
            
        except (json.JSONDecodeError, AttributeError):
            return self._fallback_diagnosis(classification)
    
    def _fallback_diagnosis(self, classification: dict) -> dict:
        """当 LLM 诊断失败时的后备方案"""
        category = classification.get("primary_category", "")
        subcategory = classification.get("primary_subcategory", "")
        
        # 规则性的根因映射
        fallback_map = {
            "execution.tool_selection": {
                "type": "tool_definition",
                "fix": "检查工具描述是否清晰，是否缺少使用条件说明"
            },
            "knowledge.hallucination": {
                "type": "context_or_prompt",
                "fix": "检查 RAG 上下文是否充分，或添加"未找到相关信息时请说明"指令"
            },
            "reasoning.goal_forgetting": {
                "type": "prompt_issue",
                "fix": "在 System Prompt 中添加"请始终牢记原始目标"的指令"
            },
            "understanding.intent_misunderstanding": {
                "type": "prompt_issue",
                "fix": "增加意图识别示例，特别是边界情况"
            }
        }
        
        key = f"{category}.{subcategory}"
        if key in fallback_map:
            return {
                "root_causes": [{
                    "type": fallback_map[key]["type"],
                    "confidence": 0.5,
                    "description": f"基于规则的根因推断: {key}",
                    "suggested_fix": fallback_map[key]["fix"]
                }],
                "severity": "medium",
                "fix_effort": "medium"
            }
        
        return {
            "root_causes": [{
                "type": "unknown",
                "confidence": 0.0,
                "description": "无法自动诊断根因，需要人工分析",
                "suggested_fix": "请人工审查此案例"
            }],
            "severity": "medium",
            "fix_effort": "unknown"
        }
```

### 3.3 聚合根因分析

```python
def aggregate_root_causes(diagnoses: list) -> dict:
    """
    聚合多个根因诊断结果，识别系统性根因
    
    找出影响面最大的根因，作为改进的优先级排序依据
    """
    from collections import Counter
    
    cause_types = Counter()
    cause_fixes = []
    severity_counter = Counter()
    
    for d in diagnoses:
        for rc in d.get("root_causes", []):
            cause_types[rc.get("type", "unknown")] += 1
            cause_fixes.append({
                "type": rc.get("type"),
                "fix": rc.get("suggested_fix", ""),
                "severity": d.get("severity", "medium")
            })
        severity_counter[d.get("severity", "medium")] += 1
    
    # 按根因类型分组，计算影响面
    total = len(diagnoses)
    systemic_issues = []
    
    for cause_type, count in cause_types.most_common():
        impact_pct = count / total * 100
        systemic_issues.append({
            "root_cause_type": cause_type,
            "affected_cases": count,
            "impact_percentage": round(impact_pct, 1),
            "suggested_fixes": list(set(
                f["fix"] for f in cause_fixes if f["type"] == cause_type
            ))[:3]  # 最多 3 个修复建议
        })
    
    return {
        "total_diagnosed": total,
        "systemic_issues": systemic_issues,
        "severity_summary": dict(severity_counter),
        "priority_action": systemic_issues[0] if systemic_issues else None,
        "recommendation": (
            f"首要改进方向: {systemic_issues[0]['root_cause_type']}, "
            f"影响 {systemic_issues[0]['impact_percentage']}% 的失败案例"
        ) if systemic_issues else "无系统性根因发现"
    }
```

## 四、第三步：Skill 改进（Skill Improvement）

### 4.1 Skill 改进策略

根据根因类型，采取不同的改进策略：

| 根因类型 | 改进策略 | 实施方式 | 预期效果 |
|---------|---------|---------|---------|
| **Prompt 问题** | 优化 System Prompt / 增加 Few-shot 示例 | 手动修改 Prompt 或自动 Prompt 优化 | 影响面大，修复快 |
| **工具定义问题** | 完善工具描述、参数约束 | 修改 Tool Definition | 直接影响工具调用准确率 |
| **上下文问题** | 优化 RAG 策略、上下文压缩 | 调整检索逻辑或上下文窗口管理 | 提升忠实度（见 20.1 节） |
| **模型能力问题** | 升级模型或添加验证步骤 | 切换到更强模型或增加自验证循环（见 14.3 节） | 成本增加，但效果显著 |
| **数据问题** | 修正知识库数据 | 清洗/更新知识库文档 | 持久性改进 |

### 4.2 改进优先级排序

```python
def prioritize_improvements(systemic_issues: list, effort_estimates: dict) -> list:
    """
    基于影响面和改进成本计算优先级
    
    使用 ICE 评分框架（Impact × Confidence × Ease）
    """
    prioritized = []
    
    for issue in systemic_issues:
        cause_type = issue["root_cause_type"]
        impact = issue["impact_percentage"] / 100.0  # 0-1
        
        # 信心分数：根因诊断的可信度
        confidence = effort_estimates.get(cause_type, {}).get("confidence", 0.5)
        
        # 改进难度（1=容易, 0=困难）
        ease = 1 - (effort_estimates.get(cause_type, {}).get("effort_days", 5) / 30)
        ease = max(0.1, min(1.0, ease))
        
        ice_score = impact * confidence * ease
        
        prioritized.append({
            "root_cause": cause_type,
            "ice_score": round(ice_score, 2),
            "impact": round(impact, 2),
            "confidence": round(confidence, 2),
            "ease": round(ease, 2),
            "estimated_effort_days": effort_estimates.get(cause_type, {}).get("effort_days", 5),
            "suggested_fixes": issue.get("suggested_fixes", [])
        })
    
    # 按 ICE 分数降序排列
    prioritized.sort(key=lambda x: x["ice_score"], reverse=True)
    
    return prioritized
```

### 4.3 自动 Prompt 优化（Advanced）

对于 Prompt 类根因，可以实施自动优化：

```python
class AutoPromptOptimizer:
    """
    基于失败案例自动优化 Prompt
    """
    
    def __init__(self, llm, eval_fn):
        self.llm = llm
        self.eval_fn = eval_fn  # 评估函数，返回成功/失败
    
    def optimize(self, current_prompt: str, failed_cases: list) -> str:
        """
        基于失败案例自动优化 Prompt
        
        Args:
            current_prompt: 当前的 System Prompt
            failed_cases: 失败案例列表（每个包含 task 和 trace）
        
        Returns:
            optimized_prompt: 优化后的 Prompt
        """
        # 步骤 1：提取失败模式
        failure_patterns = self._extract_patterns(failed_cases)
        
        # 步骤 2：生成改进建议
        suggestions = self._generate_suggestions(current_prompt, failure_patterns)
        
        # 步骤 3：生成新 Prompt
        new_prompt = self._apply_suggestions(current_prompt, suggestions)
        
        # 步骤 4：在失败案例上验证
        improved_count = 0
        for case in failed_cases:
            result = self.eval_fn(new_prompt, case)
            if result["success"]:
                improved_count += 1
        
        improvement_rate = improved_count / len(failed_cases)
        
        return {
            "optimized_prompt": new_prompt,
            "improvement_rate": improvement_rate,
            "suggestions_applied": suggestions,
            "note": f"在 {len(failed_cases)} 个失败案例上验证，"
                    f"修复率 {improvement_rate:.1%}"
        }
    
    def _extract_patterns(self, cases: list) -> list:
        """提取失败模式"""
        # 实现省略：分析失败案例中的共同模式
        patterns = []
        for case in cases:
            # 识别失败时的共同特征
            pass
        return patterns
    
    def _generate_suggestions(self, prompt: str, patterns: list) -> list:
        """生成 Prompt 改进建议"""
        suggestions = []
        
        for pattern in patterns:
            suggestion_prompt = f"""
            基于以下失败模式，给出 System Prompt 的改进建议：
            
            当前 Prompt 开头部分：{prompt[:500]}...
            失败模式：{pattern}
            
            改进建议：
            """
            response = self.llm.generate(suggestion_prompt)
            suggestions.append(response)
        
        return suggestions
    
    def _apply_suggestions(self, prompt: str, suggestions: list) -> str:
        """应用改进建议到 Prompt"""
        # 简化实现：将建议添加到 Prompt 末尾
        improved = prompt + "\n\n## 补充指令\n"
        for s in suggestions:
            improved += f"- {s}\n"
        return improved
```

## 五、第四步：回归测试（Regression Testing）

### 5.1 回归测试集的构建

回归测试集（Regression Test Suite）是所有改进过或发现过问题的案例的集合：

```python
class RegressionTestSuite:
    """
    回归测试集管理器
    
    管理所有历史失败案例，确保每次修改不会引入新的回归
    """
    
    def __init__(self, storage_path: str):
        self.storage_path = storage_path
        self.test_cases = self._load()
    
    def add_case(self, trace: dict, classification: dict, diagnosis: dict):
        """添加新的回归测试用例"""
        test_case = {
            "id": f"REG-{len(self.test_cases) + 1:05d}",
            "task": trace["task"],
            "expected_steps": trace.get("expected_steps", []),
            "expected_output": trace.get("expected_output", ""),
            "category": classification,
            "root_cause": diagnosis,
            "added_at": self._timestamp(),
            "last_result": None
        }
        
        self.test_cases.append(test_case)
        self._save()
        
        return test_case["id"]
    
    def run(self, agent_fn) -> dict:
        """
        运行全部回归测试
        
        Args:
            agent_fn: Agent 函数，输入 task 返回执行结果
        
        Returns:
            test_report: 测试报告
        """
        passed = 0
        failed = 0
        regressions = []  # 之前修好又复现的
        improvements = []  # 之前失败现在成功的
        
        for case in self.test_cases:
            result = agent_fn(case["task"])
            
            success = self._check_result(result, case)
            
            if success:
                passed += 1
                if case.get("last_result") == "failed":
                    improvements.append(case["id"])
            else:
                failed += 1
                if case.get("last_result") == "passed":
                    regressions.append(case["id"])
            
            case["last_result"] = "passed" if success else "failed"
        
        self._save()
        
        return {
            "total": len(self.test_cases),
            "passed": passed,
            "failed": failed,
            "pass_rate": round(passed / len(self.test_cases) * 100, 1) if self.test_cases else 0,
            "regressions": regressions,
            "improvements": improvements,
            "blocker": failed > len(self.test_cases) * 0.05  # 超过 5% 失败则阻塞发布
        }
    
    def _check_result(self, result: dict, case: dict) -> bool:
        """检查结果是否通过"""
        # 实现取决于具体 Agent 的评估方式
        return result.get("success", False)
    
    def _load(self) -> list:
        import os
        if os.path.exists(self.storage_path):
            with open(self.storage_path, 'r', encoding='utf-8') as f:
                return json.load(f)
        return []
    
    def _save(self):
        with open(self.storage_path, 'w', encoding='utf-8') as f:
            json.dump(self.test_cases, f, ensure_ascii=False, indent=2)
    
    def _timestamp(self) -> str:
        from datetime import datetime
        return datetime.now().isoformat()
```

### 5.2 分层的回归测试策略

```
回归测试金字塔：

  Level 1: 烟雾测试（Smoke Test） — 5-10 个核心场景
  ├── 每次代码提交时运行
  ├── 耗时 < 1 分钟
  └── 确保最基本的场景可用

  Level 2: 核心回归（Core Regression） — 50-200 个案例
  ├── 每次 PR 合入前运行
  ├── 耗时 5-15 分钟
  └── 覆盖所有已知的失败类型

  Level 3: 全量回归（Full Regression） — 500-2000+ 个案例
  ├── 发布前运行
  ├── 耗时 30-120 分钟
  └── 包含所有历史案例 + 新场景

  Level 4: 探索性回归（Exploratory） — 动态生成
  ├── 每周运行一次
  ├── 耗时 1-4 小时
  └── 覆盖边界情况和组合场景
```

## 六、第五步：部署（Deployment）

### 6.1 渐进式部署策略

改进验证通过后，采用灰度发布逐步上量：

```python
class ProgressiveDeployment:
    """
    渐进式部署管理器
    
    通过逐步增加流量比例来降低发布风险
    """
    
    def __init__(self, name: str, steps: list = None):
        self.name = name
        self.steps = steps or [
            {"traffic_pct": 5, "duration_hours": 2, "monitor_metrics": ["hhr", "ttft", "tsr"]},
            {"traffic_pct": 20, "duration_hours": 4, "monitor_metrics": ["hhr", "ttft", "tsr"]},
            {"traffic_pct": 50, "duration_hours": 8, "monitor_metrics": ["hhr", "ttft", "tsr"]},
            {"traffic_pct": 100, "duration_hours": 0, "monitor_metrics": ["hhr", "ttft", "tsr"]}
        ]
        self.current_step = 0
    
    def should_proceed(self, metrics: dict) -> bool:
        """
        根据监控指标判断是否可以进入下一阶段
        
        Args:
            metrics: 当前部署版本的监控指标
        
        Returns:
            proceed: 是否可以继续
        """
        if self.current_step >= len(self.steps):
            return True
        
        step = self.steps[self.current_step]
        
        # 检查所有需要监控的指标是否在可接受范围内
        for metric in step.get("monitor_metrics", []):
            if metric not in metrics:
                return False
            
            value = metrics[metric]
            threshold = self._get_threshold(metric, step.get("traffic_pct"))
            
            if value > threshold:
                print(f"[DEPLOY] 指标 {metric} = {value}, 超过阈值 {threshold}, 暂停发布")
                return False
        
        return True
    
    def advance(self) -> int:
        """进入下一阶段"""
        if self.current_step < len(self.steps):
            self.current_step += 1
        return self.current_step
    
    def rollback(self):
        """回滚到上一阶段"""
        if self.current_step > 0:
            self.current_step -= 1
    
    def _get_threshold(self, metric: str, traffic_pct: int) -> float:
        """获取指标的动态阈值（低流量时可容忍较高偏差）"""
        base_thresholds = {
            "hhr": 0.30,    # 转人工率 < 30%
            "ttft": 3.0,    # 首 Token 延迟 < 3s
            "tsr": 0.70,    # 任务成功率 > 70%
            "aht": 300,     # 平均处理时长 < 300s
        }
        
        # 低流量时阈值放宽（统计意义较弱）
        tolerance_factor = max(1.0, (100 - traffic_pct) / 50)
        
        if metric == "tsr":
            # 成功率：低流量时接受较低成功率
            return base_thresholds.get(metric, 0.7) * (1 / tolerance_factor)
        else:
            # 其他指标：低流量时接受较高值（更宽松）
            return base_thresholds.get(metric, 0.3) * tolerance_factor
```

### 6.2 闭环的持续运行

评估→训练闭环不是一次性的，而是需要持续运行的工程流程：

```
日常循环（Daily）：
  1. 从生产日志中采集失败案例
  2. 自动归类失败案例
  3. 累计到一定数量（如 50 个）触发根因诊断

迭代循环（Sprint）：
  4. 聚合根因分析，确定改进优先级
  5. 实施 Top 3 改进（Prompt / 工具 / 数据）
  6. 运行回归测试
  7. 灰度发布

持续监控（Continuous）：
  8. 监控各层指标（见 20.1 节四层评估模型）
  9. 指标异常时触发告警
  10. 回归测试失败时阻塞发布
```
