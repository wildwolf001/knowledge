# 20.1 四层评估模型

> "你的 Agent 好不好？"——这个问题看似简单，但 Agent 系统涉及输出生成、工具调用、多步推理、用户交互等多个环节，单一指标无法全面反映系统质量。四层评估模型从**输出质量→行为质量→用户体验→业务指标**四个递进层级构建评估体系，确保每个维度都得到量化衡量。

---

## 一、为什么需要四层评估？

### 1.1 单指标评估的陷阱

传统 LLM 评估往往只关注"回答是否正确"（准确率），这在 Agent 场景中远远不够：

| 维度 | 单一指标 | 遗漏信息 |
|------|---------|---------|
| 输出质量 | 答案准确率 95% | 但其中 30% 的任务需要 5 轮以上对话才能完成 |
| 行为质量 | 任务完成率 80%| 但每次调用工具时平均需要 2.3 次重试 |
| 用户体验 | 用户满意度 4.2/5 | 但首 Token 延迟高达 3.8 秒，用户流失率 25% |
| 业务指标 | 日均处理量 1000 单 | 但转人工率从之前的 30% 升到了 45% |

**关键洞察**：上层指标的"好看"可能掩盖下层指标的问题。例如，一个准确率很高的 Agent 可能因为响应太慢而被用户抛弃；一个任务完成率高的 Agent 可能因为频繁转人工而让运营成本飙升。

### 1.2 四层评估模型的总览

```
第一层：输出质量（Output Quality）
  ├── 准确性（Accuracy）
  ├── 忠实度（Faithfulness）
  ├── 完整性（Completeness）
  └── 格式合规性（Format Compliance）

第二层：行为质量（Behavior Quality）
  ├── 任务完成率（Task Success Rate）
  ├── 工具调用准确率（Tool Accuracy）
  ├── 推理效率（Reasoning Efficiency）
  └── 错误恢复能力（Error Recovery）

第三层：用户体验（User Experience）
  ├── 首 Token 延迟（Time to First Token）
  ├── 端到端延迟（End-to-End Latency）
  ├── 放弃率（Abandonment Rate）
  └── 用户满意度（User Satisfaction）

第四层：业务指标（Business Metrics）
  ├── 转人工率（Human Handoff Rate）
  ├── 平均处理时长（Average Handling Time）
  ├── 一次性解决率（First Contact Resolution）
  └── 成本效益比（Cost Efficiency）
```

## 二、第一层：输出质量（Output Quality）

### 2.1 准确性（Accuracy）

准确性衡量 Agent 生成内容与客观事实的一致程度。对于有标准答案的任务，这是最直接的指标。

**精确匹配（Exact Match, EM）**：
```
EM = count(预测答案 == 标准答案) / 总样本数
```

对于选择题或分类任务，EM 直接可用；对于生成式任务，需要引入**参考答案匹配**。

**F1 Score（基于 Token/词级别）**：

```python
def compute_f1_score(prediction, ground_truth):
    """计算预测与标准答案的 F1 分数（词级别）"""
    pred_tokens = set(prediction.lower().split())
    gt_tokens = set(ground_truth.lower().split())
    
    if len(pred_tokens) == 0 or len(gt_tokens) == 0:
        return 0.0
    
    common_tokens = pred_tokens & gt_tokens
    
    if len(common_tokens) == 0:
        return 0.0
    
    precision = len(common_tokens) / len(pred_tokens)
    recall = len(common_tokens) / len(gt_tokens)
    f1 = 2 * precision * recall / (precision + recall)
    
    return f1
```

**准确性评估的注意点**：
- 对于开放性任务（如"写一封营销邮件"），不存在唯一正确答案，准确性需要用**人类评估**或**LLM-as-Judge**（详见 20.3 节）来评判
- Agent 的多步输出中，中间结果的准确性与最终结果的准确性同等重要——中间步骤错误即使最终答案偶然正确也是不可靠的

### 2.2 忠实度（Faithfulness）

忠实度衡量 Agent 的输出是否忠实于给定的上下文（检索到的文档、用户输入、指令约束）。这与 14.1 节讨论的"忠实性幻觉"密切相关。

**忠实度评估的主要维度**：

| 维度 | 定义 | 检测方法 |
|------|------|---------|
| 上下文一致性 | 输出是否与给定上下文矛盾 | 检查输出声称与上下文事实的对立 |
| 指令遵循度 | 是否按照指令格式和要求输出 | 规则检查 + 模型判断 |
| 引用准确性 | 引用内容是否与原文一致 | 精确匹配引用段落 |
| 未添加无关信息 | 是否引入了上下文未提供的信息 | 查找输出中上下文不包含的声明 |

**忠实度评分实现**：

```python
def compute_faithfulness_score(response, context_chunks):
    """
    计算输出对上下文的忠实度
    
    Args:
        response: Agent 生成的回答
        context_chunks: 提供给 Agent 的上下文片段列表
    
    Returns:
        faithfulness_score: 0-1 之间的忠实度分数
    """
    # 步骤 1：从回答中提取所有事实性声明
    claims = extract_claims(response)
    
    # 步骤 2：检查每个声明是否能从上下文中得到支持
    supported = 0
    unsupported = 0
    contradicted = 0
    
    for claim in claims:
        support_evidence = check_claim_support(claim, context_chunks)
        if support_evidence == "supported":
            supported += 1
        elif support_evidence == "contradicted":
            contradicted += 1
        else:  # unsupported
            unsupported += 1
    
    total = len(claims)
    if total == 0:
        return 1.0
    
    # 分数 = 支持的声明比例 - 被矛盾的声明扣分
    score = (supported - contradicted) / total
    return max(0.0, score)


def extract_claims(text):
    """
    从文本中提取事实性声明
    
    简单实现使用句子分割 + 声明性句子识别
    生产环境推荐使用专门的 NLI 模型或 LLM 进行提取
    """
    import re
    sentences = re.split(r'[。！？\n]', text)
    claims = []
    for sent in sentences:
        sent = sent.strip()
        if sent and len(sent) > 5:
            # 过滤掉疑问句、祈使句等非声明性句子
            if not sent.endswith('？') and not sent.endswith('！'):
                claims.append(sent)
    return claims


def check_claim_support(claim, context_chunks):
    """
    使用 NLI（自然语言推理）模型判断声明是否被上下文支持
    可选方案：Entailment 模型、LLM-as-Judge、关键词匹配
    """
    # 简化实现：关键词重叠检查
    # 生产环境推荐使用 BART-MNLI 或类似的蕴含模型
    claim_keywords = set(claim.lower().split()[:10])
    max_overlap = 0
    for chunk in context_chunks:
        chunk_keywords = set(chunk.lower().split())
        overlap = len(claim_keywords & chunk_keywords)
        if overlap > max_overlap:
            max_overlap = overlap
    
    # 如果超过 40% 的关键词在上下文中出现，认为得到支持
    keyword_ratio = max_overlap / len(claim_keywords) if claim_keywords else 0
    if keyword_ratio >= 0.4:
        return "supported"
    elif keyword_ratio <= 0.1:
        return "unsupported"
    else:
        return "contradicted"
```

### 2.3 完整性（Completeness）

完整性评估 Agent 的回答是否涵盖了问题的所有必要方面。

**覆盖率评估**：对于有标准答案要点的问题，计算 Agent 回答覆盖了多少个必要要点：
```
Completeness = 覆盖的要点数 / 总必要要点数
```

**实现方式**：可以使用 LLM-as-Judge（20.3 节）或预定义检查清单来评估完整性。

### 2.4 格式合规性（Format Compliance）

格式合规性检查 Agent 输出是否符合预期的格式约束：
- JSON Schema 校验
- 指令格式遵循度
- 输出长度限制遵守度

```python
def validate_format_compliance(response, format_specs):
    """
    校验 Agent 输出是否符合格式要求
    
    Args:
        response: Agent 输出
        format_specs: 格式规范字典
    
    Returns:
        compliance_score: 0-1
        violations: 违规详情列表
    """
    score = 0.0
    violations = []
    total_checks = len(format_specs)
    
    for spec_name, spec in format_specs.items():
        if spec["type"] == "json":
            try:
                import json
                json.loads(response)
                score += 1
            except json.JSONDecodeError as e:
                violations.append(f"JSON 格式错误: {e}")
        
        elif spec["type"] == "max_length":
            if len(response) <= spec["value"]:
                score += 1
            else:
                violations.append(
                    f"超出最大长度限制 {spec['value']}, 实际 {len(response)}"
                )
        
        elif spec["type"] == "required_fields":
            all_present = all(
                field in response for field in spec["fields"]
            )
            if all_present:
                score += 1
            else:
                missing = [f for f in spec["fields"] if f not in response]
                violations.append(f"缺少必要字段: {missing}")
    
    return score / max(total_checks, 1), violations
```

## 三、第二层：行为质量（Behavior Quality）

### 3.1 任务完成率（Task Success Rate, TSR）

任务完成率是 Agent 最核心的行为指标：

```
TSR = 成功完成的任务数 / 总任务数
```

**成功的定义需要根据任务类型细化**：

| 任务类型 | 成功标准 |
|---------|---------|
| **信息查询** | 找到正确答案并正确呈现 |
| **操作执行** | 工具调用链正确，操作完成且影响正确 |
| **多轮对话** | 在约定轮数内达到用户目标 |
| **复杂推理** | 最终答案正确且推理路径合理 |

**部分成功评分（Partial Success Scoring）**：
对于复杂多步任务，二元的成功/失败评判过于粗糙。推荐使用**步骤级完成度加权**：

```python
def compute_partial_success_rate(trace, task_definition):
    """
    计算部分成功评分
    
    Args:
        trace: Agent 执行轨迹（包含所有步骤和中间结果）
        task_definition: 任务定义（包含各个步骤的权重）
    
    Returns:
        psr: 部分成功率 (0-1)
    """
    total_weight = sum(
        step["weight"] for step in task_definition["steps"]
    )
    
    achieved_weight = 0.0
    for step in task_definition["steps"]:
        step_result = trace.get_step_result(step["id"])
        if step_result["success"]:
            achieved_weight += step["weight"]
        elif step_result.get("partial", False):
            achieved_weight += step["weight"] * step_result["partial_ratio"]
    
    return achieved_weight / total_weight
```

### 3.2 工具调用准确率（Tool Accuracy）

Agent 的关键特征之一是调用外部工具。工具调用准确率衡量 Agent 是否正确选择了工具、传入了正确参数、并正确解析了结果。

**三级工具准确率**：

```
工具选择准确率 = 正确选择工具的调用次数 / 总工具调用次数

参数准确率 = 传参完全正确的调用次数 / 总工具调用次数

结果解析准确率 = 正确解析工具返回结果的次数 / 总工具调用次数

综合工具准确率 = 工具选择准确率 × 参数准确率 × 结果解析准确率
```

```python
def evaluate_tool_accuracy(traces):
    """
    评估 Agent 在一组执行轨迹中的工具调用准确率
    """
    total_calls = 0
    correct_tool = 0
    correct_params = 0
    correct_parsing = 0
    
    for trace in traces:
        for step in trace["steps"]:
            if step["type"] != "tool_call":
                continue
            total_calls += 1
            
            # 评估工具选择
            if step["tool_name"] == step["expected_tool"]:
                correct_tool += 1
            
            # 评估参数
            if step["params"] == step["expected_params"]:
                correct_params += 1
            else:
                # 部分匹配：检查必需参数是否都提供了
                required_ok = all(
                    k in step["params"] and step["params"][k] == v
                    for k, v in step["expected_params"].items()
                )
                if required_ok:
                    correct_params += 0.5
            
            # 评估结果解析
            if step.get("result_parsed_correctly", False):
                correct_parsing += 1
    
    if total_calls == 0:
        return {"tool_accuracy": 0, "detail": "no_tool_calls"}
    
    selection_acc = correct_tool / total_calls
    param_acc = correct_params / total_calls
    parsing_acc = correct_parsing / total_calls
    composite = selection_acc * param_acc * parsing_acc
    
    return {
        "selection_accuracy": selection_acc,
        "parameter_accuracy": param_acc,
        "parsing_accuracy": parsing_acc,
        "composite_accuracy": composite,
        "total_calls": total_calls
    }
```

### 3.3 推理效率（Reasoning Efficiency）

推理效率衡量 Agent 以最短路径完成任务的能力，避免不必要的步骤或重复劳动。

**关键指标**：

```
路径效率（Path Efficiency）：
  PE = 最优步数 / Agent 实际步数
  
  当 PE = 1 时，Agent 以最优路径完成任务
  当 PE < 0.5 时，Agent 做了超过必要一倍以上的步骤

冗余步骤率：
  RSR = 多余步骤数 / 总步骤数
  多余步骤包括：重复查询、不必要的工具调用、冗余确认
```

### 3.4 错误恢复能力（Error Recovery）

Agent 在遇到错误时的恢复能力是鲁棒性的关键指标。

```
错误恢复率 = 从错误中成功恢复的任务数 / 总出错任务数

恢复效率 = 恢复后的额外步数 / 恢复前已用步数
```

**错误恢复的典型模式**：
1. **自动重试**：工具调用失败后自动重试（通常在 3 次内）
2. **降级策略**：首选工具不可用时切换到备选方案
3. **求助用户**：无法恢复时向用户请求澄清信息
4. **优雅降级**：无法完成任务时提供部分结果而非完全失败

## 四、第三层：用户体验（User Experience）

### 4.1 首 Token 延迟（Time to First Token, TTFT）

首 Token 延迟是用户感知 Agent"思考时间"的最直接指标。它包含网络传输时间 + 模型处理时间。

```
TTFT = 用户发送请求时间戳 - Agent 开始输出首 Token 时间戳
```

**经验阈值**：
| TTFT 范围 | 用户体验评价 |
|-----------|------------|
| < 500ms | 流畅，几乎无感知 |
| 500ms - 1.5s | 可接受，轻微等待 |
| 1.5s - 3s | 明显等待，用户开始不耐烦 |
| > 3s | 不可接受，用户流失风险高 |

### 4.2 端到端延迟（End-to-End Latency, E2EL）

对于 Agent 的完整任务，端到端延迟衡量从用户请求到最终回应呈现的总耗时。

```python
def compute_latency_metrics(traces):
    """
    计算完整的延迟指标体系
    """
    ttft_values = []
    e2e_values = []
    
    for trace in traces:
        ttft = trace["first_token_time"] - trace["request_time"]
        e2e = trace["response_complete_time"] - trace["request_time"]
        ttft_values.append(ttft)
        e2e_values.append(e2e)
    
    # P50 / P95 / P99 分位延迟
    # P50 代表"典型"体验，P95 代表"糟糕"体验，P99 代表"极端"体验
    import numpy as np
    return {
        "ttft_p50": np.percentile(ttft_values, 50),
        "ttft_p95": np.percentile(ttft_values, 95),
        "ttft_p99": np.percentile(ttft_values, 99),
        "e2e_p50": np.percentile(e2e_values, 50),
        "e2e_p95": np.percentile(e2e_values, 95),
        "e2e_p99": np.percentile(e2e_values, 99),
    }
```

### 4.3 放弃率（Abandonment Rate）

用户在使用 Agent 过程中因等待时间过长或体验不佳而放弃的比率。

```
放弃率 = 用户中途放弃的会话数 / 总会话数
```

**放弃的判定标准**：
- 用户在 Agent 响应生成过程中关闭页面
- 用户在收到 Agent 响应后直接关闭（无后续操作、无点击、无评分）
- 用户在等待超过一定时间后重复提交同一问题

**放弃率的归因分析**：
```
放弃率 ∝ f(延迟, 回答质量, 任务复杂度, 用户耐心)
```

- 延迟与放弃率大致呈对数线性关系：TTFT 每增加 1 秒，放弃率约上升 5-8%
- 首次回答质量差导致放弃的概率是后续回答质量差的 3 倍

### 4.4 用户满意度（User Satisfaction）

通过显式反馈和隐式信号综合评估：

**显式信号**：
- 点赞/点踩（Thumbs Up/Down）
- 满意度评分（1-5 星）
- 后续评论

**隐式信号**：
- 用户是否复制/收藏回答
- 用户是否继续追问
- 用户是否在得到回答后立即结束会话

**Net Promoter Score (NPS) 改造**：
```
Agent NPS = %的"推荐"用户 - %的"贬损"用户
其中：
- 推荐用户：满意度 ≥ 4（愿意向他人推荐）
- 贬损用户：满意度 ≤ 2（对 Agent 不满）
```

## 五、第四层：业务指标（Business Metrics）

### 5.1 转人工率（Human Handoff Rate, HHR）

Agent 将用户转接给人工客服的比例。这是衡量 Agent 自主解决能力的关键指标。

```
HHR = 转人工的会话数 / 总会话数
```

**分层转人工率**（按原因细分）：
| 转人工原因 | 期望范围 | 说明 |
|-----------|---------|------|
| 自动降级（低置信度）| < 10% | Agent 主动识别自己无法处理 |
| 用户要求转人工 | < 5% | 用户对 Agent 不满意 |
| 复杂任务超限 | < 5% | 任务超出 Agent 预设能力边界 |
| 安全/合规触发 | < 1% | 需要人工审核的安全相关场景 |

### 5.2 平均处理时长（Average Handling Time, AHT）

从用户提出问题到 Agent 解决问题的完整耗时：

```
AHT = 所有已解决会话的总耗时 / 已解决会话数
```

**AHT 的构成分解**：
```
AHT = 模型推理耗时 + 工具调用耗时 + 用户交互等待耗时

成本影响：
  AHT 每降低 1 秒，对于日处理 10 万会话的系统，
  可节省约 28 小时的模型处理时间（相当于约 $X 的计算成本）
```

### 5.3 一次性解决率（First Contact Resolution, FCR）

用户在首次接触 Agent 时问题就被解决的比率，不涉及转人工或二次回访：

```
FCR = 首次接触即解决的会话数 / 总会话数
```

**FCR 判定标准**：
- 会话结束时用户问题被完全解决
- 用户未在 24 小时内就同一问题再次发起会话
- 会话未被转人工

### 5.4 成本效益比（Cost Efficiency）

```
每会话成本 = (模型推理费用 + 工具调用费用 + 基础设施费用) / 总会话数

投资回报率（ROI）：
  ROI = (人工替代成本 - Agent 运营成本) / Agent 运营成本 × 100%

例如：
  - 人工客服每会话成本：$5
  - Agent 每会话成本：$0.50  
  - ROI = (5 - 0.5) / 0.5 × 100% = 900%
```

## 六、四层评估的联动分析

### 6.1 层级之间的因果关系

```
业务指标问题（转人工率高）
  └── 用户体验差（用户不满意，要求转人工）
        └── 行为质量差（Agent 无法完成任务）
              └── 输出质量差（回答了错误的信息）
```

**实际案例**：
```
某客服 Agent 监控数据显示：
  - 转人工率：45%（目标 < 20%） [第四层]
  - 用户满意度：2.8/5（目标 > 4.0） [第三层]
  
问题归因：
  分析发现，Agent 在处理"退换货"场景时：
  - 工具调用准确率仅 62%（错误地查询订单 API） [第二层]
  - 输出中 20% 的信息与公司退换货政策不一致 [第一层]
  - 用户需要 2.8 次交互才能解决问题 [第二层]
  
  根本原因：退换货场景的 prompt 中工具选择指令不明确，
  导致 Agent 频繁调用错误的查询接口。
  
  修复方式：明确退换货场景的工具选择规则，并在评估集中
  增加 500 条退换货测试用例进行回归验证。修复后：
  - 工具调用准确率升至 91%
  - 转人工率降至 22%
  - 用户满意度升至 3.9/5
```

### 6.2 四层指标的权重设置

不同业务场景下各层指标的权重不同：

| 场景 | 输出质量权重 | 行为质量权重 | 用户体验权重 | 业务指标权重 |
|-----|------------|------------|------------|------------|
| 医疗咨询 Agent | 50% | 30% | 10% | 10% |
| 电商客服 Agent | 20% | 25% | 25% | 30% |
| 代码生成 Agent | 35% | 35% | 15% | 15% |
| 内部知识库 Agent | 30% | 25% | 20% | 25% |

**综合评分计算**：
```
Overall Score = Σ(w_i × normalized_score_i)

其中：
  - w_i 是第 i 层的权重（四层权重之和 = 1）
  - normalized_score_i 是第 i 层各指标归一化后的综合得分
```

### 6.3 四层评估的数据管道

构建四层评估需要采集不同来源的数据：

```
数据采集层：
  ├── Agent 执行日志 → 输出质量 + 行为质量
  ├── 用户行为埋点 → 用户体验
  ├── 业务系统数据 → 业务指标
  └── 标注数据集 → 准确性校准

数据处理层：
  ├── 数据清洗与标准化
  ├── 指标计算引擎
  └── 可视化仪表板

数据输出层：
  ├── 实时监控仪表板
  ├── 周/月度评估报告
  └── 告警与归因分析
```

## 七、四层评估的工程实践建议

1. **分阶段实施**：先建立第一层（输出质量），再逐层扩展
2. **自动化优先**：将评估流程集成到 CI/CD 流水线中，每次模型更新自动触发全量评估
3. **数据驱动的阈值设置**：各指标阈值应基于历史数据的分布动态设定，而非拍脑袋决定
4. **异常检测机制**：建立监控告警，当任何一层的指标超过警戒线时自动触发分析流程
5. **定期校准**：随着 Agent 迭代，评估指标的有效性可能衰减，每季度需要重新校准指标权重

## 关键概念速查

| 术语 | 解释 |
|------|------|
| 四层评估模型 | 从输出质量→行为质量→用户体验→业务指标的递进式评估体系 |
| 输出质量 | 评估 Agent 生成内容的准确性、忠实度、完整性和格式合规性 |
| 行为质量 | 评估 Agent 的工具调用、推理路径、错误恢复等行为表现 |
| 用户体验 | 评估用户在使用 Agent 过程中感知的延迟、满意度和放弃行为 |
| 业务指标 | 评估 Agent 对业务的实际影响，包括转人工率、处理时长和成本效益 |
| 首 Token 延迟（TTFT） | 从用户发出请求到 Agent 输出第一个 Token 的时间 |
| 部分成功率 | 对复杂多步任务按步骤权重加权计算的成功率 |
| 忠实度 | Agent 输出对给定上下文的一致程度，与 14.1 节幻觉问题密切相关 |
| 一次性解决率（FCR） | 用户首次接触 Agent 时问题即被解决的比例 |
| 路径效率 | Agent 实际步数与理论最优步数的比值 |
