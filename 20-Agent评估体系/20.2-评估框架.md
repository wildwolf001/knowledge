# 20.2 评估框架

> 评估框架（Benchmark）是衡量 Agent 能力的重要参照系。不同于传统 NLP 基准（如 GLUE、SuperGLUE）测试的是模型的语言理解能力，Agent 评估框架需要测试模型在**交互式、多步骤、工具调用**场景下的综合表现。本章深入对比 WebArena、OSWorld、SWE-Bench、GAIA 四个代表性基准。

---

## 一、传统基准 vs Agent 基准

### 1.1 传统 NLP 基准的局限

传统基准（如 MMLU、HellaSwag、BIG-Bench）的设计假设是"单轮、封闭、静态回答"——给定一个问题，模型输出一个答案。这在 Agent 场景下面临根本性局限：

| 维度 | 传统基准 | Agent 真实场景 |
|------|---------|--------------|
| 交互方式 | 单轮问答 | 多轮交互、工具调用、状态管理 |
| 环境 | 静态文本 | 动态环境、异步反馈 |
| 错误恢复 | 不允许重试 | 需要从错误中恢复 |
| 评估标准 | 答案是否正确 | 过程 + 结果综合评估 |
| 知识来源 | 参数知识 | 参数知识 + 检索 + 工具调用 |

### 1.2 Agent 基准的设计原则

一个好的 Agent 评估基准应满足：

1. **可交互性（Interactivity）**：Agent 不仅能"说"，还能"做"——调用 API、操作界面、执行代码
2. **状态保持（Statefulness）**：环境状态会因 Agent 的操作而改变，后续操作需感知状态变化
3. **多路径求解（Multi-path）**：允许多种策略达到目标，评估关注结果而非固定路径
4. **自动化评估（Auto-evaluation）**：大规模式评估需自动判断成功/失败，人工评估不可持续
5. **领域覆盖（Domain Coverage）**：涵盖 Web、OS、代码、通用问答等主要 Agent 应用领域

### 2.2 评估维度详细对比

#### 2.2.1 WebArena — Web 交互 Agent

**核心思想**：在自托管的模拟网站中，Agent 需要通过自然语言指令完成 Web 操作任务。

**模拟网站**：
- 购物网站 (Shop)：商品搜索、筛选、加入购物车、下单
- 论坛 (Forum)：发帖、回复、搜索、用户管理
- 内容管理 (CMS)：文章编辑、发布、分类
- 项目管理 (Kitchen)：创建/编辑任务、分配人员
- 地图 (Map)：搜索地点、规划路线（简化仿真）

**典型任务示例**：
```
任务：在购物网站上找到最便宜的"无线鼠标"，并将其加入购物车。

期望路径：
1. 打开购物网站首页
2. 在搜索框输入"无线鼠标" → 点击搜索
3. 查看搜索结果列表，获取各商品价格
4. 按价格排序（或手动比较）
5. 点击排名最低的商品进入详情页
6. 点击"加入购物车"按钮
7. 验证购物车中已添加该商品
```

**评估指标**：

| 指标 | 定义 |
|------|------|
| **Success Rate (SR)** | 最终状态是否完全达到任务目标 |
| **Task Completion Rate (TCR)** | 任务是否完成（部分成功也算） |
| **Action Efficiency (AE)** | 操作步数与最优步数的比值 |
| **DOM State Match (DSM)** | 最终 DOM 状态与期望状态的匹配度 |

**代码实现：WebArena 评估器**：

```python
class WebArenaEvaluator:
    """
    WebArena 任务自动评估器
    
    通过比较执行前后 DOM 状态的变化来判断任务是否成功
    """
    
    def __init__(self, task_config):
        self.task_id = task_config["id"]
        self.intent = task_config["intent"]
        self.start_url = task_config.get("start_url")
        self.eval_type = task_config["eval"]["eval_type"]
        self.eval_program = task_config["eval"].get("program")
        self.reference_answers = task_config["eval"].get("reference_answers", {})
        self.reference_url = task_config["eval"].get("reference_url")
    
    def evaluate(self, page, task_result):
        """
        评估 Agent 是否成功完成任务
        
        Args:
            page: Playwright Page 对象（最终状态）
            task_result: Agent 的执行轨迹和最终结果
        
        Returns:
            eval_result: {
                "success": bool,
                "score": float,
                "reason": str,
                "details": dict
            }
        """
        if self.eval_type == "string_match":
            return self._eval_string_match(page, task_result)
        elif self.eval_type == "program":
            return self._eval_program(page, task_result)
        elif self.eval_type == "url_match":
            return self._eval_url_match(page, task_result)
        elif self.eval_type == "must_include":
            return self._eval_must_include(page, task_result)
        else:
            return {"success": False, "score": 0, "reason": f"Unknown eval type: {self.eval_type}"}
    
    def _eval_string_match(self, page, task_result):
        """字符串匹配评估：检查页面上是否包含特定文本"""
        page_content = page.content()
        target = self.eval_program.get("target", "")
        method = self.eval_program.get("method", "exact")
        
        if method == "exact":
            success = target in page_content
        elif method == "fuzzy":
            # 模糊匹配：去空格、小写化后比较
            success = target.lower().replace(" ", "") in page_content.lower().replace(" ", "")
        elif method == "regex":
            import re
            success = bool(re.search(target, page_content))
        else:
            success = False
        
        return {
            "success": success,
            "score": 1.0 if success else 0.0,
            "reason": f"String '{target}' {'found' if success else 'not found'} on page" if success else f"Target string not found: {target}"
        }
    
    def _eval_program(self, page, task_result):
        """
        程序化评估：运行 JavaScript 检查页面状态
        
        例如：检查购物车中的商品数量是否正确
        """
        js_program = self.eval_program
        try:
            result = page.evaluate(js_program)
            return {
                "success": bool(result),
                "score": 1.0 if result else 0.0,
                "reason": f"Program eval: {result}"
            }
        except Exception as e:
            return {
                "success": False,
                "score": 0.0,
                "reason": f"Program eval failed: {str(e)}"
            }
    
    def _eval_url_match(self, page, task_result):
        """URL 匹配评估：检查是否到达了正确的页面"""
        current_url = page.url
        target_url = self.reference_url
        
        success = current_url.rstrip("/") == target_url.rstrip("/")
        return {
            "success": success,
            "score": 1.0 if success else 0.0,
            "reason": f"URL {'matches' if success else 'does not match'}: {current_url}"
        }
```

**WebArena 的优势与局限**：
- 优势：高仿真模拟网站，任务贴近真实 Web 场景，评估自动化程度高
- 局限：模拟网站覆盖有限，无法测试真实网站的多样性；部分任务对 DOM 状态的检查过于严格（URL 精确匹配等），可能误判路径正确但最终状态略有差异的 Agent

#### 2.2.2 OSWorld — 操作系统 Agent

**核心思想**：Agent 在真实的桌面操作系统（Ubuntu）中完成多步骤任务，涉及 GUI 操作、文件管理、命令行等。

**环境架构**：
```
┌──────────────────────────────────┐
│       OSWorld 评估平台            │
├──────────────────────────────────┤
│  ┌────────────────────────────┐  │
│  │  Ubuntu VM (QEMU)          │  │
│  │  ├── GUI (VNC 连接)        │  │
│  │  ├── 文件系统               │  │
│  │  ├── 命令行终端             │  │
│  │  ├── 应用程序 (Firefox,     │  │
│  │  │    LibreOffice, GIMP等) │  │
│  │  └── Agent 操作接口         │  │
│  └────────────────────────────┘  │
│        ▲            ▲            │
│        │  VNC       │  API       │
│  ┌─────┴────────────┴─────┐      │
│  │ Agent 接口              │      │
│  │ (截图+坐标/键盘/鼠标)   │      │
│  └────────────────────────┘       │
└──────────────────────────────────┘
```

**典型任务难度分布**：

| 难度级别 | 示例任务 | 所需步骤 | 预期成功率 |
|---------|---------|---------|-----------|
| **简单** | 在 Firefox 中打开书签管理器 | 2-3步 | 30-50% |
| **中等** | 将文件夹 A 中的图片批量重命名并移动到文件夹 B | 5-8步 | 15-30% |
| **困难** | 安装 LibreOffice 扩展，配置邮件合并模板，批量生成文档 | 10-20步 | 5-15% |
| **极难** | 编写 Python 脚本从多个 CSV 文件提取数据，生成图表并导出为 PDF | 15-30步 | <5% |

**评估指标**：
```
Success Rate (SR) = 任务目标完全达成的比例

Partial Success Rate (PSR) = 基于子任务加权达成率

Subtask Coverage = 覆盖的子任务比例

Efficiency Score = 最优操作次数 / 实际操作次数
```

**OSWorld 的特色评估方法**：
1. **截图对比**：将最终屏幕截图与期望状态截图进行对比（使用像素差异或感知哈希）
2. **文件状态检查**：检查文件系统中的目标文件是否存在、内容是否正确
3. **进程状态检查**：检查目标应用程序是否按预期运行

```python
def evaluate_osworld_task(vm_client, task_config):
    """
    OSWorld 任务评估的核心逻辑
    """
    evaluation_result = {
        "success": False,
        "score": 0.0,
        "checks": []
    }
    
    # 运行预定义的检查脚本（在 VM 内部执行）
    for check in task_config["checks"]:
        check_type = check["type"]
        
        if check_type == "file_exists":
            path = check["path"]
            exists = vm_client.run_command(f"test -f '{path}' && echo 'YES' || echo 'NO'")
            passed = "YES" in exists
            
        elif check_type == "file_content":
            path = check["path"]
            expected_content = check["expected"]
            actual = vm_client.read_file(path)
            passed = expected_content in actual
            
        elif check_type == "process_running":
            proc_name = check["name"]
            output = vm_client.run_command(f"pgrep -f '{proc_name}'")
            passed = bool(output.strip())
            
        elif check_type == "gui_state":
            # 截图对比
            screenshot = vm_client.screenshot()
            expected_hash = check["expected_hash"]
            actual_hash = perceptual_hash(screenshot)
            passed = actual_hash == expected_hash
            
        elif check_type == "command_output":
            cmd = check["command"]
            expected = check["expected"]
            output = vm_client.run_command(cmd)
            passed = expected in output
        
        result = {"check_name": check.get("name", ""), "passed": passed}
        evaluation_result["checks"].append(result)
        if passed:
            evaluation_result["score"] += check.get("weight", 1.0)
    
    # 计算总分
    total_weight = sum(c.get("weight", 1.0) for c in task_config["checks"])
    evaluation_result["score"] /= total_weight
    evaluation_result["success"] = evaluation_result["score"] >= task_config.get("pass_threshold", 0.8)
    
    return evaluation_result
```

**OSWorld 的优势与局限**：
- 优势：真实 OS 环境，任务类型极其丰富（不仅是 Web 操作）；需要综合运用 GUI、CLI、文件系统等多种交互方式
- 局限：VM 环境启动和重置耗时长（分钟级），大规模评估成本高；截图对比对窗口位置、主题等细节敏感

#### 2.2.3 SWE-Bench — 软件工程 Agent

**核心思想**：Agent 需要修改真实 GitHub 仓库的代码，修复 bug 或实现新功能，修改结果通过仓库的自动化测试来验证。

**任务构成**：

```
SWE-Bench 任务数据格式：
{
  "repo": "django/django",
  "instance_id": "django-12345",
  "base_commit": "abc123def456",
  "hints": ["Look at the QuerySet.annotate method"],
  "problem_statement": "...",
  "expected_test_patch": "--- a/tests/modeltests/test_thing.py\n+++ ...",
  "version": "3.2",
  "FAIL_TO_PASS": ["test_case_A", "test_case_B"],
  "PASS_TO_PASS": ["test_case_C", "test_case_D"],
  "created_by": "human"
}
```

**关键字段含义**：
- `FAIL_TO_PASS`：修改前失败、修改后应通过的测试（验证 bug 被修复）
- `PASS_TO_PASS`：修改前后都应通过的测试（验证未引入回归）
- `expected_test_patch`：期望的测试代码变更（评估时用，不提供给 Agent）

**评估流程**：

```
1. Agent 获取仓库在 base_commit 的代码快照
2. Agent 分析问题描述，定位需要修改的文件
3. Agent 生成代码补丁（patch）
4. 评估系统应用补丁到代码库
5. 运行 FAIL_TO_PASS 和 PASS_TO_PASS 测试
6. 验证结果：
   - FAIL_TO_PASS 全部通过 → Bug 修复成功
   - PASS_TO_PASS 全部通过 → 无回归
   - 两者都满足 → 任务成功
```

**评估指标**：

| 指标 | 公式 | 说明 |
|------|------|------|
| **Resolved Rate** | resolved / total | 任务被成功解决的比率 |
| **Test Pass Rate** | passed / total_tests | 所有测试的通过率 |
| **Apply Rate** | applied / total_patches | 生成的补丁可成功应用的比率 |
| **Identical Rate** | 与人类修复完全一致的补丁比例 | 衡量"最优解"匹配度 |

```python
def evaluate_swebench_patch(repo_path, patch, task_instance):
    """
    评估 SWE-Bench 补丁
    
    应用补丁 → 运行测试 → 判断成功
    """
    import subprocess
    import tempfile
    import os
    
    result = {
        "applied": False,
        "fail_to_pass": {"passed": 0, "failed": 0, "total": 0},
        "pass_to_pass": {"passed": 0, "failed": 0, "total": 0},
        "resolved": False,
    }
    
    # 步骤 1：恢复到 base commit
    subprocess.run(
        ["git", "checkout", task_instance["base_commit"]],
        cwd=repo_path, capture_output=True
    )
    
    # 步骤 2：尝试应用补丁
    with tempfile.NamedTemporaryFile(mode='w', suffix='.diff') as f:
        f.write(patch)
        f.flush()
        apply_result = subprocess.run(
            ["git", "apply", f.name],
            cwd=repo_path, capture_output=True
        )
        result["applied"] = apply_result.returncode == 0
    
    if not result["applied"]:
        return result
    
    # 步骤 3：运行 FAIL_TO_PASS 测试（验证 bug 修复）
    for test in task_instance["FAIL_TO_PASS"]:
        test_result = subprocess.run(
            ["python", "-m", "pytest", test, "-x", "-q"],
            cwd=repo_path, capture_output=True
        )
        if test_result.returncode == 0:
            result["fail_to_pass"]["passed"] += 1
        else:
            result["fail_to_pass"]["failed"] += 1
        result["fail_to_pass"]["total"] += 1
    
    # 步骤 4：运行 PASS_TO_PASS 测试（验证无回归）
    for test in task_instance["PASS_TO_PASS"]:
        test_result = subprocess.run(
            ["python", "-m", "pytest", test, "-x", "-q"],
            cwd=repo_path, capture_output=True
        )
        if test_result.returncode == 0:
            result["pass_to_pass"]["passed"] += 1
        else:
            result["pass_to_pass"]["failed"] += 1
        result["pass_to_pass"]["total"] += 1
    
    # 步骤 5：判定是否解决
    all_f2p_pass = result["fail_to_pass"]["failed"] == 0
    all_p2p_pass = result["pass_to_pass"]["failed"] == 0
    result["resolved"] = all_f2p_pass and all_p2p_pass
    
    return result
```

**SWE-Bench 的变体**：
- **SWE-Bench-Lite**：筛选出 300 个高质量任务，降低评估成本
- **SWE-Bench-Multimodal**：增加涉及前端修改的任务（需要理解截图）
- **SWE-Bench-Verified**：由人工验证过的子集，减少测试不充分导致的误判

**SWE-Bench 的优势与局限**：
- 优势：高度真实的软件开发场景，评估结果可直接反映 Agent 在代码维护中的实用价值；使用真实测试用例判断，评估客观
- 局限：仅覆盖 Python 仓库（Django、sphinx、sympy 等），不适用于评估其他语言的代码能力；测试覆盖率不足可能导致"假阳性解决"（补丁使测试通过但实际修复不正确）

#### 2.2.4 GAIA — 通用 AI 助手

**核心思想**：评估 Agent 解决**真实世界多步骤推理问题**的能力。GAIA 的问题设计理念是——对人类简单但对 AI 困难的日常任务。

**问题分类**：

| 类别 | 占比 | 描述 | 示例 |
|------|------|------|------|
| **多模态推理** | 30% | 需要处理图像、表格、PDF 等多种格式 | "这张图表中，2023年Q3的增长率是多少？" |
| **工具组合** | 25% | 需要组合使用多个工具/API 完成任务 | "查询 A 公司股票价格，换算成欧元，并计算与去年同期的变化百分比" |
| **代码执行** | 20% | 需要编写和执行代码来获得答案 | "写一个 Python 脚本计算 1000 以内的素数之和" |
| **网络搜索** | 15% | 需要搜索网络、整合多来源信息 | "搜索2024年诺贝尔文学奖得主，找出其代表作的中文译名" |
| **长文档处理** | 10% | 需要阅读和理解长文档/多文档 | "从这份50页的PDF中找出所有与X条款相关的修改" |

**GAIA 的独特之处**：
1. **问题具有"简单但不易"的特点**——对人类来说只需几分钟完成，但对纯 LLM 来说需要多步推理和工具调用
2. **问题有唯一正确答案**——所有问题的答案都可通过公开信息验证，不存在主观判断
3. **需要"真实世界知识"**——问题涉及真实世界的数据与知识，而非合成数据
4. **明确禁止直接猜测**——GAIA 要求 Agent 必须通过外部工具获取答案, 而非依赖模型参数知识

**评估指标**：
```
Accuracy = 答案完全正确的任务数 / 总任务数

注意：GAIA 使用**精确匹配**评估，不接受"部分正确"或"近似正确"
```

```python
def evaluate_gaia_answer(predicted_answer, ground_truth, answer_type="str"):
    """
    GAIA 答案评估
    
    根据答案类型使用不同的匹配策略
    """
    if answer_type == "str":
        # 字符串精确匹配（去空白、大小写不敏感）
        return predicted_answer.strip().lower() == ground_truth.strip().lower()
    
    elif answer_type == "number":
        # 数值匹配（允许浮点数精度误差）
        try:
            pred_num = float(predicted_answer.strip())
            true_num = float(ground_truth.strip())
            return abs(pred_num - true_num) < 0.01
        except (ValueError, TypeError):
            return False
    
    elif answer_type == "list":
        # 列表匹配（忽略顺序和空格差异）
        pred_items = [x.strip().lower() for x in predicted_answer.split(",")]
        true_items = [x.strip().lower() for x in ground_truth.split(",")]
        return set(pred_items) == set(true_items)
    
    elif answer_type == "boolean":
        return predicted_answer.strip().lower() in ["true", "yes", "1"] and \
               ground_truth.strip().lower() in ["true", "yes", "1"]
    
    return False
```

**GAIA 的优势与局限**：
- 优势：任务设计贴近真实用户需求，覆盖多种 Agent 能力维度；答案唯一确定，评估客观
- 局限：任务数量相对较少（466 个），统计显著性可能不足；精确匹配评估可能过于严苛（正确答案表述可能有多样性）

## 四、评估框架的工程实践

### 4.1 多基准联合评估

为了全面评估 Agent 能力，建议同时使用多个基准：

```python
class MultiBenchmarkEvaluator:
    """
    多基准联合评估器
    
    在一套评估流程中依次执行多个基准的测试
    """
    
    def __init__(self, benchmarks, api_key, output_dir):
        self.benchmarks = benchmarks  # ["webarena", "swebench", "gaia"]
        self.api_key = api_key
        self.output_dir = output_dir
        self.results = {}
    
    def run_evaluation(self, model_name, model_endpoint):
        """运行所有基准评估"""
        for bench in self.benchmarks:
            if bench == "webarena":
                # 需要 Docker 环境运行模拟网站
                print(f"Running WebArena evaluation for {model_name}...")
                results = self._run_webarena(model_name, model_endpoint)
            
            elif bench == "osworld":
                # 需要 QEMU VM 环境
                print(f"Running OSWorld evaluation for {model_name}...")
                results = self._run_osworld(model_name, model_endpoint)
            
            elif bench == "swebench":
                # 需要 Git 仓库和 pytest 环境
                print(f"Running SWE-Bench evaluation for {model_name}...")
                results = self._run_swebench(model_name, model_endpoint)
            
            elif bench == "gaia":
                # 需要网络搜索和工具 API
                print(f"Running GAIA evaluation for {model_name}...")
                results = self._run_gaia(model_name, model_endpoint)
            
            self.results[bench] = results
        
        return self._generate_report()
    
    def _generate_report(self):
        """生成联合评估报告"""
        report = {
            "model": self.model_name,
            "date": datetime.now().isoformat(),
            "overall_score": 0.0,
            "benchmark_results": self.results
        }
        
        # 综合评分 = 各基准成功率的加权平均
        weights = {
            "webarena": 0.25,
            "osworld": 0.25,
            "swebench": 0.25,
            "gaia": 0.25
        }
        
        total_score = 0.0
        for bench, result in self.results.items():
            success_rate = result.get("success_rate", 0)
            total_score += weights.get(bench, 0) * success_rate
        
        report["overall_score"] = total_score
        
        return report
```

### 4.2 基准选择的成本考量

不同基准的评估成本差异巨大：

| 基准 | 单任务耗时 | 全量评估估算成本 | 硬件需求 |
|------|-----------|----------------|---------|
| WebArena | 2-5 分钟 | $200-500 (API) | Docker |
| OSWorld | 5-15 分钟 | $500-1500 (API) | QEMU VM + GPU |
| SWE-Bench | 3-10 分钟 | $300-800 (API) | Linux 服务器 |
| GAIA | 1-3 分钟 | $100-300 (API) | 无特殊硬件 |

**实用建议**：
- 日常迭代中使用**子集**（如各基准随机抽取 50 个任务）快速验证
- 重大版本发布前执行**全量评估**
- 使用 SWE-Bench-Lite（300 个任务）代替完整 SWE-Bench 以降低成本

### 4.3 基准的局限性

1. **数据泄露风险**：基准任务数据集如果被纳入模型训练集，评估结果将失去意义。SWE-Bench 和 GAIA 都有专门的"验证集"和"测试集"隔离机制，详见 20.6 节。

2. **自动化评估的不完善性**：自动化评估（DOM 检查、测试用例运行）可能漏掉一些"过程正确但形式不同"的解决方案。例如 WebArena 的 URL 精确匹配可能惩罚使用了不同但等效导航路径的 Agent。

3. **环境搭建复杂度**：OSWorld 需要完整的虚拟机环境，影响了开源社区的可复现性。目前大多数 OSWorld 论文使用 AWS EC2 来托管虚拟机。

4. **领域覆盖不均匀**：四大基准主要覆盖英语和西方 IT 环境。中文、日语等非英语场景的 Agent 评估覆盖不足，这是一个活跃的研究方向。
