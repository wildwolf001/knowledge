# 19.2 三维度指标体系 —— Token 消耗 / 延迟 / 成本

> 你不知道 Agent 哪一步会变成"吞金兽"——可能是某次异常长的 LLM 调用，也可能是陷入循环的 Tool Call。建立 Token 消耗、延迟、成本三维度的指标体系，是将 Agent 从"黑盒"变为"透明"的第一步。这三个维度共同构成了生产环境中 Agent 可观测性的基石。

---

## 一、为什么是这三个维度？

Agent 系统与传统 Web 服务的核心差异在于**不确定性**：传统服务的性能指标（QPS、错误率、CPU）无法反映 Agent 特有的状态。Token 消耗、延迟和成本这三个维度直接对应 Agent 运行的三类核心风险：

| 维度 | 对应风险 | 典型问题 |
|------|---------|---------|
| **Token 消耗** | 效率风险 | 某步消耗了 10x 于平均的 Token |
| **延迟（Latency）** | 体验风险 | P99 延迟从 5s 飙升到 60s |
| **成本（Cost）** | 经济风险 | 单次 Agent 执行花费 $5 |

这三个维度需要**同时监控**才能形成完整的可观测图景。例如，Token 消耗升高可能是正常的（处理了更大文档），但如果同时延迟升高且成本升高，就可能是异常的推理循环。

## 二、Token 消耗指标

### 2.1 分层指标定义

Token 消耗指标需要在三个粒度上分别定义：

```
粒度1: 每步（Per-Step）
  ├── thought_step.prompt_tokens     本轮推理的输入 Token
  ├── thought_step.completion_tokens  本轮推理的输出 Token
  └── thought_step.total_tokens       输入+输出

粒度2: 每工作流（Per-Workflow）
  ├── workflow.total_prompt_tokens     工作流累积输入 Token
  ├── workflow.total_completion_tokens 工作流累积输出 Token
  ├── workflow.total_tokens            总 Token 消耗
  └── workflow.steps_count             步数

粒度3: 每会话（Per-Session）  
  ├── session.total_tokens             用户会话期间总 Token
  ├── session.avg_tokens_per_step      每步平均 Token
  └── session.max_tokens_per_step      单步最大 Token
```

### 2.2 指标采集代码

```python
import time
from prometheus_client import Counter, Histogram, Gauge, start_http_server

# ========== Prometheus 指标定义 ==========

# 1. Token 消耗计数器（每步）
TOKEN_COUNTER = Counter(
    'agent_tokens_total',
    'Agent 累计 Token 消耗',
    ['span_type', 'model', 'workflow']  # 标签
)

# 2. Token 直方图（用于计算百分比）
TOKEN_HISTOGRAM = Histogram(
    'agent_tokens_per_step',
    'Agent 每步 Token 消耗分布',
    ['span_type', 'model'],
    buckets=[100, 500, 1000, 2000, 4000, 8000, 16000, 32000, 64000]
)

# 3. 当前活跃 Agent 的 Token 消耗（实时）
ACTIVE_TOKENS = Gauge(
    'agent_active_tokens',
    '当前正在执行的 Agent 已消耗 Token',
    ['workflow']
)

# ========== 采集封装 ==========

class TokenCollector:
    """Token 消耗采集器"""

    def record_step_tokens(self,
                           span_type: str,
                           model: str,
                           workflow: str,
                           prompt_tokens: int,
                           completion_tokens: int):
        total = prompt_tokens + completion_tokens

        # 更新计数器
        TOKEN_COUNTER.labels(
            span_type=span_type,
            model=model,
            workflow=workflow
        ).inc(total)

        # 更新直方图
        TOKEN_HISTOGRAM.labels(
            span_type=span_type,
            model=model
        ).observe(total)

    def set_active_tokens(self, workflow: str, tokens: int):
        ACTIVE_TOKENS.labels(workflow=workflow).set(tokens)

    def get_step_statistics(self, span_type: str, model: str) -> dict:
        """获取某类步骤的 Token 统计"""
        # 通过 Prometheus HTTP API 查询或本地聚合
        # 这里展示本地模拟逻辑
        return {
            "avg": 1200,
            "p50": 800,
            "p95": 4500,
            "p99": 12000,
            "max": 64000
        }


# ========== 在 Agent 执行中的集成 ==========

class ObservableAgent:
    def __init__(self):
        self.token_collector = TokenCollector()
        self.current_workflow = ""
        self.step_tokens = []

    async def execute_step(self, step_type: str, model: str):
        """执行一步并自动采集 Token 消耗"""
        # 模拟 LLM 调用并获取 Token 消耗
        prompt_tokens, completion_tokens = await self.call_llm()

        self.token_collector.record_step_tokens(
            span_type=step_type,
            model=model,
            workflow=self.current_workflow,
            prompt_tokens=prompt_tokens,
            completion_tokens=completion_tokens
        )

        total = prompt_tokens + completion_tokens
        self.step_tokens.append(total)
        self.token_collector.set_active_tokens(
            self.current_workflow,
            sum(self.step_tokens)
        )

        # 异常检测：单步消耗超过均值的 5 倍
        if len(self.step_tokens) > 2:
            avg = sum(self.step_tokens[:-1]) / (len(self.step_tokens) - 1)
            if total > avg * 5:
                logger.warning(
                    f"Token 消耗异常: 步骤 {len(self.step_tokens)}, "
                    f"当前 {total}, 平均 {avg:.0f}"
                )
```

## 三、延迟指标（Latency P50/P95/P99）

### 3.1 为什么关注百分比而非平均值？

延迟分布通常不符合正态分布——平均值会被少数极端值拉高或拉低。**P50（中位数）**、**P95** 和 **P99** 这三个百分位值能更准确地反映真实的用户体验：

```
延迟分布示意图：

  请求数
    │
    │    ╱╲               P50 = 2.1s (半数请求在此之下)
    │   ╱  ╲╱╲            P95 = 8.5s (95%请求在此之下)
    │  ╱      ╲╱╲         P99 = 15.3s (99%请求在此之下)
    │ ╱          ╲╲╱╲
    │╱              ╲╲╱╲
    └──────────────────────→ 延迟(s)
      1  2  3  4  5  10  20

指标解读：
- P50 = 2.1s：一半的用户体验在 2s 以内（良好）
- P95 = 8.5s：5% 的用户等待超过 8.5s（需优化）
- P99 = 15.3s：1% 的用户体验极差（需紧急处理）
```

### 3.2 延迟指标采集

```python
# 延迟指标定义
LATENCY_HISTOGRAM = Histogram(
    'agent_step_duration_seconds',
    'Agent 每步执行耗时（秒）',
    ['span_type', 'model', 'workflow'],
    buckets=[0.1, 0.5, 1.0, 2.0, 5.0, 10.0, 30.0, 60.0, 120.0]
)

# Agent 总执行时间
WORKFLOW_DURATION = Histogram(
    'agent_workflow_duration_seconds',
    'Agent 工作流总耗时',
    ['workflow', 'status'],  # status: success | error | timeout
    buckets=[5, 10, 30, 60, 120, 300, 600]
)

class LatencyCollector:
    """延迟采集器"""

    def record_step_latency(self,
                            span_type: str,
                            model: str,
                            workflow: str,
                            duration_seconds: float):
        LATENCY_HISTOGRAM.labels(
            span_type=span_type,
            model=model,
            workflow=workflow
        ).observe(duration_seconds)

    def record_workflow_completion(self,
                                   workflow: str,
                                   status: str,
                                   duration_seconds: float):
        WORKFLOW_DURATION.labels(
            workflow=workflow,
            status=status
        ).observe(duration_seconds)

    def get_latency_summary(self, span_type: str) -> dict:
        """获取延迟摘要（模拟 Prometheus 查询结果）"""
        # 实际环境通过 Prometheus HTTP API 查询
        return {
            "p50": 2.1,
            "p95": 8.5,
            "p99": 15.3,
            "avg": 4.2,
            "min": 0.3,
            "max": 120.0,
            "sample_count": 15000
        }
```

## 四、成本指标

### 4.1 按模型成本核算

不同模型的 Token 单价差异巨大（从 $0.15/M token 到 $15/M token 不等）。成本指标必须按模型拆分：

```python
# 模型单价表（每百万 Token 的 USD 价格）
MODEL_PRICES = {
    "gpt-4o":            {"input": 2.50, "output": 10.00},
    "gpt-4o-mini":       {"input": 0.15, "output": 0.60},
    "claude-3-opus":     {"input": 15.00, "output": 75.00},
    "claude-3-sonnet":   {"input": 3.00, "output": 15.00},
    "claude-3-haiku":    {"input": 0.25, "output": 1.25},
    "deepseek-chat":     {"input": 0.27, "output": 1.10},
}

class CostCalculator:
    """成本计算器"""

    def calculate_step_cost(self,
                            model: str,
                            prompt_tokens: int,
                            completion_tokens: int) -> float:
        """计算单步成本（USD）"""
        if model not in MODEL_PRICES:
            return 0.0  # 未知模型

        prices = MODEL_PRICES[model]
        input_cost = (prompt_tokens / 1_000_000) * prices["input"]
        output_cost = (completion_tokens / 1_000_000) * prices["output"]
        return round(input_cost + output_cost, 6)

    def calculate_workflow_cost(self, steps: list) -> dict:
        """计算整个工作流的成本"""
        total_cost = 0.0
        model_breakdown = {}

        for step in steps:
            cost = self.calculate_step_cost(
                step["model"],
                step["prompt_tokens"],
                step["completion_tokens"]
            )
            total_cost += cost

            model_name = step["model"]
            if model_name not in model_breakdown:
                model_breakdown[model_name] = {
                    "cost": 0.0,
                    "call_count": 0,
                    "total_tokens": 0
                }
            model_breakdown[model_name]["cost"] += cost
            model_breakdown[model_name]["call_count"] += 1
            model_breakdown[model_name]["total_tokens"] += \
                step["prompt_tokens"] + step["completion_tokens"]

        return {
            "total_cost_usd": round(total_cost, 4),
            "model_breakdown": model_breakdown,
            "step_count": len(steps)
        }
```

### 4.2 成本指标采集

```python
COST_COUNTER = Counter(
    'agent_cost_usd_total',
    'Agent 累计成本（USD）',
    ['model', 'workflow']
)

COST_HISTOGRAM = Histogram(
    'agent_cost_per_workflow_usd',
    '每工作流成本分布',
    ['workflow'],
    buckets=[0.01, 0.05, 0.10, 0.50, 1.00, 5.00, 10.00]
)

def record_cost(model: str, workflow: str, cost_usd: float):
    COST_COUNTER.labels(model=model, workflow=workflow).inc(cost_usd)
    COST_HISTOGRAM.labels(workflow=workflow).observe(cost_usd)
```

## 五、三维度关联分析

### 5.1 成本-延迟-Token 关联仪表盘

三个维度单独看价值有限，**关联分析**才能发现真正的问题：

```
┌─────────────────────────────────────────────────────────────────┐
│                  Agent 三维度关联仪表盘                            │
├───────────────┬──────────────────┬───────────────────────────────┤
│  Token 消耗     │  延迟分布          │  成本消耗                       │
│  ┌──────────┐  │  ┌─────────────┐  │  ┌─────────────────────────┐ │
│  │ 总计:     │  │  │ P50  2.1s   │  │  │ 今日: $245.30           │ │
│  │ 1,245,800│  │  │ P95  8.5s   │  │  │ 本周: $1,892.10         │ │
│  │ Tokens    │  │  │ P99 15.3s   │  │  │ 本月: $7,245.80         │ │

├───────────────┴──────────────────┴───────────────────────────────┤
```

### 5.2 异常检测策略

当某个维度出现异常时，结合其他维度判断根因：

| 场景 | Token | 延迟 | 成本 | 可能根因 |
|------|-------|------|------|---------|
| **正常高负载** | 高 | 高 | 高 | 处理了更大的输入文档 |
| **推理循环** | 极高 | 极高 | 极高 | Agent 陷入思考循环 |
| **工具超时** | 低 | 高 | 低 | 外部 API 响应慢 |
| **模型退化** | 高 | 中 | 高 | 模型输出变长 / 重复 |
| **调用突增** | 高 | 低 | 高 | Agent 步骤数异常增加 |

## 关键概念速查

| 术语 | 解释 |
|------|------|
| Token 消耗 | Agent 执行过程中 LLM API 消耗的 Token 总数，分输入和输出 |
| P50 | 第 50 百分位延迟，即中位数延迟，代表"典型"用户体验 |
| P95 | 第 95 百分位延迟，代表 5% 的"较差"用户体验 |
| P99 | 第 99 百分位延迟，代表 1% 的"极差"用户体验（尾延迟） |
| Histogram | Prometheus 直方图指标类型，用于计算百分位值 |
| Counter | Prometheus 计数器指标类型，只增不减，适合累计量 |
| Gauge | Prometheus 仪表盘指标类型，可增可减，适合实时值 |
| Tail Latency | 尾部延迟（即 P99 或 P999），代表最差情况下的延迟 |
| 成本归因 | 将 Token 消耗乘以模型单价得出成本的核算方法 |
