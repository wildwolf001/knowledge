# 25.1 "把一切扔进上下文" —— 完整历史 + 全量工具 + 原始检索结果

> 反模式：开发者认为"反正模型有 200K 上下文窗口，把所有东西都塞进去就完事了"。完整历史 + 全量工具定义 + 原始检索结果 + 所有中间计算 → 上下文在几轮对话后膨胀到数十万 tokens，触发注意力退化、质量下降、成本飙升。

---

## 一、症状描述

### 1.1 经典表现

```
开发者的想法：
"Claude 支持 200K 上下文，GPT-4 支持 128K，
把全部历史、所有工具、所有检索结果都放进去，
模型自己会找到需要的信息。"
```

结果：

```
轮数  上下文大小  每轮成本  回答质量
─────────────────────────────────────
1      10K       $0.03    优秀 
5      35K       $0.10    良好
10     80K       $0.23    一般（开始出现遗忘）
15     140K      $0.40    差（频繁遗忘关键信息）
20     200K+     $0.58    极差（无法正确引用早期信息）
```

**10 轮后成本增长 7 倍，质量下降 2 个等级**。

### 1.2 典型代码（反模式）

```python
# ❌ 反模式：把一切扔进上下文
class NaiveAgent:
    """
    反模式 Agent：所有信息无差别地追加到上下文。
    """
    def __init__(self, tools: list[dict]):
        self.tools = tools  # 全部工具定义
        self.history = []   # 完整对话历史
        self.tool_results = []  # 所有工具结果
        self.messages = [
            {
                "role": "system",
                "content": self._build_system_prompt()  # 包含全部工具定义
            }
        ]
    
    def _build_system_prompt(self) -> str:
        """构建系统提示——包含全部工具定义"""
        prompt = "你是 AI 助手。\n\n可用工具：\n"
        for tool in self.tools:
            prompt += json.dumps(tool, indent=2) + "\n"
        return prompt  # 可能 20K+ tokens
    
    def run(self, user_input: str) -> str:
        """每次调用时把全部历史都塞进去"""
        self.history.append({"role": "user", "content": user_input})
        
        # 消息列表持续增长——从不压缩
        messages = self.messages + self.history + self._get_recent_results()
        
        response = openai_client.chat.completions.create(
            model="gpt-4",
            messages=messages,  # 10 轮后可能 100K+ tokens
        )
        
        self.history.append({
            "role": "assistant", 
            "content": response.choices[0].message.content
        })
        
        return response.choices[0].message.content
    
    def _get_recent_results(self) -> list:
        """返回所有工具结果（从未清理）"""
        return self.tool_results  # 全部返回，不做选择性保留
```

**问题总结**：
1. 工具定义每次推理都完整发送（20K+ tokens）
2. 对话历史从不压缩（线性增长）
3. 工具结果从不清理（累积）
4. 检索结果全量保留

## 二、根因分析

### 2.1 "更大窗口 = 更好"的误区

2024-2025 年各大模型厂商竞相推出更大的上下文窗口（128K→200K→1M→2M），给开发者传递了一个错误信号：**上下文窗口越大，就可以塞越多东西**。

但事实是：
```
上下文窗口大小 ≠ 有效信息处理能力

从 24.4 节我们知道：
- 100K+ 上下文中，中间段的信息召回率不到 40%
- 模型性能在 64K-128K 范围内降至基线水平的 52%
- 更大窗口意味着更大的注意力稀释
```

**更大的窗口不是"让你塞更多东西"，而是"让你有更多空间做压缩和优化"**。

### 2.2 对"模型自主筛选"的过度信任

开发者认为"模型会根据注意力机制自动筛选重要信息"。但注意力机制的筛选能力是有限的：

```python
# 开发者的隐含假设
模型处理上下文 = 人类阅读文本（能自动忽略无关信息）

# 实际
模型处理上下文 = 对所有内容进行注意力计算
                 → 长上下文中的"注意力稀释"
                 → 中间内容被系统性忽略
                 → 无关信息占用宝贵的注意力资源
```

### 2.3 缺乏成本意识

"把一切扔进去"在开发阶段（少量测试）看起来没问题，但在生产规模下成本呈指数级增长：

```
开发测试：
10 个测试 × 15K tokens/次 × $0.003/K = $0.45/天 → 不痛不痒

生产环境：
10,000 请求/天 × 95K tokens/次 × $0.003/K = $2,850/天
→ 月成本 $85,500，足以让 CFO 过问
```

## 三、检测方法

### 3.1 上下文增长率检测

```python
def detect_context_bloat(conversation_log: list[dict]) -> dict:
    """
    检测上下文的增长模式。
    
    健康模式：每轮增加固定或递减的 token 量
    膨胀模式：每轮增加的 token 量递增（历史累积）
    """
    tokens_per_turn = []
    for turn in conversation_log:
        total_tokens = count_tokens(turn["messages"])
        tokens_per_turn.append(total_tokens)
    
    deltas = [
        tokens_per_turn[i+1] - tokens_per_turn[i]
        for i in range(len(tokens_per_turn) - 1)
    ]
    
    avg_delta = sum(deltas) / len(deltas) if deltas else 0
    growth_trend = "increasing" if deltas and deltas[-1] > deltas[0] * 1.5 else "stable"
    
    return {
        "total_growth": tokens_per_turn[-1] - tokens_per_turn[0],
        "avg_delta_per_turn": avg_delta,
        "growth_trend": growth_trend,
        "is_bloating": growth_trend == "increasing" and avg_delta > 5000,
        "recommendation": "启用上下文压缩" if avg_delta > 5000 else "正常"
    }
```

### 3.2 "无用 Token"占比分析

```python
def analyze_useless_tokens(conversation: dict) -> dict:
    """
    分析上下文中"无用 Token"的占比。
    """
    total_tokens = count_tokens(conversation["messages"])
    
    used_tool_results = sum(
        count_tokens(msg["content"]) 
        for msg in conversation["messages"]
        if msg["role"] == "tool" and _is_already_used(msg)
    )
    
    unused_tool_schemas = sum(
        count_tokens(t["description"]) 
        for t in conversation.get("tool_definitions", [])
        if not _is_relevant_to_current_step(t, conversation["current_step"])
    )
    
    useless_total = used_tool_results + unused_tool_schemas
    useless_ratio = useless_total / total_tokens if total_tokens > 0 else 0
    
    return {
        "useless_ratio": useless_ratio,
        "verdict": "严重浪费" if useless_ratio > 0.5 
                   else "需要优化" if useless_ratio > 0.3
                   else "可接受"
    }
```

## 四、解决方案（正确做法）

### 4.1 结构化上下文 + 分层管理

```python
# ✅ 正确做法：结构化上下文
class StructuredAgent:
    """
    正确做法：结构化上下文管理。
    每层有独立的预算、压缩策略和刷新周期。
    """
    def __init__(self, tools: list[dict]):
        self.tool_categories = self._categorize_tools(tools)
        self.summary_buffer = SummaryBuffer(max_tokens=4000)
        self.result_window = ResultWindow(max_results=5)
    
    def build_context(self, user_input: str) -> list[dict]:
        messages = []
        
        # 第 1 层：系统指令（精简版，~500 tokens）
        messages.append({
            "role": "system",
            "content": self._get_system_prompt()
        })
        
        # 第 2 层：动态工具 Schema（仅加载相关类别，~3K tokens）
        relevant_tools = self._get_relevant_tools(user_input)
        messages.append({
            "role": "system",
            "content": f"当前可用工具：\n{json.dumps(relevant_tools)}"
        })
        
        # 第 3 层：对话历史摘要（~3K tokens）
        history_summary = self.summary_buffer.get_summary()
        if history_summary:
            messages.append({
                "role": "system", 
                "content": f"对话摘要：\n{history_summary}"
            })
        
        # 第 4 层：最近的工具结果（窗口版，~2K tokens）
        recent_results = self.result_window.get_recent()
        if recent_results:
            for r in recent_results:
                messages.append(r)
        
        # 第 5 层：用户输入
        messages.append({"role": "user", "content": user_input})
        
        return messages
    
    def _categorize_tools(self, tools: list[dict]) -> dict:
        categories = {}
        for tool in tools:
            category = tool.get("category", "通用")
            if category not in categories:
                categories[category] = []
            categories[category].append(tool)
        return categories
    
    def _get_relevant_tools(self, user_input: str) -> list[dict]:
        intent = self._classify_intent(user_input)
        if intent in self.tool_categories:
            return self.tool_categories[intent]
        return self.tool_categories.get("通用", [])[:5]
```

### 4.2 上下文压缩（Micro + Auto）

```python
class ContextCompressor:
    """
    上下文压缩器。
    - Micro：清除已使用的工具结果（零成本）
    - Auto：对历史做 LLM 摘要（有成本但效果好）
    """
    def compress(self, messages: list[dict]) -> list[dict]:
        messages = self._micro_compress(messages)
        total_tokens = count_tokens(messages)
        if total_tokens > 30000:
            messages = self._auto_compress_history(messages)
        return messages
    
    def _micro_compress(self, messages: list[dict]) -> list[dict]:
        """清除已消费的工具结果"""
        compressed = []
        consumed_tool_ids = set()
        for msg in reversed(messages):
            if msg["role"] == "tool" and msg.get("tool_call_id") in consumed_tool_ids:
                compressed.append({
                    "role": "tool",
                    "content": "[结果已处理]",
                    "tool_call_id": msg["tool_call_id"]
                })
            else:
                compressed.append(msg)
            if msg["role"] == "assistant" and msg.get("tool_calls"):
                for tc in msg["tool_calls"]:
                    consumed_tool_ids.add(tc["id"])
        return list(reversed(compressed))
```

### 4.3 正确做法 vs 反模式对比

| 维度 | 反模式：全部扔进去 | 正确做法：结构化 |
|------|-----------------|---------------|
| 工具定义 | 全部发送（20K+ tokens） | 按需加载（3K-5K tokens） |
| 对话历史 | 完整保留（线性增长） | 摘要 + 滑动窗口（可控增长） |
| 工具结果 | 全部保留（累积） | 消费后清理或摘要 |
| 检索文档 | 原始全文保留 | 摘要 + 仅保留关键信息 |
| 总长度 | 20 轮后 100K+ | 20 轮后 15K-25K |

## 五、预防措施

### 5.1 上下文预算意识培养

```yaml
上下文预算守则:
  1. "200K 窗口是上限，不是目标"：目标是让上下文越小越好
  2. "每增加 1K tokens，增加 $0.003 成本"：每个决策都有成本
  3. "上下文每隔 N 步做一次体检"：检查上下文是否健康
  4. "先压缩，再发送"：发送前的最后一步是压缩
```

### 5.2 开发阶段的上下文检查

```python
def assert_context_healthy(messages: list[dict]):
    total = count_tokens(messages)
    assert total < 30000, f"上下文过长：{total} tokens"
    
    tool_content = [m for m in messages if "可用工具" in m.get("content", "")]
    for tc in tool_content:
        tool_tokens = count_tokens(tc["content"])
        assert tool_tokens < 8000, f"工具定义占用 {tool_tokens} tokens，考虑按需加载"
```

### 5.3 "端到端 Token 预算"作为架构要求

```yaml
架构要求：Token 预算
  每轮推理总 token 上限: 25,000
  其中：
    - 系统指令: ≤ 1,000
    - 工具 Schema: ≤ 5,000（按需加载）
    - 对话历史: ≤ 5,000（摘要 + 滑动窗口）
    - 工具结果: ≤ 3,000（消费后清除）
    - 检索结果: ≤ 3,000（仅关键片段）
    - 模型输出预留: ≤ 3,000
```

## 关键教训速查

| 教训 | 说明 |
|------|------|
| 大窗口不是乱塞的借口 | 更大窗口意味着更大的注意力稀释 |
| 工具定义按需加载 | 不用的工具不要发送 |
| 对话历史必须压缩 | 完整历史是最隐蔽的 Token 杀手 |
| 工具结果消费后清除 | Agent 已经"消化"过的结果没有保留价值 |
| 设定 Token 预算是架构要求 | 不是可选项，是必须项 |
| 开发环境不痛不痒，生产环境致命 | 成本和质量问题在量产后才暴露 |
