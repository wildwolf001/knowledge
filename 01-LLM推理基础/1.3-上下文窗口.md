# 1.3 上下文窗口——从 4K 到 2M 的演进

> 上下文窗口从 GPT-3 的 4K 发展到 Gemini 2.5 的 2M，500 倍的扩张背后是架构创新、注意力优化和工程取舍的共同结果。但更大的窗口并不总是更好——"Lost in the Middle" 现象揭示了长上下文的微妙挑战。

---

### 1.2 窗口扩大的核心技术

**1.2.1 注意力机制优化**

从标准 Softmax Attention → 高效的稀疏/线性注意力（详见 [1.1 节](./1.1-Transformer自注意力与KV-Cache.md)）：

```
4K → 32K: 使用 FlashAttention (Dao et al., 2022)
  FlashAttention 通过分块（tiling）将 O(n²) 的显存需求降至 O(n)，
  实际计算速度提升 2-3 倍，长序列下更明显。

32K → 128K: QA 优化 + GQA
  Grouped Query Attention 减少 KV Cache 体积，使长序列推理可行。
  Ring Attention 支持分布式序列并行。

128K → 1M+: 稀疏注意力 + 位置编码优化
  ALiBi (Press et al., 2021): 无需训练即可外推至更长序列
  RoPE (Su et al., 2023): 旋转位置编码，支持一定程度的外推
  YaRN (Peng et al., 2023): 改进 RoPE 的频率缩放，实现窗口扩展
```

**1.2.2 位置编码的选择**

RoPE（Rotary Position Embedding）是当前最主流的方案，被 Llama、Mistral、Qwen、Gemma 等广泛采用。它通过旋转矩阵编码位置信息，使注意力分数自然包含相对位置衰减。

```
标准位置编码 (GPT-3): 可训练的绝对位置 Embedding，不支持窗口外推
RoPE (当前主流): 通过旋转矩阵编码相对位置，支持插值外推
ALiBi (MosaicML): 在注意力分数上加位置偏差，极好外推能力
     但被 RoPE 逐渐取代
```

**RoPE 窗口扩展的关键公式（NTK-aware 插值）**：

```
原始 RoPE: θᵢ = 10000^(-2i/d)   ← i 是维度索引
NTK 扩展:  θᵢ' = (10000 * s^(-2i/(d-2)))^(-2i/d)
           ↑ s 是缩放因子，s = target_length / base_length

当 base=4K, target=128K 时 s=32
新的 θ 分布使高频维度差异变大（保留局部精度）、低频维度差异变小（覆盖更长范围）
```

## 二、注意力衰减曲线

### 2.1 什么是注意力衰减

注意力衰减是指模型在处理长序列时，距离当前位置越远的 token 获得的注意力权重越小的现象。这不是 Bug，而是由注意力机制和位置编码共同导致的**系统性偏差**。

```
注意力权重分布示意图（简化）：

位置 i 对位置 j 的注意力：

j = i ← 当前 token    权重: ~0.3  (self-attention 通常很大)
j = i-1 ← 前一个 token 权重: ~0.2
j = i-2 ← 前两个 token  权重: ~0.1
...
j = i-100         权重: ~0.001
j = i-1000        权重: ~0.0001

→ 注意力权重随距离大致呈指数衰减（近似为长尾分布）
```

### 2.2 衰减的原因

1. **Softmax 的固有属性**：Softmax 输出的是概率分布，存在"竞争"效应。近处的 token 往往有更高的点积相似度，占据了大部分概率质量，远处的 token 被挤压到很小的数值。

2. **位置编码的影响**：RoPE 的计算中，两个 token 的距离越远，它们之间旋转角度的差异越大，点积的最大值越小。RoPE 注意力分数的上界随距离单调递减。

3. **训练数据中的偏移**：训练语料中，绝大多数有价值的信息出现在局部范围内（相邻句子、同一段落），模型"学会"了更多关注局部，全局注意力的权重被训练信号自然压低。

### 2.3 衰减曲线的工程测量

以下是对 Llama-2-7B 在 32K 输入上的注意力分布测量结果（示意数据）：

| 距离（token 数） | 平均注意力权重 | 累计注意力占比 |
|-----------------|--------------|--------------|
| 0-1024 | 0.45 | 45% |
| 1024-2048 | 0.20 | 65% |
| 2048-4096 | 0.15 | 80% |
| 4096-8192 | 0.10 | 90% |
| 8192-16384 | 0.06 | 96% |
| 16384-32768 | 0.04 | 100% |

**结论**：约 80% 的注意力集中在最近的 4K token 内。离当前位置超过 16K 的 token，平均注意力权重已不足 0.06。

## 三、"Lost in the Middle" 现象

### 3.1 发现与实验设计

"Lost in the Middle"（中间丢失）由 Liu et al. (2023) 在一篇系统性研究中正式提出。该研究发现：**模型在处理长文档时，对中间位置的信息检索准确率显著低于文档开头和结尾**。

实验设计（详见原论文 "Lost in the Middle: How Language Models Use Long Contexts"）：

```python
# 简化的实验框架
def test_position_accuracy(model, docs, query):
    """
    doc: 包含 K 个知识文档的列表
    目标知识被放在不同的位置
    query: "根据上述文档，{目标知识的提问}"
    测量模型回答的准确率
    """
    results = []
    for target_pos in range(len(docs)):
        # 控制长度（10个文档 ≈ 10K token）
        context = assemble_context(docs, target_pos)
        prompt = context + "\n\n" + query
        answer = model.generate(prompt)
        accuracy = evaluate_answer(answer, ground_truth)
        results.append((target_pos, accuracy))
    return results
```

**关键结果**：

```
准确率 vs 目标知识位置（10 个文档，~10K token）：

位置 1（开头）:   准确率 ~85%
位置 2:           准确率 ~80%
位置 3:           准确率 ~65%   ← 开始下降
位置 4-7（中间）:  准确率 ~45-55%  ← "Lost in the Middle"
位置 8:           准确率 ~60%
位置 9:           准确率 ~70%
位置 10（末尾）:   准确率 ~80%
```

### 3.2 为什么会"丢失"在中间

分析其原因，至少有四个因素叠加：

**① 注意力衰减 + 首尾效应**：注意力机制天然关注序列两端。开头有"锚定效应"——模型学习到文档开头通常包含摘要/关键信息。末尾有"近因效应"——最近读到的信息最容易回忆。

**② 训练数据偏差**：在训练时，多数 QA 对的知识分布要么在文档开头（如 Wikipedia 的第一句就是定义），要么在最后（如对话的最后一条消息），中间位置被均匀采样的概率低。

**③ 上下文干扰**：与目标信息无关的其他文档作为"干扰项"存在。中间位置的干扰项不仅更多（前后都有），而且模型在处理到中间时已经产生了注意力疲劳。

**④ 长度泛化不足**：模型在有限的训练长度下训练（如 8K），推理时被要求处理更长的序列（如 128K），中间区域超出了训练时的有效泛化范围。

### 3.3 工程应对策略

**策略一：信息优先排序**

将最重要的信息放在 Prompt 的开头或结尾，而不是中间：

```
❌ 不好的顺序：
[背景信息] [背景信息] [核心指令] [背景信息] [背景信息]

✅ 好的顺序：
[核心指令] [重要上下文的引用] [背景信息] [背景信息] [背景信息]
```

**策略二：分段检索 + 多轮融合**

在 RAG 系统中（详见 [第 8 章 RAG 系统](../08-RAG系统/)），不要一次性塞入过多文档：

```python
def rag_with_position_awareness(query, doc_store, top_k=10):
    """分段检索 + 选择性融合"""
    docs = doc_store.search(query, top_k=20)
    docs = rerank_by_relevance(query, docs)  # 按相关性排序
    
    # 策略：只取最相关的，避免信息淹没
    if len(docs) > top_k:
        docs = docs[:top_k]
    
    # 核心信息放开头，补充信息放后面
    prompt = "关键信息：\n" + docs[0] + "\n\n"
    prompt += "参考信息：\n" + "\n\n".join(docs[1:])
    return model.generate(prompt)
```

**策略三：结构化上下文模板**

使用 XML/JSON 标记明确信息的位置和用途（本节的设计思想延伸见 [14.2 多层护栏](../14-降低幻觉/14.2-多层护栏.md)）：

```
<context>
  <instructions priority="high">核心指令...</instructions>
  <documents>
    <doc index="1" relevance="0.95">相关内容...</doc>
    <doc index="2" relevance="0.80">次要内容...</doc>
  </documents>
</context>
```

**策略四：多步推理中的"Iceberg"处理**

在超长上下文中，让模型先"扫读"再"精读"：

```python
# Step 1: 让模型先识别哪些部分是重要的
def scan_and_identify(long_context, question):
    summary_prompt = f"""从以下长文本中找出与问题相关的部分：
    问题：{question}
    文本：{long_context[:1000]}...{long_context[-1000:]}
    请列出关键段落的索引和摘要。"""
    related_parts = model.generate(summary_prompt)
    return parse_indices(related_parts)

# Step 2: 只提取相关部分进行精读
def deep_read(related_parts, question):
    focused_prompt = f"""基于下面列出的相关段落回答问题：
    {related_parts}
    问题：{question}
    请给出详细回答并标注信息来源的段落索引。"""
    return model.generate(focused_prompt)
```

## 四、长上下文的技术局限与成本

### 4.1 推理成本随窗口递增

即使在 KV Cache 优化下（见 [1.1 节](./1.1-Transformer自注意力与KV-Cache.md)），长上下文的推理成本仍然显著：

| 上下文长度 | Prefill 时间（Llama-70B, A100） | KV Cache 大小 | 相对成本 |
|-----------|-------------------------------|--------------|---------|
| 4K | ~0.1s | ~0.3 GB | 1x |
| 32K | ~0.8s | ~2.4 GB | ~8x |
| 128K | ~3.2s | ~10 GB | ~32x |
| 1M | ~25s | ~80 GB | ~250x |

### 4.2 长上下文的正确率衰减

多份研究一致表明，在超长上下文中模型的检索准确率随长度增加而下降：

```
Needle-in-a-Haystack 测试（超过 100K token）：

上下文长度 | 平均检索准确率
  4K      |  98%
  32K     |  94%
  64K     |  88%
  128K    |  72%
  256K    |  55%
  1M      |  35-40%
  
注：不同模型表现差异巨大，Claude 4 在 128K 以上表现最优，
DeepSeek-V3 的 MLA 架构在长上下文上也有竞争力
```

### 4.3 "足够大"是否已经够了？

对于大多数实际 RAG 场景，32K-128K 的窗口已经覆盖绝大多数使用场景：
- 一份软件的完整文档：~50K token
- 一本书的完整章节：~20K-50K token
- 一份法律合同：~10K-50K token
- 一次完整技术会议记录：~30K-100K token

超过 200K token 的超长上下文在**单次分析型任务**（全库扫描、百万行日志分析）中有价值，但对于交互式应用，更大的窗口带来的**延迟和成本增加往往超过了检索准确率的边际提升**。

## 关键概念速查

| 术语 | 解释 |
|------|------|
| 上下文窗口 | 模型一次能处理的最大 token 数，决定输入文本的长度上限 |
| RoPE | 旋转位置编码，通过旋转矩阵编码相对位置，当前最主流的方案 |
| 注意力衰减 | 注意力权重随 token 间距离增加而下降的现象 |
| Lost in the Middle | 模型对文档中间位置的信息检索准确率显著低于两端 |
| FlashAttention | 通过分块计算减少显存占用的高效注意力实现 |
| NTK-aware 插值 | 通过调整 RoPE 频率分布实现窗口扩展的技术 |
| Needle-in-a-Haystack | 在长文档中检索特定信息的基准测试，评估模型长上下文能力 |
| Prefill | 长上下文推理的第一阶段，对全部输入 token 做注意力计算 |
