# 1.1 Transformer 自注意力与 KV Cache

> 为什么大语言模型处理长文本时计算量和内存会急剧增长？答案藏在自注意力机制 O(n²) 的复杂度里。KV Cache 是缓解这一瓶颈的核心工程优化，理解它才能理解长上下文的成本构成。

---

## 一、自注意力机制（Self-Attention）

### 1.1 从词向量到 QKV

自注意力是 Transformer 架构的核心运算。对于输入序列中的每个 token，模型通过三个不同的线性变换将其映射为三个向量：**Query（查询）**、**Key（键）**、**Value（值）**。

设输入序列长度为 n，每个 token 的嵌入维度为 d，则三个权重矩阵分别为 W_Q, W_K, W_V ∈ R^{d×d_k}（其中 d_k = d/h，h 为注意力头数）：

```
输入 X ∈ R^{n×d}
Q = X · W_Q     →  R^{n×d_k}
K = X · W_K     →  R^{n×d_k}
V = X · W_V     →  R^{n×d_k}
```

直观理解：
- **Query**：当前 token "想查找什么"
- **Key**：当前 token "有什么可被查找的"
- **Value**：当前 token "实际贡献的信息"

### 1.2 注意力分数的计算

自注意力的核心公式如下：

```
Attention(Q, K, V) = softmax(Q × K^T / √d_k) × V

                  = softmax( 分数矩阵  ) × 值矩阵

                  = softmax( [n×d_k] × [d_k×n] / √d_k ) × [n×d_k]

                  = softmax(       [n×n]          ) × [n×d_k]

                  =                [n×d_k]
```

其中 `Q × K^T` 得到一个 n×n 的注意力分数矩阵，矩阵中第 i 行第 j 列的元素表示位置 i 对位置 j 的注意力强度。除以 `√d_k` 是为了防止 softmax 进入梯度饱和区。Softmax 按行归一化，使每行的注意力权重之和为 1。

**具体的逐元素计算**：

```
score(i, j) = (Q[i] · K[j]) / √d_k

权重(i, j) = exp(score(i, j)) / ∑_{k=1}^{n} exp(score(i, k))

输出[i] = ∑_{j=1}^{n} 权重(i, j) × V[j]
```

这意味着位置 i 的输出是所有位置 V 的加权和，权重由 Q[i] 与所有 K[j] 的相似度决定。

### 1.3 为什么是 O(n²)——长上下文的成本爆炸

自注意力机制的计算量随序列长度呈平方级增长：

| 运算 | 复杂度 | 说明 |
|------|--------|------|
| Q/K/V 投影 | O(n·d²) | 每个 token 做线性变换 |
| QK^T 计算 | O(n²·d_k) | 每对 token 计算点积 |
| Softmax | O(n²·d_k) | 每行归一化 |
| 加权求和 | O(n²·d_k) | V 加权求和 |
| **总体** | **O(n²·d)** | n 是主导因子 |

当 n 从 4K 增长到 128K：
- QK^T 矩阵从 4K×4K = 16M 个元素 → 128K×128K = 16.4G 个元素
- 计算量增加约 1024 倍（n² 增长因子）

这就是为什么在没有优化的情况下处理 128K 上下文比 4K 昂贵两个数量级。这也解释了为什么上下文窗口每扩大一倍，推理成本理论上增加约 4 倍。

## 二、KV Cache：工程上的核心优化

### 2.1 自回归生成中的重复计算

LLM 的生成是**自回归**（Autoregressive）的：每个新 token 的生成依赖于之前所有 token。

以生成"今天天气真好"为例：

```
Step 1: 输入 [<BOS>]              → 输出"今天"
Step 2: 输入 [<BOS>, 今天]        → 输出"天气"
Step 3: 输入 [<BOS>, 今天, 天气]  → 输出"真好"
```

**朴素实现的问题**：在 Step 3 计算 `[<BOS>, 今天, 天气]` 的注意力时，前三步的计算结果被完全丢弃，需要从头重新计算所有 Q、K、V 和注意力分数。

Step 3 的 QK^T 矩阵中，有 2/3 的行（与 <BOS>、今天 相关的行）在 Step 2 已经算过。如果每次重新计算，总计算量将达到 O(n³)。

### 2.2 KV Cache 的原理

KV Cache 的核心思想是：**把每一步计算得到的 K 和 V 矩阵缓存起来，下一歩只需要计算新增 token 的 K 和 V，然后拼接即可**。

具体做法：

```
Step 1: 输入 [t₁]
         计算 K₁, V₁          → Cache: [K₁], [V₁]
         用 [Q₁, K₁, V₁] 生成 t₂

Step 2: 输入 [t₂]
         只计算 K₂, V₂          → Cache: [K₁, K₂], [V₁, V₂]
         用 [Q₂, Cache_K, Cache_V] 生成 t₃

Step 3: 输入 [t₃]
         只计算 K₃, V₃          → Cache: [K₁, K₂, K₃], [V₁, V₂, V₃]
         用 [Q₃, Cache_K, Cache_V] 生成 t₄
```

**关键点**：对于位置 i 的 query，它只需要和所有 K/V 做注意力计算。Cache 已经包含了之前所有位置的 K/V，新 token 只需要计算自己的 K/V 并拼接即可。

### 2.3 计算量对比

| 阶段 | 朴素实现 | KV Cache 优化 |
|------|---------|--------------|
| Prefill（预填充） | O(n²·d) | O(n²·d)（完全计算第一个 n 个 token） |
| 每步生成 | O(n²·d) | O(n·d)（仅新 token 的自注意力） |
| 总生成 m 个 token | O((n+m)³·d) | O(n²·d) + O(m·n·d) |
| 加速比（m >> n） | — | ~O(m) 倍 |

典型场景（n=1000, m=1000）：
- 朴素实现：需要约 (2000)³ = 8×10⁹ 次操作
- KV Cache：需要约 1000² + 1000×1000 ≈ 2×10⁶ 次操作
- **加速约 4000 倍**

### 2.4 KV Cache 的代价

KV Cache 不是免费的。它通过**空间换时间**——用 GPU 显存换取计算速度：

```
KV Cache 大小 = 2 (K 和 V) × n × d_k × h × b × precision

示例（Llama 65B, n=4096, d_k=128, h=64, b=1, FP16）:
= 2 × 4096 × 128 × 64 × 1 × 2 bytes
= 2 × 4096 × 128 × 64 × 2
= 134,217,728 bytes ≈ 134 MB

当 n=128K 时 ≈ 134 MB × 32 ≈ 4.3 GB（一个请求）
```

| 模型 | 参数量 | 单层 KV Cache 大小 (4K) | 单层 KV Cache 大小 (128K) |
|------|--------|------------------------|-------------------------|
| GPT-3 | 175B | ~800 MB | ~25 GB |
| Llama 70B | 70B | ~320 MB | ~10 GB |
| Qwen 7B | 7B | ~40 MB | ~1.3 GB |

在服务高并发时（batch_size=64, 128K 上下文），单个推理节点的显存很快会被 KV Cache 耗尽，这是长上下文部署的主要瓶颈。

## 三、KV Cache 的高级优化

### 3.1 MQA 与 GQA

标准多头注意力（Multi-Head Attention, MHA）中每个注意力头有独立的 K 和 V，导致 KV Cache 随头数线性增长。

**Multi-Query Attention (MQA)**：所有注意力头共享同一组 K 和 V。KV Cache 缩小为 1/h，但精度可能下降。

**Grouped Query Attention (GQA)**：折中方案。将 h 个头分为 g 组，每组共享一对 K 和 V。当 g=4 时 KV Cache 减少至约 1/4，而质量损失微小。

当前主流模型广泛使用 GQA：
- Llama 2 70B: GQA (g=8)
- Mistral: GQA (g=8)
- DeepSeek-V3: MLA（Multi-head Latent Attention，一种压缩比率更高的变体）
- GPT-4o: 推测使用 GQA 或类似优化

### 3.2 PagedAttention 与 vLLM

传统 KV Cache 在内存中按请求连续存储，碎片化严重且无法动态扩展。vLLM 提出的 **PagedAttention** 借鉴操作系统虚拟内存的分页思想：

```
传统方式: [请求1的KV][请求2的KV][请求3的KV] ← 连续分配
          ↑ 碎片多，无法按需扩展

PagedAttention: [块1][块5][块2]  ← 分页存储
                [块3][块4][块6]
                ↑ 物理不连续，逻辑连续
```

PagedAttention 实现了：
- **零碎片**：按 Block（通常 16 个 token）分配，消除内部和外部碎片
- **按需分配**：随解码过程动态分配新 Block，不预分配超额内存
- **Copy-on-Write**：多条生成路径共享相同前缀的 KV Cache（Tree-of-Thoughts 时非常有用）

vLLM 实测在相同硬件上实现 2-4 倍的吞吐量提升，已成为 LLM 推理服务的行业标准。

### 3.3 滑动窗口注意力

Sliding Window Attention（如 Mistral 和 Gemma 使用）限制每个 token 只与窗口内的 W 个 token 做注意力，将复杂度从 O(n²) 降至 O(n·W)：

```
窗口 W=4:
token 1: [1, 2, 3, 4, 5]
token 2: [1, 2, 3, 4, 5]
token 3: [1, 2, 3, 4, 5]
...
token 9: [5, 6, 7, 8, 9, 10] ← 只关注最近 4 个位置
```

滑动窗口的核心假设是**局部性**——语言建模中，当前 token 主要受其相邻 token 影响。错层的多层滑动窗口（通过堆叠多层使有效感受野达到 O(W·L)）可部分弥补长程依赖。

## 关键概念速查

| 术语 | 解释 |
|------|------|
| 自注意力（Self-Attention） | Transformer 中每个 token 与其他所有 token 计算关联权重的机制 |
| QKV | Query（查询）、Key（键）、Value（值）——注意力机制的三个基本投影向量 |
| O(n²) 复杂度 | 自注意力的计算量随序列长度平方增长，是长上下文的主要瓶颈 |
| KV Cache | 缓存已计算的 Key 和 Value 矩阵，避免自回归生成中的重复计算 |
| Prefill | 第一阶段计算，对所有 prompt token 做完整注意力并填充 KV Cache |
| Grouped Query Attention (GQA) | 分组共享 K/V 的注意力变体，在质量和效率间取得平衡 |
| PagedAttention | vLLM 的分页式 KV Cache 管理，消除碎片、支持动态扩展 |
| 滑动窗口注意力 | 限制每个 token 只关注附近 W 个 token，复杂度 O(n·W) |
| 自回归生成 | 逐 token 生成，每个新 token 依赖之前的所有 token |
