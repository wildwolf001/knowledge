# 1.2 Tokenization 的工程影响

> Tokenization（分词）是 LLM 处理文本的第一步，也是工程师最常忽视的成本陷阱。不同分词器在相同文本上产生的 token 数差异可达数倍，直接影响推理延迟、上下文窗口利用率和 API 账单。

---

## 一、什么是 Tokenization

Tokenization 是将原始文本切分成模型可以处理的"原子单位"——token 的过程。这些 token 被映射为整数 ID 后送入模型。Tokenization 不是简单的"按字切分"，它涉及复杂的算法决策。

LLM 的整个流程可以表示为：

```
原始文本 → Tokenizer → [t₁, t₂, ..., tₙ] → Embedding → Transformer → ...
```

目前主流的分词方法是 **Byte Pair Encoding (BPE)** 和 **SentencePiece**，二者在预分词策略和分词粒度上存在本质差异。

---

## 二、BPE（Byte Pair Encoding）

### 2.1 BPE 的工作原理

BPE 最初是数据压缩算法，被 GPT 系列引入 NLP 领域。其核心思想是从字符级别开始，逐步合并训练数据中**频率最高的相邻 token 对**，直到达到目标词表大小。

训练过程（简化的 Python 伪代码）：

```python
def train_bpe(corpus: str, vocab_size: int) -> dict:
    # 1. 初始词表：所有单个字符
    vocab = {}  # token → id
    for char in set(corpus):
        vocab[char] = len(vocab)
    
    # 2. 统计所有相邻 token 对的频率
    # 3. 合并频率最高的 token 对
    while len(vocab) < vocab_size:
        pairs = count_adjacent_pairs(tokenized_corpus)
        most_frequent = max(pairs, key=pairs.get)
        
        # 合并：将 (a, b) 合并为新 token "ab"
        new_token = most_frequent[0] + most_frequent[1]
        vocab[new_token] = len(vocab)
        
        # 重新分词语料库（将 a,b 的出现替换为 ab）
        tokenized_corpus = merge_tokens(tokenized_corpus, most_frequent)
    
    return vocab
```

经过约 30K-100K 次合并（取决于目标词表大小），BPE 学会了常见的子词（如 "ing"、"tion"、"est"）和常见单词本身（如 "the"、"and"），使其成为单个 token。

### 2.2 BPE 的分词特点

```
输入: "unbelievable"
BPE分词: ["un", "believable"]  ← 如果 "un" 在词表中
      或: ["un", "believ", "able"]  ← 更细粒度

输入: "hello world"
BPE分词: ["hello", " world"]  ← 注意空格被保留
```

BPE 的一个关键特性是**贪心匹配**——从前向后查找词表中匹配的最长 token。这意味着分词结果并非唯一确定，且对输入文本的微小变化敏感（空格、标点）。

### 2.3 BPE 的局限

1. **预分词依赖**：BPE 需要先用空格和标点做预分词（pre-tokenization）。这意味着多语言（如中文、日文这类没有空格分隔的语言）表现不佳。
2. **空间效率**：同一个词经过不同上下文合并可能不同，导致推理时 token 数不稳定。
3. **退化的 token**：压缩比低的罕见词可能被切得很碎，浪费上下文窗口。

## 三、SentencePiece

### 3.1 SentencePiece 的原理

SentencePiece 由 Google 提出（2018），它不依赖预分词，而是将原始文本视为 **Unicode 字符流**或**字节流**直接处理。这使得它对任何语言都一视同仁。

**核心区别**：

```
BPE: 文本 → 预分词（按空格/标点切分）→ BPE 合并
SentencePiece: 文本 → Unicode 编码 → BPE/Unigram 合并
```

SentencePiece 支持两种子词算法：
- **BPE**（同上，但无预分词）
- **Unigram Language Model**：从较大 seed 词表开始，逐步剪枝移除使概率损失最小的 token，直至目标大小

### 3.2 SentencePiece 的中文处理

SentencePiece 对中文的处理方式决定了 token 效率：

```python
# 不同分词器对同一中文句子的分词结果
text = "深度学习模型在自然语言处理任务中表现出色"

# 基于 BPE 的 GPT-4 Tokenizer (cl100k_base):
# → ['深度', '学习', '模型', '在', '自然', '语言', '处理', '任务', '中', '表现', '出色']
# → 大约 11-15 个 token（取决于合并频率）

# 基于 SentencePiece 的 Llama 2 Tokenizer:
# → ['▁深', '度', '学', '习', '模型', '在', '自然', '语言', '处理', '任务', '中', '表现', '出色']
# → 大约 12-16 个 token
```

注意 SentencePiece 使用 `▁`（U+2581）表示空格位置——这也是为什么你在解码 Llama 输出时偶尔会看到前缀空格。

### 3.3 BPE vs SentencePiece 对比

| 维度 | BPE | SentencePiece |
|------|-----|---------------|
| 预分词 | 需要（空格/标点分割） | 不需要（直接处理原始文本） |
| 多语言支持 | 英文优秀，中文/日文较差 | 统一对待，多语言更均衡 |
| 可逆性 | 可逆（可还原原始文本） | 可逆 |
| 解码速度 | 快（贪心匹配） | 快（贪心匹配） |
| 词表大小 | GPT-4: ~100K | Llama 3: 128K, Gemma: 256K |
| 典型使用 | OpenAI GPT 系列 | Google 系列、Llama、Mistral |

## 四、中文 Token 膨胀问题

### 4.1 膨胀比率

中文文本的 token 数是英文的 2-4 倍，这不是感知上的错觉，而是分词器设计中语言偏见的直接结果。

```python
def count_tokens(text: str, encoding_name: str) -> int:
    """模拟不同语言的 token 计数"""
    import tiktoken
    enc = tiktoken.get_encoding(encoding_name)
    return len(enc.encode(text))

# 对比测试（使用 GPT-4 的 cl100k_base 编码）
english = "Deep learning models have achieved remarkable results"
chinese = "深度学习模型取得了令人瞩目的成果"

print(f"英文 token 数: {count_tokens(english, 'cl100k_base')}")
# → 8 个 token

print(f"中文 token 数: {count_tokens(chinese, 'cl100k_base')}")
# → 18 个 token（约 2.25 倍）
```

**实测数据**（使用 GPT-4 Tokenizer）：

| 语言 | 原文 | Token 数 | 比值 |
|------|------|---------|------|
| 英文 | "Hello, how are you today?" | 6 | 1.0x |
| 中文 | "你好，今天怎么样？" | 9 | 1.5x |
| 英文 | "Deep learning for natural language processing" | 7 | 1.0x |
| 中文 | "深度学习在自然语言处理中的应用" | 16 | 2.3x |
| 英文 | 100 词标准段落（~500 字符） | ~130 | 1.0x |
| 中文 | 等量信息段落（~200 汉字） | ~300 | 2.3x |

### 4.2 膨胀的工程影响

**直接后果**（以 GPT-4o API 价格为例，输入 $2.5/1M tokens）：

```
中文文档 × 100 页（约 50,000 汉字）
→ 约 75,000 tokens
→ 单次处理成本 ≈ $0.19

同等信息的英文文档
→ 约 25,000 tokens
→ 单次处理成本 ≈ $0.06  ← 便宜 68%
```

**更深层的影响**：
1. **有效上下文窗口缩减**：128K 窗口对中文用户实际只有约 50K-60K token 的等效窗口
2. **KV Cache 放大**：更多 token 意味着更大的 KV Cache，直接增加显存压力（见 [1.1 节 KV Cache 代价讨论](./1.1-Transformer自注意力与KV-Cache.md#24-kv-cache-的代价)）
3. **思维链效率降低**：中文推理需要更多 token 来"思考"，增加推理延迟
4. **价格不平等**：中文用户的 API 成本实际上比英文用户高 2-3 倍

### 4.3 缓解策略

1. **选用对中文友好的模型**：选择在中文语料上充分训练、词表包含更多中文字词的模型（如 Qwen、DeepSeek 的 tokenizer 对中文的压缩比优于 GPT 系列）
2. **输入优化**：去除冗余空格、精简指令、使用垂直格式（如 JSON 只保留必要字段，详见 [第 8 章 RAG 系统](../08-RAG系统/) 的 Prompt 压缩策略）
3. **token 感知的输入截断**：基于 token 数而非字符数决定截断点

## 五、Tokenizer 选择的工程决策

### 5.1 词表大小的权衡

| 词表大小 | 优势 | 劣势 |
|----------|------|------|
| 小（~32K） | Embedding 矩阵小，显存省 | 长文本 token 数多，长词被切碎 |
| 中（~128K） | 压缩比好，常见词整词编码 | Embedding 变大，尾部词表利用率低 |
| 大（~256K） | 极佳压缩比，少见词也整词编码 | Embedding 矩阵过大（256K×d），训练慢 |

### 5.2 特殊 Token 的设计

Tokenization 中的特殊 token 对 Agent 系统影响重大：

- **`<|begin_of_text|>` / `<|end_of_text|>`**：标记序列边界
- **`<|im_start|>` / `<|im_end|>`**：ChatML 格式分隔（标记对话轮次）
- **`<|tool_call|>` / `<|tool_result|>`**：工具调用标记（影响 Agent 的工具使用能力）
- **`<|thinking|>` / `<|/thinking|>`**：思考标记，影响 [1.4 节](./1.4-推理模式.md) 讨论的 Thinking Tokens 触发

GPT-4 的 tokenizer 中，特殊 token 设计直接影响 Agent 框架的可靠性——错误的 token 序列可能导致工具调用解析失败。

## 关键概念速查

| 术语 | 解释 |
|------|------|
| Tokenization | 将原始文本切分成模型可处理的基本单位（token）的过程 |
| BPE (Byte Pair Encoding) | 从字符级别开始，逐步合并高频相邻对的算法，GPT 系列使用 |
| SentencePiece | Google 提出的不依赖预分词的 tokenizer，支持 BPE 和 Unigram 两种算法 |
| 预分词 | BPE 前按空格和标点进行的初步切分，影响多语言表现 |
| Token 膨胀 | 中文等非空格分隔语言的 token 数显著多于英文的现象 |
| 词表大小 (Vocab Size) | 子词单元的总数量，影响压缩比和 Embedding 矩阵大小 |
| 特殊 Token | 标记对话、工具调用、文本边界的保留 token ID |
| 贪心匹配 | Tokenizer 解码时从前向后匹配词表中最长子串的策略 |
