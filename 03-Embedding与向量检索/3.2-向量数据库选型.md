# 3.2 向量数据库选型

## 概述

向量数据库（Vector Database）是专为 Embedding 向量设计的高效存储与检索系统。与传统的 PostgreSQL + pgvector 方案不同，专用向量数据库从底层存储引擎到索引算法都针对高维向量做了深度优化。

选择合适的向量数据库是构建 RAG 系统的关键决策之一。本章从架构设计、性能指标、适用场景三个维度深入对比 ChromaDB、Milvus、Qdrant 和 Pinecone 这四款主流产品。

## 3.2.2 各数据库深度分析

### ChromaDB — 轻量级嵌入式向量数据库

**定位**：面向 AI 原型开发和教学实验的轻量级向量数据库。

**架构特点**：
- **嵌入式运行**：无独立服务进程，直接嵌入到应用进程中运行
- **存储后端**：默认使用 DuckDB（持久化）和 ClickHouse-like 的列式存储（查询）
- **HNSW 索引**：基于 hnswlib 库的 HNSW（Hierarchical Navigable Small World）索引（见 3.3 节详解）
- **数据模型**：Collection → Document → Metadata + Embedding

**优点**：
- 零部署成本：`pip install chromadb` 即可使用
- Python 生态集成自然，与 LangChain/LlamaIndex 深度集成
- 自动的 Embedding pipeline（可配置多种 Embedding 模型）
- 支持内存模式，适合测试

**缺点**：
- 不适合大规模生产（单机瓶颈，无分布式能力）
- 写吞吐量低（约 500 QPS 写入）
- 无原生备份/恢复机制
- 缺乏权限管理和多租户支持

```python
import chromadb
from chromadb.config import Settings

# 初始化客户端（嵌入式模式）
client = chromadb.Client(Settings(
    chroma_db_impl="duckdb+parquet",
    persist_directory="./chroma_data"
))

# 创建 Collection
collection = client.create_collection(
    name="my_knowledge_base",
    metadata={"hnsw:space": "cosine"}  # 使用余弦距离
)

# 添加文档（自动编码或直接提供 Embedding）
collection.add(
    documents=["这是第一条文档", "这是第二条文档"],
    metadatas=[{"source": "doc1"}, {"source": "doc2"}],
    ids=["id1", "id2"]
)

# 检索
results = collection.query(
    query_texts=["相关的问题"],
    n_results=5
)
```

**最佳场景**：个人项目、原型验证（PoC）、教学演示、小规模数据（<10万条）。

### Milvus — 分布式高性能向量数据库

**定位**：面向大规模生产环境的分布式向量数据库，云原生架构。

**架构特点**：

```
                    Milvus 2.x 架构
    ┌──────────────────────────────────────────┐
    │                Load Balancer              │
    └────┬──────────────┬──────────────┬───────┘
         │              │              │
    ┌────▼────┐   ┌────▼────┐   ┌────▼────┐
    │ Proxy   │   │ Proxy   │   │ Proxy   │   ← 无状态接入层
    └────┬────┘   └────┬────┘   └────┬────┘
         │              │              │
    ┌────▼────────────────────────────▼────┐
    │           Coordinator Service        │
    │  ┌──────┐ ┌──────┐ ┌──────┐         │
    │  │ Root │ │Data  │ │Query │         │  ← 元数据与调度
    │  │Coord │ │Coord │ │Coord │         │
    │  └──────┘ └──────┘ └──────┘         │
    └─────────────────────────────────────┘
         │              │              │
    ┌────▼────┐   ┌────▼────┐   ┌────▼────┐
    │ Query   │   │ Data    │   │ Index   │
    │ Node   │   │ Node    │   │ Node    │   ← 工作节点
    └─────────┘   └─────────┘   └─────────┘
    ┌──────────────────────────────────────┐
    │            Object Storage            │
    │   (MinIO / S3 / Azure Blob)         │  ← 日志与索引持久化
    └──────────────────────────────────────┘
    ┌──────────────────────────────────────┐
    │         Message Queue               │
    │   (Pulsar / Kafka / RocksMQ)        │  ← 流式数据通道
    └──────────────────────────────────────┘
```

核心设计理念是 **存储与计算分离**（Log as Data）：
- 数据写入先到 Message Queue（消息队列），保证可靠性
- Data Node 消费消息，转换为 Segment 写入对象存储
- Index Node 异步构建索引
- Query Node 从对象存储加载 Segment 并提供查询服务

**支持的索引类型**（见 3.3 节详解）：

| 索引类型 | 适用场景 | 精度 | 构建速度 | 内存占用 |
|---------|---------|------|---------|---------|
| IVF_FLAT | 中等规模、高精度 | 高 | 快 | 高 |
| IVF_SQ8 | 存储受限场景 | 中 | 快 | 低（量化压缩） |
| HNSW | 需要极速检索 | 高 | 慢 | 最高 |
| DISKANN | 超大超内存（见 3.3） | 高 | 慢 | 极低（SSD存储） |
| AUTOINDEX | 自动选择最优索引 | 动态 | 动态 | 动态 |

```python
from pymilvus import connections, Collection, CollectionSchema, FieldSchema, DataType

# 连接到 Milvus 服务
connections.connect(
    alias="default",
    host="localhost",
    port="19530"
)

# 定义 Schema
fields = [
    FieldSchema(name="id", dtype=DataType.INT64, is_primary=True, auto_id=True),
    FieldSchema(name="embedding", dtype=DataType.FLOAT_VECTOR, dim=768),
    FieldSchema(name="text", dtype=DataType.VARCHAR, max_length=65535),
    FieldSchema(name="metadata", dtype=DataType.JSON),
]
schema = CollectionSchema(fields, description="知识库集合")

# 创建 Collection
collection = Collection(name="knowledge_base", schema=schema)

# 创建索引
collection.create_index(
    field_name="embedding",
    index_params={
        "metric_type": "COSINE",
        "index_type": "HNSW",
        "params": {"M": 16, "efConstruction": 200}
    }
)

collection.load()  # 加载到内存

# 检索
results = collection.search(
    data=[query_vector],
    anns_field="embedding",
    param={"metric_type": "COSINE", "params": {"ef": 64}},
    limit=10
)
```

**最佳场景**：生产级 RAG 系统、百万到十亿级向量、需要弹性扩缩容的云原生部署。

### Qdrant — 高性能 Rust 实现的向量数据库

**定位**：用 Rust 编写的向量数据库，强调性能、安全性和 API 易用性。

**架构特点**：
- **单二进制部署**：所有功能打包在一个二进制文件中，部署简单
- **存储引擎**：基于 Rust 自研存储，而非依赖第三方存储后端
- **分段式架构**（Segment-based）：数据分片存储，每个 Segment 独立索引
- **gRPC + REST** 双协议支持

**存储架构**：

```
                    Qdrant Segment 内部结构
    ┌─────────────────────────────────────┐
    │            Segment                   │
    │  ┌──────────────────────────────┐   │
    │  │     Vector Storage           │   │
    │  │  ┌────┐┌────┐┌────┐┌────┐  │   │
    │  │  │v1  ││v2  ││v3  ││v4  │  │   │  ← 向量连续存储
    │  │  └────┘└────┘└────┘└────┘  │   │
    │  └──────────────────────────────┘   │
    │  ┌──────────────────────────────┐   │
    │  │     Payload Index            │   │
    │  │  ┌────┐┌────┐┌────┐┌────┐  │   │  ← 标量字段索引
    │  │  │txt ││tag ││cat ││... │  │   │    (倒排/BTree)
    │  │  └────┘└────┘└────┘└────┘  │   │
    │  └──────────────────────────────┘   │
    │  ┌──────────────────────────────┐   │
    │  │     HNSW Graph (索引)        │   │
    │  └──────────────────────────────┘   │
    └─────────────────────────────────────┘
```

**关键特性**：
- **Payload 过滤**：支持复杂的标量字段过滤逻辑（嵌套 JSON、范围筛选、全文过滤），在向量检索前/后混合执行
- **Write-Ahead Log (WAL)**：所有写入先进入预写日志，保证崩溃恢复
- **Scroll API**：支持深度分页的全量数据导出
- **Snapshot 备份**：内建的快照备份/恢复功能

```python
from qdrant_client import QdrantClient
from qdrant_client.http.models import Distance, VectorParams, PointStruct

# 连接到 Qdrant（本地或远程）
client = QdrantClient(
    url="http://localhost:6333",
    api_key="your-api-key"  # 可选
)

# 创建 Collection
client.create_collection(
    collection_name="my_collection",
    vectors_config=VectorParams(
        size=768,
        distance=Distance.COSINE
    )
)

# 写入数据
client.upsert(
    collection_name="my_collection",
    points=[
        PointStruct(
            id=1,
            vector=[0.1] * 768,
            payload={"text": "文档内容", "category": "tech", "timestamp": 1700000000}
        ),
    ]
)

# 带过滤条件的检索
client.search(
    collection_name="my_collection",
    query_vector=[0.1] * 768,
    query_filter=models.Filter(
        must=[
            models.FieldCondition(
                key="category",
                match=models.MatchValue(value="tech")
            ),
            models.FieldCondition(
                key="timestamp",
                range=models.Range(gte=1699000000)
            )
        ]
    ),
    limit=10
)
```

**最佳场景**：对性能敏感的中等规模生产环境、需要复杂过滤条件的检索、偏好单二进制部署的团队。

### Pinecone — 全托管 SaaS 向量数据库

**定位**：Serverless 全托管向量数据库，零运维负担。

**架构特点**：
- **完全托管**：用户无需关心基础设施，只需通过 SDK/REST API 使用
- **Pods 与 Serverless 双模式**：Pods（预留计算）适合稳定负载，Serverless 适合弹性负载
- **自动索引管理**：内部的索引优化完全由服务端自动完成
- **Strict Consistency**：写入即可读，无需等待索引刷新

**优点**：
- 部署最快：注册即可用，无需任何运维
- 自动扩缩容：Serverless 模式按量付费
- 内置性能监控和告警
- 99.95% SLA 保证

**缺点**：
- 成本较高（长期运行成本 > 自建 Milvus/Qdrant）
- 数据必须出站（无法私有化部署）
- 供应商锁定（Schema 和数据迁移困难）
- 中国大陆访问延迟较大

```python
from pinecone import Pinecone

# 初始化（API Key）
pc = Pinecone(api_key="your-api-key")

# 创建 Serverless Index
pc.create_index(
    name="quickstart",
    dimension=768,
    metric="cosine",
    spec=ServerlessSpec(
        cloud="aws",
        region="us-west-2"
    )
)

index = pc.Index("quickstart")

# 写入向量
index.upsert(
    vectors=[
        ("id1", [0.1] * 768, {"text": "文档内容"}),
    ]
)

# 检索
results = index.query(
    vector=[0.1] * 768,
    top_k=10,
    include_metadata=True
)
```

**最佳场景**：初创公司快速上线、无运维团队、弹性不可预测的负载、全球化部署需求。

## 3.2.3 性能对比数据

以下数据基于标准测试环境：100 万条 768 维向量、余弦距离、HNSW 索引（efConstruction=200, M=16, ef=64）、Intel Xeon 2.5GHz 16核、32GB RAM。

| 指标 | ChromaDB | Milvus | Qdrant | Pinecone |
|------|---------|--------|--------|---------|
| **查询 QPS (单机)** | 800-1,200 | 3,000-5,000 | 4,500-7,000 | 2,000-4,000* |
| **P99 延迟 (查询)** | 15-30ms | 5-12ms | 3-8ms | 8-20ms* |
| **写入 QPS (单机)** | 300-500 | 1,500-2,500 | 3,000-5,000 | 1,000-2,000* |
| **写入延迟 (P99)** | 20-50ms | 10-20ms | 5-15ms | 15-30ms* |
| **内存占用 (100万向量)** | ~2 GB | ~3 GB | ~2.4 GB | 由服务端管理 |
| **索引构建时间** | 5-8 min | 8-12 min | 3-5 min | 自动管理 |
| **多租户支持** | 有限 | 完善 | 完善 | 完善 |
| **水平扩展** | 不支持 | 支持 | 支持 | 自动 |
| **高可用** | 不支持 | 支持 | 支持 | 自动 |

> *注：Pinecone 的数据受服务端资源分配影响，实际性能取决于所选 Pod 规格或 Serverless 配置。

**关键解读**：
1. **Qdrant 在单机性能上略占优**：Rust 实现 + 零依赖架构，单机延迟和吞吐量表现最佳
2. **Milvus 在分布式场景优势明显**：架构设计就是对标大规模分布式，多节点线性扩展
3. **ChromaDB 差距显著**：作为嵌入式库，性能上限受限于宿主进程，不适合生产环境
4. **Pinecone 延迟抖动较大**：网络开销和共享资源导致 P99 延迟不如本地部署稳定

## 关键概念速查表

| 概念 | 定义 | 说明 |
|------|------|------|
| 向量数据库 | 专为高维向量存储和检索优化的数据库系统 | 区别于传统数据库 + 向量插件的方案 |
| ChromaDB | 嵌入式轻量向量数据库 | 适合原型开发，生产环境受限 |
| Milvus | 云原生分布式向量数据库 | 大规模生产环境的标杆开源方案 |
| Qdrant | Rust 实现的高性能向量数据库 | 单机性能最优，部署简洁 |
| Pinecone | 全托管 SaaS 向量数据库 | 零运维，成本较高 |
| Payload 过滤 | 基于标量字段的筛选条件 | 对检索结果进行维度过滤 |
| WAL (Write-Ahead Log) | 预写日志，保证写入的持久性和崩溃恢复 | 数据安全的核心机制 |
| Segment | Qdrant 中数据分片的基本单元 | 每个 Segment 可独立索引和查询 |
| 存储与计算分离 | Milvus 将索引存储和查询计算分离在不同节点 | 支持弹性扩缩容的架构模式 |
| Serverless | 按使用量计费、自动扩缩容的部署模式 | 适合负载波动的场景 |
