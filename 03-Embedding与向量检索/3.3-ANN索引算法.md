# 3.3 ANN 索引算法

## 概述

近似最近邻搜索（Approximate Nearest Neighbor, ANN）是向量数据库的核心技术。与精确最近邻搜索（Exact NN，即暴力搜索 $O(n)$ 复杂度）不同，ANN 通过牺牲一定程度的精度换取数量级的检索速度提升。

在高维向量空间中，"维度灾难"（Curse of Dimensionality）使得精确搜索的效率随着维度增加急剧下降。ANN 索引算法通过巧妙的索引结构设计，将搜索复杂度从 $O(n)$ 降低到 $O(\log n)$ 甚至近似 $O(1)$。

```
             精确搜索 vs 近似搜索
             
             ┌───────────────────┐
             │  暴力搜索 (Exact)  │
             │  复杂度: O(n)      │
             │  精度: 100%       │
             │  100万向量 ≈ 30ms │
             └───────────────────┘
                        │
               ┌────────▼────────┐
               │  ANN 索引       │
               │  复杂度: O(log n)│
               │  精度: 95-99%   │
               │  100万向量 ≈ 2ms│
               └─────────────────┘
```

本章深入分析三种最具代表性的 ANN 索引算法：**HNSW**（层级可导航小世界图）、**IVF**（倒排文件索引）和 **DiskANN**（基于 SSD 的大规模 ANN 索引），重点讨论它们在精度（Recall）、检索速度（QPS）和内存占用之间的三角权衡关系。

---

## 3.3.1 三角权衡：精度、速度、内存

所有 ANN 索引算法都面临着经典的三元制约关系：

```
                    ● 精度 (Recall)
                   / \
                  /   \
                 /     \
                /       \
               /         \
              /           \
             /             \
   速度 (QPS) ●─────────────● 内存 (RAM)
```

- **HNSW**：偏向速度优先，内存占用最高
- **IVF**：平衡方案，各项指标中规中矩
- **DiskANN**：偏向低内存占用，速度略低于 HNSW

| 维度 | HNSW | IVF | DiskANN |
|------|------|-----|---------|
| 检索速度 (Recall@95%) | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐⭐ |
| 构建速度 | ⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐ |
| 内存占用 | ⭐⭐ (最高) | ⭐⭐⭐⭐ (可量化压缩) | ⭐⭐⭐⭐⭐ (最低) |
| 支持删除 | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐ |
| 扩展性 (十亿级) | ⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ |

## 3.3.2 HNSW — 层级可导航小世界图

### 背景

HNSW（Hierarchical Navigable Small World）由 Yury Malkov 在 2016 年提出，是目前工业界最广泛使用的高性能 ANN 算法。几乎所有主流向量数据库（Milvus、Qdrant、Pinecone、ChromaDB 等）都将 HNSW 作为默认或首选索引。

### 核心原理

HNSW 构建的是一个**多层级图结构**，灵感来源于跳表（Skip List）和小世界网络（Small World Network）：

- **底层（Layer 0）**：包含所有数据点，每个节点连接到其最近的若干邻居
- **上层（Layer 1, 2, ...）**：每层包含下层的一部分节点（概率采样），节点越少层数越高
- **导航过程**：从最高层开始"粗定位"，逐层下降到最底层进行"精确搜索"

```
                    HNSW 层级图结构示意
    
    顶层 (Layer 2)     prob=1/L^2
    ┌─────────────────────────────────────┐
    │         ● ←---→ ●                    │
    │                          ●           │
    └─────────┬───────────┬────────────────┘
              │           │
    中层 (Layer 1)       │  prob=1/L
    ┌──────────┴────┬────┴─────────────────┐
    │  ● ←---→ ● ←─┴─→ ● ←---→ ●          │
    │         │              │              │
    │    ● ←──┴──→ ●         │              │
    └──────────┬─────────────┴──────────────┘
              │              │
    底层 (Layer 0)  prob=1 (所有节点)
    ┌──────────┴──────────────┴──────────────┐
    │  ● ←---→ ● ←---→ ● ←---→ ● ←---→ ●    │
    │  │       │       │       │       │     │
    │  │   ● ←─┴─→ ● ←─┴─→ ●   │   ●   │     │
    │  │   │       │       │   │   │   │     │
    │  ● ←─┴───→ ● ←───→ ● ←─┴─→ ● ←─┴─→ ●  │
    │  │       │       │       │       │     │
    │  ● ←---→ ● ←---→ ● ←---→ ● ←---→ ●    │
    └────────────────────────────────────────┘
    
    █ 入口点 (Entry Point) — 搜索从此开始
    ● 数据节点
    ─ 边 (连接)
```

### 搜索过程详解

假设我们在上图的 HNSW 结构中搜索一个 query 的最远近邻：

```
搜索路径示例:
Step 1: 从顶层入口点开始
    Layer 2: 入口点 → 候选A (距离更近)
    
Step 2: 贪婪下降到下一层
    Layer 1: 候选A → 候选B → 候选C (在当前层找到了局部最优)
    
Step 3: 下降到最底层，精细搜索
    Layer 0: 候选C → 候选D → 结果E (逐跳逼近最终结果)
    
在整个过程中，维护一个动态的候选队列（efSearch 参数控制队列大小），
每次选择队列中最近的节点进行扩展访问。
```

关键参数：

| 参数 | 默认值 | 作用 | 对性能的影响 |
|------|--------|------|------------|
| **M** | 16 | 每个节点的最大连接数 | M↑ 精度↑ 内存↑ 速度↓ |
| **efConstruction** | 200 | 构建时的动态候选列表大小 | ef↑ 精度↑ 构建时间↑ |
| **efSearch** | 64 | 搜索时的动态候选列表大小 | ef↑ 精度↑ 延迟↑ |
| **Mmax** | M | 上层节点的最大连接数 | 通常等于 M |
| **mL** | 1/ln(M) | 层数归一化因子 | 控制层级概率分布 |

### 参数调优指南

```python
# Milvus 中的 HNSW 参数配置
index_params = {
    "index_type": "HNSW",
    "metric_type": "COSINE",
    "params": {
        "M": 16,                # 基础: 8-64，越大精度越高但内存越大
        "efConstruction": 200   # 构建质量: 100-500，越大构建越慢但精度越高
    }
}

# 搜索时的 ef 参数
search_params = {
    "metric_type": "COSINE",
    "params": {
        "ef": 64  # 搜索宽度: 64-256，越大搜索越慢但召回率越高
    }
}
```

**参数调整经验法则**：

```
精度要求 95%+      → M=32, efConstruction=400, ef=128
精度要求 90-95%    → M=16, efConstruction=200, ef=64
低延迟要求 (<5ms)  → M=8,  efConstruction=100, ef=32
内存受限           → M=8-12 (M 对内存影响最大)
```

### 内存占用分析

HNSW 内存占用公式：
$$\text{Memory} \approx N \times (M \times 2 + 1) \times d \times 4 \text{ bytes}$$

其中 N 为向量数，d 为维度，M 为连接数（因子 2 因为需要存双向边）。

例如：100 万向量、768 维、M=16：
$$\approx 1,000,000 \times (16 \times 2 + 1) \times 768 \times 4 \approx 101 \text{ GB}$$

这还只是索引的内存，不包括向量本身，这就是为什么 HNSW 在大规模场景下内存消耗极高。

**优化方案**：
1. **PQ (Product Quantization，乘积量化)**：对向量进行压缩编码，将 768 维 float32 向量压缩到 32-64 字节
2. **降维**：使用 PCA 等降维后再建索引
3. **分片**：多机分摊内存

```python
# 使用 FAISS 的 HNSW + PQ 示例
import faiss

dim = 768
nlist = 100  # 聚类中心数

# 原始 HNSW
index_hnsw = faiss.IndexHNSWFlat(dim, 32)
index_hnsw.hnsw.efConstruction = 200

# HNSW + PQ (量化压缩，内存降低 80%)
pq_code_size = 64  # 每个向量用 64 字节表示
index_hnsw_pq = faiss.IndexHNSWPQ(dim, 32, pq_code_size)

# 训练和添加
index_hnsw_pq.train(xb)
index_hnsw_pq.add(xb)

# 搜索
D, I = index_hnsw_pq.search(xq, k=10)
```

## 3.3.3 IVF — 倒排文件索引

### 核心原理

IVF（Inverted File Index，倒排文件索引）的核心思想是**聚类 + 倒排**。它与文本检索中的倒排索引（Inverted Index）有相似的思路，只不过文本检索以"词"为单位，而 IVF 以"向量聚类中心"为单位。

```
                    IVF 索引结构
    
    ┌─────────────────────────────────────┐
    │          K-Means 聚类               │
    │                                      │
    │  ● ← 聚类中心 1 (Voronoi Cell)      │
    │  │  ● ● ●  ●                        │
    │  │  ●   ●   ●  ← 属于此聚类的向量   │
    │  │    ●     ●                        │
    │  │      ●                            │
    ├─────────────────────────────────────┤
    │  ● ← 聚类中心 2                      │
    │  │  ● ●    ●                         │
    │  │  ●   ●    ●                       │
    ├─────────────────────────────────────┤
    │  ...                                 │
    │                                      │
    │  ● ← 聚类中心 nlist                  │
    │     ●    ●                           │
    │     ● ●                              │
    └─────────────────────────────────────┘
    
    搜索时：
    Step 1: 计算 query 到 nlist 个聚类中心的距离
    Step 2: 选择最近的 nprobe 个聚类
    Step 3: 只在这些聚类的倒排列表中进行搜索
```

### 参数详解

| 参数 | 说明 | 典型值 | 影响 |
|------|------|--------|------|
| **nlist** | 聚类中心的数量 | 100-4096 | nlist↑ 精度↑ 建索引时间↑ |
| **nprobe** | 搜索时访问的聚类数量 | 1-100 | nprobe↑ 精度↑ 延迟↑ |
| **量化方式** | 向量压缩方法 | FLAT/SQ8/PQ | 影响精度和内存 |

### IVF 变体对比

| 变体 | 压缩方式 | 每个向量大小 | 精度损失 | 适用场景 |
|------|---------|-------------|---------|---------|
| IVF_FLAT | 无压缩 | 4×d bytes | 无 | 高精度需求，内存充足 |
| IVF_SQ8 | 标量量化 | 1×d bytes | 1-2% | 内存中等，768维节省75% |
| IVF_PQ | 乘积量化 | 8-64 bytes | 2-5% | 极致内存压缩，大规模场景 |

```python
# FAISS IVF 参数配置示例
import faiss

dim = 768
nlist = 4096  # 4096 个聚类中心

# IVF_FLAT (无压缩)
index_flat = faiss.IndexIVFFlat(
    faiss.IndexFlatL2(dim),  # 量化器
    dim,
    nlist
)

# IVF_SQ8 (标量量化，内存降至1/4)
index_sq8 = faiss.IndexIVFScalarQuantizer(
    faiss.IndexFlatL2(dim),
    dim,
    nlist,
    faiss.ScalarQuantizer.QT_8bit
)

# IVF_PQ (乘积量化，极致压缩)
index_pq = faiss.IndexIVFPQ(
    faiss.IndexFlatL2(dim),
    dim,
    nlist,
    m=64,          # 子空间数量
    nbits=8        # 每个子空间的比特数
)

# 训练和添加
index.train(xb)
index.add(xb)

# 设置 nprobe
index.nprobe = 10  # 搜索时访问 10 个最近聚类
```

### IVF 与 HNSW 的选择

| 对比维度 | IVF-FLAT | HNSW |
|---------|---------|------|
| 建索引速度 | 快 (O(kN)) | 慢 (O(N log N)) |
| 搜索速度 (小规模) | 中等 | 快速 |
| 搜索速度 (大规模) | 快速 (nlist 可调) | 快速但有上限 |
| 内存占用 | 低 (~向量大小) | 高 (额外边信息) |
| 支持删除 | 容易 (直接删除倒排条目) | 困难 (图结构复杂) |
| 实时插入 | 容易 | 困难 (需要动态重连) |

## 3.3.4 DiskANN — 基于 SSD 的大规模 ANN

### 问题背景

当数据规模达到十亿级时，HNSW 的内存需求变得不可接受。例如：10 亿个 768 维向量的 HNSW 索引需要约 100 TB 内存——即使是最昂贵的服务器也无法满足。

DiskANN（Microsoft 2021）的核心理念是：**将图索引存储在 SSD 上，利用 SSD 的随机读取性能和大容量，在成本可控的前提下实现十亿级 ANN 搜索**。

### 核心架构

```
                    DiskANN 三层架构
    
    ┌────────────────────────────────────────┐
    │          内存驻留 (RAM)                 │
    │  ┌──────────────────────────────────┐  │
    │  │  粗粒度量化码本 (PQ Codebook)     │  │
    │  │  用于 Vamana 图剪枝的重排序        │  │
    │  └──────────────────────────────────┘  │
    │  ┌──────────────────────────────────┐  │
    │  │  BFS 搜索状态缓存                │  │
    │  └──────────────────────────────────┘  │
    ├────────────────────────────────────────┤
    │          SSD 存储                       │
    │  ┌──────────────────────────────────┐  │
    │  │  Vamana 图结构                   │  │
    │  │  ● → ● → ●                      │  │
    │  │  ↓   ↓   ↓                       │  │
    │  │  ● → ● → ●                      │  │
    │  └──────────────────────────────────┘  │
    │  ┌──────────────────────────────────┐  │
    │  │  完整向量数据 (float32)          │  │
    │  │  [v1][v2][v3]...[vN]             │  │
    │  └──────────────────────────────────┘  │
    └────────────────────────────────────────┘
    
    搜索流程:
    1. 使用内存中的 PQ 码本计算查询与节点距离
    2. 在 Vamana 图上进行 BFS 搜索
    3. 从 SSD 读取候选节点的完整向量做精确距离计算
    4. 返回 top-k 结果
```

### Vamana 图算法

DiskANN 引入了一种新的图结构——**Vamana**，它在有向图的基础上做了两点关键优化：

1. **度数控制**：每个节点的出度限制为参数 $R$（典型值 64），入度不限制
2. **剪枝策略**：在插入新节点时，只保留那些不能通过其他路径到达的邻居，避免冗余连接

```
            Vamana 剪枝示意 (度限制 R=3)
    
    剪枝前 (冗余连接多)        剪枝后 (保留必需连接)
    ┌──────────────┐         ┌──────────────┐
    │    ● ←→ ●    │         │    ●──→●    │
    │   ↕↕   ↕↕   │         │         ↕    │
    │    ● ←→ ●    │         │    ●──→●    │
    │   ↕ ↕ ↕ ↕   │         │              │
    │   ●──→●──→● │         │   ●──→●──→●  │
    └──────────────┘         └──────────────┘
    
    剪枝后的图显著减少了边数：
    - 内存占用 ↓ 80-90%
    - SSD 读取量 ↓ (每次搜索只需读取更少的节点)
    - 精度略微下降 (<1%)
```

### 性能特征

| 指标 | DiskANN | HNSW (内存) | IVF (内存) |
|------|---------|-------------|-----------|
| 1亿向量精度@10 | 0.96 | 0.98 | 0.95 |
| 延迟 (1亿向量) | 3-8ms | 1-3ms | 5-15ms |
| 内存占用 (1亿, 768维) | ~2 GB (PQ码本) | ~120 GB | ~30 GB (SQ8) |
| 单机容量上限 | 10亿+ | 1-2千万 | 1千万-1亿 |
| 建索引时间 (1亿) | 3-5小时 | 2-3小时 | 0.5-1小时 |

## 3.3.5 三种算法的综合对比

### 完整对比矩阵

| 维度 | HNSW | IVF | DiskANN |
|------|------|-----|---------|
| **核心数据结构** | 多层可导航图 | 倒排列表 + 聚类 | Vamana 有向图 |
| **搜索复杂度** | O(log N) | O(nlist + nprobe * N/nlist) | O(log N) + SSD I/O |
| **精度 (Recall@10)** | 0.95-0.99 | 0.90-0.98 | 0.93-0.97 |
| **建索引速度** | 慢 | 快 | 慢-中 |
| **实时插入** | 困难 | 容易 | 困难 |
| **批量删除** | 困难 | 容易 | 困难 |
| **内存效率** | 最低 | 中 (可压缩) | 最高 |
| **SSD 利用** | 不支持 | 有限 (mmap) | 原生支持 |
| **主要维护者** | FAISS, 社区 | FAISS | Microsoft |
| **库/框架** | FAISS, hnswlib | FAISS | DiskANN C++ |

## 关键概念速查表

| 概念 | 定义 | 说明 |
|------|------|------|
| ANN (Approximate Nearest Neighbor) | 近似最近邻搜索，牺牲少量精度换取大幅速度提升 | 高维向量检索的默认方案 |
| 维度灾难 (Curse of Dimensionality) | 高维空间中，距离度量失效，所有点几乎等距 | ANN 算法要解决的核心问题 |
| HNSW | 层级可导航小世界图，多层级图结构实现 O(log N) 搜索 | 当前最流行的 ANN 算法 |
| IVF | 倒排文件索引，通过 K-Means 聚类缩小搜索范围 | 经典平衡方案 |
| DiskANN | 基于 SSD 存储的大规模 ANN 索引，使用 Vamana 图 | 十亿级向量的首选方案 |
| efConstruction | HNSW 构建时的候选队列大小参数 | 控制索引质量与构建时间 |
| efSearch | HNSW 搜索时的候选队列大小参数 | 控制召回率与延迟 |
| nlist | IVF 的聚类中心数量 | 控制搜索粒度 |
| nprobe | IVF 搜索时访问的聚类数量 | 控制精度-速度权衡 |
| PQ (Product Quantization) | 乘积量化，将高维向量压缩为短编码 | 大幅降低内存占用 |
| SQ8 (Scalar Quantization) | 标量量化，将 float32 压缩为 int8 | 简单高效的压缩方法 |
| Vamana | DiskANN 使用的有向图结构，带度数限制和剪枝 | 专为 SSD 存储设计的图算法 |
