# 3.5 检索-重排序流水线

## 概述

一个完整的检索系统远不止"查向量数据库、取 top-k"这么简单。在实际 RAG 应用中，单纯的向量检索（Bi-Encoder 检索）通常只能达到 60-75% 的 Hit Rate——剩余的 25-40% 的相关文档被排在靠后的位置或直接被遗漏。

**检索-重排序流水线**（Retrieve-and-Rerank Pipeline）通过引入第二阶段的重排序（Reranking）步骤，使用更精确但更慢的 Cross-Encoder 模型对检索结果进行精细化排序，能将 Hit Rate 从 70% 提升到 95% 以上。

```
    传统检索 (单阶段)
    ┌──────────┐    ┌──────────┐    ┌──────────┐
    │ Query    │───→│ Bi-Encoder│───→│ Top-k    │───→ LLM
    │          │    │ 检索      │    │ 结果     │
    └──────────┘    └──────────┘    └──────────┘
                     Hit Rate: 60-75%
    
    检索-重排序 (两阶段)
    ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
    │ Query    │───→│ Bi-Encoder│───→│ 候选池   │───→│Cross-En- │───→ LLM
    │          │    │ 粗筛      │    │ top-100  │    │coder 精排│
    └──────────┘    └──────────┘    └──────────┘    └──────────┘
                     Hit Rate: 92-98%
```

---

## 3.5.1 为什么需要两阶段检索？

### 单一 Bi-Encoder 的局限性

Bi-Encoder（双编码器）是向量检索中使用的 Embedding 模型，它将 query 和 document 独立编码为向量，通过余弦相似度评分。这种架构为了效率做出了妥协：

- **信息瓶颈**：整篇文档的信息被压缩进一个固定长度的向量（如 768 维），必然会丢失细粒度信息
- **交互缺失**：Query 和 Document 在编码阶段没有任何交互，缺乏对 query 中关键词语的关注
- **精确匹配弱**：对于专有名词、数字等需要精确匹配的信号，稠密向量不如稀疏方法（如 BM25）有效

```
    Bi-Encoder 编码过程（无交互）
    
    Query: "2024年诺贝尔物理学奖得主是谁？"
    ┌────────────────────┐      ┌──────────────────┐
    │ "2024年诺贝尔"     │      │  [0.21, 0.87,    │
    │ "物理学奖得主"     │      │   0.45, 0.12,    │
    │ "是谁？"           │      │   0.91, ...]     │
    └────────┬───────────┘      └──────────────────┘
             │ 独立编码                          ▲
             ▼                                   │
    ┌────────────────────┐      ┌──────────────────┘
    │ "2024 Nobel Prize  │      │   
    │ in Physics was..." │      │ 独立编码
    └────────────────────┘      └──────────────────
    
    ⚠ Query 和 Document 在编码过程中完全独立，
       无法针对性地关注 query 中"2024年"这个关键限定词
```

### Cross-Encoder 的解决方案

Cross-Encoder（交叉编码器）将 query 和 document **拼接**后作为一个序列输入到同一个 Transformer 中，让模型可以自由地让 query 中的每个 token 与 document 中的所有 token 进行注意力交互。

```
    Cross-Encoder 编码过程（完全交互）
    
    Query: "2024年诺贝尔物理学奖得主是谁？"
    Document: "2024 Nobel Prize in Physics was awarded..."
    
    ┌─────────────────────────────────────────────┐
    │ [CLS] 2024 年 诺 贝 尔 物 理 学 奖 ...     │
    │        │  │  │  │  │  │  │  │  │           │
    │        ▼  ▼  ▼  ▼  ▼  ▼  ▼  ▼  ▼           │
    │    ┌────────────────────────────────┐       │
    │    │      Multi-Head Self-Attention  │       │
    │    │    (Query × Document 全交互)    │       │
    │    └────────────────────────────────┘       │
    │           │  │  │  │  │  │  │  │            │
    │           ▼  ▼  ▼  ▼  ▼  ▼  ▼  ▼           │
    │ [CLS] 2024 年 诺 贝 尔 物 理 学 奖 ...     │
    └─────────────────────────────────────────────┘
                      │
                      ▼
                 ┌──────────┐
                 │ 相关性分  │ ← 0.0 - 1.0 的匹配分数
                 │ 数 (0.97) │
                 └──────────┘
    
    ✓ Query 中的"2024年"直接与 Document 中的"2024"交互
    ✓ "诺贝尔物理学奖"与 "Nobel Prize in Physics" 深层对齐
    ✓ 最终输出一个精确的相关性评分
```

## 3.5.2 Cross-Encoder Reranker 详解

### 模型架构对比

| 特性 | Bi-Encoder (检索) | Cross-Encoder (重排序) |
|------|------------------|----------------------|
| 编码方式 | Query 和 Document 独立编码 | Query + Document 拼接后联合编码 |
| 输出 | 固定维度向量 (768/1024d) | 单一相关性分数 (0-1) |
| 交互程度 | 零交互 | 全注意力交互 |
| 时间复杂度 | O(N) 线性 | O(N) 线性（但系数大得多） |
| 处理速度 | 快 (1000条/秒) | 慢 (50-200条/秒) |
| 精度 | 中等 (Recall@10: 70-80%) | 高 (Recall@10: 92-98%) |
| 适用阶段 | 第一阶段粗筛 | 第二阶段精排 |

### 主流 Cross-Encoder 模型

| 模型 | 参数量 | 速度 (条/秒)* | 精度 (MRR@10) | 语言 | 推荐场景 |
|------|--------|-------------|--------------|------|---------|
| BAAI/bge-reranker-base | 102M | ~200 | 0.92 | 多语言 | 通用场景首选 |
| BAAI/bge-reranker-large | 326M | ~80 | 0.95 | 多语言 | 高精度要求 |
| cross-encoder/ms-marco-MiniLM-L-6-v2 | 22M | ~500 | 0.85 | 英文 | 轻量快速 |
| cross-encoder/ms-marco-MiniLM-L-12-v2 | 33M | ~300 | 0.88 | 英文 | 平衡方案 |
| BAAI/bge-reranker-v2-minicpm-layerwise | 2.7B | ~30 | 0.97 | 多语言 | 顶级精度 |

> *速度测试条件：单张 T4 GPU, batch_size=32, 输入长度 256 tokens

```python
from sentence_transformers import CrossEncoder

# 加载 Cross-Encoder 模型
reranker = CrossEncoder("BAAI/bge-reranker-base", max_length=512)

# Query 和候选文档
query = "Transformer 架构中自注意力机制的计算复杂度是多少？"
candidates = [
    "自注意力机制的计算复杂度是 O(n²·d)，其中 n 是序列长度。",
    "Transformer 由编码器和解码器组成。",
    "注意力机制允许模型关注输入序列的不同位置。",
    "计算复杂度是衡量算法效率的重要指标。",
    "自注意力的计算复杂度 O(n²·d) 在长序列场景下成为瓶颈。"
]

# 构造 Cross-Encoder 输入对
pairs = [(query, doc) for doc in candidates]

# 评分
scores = reranker.predict(pairs)

# 按分数排序
ranked = sorted(zip(candidates, scores), key=lambda x: x[1], reverse=True)

print("重排序结果:")
for i, (doc, score) in enumerate(ranked):
    print(f"  {i+1}. [{score:.4f}] {doc}")

# 输出:
#   1. [0.9712] 自注意力机制的计算复杂度是 O(n²·d)...
#   2. [0.9345] 自注意力的计算复杂度 O(n²·d) 在...
#   3. [0.2314] 注意力机制允许模型关注输入序列...
#   4. [0.1201] Transformer 由编码器和解码器组成
#   5. [0.0893] 计算复杂度是衡量算法效率的重要指标
```

## 3.5.3 完整检索-重排序流水线实现

### 流水线架构

```
    完整的两阶段检索流水线
    
    ┌─────────────┐
    │   User Query │
    └──────┬──────┘
           │
           ▼
    ┌──────────────────────────────────────────────────┐
    │  第一阶段: 多路召回 (候选生成)                    │
    │                                                   │
    │  ┌────────────┐  ┌────────────┐  ┌────────────┐  │
    │  │ 稠密检索    │  │ 稀疏检索   │  │ Hybrid     │  │
    │  │ (Bi-Encoder)│  │ (BM25)    │  │ 加权融合   │  │
    │  │ top-100    │  │ top-50    │  │ top-100    │  │
    │  └────────────┘  └────────────┘  └────────────┘  │
    │                      │                            │
    │                 Union 去重                         │
    │                 候选池: ~150 条                     │
    └──────────────────────┬───────────────────────────┘
                           │
                           ▼
    ┌──────────────────────────────────────────────────┐
    │  第二阶段: Cross-Encoder 重排序                   │
    │                                                   │
    │  候选池: 150 条 → Cross-Encoder 评分 → 排序       │
    │                                                   │
    │  ┌────────────────────┐                           │
    │  │ 排序后取 top-10    │ → 最终检索结果           │
    │  └────────────────────┘                           │
    └──────────────────────────────────────────────────┘
                           │
                           ▼
                    ┌──────────────┐
                    │ LLM 生成回答 │
                    └──────────────┘
```

### 完整代码实现

```python
import numpy as np
from typing import List, Tuple
from sentence_transformers import SentenceTransformer, CrossEncoder
from rank_bm25 import BM25Okapi

class TwoStageRetriever:
    """
    检索-重排序流水线
    """
    def __init__(
        self,
        embed_model_name: str = "BAAI/bge-base-zh-v1.5",
        reranker_model_name: str = "BAAI/bge-reranker-base",
        device: str = "cpu"
    ):
        self.bi_encoder = SentenceTransformer(embed_model_name, device=device)
        self.reranker = CrossEncoder(reranker_model_name, max_length=512, device=device)
        self.documents = []
        self.doc_embeddings = None
        self.bm25 = None
        self.tokenized_docs = []
        
    def index(self, documents: List[str]):
        """
        索引文档：同时构建稠密向量索引和 BM25 稀疏索引
        """
        self.documents = documents
        
        # 稠密向量索引
        print("构建稠密向量索引...")
        self.doc_embeddings = self.bi_encoder.encode(
            documents, 
            normalize_embeddings=True,
            batch_size=64,
            show_progress_bar=True
        )
        
        # BM25 稀疏索引
        print("构建 BM25 索引...")
        self.tokenized_docs = [doc.split() for doc in documents]  # 中文需使用分词器
        self.bm25 = BM25Okapi(self.tokenized_docs)
        
    def retrieve(
        self,
        query: str,
        top_k: int = 10,
        candidates: int = 150,
        alpha: float = 0.5
    ) -> List[Tuple[str, float]]:
        """
        两阶段检索
        
        Args:
            query: 查询字符串
            top_k: 最终返回结果数
            candidates: 重排序阶段的候选池大小
            alpha: 稠密/稀疏检索的融合权重 (0=纯BM25, 1=纯稠密)
        """
        # ===== 第一阶段: 多路召回 =====
        
        # 稠密检索
        q_emb = self.bi_encoder.encode(query, normalize_embeddings=True)
        dense_scores = np.dot(self.doc_embeddings, q_emb)
        
        # 稀疏检索 (BM25)
        tokenized_query = query.split()
        bm25_scores = self.bm25.get_scores(tokenized_query)
        
        # 归一化
        dense_scores = (dense_scores - dense_scores.mean()) / dense_scores.std()
        bm25_scores = (bm25_scores - bm25_scores.mean()) / bm25_scores.std()
        
        # 融合评分
        hybrid_scores = alpha * dense_scores + (1 - alpha) * bm25_scores
        
        # 取 top-candidates
        candidate_indices = np.argsort(hybrid_scores)[-candidates:][::-1]
        
        # ===== 第二阶段: Cross-Encoder 重排序 =====
        
        # 构造 (query, doc) 对
        candidate_docs = [self.documents[i] for i in candidate_indices]
        pairs = [(query, doc) for doc in candidate_docs]
        
        # Cross-Encoder 评分
        rerank_scores = self.reranker.predict(pairs)
        
        # 按重排序分数排序，取 top-k
        final_indices = np.argsort(rerank_scores)[-top_k:][::-1]
        
        results = [
            (self.documents[candidate_indices[i]], rerank_scores[i])
            for i in final_indices
        ]
        
        return results


# 使用示例
retriever = TwoStageRetriever()
retriever.index([
    "Python 是一种高级编程语言...",
    "向量数据库用于存储和检索 Embedding...",
    # ... 更多文档
])

results = retriever.retrieve(
    query="向量数据库的选型建议", 
    top_k=10,
    alpha=0.7  # 稠密检索权重 0.7, BM25 权重 0.3
)
```

## 3.5.5 工程优化与注意事项

### 批量评分

Cross-Encoder 的 GPU 利用率在单个样本评分时极低。使用批量评分可以充分利用 GPU 并行能力：

```python
# ❌ 逐个评分 (慢)
scores = [reranker.predict([(query, doc)])[0] for doc in candidates]

# ✅ 批量评分 (快 5-10x)
pairs = [(query, doc) for doc in candidates]
scores = reranker.predict(pairs, batch_size=64)
```

### 结果缓存

对于频繁出现的相同或相似 query，可以缓存 Cross-Encoder 的评分结果：

```python
from functools import lru_cache
import hashlib

class CachedReranker:
    def __init__(self, model_name="BAAI/bge-reranker-base"):
        self.model = CrossEncoder(model_name)
    
    @lru_cache(maxsize=10000)
    def _score_pair(self, query_hash: str, doc_hash: str):
        """
        缓存(query, doc)对的评分结果
        实际使用时需要存储原始字符串
        """
        pass
    
    def score(self, query: str, documents: List[str]) -> List[float]:
        """带缓存的批量评分"""
        uncached_pairs = []
        uncached_indices = []
        
        for i, doc in enumerate(documents):
            key = (query, doc)
            if key not in self.cache:
                uncached_pairs.append(key)
                uncached_indices.append(i)
        
        if uncached_pairs:
            scores = self.model.predict(uncached_pairs)
            for idx, score in zip(uncached_indices, scores):
                self.cache[(query, documents[idx])] = score
        
        return [self.cache[(query, doc)] for doc in documents]
```

### 延迟预算分配

在端到端 RAG 系统中，检索阶段的延迟预算通常为 **100-300ms**：

```
    检索延迟预算分配 (目标: 200ms)
    
    ┌─────────────────────────────────────────┐
    │  第一阶段: 检索 (~20%)                   │
    │  ├─ Bi-Encoder 编码 Query: 2-5ms        │
    │  ├─ ANN 索引搜索: 3-8ms                 │
    │  └─ BM25 搜索: 1-3ms                   │
    │                     总计: 6-16ms        │
    ├─────────────────────────────────────────┤
    │  第二阶段: 重排序 (~80%)                 │
    │  ├─ 构造 150 个 (query, doc) 对: 1-2ms  │
    │  ├─ Cross-Encoder 批量推理: 20-40ms     │
    │  └─ 排序和过滤: 1-2ms                   │
    │                     总计: 22-44ms        │
    ├─────────────────────────────────────────┤
    │  其他开销 (~20%)                         │
    │  ├─ 网络传输: 5-20ms                    │
    │  ├─ 结果后处理: 2-5ms                   │
    │  └─ 上下文组装: 1-3ms                   │
    │                     总计: 8-28ms        │
    ├─────────────────────────────────────────┤
    │  总预计延迟: 36-88ms ✓                  │
    └─────────────────────────────────────────┘
```

### 常见问题

**Q: 什么时候可以跳过重排序？**
A: 当满足以下任一条件时可以考虑跳过：
- 文档库 < 1 万条，且 Bi-Encoder 检索已经足够准确
- 延迟要求 < 50ms 且不能使用 GPU
- query 简单（如短关键词检索而非语义查询）

**Q: Cross-Encoder 的输入长度限制怎么办？**
A: 通常将 document 截断为 512 tokens。对于超长 document，建议：
1. 将其进一步拆分为多个段（见 3.4 分块策略）
2. 对每个段分别评分，取最高分作为该 document 的评分

**Q: 如何评估重排序的收益？**
A: 核心指标是 **R-Precision（R 精度）** 和 **MRR（Mean Reciprocal Rank，平均倒数排名）**。一个简单的 A/B 测试方法：记录同一 query 在重排序前后 top-10 结果的重叠率和排名变化。

## 3.5.6 进阶：多阶段分层重排序

在超大规模场景下，可以采用多阶段重排序来进一步优化效率：

```
                   多阶段分层重排序
    
    ┌──────────────┐
    │ 原始候选池:   │  ~10,000 条
    │ FAISS 检索    │
    └──────┬───────┘
           │
           ▼
    ┌──────────────┐
    │ 第一阶段:    │  ~1,000 条
    │ 轻量 Reranker│  MiniLM-L2 (22M params)
    │              │  延迟: ~5ms
    └──────┬───────┘
           │
           ▼
    ┌──────────────┐
    │ 第二阶段:    │  ~150 条
    │ 中型 Reranker│  bge-reranker-base (102M)
    │              │  延迟: ~20ms
    └──────┬───────┘
           │
           ▼
    ┌──────────────┐
    │ 第三阶段:    │  ~10 条 (最终结果)
    │ 大型 Reranker│  bge-reranker-large (326M)
    │              │  延迟: ~30ms
    └──────────────┘
    
    总延迟: ~55ms (vs 单阶段大型 Reranker 直接处理 150 条: ~50ms)
    精度: 相同
    优势: 候选池从 10,000 到最终 10 条，全程可控
```

## 关键概念速查表

| 概念 | 定义 | 说明 |
|------|------|------|
| 检索-重排序流水线 | 两阶段检索架构：先快速粗筛，再精确重排序 | 提升检索精度的标准做法 |
| Bi-Encoder | Query 和 Document 独立编码的双塔模型 | 第一阶段检索，高效但精度有限 |
| Cross-Encoder | Query 和 Document 拼接后联合编码的交互模型 | 第二阶段重排序，高精度但速度慢 |
| Hit Rate | 检索结果中包含相关文档的比例 | 衡量检索系统召回能力的基本指标 |
| MRR (Mean Reciprocal Rank) | 第一个相关文档的排名倒数的平均值 | 衡量排序质量的指标 |
| Reranker (重排序器) | 对粗筛结果进行精细化排序的模型 | 流水线的第二阶段核心 |
| 多路召回 | 同时使用多种检索策略（稠密+稀疏+其他） | 提升召回覆盖率的有效手段 |
| 候选池 (Candidate Pool) | 送入重排序阶段的文档集合大小 | 典型值 100-200，过大无意义 |
| BM25 | 基于词频-逆文档频率的经典稀疏检索算法 | 与稠密检索互补的有效方案 |
| 混合检索 (Hybrid Search) | 融合稠密检索和稀疏检索结果的策略 | 兼顾语义匹配和关键词匹配 |
