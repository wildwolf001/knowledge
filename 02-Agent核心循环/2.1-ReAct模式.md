# 2.1 ReAct 模式

## 论文来源

- **ReAct: Synergizing Reasoning and Acting in Language Models** -- Shunyu Yao, Jeffrey Zhao, Dian Yu, Nan Du, Izhak Shafran, Karthik Narasimhan, Yuan Cao (2022)
  - arXiv: [2210.03629](https://arxiv.org/abs/2210.03629)
  - 发表于 NeurIPS 2023

## 核心思想

ReAct 的核心洞察是：**推理（Reasoning）与行动（Acting）应当交织进行，而非分离**。传统的思维链（Chain-of-Thought, CoT）只生成推理轨迹但不与环境交互；传统的"纯行动"Agent 直接调用工具但缺乏推理过程。ReAct 将两者结合，形成一个紧密耦合的循环。

### 核心循环

```
Thought  →  Action  →  Observation  →  Thought  →  Action  →  Observation  →  ...  →  Final Answer
```

每一轮迭代包含三个步骤：

1. **Thought（思考）**：模型用自然语言描述当前状态、分析已有信息、决定下一步做什么。这个推理轨迹不对外产生副作用，仅用于引导模型自身的后续决策。
2. **Action（行动）**：模型输出一个具体的工具调用指令，通常格式化为结构化命令（如 JSON 函数调用或特定领域语言）。
3. **Observation（观察）**：工具执行结果被反馈回模型，作为下一轮思考的输入。

### 与 CoT 和 Action-only 的对比

| 维度 | Chain-of-Thought | Action-only | ReAct |
|------|-------------------|-------------|-------|
| 推理可见 | 有完整推理链 | 无推理 | 有推理链 |
| 环境交互 | 无 | 有 | 有 |
| 可解释性 | 高 | 低 | 高 |
| 纠错能力 | 无（无法验证） | 弱（盲目行动） | 强（观察后调整） |
| Token消耗 | 中 | 低 | 高 |

Yao et al. 在 HotpotQA 和 Fever 等知识密集型 QA 任务上的实验显示，ReAct 在幻觉率上显著低于纯 CoT（因为观察结果可以纠正错误推理），在成功率上显著高于纯 Action-only（因为推理轨迹帮助模型理解上下文）。

## 具体示例：Wikipedia 问答

以下是一个 Agent 使用 ReAct 循环回答"哪个城市的面积更大：东京还是悉尼？"的完整轨迹：

```
用户: 哪个城市的面积更大：东京还是悉尼？

Thought 1: 我需要比较东京和悉尼的城市面积。我先查一下东京的面积。

Action 1: 
{
  "tool": "search_wikipedia",
  "query": "Tokyo area"
}

Observation 1: 
东京（Tokyo）是日本的首都。东京都（Tokyo Metropolis）总面积约 2,194 km²，
其中包含23个特别区（约 627 km²）和西部多摩地区等。

Thought 2: 东京都的面积约 2,194 km²。现在我需要查悉尼的面积。

Action 2:
{
  "tool": "search_wikipedia",
  "query": "Sydney area"
}

Observation 2:
悉尼（Sydney）是澳大利亚新南威尔士州的首府。悉尼城市面积约 1,687 km²
（城市边界内），大悉尼都会区面积约 12,368 km²。

Thought 3: 这里要注意"城市面积"的比较口径。东京都的面积是 2,194 km²，
而悉尼城市边界内面积是 1,687 km²。但悉尼的大都会区面积远大于东京。
我需要明确用户指的是行政城市面积还是都会区面积。
根据常见的城市面积比较（通常指行政边界内），东京 2,194 km² > 悉尼 1,687 km²。

Final Answer:
以行政边界内面积计算，**东京更大**（2,194 km² vs 悉尼的 1,687 km²）。
但需要注意悉尼的大悉尼都会区（12,368 km²）远大于东京都。
如果问题是"都会区面积"，则悉尼更大。这在城市比较中是一个常见口径问题。
```

## 何时使用 ReAct

### 优势场景

1. **动态探索性任务**：解决方案路径不明确，需要边探索边决策。例如研究性问题、开放域问答、调试未知错误。
2. **需要事实验证的任务**：模型可以利用工具结果校正自身幻觉。Yao et al. 的实验证明 ReAct 显著降低了 LLM 的事实性错误。
3. **需要多步推理+信息收集的任务**：如"这个药物有哪些已知副作用？"需要搜索、摘要、交叉验证。
4. **可解释性要求高的场景**：Thought 轨迹为最终答案提供了完整的推理链路，便于审计和调试。

### 劣势场景

1. **高延迟任务**：每个 ReAct 循环都需要一次 LLM 推理 + 工具执行。如果单次工具调用耗时很长（如数据库查询 10 秒），多轮循环的累积延迟会远超用户可接受范围。
2. **简单任务**：如果答案可以直接由模型知识给出，ReAct 的额外推理和工具调用轮次浪费了 tokens。对于这类任务，直接生成答案效率更高。
3. **工具调用不稳定**：当工具结果不可靠（如搜索 API 返回错误、代码执行环境不稳定）时，ReAct 的 Observation 步骤会引入噪声，反而降低性能。

## Token 成本分析

每个 ReAct 循环的 Token 消耗构成：

```
单轮 ReAct 循环 Token 开销：
  ├── 输入的 Thought 前缀          ~50-200 tokens（历史上下文的延续）
  ├── 生成的 Thought 内容           ~50-300 tokens（取决于推理深度）
  ├── 生成的 Action 结构            ~30-100 tokens（函数名 + 参数）
  ├── Observation（工具返回结果）   ~100-10,000+ tokens（取决于结果大小）
  └── 上述所有内容在下一轮中重复输入（累积上下文）

示例（5轮 ReAct）：
  - 推理 tokens（Thought + Action）：5 × 250 = 1,250 tokens 输出
  - 工具结果 tokens（Observation）：5 × 500 = 2,500 tokens 输入
  - 累积历史：每轮递增，第5轮时上下文已达 ~18,750 tokens
  - 总计输入 ≈ 37,500 tokens，输出 ≈ 1,250 tokens
```

当工具返回大型文档（如整个网页、SQL 查询全部结果）时，Observation 的 token 消耗往往占据大头。实践中常用的优化手段包括：

- **截断**：只保留工具结果的前 N 个 tokens（通常 2,000-4,000）。
- **摘要**：先让一个小模型或 LLM 对工具结果做摘要，再将摘要作为 Observation 输入。
- **结构化提取**：只提取工具结果中与当前任务相关的字段。

## 工程实现伪代码

```python
class ReActAgent:
    def __init__(self, llm, tools, max_steps=10):
        self.llm = llm
        self.tools = {t.name: t for t in tools}
        self.max_steps = max_steps
    
    def run(self, user_query: str) -> str:
        history = [{"role": "user", "content": user_query}]
        system_prompt = self._build_system_prompt()
        
        for step in range(self.max_steps):
            # 1. 生成 Thought + Action
            response = self.llm.generate(
                system=system_prompt,
                messages=history,
                stop=["Observation:"]
            )
            thought_action = response.content
            history.append({"role": "assistant", "content": thought_action})
            
            # 2. 解析 Action
            action = self._parse_action(thought_action)
            if action is None:  # 模型输出 Final Answer
                return self._extract_final_answer(thought_action)
            
            # 3. 执行工具调用
            tool = self.tools.get(action["name"])
            if not tool:
                observation = f"Error: tool '{action['name']}' not found"
            else:
                try:
                    observation = tool.execute(**action["args"])
                except Exception as e:
                    observation = f"Error executing tool: {str(e)}"
            
            # 4. 添加 Observation 到历史
            history.append({"role": "user", "content": f"Observation: {observation}"})
        
        return "Max steps reached, unable to complete task."
```
