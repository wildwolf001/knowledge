# 2.2 Plan-and-Execute 模式

## 论文来源

- **Plan-and-Solve Prompting: Improving Zero-Shot Chain-of-Thought Reasoning by Large Language Models** -- Lei Wang, Wanyu Xu, Yihuai Lan, Zhiqiang Hu, Yunshi Lan, Roy Ka-Wei Lee, Ee-Peng Lim (2023)
  - arXiv: [2305.04091](https://arxiv.org/abs/2305.04091)
- **Tree-of-Thoughts: Deliberate Problem Solving with Large Language Models** -- Shunyu Yao, Dian Yu, Jeffrey Zhao, Izhak Shafran, Thomas L. Griffiths, Yuan Cao, Karthik Narasimhan (2023)
  - arXiv: [2305.10601](https://arxiv.org/abs/2305.10601)
  - 将单步推理扩展为树的搜索，是 Plan-and-Execute 的高阶形式

## 核心思想

Plan-and-Execute 的核心洞察是：**将"思考做什么"和"动手去做"这两个阶段彻底分离**。与 ReAct（详见 [2.1 ReAct模式](./2.1-ReAct模式.md)）中"边想边做"的紧密耦合不同，Plan-and-Execute 先由 Planner 模块生成完整的执行计划，再由 Executor 模块逐一执行计划中的步骤。

```
ReAct 模式:         Thought → Action → Observation → Thought → Action → ...
                    （想一步，做一步，看一步）

Plan-and-Execute:   Plan (完整计划) → Step_1 → Step_2 → Step_3 → ... → Done
                    （先想完整，再依次执行）
```

这种分离带来的核心优势是：Planner 可以全局优化步骤顺序，而 Executor 可以专注于单步执行，互不干扰。

## 架构设计

### 两阶段流水线

```
┌─────────────────────────────────────────────────────┐
│                   Plan-and-Execute Agent              │
├─────────────────────────────────────────────────────┤
│  阶段一：规划 (Planning Phase)                        │
│                                                       │
│  用户输入 ──→  Planner (LLM) ──→ 执行计划              │
│                 │                                      │
│                 ├── 步骤 1: 搜索东京面积               │
│                 ├── 步骤 2: 搜索悉尼面积               │
│                 ├── 步骤 3: 比较并输出结果             │
│                 └── 依赖图 (可选)                      │
│                                                       │
│  阶段二：执行 (Execution Phase)                        │
│                                                       │
│  执行计划 ──→  Executor (LLM + Tools) ──→ 最终答案    │
│                 │                                      │
│  步骤 1 ───→ search_wikipedia("Tokyo area")           │
│              ←── Observation: 2,194 km²               │
│  步骤 2 ───→ search_wikipedia("Sydney area")          │
│              ←── Observation: 1,687 km²               │
│  步骤 3 ───→ Compare(2194, 1687) → "东京更大"         │
│                                                       │
└─────────────────────────────────────────────────────┘
```

### Planner 模块

Planner 接收用户任务，输出一个结构化的执行计划。常见的计划格式有三种：

| 格式 | 描述 | 适用场景 |
|------|------|----------|
| **线性步骤列表** | `[step1, step2, step3, ...]` | 顺序依赖明确的任务 |
| **DAG 依赖图** | 步骤之间有并行/分支关系 | 可并行执行的任务 |
| **分层计划** | 步骤可递归展开为子步骤 | 复杂任务需要多层次分解 |

```python
# Planner 的输出示例：线性步骤列表
{
  "plan": [
    {"step_id": 1, "description": "搜索东京的行政区面积", "tool": "search", "depends_on": []},
    {"step_id": 2, "description": "搜索悉尼的城市面积", "tool": "search", "depends_on": []},
    {"step_id": 3, "description": "比较两个面积数值", "tool": "compare", "depends_on": [1, 2]},
    {"step_id": 4, "description": "输出最终结论", "tool": "final_answer", "depends_on": [3]}
  ],
  "parallel_groups": [[1, 2], [3], [4]]  # 步骤 1 和 2 可并行执行
}
```

### Executor 模块

Executor 遍历计划中的步骤，按依赖顺序依次或并行执行。与 ReAct 不同，Executor **不需要在每个步骤之间调用 LLM 进行推理**——它只需机械地执行计划中的工具调用即可。这大幅减少了 LLM 推理调用次数。

```python
class Executor:
    def __init__(self, tools):
        self.tools = {t.name: t for t in tools}
    
    def execute_plan(self, plan: list[dict], context: dict) -> dict:
        results = {}
        # 按并行组依次执行
        for group in plan["parallel_groups"]:
            # 同一组内的步骤可并行执行
            for step_id in group:
                step = next(s for s in plan["plan"] if s["step_id"] == step_id)
                tool = self.tools[step["tool"]]
                # 从 context 中填充依赖步骤的结果
                args = self._resolve_args(step, results)
                results[step_id] = tool.execute(**args)
        return results
```

## Plan-and-Execute vs. ReAct

### 关键区别

| 维度 | ReAct | Plan-and-Execute |
|------|-------|------------------|
| **规划时机** | 边执行边规划（局部的每步决策） | 执行前一次性规划（全局视角） |
| **LLM 调用次数** | 每步 1 次推理（N 步 = N 次） | 1 次规划 + 0 次执行中推理（仅工具调用） |
| **灵活性** | 高——可根据观察动态调整 | 低——计划固定后难以调整 |
| **Token 消耗** | 高（每步生成完整 Thought） | 低（仅规划阶段消耗推理 tokens） |
| **可预见性** | 低——最终路径不可预测 | 高——计划本身承诺了执行路径 |
| **错误传播** | 早期错误可在后续步骤纠正 | 规划错误会贯穿整个执行过程 |
| **并行执行** | 天然串行，难以并行 | 支持步骤级并行 |

### 何时选择 Plan-and-Execute

**Plan-and-Execute 更优的场景：**

1. **步骤明确的批处理任务**：如"对目录下 100 个文件执行相同的数据清洗流程"。Planner 只需生成一次清洗计划，Executor 批量执行，无需每步思考。
2. **延迟敏感的在线服务**：LLM 推理延迟高（通常 1-5 秒/次），而工具调用延迟低（如本地函数调用 <1ms）。Plan-and-Execute 将 LLM 推理压缩到 1 次，后续全为低延迟执行。
3. **需要全局最优顺序的任务**：例如调度问题、资源分配问题。Planner 可以一次性考虑全局约束（如"步骤 A 必须在 B 之前，但 C 可以随时执行"），而 ReAct 的贪心策略（每次只选择当前最优动作）可能陷入局部最优。
4. **可审计性要求高的场景**：计划本身就是一份可审查的文档。审计员可以在执行前批准或修改计划，而非事后追踪 ReAct 的每步思考轨迹。

```
示例：批量文件处理

用户: "将 /data/invoices 目录下所有 PDF 发票提取为结构化 JSON"

Plan-and-Execute 方式:
  Plan:
    1. 列出 /data/invoices 下所有 .pdf 文件
    2. 对每个文件并行执行: 读取 PDF → OCR → 提取字段 → 输出 JSON
    3. 汇总处理结果报告
  
  执行: 对 100 个文件，Executor 仅需 1 次 LLM 调用（规划）+ 100 次工具调用。
  总计：1 次 LLM 推理 + 100 次 PDF 处理。

ReAct 方式:
  每处理一个文件都需要: Thought → 调用读取工具 → 观察结果 → 思考下一步...
  对 100 个文件可能产生 300-500 次 LLM 推理调用。
  总计：300-500 次 LLM 推理 + 100 次 PDF 处理。

结论：当任务具有重复性且步骤可预测时，Plan-and-Execute 在成本上
有数量级优势。
```

### 何时不选择 Plan-and-Execute

1. **探索性/不确定性任务**：如果无法预先知道需要哪些步骤（如"研究这个新框架的优缺点"），Plan-and-Execute 的固定计划会限制探索。
2. **环境高度动态的任务**：如果工具结果可能随时间变化（如实时股票价格、天气数据），执行时计划可能已过期。
3. **计划本身就很困难的任务**：某些任务规划复杂度和执行复杂度相当（如"修复这个代码 bug"），此时 ReAct 的边做边想更自然。

## 工程实现伪代码

```python
class PlanAndExecuteAgent:
    def __init__(self, llm, tools, max_execution_steps=50):
        self.llm = llm
        self.tools = {t.name: t for t in tools}
        self.max_execution_steps = max_execution_steps
        self.planner = Planner(llm)
        self.executor = Executor(tools)
    
    def run(self, user_query: str) -> str:
        # 阶段一：生成计划
        plan = self.planner.create_plan(user_query, self.tools.keys())
        print(f"[Plan] 共 {len(plan['plan'])} 步:")
        for step in plan["plan"]:
            print(f"  Step {step['step_id']}: {step['description']}")
        
        # 可选：用户审核/修改计划
        # plan = self.user_approve_plan(plan)
        
        # 阶段二：执行计划
        context = {"user_query": user_query}
        results = self.executor.execute_plan(plan, context)
        
        # 阶段三：汇总结果
        final = self.llm.generate(
            f"根据以下执行结果回答用户问题：{user_query}\n\n"
            f"执行结果：{results}"
        )
        return final


class Planner:
    def __init__(self, llm):
        self.llm = llm
    
    def create_plan(self, task: str, available_tools: list[str]) -> dict:
        prompt = f"""你是一个任务规划器。请为以下任务生成执行计划。

可用工具: {', '.join(available_tools)}

任务: {task}

请输出一个 JSON 格式的计划，包含：
1. 按顺序排列的步骤列表
2. 每个步骤的 tool 和参数说明
3. 步骤间的依赖关系
4. 可并行执行的步骤分组

确保步骤完整且没有遗漏。"""
        
        response = self.llm.generate(prompt)
        plan = self._parse_plan(response)
        
        # 计划验证：检查工具是否存在、参数是否完整
        self._validate_plan(plan, available_tools)
        
        return plan
    
    def _validate_plan(self, plan, available_tools):
        """确保计划中的每个工具都存在"""
        for step in plan["plan"]:
            if step["tool"] not in available_tools:
                raise ValueError(f"Plan references unknown tool: {step['tool']}")
        # 还可以做循环检测、可达性分析等


class Executor:
    def __init__(self, tools):
        self.tools = tools
    
    def execute_plan(self, plan, context):
        results = {}
        completed = set()
        
        for group in plan.get("parallel_groups", [[s["step_id"] for s in plan["plan"]]]):
            # 检查当前组所有依赖是否已满足
            step_objects = {s["step_id"]: s for s in plan["plan"]}
            
            for step_id in group:
                step = step_objects[step_id]
                deps = step.get("depends_on", [])
                if not all(d in completed for d in deps):
                    continue  # 依赖未完成，跳过（这种情况在正确计划中不应出现）
            
            # 执行当前组（可并行）
            for step_id in group:
                step = step_objects[step_id]
                tool = self.tools[step["tool"]]
                args = self._resolve_args(step, results, context)
                
                try:
                    results[step_id] = tool.execute(**args)
                except Exception as e:
                    results[step_id] = f"Error: {str(e)}"
                    # Plan-and-Execute 中错误的处理策略：
                    # 1. 继续执行（skip） 2. 重试 3. 终止
                
                completed.add(step_id)
        
        return results
    
    def _resolve_args(self, step, results, context):
        """解析参数，支持引用前序步骤的结果"""
        args = {}
        for param_name, param_value in step.get("args", {}).items():
            if isinstance(param_value, str) and param_value.startswith("$"):
                # 引用前序结果，如 "$3" 表示步骤 3 的结果
                ref_step = int(param_value[1:])
                args[param_name] = results.get(ref_step)
            else:
                args[param_name] = param_value
        return args
```

## 变体：动态 Plan-and-Execute

纯 Plan-and-Execute 的最大弱点是一旦计划生成便不再调整。实践中常引入轻量级的**计划修正机制**：

```python
class DynamicPlanExecutor:
    def execute_with_monitoring(self, plan, context):
        results = {}
        for i, step in enumerate(plan["plan"]):
            result = self._execute_step(step, results, context)
            results[step["step_id"]] = result
            
            # 检查是否需要修正计划
            if self._should_replan(result, step):
                print(f"[Replan] Step {step['step_id']} 结果异常，重新规划剩余步骤")
                remaining = plan["plan"][i+1:]
                plan = self.planner.replan(
                    context, results, remaining
                )
                # 重新从修正后的计划开始执行
                return self.execute_with_monitoring(plan, context)
        
        return results
    
    def _should_replan(self, result, expected):
        """决策是否修正计划：结果错误、超时、环境变化"""
        if result.startswith("Error:"):
            return True
        # 其他重规划触发条件
        return False
```

这种动态变体本质上已接近下一节 [2.3 Plan-then-ReAct 混合模式](./2.3-Plan-then-ReAct%E6%B7%B7%E5%90%88%E6%A8%A1%E5%BC%8F.md) 的思想——用全局规划保证方向，用局部灵活性应对不确定性。

## Token 成本分析

```
5 步任务的成本对比：

Plan-and-Execute:
  ├── 规划阶段（1 次 LLM 调用）
  │    输入: 任务描述 + 工具列表 ~200 tokens
  │    输出: 计划 JSON           ~300 tokens
  │    总计: 500 tokens
  ├── 执行阶段（0 次 LLM 调用，仅工具调用）
  │    Step 1: search           ~200 tokens (结果)
  │    Step 2: search           ~200 tokens
  │    Step 3: compare          ~50 tokens
  │    总计: 450 tokens
  ├── 汇总（1 次 LLM 调用）
  │    输入: 所有执行结果        ~700 tokens
  │    输出: 最终答案            ~100 tokens
  │    总计: 800 tokens
  └── 总消耗: 1,750 tokens

ReAct（同样 5 步）:
  每步: Thought(~150) + Action(~50) + Observation(~200) = 400 tokens/步
  + 历史累积递增
  总计: ~8,750 tokens (含累积历史)

结论：Plan-and-Execute 在 Token 消耗上约为 ReAct 的 1/5 到 1/10。
```

## 关键概念速查表

| 概念 | 定义 | 要点 |
|------|------|------|
| **Planner** | 生成执行计划的模块 | 一次性输出完整步骤序列；可使用线性/DAG/分层三种计划格式 |
| **Executor** | 按计划执行工具调用的模块 | 不需要 LLM 推理；可并行执行无依赖的步骤 |
| **计划验证** | 执行前检查计划的有效性 | 检查工具是否存在、参数类型、依赖循环 |
| **动态重规划** | 执行中根据结果修正计划 | 折中方案，保留 Plan 的方向感，加入 ReAct 的灵活性 |
| **依赖图 (DAG)** | 步骤间的前驱后继关系 | 无依赖的步骤可并行执行，降低总耗时 |
| **全局最优** | 考虑所有步骤的整体排序 | 对比 ReAct 的贪心策略，避免局部最优 |
