## 核心思想

Plan-then-ReAct 混合模式的核心洞察是：**用全局规划提供方向感，用局部 ReAct 提供灵活性**。这是 [2.1 ReAct模式](./2.1-ReAct模式.md) 和 [2.2 Plan-and-Execute](./2.2-Plan-and-Execute.md) 两种极端方案的折中。

```
纯 ReAct:        Thought → Action → Obs → Thought → Action → Obs → ...
                 （没有全局计划，每一步都在即兴发挥）

纯 Plan-Execute:  Plan → Step1 → Step2 → Step3 → ... → Done
                 （计划固定，执行僵化）

混合模式:         Plan → [ReAct循环] → [ReAct循环] → [ReAct循环] → Done
                 （有全局计划，但每个步骤内灵活执行）
```

### 为什么是工业界的主流方案？

在实际生产环境中，纯 ReAct 和纯 Plan-and-Execute 都暴露出明显缺陷：

1. **纯 ReAct** 在复杂任务中缺乏方向感——Agent 可能在子问题上反复打转（如"搜索 A → 发现相关 B → 搜索 B → 发现 A 才是关键 → 回到 A"），浪费大量 tokens 和时间。
2. **纯 Plan-and-Execute** 过于脆弱——现实中工具调用可能失败、返回意外结果、需求在执行中变化，固定计划无法应对。

混合模式通过**分层抽象**解决了这个问题：高层计划定义"做什么"，低层 ReAct 循环决定"怎么做"。

### 三要素

| 组件 | 职责 | LLM 调用频率 |
|------|------|-------------|
| **Planner** | 生成宏观步骤列表，定义每个步骤的目标 | 每次任务 1 次 |
| **Step Executor** | 每个步骤内运行 ReAct 循环，直到该步骤目标达成 | 每子步骤 1 次 |
| **Tracker** | 维护已完成/进行中/待处理的步骤状态，检测进度停滞 | 持续运行（无 LLM） |

## 具体示例：市场调研 Agent

用户输入：*"调研中国新能源汽车市场，分析比亚迪、蔚来、小鹏三家的 2024 年销量和市场份额，给出对比报告。"*

### 步骤 1: Planner 生成宏观计划

```json
{
  "plan": [
    {
      "step": 1,
      "goal": "搜索比亚迪 2024 年销量数据",
      "success_criteria": "找到比亚迪 2024 年全年销量及市场份额",
      "max_substeps": 5
    },
    {
      "step": 2,
      "goal": "搜索蔚来 2024 年销量数据",
      "success_criteria": "找到蔚来 2024 年全年销量及市场份额",
      "max_substeps": 5
    },
    {
      "step": 3,
      "goal": "搜索小鹏 2024 年销量数据",
      "success_criteria": "找到小鹏 2024 年全年销量及市场份额",
      "max_substeps": 5
    },
    {
      "step": 4,
      "goal": "对比三家数据并生成最终报告",
      "success_criteria": "输出包含表格和趋势分析的对比报告",
      "max_substeps": 3
    }
  ],
  "global_context": "2024年中国新能源汽车市场竞争激烈，比亚迪保持领先，蔚来和小鹏在高端市场角逐。"
}
```

### 步骤 2: Step 1 内部的 ReAct 子循环

```
进入 Step 1: 搜索比亚迪 2024 年销量数据

Sub-Thought 1: 我需要搜索比亚迪 2024 年的销量数据。用一个通用搜索来获取。
Sub-Action 1: search("比亚迪 2024 年销量")
Sub-Observation 1: 搜索结果：比亚迪 2024 年全年销量 4,252 万辆？...
                    （数据看起来有误，这可能是全公司数据而非汽车销量）

Sub-Thought 2: 这个数据看起来异常大。我需要更精确的搜索，加上"新能源汽车"限定词。
Sub-Action 2: search("比亚迪 新能源汽车 2024 年 销量 数据")
Sub-Observation 2: 搜索结果：2024 年比亚迪新能源汽车销量 3,412,487 辆，
                    同比增长 42%。市场份额约 33.5%。

Sub-Thought 3: 现在我有正确的数据了。验证一下数据来源的可靠性。
Sub-Action 3: open_url("https://.../byd-2024-sales-report")
Sub-Observation 3: 中国汽车工业协会数据确认：比亚迪 2024 年新能源车销量 3,412,487 辆。

Sub-Thought 4: 数据已确认。Step 1 完成。
输出结果: {"company": "比亚迪", "sales_2024": 3412487, "market_share": "33.5%", "growth": "42%"}

Step 1 完成，进入 Step 2。
```

注意这里的关键点：**Planner 只定义了"搜索比亚迪 2024 年销量数据"这个目标，但具体怎么搜、搜错了怎么纠正，都由 Step Executor 内部的 ReAct 循环自主决定。** 这正是混合模式的核心优势。

## 三种模式的对比

| 维度 | ReAct | Plan-and-Execute | Plan-then-ReAct (混合) |
|------|-------|------------------|----------------------|
| **全局规划** | 无 | 有（一次性） | 有（可迭代修正） |
| **局部灵活性** | 高（每步动态决策） | 低（严格按计划） | 高（子步骤自由探索） |
| **LLM 调用** | N 步 = N 次 | 约 1 次 | M(计划步数) × N(子步骤) 次 |
| **方向偏离风险** | 高（容易跑偏） | 低（计划锁定） | 中（计划提供锚点） |
| **实现复杂度** | 低 | 中 | 高 |
| **适用任务长度** | 短（<10 步） | 中（10-50 步） | 长（50+ 步） |
| **容错能力** | 强（每步可调整） | 弱（错误传播） | 强（子循环内可纠错） |

## 工程实现伪代码

```python
class PlanThenReActAgent:
    def __init__(self, llm, tools, max_plan_steps=8, max_substeps_per_step=10):
        self.llm = llm
        self.tools = {t.name: t for t in tools}
        self.max_plan_steps = max_plan_steps
        self.max_substeps = max_substeps_per_step
        self.context = {}  # 全局上下文，跨步骤共享
    
    def run(self, user_query: str) -> str:
        # 阶段一：生成宏观计划
        plan = self._generate_plan(user_query)
        print(f"[Planner] 生成 {len(plan)} 个宏观步骤:")
        for i, step in enumerate(plan):
            print(f"  Step {i+1}: {step['goal']}")
        
        # 阶段二：逐步骤执行 ReAct 子循环
        step_results = []
        for step_idx, step_plan in enumerate(plan):
            print(f"\n{'='*50}")
            print(f"[Executor] 开始执行 Step {step_idx + 1}: {step_plan['goal']}")
            print(f"{'='*50}")
            
            result = self._execute_step(
                step_plan=step_plan,
                step_context={
                    "previous_results": step_results,
                    "global_context": self.context
                }
            )
            step_results.append(result)
            
            # 步骤完成后可选的规划修正
            if self._should_replan(step_idx, plan, step_results):
                print(f"[Replanner] Step {step_idx + 1} 后重新评估剩余计划")
                plan = self._replan(user_query, step_results, plan[step_idx + 1:])
        
        # 阶段三：汇总所有步骤结果
        final = self._synthesize(user_query, step_results)
        return final
    
    def _generate_plan(self, task: str) -> list[dict]:
        """Planner: 生成宏观步骤列表"""
        prompt = f"""将以下任务分解为 {self.max_plan_steps} 个以内的宏观步骤。

任务: {task}

要求：
- 每个步骤是一个独立的目标，可以独立完成
- 步骤之间按逻辑顺序排列
- 每个步骤包含 success_criteria 用于判断是否完成
- 步骤不要太细（每个步骤内部可能需要多次工具调用）

请以 JSON 格式输出步骤列表。"""
        
        response = self.llm.generate(prompt)
        plan = json.loads(self._extract_json(response))
        return plan["steps"] if "steps" in plan else plan
    
    def _execute_step(self, step_plan: dict, step_context: dict) -> dict:
        """Step Executor: 在一个步骤内运行 ReAct 子循环"""
        goal = step_plan["goal"]
        success_criteria = step_plan.get("success_criteria", "")
        max_steps = step_plan.get("max_substeps", self.max_substeps)
        
        # 子循环的初始提示，包含步骤目标和全局上下文
        sub_history = [
            {"role": "system", "content": f"当前步骤目标: {goal}\n"
                                          f"完成标准: {success_criteria}\n"
                                          f"前序步骤结果: {step_context.get('previous_results', [])}"}
        ]
        
        for sub_step in range(max_steps):
            # ReAct 子循环（详见 2.1 节的 ReAct 核心循环）
            response = self.llm.generate(messages=sub_history)
            
            thought_action = response.content
            sub_history.append({"role": "assistant", "content": thought_action})
            
            # 检查是否达成步骤目标
            if self._is_step_complete(thought_action, success_criteria):
                print(f"  [Step Done] 目标达成: {goal}")
                return self._extract_step_result(thought_action)
            
            # 解析并执行工具调用
            action = self._parse_action(thought_action)
            if action:
                observation = self._execute_tool(action)
                sub_history.append({"role": "user", "content": f"Observation: {observation}"})
        
        # 子步骤超限，返回已有结果
        print(f"  [Warning] Step 达到最大子步骤数 {max_steps}，强制结束")
        return {"partial_result": sub_history[-1]["content"], "goal": goal}
    
    def _should_replan(self, step_idx, original_plan, results_so_far) -> bool:
        """评估是否需要修正剩余计划"""
        # 触发重规划的典型条件：
        # 1. 当前步骤结果与预期严重不符
        # 2. 当前步骤发现了计划时未预料到的关键信息
        # 3. 用户在执行过程中修改了需求
        if "unexpected" in str(results_so_far[-1]).lower():
            return True
        return False
    
    def _replan(self, original_task, completed_results, remaining_plan):
        """Replanner: 根据已完成步骤的结果重新规划剩余步骤"""
        prompt = f"""原始任务: {original_task}
已完成步骤的结果: {completed_results}
原计划中剩余步骤: {remaining_plan}

请根据已完成步骤的实际结果，重新规划剩余步骤。
如有必要，可以修改、合并或拆分原计划中的剩余步骤。"""
        
        response = self.llm.generate(prompt)
        return json.loads(self._extract_json(response))
    
    def _synthesize(self, task, step_results):
        """汇总所有步骤结果生成最终答案"""
        prompt = f"""根据以下步骤执行结果回答用户问题。

问题: {task}

各步骤结果:
{json.dumps(step_results, ensure_ascii=False, indent=2)}

请整合所有信息，给出完整的最终答案。"""
        return self.llm.generate(prompt)
    
    def _execute_tool(self, action):
        tool = self.tools.get(action["name"])
        if not tool:
            return f"Error: tool '{action['name']}' not found"
        try:
            return tool.execute(**action["args"])
        except Exception as e:
            return f"Error: {str(e)}"
```

## 关键实现细节

### 步骤间上下文管理

一个常见陷阱是每个 ReAct 子循环独立运行，丢失了步骤间积累的信息。正确的做法是维护一个**全局上下文对象**，在每个步骤开始时注入：

```python
class StepContext:
    def __init__(self):
        self.global_memory = {}       # 跨步骤共享的关键信息
        self.step_results = []        # 已完成的步骤结果
        self.intermediate_outputs = []  # 所有步骤产生的中间产物
    
    def update(self, step_id, result, key_findings):
        self.step_results.append({"step_id": step_id, "result": result})
        for key, value in key_findings.items():
            self.global_memory[key] = value  # 覆盖或新增全局信息
```

### 成功标准检查

每个步骤的 `success_criteria` 是关键的设计决策。太严格会导致步骤无法结束，太宽松会导致步骤目标未达成就提前退出。实践中常用两种策略：

1. **关键词匹配**：检查输出中是否包含特定关键词（如"销量""市场份额"）。
2. **LLM 判断**：让 LLM 自己判断是否满足成功标准，输出 `{"done": true/false, "reason": "..."}`。

```python
def _is_step_complete(self, thought_action, criteria):
    # 策略一：关键词匹配（轻量级）
    if criteria and all(kw in thought_action for kw in criteria.split()):
        return True
    
    # 策略二：LLM 判断（更准确但消耗 tokens）
    check_prompt = f"""当前步骤完成标准: {criteria}
Agent 最新输出: {thought_action}
请判断步骤目标是否已达成？回答 yes 或 no。"""
    response = self.llm.generate(check_prompt)
    return "yes" in response.content.lower()
```

## 常见陷阱与最佳实践

| 陷阱 | 现象 | 解决方案 |
|------|------|----------|
| **步骤粒度过细** | Planner 生成了 50 个步骤，每个步骤只做一件事 | 限制 Planner 输出步骤数（3-8 步），过细的步骤合并 |
| **上下文爆炸** | 每个 ReAct 子循环的累积历史在步骤间不断膨胀 | 步骤间截断历史，仅保留步骤结果摘要而非完整轨迹 |
| **步骤间信息孤岛** | 第二步不知道第一步发现了什么 | 显式传递全局上下文对象，关键信息写入 shared_memory |
| **循环陷阱** | Agent 在某个步骤内反复做同一件事 | 设置子步骤上限，检测重复模式（连续 3 次相同 Action 则强制结束） |

## Token 成本分析

```
假设任务 = 4 个宏观步骤，平均每个步骤内部 3 个子步骤：

Plan-then-ReAct 混合模式:
  ├── 规划: 1 次 LLM
  │    输入: 任务描述 ~150 tokens
  │    输出: 计划 JSON ~250 tokens
  │    小计: 400 tokens
  ├── 步骤 1 ReAct 子循环（3 子步）:
  │    Thought + Action(×3): 3 × 200 = 600 tokens 输出
  │    Observation(×3): 3 × 300 = 900 tokens 输入
  │    小计: 1,500 tokens
  ├── 步骤 2 ReAct 子循环（3 子步）:
  │    同上: 1,500 tokens
  ├── 步骤 3 ReAct 子循环（3 子步）:
  │    同上: 1,500 tokens
  ├── 步骤 4 ReAct 子循环（2 子步）:
  │    2 × 200 + 2 × 300 = 1,000 tokens
  ├── 汇总: 1 次 LLM ~300 tokens
  └── 总计: ~6,200 tokens

作为对比：
  - 纯 ReAct（12 步）: ~21,000 tokens（含累积历史）
  - 纯 Plan-and-Execute: ~2,100 tokens（但面对意外 0 容错）

混合模式在灵活性和成本之间取得了实用的平衡。
```

## 关键概念速查表

| 概念 | 定义 | 要点 |
|------|------|------|
| **宏观计划** | 由 Planner 生成的高层步骤序列 | 每个步骤是一个独立目标（非具体操作）；3-8 步为宜 |
| **ReAct 子循环** | 每个步骤内部的思考-行动-观察循环 | 可自由探索步骤的实现方式；达到 success_criteria 即结束 |
| **全局上下文** | 跨步骤共享的信息存储器 | 避免步骤间信息孤岛；需显式传递关键发现 |
| **成功标准** | 判断步骤是否完成的规则 | 用关键词匹配或 LLM 判断；决定子循环何时退出 |
| **重规划 (Replan)** | 执行中修正剩余计划 | 触发条件：意外结果、新信息发现、需求变更 |
| **步骤粒度** | 每个宏观步骤的抽象级别 | 太粗：步骤内部太复杂；太细：规划失去意义 |
