# 22.1 推理加速

> 推理加速（Inference Acceleration）是通过算法和工程手段减少大语言模型生成回复的计算开销和延迟。推理速度直接决定了 Agent 的响应时间、并发能力和运营成本——尤其是在需要多轮工具调用和长上下文理解的场景中。

---

## 一、为什么推理加速至关重要？

### 1.1 推理 vs 训练的计算不对称

大语言模型的计算开销在训练和推理阶段呈现完全不同的分布。训练是一次性投入，而推理是每次请求都会产生的持续成本：

| 维度 | 训练 | 推理 |
|------|------|------|
| **执行频率** | 一次（或数次） | 数百万次/天 |
| **批量大小** | 大（数万样本） | 小（通常 1-32） |
| **硬件利用** | 接近 100% | 可能低至 20-50% |
| **延迟要求** | 宽松（小时级） | 严格（秒级） |
| **成本占比** | 前期投入 | 长期运营成本的主要部分 |

对于 Agent 系统，推理开销问题更为突出。一个简单的 Agent 调用链可能包括：系统提示词 + 用户问题 + 工具描述 + 工具调用结果 + 多轮推理。上下文长度的增加使得推理的 FLOPs 以平方级别增长（注意力机制 O(n²) 的复杂度），这使得推理加速成为 Agent 系统能否落地的关键瓶颈。

### 1.2 Agent 场景的特殊挑战

与单轮问答不同，Agent 的推理过程通常包含多个阶段：

```
用户输入 → 计划生成 → 工具调用 → 结果分析 → 下一步决策 → 最终回复
                ↑                                       |
                └───────────────── 循环 ────────────────┘
```

每一轮推理都包含完整的 Transformer 前向传播，而工具调用结果通常较长（例如数据库查询结果、网页抓取内容），进一步拉长了上下文。因此推理加速对于 Agent 系统不仅是"锦上添花"，而是"生死存亡"的问题。

## 二、量化（Quantization）：用精度换速度

### 2.1 量化原理

量化（Quantization）是指将模型参数从高精度数据类型（如 FP32）映射到低精度数据类型（如 INT8、INT4）的过程。其核心思想是：**神经网络对数值精度的容忍度远高于常规计算**。

**数学原理**：

模型的权重和激活值通常以 32 位浮点数（FP32）存储。量化将其映射到整数范围：

```
FP32 范围: [-3.4×10³⁸, 3.4×10³⁸]  （4字节）
INT8 范围: [-128, 127]              （1字节）
INT4 范围: [-8, 7]                  （0.5字节）
```

量化映射公式（对称量化）：
```
量化值 = round(原始值 / 缩放因子)
反量化值 = 量化值 × 缩放因子
缩放因子 = max(|原始值|) / (2^(位宽-1) - 1)
```

以 INT8 量化为例，每一个权重从 4 字节压缩为 1 字节，模型大小减少 75%，同时由于整数运算比浮点运算快得多，推理速度可以提升 2-4 倍。

### 2.2 量化方法分类

| 方法 | 描述 | 精度损失 | 是否需要校准数据 | 适用场景 |
|------|------|---------|---------------|---------|
| **PTQ（Post-Training Quantization）** | 训练后量化，无需重新训练 | 低-中 | 需要少量 | 通用 |
| **GPTQ** | 基于最优脑外科框架的 1 次量化 | 低 | 需要 128 样本 | GPU 推理 |
| **GGUF 量化** | llama.cpp 使用的量化格式 | 中 | 不需要 | CPU/边缘设备 |
| **AWQ（Activation-aware Weight Quantization）** | 感知激活值的量化 | 极低 | 需要少量 | GPU 高性能推理 |
| **BitsAndBytes（BNB）** | HF 生态的 4bit 量化（QLoRA） | 低 | 不需要 | 微调/推理 |
| **NF4（Normal Float 4）** | 正态分布优化的 4bit 格式 | 低 | 不需要 | 保持精度最佳 |

### 2.3 精度损失数据

以下为 LLaMA-3-70B 在不同量化精度下的 benchmark 数据（基于 MMLU 和 HumanEval）：

| 量化格式 | 模型大小 | MMLU（5-shot） | HumanEval pass@1 | 推理速度（token/s） | 显存占用 |
|---------|---------|---------------|------------------|-------------------|---------|
| FP16（基线） | 140GB | 82.0% | 81.7% | 18.5 | 140GB |
| INT8（GPTQ） | 70GB | 81.5% (-0.5%) | 81.1% (-0.6%) | 32.1 | 70GB |
| INT4（GPTQ） | 35GB | 80.2% (-1.8%) | 78.9% (-2.8%) | 45.3 | 35GB |
| INT4（AWQ） | 35GB | 81.1% (-0.9%) | 80.5% (-1.2%) | 43.8 | 35GB |
| NF4（BNB） | 35GB | 80.8% (-1.2%) | 80.1% (-1.6%) | 41.2 | 36GB |

**关键发现**：
- INT8 量化几乎不损失精度（< 1%），是"无痛加速"的最佳选择
- AWQ 在 INT4 级别明显优于 GPTQ，特别是在代码生成任务上
- 70B 模型在 INT4 下可以在单张 A100（80GB）上运行，而 FP16 需要两张
- 精度损失在复杂推理任务（数学、代码）上比简单问答更明显

### 2.4 量化代码示例

使用 `bitsandbytes` 和 `transformers` 加载 4bit 量化模型：

```python
import torch
from transformers import AutoModelForCausalLM, AutoTokenizer, BitsAndBytesConfig

# 配置 4-bit 量化
bnb_config = BitsAndBytesConfig(
    load_in_4bit=True,                              # 4bit 量化
    bnb_4bit_quant_type="nf4",                      # NormalFloat4 格式
    bnb_4bit_compute_dtype=torch.float16,           # 计算时用 FP16
    bnb_4bit_use_double_quant=True,                 # 双重量化（省更多显存）
)

model = AutoModelForCausalLM.from_pretrained(
    "meta-llama/Meta-Llama-3-70B",
    quantization_config=bnb_config,
    device_map="auto",                              # 自动分配到可用设备
    torch_dtype=torch.float16,
)

tokenizer = AutoTokenizer.from_pretrained("meta-llama/Meta-Llama-3-70B")

# 推理
def generate_response(prompt: str) -> str:
    inputs = tokenizer(prompt, return_tensors="pt").to("cuda")
    with torch.no_grad():
        outputs = model.generate(
            **inputs,
            max_new_tokens=512,
            temperature=0.7,
            do_sample=True,
        )
    return tokenizer.decode(outputs[0], skip_special_tokens=True)
```

使用 AutoGPTQ 加载 GPTQ 量化模型：

```python

import torch

```

## 三、Continuous Batching（连续批处理）

### 3.1 什么是 Continuous Batching？

Continuous Batching（连续批处理）是一种动态的请求调度策略。传统的批处理（Static Batching）需要等待批次中所有请求完成后统一返回，而 Continuous Batching 允许在批次中动态添加和移除序列，一旦某个序列完成生成就立即返回，同时将新请求加入批次。

```
传统批处理:
┌────── 批次 1 ──────┐  ┌────── 批次 2 ──────┐
│ Req_1  Req_2  Req_3 │→ │ Req_4  Req_5  Req_6 │→ ...
│   所有请求必须一起完成  │  │   所有请求必须一起完成  │
└─────────────────────┘  └─────────────────────┘

Continuous Batching:
时间 →
Req_1 ████████░░░░░░░░░░░░░░░░░  ← 完成后立即返回
Req_2 ████████████████░░░░░░░░░
Req_3 ████████████████████████  ← 加入新请求
Req_4                     ████▒▒▒▒░░░░░
Req_5                         ████████████░░
              ↑请求动态插入
```

### 3.2 性能提升

| 场景 | Static Batching | Continuous Batching | 提升幅度 |
|------|----------------|-------------------|---------|
| 短文本（< 128 tokens） | 180 req/s | 450 req/s | 2.5x |
| 中等文本（512 tokens） | 85 req/s | 210 req/s | 2.47x |
| 长文本（2048 tokens） | 32 req/s | 78 req/s | 2.44x |
| 混合长度场景 | 55 req/s | 190 req/s | 3.45x |

混合长度场景下 Continuous Batching 的提升最为显著，这正好符合 Agent 系统的特点——不同 Agent 的上下文长度和生成长度差异巨大。

### 3.3 实现原理

Continuous Batching 的核心是 **KV Cache 的内存管理**。每个序列维护自己的 KV Cache，当序列完成生成时释放其 KV Cache 占用的显存，新请求复用这部分空间。

```python
# Continuous Batching 的简化伪代码
class ContinuousBatchingScheduler:
    def __init__(self, max_batch_size: int):
        self.running_requests = []      # 正在生成的请求
        self.pending_requests = []      # 等待的请求
        self.max_batch_size = max_batch_size
    
    def step(self):
        # 1. 填充新请求到批次中
        while len(self.running_requests) < self.max_batch_size \
              and self.pending_requests:
            req = self.pending_requests.pop(0)
            self._init_kv_cache(req)
            self.running_requests.append(req)
        
        # 2. 对批次中所有请求前进一步（prefill + decode）
        outputs = self.model.forward(
            [r.last_token for r in self.running_requests],
            kv_caches=[r.kv_cache for r in self.running_requests],
        )
        
        # 3. 处理完成的请求
        completed = []
        for i, req in enumerate(self.running_requests):
            req.append_token(outputs.tokens[i])
            if req.is_finished():
                completed.append(req)
                self._free_kv_cache(req)  # 释放显存
        
        # 4. 移除完成的请求
        self.running_requests = [
            r for r in self.running_requests if r not in completed
        ]
        return completed
```

## 四、KV Cache 复用

### 4.1 KV Cache 的概念

KV Cache（Key-Value 缓存）是 Transformer 推理中的中间计算结果缓存。在自回归生成过程中，每生成一个新 token 都需要计算其与所有之前 token 的注意力。但之前 token 的 Key 和 Value 矩阵在每一步的计算结果是一样的，因此可以缓存起来避免重复计算。

**无 KV Cache 的计算**：
```
生成第 N 个 token 时，从头计算 token_1 到 token_N 的注意力
复杂度：O(N² × d) 每一步
```

**有 KV Cache 的计算**：
```
生成第 N 个 token 时，只需要计算 token_N 的 Key 和 Value
之前的 K[1:N-1] 和 V[1:N-1] 从缓存中读取
复杂度：O(N × d) 每一步
```

### 4.2 KV Cache 的复用策略

在 Agent 场景中，KV Cache 复用有几种模式：

**① Prefix Caching（前缀缓存）**
当多个请求共享相同的系统提示词时（例如同一个 Agent 的多次调用），共享前缀的 KV Cache 只需计算一次。

**② Session-level Caching（会话级缓存）**
在多轮对话中，上一轮的 KV Cache 可以在下一轮中复用，只需增量计算新输入的部分。

**③ Cross-request Caching（跨请求缓存）**
对于共享系统提示词的多个独立请求，在 vLLM 等框架中可以自动检测并复用。

### 4.3 性能影响

| 复用策略 | 首 Token 延迟降低 | 总推理时间降低 | 额外显存需求 |
|---------|-----------------|--------------|------------|
| 无复用（基线） | - | - | 无 |
| Prefix Caching | 60-80% | 30-50% | 需要缓存池 |
| Session Caching | 40-60% | 50-70% | 需要持久化 |
| 跨请求复用 | 50-70% | 20-40% | 需要共享缓存 |

## 五、Speculative Decoding（推测解码）

### 5.1 为什么需要 Speculative Decoding？

自回归生成的核心瓶颈是**串行性**——每一步只能生成一个 token，无法并行。现代 GPU 的计算能力远超单 token 解码的需求，因此出现了计算资源的浪费。

Speculative Decoding（推测解码）使用一个**小模型（draft model）**快速草拟多个候选 tokens，再由**大模型（target model）**一次性验证这些 tokens 的质量。

### 5.2 工作原理

```
步骤 1: 草稿模型（如 68M 参数）快速生成 K 个候选 tokens
       "法国的首都是" → 草稿模型: "巴黎是欧洲的文化中心"

步骤 2: 目标模型（如 70B 参数）一次性验证所有 K 个候选
       验证结果: ✓"巴黎" ✓"是" ✓"欧洲" ✗"的文化中心"
       
步骤 3: 接受通过的前 N 个 tokens，丢弃第一个失败之后的
       接受: "巴黎是欧洲"
       退回: "的文化中心"（丢弃）
       目标模型生成下一个正确 token: "最"
```

**关键参数**：
- **草稿长度（K）**：草稿模型每次生成的候选 token 数量
- **接受率**：目标模型接受草稿 tokens 的比例，通常在 0.7-0.9 之间

### 5.3 性能提升

| 配置 | 草稿模型 | 目标模型 | 加速比 | 接受率 |
|------|---------|---------|-------|-------|
| 同架构小模型 | 68M | 7B | 2.1x | 0.82 |
| 同架构小模型 | 68M | 70B | 2.8x | 0.75 |
| 独立草稿模型 | 1.5B | 70B | 1.8x | 0.85 |
| 多草稿并行 | 4×68M | 70B | 3.2x | 0.88 |

加速比随目标模型增大而增加——因为大模型的计算开销更大，而"一次验证 K 个 tokens"的边际成本相对较低。

### 5.4 代码示例

```python
# Speculative Decoding 的简化实现（使用 HuggingFace）
from transformers import AutoModelForCausalLM, AutoTokenizer

# 加载目标模型（生成验证用）
target_model = AutoModelForCausalLM.from_pretrained("meta-llama/Meta-Llama-3-70B")
# 加载草稿模型（快速生成候选）
draft_model = AutoModelForCausalLM.from_pretrained("facebook/opt-125m")

tokenizer = AutoTokenizer.from_pretrained("meta-llama/Meta-Llama-3-70B")

def speculative_decode(prompt: str, k: int = 5) -> str:
    """使用推测解码生成文本"""
    input_ids = tokenizer(prompt, return_tensors="pt").input_ids
    
    # 步骤 1: 草稿模型生成 K 个候选
    draft_outputs = draft_model.generate(
        input_ids,
        max_new_tokens=k,
        do_sample=False,  # 草稿模型使用 greedy decoding
    )
    draft_tokens = draft_outputs[0][len(input_ids[0]):]
    
    # 步骤 2: 目标模型验证候选 tokens
    # 用候选 tokens 扩展输入，计算目标模型的 logits
    extended_input = torch.cat([input_ids, draft_tokens.unsqueeze(0)], dim=-1)
    with torch.no_grad():
        outputs = target_model(extended_input)
    
    # 步骤 3: 逐个验证，找到第一个不接受的 token
    accepted = []
    for i in range(len(draft_tokens)):
        target_logits = outputs.logits[0, len(input_ids[0]) + i - 1]
        target_prob = torch.softmax(target_logits, dim=-1)
        
        if _accept_token(draft_tokens[i], target_prob):
            accepted.append(draft_tokens[i])
        else:
            # 从目标模型采样一个 token 替换
            new_token = torch.multinomial(target_prob, 1)
            accepted.append(new_token)
            break
    
    return tokenizer.decode(accepted)
```

## 六、各加速技术的选型矩阵

| 技术 | 加速效果 | 精度影响 | 实现复杂度 | 硬件要求 | 推荐场景 |
|------|---------|---------|-----------|---------|---------|
| INT8 量化 | 2-4x | 几乎无 | 低 | 任意 GPU | 一切生产部署 |
| INT4 量化 | 3-6x | 轻微 | 低 | 任意 GPU | 显存受限场景 |
| Continuous Batching | 2-3x | 无 | 中（需框架支持） | 高吞吐 GPU | 高并发 API 服务 |
| KV Cache 复用 | 1.5-3x | 无 | 中 | 需缓存管理 | 多轮对话/共享前缀 |
| Speculative Decoding | 1.8-3x | 无 | 高 | 需额外小模型 | 大模型（>30B） |

**工程建议**：
- **优先选择**：INT8 量化 + KV Cache 复用，是最容易实现的组合
- **高并发场景**：Continuous Batching 是必须的，选择 vLLM 或 SGLang 作为推理框架
- **超大规模模型**：Speculative Decoding + INT4 量化，在单卡上运行 70B+ 模型
- **成本敏感场景**：INT4 量化 + 小批次 Continuous Batching

## 关键概念速查

| 术语 | 解释 |
|------|------|
| 量化（Quantization） | 将模型参数从高精度（FP32）映射到低精度（INT8/INT4）以减小模型体积和加速推理 |
| Continuous Batching | 动态批处理策略，允许请求在批次中动态加入和离开，提高 GPU 利用率 |
| KV Cache | 注意力机制中 Key 和 Value 矩阵的缓存，避免重复计算已生成 token 的注意力 |
| Speculative Decoding | 用小模型快速草稿多个候选 tokens，大模型一次性验证，突破自回归串行瓶颈 |
| PTQ | Post-Training Quantization，训练后量化，无需重新训练 |
| AWQ | Activation-aware Weight Quantization，感知激活值的量化方法 |
| NF4 | Normal Float 4，正态分布优化的 4bit 数据格式 |
| Prefix Caching | 前缀缓存，复用共享上下文（如系统提示词）的 KV Cache |
| 首 Token 延迟（TTFT） | 从请求发出到收到第一个 token 的时间，衡量响应感知速度 |
| 吞吐量（Throughput） | 单位时间内生成的 token 数量，衡量系统处理能力 |
