# 22.4 延迟优化

> 延迟优化（Latency Optimization）是在推理速度和质量之间寻找最佳平衡点的工程实践。对于 Agent 系统，延迟不仅影响用户体验，还直接影响 Agent 的执行效率——每一步的延迟都会在工具调用链中被放大。**用户不会注意到节省的 50ms 计算时间，但会注意到 500ms 的响应卡顿**。

---

## 一、延迟的核心指标

### 1.1 TTFT（Time To First Token）

TTFT（首 Token 时间）是指从请求发出到模型生成第一个 token 的时间。它衡量的是用户"感知到"的响应速度——也就是从用户按下回车到看到第一个字出现的时间。

**TTFT 的组成**：

```
TTFT = 网络传输时间 + 请求排队时间 + Prefill 时间 + 第一个 Decode 时间

其中 Prefill 时间是瓶颈：
- Prefill：一次性处理所有输入 tokens（并行计算）
- 复杂度：O(输入长度 × 模型维度) —— 注意力机制 O(n²)
- 输入越长，Prefill 时间越长
```

**TTFT 的典型基准**（以 8B 模型为例）：

| 输入长度 | FP16（A100） | INT8（A100） | FP16（RTX 4090） | 用户感知 |
|---------|------------|------------|----------------|---------|
| 256 | 25ms | 18ms | 35ms | 瞬时 |
| 1,024 | 80ms | 52ms | 120ms | 可接受 |
| 4,096 | 320ms | 200ms | 520ms | 轻微卡顿 |
| 8,192 | 650ms | 400ms | 1,100ms | 明显等待 |
| 32,768 | 3,200ms | 1,900ms | 5,400ms | 不可接受 |

### 1.2 总吞吐（Throughput）

总吞吐（Throughput）是指系统在单位时间内生成的 token 总量，通常以 tokens/s 衡量。它反映的是系统的**整体处理能力**而非单次请求速度。

**通过量的制约因素**：
- GPU 计算能力（FLOPs）
- 显存带宽
- 批处理大小
- KV Cache 管理效率

### 1.3 TTFT vs Throughput 的权衡

```
低并发场景（Agent 的关键路径）：
    TTFT 更重要——用户等待第一个 token 的时间

高并发场景（API 服务）：
    Throughput 更重要——每秒能处理多少请求

Agent 系统两者都需要：
    - 工具调用链中每一步的 TTFT 累加
    - 多个 Agent 并发工作时需要高 Throughput
```

**Trade-off 的具体表现**：

| 优化方向 | TTFT 影响 | Throughput 影响 | 适用场景 |
|---------|-----------|---------------|---------|
| 增大 Batch Size | 增加（排队变长） | 增加 | 高并发 API |
| 减小 Batch Size | 减少 | 减少 | 交互式 Agent |
| 使用 KV Cache 复用 | 大幅减少 | 增加 | 共享前缀场景 |
| 使用量化 | 减少 | 增加 | 通用 |
| 减少输入长度 | 大幅减少 | 小幅增加 | Prompt 优化 |
| 使用流式输出 | 用户感知减少 | 不变 | 所有场景 |

### 1.4 Agent 场景中的延迟放大效应

Agent 与传统聊天的最大区别在于：Agent 的延迟是**累积的**，不是单次的。

```
传统 ChatGPT：
用户 → [推理 500ms] → 回复         总延迟：500ms

Agent 系统：
用户 → [推理 300ms] → 调用工具API → [推理 400ms] → 调用工具API → [推理 500ms] → 回复
  ↑_______________↑___________↑_______________↑___________↑_______________↑
  每步 TTFT      网络延迟      每步 TTFT      网络延迟      最终 TTFT
  总延迟 = 300 + 200 + 400 + 200 + 500 = 1,600ms（不含工具执行时间）
```

每一步的延迟都在叠加。一个 3 步推理的 Agent 系统，如果单步延迟从 500ms 降低到 300ms，总延迟从 1,500ms 降低到 900ms——**节省了 40% 的用户等待时间**。

## 二、流式响应与感知延迟

### 2.1 流式响应的机制

流式响应（Streaming Response）是指模型生成 token 的同时逐步返回结果，而非等待全部生成完成后一次性返回。虽然流式响应不改变总生成时间，但它显著改善了**感知延迟**。

```python
# 流式 vs 非流式对比
from openai import OpenAI
import time

client = OpenAI()

# 非流式（等待全部生成）
start = time.time()
response = client.chat.completions.create(
    model="gpt-4",
    messages=[{"role": "user", "content": "写一篇500字的技术文章"}],
    stream=False,  # 等全部生成完再返回
)
full_text = response.choices[0].message.content
# 用户在 3 秒后看到全部文本

# 流式（逐步返回）
start = time.time()
stream = client.chat.completions.create(
    model="gpt-4",
    messages=[{"role": "user", "content": "写一篇500字的技术文章"}],
    stream=True,  # 实时流式输出
)

collected = []
for chunk in stream:
    if chunk.choices[0].delta.content:
        token = chunk.choices[0].delta.content
        collected.append(token)
        # 立即显示 token，用户在 0.5s 后看到第一个字符
```

### 2.2 感知延迟优化策略

| 策略 | 机制 | 效果 | 实现成本 |
|------|------|------|---------|
| **流式输出** | token 逐字返回 | 大幅改善感知延迟 | 低 |
| **进度指示** | 显示"思考中"或进度条 | 减少用户焦虑 | 极低 |
| **预填充** | 先生成固定前缀（如"好的，"） | 让用户感觉更快 | 低 |
| **渐进式呈现** | 先返回关键结论，再补充细节 | 用户先看到核心内容 | 中 |
| **猜测性呈现** | 根据历史模式预判回复开头 | 零感知延迟 | 高（维护成本） |

### 2.3 流式优化在 Agent 中的实现

Agent 可以采取"先返回计划，再逐步执行"的策略来管理用户预期：

```python
# Agent 的流式执行——逐步展示推理过程
async def streaming_agent_execution(user_query: str):
    """逐步展示 Agent 的推理过程"""
    
    # 阶段 1：展示思考过程（立即返回）
    yield {"type": "thinking", "content": "正在分析你的问题..."}
    await asyncio.sleep(0.1)  # 确保前端看到状态更新
    
    # 阶段 2：生成并展示计划
    plan = await generate_plan(user_query)
    yield {"type": "plan", "content": f"我计划按以下步骤回答:\n{plan}"}
    
    # 阶段 3：逐步执行工具调用
    for step in plan.steps:
        yield {"type": "step_start", "content": f"正在执行: {step.description}"}
        
        # 执行工具
        result = await execute_tool(step.tool, step.params)
        
        # 流式展示工具结果分析
        async for token in stream_analyze_result(result):
            yield {"type": "step_progress", "content": token}
    
    # 阶段 4：最终回复
    yield {"type": "final", "content": "根据以上分析，我的结论是..."}
```

## 三、预填充缓存（Prefill Cache）

### 3.1 预填充的概念

预填充（Prefill）是 Transformer 推理的第一阶段——一次性处理所有输入 tokens，生成第一个输出 token 的 KV Cache。这是推理中最耗时的阶段之一，特别是当输入长度很大时。

**预填充 vs 解码**：
```
预填充阶段（Prefill）：
    输入：所有 tokens [t₁, t₂, ..., tₙ]
    计算：并行计算所有位置的注意力
    特点：计算密集（compute-bound）
    输出：第 n+1 个 token 的 logits + 完整的 KV Cache

解码阶段（Decode）：
    输入：第 n+1 个 token
    计算：单 token 的前向传播 + 注意力查询
    特点：带宽密集（memory-bound）
    输出：第 n+2 个 token 的 logits + 更新的 KV Cache
```

### 3.2 预填充缓存的策略

预填充缓存的核心思想是：**将系统提示词、工具 Schema 等固定输入部分的 KV Cache 预先计算并缓存，避免每次请求都重复计算**。

```python
class PrefillCache:
    """预填充缓存——缓存系统提示词和工具 Schema 的 KV Cache"""
    
    def __init__(self, model, max_cache_size: int = 100):
        self.model = model
        self.cache = {}  # cache_key → precomputed KV Cache
        self.max_cache_size = max_cache_size
    
    def compute_cache_key(self, system_prompt: str, tool_schemas: list[dict]) -> str:
        """生成缓存键"""
        import hashlib
        content = system_prompt + str(tool_schemas)
        return hashlib.md5(content.encode()).hexdigest()
    
    def get_or_compute(self, system_prompt: str, tool_schemas: list[dict]) -> dict:
        """获取或计算预填充缓存"""
        cache_key = self.compute_cache_key(system_prompt, tool_schemas)
        
        if cache_key in self.cache:
            return self.cache[cache_key]
        
        # 计算完整的 KV Cache
        full_input = self._format_input(system_prompt, tool_schemas)
        input_ids = self.model.tokenizer.encode(full_input, return_tensors="pt")
        
        with torch.no_grad():
            outputs = self.model(
                input_ids=input_ids,
                use_cache=True,
                output_hidden_states=False,
            )
        
        kv_cache = outputs.past_key_values
        
        # 缓存并管理大小
        if len(self.cache) >= self.max_cache_size:
            # LRU 淘汰
            oldest_key = next(iter(self.cache))
            del self.cache[oldest_key]
        
        self.cache[cache_key] = {
            "kv_cache": kv_cache,
            "cache_len": len(input_ids[0]),
            "created_at": time.time(),
        }
        
        return self.cache[cache_key]
    
    def format_with_cache(self, user_input: str, cache_entry: dict) -> dict:
        """使用缓存的 KV Cache + 用户输入增量生成"""
        user_ids = self.model.tokenizer.encode(user_input, return_tensors="pt")
        
        # 只需要对用户输入部分做 prefill
        # 系统提示词的 KV Cache 已经缓存
        return {
            "input_ids": user_ids,
            "past_key_values": cache_entry["kv_cache"],
        }
```

### 3.3 预填充缓存的性能收益

| 场景 | 系统提示词长度 | 无缓存 TTFT | 有缓存 TTFT | 节省百分比 |
|------|-------------|------------|------------|----------|
| 通用聊天 | 200 tokens | 20ms | 5ms | 75% |
| RAG Agent | 1,500 tokens | 120ms | 18ms | 85% |
| 复杂工具 Agent | 3,000 tokens | 240ms | 25ms | 90% |
| 多 Agent 协作 | 5,000 tokens | 420ms | 35ms | 92% |

**Agent 场景的缓存收益最高**——因为 Agent 系统通常有冗长的系统提示词（包含工具描述、角色设定、输出格式约束等），这些内容在不同请求间高度共享。

### 3.4 Agent 的缓存友好型系统提示词设计

为了让预填充缓存更高效，系统提示词应该按"静态部分"和"动态部分"组织：

```
Agent 系统提示词结构（缓存友好）：
┌─────────────────────────────────────┐
│  静态部分（可缓存）                    │
│  ─────────────────────────────────    │
│  • 角色设定                           │
│  • 通用行为规则                       │
│  • 工具 Schema 定义                   │
│  • 输出格式约束                       │
│  • 安全限制                           │
├─────────────────────────────────────┤
│  动态部分（不可缓存）                  │
│  ─────────────────────────────────    │
│  • 当前任务上下文                     │
│  • 用户具体指令                       │
│  • 会话级变量                         │
│  • 检索结果摘要                       │
└─────────────────────────────────────┘
```

推荐的分界方法：在系统提示词中插入一个明确的分界标记（如 `---DYNAMIC---`），让推理框架自动识别哪些部分可以缓存。

## 四、延迟优化的全链路分析

### 4.1 延迟分解

一个典型的 Agent 请求的延迟构成：

```
总延迟 = 2,450ms

┌────────────────────┬──────────┬─────────┐
│ 阶段               │ 耗时     │ 占比    │
├────────────────────┼──────────┼─────────┤
│ 网络传输（上行）    │ 50ms     │ 2%      │
│ 请求排队             │ 120ms    │ 5%      │
│ 输入预处理           │ 80ms     │ 3%      │
│ Prefill（首 Token） │ 350ms    │ 14%     │
│ 解码（后续 Tokens） │ 1,200ms  │ 49%     │
│ 工具调用（网络）     │ 450ms    │ 18%     │
│ 后处理               │ 100ms    │ 4%      │
│ 网络传输（下行）    │ 100ms    │ 4%      │
└────────────────────┴──────────┴─────────┘
```

### 4.2 针对性优化策略

根据延迟分解，针对瓶颈进行优化：

| 优化手段 | 影响的阶段 | 预期收益 | 实施优先级 |
|---------|-----------|---------|-----------|
| **Pre-fill缓存** | Prefill | 减少 60-90% | P0 |
| **流式输出** | 用户感知 | 感知延迟减少 50-70% | P0 |
| **量化** | Prefill + Decode | 减少 30-50% | P0 |
| **模型蒸馏/小模型** | 所有阶段 | 减少 50-80% | P1 |
| **Batch Size 优化** | 排队 + Decode | 减少 20-40% | P1 |
| **KV Cache 复用** | Prefill | 减少 40-80% | P1 |
| **Speculative Decoding** | Decode | 减少 30-60% | P2 |
| **网络优化（边缘部署）** | 网络传输 | 减少 50-90% | P2 |
| **工具调用并行化** | 工具调用 | 减少 30-70% | P2 |

### 4.3 延迟预算管理

在 Agent 系统中，应该为每个阶段设置延迟预算：

```python
class LatencyBudget:
    """Agent 系统的延迟预算管理"""
    
    def __init__(self, total_budget_ms: int = 5000):
        self.total_budget_ms = total_budget_ms
        self.budgets = {
            "system_prompt_prefill": 300,    # ms
            "first_tool_call": 800,          # ms
            "tool_execution": 2000,          # ms（外部API）
            "result_analysis": 500,          # ms
            "final_generation": 1000,        # ms
            "buffer": 400,                   # ms（保留余量）
        }
        
        # 验证总预算
        allocated = sum(self.budgets.values())
        assert allocated <= total_budget_ms, \
            f"预算超支: {allocated}ms > {total_budget_ms}ms"
    
    def track(self, phase: str, actual_ms: int):
        """跟踪阶段耗时，超时则告警"""
        budget = self.budgets.get(phase, 0)
        if actual_ms > budget:
            print(f"[WARN] {phase} 超预算: {actual_ms}ms > {budget}ms")
            return True
        return False
    
    def optimize_for_agent(self, num_steps: int):
        """根据 Agent 的步数自动调整预算"""
        # 多步 Agent 的预算分配
        if num_steps > 3:
            # 减少每步的推理预算，增加工具执行预算
            self.budgets["result_analysis"] = 300
            self.budgets["first_tool_call"] = 600
    
    def get_slo_compliance(self, actual_times: dict) -> float:
        """计算 SLO（服务等级目标）合规率"""
        violations = sum(
            1 for phase, time in actual_times.items()
            if time > self.budgets.get(phase, float("inf"))
        )
        total = len(actual_times)
        return (total - violations) / total * 100
```

### 4.4 不同 Agent 模式的延迟特征

| Agent 模式 | TTFT 敏感度 | Throughput 需求 | 主要瓶颈 | 优化重点 |
|-----------|------------|----------------|---------|---------|
| **聊天 Agent** | 高 | 中 | TTFT | Prefill 缓存、流式输出 |
| **RAG Agent** | 中 | 高 | 检索 + 推理 | 检索加速、Prefill 缓存 |
| **代码 Agent** | 中 | 中 | 解码 | Speculative Decoding |
| **多 Agent 协作** | 低 | 极高 | Throughput | Continuous Batching |
| **实时监控 Agent** | 极高 | 低 | TTFT | 小模型 + 预填充 |
| **批处理 Agent** | 极低 | 极高 | Throughput | 大 Batch + 量化 |

## 关键概念速查

| 术语 | 解释 |
|------|------|
| TTFT（Time To First Token） | 首 Token 时间，从请求发出到收到第一个输出 token 的延迟 |
| Throughput（吞吐量） | 系统单位时间内生成的 token 总数，衡量整体处理能力 |
| 流式响应（Streaming） | 逐步返回 token 而非等待全部生成完成的输出方式 |
| 感知延迟（Perceived Latency） | 用户主观感受到的延迟，可通过流式、进度指示等手段改善 |
| 预填充（Prefill） | Transformer 推理中一次性处理所有输入 tokens 的阶段 |
| 解码（Decode） | Transformer 推理中逐 token 生成的自回归阶段 |
| Prefill Cache | 缓存系统提示词等固定输入部分的 KV Cache，避免重复计算 |
| 延迟预算（Latency Budget） | 为每个处理阶段分配的最大可接受延迟时间 |
| SLO（Service Level Objective） | 服务等级目标，如"95% 的请求 TTFT < 500ms" |
| Compute-bound | 计算瓶颈，受 GPU 算力限制（如 Prefill 阶段） |
| Memory-bound | 显存带宽瓶颈，受显存读取速度限制（如 Decode 阶段） |
