# 22.3 成本控制策略

> 成本控制（Cost Control）是在保持 Agent 系统质量的前提下，系统性降低推理开销的方法论。在生产环境中，Agent 的推理成本往往随着用户量和调用频率呈线性甚至超线性增长，不加控制的成本会快速侵蚀业务的经济可行性。**低成本不是目标，性价比才是**。

---

## 一、Agent 系统的成本结构分析

### 1.1 成本的构成要素

Agent 系统的推理成本并非简单的"每 token 价格 × token 数量"。实际成本由多个维度构成：

| 成本维度 | 描述 | 占比（典型） | 控制潜力 |
|---------|------|-----------|---------|
| **输入 Tokens** | 系统提示词 + 用户输入 + 检索结果 + 对话历史 | 40-60% | 高 |
| **输出 Tokens** | 模型生成的回复内容 | 20-30% | 中 |
| **工具调用 Tokens** | 工具描述 Schema + 工具调用输出 | 10-20% | 高 |
| **重试/纠错 Tokens** | 失败后重试、验证性调用 | 5-15% | 低 |
| **验证 Tokens** | Guardrails、自验证循环的额外调用 | 5-20% | 中 |

### 1.2 成本规模估算

假设一个中等规模的 Agent 系统：

```
每日活跃用户：10,000
每用户对话轮次：10 轮
每轮输入 tokens：2,000（含上下文）
每轮输出 tokens：500
API 单价（GPT-4o）：$2.50 / 1M 输入 tokens，$10.00 / 1M 输出 tokens

每日成本计算：
输入：10,000 × 10 × 2,000 = 200M tokens → $500
输出：10,000 × 10 × 500 = 50M tokens → $500
每日总成本：$1,000
每月总成本：$30,000
每年总成本：$365,000
```

这仅是一个中等规模系统的估算。对于大型生产系统，年成本可能轻易突破百万美元。这就是为什么成本控制不是"有更好"，而是"必须有"。

## 二、模型蒸馏（Model Distillation）

### 2.1 蒸馏原理

模型蒸馏（Model Distillation）是指用大模型（Teacher Model）的输出作为训练数据，训练一个小模型（Student Model）来模仿大模型的行为。这样在推理时使用小模型，可以大幅降低成本。

**蒸馏的核心机制**：

```
教师模型（大模型，如 GPT-4）
         │
         ▼
    ┌─────────────┐
    │  Soft Labels  │ ← 概率分布（包含更多信息，如"接近正确答案的错误选项"）
    └─────────────┘
         │
         ▼
学生模型（小模型，如 LLaMA-3-8B）
   损失函数 = α × KL(教师分布 || 学生分布) + (1-α) × CrossEntropy(硬标签)
```

**为什么蒸馏有效？**
- 教师模型的输出概率分布包含了**暗知识（Dark Knowledge）**——它不仅告诉学生"正确答案是什么"，还告诉学生"哪些错误答案更接近正确"
- 例如，对于"北京是中国的什么？"这个问题，教师模型可能输出：首都(0.95)、城市(0.03)、省份(0.01)、国家(0.01)。学生从这个分布中学到"首都"是正确答案，同时"城市"比"省份"更接近——这是硬标签（one-hot）无法传达的信息

### 2.2 蒸馏的策略选择

| 蒸馏策略 | 描述 | 数据需求 | 质量保持 | 适用场景 |
|---------|------|---------|---------|---------|
| **离线蒸馏** | 先用大模型生成一批训练数据，再训练小模型 | 5,000-50,000 样本 | 80-95% | 任务相对固定的场景 |
| **在线蒸馏** | 训练过程中动态让大模型生成数据 | 更多（10 万+） | 85-98% | 任务多变、需要泛化 |
| **自蒸馏** | 同一模型的大版本教小版本 | 无额外需求 | 70-85% | 版本迭代时顺便蒸馏 |
| **知识蒸馏 + RLHF** | 蒸馏后做偏好对齐 | 需偏好数据 | 90-95% | 追求极致质量 |

### 2.3 蒸馏的 ROI 计算

**典型的蒸馏 ROI**：

| 指标 | 教师模型（GPT-4） | 学生模型（蒸馏后 8B） |
|------|-----------------|--------------------|
| 推理成本 | $10/1M tokens | $0.20/1M tokens |
| 延迟 | 800ms | 150ms |
| 质量（MMLU） | 88% | 82% |
| 质量保留率 | 100% | 93% |

**成本节约**：50 倍成本降低，换取 7% 的质量损失。对于大多数 Agent 场景，这个权衡是非常值得的。

### 2.4 蒸馏代码示例

```python
# 知识蒸馏的简化实现
import torch
import torch.nn.functional as F
from transformers import AutoModelForCausalLM, AutoTokenizer

class DistillationTrainer:
    def __init__(
        self,
        teacher_model_name: str = "gpt-4",
        student_model_name: str = "meta-llama/Llama-3.2-3B",
        temperature: float = 4.0,     # 蒸馏温度（越高，软标签越平滑）
        alpha: float = 0.5,           # KL 散度的权重
    ):
        self.teacher = teacher_model_name  # API 调用
        self.student = AutoModelForCausalLM.from_pretrained(student_model_name)
        self.tokenizer = AutoTokenizer.from_pretrained(student_model_name)
        self.temperature = temperature
        self.alpha = alpha
    
    def compute_distillation_loss(self, input_ids, teacher_logits, student_logits):
        """
        计算蒸馏损失
        loss = α * T² * KL(soft_teacher || soft_student) + (1-α) * CE(student, hard_labels)
        """
        # 软标签损失（KL 散度）
        soft_teacher = F.softmax(teacher_logits / self.temperature, dim=-1)
        soft_student = F.log_softmax(student_logits / self.temperature, dim=-1)
        kl_loss = F.kl_div(soft_student, soft_teacher, reduction="batchmean")
        kl_loss *= self.temperature ** 2  # 温度缩放
        
        # 硬标签损失（CrossEntropy，使用真实标签）
        ce_loss = F.cross_entropy(
            student_logits.view(-1, student_logits.size(-1)),
            input_ids.view(-1),
            ignore_index=self.tokenizer.pad_token_id,
        )
        
        return self.alpha * kl_loss + (1 - self.alpha) * ce_loss
```

## 三、缓存命中率优化

### 3.1 缓存策略层级

缓存是最直接有效的成本控制手段——获取一次结果后，后续相同请求无需重新调用模型。Agent 系统中的缓存可以分为多个层级：

```
请求到达
    │
    ├─ L1: 精确匹配缓存 ─── 命中 → 直接返回
    │   完全相同的用户输入
    │
    ├─ L2: 语义缓存 ─────── 命中 → 返回近似匹配结果
    │   语义相似的用户输入
    │
    ├─ L3: 模板缓存 ─────── 命中 → 填充模板后返回
    │   意图相同但参数不同
    │
    └─ 未命中 → 调用模型 → 写入缓存
```

### 3.2 缓存命中率公式与优化目标

**核心指标**：
```
缓存命中率 = 缓存命中的请求数 / 总请求数 × 100%
有效缓存率 = 缓存命中所节约的 tokens / 总 tokens × 100%
```

**为什么需要"有效缓存率"？** 如果命中的都是小请求，未命中的都是大请求，命中率很高但成本节约有限。有效缓存率更准确地反映成本节约效果。

**优化目标的层级**：
```
一般系统：命中率 30-50% → 成本节约 20-35%
优化系统：命中率 50-70% → 成本节约 35-50%
极致系统：命中率 70-90% → 成本节约 50-80%
```

### 3.3 语义缓存

语义缓存（Semantic Caching）基于语义相似度而非字符串精确匹配，能够大幅提升命中率。

```python
from sentence_transformers import SentenceTransformer
import numpy as np
import hashlib

class SemanticCache:
    """语义缓存——基于嵌入相似度的缓存"""
    
    def __init__(self, similarity_threshold: float = 0.92):
        self.encoder = SentenceTransformer("all-MiniLM-L6-v2")  # 768维嵌入
        self.cache: dict[str, dict] = {}        # key_hash → {embedding, response, tokens_saved}
        self.threshold = similarity_threshold
    
    def _hash_key(self, text: str) -> str:
        return hashlib.md5(text.encode()).hexdigest()
    
    def get(self, query: str) -> str | None:
        """查找语义相似的缓存条目"""
        query_emb = self.encoder.encode(query, normalize_embeddings=True)
        
        best_similarity = 0
        best_key = None
        
        for key, entry in self.cache.items():
            similarity = np.dot(query_emb, entry["embedding"])
            if similarity > best_similarity:
                best_similarity = similarity
                best_key = key
        
        if best_similarity >= self.threshold:
            return self.cache[best_key]["response"]
        return None
    
    def set(self, query: str, response: str, tokens_saved: int = 0):
        """存储查询结果"""
        query_emb = self.encoder.encode(query, normalize_embeddings=True)
        key = self._hash_key(query)
        self.cache[key] = {
            "embedding": query_emb,
            "response": response,
            "tokens_saved": tokens_saved,
            "hit_count": 0,
        }
    
    def get_hit_rate(self) -> dict:
        """计算命中率和有效缓存率"""
        total_requests = sum(
            e["hit_count"] + 1 for e in self.cache.values()
        )  # 简化：每个条目至少有1次miss
        total_hits = sum(
            e["hit_count"] for e in self.cache.values()
        )
        total_tokens_saved = sum(
            e["tokens_saved"] * e["hit_count"] for e in self.cache.values()
        )
        
        return {
            "hit_rate": total_hits / total_requests if total_requests > 0 else 0,
            "total_tokens_saved": total_tokens_saved,
            "estimated_cost_saved": total_tokens_saved * 0.00001,  # 假设 $10/1M tokens
        }
```

### 3.4 模板缓存

对于 Agent 的工具调用场景，许多请求本质上是同一模板的不同参数填充：

```python
class TemplateCache:
    """模板缓存——识别意图相同的模式化请求"""
    
    def __init__(self):
        # 缓存结构: {template_hash: {template, response_template}}
        self.cache = {}
    
    def extract_template(self, query: str) -> tuple[str, dict]:
        """将查询拆解为模板 + 参数"""
        # 示例: "对比Python和Java" → 模板: "对比{lang1}和{lang2}", 参数: {lang1: Python, lang2: Java}
        patterns = [
            (r"对比(.+)和(.+)", "对比_{lang1}_和_{lang2}"),
            (r"解释(.+)的原理", "解释_{topic}_的原理"),
            (r"用(.+)实现(.+)", "用_{lang}_实现_{task}"),
        ]
        
        for pattern, template_name in patterns:
            match = re.match(pattern, query)
            if match:
                return template_name, {"groups": match.groups()}
        
        return None, {}
    
    def get(self, query: str) -> str | None:
        template, params = self.extract_template(query)
        if template and template in self.cache:
            # 用参数填充缓存的响应模板
            return self.cache[template].format(**params)
        return None
```

### 3.5 缓存的失效策略

缓存不是永远有效。需要制定合理的失效策略：

| 失效策略 | 机制 | 适用场景 | 缓存命中率影响 |
|---------|------|---------|--------------|
| **TTL（Time To Live）** | 固定时间后自动失效 | 时效性敏感（新闻、天气） | 低（短 TTL）到高（长 TTL） |
| **LRU（Least Recently Used）** | 淘汰最久未使用的 | 请求分布不均匀 | 中 |
| **基于版本号** | 模型升级后全量失效 | 模型版本迭代 | 暂时性下降 |
| **主动失效** | 检测到源数据变更时失效 | RAG 知识库更新 | 保持准确性的代价 |
| **概率性失效** | 以概率 p 随机失效 | 平衡新鲜度和命中率 | 可控 |

### 3.6 缓存命中率优化路线图

```
第一阶段（快速见效，+20-30% 命中率）
    ├── 实现精确匹配缓存（最简单，收益明显）
    └── 设置合理的 TTL（分析请求重复模式）

第二阶段（工程优化，+15-20% 命中率）
    ├── 引入语义缓存（需要嵌入模型）
    ├── 实现模板缓存（需要意图识别）
    └── 监控缓存命中率，设置告警

第三阶段（智能化，+10-20% 命中率）
    ├── 预测性预热（根据历史模式预加载缓存）
    ├── 多级缓存（L1/L2/L3 级联）
    ├── 缓存压缩（减少嵌入存储开销）
    └── A/B 测试不同缓存策略
```

## 四、多模型路由（Multi-Model Routing）

### 4.1 路由的核心思想

多模型路由（Multi-Model Routing）的核心思想是：**不是所有请求都需要大模型处理**。简单任务用小模型，困难任务用大模型，可以在不明显影响用户体验的前提下大幅降低成本。

```
请求分类器
    │
    ├── 简单任务 (50-70%) → 小模型 (1-8B)    成本：$0.05/1M tokens
    │    常见问题、知识查询、简单翻译
    │
    ├── 中等任务 (20-30%) → 中模型 (20-40B)   成本：$0.50/1M tokens
    │    代码编写、逻辑推理、多步指令
    │
    └── 困难任务 (5-15%) → 大模型 (70B+)      成本：$2.00/1M tokens
      复杂推理、创意写作、歧义消解
```

### 4.2 路由策略

| 路由策略 | 机制 | 准确率 | 实现难度 | 额外成本 |
|---------|------|-------|---------|---------|
| **规则路由** | 基于关键词、长度、正则匹配 | 60-70% | 低 | 无 |
| **分类模型路由** | 用小型分类模型（如 BERT）判断难度 | 80-85% | 中 | 极小 |
| **LLM 自路由** | 用 LLM 自我评估是否超出能力范围 | 75-85% | 低 | 一次小模型调用 |
| **级联路由** | 先小模型，失败后升级大模型 | 90-95% | 低 | 失败的 retry 成本 |
| **强化学习路由** | 基于请求特征和反馈动态调整 | 85-95% | 高 | 训练成本 |

### 4.3 级联路由的实现

```python
class CascadeRouter:
    """级联路由——先用小模型，失败或低置信度时升级"""
    
    def __init__(self):
        self.small_model = OllamaAgent("llama3.2:3b")     # 低成本模型
        self.medium_model = OllamaAgent("llama3:8b")       # 中等成本模型
        self.large_model = OllamaAgent("llama3.1:70b")     # 高成本模型
    
    def route(self, query: str, max_attempts: int = 3) -> str:
        """级联路由"""
        models = [
            (self.small_model, 0.7),   # 模型 + 置信度阈值
            (self.medium_model, 0.85),
            (self.large_model, 0.0),    # 最终模型，不设阈值
        ]
        
        for i, (model, threshold) in enumerate(models):
            response = model.generate(query)
            confidence = self._estimate_confidence(response)
            
            if confidence >= threshold:
                return response
            elif i < max_attempts - 1:
                # 低置信度，升级模型并附加上下文
                query = f"前面给出的答案可能不准确，请重新回答: {query}\n之前的回答: {response}"
        
        return response  # 兜底返回
    
    def _estimate_confidence(self, response: str) -> float:
        """估算回答的置信度（基于语言表达）"""
        uncertainty_markers = [
            "不确定", "可能", "也许", "大概", "我认为",
            "I'm not sure", "maybe", "perhaps", "might",
        ]
        
        marker_count = sum(
            1 for marker in uncertainty_markers 
            if marker in response.lower()
        )
        
        # 越多的不确定性标记，置信度越低
        base_confidence = 0.9
        penalty = marker_count * 0.15
        return max(0.1, base_confidence - penalty)
```

### 4.4 多模型路由的 ROI 计算

假设系统每天处理 100 万请求：

| 方案 | 模型分配 | 每请求成本 | 日均成本 | 月均成本 | 质量得分 |
|------|---------|-----------|---------|---------|---------|
| 全量使用大模型 | 100% 大模型 | $0.008 | $8,000 | $240,000 | 95 |
| 全量使用小模型 | 100% 小模型 | $0.0005 | $500 | $15,000 | 70 |
| 路由策略 A | 60%小+25%中+15%大 | $0.0019 | $1,900 | $57,000 | 88 |
| 路由策略 B（级联） | 70%小+20%中+10%大 | $0.0014 | $1,400 | $42,000 | 91 |
| 路由策略 C（RL优化） | 55%小+30%中+15%大 | $0.0025 | $2,500 | $75,000 | 93 |

**结论**：路由策略 B 在成本（$42,000/月 vs $240,000/月）和质量（91 vs 95）之间取得了最佳平衡——**成本降低 82%，质量仅下降 4%**。

## 五、成本控制的计算框架

### 5.1 总成本公式

```
总成本 = Σ(各模型调用量 × 单价)
       + 缓存基础设施成本
       + 路由/分类模型的成本
       - 缓存节约的成本

其中：
  模型单价 = (输入 tokens × 输入单价) + (输出 tokens × 输出单价)
  缓存节约 = 缓存命中量 × 模型单价
```

### 5.2 综合成本控制策略组合

将上述三种策略叠加，形成完整的成本控制体系：

```
┌─────────────────────────────────────────────────────────────┐
│                    成本控制策略组合                           │
│                                                             │
│  请求到达                                                     │
│     │                                                       │
│     ▼                                                       │
│  ┌─────────┐   命中                                          │
│  │  缓存   │ ────────→ 直接返回（成本 = 0）                    │
│  └────┬────┘                                                 │
│       │ 未命中                                               │
│       ▼                                                         │
│  ┌─────────┐                                                  │
│  │  路由   │ ───→ 简单 → 蒸馏后小模型（成本 = $0.05/1M）        │
│  └────┬────┘ ───→ 中等 → 中等模型（成本 = $0.50/1M）           │
│       │      └──→ 困难 → 大模型（成本 = $2.00/1M）             │
│       ▼                                                        │
│  ┌─────────┐                                                  │
│  │  量化   │ ───→ 通过量化进一步降低推理成本                     │
│  └────┬────┘                                                  │
│       ▼                                                        │
│  返回结果 → 写入缓存                                           │
└─────────────────────────────────────────────────────────────┘
```

### 5.3 成本控制的 KPI 监控

建立成本控制的仪表盘，持续监控以下指标：

```python
class CostControlDashboard:
    """成本控制监控仪表盘"""
    
    def __init__(self):
        self.metrics = {
            "daily_requests": 0,
            "cache_hit_rate": 0.0,
            "model_distribution": {},  # {"small": 0.6, "medium": 0.25, "large": 0.15}
            "avg_cost_per_request": 0.0,
            "daily_total_cost": 0.0,
            "quality_score": 0.0,       # 用户满意度或任务成功率
            "cost_per_quality_point": 0.0,  # 每质量分的成本
        }
    
    def compute_efficiency_ratio(self) -> float:
        """计算成本效率比——越低越好"""
        return self.metrics["daily_total_cost"] / max(
            self.metrics["quality_score"], 0.001
        )
    
    def suggest_optimizations(self) -> list[str]:
        """基于当前指标给出优化建议"""
        suggestions = []
        
        if self.metrics["cache_hit_rate"] < 0.3:
            suggestions.append("缓存命中率低于30%，建议：1) 检查TTL设置 2) 引入语义缓存")
        
        if self.metrics["model_distribution"].get("large", 0) > 0.3:
            suggestions.append("大模型使用率超过30%，建议：1) 检查路由阈值 2) 实施级联路由")
        
        small_ratio = self.metrics["model_distribution"].get("small", 0)
        if small_ratio > 0 and self.metrics["quality_score"] > 0.9:
            suggestions.append("质量分超过90%但小模型使用率低，建议：放宽路由条件让更多请求走小模型")
        
        return suggestions
```

## 关键概念速查

| 术语 | 解释 |
|------|------|
| 模型蒸馏（Model Distillation） | 用大模型输出训练小模型，使小模型行为接近大模型，降低推理成本 |
| 缓存命中率 | 缓存命中的请求占总请求的比例 |
| 有效缓存率 | 缓存节约的 token 量占总 token 量的比例 |
| 语义缓存（Semantic Caching） | 基于语义相似度而非精确匹配的缓存策略 |
| 多模型路由（Multi-Model Routing） | 根据任务难度将请求分配给不同大小的模型处理 |
| 级联路由（Cascade Routing） | 先用小模型处理，失败或低置信度时自动升级到大模型 |
| TTL（Time To Live） | 缓存项的有效生存时间 |
| LRU（Least Recently Used） | 淘汰最久未访问的缓存项的算法 |
| 教师模型（Teacher Model） | 蒸馏过程中用于生成训练目标的大模型 |
| 学生模型（Student Model） | 蒸馏过程中被训练的小模型 |
| 暗知识（Dark Knowledge） | 教师模型输出的概率分布中蕴含的软标签信息 |
| 软标签（Soft Label） | 模型输出的完整概率分布，包含错误类别的相对概率信息 |
