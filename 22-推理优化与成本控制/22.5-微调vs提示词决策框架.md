# 22.5 微调 vs 提示词决策框架

> 微调（Fine-tuning）和提示词工程（Prompt Engineering）是优化 LLM 输出的两种根本不同的方法。微调修改模型自身的权重，提示词则在推理时指导模型行为。选择哪种方法决定了成本、质量、维护方式和迭代速度——**这是一个必须基于数据和场景做出的工程决策，而非信仰之争**。

---

## 一、两种方法的本质区别

### 1.1 微调（Fine-tuning）

微调（Fine-tuning）是指在预训练模型的基础上，使用特定领域的数据集对模型参数进行进一步训练。对于 Agent 系统，常见的微调形式包括全参数微调（Full Fine-tuning）和参数高效微调（PEFT，如 LoRA）。

**微调的机制**：
```
预训练模型（基础能力，通用知识）
      │
      ▼
状态：冻结权重 → 在领域数据上继续训练 → 权重更新
      │                                      │
      │   全量微调（Full FT）：所有参数更新    │
      │   LoRA：在原有权重旁加低秩适配器      │
      │   QLoRA：量化 + LoRA 进一步降低显存   │
      │                                      │
      ▼
微调后的模型（领域能力增强，通用知识保留）
```

### 1.2 提示词工程（Prompt Engineering）

提示词工程（Prompt Engineering）见[第 6 章](../06-提示词工程/)，是通过设计输入提示词来引导模型行为，不修改任何模型参数。常见技术包括：

- **指令提示**：明确描述任务和输出格式
- **Few-shot 示例**：在提示词中包含输入-输出示例
- **Chain-of-Thought（CoT）**：引导模型逐步推理
- **角色设定（System Prompt）**：定义模型的行为框架
- **约束式提示**：指定必须/禁止的内容

### 1.3 核心差异对比

| 维度 | 提示词工程 | 微调（Fine-tuning） |
|------|-----------|-------------------|
| **修改对象** | 输入文本 | 模型权重 |
| **成本** | 极低（仅设计成本） | 高（训练费用 + 数据标注） |
| **推理成本** | 增加（few-shot 示例占用 tokens） | 不变（甚至减少，不需要示例） |
| **效果深度** | 浅层引导 | 深层内化 |
| **泛化边界** | 受限于模型已有能力 | 可扩展模型在特定领域的能力 |
| **迭代速度** | 分钟级（修改 prompt 即可） | 小时-天级（需要训练） |
| **维护成本** | 需持续关注 prompt 鲁棒性 | 模型固化后低维护 |
| **可解释性** | 高（prompt 是明文的） | 低（变化分布在权重中） |
| **退化风险** | 无（不影响其他能力） | 有（灾难性遗忘） |

### 2.2 信号判断矩阵

以下 7 个信号可以帮助判断是否需要微调：

| # | 信号 | 含义 | 倾向于... |
|---|------|------|----------|
| 1 | **任务确定性高** | 输出格式固定、规则明确（如 JSON 提取） | 微调 |
| 2 | **输出长度长** | 每次需要生成 1000+ tokens 的结构化内容 | 微调 |
| 3 | **Prompt 中大量 Few-shot 示例** | 示例占据 2000+ tokens，成本高 | 微调 |
| 4 | **风格/语调高度特定** | 需要严格模仿特定角色的说话风格 | 微调 |
| 5 | **任务经常变化** | 需求每周变化，需要快速迭代 | Prompt |
| 6 | **低推理成本要求** | 需要最小化每请求的 token 消耗 | 微调 |
| 7 | **需要模型掌握新知识** | 涉及模型训练数据之后的新知识或私域知识 | 微调 |

**综合决策**：如果 7 个信号中有 4+ 倾向于微调，微调可能是合理的选择。

## 三、LoRA 微调的 ROI 计算

### 3.1 LoRA 简介

LoRA（Low-Rank Adaptation，低秩适配）是一种参数高效微调方法。它不是修改模型的全量参数，而是在原有权重矩阵旁边添加低秩的适配矩阵，仅训练这些适配矩阵。

**LoRA 的原理**：

```
原始权重矩阵 W （shape: d × k）
    │
    ▼
LoRA 分解：
    W' = W + BA
    其中 B（shape: d × r）和 A（shape: r × k），r << min(d, k)
    
    例如 d=4096, k=4096 时：
    原始参数：16,777,216
    LoRA（r=8）：B(4096×8) + A(8×4096) = 65,536
    训练参数减少：99.6%
```

**LoRA 的优势**：
- 可训参数减少 99%+
- 显存需求从全量微调的 200GB+ 降低到 24-48GB
- 多个 LoRA 适配器可以同时加载，动态切换
- 原始模型权重不变，没有灾难性遗忘风险

### 3.2 ROI 计算公式

微调的 ROI（投资回报率）可以从三个维度计算：

```
ROI = (质量提升收益 - 微调成本 - 持续运营成本差) / 持续运营成本差

其中：
质量提升收益 = (微调后准确率 - 基线准确率) × 每次错误损失 × 日均请求数 × 365
微调成本 = 训练算力成本 + 数据标注成本 + 人力成本
持续运营成本差 = (提示词 token 成本 - 微调后 token 成本) × 日均请求数 × 365
```

### 3.3 实际 ROI 计算示例

**场景**：一个企业内部的代码审查 Agent，需要将代码按公司规范标注安全等级。

**基线（纯 Prompt）**：
- 每月 API 调用：100 万次
- 每次消耗 tokens：2,000（含 1,500 的 few-shot 示例和规则描述）
- 每月成本：100万 × 2000 × $0.003/1K = $6,000
- 准确率：88%
- 每次误判损失：$50（人工复核成本）

**LoRA 微调方案**：
- 训练数据：2,000 条标注好的代码审查案例
- 训练成本：$150（H100 约 2 小时）
- 数据标注成本：$2,000（1000 元/人 × 2 天工时）
- 微调后推理成本：每月 100万 × 800（无需 few-shot）× $0.003/1K = $2,400
- 准确率：96%

**ROI 计算**：

```
成本节约：
- 推理成本降低：$6,000 - $2,400 = $3,600/月
- 误判损失降低：(88% - 96%) × 100万 × 50 / 100 = $4,000/月
- 总收益：$7,600/月

微调投入（一次性）：
- 训练 + 标注：$2,150

投资回收期 = $2,150 / $7,600 = 0.28 月 ≈ 9 天
首年 ROI = (7,600 × 12 - 2,150) / 2,150 = 4,140%
```

### 3.4 不同场景的 ROI 基准

| 场景 | 微调成本 | 月节约成本 | 回收期 | 首年 ROI | 推荐度 |
|------|---------|-----------|-------|---------|-------|
| 内部工具（日请求 1K） | $500 | $200 | 2.5 月 | 380% | 谨慎推荐 |
| 客户服务（日请求 10K） | $2,000 | $3,500 | 17 天 | 2,000% | 推荐 |
| 代码审查（日请求 30K） | $2,150 | $7,600 | 9 天 | 4,140% | 强烈推荐 |
| 合规审查（日请求 100K） | $3,000 | $30,000 | 3 天 | 11,900% | 必须微调 |

### 3.5 LoRA 微调的代码示例

```python
# 使用 HuggingFace PEFT 进行 LoRA 微调
from transformers import (
    AutoModelForCausalLM, 
    AutoTokenizer, 
    TrainingArguments,
    Trainer,
)
from peft import (
    LoraConfig,
    get_peft_model,
    TaskType,
    prepare_model_for_kbit_training,
)
from datasets import Dataset
import torch

# 加载基础模型（QLoRA：4bit 量化 + LoRA）
model = AutoModelForCausalLM.from_pretrained(
    "meta-llama/Meta-Llama-3-8B-Instruct",
    torch_dtype=torch.bfloat16,
    device_map="auto",
    load_in_4bit=True,  # QLoRA：4bit 量化
)

# 配置 LoRA
lora_config = LoraConfig(
    task_type=TaskType.CAUSAL_LM,
    r=8,                    # LoRA 秩（rank），越大越强但也越贵
    lora_alpha=16,          # 缩放参数
    lora_dropout=0.1,       # Dropout 防止过拟合
    target_modules=[        # 目标模块（不同模型不同）
        "q_proj", "k_proj", "v_proj", "o_proj",
        "gate_proj", "up_proj", "down_proj",
    ],
    bias="none",
)

# 将模型包装为 PEFT 模型
model = prepare_model_for_kbit_training(model)
peft_model = get_peft_model(model, lora_config)

tokenizer = AutoTokenizer.from_pretrained("meta-llama/Meta-Llama-3-8B-Instruct")
tokenizer.pad_token = tokenizer.eos_token

# 准备训练数据
def format_training_example(example):
    """将训练样本格式化为对话形式"""
    return {
        "text": f"<|system|>{example['system']}</s>"
                f"<|user|>{example['user_input']}</s>"
                f"<|assistant|>{example['target_output']}</s>"
    }

def tokenize_function(examples):
    return tokenizer(
        examples["text"],
        truncation=True,
        max_length=4096,
        padding="max_length",
    )

# 加载数据集
dataset = Dataset.from_json("code_review_training.jsonl")
dataset = dataset.map(format_training_example)
dataset = dataset.map(tokenize_function, batched=True)

# 训练参数
training_args = TrainingArguments(
    output_dir="./lora-code-review",
    per_device_train_batch_size=4,
    gradient_accumulation_steps=4,    # 有效 batch size = 16
    num_train_epochs=3,
    learning_rate=2e-4,
    fp16=True,
    logging_steps=10,
    save_strategy="epoch",
    report_to="none",
)

# 训练
trainer = Trainer(
    model=peft_model,
    args=training_args,
    train_dataset=dataset,
)

trainer.train()

# 保存 LoRA 适配器
peft_model.save_pretrained("./lora-code-review-final")
```

### 3.6 LoRA 适配器的推理使用

```python
# 加载 LoRA 适配器进行推理
from peft import PeftModel

# 加载基础模型 + LoRA 适配器
base_model = AutoModelForCausalLM.from_pretrained(
    "meta-llama/Meta-Llama-3-8B-Instruct",
    device_map="auto",
    torch_dtype=torch.bfloat16,
)

lora_model = PeftModel.from_pretrained(
    base_model,
    "./lora-code-review-final",
)

# 推理——不需要 few-shot 示例
def code_review(code_snippet: str) -> str:
    prompt = f"""<|system|>你是一个代码安全审查专家。请按公司安全规范审查以下代码并返回 JSON 格式结果。

输出格式：
{{"security_level": "safe|warning|danger", "issues": [...], "recommendation": "..."}}</s>

<|user|>请审查以下代码：
```python
{code_snippet}
```</s>

<|assistant|>"""

    inputs = tokenizer(prompt, return_tensors="pt").to("cuda")
    outputs = lora_model.generate(
        **inputs,
        max_new_tokens=256,
        temperature=0.1,  # 低温度，增加确定性
        do_sample=False,
    )
    return tokenizer.decode(outputs[0], skip_special_tokens=True)

## 四、混合策略：Prompt + 微调的组合使用

### 4.1 最常见的错误认知

**"微调是提示词不够好时的最后手段"** —— 这是错误的二分法。在实践中，最有效的策略是两者结合：

| 策略 | 描述 | 适用场景 |
|------|------|---------|
| **纯 Prompt** | 仅使用提示词引导 | 任务简单、快速迭代、数据不足 |
| **纯微调** | 仅使用微调优化 | 任务固定，有充足数据 |
| **Prompt + 微调** | 微调掌握核心能力，Prompt 控制输出细节 | 大多数生产场景 |
| **多 LoRA 路由** | 不同任务使用不同的 LoRA 适配器+统一 Prompt 框架 | 多任务 Agent |

### 4.2 推荐的混合策略

```
┌─────────────────────────────────────────────────────────┐
│                    Agent 系统提示词结构                    │
│                                                         │
│  静态部分：                                               │
│  • Agent 角色设定（始终相同）                              │
│  • 通用行为规则（始终相同）                                │
│  • 安全约束（始终相同）                                   │
│  • 工具调用格式（始终相同）                                │
│  ──────────── 使用 Prompt 定义，无需微调 ─────────────    │
│                                                         │
│  动态部分：                                               │
│  • 当前任务上下文                                         │
│  • 用户具体指令                                           │
│  • 检索结果注入                                           │
│  ──────────── 每次请求动态生成 ─────────────                 │
│                                                         │
│  LoRA 适配器层：                                          │
│  • 代码审查能力（LoRA #1）   ─── 任务特定的领域知识          │
│  • SQL 生成能力（LoRA #2）      通过微调注入                 │
│  • 合规检查能力（LoRA #3）                                 │
│  • ...（根据需求动态切换）                                 │
└─────────────────────────────────────────────────────────┘
```

### 4.3 多 LoRA 路由架构

```python
class LoRARouter:
    """多 LoRA 适配器路由——不同任务使用不同的微调能力"""
    
    def __init__(self, base_model_path: str):
        self.base_model = AutoModelForCausalLM.from_pretrained(
            base_model_path,
            device_map="auto",
            torch_dtype=torch.bfloat16,
        )
        self.tokenizer = AutoTokenizer.from_pretrained(base_model_path)
        self.adapters = {}  # task_name → peft_path
    
    def register_adapter(self, task: str, adapter_path: str):
        """注册 LoRA 适配器"""
        self.adapters[task] = adapter_path
    
    def classify_task(self, user_input: str) -> str:
        """用小模型或规则判断任务类型"""
        # 实现任务分类逻辑
        if "审查" in user_input or "review" in user_input.lower():
            return "code_review"
        elif "SQL" in user_input or "查询" in user_input:
            return "sql_generation"
        elif "合规" in user_input or "compliance" in user_input.lower():
            return "compliance_check"
        return "general"
    
    def generate(self, task: str, prompt: str, **kwargs) -> str:
        """为特定任务加载适配器并生成"""
        if task in self.adapters:
            # 加载对应任务的 LoRA 适配器
            model = PeftModel.from_pretrained(
                self.base_model, self.adapters[task]
            )
        else:
            model = self.base_model
        
        inputs = self.tokenizer(prompt, return_tensors="pt").to("cuda")
        outputs = model.generate(
            **inputs,
            **kwargs,
        )
        return self.tokenizer.decode(outputs[0], skip_special_tokens=True)
```

## 五、实验验证框架

### 5.1 对比实验设计

在决定微调之前，应该进行系统的对比实验：

```python
class FinetuneVsPromptExperiment:
    """微调 vs 提示词对比实验框架"""
    
    def __init__(self, test_dataset: list[dict]):
        """
        test_dataset: [{"input": ..., "expected_output": ...}, ...]
        """
        self.test_data = test_dataset
    
    def evaluate_prompt(self, prompt_template: str) -> dict:
        """评估纯 Prompt 方法的准确率"""
        results = []
        for item in self.test_data:
            prompt = prompt_template.format(input=item["input"])
            output = call_llm(prompt)
            results.append({
                "input": item["input"],
                "expected": item["expected_output"],
                "actual": output,
                "correct": self._check_correctness(output, item["expected_output"]),
            })
        
        accuracy = sum(1 for r in results if r["correct"]) / len(results)
        return {"accuracy": accuracy, "results": results}
    
    def evaluate_finetuned(self, model_path: str) -> dict:
        """评估微调后模型的准确率"""
        model = AutoModelForCausalLM.from_pretrained(model_path)
        results = []
        for item in self.test_data:
            output = model.generate(item["input"])
            results.append({
                "input": item["input"],
                "expected": item["expected_output"],
                "actual": output,
                "correct": self._check_correctness(output, item["expected_output"]),
            })
        
        accuracy = sum(1 for r in results if r["correct"]) / len(results)
        return {"accuracy": accuracy, "results": results}
    
    def compute_roi(self, daily_requests: int, cost_per_1k_tokens: float) -> dict:
        """计算投资回报率"""
        prompt_result = self.evaluate_prompt(self.prompt_template)
        finetune_result = self.evaluate_finetuned(self.finetune_model_path)
        
        # 精度差
        accuracy_gain = finetune_result["accuracy"] - prompt_result["accuracy"]
        
        # token 节约
        prompt_tokens_per_request = 1500  # 含 few-shot
        finetune_tokens_per_request = 500  # 无需 few-shot
        token_saving = (prompt_tokens_per_request - finetune_tokens_per_request) \
                       * daily_requests * 365 / 1000000  # 百万 tokens
        
        return {
            "prompt_accuracy": prompt_result["accuracy"],
            "finetune_accuracy": finetune_result["accuracy"],
            "accuracy_gain": accuracy_gain,
            "estimated_yearly_token_saving": token_saving,
            "recommendation": "微调" if accuracy_gain > 0.05 else "Prompt 已足够",
        }
```

### 5.2 渐进式优化路线

```
第 1 步：Prompt 基线
    ├── 设计 System Prompt + Few-shot 示例
    ├── 在 100+ 测试样本上验证准确率
    └── 记录准确率和 token 消耗

第 2 步：Prompt 优化（如果准确率不够）
    ├── 迭代优化 prompt 结构
    ├── 增加高质量示例
    ├── 引入 CoT 推理链
    └── 记录准确率变化

第 3 步：小规模微调验证（如果 Prompt 优化后仍不达标）
    ├── 准备 200-500 条高质量标注数据
    ├── 用 LoRA（r=4）做小规模微调
    ├── 在验证集上对比 Prompt 效果
    └── 计算 ROI

第 4 步：生产级微调（验证通过后）
    ├── 扩展训练数据到 1000-5000 条
    ├── 用 LoRA（r=8-16）充分训练
    ├── 设置 A/B 测试（Prompt vs 微调）
    └── 监控线上准确率和成本

第 5 步：持续迭代
    ├── 定期评估模型漂移
    ├── 收集错误样本扩充训练集
    └── 每季度或半年重新训练 LoRA 适配器
```

## 关键概念速查

| 术语 | 解释 |
|------|------|
| 微调（Fine-tuning） | 在预训练模型基础上使用领域数据继续训练，修改模型权重的过程 |
| 提示词工程（Prompt Engineering） | 通过设计输入文本引导 LLM 行为，不修改模型参数的技术 |
| LoRA（Low-Rank Adaptation） | 低秩适配，在权重矩阵旁添加可训练的低秩矩阵的参数高效微调方法 |
| QLoRA | 量化 + LoRA，在 4bit 量化模型上执行 LoRA 微调，大幅降低显存需求 |
| PEFT（Parameter-Efficient Fine-Tuning） | 参数高效微调，只训练少量新增参数而不是全量参数的微调方法 |
| 灾难性遗忘（Catastrophic Forgetting） | 微调过程中模型丢失预训练阶段学习到的通用知识 |
| Rank（秩） | LoRA 中低秩矩阵的维度，决定适配器的参数量和学习能力 |
| Few-shot 示例 | 在提示词中包含输入-输出的示例对，引导模型理解任务 |
| ROI（Return on Investment） | 投资回报率，衡量微调投入带来的成本节约和质量提升 |
| A/B 测试 | 将流量分配给不同策略（Prompt vs 微调），对比效果的实验方法 |
