# 16.3 12-Factor Agents 方法论

> "12-Factor App"（Heroku, 2011）是现代 SaaS 应用的架构纲领。受其启发，12-Factor Agents 将同样的"关注分离、约定优先、环境可移植"的设计哲学迁移到 Agent 工程领域，形成一套构建可维护、可观测、可演化的 Agent 系统的架构原则。

---

## 一、背景：从 12-Factor App 到 12-Factor Agents

### 为什么要借鉴 12-Factor App？

原始的 **12-Factor App**（12要素应用）由 Heroku 联合创始人 Adam Wiggins 提出，旨在解决 SaaS 应用开发中的共性问题——环境不一致、配置泄露、日志不可靠、依赖管理混乱。这套方法论深刻影响了云原生应用的设计。

Agent 工程在 2024-2026 年间遇到了类似的挑战：

| 挑战 | 传统表现 | Agent 工程中的表现 |
|------|---------|------------------|
| 环境不一致 | "在我的机器上能运行" | "在我的 Prompt 里能工作，换一个模型就不行" |
| 配置泄露 | 密钥硬编码在代码中 | 系统提示词混杂业务逻辑和工具定义 |
| 依赖管理 | 缺少 requirements.txt | 工具定义散落在多个 Prompt 中，难以审计 |
| 日志不可靠 | print vs logging | Agent 的思考过程被丢弃，无法回溯错误 |
| 可移植性差 | 绑定特定云服务 | Agent 绑定特定模型和工具实现 |

**12-Factor Agents** 正是为了解决 Agent 工程中的这些"成长痛"而提出的一套架构原则。

---

## 二、12 个 Factor 详解

### Factor 1: 工具即结构化输出（Tools as Structured Outputs）

> Agent 使用的每个工具都应定义为结构化 Schema（JSON Schema / Zod / Pydantic），而非自然语言描述。

**核心思想**：传统 Agent 开发中，工具定义常以自然语言写在系统提示词中：

```python
# 糟糕的做法：工具定义混在 Prompt 中
SYSTEM_PROMPT = """
你有一个函数叫 search_products，用于搜索产品。
参数有 query（字符串）、category（字符串，可选）、page（整数，默认1）。
"""
```

12-Factor Agents 的做法是将工具定义提升为一等公民——结构化、可校验、可版本管理：

```python
# 好的做法：工具定义为结构化 Schema
TOOL_REGISTRY = {
    "search_products": {
        "description": "搜索产品目录",
        "parameters": {
            "query": {"type": "string", "description": "搜索关键词"},
            "category": {"type": "string", "description": "产品分类（可选）"},
            "page": {"type": "integer", "default": 1, "description": "页码"}
        },
        "required": ["query"],
        "handler": search_products_impl  # 解耦：实现与定义分离
    }
}
```

**好处**：
- 工具定义可自动验证（参数类型、必填检查）
- 工具列表可被序列化、版本化、跨 Agent 共享
- 工具 Schema 可直接用于 LLM 的 Function Calling API（无需模型"理解"自然语言描述）
- 工具调用日志可结构化记录（便于调试和分析）

**工程实践**：把所有工具定义放在一个中心化的 `tools/` 目录下，每个工具一个文件，类似 REST API 的端点定义。

### Factor 2: 小而专注（Small & Focused）

> 每个 Agent 只做一件事并把它做好。通过组合多个"小而专注"的 Agent 构建复杂系统，而非构建一个"全能"Agent。

**核心思想**：一个 Agent 拥有的工具越多、知识越杂，它的行为就越不可预测。这类似于微服务架构中"单一职责原则"——每个服务只负责一个业务能力。

```python
# 错误做法：一个 Agent 拥有 50 个工具
super_agent = Agent(
    name="全能Agent",
    tools=[search, analyze, write, email, calendar, billing, 
           inventory, shipping, refund, report, ...]  # 50+ 工具
)
# 问题：工具选择准确率随工具数量增加而下降，容易选错工具

# 正确做法：多个专注的 Agent
search_agent = Agent(name="搜索专家", tools=[search_catalog, search_knowledge])
analysis_agent = Agent(name="分析专家", tools=[analyze_data, generate_chart])
write_agent = Agent(name="内容专家", tools=[write_article, edit_text])

# 通过 Orchestrator（见 16.1 节）协调这些 "小而专注" 的 Agent
orchestrator = Orchestrator(agents=[search_agent, analysis_agent, write_agent])
```

**好处**：
- 每个 Agent 的工具选择空间小，准确率更高
- Agent 的 Prompt 更简洁，系统提示词可针对特定领域优化
- 独立开发、独立测试、独立部署
- 一个 Agent 的失败不会拖垮整个系统

**适用范围**：当一个 Agent 的工具数量超过 15-20 个时，就应该考虑拆分。

### Factor 3: 拥有你的上下文窗口（Own Your Context Window）

> 显式管理上下文的每个部分——系统提示词、工具定义、对话历史、检索内容——而不是让它们无序地堆积在上下文窗口中。

**核心思想**：Agent 的上下文窗口是最宝贵的计算资源。12-Factor Agents 要求明确规划上下文窗口中的"每一寸空间"：

```
┌──────────────────────────────────────────────────────┐
│                  上下文窗口布局                         │
├──────────────────────────────────────────────────────┤
│ 永久区域（不被轮换）                                    │
│   - 系统提示词（角色定义、行为规则）       ~1K tokens   │
│   - 工具 Schema（结构化描述）             ~2K tokens   │
├──────────────────────────────────────────────────────┤
│ 会话区域（滑动窗口）                                   │
│   - 最近的 N 轮对话历史                   ~4K tokens   │
│   - 当前任务上下文                        ~2K tokens   │
├──────────────────────────────────────────────────────┤
│ 临时区域（按需注入）                                   │
│   - RAG 检索结果                          ~4K tokens   │
│   - 工具执行结果                          ~2K tokens   │
├──────────────────────────────────────────────────────┤
│ 保留空间（防止意外溢出）                  ~2K tokens   │
├──────────────────────────────────────────────────────┤
│ 总计可用窗口                              ~16K/200K   │
└──────────────────────────────────────────────────────┘
```

```python
class ContextManager:
    """显式管理上下文窗口的各个区域"""
    
    def __init__(self, max_tokens=128000):
        self.max_tokens = max_tokens
        self.reserved = 2000  # 保留空间
        self.system_prompt = None
        self.tool_definitions = None
        self.conversation_history = []
        self.retrieved_context = None
    
    def build_context(self, user_input):
        # 计算各部分大小，确保不超出窗口
        used = self.used_tokens()
        
        if used > self.max_tokens - self.reserved:
            # 压缩策略：优先裁剪对话历史
            self.trim_history()
        
        return assemble(self.system_prompt, self.tool_definitions,
                       self.conversation_history, self.retrieved_context,
                       user_input)
    
    def used_tokens(self):
        return sum(len(tokenize(part)) for part in [
            self.system_prompt, self.tool_definitions,
            str(self.conversation_history), self.retrieved_context
        ])
```

**好处**：
- 避免关键信息（如系统提示词）被后续内容"挤出"上下文窗口
- 可预测的 Token 消耗（便于估算成本和延迟）
- 上下文压缩策略可控（优先保留什么、优先丢弃什么）

### Factor 4: 显式依赖声明（Explicit Dependency Declaration）

> Agent 所依赖的工具、模型、知识库和外部服务必须显式声明，而非隐式依赖。

**核心思想**：类似于 `package.json` 或 `requirements.txt`，每个 Agent 都应该有依赖清单。

```yaml
# agent-manifest.yaml - Agent 依赖声明文件
agent:
  name: customer-support-agent
  version: 2.1.0
  
dependencies:
  models:
    - provider: anthropic
      model: claude-sonnet-4
      min_temperature: 0.0
      max_temperature: 0.7
  
  tools:
    - name: search_knowledge_base
      version: ">=1.0.0"
      required: true
    - name: get_order_status
      version: "~2.0.0"
      required: true
    - name: send_email
      version: "^3.1.0"
      required: false
  
  knowledge_bases:
    - name: product_catalog
      index_type: vector
      embedding_model: voyage-3-large
      refresh_policy: hourly
  
  external_services:
    - name: payment_gateway
      endpoint: "https://api.payment.com/v3"
      timeout_ms: 5000
      retry_policy: "exponential_backoff"
```

**好处**：
- 启动时验证所有依赖是否可用，避免运行时"缺少工具"错误
- 依赖版本管理，避免工具接口变更导致 Agent 行为异常
- 新团队成员可以通过清单快速理解 Agent 的能力边界

### Factor 5: 可观测性优先（Observability First）

> Agent 的每个步骤——思考、行动、观察——都必须被记录和可追溯。

**核心思想**：Agent 的非确定性行为使得传统的"加个 print"调试方式完全不够用。需要系统化的可观测性基础设施。

```python
class ObservableAgent:
    def step(self, thought, action, observation):
        # 每条执行记录都包含完整轨迹
        trace = {
            "timestamp": datetime.now().isoformat(),
            "step_id": uuid4(),
            "parent_step_id": self.current_step_id,
            "thought": thought,      # LLM 的推理过程
            "action": {               # 工具调用的完整细节
                "tool": action.tool_name,
                "parameters": action.parameters,
                "start_time": action.start_time,
                "end_time": action.end_time,
                "latency_ms": action.latency_ms
            },
            "observation": {          # 工具返回的完整结果
                "raw": observation.raw_output,
                "truncated": observation.was_truncated,
                "error": observation.error
            },
            "token_usage": {          # 每一步的成本信息
                "input_tokens": self.last_input_tokens,
                "output_tokens": self.last_output_tokens,
                "cost": self.last_cost
            }
        }
        
        # 写入可观测性存储（不仅记录日志）
        self.trace_store.append(trace)
        
        # 同时发送到实时监控
        self.monitor.emit("agent_step", trace)
        
        return trace.step_id
```

**必须记录的三类数据**：

| 数据类型 | 内容 | 用途 |
|---------|------|------|
| **Trace（轨迹）** | 完整的 Thought-Action-Observation 序列 | 调试、回放、审计 |
| **Metrics（指标）** | 延迟、Token 消耗、成功率、重试次数 | 性能监控、成本控制 |
| **Logs（日志）** | 非结构化的运行事件 | 异常排查 |

### Factor 6: 配置与代码分离（Config-Code Separation）

> 所有可变参数（模型选择、温度、API 端点、超时时间）通过配置注入，而非硬编码。

**核心思想**：Agent 的行为应通过配置文件调整，不需要修改代码。

```python
# 糟糕的做法：配置硬编码在代码中
def create_agent():
    return Agent(
        model="claude-sonnet-4-20250514",  # 硬编码
        temperature=0.3,                    # 硬编码
        max_tokens=4096,                    # 硬编码
        tools=[search_kb, get_weather]      # 硬编码
    )

# 好的做法：配置从外部注入
def create_agent(config):
    # config 来自 YAML / 环境变量 / 配置中心
    model = config.get("agent.model", "claude-sonnet-4")
    temperature = config.get("agent.temperature", 0.3)
    tool_names = config.get("agent.tools", [])
    tools = [TOOL_REGISTRY[name] for name in tool_names]
    
    return Agent(model=model, temperature=temperature, tools=tools)
```

**适用场景**：
- 同一 Agent 在不同环境（dev/staging/prod）使用不同模型
- A/B 测试不同温度和 Prompt 版本
- 动态调整 Agent 行为而不需要重新部署

### Factor 7: 可复现执行（Reproducible Execution）

> 给定相同的输入和相同的历史轨迹，Agent 应产生相同的输出。

**核心思想**：Agent 的非确定性（LLM 采样随机性、工具调用的外部不确定性）使得"重现 Bug"成为挑战。需要通过技术手段保证某种程度的确定性。

```python
def reproducible_generate(prompt, seed=42, temperature=0.0):
    """确定性的 LLM 调用"""
    return llm.generate(
        prompt=prompt,
        temperature=temperature,
        seed=seed,       # 控制随机种子（API 支持时）
        top_p=0.1        # 减少采样随机性
    )

# 注意：设置 temperature=0 并不保证 100% 确定性
# 不同 API 实现、GPU 浮点运算差异都可能导致微小变化
# 最佳实践是同时保持：temperature=0 + 相同模型版本 + 相同 API provider
```

**可复现执行的层级**：

| 层级 | 方法 | 确定性程度 |
|------|------|-----------|
| L0 | temperature=0 + seed固定 | 通常可达（但依赖 API provider） |
| L1 | + 记录完整输入（Prompt + 历史） | 保证输入相同 |
| L2 | + 固定模型版本（如 claude-sonnet-4-20250514） | 避免模型更新影响 |
| L3 | + Mock 工具调用 | 消除外部不确定性 |

### Factor 8: 优雅降级（Graceful Degradation）

> 当模型不可用、工具调用失败、检索无结果时，Agent 应能提供部分功能，而非直接崩溃。

**核心思想**：Agent 系统涉及多个外部依赖（LLM API、工具 API、数据库），任何一个都可能宕机。优雅降级是生产就绪 Agent 的基本要求。

```python
class DegradableAgent:
    def search_with_degradation(self, query):
        try:
            # 首选：向量搜索（最准确）
            return self.vector_search(query)
        except VectorDBUnavailable:
            # 降级1：关键词搜索（准确度降低，但可用）
            self.monitor.warn("VectorDB 不可用，降级到关键词搜索")
            return self.keyword_search(query)
        except KeywordSearchUnavailable:
            # 降级2：返回缓存结果（可能过时）
            self.monitor.warn("关键词搜索不可用，使用缓存")
            return self.cache.get(query)
        except:
            # 最终：告知用户能力受限
            return {"status": "degraded", "message": "搜索服务暂时不可用，请稍后再试"}
```

**降级策略分类**：

| 故障类型 | 降级方案 | 影响 |
|---------|---------|------|
| LLM API 不可用 | 切到备用模型 / 使用缓存 | 质量可能下降 |
| 知识库不可用 | 仅使用模型参数知识 | 事实准确性下降 |
| 工具调用失败 | 跳过该步骤 / 使用默认值 | 功能受限 |
| 全部不可用 | 返回友好错误信息 | 无法提供服务 |

### Factor 9: 批处理与流式（Batch & Streaming）

> 支持两种执行模式：批处理（离线批量任务）和流式（实时逐步骤输出）。

**核心思想**：同一 Agent 架构应同时支持同步和异步、批处理和流式执行。

```python
class StreamingCapableAgent:
    async def stream_execute(self, task):
        """流式执行：每步完成时立即输出"""
        async for step in self._plan(task):
            yield {"type": "plan", "content": step}
        
        async for step_result in self._execute(task):
            yield {"type": "step", "step": step_result}
            
            if step_result.tool_call:
                yield {"type": "tool_call", 
                       "tool": step_result.tool_call.name,
                       "parameters": step_result.tool_call.parameters}
        
        yield {"type": "complete", "result": self.final_answer}
    
    async def batch_execute(self, tasks):
        """批量执行：并行处理多个任务"""
        async with asyncio.TaskGroup() as group:
            tasks = [group.create_task(self.execute(task)) for task in tasks]
        
        return [task.result() for task in tasks]
```

### Factor 10: 一次写入，多次读取（Write Once, Read Many）

> Agent 的 Prompt、工具定义和知识库内容应当按照"一次写入，多次读取"的原则管理，避免同一个 Prompt 内容被复制粘贴到多个地方。

**核心思想**：将 Agent 的"知识"和"行为规则"与"执行逻辑"分离，类似于数据库的规范化和 DRY 原则。

```python
# 知识/规则库（写一次）
KNOWLEDGE_LIBRARY = {
    "refund_policy": "30天内可退换，需要原始收据...",
    "shipping_policy": "满99元包邮，标准配送3-5个工作日...",
    "return_process": "退货流程：1. 登录账户 2. 选择订单 3. ..."
}

# Prompt 模板（读多次）
PROMPT_TEMPLATES = {
    "customer_support": """
    作为客服 Agent，请遵循以下规则：
    
    退换货政策：{refund_policy}
    物流政策：{shipping_policy}
    退货流程：{return_process}
    
    用户问题：{user_question}
    """
}

# 使用时才动态组装
def build_prompt(template_name, **kwargs):
    template = PROMPT_TEMPLATES[template_name]
    knowledge = {k: KNOWLEDGE_LIBRARY[k] for k in extract_refs(template)}
    return template.format(**knowledge, **kwargs)
```

### Factor 11: 安全边界（Security Boundaries）

> Agent 的每个能力（工具调用、知识访问、网络请求）都应有明确的安全边界和权限控制。

**核心思想**：Agent 本质上是一个"自动执行代码的系统"，每个工具有一定的权限。必须用工程手段确保 Agent 不会超出预期权限行事。

```python
class SecureToolExecutor:
    def __init__(self):
        self.permissions = {
            "search_knowledge_base": {"read": True, "write": False},
            "update_order": {"read": True, "write": True, "role": "admin"},
            "send_email": {"read": False, "write": True, "rate_limit": 10}
        }
    
    def check_permission(self, tool_name, operation, user_role):
        perms = self.permissions.get(tool_name, {})
        
        if not perms.get(operation, False):
            raise PermissionError(f"工具 {tool_name} 没有 {operation} 权限")
        
        if "role" in perms and user_role not in perms["role"]:
            raise PermissionError(f"角色 {user_role} 无权使用 {tool_name}")
        
        if "rate_limit" in perms:
            self.check_rate_limit(tool_name, perms["rate_limit"])
        
        return True
```

### Factor 12: 持续演进（Continuous Evolution）

> Agent 的行为应当可以通过 A/B 测试、Prompt 版本管理、监控反馈持续改进，而非"写完就冻结"。

**核心思想**：由于 LLM 的行为具有非确定性，Agent 系统需要持续的实验和优化循环。

```python
class EvolutionPipeline:
    def __init__(self):
        self.prompt_registry = PromptRegistry()
        self.experiment_tracker = ExperimentTracker()
    
    def deploy_experiment(self, agent_id, new_prompt_version, traffic_percent=10):
        """将新版本 Prompt 以一定流量比例上线"""
        experiment_id = uuid4()
        self.experiment_tracker.start(
            id=experiment_id,
            agent=agent_id,
            version=new_prompt_version,
            traffic_percent=traffic_percent
        )
        
        # 路由：新版本处理 traffic_percent% 的请求
        router.add_rule(
            match={"agent": agent_id},
            route={"version": "control", "weight": 100 - traffic_percent},
            route={"version": new_prompt_version, "weight": traffic_percent}
        )
        
        return experiment_id
    
    def analyze_experiment(self, experiment_id):
        """分析实验效果"""
        metrics = self.experiment_tracker.get_metrics(experiment_id)
        
        if metrics["success_rate"] > metrics["control_success_rate"] * 1.05:
            # 显著提升 → 全量上线
            return {"decision": "promote", "confidence": 0.95}
        elif metrics["success_rate"] < metrics["control_success_rate"] * 0.95:
            # 显著下降 → 回滚
            return {"decision": "rollback", "confidence": 0.95}
        else:
            # 无显著差异 → 继续实验
            return {"decision": "continue", "sample_size_needed": ...}
```

## 三、12 个 Factor 的分组

| 分组 | Factor | 核心关注点 |
|------|--------|-----------|
| **结构** | 1. 工具即结构化输出 | 工具定义的工程化 |
| | 2. 小而专注 | Agent 粒度和职责 |
| | 3. 拥有你的上下文窗口 | Token 资源管理 |
| | 4. 显式依赖声明 | 依赖的可追溯性 |
| **运维** | 5. 可观测性优先 | 调试和监控 |
| | 6. 配置与代码分离 | 环境适应性 |
