# 16.1 HuggingFace 六种基础模式

> HuggingFace 在其官方指南中总结了六种 LLM Agent 的基础设计模式，构成了构建更复杂 Agent 系统的积木。这六种模式覆盖了从单步调用到多步协作的完整光谱，是 Agent 架构的"设计模式入门"。

---

## 一、概述

在 Agent 工程中，**设计模式（Design Pattern）** 指的是被反复验证的、可复用的架构解决方案。HuggingFace 提出的六种基础模式并非互斥关系——实际生产系统中的 Agent 通常组合使用多种模式。

这六种模式可以按照"控制流复杂度"排列为以下光谱：

```
单一 Prompt         链式调用           并行分支          动态路由          编排协调
    │                  │                  │                 │                 │
    ▼                  ▼                  ▼                 ▼                 ▼
Context-Augmentation → Prompt-Chaining → Parallelization → Routing → Orchestrator-Workers
                                                                                    │
                                                                                    ▼
                                                                           Evaluator-Optimizer
                                                                           评价反馈闭环
```

下面逐一深入解析每种模式。

---

## 二、Evaluator-Optimizer（评估-优化循环）

### 一句话定位

> 一个 LLM 生成输出，另一个 LLM（或同一 LLM 的验证模式）评估输出质量并反馈，形成迭代优化循环。

### 工作原理

```
┌────────────────────────────────────────────────────┐
│                   输入任务                            │
│                        │                             │
│                        ▼                             │
│  ┌──────────────┐     ┌──────────────┐              │
│  │  Generator    │────→│  Evaluator   │              │
│  │  (生成回答)   │     │  (评估质量)   │              │
│  └──────────────┘     └──────┬───────┘              │
│                              │                        │
│                     ┌────────┴────────┐               │
│                     ▼                 ▼               │
│                  通过               未通过             │
│                     │                 │               │
│                     ▼                 │               │
│                 输出结果    ┌──────────┴──────┐       │
│                            │  反馈 + 优化      │       │
│                            │  重新生成        │       │
│                            └──────────┬──────┘       │
│                                       │               │
│                                       ▼               │
│                                 Generator            │
│                              (带着反馈再次生成)        │
└────────────────────────────────────────────────────┘
```

### 核心机制

Evaluator（评估器）的反馈包含三个层级：

```python
def evaluator_optimizer_loop(task, max_iterations=3):
    context = task
    
    for i in range(max_iterations):
        # 生成阶段
        response = llm.generate(
            prompt=f"请完成以下任务：\n{context}",
            temperature=0.7  # 生成需要一定多样性
        )
        
        # 评估阶段
        evaluation = llm.generate(
            prompt=f"""请评估以下回答的质量：
            
            任务：{task}
            回答：{response}
            
            评估维度：
            1. 准确性：是否有事实错误？
            2. 完整性：是否遗漏了重要方面？
            3. 清晰度：是否易于理解？
            
            返回 JSON：
            {{"pass": true/false, "score": 1-10, 
              "issues": ["问题1", "问题2"],
              "suggestions": ["改进建议1"]}}
            """,
            temperature=0.0  # 评估用低温，增加确定性
        )
        
        if evaluation.pass and evaluation.score >= 7:
            return response
        
        # 带着反馈重新生成
        context = f"""
        原始任务：{task}
        
        上一次的回答：{response}
        
        评估反馈：
        - 问题：{evaluation.issues}
        - 建议：{evaluation.suggestions}
        
        请根据上述反馈改进回答。
        """
    
    # 达到最大迭代次数，返回最佳结果
    return response
```

### 适用场景

- **内容生成质量要求高**：文案撰写、报告生成、代码审查
- **需要多轮打磨**：学术写作、翻译润色、营销文案
- **安全敏感场景**：评估回答是否包含有害内容（见第 17 章内容安全）

### 优缺点

| 优点 | 缺点 |
|------|------|
| 输出质量显著高于单次生成 | 延迟增加 2-3 倍 |
| 可发现单次生成的盲点 | Token 消耗翻倍 |
| 评估标准可定制（准确性、安全性、风格） | 评估器本身可能误判 |
| 支持渐进式优化 | 需要精心设计评估提示词 |

## 三、Context-Augmentation（上下文增强）

### 一句话定位

> 在执行 LLM 调用之前，通过检索外部数据来丰富输入上下文，使模型获得回答问题所需的精确知识。

### 工作原理

```
                  用户输入
                     │
                     ▼
              ┌──────────────┐
              │ 输入分析器    │
              │ - 识别意图    │
              │ - 提取关键实体 │
              │ - 确定查询类型│
              └──────┬───────┘
                     │
              ┌──────┴───────┐
              │ 知识检索     │
              │ - 向量数据库 │
              │ - 搜索引擎   │
              │ - API 调用   │
              │ - 文档查询   │
              └──────┬───────┘
                     │
                     ▼
             ┌──────────────┐
             │ 上下文组装   │
             │ 用户输入      │
             │ + 检索结果    │
             │ + 系统提示    │
             │ + 历史对话    │
             └──────┬───────┘
                    │
                    ▼
              ┌──────────────┐
              │   LLM 推理    │
              │ (带增强上下文)│
              └──────┬───────┘
                     │
                     ▼
                最终输出
```

### RAG（检索增强生成）是实现 Context-Augmentation 最主流的工程范式

```python
def context_augmented_generation(query, knowledge_base):
    # 步骤1：分析查询意图
    intent = analyze_query_intent(query)
    
    # 步骤2：根据意图构造检索查询
    if intent == "factual":
        search_query = extract_entities(query)
    elif intent == "code":
        search_query = f"{query} code example"
    else:
        search_query = query
    
    # 步骤3：从知识库检索相关内容
    retrieved_docs = knowledge_base.search(search_query, top_k=5)
    
    # 步骤4：组装增强上下文
    augmented_prompt = f"""
    用户问题：{query}
    
    参考信息：
    {format_documents(retrieved_docs)}
    
    请基于上述参考信息回答问题。如果参考信息不足，
    请明确说明"我无法从已有信息中找到答案"。
    """
    
    # 步骤5：用增强上下文生成回答
    return llm.generate(augmented_prompt, temperature=0.3)
```

### 适用场景

- **知识密集型问答**：需要精确事实的 RAG 系统（详见第 8 章 RAG）
- **私有知识库查询**：企业内部文档、产品文档
- **实时信息需求**：需要从搜索引擎获取最新信息
- **多模态场景**：检索图片、表格、代码等非文本信息

### 优缺点

| 优点 | 缺点 |
|------|------|
| 大幅降低事实性幻觉 | 检索质量直接影响最终结果 |
| 可访问私有和实时知识 | 需要维护知识库 |
| 无需重新训练模型 | 上下文窗口有限制 |
| 知识可随时更新 | 检索延迟增加了响应时间 |

## 四、Prompt-Chaining（提示链）

### 一句话定位

> 将一个复杂任务拆解为多个顺序执行的子任务，每个子任务的输出作为下一个子任务的输入。

### 工作原理

```
任务：撰写一份产品分析报告

    步骤1：信息收集
    Prompt: "搜索关于产品X的市场信息"
          │
          ▼
    步骤2：数据分析
    Prompt: "基于以下信息，提取关键指标：{步骤1的输出}"
          │
          ▼
    步骤3：竞品对比
    Prompt: "将产品X的关键指标与竞品对比：{步骤2的输出}"
          │
          ▼
    步骤4：报告撰写
    Prompt: "基于上述分析撰写报告：{步骤3的输出}"
          │
          ▼
    步骤5：格式润色
    Prompt: "将报告格式化为Markdown：{步骤4的输出}"
          │
          ▼
        最终报告
```

### 链式设计的两种模式

**线性链**：每个步骤严格顺序执行。

```python
def linear_chain(user_request):
    # 链式传递：每一站的输出是下一站的输入
    step1 = llm.generate(f"解析用户请求的结构：{user_request}")
    step2 = llm.generate(f"根据结构生成大纲：{step1}")
    step3 = llm.generate(f"根据大纲撰写内容：{step2}")
    step4 = llm.generate(f"检查并改进内容：{step3}")
    return step4
```

**带门控的链**：每个步骤后增加验证节点，决定继续或重试。

```python
def gated_chain(user_request):
    plan = llm.generate(f"制定执行计划：{user_request}")
    gate = verify_plan(plan)  # 门控验证
    
    if not gate["pass"]:
        return retry_with_feedback(user_request, gate["issues"])
    
    result = execute_plan(plan)
    return result
```

### 适用场景

- **多步骤复杂任务**：需要先分析、再规划、再执行的流水线
- **输出需要逐步精炼**：从大纲到草稿到最终版本
- **各步骤依赖前置结果**：像传统软件工程中的 pipeline

### 优缺点

| 优点 | 缺点 |
|------|------|
| 将复杂问题分解为可管理的子任务 | 错误会沿链传播（级联效应） |
| 每步可单独调试和优化 | 延迟与链长度成正比 |
| 可在任意步骤插入验证或人工审核 | 前序步骤的失败可能导致后续步骤全部无效 |
| 流程透明，可观测性强 | 链的拓扑结构固定，不够灵活 |

## 五、Parallelization（并行化）

### 一句话定位

> 将同一个任务拆分为多个 LLM 调用并行执行，再通过聚合策略合并结果。

### 工作原理

```
                    ┌─────────────────────┐
                    │      用户输入        │
                    │  "分析这篇论文"      │
                    └──────────┬──────────┘
                               │
             ┌─────────────────┼─────────────────┐
             ▼                 ▼                  ▼
      ┌────────────┐   ┌────────────┐   ┌────────────┐
      │ 摘要提取    │   │ 核心论点    │   │ 实验评估    │
      │ (temperature │   │ (temperature │   │ (temperature │
      │  = 0.3)    │   │  = 0.5)    │   │  = 0.2)    │
      └──────┬─────┘   └──────┬─────┘   └──────┬─────┘
             │                 │                 │
             └─────────────────┼─────────────────┘
                               │
                               ▼
                    ┌─────────────────────┐
                    │     结果聚合器       │
                    │ - 去重               │
                    │ - 合并               │
                    │ - 排序               │
                    │ - 格式统一           │
                    └─────────────────────┘
                               │
                               ▼
                    ┌─────────────────────┐
                    │     最终输出          │
                    └─────────────────────┘
```

### 两种并行策略

**① 扇出聚合（Fan-out Aggregation）**：同一任务分给多个 LLM 独立处理，然后聚合结果。

```python
def parallel_fanout(task, num_workers=5):
    # 扇出：并行执行多个独立的 LLM 调用
    responses = parallel_map(
        lambda _: llm.generate(
            f"请完成以下任务：{task}\n请从不同角度分析。",
            temperature=0.8  # 高温度确保多样性
        ),
        range(num_workers)
    )
    
    # 聚合：合并多个视角的结果
    aggregated = llm.generate(
        f"""以下是多个分析者对同一任务的回答：
        
        任务：{task}
        
        各个回答：
        {format_responses(responses)}
        
        请综合这些回答，生成一份全面、没有矛盾的最终分析。
        """,
        temperature=0.2
    )
    
    return aggregated
```

**② 分工并行（Division of Labor）**：将任务拆分为不同子任务，每个子任务由专门的 LLM 调用处理。

```python
def parallel_division_of_labor(paper_text):
    # 每个子任务并行执行
    futures = {
        "summary": llm.generate_async(f"提取论文摘要：{paper_text[:2000]}"),
        "methodology": llm.generate_async(f"分析研究方法：{paper_text}"),
        "results": llm.generate_async(f"提取实验结果：{paper_text}"),
        "limitations": llm.generate_async(f"分析论文局限性：{paper_text}"),
    }
    
    # 等待所有并行任务完成
    results = await_all(futures)
    
    # 合并为结构化报告
    return format_sections(results)
```

### 适用场景

- **需要多角度分析**：从多个维度分析同一个问题
- **高吞吐量要求**：独立子任务无需等待彼此
- **投票/共识机制**：多个模型各自推理后投票决定最终答案（见 14.3 节 Self-Consistency）

### 优缺点

| 优点 | 缺点 |
|------|------|
| 显著降低延迟（子任务并行） | Token 消耗倍增 |
| 多角度覆盖减少盲点 | 聚合逻辑可能出错 |
| 天然支持容错（个别失败不影响整体） | 需要管理并发资源 |
| 容易扩展（增加更多 worker） | 并行数量受 API 速率限制 |

## 六、Routing（路由）

### 一句话定位

> 根据输入内容的特点，动态选择最合适的处理路径或专用模型，实现"分而治之"。

### 工作原理

```
                  ┌──────────────────┐
                  │    用户输入       │
                  └────────┬─────────┘
                           │
                    ┌──────┴──────┐
                    │  路由分类器   │
                    │  (小而快的   │
                    │   LLM 或    │
                    │   传统分类器) │
                    └──────┬──────┘
                           │
           ┌───────────────┼───────────────┐
           │               │               │
           ▼               ▼               ▼
    ┌────────────┐  ┌────────────┐  ┌────────────┐
    │ 技术问题    │  │ 客服咨询    │  │ 创意写作    │
    │ → 技术模型  │  │ → 客服模型  │  │ → 创意模型  │
    │ → 技术RAG  │  │ → 知识库   │  │ → 高温度   │
    └────────────┘  └────────────┘  └────────────┘
           │               │               │
           ▼               ▼               ▼
     技术回答           客服回答         创意文本
```

### 路由的三种实现层次

**层次一：Prompt 路由**——用同一个模型，不同系统提示词

```python
def prompt_routing(user_input):
    # 先用分类器判断意图
    category = llm.generate(
        f"""将以下用户输入分类为 ['tech', 'support', 'creative'] 之一：
        {user_input}"""
    )
    
    # 根据类别使用不同的系统提示词
    system_prompts = {
        "tech": "你是一名技术专家，请精确、专业地回答技术问题。",
        "support": "你是一名客服代表，请耐心、友好地解决用户问题。",
        "creative": "你是一名创意写手，请发挥想象力进行创作。"
    }
    
    return llm.generate(
        system=system_prompts[category],
        user=user_input
    )
```

**层次二：模型路由**——不同复杂度的问题路由到不同规模的模型

```python
def model_routing(user_input):
    complexity = estimate_complexity(user_input)
    
    if complexity == "simple":
        # 简单问题用轻量模型（低成本、低延迟）
        model = "claude-3-haiku"
    elif complexity == "medium":
        model = "claude-3-sonnet"  
    elif complexity == "hard":
        model = "claude-3-opus"  # 复杂问题用最强模型
    
    return llm.generate(model=model, user=user_input)
```

**层次三：工具路由**——不同意图触发不同的工具链

### 适用场景

- **多领域客服系统**：技术问题 vs 账户问题 vs 退货问题
- **成本优化**：简单问题用小模型，复杂问题用大模型
- **多模态输入**：图像输入路由到视觉模型，文本输入路由到语言模型

### 优缺点

| 优点 | 缺点 |
|------|------|
| 每个分支可深度优化 | 路由分类器本身可能出错 |
| 显著降低成本（用小模型处理简单问题） | 需要维护多条处理路径 |
| 降低延迟（简单请求快速响应） | 类别过多时分发质量下降 |
| 支持 A/B 测试和渐进式迁移 | 冷启动时需要标注数据训练分类器 |

## 七、Orchestrator-Workers（编排器-工作器）

### 一句话定位

> 一个"编排器（Orchestrator）"LLM 负责分解任务、调度和协调多个"工作器（Worker）"LLM 或工具，形成动态的任务执行网络。

### 工作原理

```
                          ┌──────────────────┐
                          │     Orchestrator  │
                          │   (编排器 LLM)    │
                          │                   │
                          │  - 任务分解        │
                          │  - Worker 调度     │
                          │  - 结果合并        │
                          │  - 异常处理        │
                          └──┬──┬──┬──┬──┬───┘
                             │  │  │  │  │
              ┌──────────────┘  │  │  │  └──────────────┐
              │                 │  │  │                 │
              ▼                 ▼  ▼  ▼                 ▼
      ┌──────────────┐  ┌──────────────────────┐  ┌──────────────┐
      │  Worker 1     │  │  Worker 2 ... N       │  │  工具调用     │
      │  (LLM + RAG)  │  │  (专用 LLM Agent)    │  │  (API/SDK)   │
      │  搜索信息      │  │  子任务处理           │  │  执行操作     │
      └──────┬───────┘  └──────────┬───────────┘  └──────┬───────┘
             │                     │                      │
             └─────────────────────┼──────────────────────┘
                                   │
                                   ▼
                          ┌──────────────────┐
                          │   结果汇总         │
                          │   (Orchestrator   │
                          │    最终整合)      │
                          └──────────────────┘
```

### 核心机制

Orchestrator 在每一次执行周期中的决策逻辑：

```python
class Orchestrator:
    def __init__(self):
        self.workers = {
            "research": ResearchWorker(),
            "code": CodeWorker(),
            "write": WriteWorker(),
            "analyze": AnalyzeWorker()
        }
    
    def execute(self, task):
        # 阶段1：任务分析
        plan = self.task_decomposition(task)
        # 输出：[{"worker": "research", "goal": "搜索X的市场规模"},
        #        {"worker": "analyze", "goal": "分析竞品Y的财报"},
        #        {"worker": "write", "goal": "撰写竞争分析段落"}]
        
        # 阶段2：并行调度 Worker
        results = {}
        for step in plan:
            worker = self.workers[step["worker"]]
            results[step["goal"]] = worker.execute(step["goal"])
        
        # 阶段3：结果整合
        final_output = self.synthesize(task, results)
        
        # 阶段4：质量检查
        if self.quality_check(final_output):
            return final_output
        else:
            return self.revise(task, results, final_output)
```

### 与 Routing 和 Chaining 的区别

| 维度 | Routing | Chaining | Orchestrator-Workers |
|------|---------|----------|---------------------|
| 控制流 | 一次性分发 | 线性序列 | 动态图 |
| 灵活性 | 固定分支 | 固定顺序 | 运行时决定 |
| 复杂度 | 低 | 中 | 高 |
| 适用任务 | 分类清晰 | 步骤确定 | 动态变化 |

### 适用场景

- **复杂研究任务**：需要搜索、分析、写作、验证的多步骤流程
- **软件开发 Agent**：需求分析→编码→测试→部署的全流程
- **多源信息融合**：需要同时查询多个数据源并整合

### 优缺点

| 优点 | 缺点 |
|------|------|
| 最灵活的模式，适应动态任务 | 架构复杂度最高 |
| Worker 可独立复用和测试 | Orchestrator 的决策质量是关键瓶颈 |
| 天然支持并行和容错 | 调试困难（多 Agent 交互的非线性） |
| 水平扩展能力强 | 需要处理 Worker 间的冲突和冗余 |
| 每个 Worker 可针对性优化 | Token 消耗大（Orchestrator 需要完整的全局上下文） |

## 八、六种模式的组合使用

在实际生产系统中，这六种模式很少单独使用。常见的组合模式包括：

```
            Routing
               │
        ┌──────┴──────┐
        ▼              ▼
  Prompt-Chain    Orchestrator-Workers
  带 Evaluator       │
  在每个门控点    ┌──┴──┐
               ▼      ▼
          Worker1  Worker2
               │      │
               ▼      ▼
          Context-Augmentation
          (每个 Worker 都做 RAG)
```

**经典组合示例：智能客服系统**
1. **Routing**：判断是"技术咨询"还是"账户问题"
2. **Context-Augmentation**：从知识库检索相关信息
3. **Orchestrator-Workers**：需要时协调多个子系统的 Worker
4. **Evaluator-Optimizer**：最终输出前进行质量检查

## 关键概念速查

| 术语 | 解释 |
|------|------|
| Design Pattern | 被反复验证的、可复用的架构解决方案 |
| Evaluator-Optimizer | 生成-评估-优化的迭代循环模式 |
| Context-Augmentation | 检索外部数据增强输入上下文的模式（RAG 的核心） |
| Prompt-Chaining | 串行执行多个子任务的链式模式 |
| Parallelization | 并行执行多个 LLM 调用并聚合结果的模式 |
| Routing | 根据输入特征动态选择处理路径的模式 |
| Orchestrator-Workers | 编排器调度多个专用 Worker 的协作模式 |
| Fan-out Aggregation | 同一任务分发给多个 Worker 并行处理再聚合 |
| Division of Labor | 将任务拆分为不同的子任务由不同 Worker 处理 |
| Gated Chain | 在链的节点加入验证门控的增强链式模式 |
