# 16.2 Agent Patterns 九种进阶模式

> 从 ReAct 到 STORM，学术和工业界在过去两年中涌现了大量 Agent 设计模式。本章聚焦 9 种经过论文验证的进阶模式，按从基础到前沿的顺序组织。每种模式都解决了一个特定的核心问题：如何让 Agent 更系统地思考、更可靠地执行、更有效地学习。

---

## 一、ReAct（Reasoning + Acting）

> 交叉执行推理轨迹和工具调用，让思考引导行动、行动反馈驱动进一步思考。

### 一句话定位

ReAct（Yao et al., 2022）是 Agent 领域最具影响力的基础模式，它将"推理（Reasoning）"和"行动（Acting，即工具调用）"交织在同一个循环中，使 Agent 能够通过推理决定下一步行动，并通过行动结果修正推理方向。

### 工作原理

```
                    Thought: 用户想知道天气，我
                    需要查询天气API
                         │
                         ▼
                    Action: call get_weather(city="北京")
                         │
                         ▼
                    Observation: {"temp": 25, "condition": "晴"}
                         │
                         ▼
                    Thought: 北京今天25度，晴天。
                    用户穿单衣就行。还需要什么信息吗？
                         │
                         ▼
                    Action: call nothing (完成)
                         │
                         ▼
                    Final Answer: 北京今天25度，晴天...
```

ReAct 的核心循环是 **Thought → Action → Observation → Thought** 的四步螺旋：

```python
def react_agent(task, tools, max_steps=10):
    """ReAct 模式的标准实现"""
    context = [f"任务：{task}"]
    
    for step in range(max_steps):
        # 步骤1：思考（推理当前状态和下一步行动）
        thought = llm.generate(f"""
        根据当前进度，思考下一步需要做什么。
        
        历史记录：
        {format_history(context)}
        
        可用工具：
        {format_tools(tools)}
        
        输出格式：Thought: <推理过程>
        """)
        
        # 步骤2：行动（执行工具调用）
        action = llm.generate(f"""
        基于以上思考，选择要执行的动作。
        
        只输出一个工具调用：Action: tool_name(param1, param2)
        """)
        
        # 步骤3：观察（获取工具执行结果）
        observation = execute_tool(action)
        
        # 将这一轮添加到上下文
        context.append(f"Thought: {thought}")
        context.append(f"Action: {action}")
        context.append(f"Observation: {observation}")
        
        # 判断是否完成
        if is_complete(thought):
            break
    
    # 步骤4：生成最终回答
    return llm.generate(f"基于以下信息回答用户问题：\n{format_history(context)}")
```

### ReAct 与 CoT 的关键区别

**CoT（Chain-of-Thought，思维链）** 只在推理层面工作，不与环境交互。ReAct 则是在 CoT 的基础上增加了"行动"维度——模型不仅"思考"，还"做事"，并从"做事的结果"中获得新的信息来更新思考。

**类比**：CoT 是一个人在脑海中推演；ReAct 是这个人边尝试边思考。

### 适用场景

- **需要外部信息的多步骤任务**：如查询天气、搜索信息（详见 Ch02.1）
- **工具调用密集型场景**：Agent 需要动态决定何时调用什么工具
- **推理路径与工具结果相互依赖**：模型需要根据工具返回的信息调整推理方向

### 优缺点

| 优点 | 缺点 |
|------|------|
| 推理透明（每一步 Thought 都可审计） | 长轨迹中可能"遗忘"早期信息 |
| 灵活适应动态变化的环境 | 工具错误的观察会误导推理 |
| 理论基础扎实，论文验证充分 | 需要在 Prompt 中精心构造示例 |
| 可扩展（可叠加 Reflection、Memory 等） | 每个步骤都需要 LLM 调用，Token 消耗大 |

## 二、Reflection（自我反思）

> Agent 在生成输出后，对自己生成的内容进行批判性审查，识别并修正错误。

### 一句话定位

Reflection 是让 Agent 扮演"批评家"角色审查自己输出的模式。它利用了 LLM 的"非对称能力"——模型辨别错误的能力通常强于避免错误的能力。

### 工作原理

```
              ┌─────────────────────┐
              │   Agent 初次生成      │
              │  (温度 0.7)          │
              └──────────┬──────────┘
                         │
                         ▼
              ┌─────────────────────┐
              │   自我反思阶段        │
              │                     │
              │    "检查以下回答，    │
              │    找出事实错误、     │
              │    逻辑漏洞和         │
              │    不严谨的表述。"    │
              └──────────┬──────────┘
                         │
              ┌──────────┴──────────┐
              ▼                     ▼
          无错误                 发现错误
              │                     │
              ▼                     ▼
          直接输出          ┌─────────────────┐
                          │  修正阶段        │
                          │  "根据以下反馈   │
                          │   改进你的回答：" │
                          └────────┬────────┘
                                   │
                                   ▼
                          ┌─────────────────┐
                          │  最终输出（修正后）│
                          └─────────────────┘
```

### 与 Evaluator-Optimizer 的区别

虽然"审查-修正"机制相似，但 Reflection 和 Evaluator-Optimizer 有以下区别：

| 维度 | Reflection | Evaluator-Optimizer |
|------|-----------|-------------------|
| 审查者 | 同一 LLM | 可以是不同 LLM |
| 语境 | 通常与 Agent 主循环融合 | 作为独立模块 |
| 粒度 | 通常只做一轮反思 | 可多轮迭代优化 |
| 典型应用 | Agent 单步输出检查 | 内容生成质量提升 |

```python
def reflection_generation(prompt):
    # 第一轮：初始生成
    initial_response = llm.generate(prompt, temperature=0.7)
    
    # 第二轮：自我反思
    reflection = llm.generate(f"""
    你是一名严格的评审专家。请审查以下回答，找出所有问题。
    
    原始问题：{prompt}
    
    回答：{initial_response}
    
    请列出：
    1. 事实错误（如有）
    2. 逻辑漏洞（如有）
    3. 遗漏的关键点（如有）
    4. 表述不准确之处（如有）
    """, temperature=0.0)
    
    # 第三轮：反思后修正
    if has_issues(reflection):
        final_response = llm.generate(f"""
        原始问题：{prompt}
        
        你的初版回答：{initial_response}
        
        审查发现的问题：{reflection}
        
        请根据上述反馈改进回答。保持正确部分不变，仅修正有问题的部分。
        """, temperature=0.3)
        return final_response
    
    return initial_response
```

### 适用场景

- **事实准确性要求高**：需要"二次检查"的知识问答
- **代码生成**：生成后检查 bug 和安全隐患
- **长文本生成**：检查逻辑一致性和结构完整性

## 三、Plan & Solve（计划与求解）

> 先制定完整的执行计划，再严格按照计划逐步执行，避免执行过程中的目标漂移。

### 一句话定位

Plan & Solve（Wang et al., 2023）将"计划"和"执行"两个阶段明确分离：Agent 先用推理能力制定一个完整的、分步骤的计划，然后再按计划执行。这种"先想清楚再做"的方式避免了边做边想可能导致的路径偏离。

### 工作原理

```
                      ┌─────────────────────┐
                      │      阶段1：计划      │
                      │                     │
                      │  "分析用户需求，      │
                      │  制定分步骤执行计划。" │
                      │                     │
                      │  计划：               │
                      │  1. 查询用户账户信息  │
                      │  2. 检查订单状态     │
                      │  3. 计算退款金额     │
                      │  4. 调用退款API     │
                      └──────────┬──────────┘
                                 │
                                 ▼
                      ┌─────────────────────┐
                      │      阶段2：执行      │
                      │                     │
                      │  Step 1: 查询账户    │
                      │  Result: 账户正常    │
                      │                     │
                      │  Step 2: 检查订单    │
                      │  Result: 已发货      │
                      │                     │
                      │  Step 3: 计算退款   │
                      │  ...                │
                      └──────────┬──────────┘
                                 │
                                 ▼
                      ┌─────────────────────┐
                      │      最终输出         │
                      │  汇总所有步骤结果     │
                      └─────────────────────┘
```

### 核心代码模式

```python
def plan_and_solve(task):
    # 阶段1：制定计划
    plan = llm.generate(f"""
    任务：{task}
    
    请制定一个详细的分步骤执行计划。每一步应清晰定义要做什么。
    
    输出格式（JSON）：
    {{
        "steps": [
            {{"id": 1, "action": "具体操作", "expected_outcome": "预期结果"}},
            ...
        ],
        "dependencies": "步骤间的依赖关系说明"
    }}
    """)
    
    # 阶段2：严格执行计划
    results = []
    for step in plan.steps:
        result = execute_step(step)
        results.append(result)
        
        # 检查结果是否符合预期
        if not check_result(step, result):
            # 可选：计划修正（Plan & Solve 的变体）
            plan = revise_plan(plan, step, result)
    
    # 阶段3：汇总输出
    return synthesize_results(task, plan, results)
```

### 适用场景

- **数学和逻辑推理题**：先理解题目，制定解题步骤，再逐步计算
- **复杂操作流程**：需要按步骤执行的多阶段任务
- **任务编排**：子任务之间有明确的依赖关系

### 优缺点

| 优点 | 缺点 |
|------|------|
| 执行路径清晰可预测 | 计划可能过于理想化，与实时情况不符 |
| 避免目标漂移 | 缺乏灵活性——严格执行计划可能错过更好的路径 |
| 中间结果可审计 | 计划阶段消耗额外 Token |
| 执行阶段可并行化（无依赖的步骤） | 计划制定依赖模型的推理能力 |

### Plan & Solve vs ReAct

Plan & Solve 是"先计划后执行"，ReAct 是"边想边做"。前者更适合步骤明确的任务，后者更适合需要动态探索的任务。

## 四、Reflexion（带长期记忆的反思）

> 在 Reflection 的基础上增加长期记忆（Episodic Memory），让 Agent 能从过去的成功和失败中学习。

### 一句话定位

Reflexion（Shinn et al., 2023）解决了"同一个错误反复犯"的问题。它将每次执行过程的"反思结果"持久化存储，在后续任务中作为上下文注入，实现从经验中持续学习的效果。详见 Ch02.4 和 14.3 节。

### 工作原理

```
   Episode N                     Episode N+1                     Episode N+2
       │                              │                              │
       ▼                              ▼                              ▼
  ┌──────────┐                  ┌──────────┐                  ┌──────────┐
  │ 执行任务  │                  │ 执行任务  │                  │ 执行任务  │
  └────┬─────┘                  └────┬─────┘                  └────┬─────┘
       │                              │                              │
       ▼                              ▼                              ▼
  ┌──────────┐                  ┌──────────┐                  ┌──────────┐
  │ 自我反思  │                  │ 自我反思  │                  │ 自我反思  │
  └────┬─────┘                  └────┬─────┘                  └────┬─────┘
       │                              │                              │
       ▼                              ▼                              ▼
  ┌──────────────┐             ┌──────────────┐             ┌──────────────┐
  │ 反思笔记存储   │             │ 反思笔记存储   │             │ 反思笔记存储   │
  │ "工具B容易   │             │ "工具B容易    │             │ "工具B容易    │
  │  参数错误"   │             │  参数错误"    │             │  参数错误"    │
  └──────────────┘             │ "查询前应先   │             │ "查询前应先   │
        │                      │  验证权限"    │             │  验证权限"    │
        │                      └──────────────┘             │ "数据格式需   │
        │                            │                      │  统一转换"   │
        │                            │                      └──────────────┘
        │                            │                            │
        └────────────────────────────┼────────────────────────────┘
                                     │
                                     ▼
                          ┌──────────────────────────┐
                          │  每次执行前注入所有反思笔记 │
                          │  "以下是你过去学到的教训： " │
                          └──────────────────────────┘
```

### 核心实现

```python
class ReflexionAgent:
    def __init__(self):
        self.reflexion_memory = []  # 长期记忆：反思笔记列表
    
    def execute(self, task):
        # 注入长期记忆
        memory_context = self.format_memory()
        
        # 执行任务（使用 ReAct 循环）
        result = self.react_with_context(task, memory_context)
        
        # 事后反思
        reflection = self.reflect(task, result)
        
        if reflection["has_lesson"]:
            # 将反思存入长期记忆
            self.reflexion_memory.append({
                "lesson": reflection["lesson"],
                "trigger": reflection["trigger_condition"],
                "task_type": reflection["task_type"]
            })
        
        return result
    
    def format_memory(self):
        if not self.reflexion_memory:
            return "暂无历史经验。"
        
        formatted = "以下是你过去的经验教训，请在本次任务中注意避免：\n"
        for i, memo in enumerate(self.reflexion_memory[-10:]):  # 取最近10条
            formatted += f"{i+1}. {memo['lesson']}\n"
        return formatted
```

### 适用场景

- **需要持续改进的 Agent**：同一个 Agent 反复执行类似任务
- **高重复性错误场景**：工具调用参数错误、格式错误等容易重复犯的错误
- **需要个性化适应的系统**：Agent 应该越用越好

## 五、LLM Compiler（LLM 编译器）

> 将任务编译为并行执行的 DAG（有向无环图），通过依赖分析最大化并行度。

### 一句话定位

LLM Compiler（Liu et al., 2024）借鉴了传统编译器的思想：将 Agent 的任务分析为相互依赖的"计算单元"，通过识别出无依赖关系的单元进行并行执行，显著降低端到端延迟。

### 工作原理

```
  传统 Agent 执行（串行）：
  
  A → B → C → D → E → F → G
  总时间 = 7 个时间单位
  
  
  LLM Compiler 执行（并行）：
  
     A
     │
     ▼
  ┌──B──┐
  │     │
  ▼     ▼
  C     D
  │     │
  └──┬──┘
     ▼
     E
     │
     ▼
  ┌──F──┐
  │     │
  ▼     ▼
  G     H
  │     │
  └──┬──┘
     ▼
     I
  总时间 = 5 个时间单位（减少 29%）
```

### 核心机制

```python
def llm_compiler_execute(task):
    # 阶段1：编译——将任务分解为依赖图
    dag = compile_to_dag(task)
    # 输出：{"nodes": {1: "搜索资料", 2: "分析数据", 3: "撰写报告"},
    #        "edges": {1→2, 1→3}}   分析依赖2依赖于搜索1，撰写3依赖于搜索1
    
    # 阶段2：拓扑排序 + 并行调度
    sorted_layers = topological_sort_layers(dag)
    # 输出：[{1}, {2, 3}]    第1层只有节点1，第2层2和3可以并行
    
    results = {}
    for layer in sorted_layers:
        # 同一层内的节点并行执行
        parallel_results = {}
        for node_id in layer:
            deps = {dep: results[dep] for dep in dag.dependencies(node_id)}
            parallel_results[node_id] = execute_async(node_id, deps)
        
        # 等待本层所有节点完成
        results.update(wait_all(parallel_results))
    
    # 阶段3：从最终的输出节点获取结果
    return results[dag.output_node]
```

### 适用场景

- **延迟敏感的应用**：需要最小化从请求到响应的总时间
- **多依赖的复杂任务**：子任务之间有复杂的依赖关系
- **批处理场景**：大批量独立任务的处理

### 优缺点

| 优点 | 缺点 |
|------|------|
| 最大化并行度，降低延迟 | 编译阶段有额外开销 |
| 依赖关系清晰，执行可预测 | DAG 可能过于复杂难以管理 |
| 天然支持容错（一个分支失败不影响其他） | 不是所有任务都可以被编译为 DAG |
| 每个节点的调用可独立缓存 | 需要处理动态依赖（执行时才知道的依赖） |

## 六、REWOO（ReAct Without Observation Ordering）

> 将推理与执行分离，先集中推理出所有需要的工具调用，再统一执行所有工具调用，最后基于所有观察结果综合推理。

### 一句话定位

REWOO（Xu et al., 2023）旨在解决 ReAct 模式的一个效率问题：ReAct 中推理和工具调用交替进行，工具调用的延迟会阻塞推理进程。REWOO 将两者分离——先推理再执行再推理，减少交互次数。

### 工作原理

```
  ReAct（交替式）：
  Thought1 → Action1 → [等待API] → Observation1 → Thought2 → Action2 → ...
  每次工具调用都需等待，推理也被打断
  
  REWOO（分离式）：
  
    阶段1：集中推理（零工具调用）
    Thought1: 我需要查天气和空气质量
    Thought2: 先查北京的天气
    Thought3: 再查北京的空气质量
    Thought4: 最后综合回答
    
    阶段2：集中执行（无推理）
    Action1: get_weather("北京")    ← 并行执行！
    Action2: get_aqi("北京")        ← 并行执行！
    
    阶段3：综合推理（基于所有观察）
    Observation1: {"temp": 25}
    Observation2: {"aqi": 42}
    Thought5: 北京今天25度，空气质量优
    Final Answer: ...
```

### 核心实现

```python
def rewoo_execute(task, tools):
    # 阶段1：推理阶段——制定需要哪些工具调用
    plan = llm.generate(f"""
    任务：{task}
    可用工具：{format_tools(tools)}
    
    请分析完成此任务需要多少次工具调用。
    不要执行工具，只列出需要调用的内容。
    
    输出格式：
    Plan:
    1. tool_name(param1=value1)
    2. tool_name(param1=value1)
    ...
    """)
    
    # 阶段2：执行阶段——并行执行所有工具调用
    action_list = parse_actions(plan)
    observations = parallel_execute_all(action_list)  # 一次并行，无需等待
    
    # 阶段3：综合阶段——基于所有观察结果推理最终答案
    final_answer = llm.generate(f"""
    任务：{task}
    
    原始计划：{plan}
    
    执行结果：
    {format_observations(action_list, observations)}
    
    请基于所有执行结果，给出完整的最终回答。
    """)
    
    return final_answer
```

### 适用场景

- **工具调用可并行**：多个工具调用之间无依赖关系
- **工具延迟较高**：API 调用耗时较长，需要批量处理
- **推理链相对简单**：不需要根据中间结果动态调整后续工具调用

### 优缺点

| 优点 | 缺点 |
|------|------|
| 减少 LLM 调用次数（降低延迟和成本） | 无法根据中间结果动态调整 |
| 工具调用可完全并行 | 不适合需要逐步探索的任务 |
| 结构清晰，易于调试 | 如果计划错误，整个执行全部浪费 |

## 七、LATS（Language Agent Tree Search）

> 使用树搜索算法（如 MCTS，蒙特卡洛树搜索）同时探索多条推理路径，选择最优路径执行。

### 一句话定位

LATS（Zhou et al., 2024）将强化学习中的树搜索思想引入 Agent 推理：Agent 不是沿着一条路径走到黑，而是同时探索多个可能的推理分支，通过评估各分支的价值选择最优路径。

### 工作原理

```
                          Root（根问题）
                        /    |    \
                       /     |     \
                      ▼      ▼      ▼
                   Thought  Thought  Thought
                   A1       A2       A3
                    |        |        |
                    ▼        ▼        ▼
                 Action   Action   Action
                   |        |        |
                   ▼        ▼        ▼
                Obs1-1   Obs1-2   Obs1-3
                 /   \      |        |
                ▼    ▼      ▼        ▼
              T-A   T-B    T-C      T-D
               |     |      |        |
               ▼     ▼      ▼        ▼
             Act   Act    Act      Act
              |     |      |        |
              ▼     ▼      ▼        ▼
            Obs   Obs    Obs      Obs

            选择逻辑：
            - 每个节点有"价值分数"
            - 探索（exploration）：尝试未走过的路径
            - 利用（exploitation）：走已知的高价值路径
            - 平衡探索和利用 → 选择最优路径
```

### 核心机制

```python
def lats_search(task, max_iterations=20):
    tree = {
        "root": {
            "thought": task,
            "children": [],
            "visits": 0,
            "value": 0
        }
    }
    
    for _ in range(max_iterations):
        # 阶段1：选择——使用 UCB（Upper Confidence Bound）选择最有希望的节点
        node = select_node(tree["root"])
        
        # 阶段2：扩展——在当前节点生成多个子节点
        children = expand_node(node, task)
        node["children"].extend(children)
        
        # 阶段3：模拟——从每个子节点模拟完整执行
        for child in children:
            child["value"] = simulate_execution(child)
        
        # 阶段4：反向传播——将结果传播回祖先节点
        backpropagate(child, child["value"])
    
    # 选择价值最高的叶节点路径
    best_path = extract_best_path(tree)
    return execute_path(best_path)
```

### 适用场景

- **有明确评估标准的任务**：可以给不同路径打分
- **复杂推理任务**：存在多条可能的推理路径
- **探索-利用平衡重要**：既要尝试新策略，又要用已知可靠的策略

### 优缺点

| 优点 | 缺点 |
|------|------|
| 系统性地探索多条路径，找到最优解 | Token 消耗极大（探索多条路径） |
| 平衡探索与利用 | 实现复杂度高 |
| 可证明的最优路径选择 | 评估函数的设计是关键难点 |

## 八、Self-Discovery（自我发现）

> Agent 在任务开始时自主发现和组合最适合当前任务的推理模块（Reasoning Modules），而非使用固定推理结构。

### 一句话定位

Self-Discovery（Zhou et al., 2024）让 Agent 动态地"组装"自己的推理过程——不是使用预设的 CoT 或 ReAct，而是从一组原子推理模块中选择、调整和组合，形成针对当前任务的最优推理结构。

### 工作原理

```
    阶段1：发现（DISCOVER）
    
    推理模块库：
    [批判性思考, 逐步推理, 逆向推理,
     类比推理, 分解任务, 可行性分析,
     假设检验, 案例分析, 风险评估]
                    │
                    ▼
    Agent 基于当前任务选择并组合相关模块：
    
    任务："评估收购方案的风险"
       → 选中模块：[分解任务, 可行性分析, 风险评估, 批判性思考]
       → 组合顺序：分解任务 → 可行性分析 → 风险评估 → 批判性思考
                    │
                    ▼
    阶段2：执行（EXECUTE）
    
    Step 1: 分解任务
            "将收购方案拆解为财务、法律、运营三个子任务"
    Step 2: 可行性分析
            "分析每个子任务的可行性和前提条件"
    Step 3: 风险评估
            "识别每个子任务的潜在风险"
    Step 4: 批判性思考
            "对整体方案提出质疑和反证"
```

### 核心实现

```python
def self_discovery(task):
    # 推理模块库（预定义的原子推理能力）
    REASONING_MODULES = {
        "分解": "将复杂问题分解为更小的子问题",
        "逐步推理": "按顺序一步步推理",
        "逆向推理": "从目标出发反向推断所需条件",
        "类比": "寻找类似案例进行类比",
        "批判性思考": "从对立面审视结论",
        "可行性分析": "评估方案的可行性",
        "假设检验": "提出假设并验证",
        "风险评估": "识别潜在风险和缓解措施"
    }
    
    # 阶段1：自我发现——让 LLM 选择推理模块
    selected_modules = llm.generate(f"""
    任务：{task}
    
    可用的推理模块：
    {format_modules(REASONING_MODULES)}
    
    请选择最适合此任务的 3-5 个模块，并说明使用顺序。
    选择标准：
    - 模块是否直接相关
    - 组合起来是否能覆盖任务的各个方面
    - 顺序是否逻辑合理
    """)
    
    # 阶段2：结构化推理——按发现的顺序执行
    reasoning_structure = parse_structure(selected_modules)
    
    result = None
    for module_name in reasoning_structure.sequence:
        adapter = get_adapter(module_name)
        result = adapter.execute(previous_result=result, task=task)
    
    return result
```

### 适用场景

- **任务类型多样**：Agent 面临不同类型的复杂推理任务
- **需要自适应推理**：固定推理模式效果不佳
- **探索最优推理结构**：不同任务最适合不同的推理方式

## 九、STORM（STructured ORganic Memory）

> 通过多 Agent 协作和结构化记忆构建，实现从"头脑风暴"到"结构化文章"的完整写作流程。

### 一句话定位

STORM（Shao et al., 2024）是一种多 Agent 写作框架，通过"观点碰撞"来生成高质量的长文。它模拟学术界的研究过程：多个"专家"Agent 从不同角度探讨话题，通过对话产生多维度的见解，最终综合成一篇结构完整的长文。

### 工作原理

```
                     ┌──────────────────────┐
                     │     STORM Manager     │
                     │  (协调整个流程)        │
                     └──────────┬───────────┘
                                │
           ┌────────────────────┼────────────────────┐
           ▼                    ▼                    ▼
    ┌──────────────┐    ┌──────────────┐    ┌──────────────┐
    │ 专家 Agent 1 │    │ 专家 Agent 2 │    │ 专家 Agent N │
    │ (计算机科学)  │    │  (社会学)     │    │  (经济学)     │
    └──────┬───────┘    └──────┬───────┘    └──────┬───────┘
           │                    │                    │
           └────────────────────┼────────────────────┘
                                │
                                ▼
                     ┌──────────────────────┐
                     │  观点碰撞与整合       │
                     │  (多轮对话)           │
                     └──────────┬───────────┘
                                │
                                ▼
                     ┌──────────────────────┐
                     │   大纲生成            │
                     │   (基于所有观点)      │
                     └──────────┬───────────┘
                                │
                                ▼
                     ┌──────────────────────┐
                     │   分段写作 + 引用溯源  │
                     │   (LLM-as-Writer)     │
                     └──────────┬───────────┘
                                │
                                ▼
                     ┌──────────────────────┐
                     │   最终长文输出         │
                     │   (含引用来源)         │
                     └──────────────────────┘
```

### 核心机制

```python
def storm_write(topic, num_experts=3):
    # 阶段1：创建多个专家 Agent（不同视角）
    experts = [
        ExpertAgent("计算机科学", computer_science_kb),
        ExpertAgent("社会学", sociology_kb), 
        ExpertAgent("经济学", economics_kb),
    ]
    
    # 阶段2：多轮观点碰撞
    conversation = []
    for round in range(3):
        for expert in experts:
            # 专家基于已有对话发表见解
            perspective = expert.contribute(topic, conversation)
            conversation.append(perspective)
    
    # 阶段3：综合对话生成大纲
    outline = llm.generate(f"""
    主题：{topic}
    
    以下是多个专家的讨论：
    {format_conversation(conversation)}
    
    请基于以上讨论，生成一个详细的文章大纲。
    大纲应覆盖所有专家观点，并保持逻辑连贯。
    """)
    
    # 阶段4：分节写作（可并行）
    sections = {}
    for section_title in outline.sections:
        sections[section_title] = write_section(
            section_title, conversation, outline
        )
    
    # 阶段5：最终整合
    return assemble_article(topic, outline, sections)
```

### 适用场景

- **长文写作**：需要多角度讨论的综述、分析报告
- **研究论文**：需要全面覆盖相关领域的研究成果
- **策略分析**：需要综合多学科视角的决策分析

### 优缺点

| 优点 | 缺点 |
|------|------|
| 生成内容视角全面 | Token 消耗极大（多 Agent 对话） |
| 观点碰撞产生深度洞察 | 实现复杂度高 |
| 自动生成引用来源 | 专家 Agent 的角色知识依赖 Prompt 设计 |
| 结构化输出，可直接使用 | 多轮对话可能产生冗余 |
