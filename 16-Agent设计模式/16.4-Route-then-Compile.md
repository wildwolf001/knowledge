# 16.4 Route-then-Compile

> Route-then-Compile（路由-编译模式）通过将"意图分类"与"确定性路径执行"相分离，从根本上解决了 Agent 在开放式工具选择中产生的幻觉问题。其核心理念是：让 LLM 做它擅长的事（理解和分类），把不擅长的事（精确决策和编排）交给确定性代码。

---

## 一、问题背景：开放式工具选择的幻觉

### 1.1 传统 Agent 架构的问题

在传统的 ReAct 模式（见 16.2 节）中，Agent 在每一轮都需要自主决定：

1. **下一步要做什么？**（意图判断）
2. **使用哪个工具？**（工具选择）
3. **传入什么参数？**（参数构造）
4. **观察结果意味着什么？**（结果解释）

这四个决策每一步都存在"开放式选择"——Agent 从数十甚至上百个可能的工具中做选择。研究表明，当工具数量超过 10-15 个时，工具选择的准确率开始显著下降（详见 24.8 节小模型的工具调用幻觉）：

```
工具选择准确率 vs 工具数量（示意数据）：

  100% │  ●
       │    ●
   90% │       ●
       │          ●
   80% │             ●
       │                ●
   70% │                   ●
       │                      ●
   60% │                         ●
       │                            ●
   50% │                               ●
       └────────────────────────────────────
          5   10   15   20   25   30  工具数量
```

### 1.2 幻觉的来源分析

在开放式工具选择中，Agent 的幻觉主要来自三个层面：

**层面一：工具存在幻觉**
Agent "自信地"调用一个不存在的工具。例如，模型生成了 `get_user_address()`，但系统中实际只有 `get_user_profile()`。

**层面二：工具参数幻觉**
Agent 使用了正确的工具，但生成了错误的或不存在的参数。例如，`search_products(category="tech", sort_by="popularity")`，但 `sort_by` 参数实际上只接受 `"price"` 和 `"rating"`。

**层面三：工具组合幻觉**
Agent 选择了正确的工具和参数，但工具的执行顺序或组合方式不合理。例如，先调用"发送订单确认"再调用"创建订单"。

Route-then-Compile 正是针对这三个层面的问题进行设计的。

## 二、Route-then-Compile 的工作原理

### 2.1 整体架构

```
                        用户输入
                           │
                           ▼
              ┌─────────────────────────┐
              │        Phase 1          │
              │        路由（Route）      │
              │    LLM 仅做意图分类       │
              └──────────┬──────────────┘
                         │
                  ┌──────┴──────┐
                  ▼              ▼
              ┌────────┐   ┌────────┐
              │ 意图A   │   │ 意图B   │   ...（有限数量）
              └───┬────┘   └───┬────┘
                  │            │
                  ▼            ▼
              ┌─────────────────────────┐
              │        Phase 2          │
              │      编译（Compile）      │
              │    执行确定性代码路径     │
              │   - 预定义的 DAG         │
              │   - 确定性工具调用       │
              │   - 结构化参数绑定       │
              └──────────┬──────────────┘
                         │
                         ▼
              ┌─────────────────────────┐
              │        Phase 3          │
              │      合成（Synthesize）   │
              │    LLM 基于结构化结果     │
              │    生成自然语言回答       │
              └─────────────────────────┘
```

### 2.2 Phase 1：路由（Route）—— 缩小选择空间

路由阶段的核心目标是将"开放式选择"转化为"有限选项选择"。LLM 只需要判断用户意图属于哪个预定义的类别，而不是从几十个工具中选择。

```python
class Router:
    """意图路由：将开放式用户输入映射到有限的意图类别"""
    
    INTENTS = [
        "query_order_status",      # 查询订单状态
        "request_refund",          # 申请退款
        "modify_order",            # 修改订单
        "product_inquiry",         # 产品咨询
        "account_issue",           # 账户问题
        "technical_support",       # 技术支持
        "general_inquiry"          # 一般咨询
    ]
    
    def route(self, user_input, conversation_history=None):
        """路由决策——LLM 仅做分类"""
        prompt = f"""
        请将以下用户输入分类到最合适的意图类别。
        
        可用类别：
        {format_intents(self.INTENTS)}
        
        用户输入：{user_input}
        对话历史：{conversation_history or "无"}
        
        注意事项：
        - 如果输入包含多个意图，选择最主要的那个
        - 如果无法确定，选择 "general_inquiry"
        - 不要分析如何解决问题，只需分类
        
        请只返回一个类别名称。
        """
        
        intent = llm.generate(prompt, temperature=0.0)  # 分类用 temperature=0
        
        # 验证：确保输出是有效类别
        if intent not in self.INTENTS:
            intent = self.fallback(intent)  # 映射到最接近的类别
        
        return intent
```

**路由为什么能降低幻觉？**

1. **选择空间从"几十个工具"降为"几个意图"**：分类比选择更容易。LLM 在 7 选 1 的任务上的准确率远高于 50 选 1。
2. **路由阶段的输出是类别（单 token 或短文本）**：而不是需要精确构造的工具调用，出错概率大幅降低。
3. **路由失败有兜底**：`general_inquiry` 作为 catch-all 类别，保证不会出现"无法分类"的情况。

### 2.3 Phase 2：编译（Compile）—— 执行确定性路径

编译阶段是 Route-then-Compile 区别于其他模式的核心。对于每个意图，开发者预先定义好一个**确定性的执行路径**——工具调用序列、参数绑定、错误处理逻辑全部预编码，不由 LLM 动态决定。

```python
class Compiler:
    """编译器：将分类后的意图映射到确定性执行路径"""
    
    def __init__(self):
        # 每个意图对应一个确定性的执行 DAG
        self.execution_paths = {
            "query_order_status": self._compile_query_order,
            "request_refund": self._compile_refund,
            "modify_order": self._compile_modify_order,
            "product_inquiry": self._compile_product_inquiry,
            "account_issue": self._compile_account_issue,
            "technical_support": self._compile_technical_support,
            "general_inquiry": self._compile_general_inquiry,
        }
    
    def compile(self, intent, user_input):
        """基于意图返回确定性的执行路径"""
        if intent in self.execution_paths:
            return self.execution_paths[intent](user_input)
        return self.execution_paths["general_inquiry"](user_input)
    
    def _compile_query_order(self, user_input):
        """查询订单状态的确定性路径"""
        return ExecutionPath(
            steps=[
                # LLM 不决定参数——参数从输入中结构化提取
                ToolCall("extract_entities", 
                         params={"target": "order_id", "source": user_input}),
                ToolCall("validate_order_id", 
                         params={"order_id": "$steps[0].order_id"}),
                # 分支：如果验证通过
                Conditional(
                    condition="$steps[1].is_valid",
                    true_branch=[
                        ToolCall("get_order_status",
                                 params={"order_id": "$steps[0].order_id"}),
                        ToolCall("get_order_timeline",
                                 params={"order_id": "$steps[0].order_id"})
                    ],
                    # 分支：如果订单号无效
                    false_branch=[
                        ToolCall("search_orders_by_user",
                                 params={"user_id": "$context.user_id"})
                    ]
                )
            ],
            error_handler=self._handle_order_query_error
        )
```

**确定性路径的保证**：

```
传统 Agent：LLM 决定每一步做什么、用什么工具、传什么参数
  → 每次执行路径都可能不同
  → 存在"幻觉路径"——LLM 选择了一个不存在的工具或参数

Route-then-Compile 编译阶段：
  → 执行路径在代码中预先定义
  → 工具名称、参数模式在编译时已固定
  → 只有"参数值"可能来自输入提取
  → 零工具选择幻觉、零参数结构幻觉
```

### 2.4 Phase 3：合成（Synthesize）—— 生成最终回复

合成阶段是最后一次调用 LLM，但此时 LLM 面对的不是开放式工具选择，而是结构化的执行结果。它只需要"把数据翻译成自然语言"。

```python
def synthesize(self, intent, execution_result, user_input):
    """基于确定性执行的结构化结果生成自然语言回答"""
    
    # 此时 LLM 不需要做任何工具选择决策
    # 只需要将结构化数据格式化为良好的回答
    prompt = f"""
    用户问题：{user_input}
    查询类型：{intent}
    执行结果：{json.dumps(execution_result, ensure_ascii=False, indent=2)}
    
    请根据执行结果生成友好的回答。
    要求：
    - 准确反映数据，不要添加执行结果中没有的信息
    - 如果结果中包含错误信息，向用户说明并提供解决方案
    - 保持回答简洁但完整
    """
    
    return llm.generate(prompt, temperature=0.3)
```

## 三、完整的工作流程示例

以一个"电商客服 Agent"为例，展示 Route-then-Compile 的完整工作流程：

```
用户输入："帮我查一下订单 ORD-2024-12345 什么时候发货"

Phase 1 - 路由：
  Router 判断意图 → "query_order_status"
  这一步只需要模型做 7 选 1 的分类

Phase 2 - 编译：
  路径：query_order_status 的确定性 DAG
  
  Step 1: extract_entities(user_input)
          → {"order_id": "ORD-2024-12345", "entities": ["订单号"]}
  
  Step 2: validate_order_id("ORD-2024-12345")
          → {"is_valid": true, "format": "standard"}
  
  Step 3: get_order_status(order_id="ORD-2024-12345")
          → {"status": "shipped", "tracking_number": "SF1234567890",
             "estimated_delivery": "2024-06-05"}
  
  Step 4: get_order_timeline(order_id="ORD-2024-12345")
          → [{"event": "已付款", "time": "2024-05-28 14:30"},
              {"event": "已发货", "time": "2024-05-30 09:15"},
              {"event": "运输中", "time": "2024-05-30 14:00"}]

Phase 3 - 合成：
  LLM 基于结构化数据生成回答：
  "您的订单 ORD-2024-12345 已于 5月30日发货，
   顺丰快递单号：SF1234567890，预计 6月5日前送达。
   物流跟踪：已付款→已发货→运输中。"
```

**对比传统 ReAct 模式的路径**：

```
传统 ReAct 可能产生的幻觉路径：

Thought: 我需要查这个订单
Action: search_orders(query="ORD-2024-12345")  
  → 错误：工具名应为 get_order_status，不是 search_orders
  
Thought: 订单号格式不对，我用 get_customer_info  
Action: get_customer_info(order_id="ORD-2024-12345")
  → 错误：参数 order_id 对 get_customer_info 无效
  
Thought: 用户想知道什么时候发货，我调用 order_tracking  
Action: order_tracking(tracking_id="ORD-2024-12345")
  → 错误：tracking_id 应该是物流单号而非订单号
```

可以看到，传统 ReAct 在每一步都可能产生幻觉。Route-then-Compile 通过将决策权从 LLM 移交给确定性代码，从根本上消除了这些幻觉。

## 四、路由策略的进阶设计

### 4.1 多级路由

单层路由在意图类别较少时效果良好，但面对数百个意图类别时精度会下降。多级路由通过"先粗分类，再细分类"来应对：

```python
class HierarchicalRouter:
    def __init__(self):
        self.first_level = {
            "order": ["query_status", "modify", "cancel", "refund"],
            "product": ["search", "detail", "compare", "recommend"],
            "account": ["login_issue", "profile_update", "permission"],
            "payment": ["method", "invoice", "dispute"]
        }
    
    def route(self, user_input):
        # 第一级：粗分类（4 选 1）
        category = self._classify_category(user_input)
        
        # 第二级：细分类（在子类别中做 3-4 选 1）
        sub_intent = self._classify_sub_intent(user_input, category)
        
        return f"{category}.{sub_intent}"
```

### 4.2 路由置信度与降级

当路由分类的置信度低时，系统可以采取保守策略：

```python
class ConfidenceRouter:
    MIN_CONFIDENCE_FOR_AUTO = 0.85
    
    def route(self, user_input):
        intent, confidence = self._classify_with_confidence(user_input)
        
        if confidence >= self.MIN_CONFIDENCE_FOR_AUTO:
            # 高置信度 → 自动路由到确定性路径
            return self.compile_and_execute(intent, user_input)
        
        elif confidence >= 0.6:
            # 中等置信度 → 使用"审核模式"：需要人工确认
            return self.await_human_confirmation(intent, user_input)
        
        else:
            # 低置信度 → 回退到通用 Agent（允许更多 LLM 自主权）
            return self.fallback_general_agent(user_input)
```

### 4.3 意图覆盖检测

新出现的用户意图可能不在预定义的意图列表中。需要检测"意图覆盖缺口"：

```python
def detect_coverage_gap(user_input, all_intents):
    """检测用户意图是否在已有意图覆盖范围内"""
    # 用较低的阈值判断是否需要新增意图
    best_intent, confidence = classifier.predict(user_input, all_intents)
    
    if confidence < 0.5:
        # 发现潜在的新意图类型
        new_intent_suggestion = suggest_new_intent(user_input)
        
        # 发送告警
        alert_team(
            f"发现可能的未覆盖意图：{user_input[:50]}...\n"
            f"建议的新意图：{new_intent_suggestion}"
        )
        
        return CoverageGap(
            detected=True,
            suggested_intent=new_intent_suggestion,
            fallback_intent="general_inquiry"
        )
    
    return CoverageGap(detected=False)
```

## 五、Route-then-Compile 与 Agent 模式的对比

| 维度 | 传统 ReAct Agent | Route-then-Compile |
|------|-----------------|-------------------|
| 工具选择方式 | LLM 自由选择 | 代码预定义路径 |
| 选择空间 | 全部工具（10-50+） | 预定义意图（3-10） |
| 执行确定性 | 低（每次可能不同） | 高（相同输入相同路径） |
| 工具调用幻觉 | 高 | 几乎为零 |
| 参数幻觉 | 中-高 | 低（参数绑定在代码中） |
| 灵活性 | 高（可处理意外情况） | 中（限于预定义路径） |
| 维护成本 | 低（无需预编码路径） | 中（需要维护路径定义） |
| 适用场景 | 探索性、开放域任务 | 确定性、高可靠要求任务 |

### 何时使用 Route-then-Compile

**推荐使用**：
- 客服系统（意图清晰、路径固定的高频场景）
- 业务流程自动化（审批流、订单处理等有固定流程的场景）
- 金融交易（出错成本高，需要确定性保证）
- 医疗咨询（需要严格按照临床路径执行）

**不推荐使用**：
- 开放域对话（意图无法被穷举）
- 创意写作（需要 LLM 自由探索）
- 研究分析（需要动态发现信息）

## 六、降低幻觉的量化分析

### 6.1 幻觉降低的数学解释

假设系统中包含 `N` 个工具，每个工具的平均幻觉概率为 `p`。

**传统 ReAct Agent 在单步中的幻觉概率**：
```
P(单步无幻觉) = (1 - p)^N    （从 N 个工具中选对的概率）
P(单步有幻觉) ≈ N × p         （近似，Np 较小时）
```

当 N=20, p=0.02 时：
```
P(单步无幻觉) ≈ (0.98)^20 ≈ 0.668
P(单步有幻觉) ≈ 0.332
```

经过 M 步后无幻觉的概率：
```
P(M步都无幻觉) ≈ 0.668^M

M=3: 0.668^3 ≈ 0.298  （超过 70% 的概率至少出现一次幻觉）
M=5: 0.668^5 ≈ 0.133  （接近 87%）
```

**Route-then-Compile 中**，路由阶段只需做 K 选 1（K 是意图类别数，通常 5-10），编译阶段的工具调用是确定性的（幻觉概率趋近于 0）：

```
P(Route单步准确) = 满足 LLM 在 K 选 1 上的分类准确率

当 K=7 时，典型分类准确率 > 95%（with temperature=0）
P(后续编译阶段幻觉) ≈ 0（确定性代码）

因此，总失败概率 ≈ 1 - 0.95 = 0.05
```

即使用 7 个意图类别的 Route-then-Compile，端到端的失败概率约为 5%，远低于传统 ReAct 在同等工具数量下的 70-87%。

### 6.2 实际观测数据

基于多个生产系统的运行数据（行业报告综合）：

| 指标 | 传统 ReAct | Route-then-Compile | 改善 |
|------|-----------|-------------------|------|
| 工具调用幻觉率 | 8-15% | < 0.5% | 16-30x 改善 |
| 参数幻觉率 | 5-12% | < 1% | 5-12x 改善 |
| 端到端任务成功率 | 65-80% | 90-96% | +15-20% |
| 平均响应延迟 | 2-5s | 1-3s | 降低 30-40% |
| Token 消耗（每步） | 500-1500 | 200-500 | 降低 50-60% |

## 七、与其他模式的关系

Route-then-Compile 不是 ReAct 的替代品，而是特定场景下的优化模式。它与本章其他模式的关系：

```
                       ┌────────────────────┐
                       │     传统 ReAct       │
                       │   (最大灵活性)      │
                       └──────────┬─────────┘
                                  │ 确定性需求增加
                                  ▼
        ┌───────────────────────────────────────────┐
        │             Route-then-Compile              │
        │  意图路由（16.1 Routing的极致化）+ 确定性路径  │
        └──────┬───────────────────────┬────────────┘
               │                       │
               ▼                       ▼
        ┌────────────┐         ┌──────────────┐
        │ + 16.3     │         │ + 16.2       │
        │ 12-Factor  │         │ Evaluator-   │
        │ 配置分离    │         │ Optimizer    │
        └────────────┘         │ 在合成阶段    │
                               │ 加入质量检查  │
                               └──────────────┘
```

- 当任务的确定性要求极高时 → Route-then-Compile
- 当任务需要动态探索时 → ReAct 或 REWOO
- 当任务介于两者之间 → 混合使用：先 Route 确定意图，再用 ReAct 在意图内灵活执行

## 关键概念速查

| 术语 | 解释 |
|------|------|
| Route（路由） | 将用户输入分类到预定义意图类别，缩小 LLM 的选择空间 |
| Compile（编译） | 基于分类结果执行预先编码的确定性工具调用路径 |
| Synthesize（合成） | 将结构化执行结果翻译为自然语言回答 |
| 工具选择幻觉 | LLM 调用不存在或不适当的工具的幻觉 |
| 参数结构幻觉 | LLM 使用正确工具但传入错误参数结构的幻觉 |
| 确定性路径 | 在代码中预先定义的工具调用序列和参数绑定 |
| 多级路由 | 先粗分类再细分类的分层路由策略 |
| 意图覆盖缺口 | 用户实际意图不在预定义意图列表中的情况 |
| 兜底意图（Fallback Intent） | catch-all 类别，处理无法匹配的输入 |
