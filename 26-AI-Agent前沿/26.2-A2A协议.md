# 26.2 A2A（Agent-to-Agent）协议

> A2A（Agent-to-Agent）协议是 Google 于 2025 年提出的跨平台、跨厂商 Agent 通信标准。它定义了一套通用的"语言"和交互流程，使不同框架、不同供应商开发的 Agent 能够相互发现、协商任务、交换信息，是 Agent 互联互通的基础设施级协议。

---

## 一、A2A 协议的背景与设计理念

### 1.1 为什么需要 A2A？

在 A2A 出现之前，Agent 的世界是"孤岛"式的：

- 每个 Agent 框架（LangChain、AutoGen、CrewAI）使用私有的通信协议。
- 不同厂商的 Agent（如 Google Agent、OpenAI GPTs、Microsoft Copilot）无法直接协作。
- Agent 间的交互依赖开发者手动编写胶水代码（Glue Code），不可复用、不可扩展。

这与互联网早期的情况类似——在 TCP/IP 成为标准之前，每个网络（ARPANET、X.25、SNA）都使用自己的协议，无法互联互通。A2A 的目标就是成为 Agent 世界的 TCP/IP。

### 1.2 核心设计理念

A2A 的设计遵循以下原则：

| 原则 | 说明 |
|------|------|
| **基于能力（Capability-Based）** | Agent 声明自己能做什么，而不是自己是什么。消费者按能力匹配而非按身份匹配 |
| **异步优先（Async-First）** | Agent 任务可能是长时间运行的（分钟级甚至小时级），协议必须支持异步通信 |
| **无中心化（Decentralized）** | 不需要中央注册中心或协调器，Agent 之间直接点对点通信 |
| **安全可审计（Auditable）** | 所有交互记录可追溯，支持审计和合规要求 |
| **传输无关（Transport-Agnostic）** | 底层传输可以是 HTTP、WebSocket、gRPC，不绑定特定协议 |

### 1.3 A2A 与 MCP 的关系

MCP（Model Context Protocol，详见第 10 章）和 A2A 是互补关系，并非竞争关系：

```
┌──────────────────────────────────────────────────────────┐
│                    Agent 生态                           │
│                                                          │
│  ┌──────────────────────┐  ┌──────────────────────────┐  │
│  │        MCP           │  │         A2A              │  │
│  │  (Model-Client协议)   │  │  (Agent-to-Agent协议)    │  │
│  │                      │  │                          │  │
│  │ LLM ↔ Tool/Resource  │  │ Agent ↔ Agent            │  │
│  │ 客户端 ↔ 服务器        │  │ 对等体 ↔ 对等体           │  │
│  │ 请求-响应模式          │  │ 任务协商+异步通信         │  │
│  │ 工具发现+调用          │  │ 能力发现+任务委托         │  │
│  └──────────────────────┘  └──────────────────────────┘  │
│                                                          │
│  典型场景：Agent 调用外部工具          典型场景：Agent 间协作     │
│  - Agent → 数据库 MCP Server          - 客服 Agent → 物流 Agent  │
│  - Agent → 文件系统 MCP Server        - 排程 Agent → 支付 Agent  │
│  - Agent → API MCP Server             - 分析 Agent → 报表 Agent  │
└──────────────────────────────────────────────────────────┘
```

**关键差异总结**：

| 维度 | MCP | A2A |
|------|-----|-----|
| 通信主体 | LLM Client & Server | Agent & Agent |
| 交互模式 | 请求-响应（同步） | 任务协商（异步） |
| 角色关系 | 客户端-服务器（不对等） | 对等（Peer-to-Peer） |
| 核心操作 | 工具调用、资源读取 | 能力协商、任务委托 |
| 状态管理 | 无状态 | 有状态（长任务追踪） |
| 设计渊源 | Anthropic | Google |

在实际系统中，一个 Agent 可能同时是 MCP 客户端（调用工具）和 A2A 节点（与其他 Agent 通信）。MCP 解决"Agent 如何与工具交互"，A2A 解决"Agent 如何与其他 Agent 交互"。

## 二、A2A 协议的核心概念

### 2.1 Agent Card

每个参与 A2A 的 Agent 需要发布一个 **Agent Card**（类似 MCP 的 Service Discovery），用于描述自身能力。Agent Card 是一个 JSON 文档，典型结构如下：

```json
{
  "schemaVersion": "1.0",
  "agent": {
    "name": "OrderFulfillmentAgent",
    "description": "处理订单履约全流程，包括库存检查、物流安排和状态更新",
    "url": "https://agents.example.com/order-fulfillment"
  },
  "capabilities": [
    {
      "id": "check_inventory",
      "name": "库存检查",
      "description": "检查指定商品的库存可用性",
      "inputSchema": {
        "type": "object",
        "properties": {
          "sku": {"type": "string", "description": "商品 SKU"},
          "warehouse": {"type": "string", "description": "仓库编码"}
        },
        "required": ["sku"]
      },
      "outputSchema": {
        "type": "object",
        "properties": {
          "available": {"type": "boolean"},
          "quantity": {"type": "integer"},
          "estimatedRestock": {"type": "string"}
        }
      }
    },
    {
      "id": "arrange_shipping",
      "name": "安排物流",
      "description": "根据地址和商品生成物流单",
      "inputSchema": {
        "type": "object",
        "properties": {
          "orderId": {"type": "string"},
          "address": {"type": "string"},
          "items": {"type": "array", "items": {"type": "string"}}
        },
        "required": ["orderId", "address", "items"]
      }
    }
  ],
  "authentication": {
    "type": "oauth2",
    "tokenUrl": "https://auth.example.com/token"
  }
}
```

Agent Card 通过标准的 HTTP 端点发布：

```
GET https://agents.example.com/.well-known/agent.json
```

### 2.2 任务（Task）

A2A 的核心交互单元是**任务（Task）**。一个任务代表一个需要完成的作业，从创建到完成的全生命周期包括：

```
任务生命周期：

         ┌──────────┐
         │  Created  │  ← 客户端 Agent 创建一个任务
         └─────┬────┘
               │
         ┌─────▼────┐
         │ Pending  │  ← 服务端 Agent 确认接收但尚未开始
         └─────┬────┘
               │
         ┌─────▼────┐
         │ Working  │  ← 正在执行（可能持续很长时间）
         └─────┬────┘
               │
    ┌──────────┼──────────┐
    │          │          │
┌───▼───┐ ┌───▼───┐ ┌───▼───┐
│Completed│ │ Failed │ │ Canceled│
│ (成功)  │ │ (失败) │ │ (取消)  │
└────────┘ └────────┘ └────────┘
```

任务通过标准的消息结构传递：

```json
{
  "taskId": "task-001-abc123",
  "agentId": "OrderFulfillmentAgent",
  "status": "working",
  "createdAt": "2025-04-01T10:00:00Z",
  "input": {
    "capability": "check_inventory",
    "parameters": {
      "sku": "SKU-2025-001",
      "warehouse": "WH-01"
    }
  },
  "output": null,
  "history": [
    {
      "role": "client",
      "type": "text",
      "content": "请检查 SKU-2025-001 在 WH-01 的库存",
      "timestamp": "2025-04-01T10:00:00Z"
    },
    {
      "role": "server",
      "type": "text",
      "content": "正在查询...预计需要 2 秒",
      "timestamp": "2025-04-01T10:00:01Z"
    }
  ]
}
```

### 2.3 交互模式

A2A 支持两种交互模式：

**模式一：简单请求-响应**
适用于耗时短（< 5 秒）、不需要流式反馈的任务。

```
Client Agent          Server Agent
     │                     │
     │─── POST /task ──────►│
     │                     │
     │◄─── 200 OK ────────│ (task status: completed)
     │                     │
```

**模式二：异步推送**
适用于耗时长的任务，服务端通过 WebSocket 或 webhook 主动推送状态更新。

```
Client Agent          Server Agent
     │                     │
     │─── POST /task ──────►│
     │◄── 202 Accepted ────│ (taskId 返回)
     │                     │
     │                     │ (执行中...)
     │◄── push: working ──│ (WebSocket 推送进度)
     │                     │
     │◄── push: completed ─│ (最终结果)
     │                     │
```

## 三、A2A 的通信流程详解

### 3.1 Agent 发现与能力匹配

```
┌─────────────────┐          ┌─────────────────┐
│  请求方 Agent    │          │  服务方 Agent    │
│  (Client Agent)  │          │  (Server Agent)  │
└────────┬────────┘          └────────┬────────┘
         │                            │
         │  1. 获取 Agent Card         │
         │  GET /.well-known/agent.json│
         │◄───────────────────────────│
         │                            │
         │  2. 分析 capabilities      │
         │  匹配需要的功能             │
         │                            │
         │  3. 创建 Task              │
         │  POST /task               │
         │───────────────────────────►│
         │                            │
         │  4. 协商任务参数            │
         │  (可选的多轮对话)            │
         │◄──────────────────────────►│
         │                            │
         │  5. 执行并返回结果          │
         │◄───────────────────────────│
```

### 3.2 安全模型

A2A 的安全模型建立在现有 Web 安全标准之上：

- **认证（Authentication）**：OAuth 2.0 / JWT，Agent Card 中声明认证方式。
- **授权（Authorization）**：基于 Capability 级别的权限控制，每个能力可独立授权。
- **传输安全**：强制 HTTPS，可选的 mTLS（双向 TLS）。
- **审计日志**：所有 Task 的创建、更新、完成事件都需记录，支持追溯。

### 3.3 错误处理

```json
{
  "taskId": "task-001-abc123",
  "status": "failed",
  "error": {
    "code": "CAPABILITY_NOT_FOUND",
    "message": "请求的能力 'check_inventory_v2' 不存在",
    "details": {
      "availableCapabilities": ["check_inventory", "arrange_shipping", "track_order"]
    }
  }
}
```

标准错误码：

| 错误码 | 含义 | 处理建议 |
|--------|------|----------|
| `CAPABILITY_NOT_FOUND` | 请求的能力不存在 | 重新获取 Agent Card 检查可用能力 |
| `INVALID_PARAMETERS` | 参数校验失败 | 对照 inputSchema 修正参数 |
| `RATE_LIMITED` | 请求频率过高 | 退避重试（Exponential Backoff） |
| `TASK_TIMEOUT` | 任务执行超时 | 调大 timeout 或拆分任务 |
| `AUTH_EXPIRED` | 认证过期 | 重新获取 token |

## 四、A2A 的发展历程与展望

### 4.1 A2A 里程碑时间线

```
2025.04         2025.06             2025.12           2026.05
  │               │                   │                 │
  ▼               ▼                   ▼                 ▼
Google 提出    捐赠给 Linux        首个正式        规范 0.3.x
A2A 协议         Foundation          参考实现        趋向 1.0
~50 家合作伙伴   治理中立化          (~a2a-py 0.2)
```

- **2025 年 4 月**：Google 在 Google Cloud Next 上正式提出 A2A 协议，初始约 50 家合作伙伴，包括 Atlassian、LangChain、ServiceNow 等。
- **2025 年 6 月**：Google 将 A2A 协议捐赠给 Linux Foundation，标志着协议治理走向中立化，降低了其他厂商的采用顾虑。
- **2026 年 5 月**：规范迭代至 0.3.x 版本，核心 API 已趋于稳定，社区普遍预期 1.0 正式版将在 2026 年下半年发布。

### 4.2 生态支持

截至 2026 年，A2A 已获得以下主要采用者支持：

| 厂商/项目 | 角色 | 集成方式 |
|-----------|------|----------|
| **Google Cloud** | 发起方 | Vertex AI Agent Builder 原生内置 A2A |
| **Atlassian** | 早期采用者 | Jira、Confluence Agent 通过 A2A 对外提供服务 |
| **LangChain** | SDK 集成 | LangGraph Agent 支持 A2A 作为通信层 |
| **ServiceNow** | 企业级采用 | Now Platform AI Agent 支持 A2A 协议 |
| **Microsoft** | 生态合作 | Copilot Studio 实验性支持 A2A 互操作 |
| **CrewAI** | 框架集成 | 跨 Crew Agent 通信支持 A2A |
| **开源社区** | 参考实现 | GitHub 上多个 A2A 实现（`a2a-py`、`a2a-js`） |

### 4.3 Agent Card 发现机制的标准化

Agent Card 的发布地址已标准化为 `/.well-known/agent.json`（与 MCP 的 `mcp.json` 类似），遵循 RFC 8615（Well-Known URIs）规范。消费者 Agent 只需知道服务 Agent 的域名，即可通过标准路径获取其能力声明，实现完全去中心化的服务发现。

### 4.4 与 MCP 的未来融合

MCP + A2A 的组合将形成完整的 Agent 通信栈：

```
                  ┌─────────────────────────────┐
                  │       Agent Application       │
                  ├─────────────────────────────┤
                  │   A2A Client / Server SDK    │  ← Agent 间通信
                  ├─────────────────────────────┤
                  │   MCP Client SDK             │  ← 工具/资源调用
                  ├─────────────────────────────┤
                  │   传输层 (HTTP/WSS/gRPC)      │
                  └─────────────────────────────┘
```

这种分层架构使得 Agent 可以：
1. 通过 MCP 调用本地或远程工具（数据库、API、文件系统）。
2. 通过 A2A 与其他 Agent 协作完成复杂任务。
3. 底层传输可插拔，适配不同的部署环境。

## 五、关键概念速查表

| 概念 | 英文 | 解释 |
|------|------|------|
| A2A | Agent-to-Agent Protocol | Google 提出的跨平台 Agent 通信标准 |
| Agent Card | Agent Card | 描述 Agent 能力的元数据文档，类似"能力名片" |
| 任务 | Task | A2A 的核心交互单元，代表一个需要完成的作业 |
| 能力声明 | Capability Declaration | Agent Card 中 structured 的能力描述 |
| 异步通信 | Async Communication | 无需实时等待的通信模式，通过推送获取结果 |
| 对等架构 | Peer-to-Peer | 无中心节点的直接通信架构 |
| 能力匹配 | Capability Matching | 根据需求自动匹配合适的服务 Agent |
| 任务生命周期 | Task Lifecycle | 从创建到完成/失败的完整状态流转 |
| 审计追踪 | Audit Trail | 所有交互记录的不可篡改日志 |
| 传输无关 | Transport-Agnostic | 不绑定特定传输协议的设计原则 |
