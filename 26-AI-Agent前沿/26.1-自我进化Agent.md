# 26.1 自我进化 Agent —— Skill 自动优化、Tool 描述自动改进

> 自我进化 Agent（Self-Evolving Agent）指 Agent 能够在运行过程中自动评估并改进自身的工具调用能力、Skill 执行效率和描述质量，形成"描述→评估→改进"的持续优化闭环。这是 Agent 从"可用"迈向"自优化"的关键能力。

---

## 一、什么是自我进化 Agent

### 1.1 背景与动机

传统 Agent 的能力边界由开发者预先定义：注册 Tool、编写 Prompt、设定 Workflow。一旦部署，Agent 的能力是**静态的**——它不会越用越好，反而可能因为环境变化而逐渐退化。

自我进化 Agent 试图打破这一限制。借鉴**元学习（Meta-Learning）**的思想，Agent 在执行过程中持续收集反馈数据，自动调整自身的行为参数。其核心洞察在于：**Agent 的每次调用都是一次潜在的"训练机会"**。

### 1.2 进化的三个维度

| 进化维度 | 对象 | 目标 | 类比 |
|---------|------|------|------|
| **Skill 优化** | LLM 调用的子任务流程 | 提高子任务执行的准确率和效率 | 程序员重构代码 |
| **Tool 描述改进** | Tool 的 name/description/parameters | 提升 LLM 选择正确 Tool 的概率 | API 文档更新 |
| **Prompt 自适应** | Agent 的系统提示词 | 适应新的任务分布 | 调参 |

本章重点讨论前两个维度。

---

## 二、进化闭环："描述→评估→改进"

自我进化的核心是一个闭环流程：

```
                    ┌──────────────────┐
                    │   Skill / Tool   │
                    │   初始定义        │
                    └────────┬─────────┘
                             │
                             ▼
┌──────────────────────────────────────────────────┐
│                  执行阶段                          │
│  ┌──────────┐   ┌──────────┐   ┌──────────────┐  │
│  │ 任务输入  │ → │ Agent执行 │ → │ 结果输出      │  │
│  └──────────┘   └─────┬────┘   └──────────────┘  │
│                        │                          │
│                   ┌────▼────┐                    │
│                   │ 执行轨迹  │                    │
│                   │ (Trajectory) │                │
│                   └─────────┘                    │
└──────────────────────────────────────────────────┘
                             │
                             ▼
┌──────────────────────────────────────────────────┐
│                  评估阶段                          │
│  ┌────────────┐   ┌────────────┐   ┌───────────┐ │
│  │ 结果正确性  │   │ 工具选择    │   │ 执行效率   │ │
│  │ 验证       │   │ 合理性评估  │   │ 评估      │ │
│  └────────────┘   └────────────┘   └───────────┘ │
└──────────────────────────────────────────────────┘
                             │
                             ▼
┌──────────────────────────────────────────────────┐
│                  改进阶段                          │
│  ┌──────────────────────────────────────────────┐ │
│  │  基于评估反馈自动修改 Skill/Tool 定义          │ │
│  │  (LLM 作为优化器，生成新的描述文本)             │ │
│  └──────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────┘
                             │
                             └──────────► 循环迭代
```

### 2.1 评估阶段（Evaluation）

评估是闭环中最关键的环节。没有准确的评估，改进就是盲目的。

**结果正确性验证**：
- **确定性验证**：对于有确定答案的任务（如计算、数据库查询），直接比对结果。
- **LLM-as-Judge**：对于开放任务，用另一个 LLM 评估输出质量。
- **用户隐式反馈**：用户是否采纳了结果？是否继续追问？这些行为信号是天然的评估数据。

**工具选择合理性评估**：
```python
# 伪代码：工具选择合理性评分

def evaluate_tool_selection(trajectory: Trajectory) -> float:
    """
    评估 Agent 在轨迹中选择工具是否合理。
    分数范围 0.0 ~ 1.0
    """
    score = 1.0
    
    for step in trajectory.steps:
        # 1. 是否选择了完全错误的工具
        if step.selected_tool not in step.expected_tools:
            score -= 0.3
        
        # 2. 是否选择了不必要的工具（过度调用）
        if is_unnecessary_call(step):
            score -= 0.1
            
        # 3. 工具参数是否正确
        if not validate_arguments(step):
            score -= 0.2
    
    return max(0.0, score)
```

**执行效率评估**：
- **Token 消耗**：是否有多余的思考步骤？
- **API 调用次数**：是否重复调用了相同的工具？
- **延迟**：是否存在不必要的串行化？

### 2.2 改进阶段（Improvement）

改进的核心机制是**用 LLM 自身来优化 Agent 的配置**。这实际上是一个"元提示词工程（Meta-Prompting）"过程。

#### Tool 描述自动改进

Tool 描述的质量直接影响 LLM 是否能在正确的时机选择正确的工具。常见的优化模式：

```python
# 原始描述（模糊）
{
    "name": "search_knowledge_base",
    "description": "搜索知识库获取信息",
    "parameters": {...}
}

# 改进后的描述（具体、有场景提示）
{
    "name": "search_knowledge_base",
    "description": "当用户询问技术概念、历史决策或项目规范时，"
                   "优先使用此工具搜索内部知识库。"
                   "适用于事实性问题（What/Why/How），"
                   "不适用于需要实时数据的查询。"
                   "注意：搜索关键词应提取核心实体而非完整句子。",
    "parameters": {...}
}
```

自动改进流程：

```
┌─────────────────────┐
│  收集失败案例         │  例：用户问"Python GIL是什么"
│  (Tool Selection     │  Agent 选择了 calculator 而非
│   Failure Cases)     │  search_knowledge_base
└──────────┬──────────┘
           ▼
┌─────────────────────┐
│  分析失败模式         │  "description不够具体，没有说明
│  (Pattern Analysis)  │   适用场景和反例"
└──────────┬──────────┘
           ▼
┌─────────────────────┐
│  LLM 生成优化建议     │  → "补充：适用于事实性问题，
│                      │    不适于计算任务"
└──────────┬──────────┘
           ▼
┌─────────────────────┐
│  A/B 测试验证        │  新描述 → 跑历史案例 → 对比召回率
└─────────────────────┘
```

#### Skill 自动优化

Skill（或称为"子流程"、"能力单元"）是多步操作的模板。自动优化的对象包括：

1. **Skill 的触发条件**：什么情况下应该调用这个 Skill？
2. **Skill 的执行步骤**：步骤顺序是否合理？是否有冗余？
3. **Skill 中的 Prompt**：子任务的指令是否清晰？

```yaml
# 优化前的 Skill：代码审查
skill_review_code:
  trigger: "用户请求代码审查"
  steps:
    - "阅读代码"
    - "找出问题"
    - "给出建议"

# 优化后的 Skill（经过自动改进）
skill_review_code:
  trigger: "用户请求代码审查 或 提交了 Pull Request"
  steps:
    - "步骤1：理解代码上下文——检查代码所属模块、关联文件"
    - "步骤2：安全性审查——查找 SQL 注入、XSS、敏感信息泄露"
    - "步骤3：性能审查——识别 N+1 查询、内存泄漏、不必要的重复计算"
    - "步骤4：可维护性审查——命名规范、函数长度、注释质量"
    - "步骤5：生成结构化报告——按严重程度分类发现的问题"
  prompt_template: |
    你是一个资深的代码审查专家。请按照以下维度审查代码：
    1. 安全性（最高优先级）
    2. 性能
    3. 可维护性
    4. 最佳实践
    对每个发现的问题给出严重程度（CRITICAL/MAJOR/MINOR）和修复建议。
```

## 三、关键技术挑战

### 3.1 评估信号的可靠性

自我进化的最大风险是"在错误的方向上越走越远"。如果评估信号不准确，改进反而会降低性能。

**解决方案**：
- **人类参与验证（Human-in-the-Loop）**：关键改进需要人工确认。
- **渐进式部署**：在影子模式（Shadow Mode）下运行新版本，对比新旧版本的效果后再切换。
- **回滚机制**：保存每个 Skill/Tool 的历史版本，支持一键回退。

### 3.2 改进的稳定性

LLM 生成的改进文本可能引入新的问题：

```
原始描述："搜索用户手册"
LLM 改进后："仅当用户明确说"查手册"时才搜索用户手册"
```
这个改进过于严格，导致召回率骤降。

**应对策略**：使用**约束生成**（见第 14.6 节），确保改进的幅度可控，避免"过度优化"。

### 3.3 冷启动问题

新注册的 Tool 或 Skill 缺乏历史执行数据，无法评估。

**应对策略**：提供**种子示例（Seed Examples）**——开发者预先给出一些典型的正确/错误调用案例，作为初始评估基准。

## 四、工业界实践案例

### 4.1 自动 Prompt 优化工具

- **DSPy**：声明式编程框架，自动优化 LLM 程序的 Prompt 和权重。
- **TextGrad**：将 LLM 输出的文本作为"计算图"，通过反向传播思想自动优化 Prompt。

两者的对比：

| 特性 | DSPy | TextGrad |
|------|------|----------|
| 优化对象 | Prompt、示例、权重 | Prompt |
| 优化方法 | 贝叶斯搜索+LLM 评判 | 文本梯度下降 |
| 适用范围 | 分类、RAG、Agent | 任意文本输出任务 |
| 需要标注数据 | 少量 | 不需要 |
| 可解释性 | 中 | 低 |

## 五、关键概念速查表

| 概念 | 英文 | 解释 |
|------|------|------|
| 自我进化 Agent | Self-Evolving Agent | 能自动评估并改进自身能力的 Agent |
| 元学习 | Meta-Learning | 学习如何学习，优化学习策略本身 |
| 评估阶段 | Evaluation Phase | 收集执行轨迹并评估质量的阶段 |
| 改进阶段 | Improvement Phase | 根据评估反馈修改配置的阶段 |
| LLM-as-Judge | LLM as Judge | 用 LLM 评估另一个 LLM 的输出质量 |
| 元提示词工程 | Meta-Prompting | 用 LLM 优化 Prompt 本身的技术 |
| 影子模式 | Shadow Mode | 新版本与旧版本并行运行但不生效的模式 |
| DSPy | Declarative Self-improving Python | 声明式自动优化框架 |
| 冷启动问题 | Cold Start Problem | 缺乏历史数据导致无法评估 |
| 版本管理 | Versioning | 保留配置历史支持回滚 |
