# 26.5 形式化验证在 Agent 中的应用

> 形式化验证（Formal Verification）是用数学方法证明系统行为满足特定规范的技术。在 Agent 工程中，形式化验证用于在关键决策路径上提前发现逻辑错误、死循环、越权行为和资源泄露等问题，为"黑盒"的 LLM 决策提供数学级别的正确性保证。

---

## 一、为什么 Agent 需要形式化验证

### 1.1 LLM 的不确定性困境

LLM-based Agent 的核心矛盾在于：**决策过程基于概率模型，但某些决策后果是不可逆的**。

- 一个错误的 SQL 删除操作可能导致数据永久丢失。
- 一个错误的金融交易指令可能导致数万美元损失。
- 一个错误的权限授予可能导致安全漏洞。

传统的测试方法（单元测试、集成测试、E2E 测试）只能覆盖有限的"预期路径"，无法穷举 Agent 可能遇到的所有状态组合。形式化验证提供了**数学上的全量化保证**——对于验证通过的属性，Agent 在所有可能的执行路径上都满足该属性。

### 1.2 形式化验证 vs 传统测试

| 维度 | 传统测试 | 形式化验证 |
|------|----------|------------|
| **覆盖范围** | 有限的测试用例 | 所有可能的执行路径 |
| **结论类型** | "没发现 bug" | "证明了没有某类 bug" |
| **适用阶段** | 开发后期 | 设计+开发全程 |
| **自动化程度** | 高度自动 | 需要人工建模 |
| **可扩展性** | 好 | 差（状态爆炸问题） |
| **对 LLM 的适用性** | 直接 | 需要抽象建模 |

### 1.3 形式化验证在 Agent 中的三个层次

```
Agent 形式化验证的三个层次：

层次1：工具调用验证（最易实现，收益最高）
  ┌──────────────────────────────────────────┐
  │  验证 Agent 对工具的调用参数是否合法        │
  │  - 类型检查（字符串 vs 整数）               │
  │  - 取值范围检查（ID 是否在有效范围内）        │
  │  - 权限检查（Agent 是否有权限调用此工具）      │
  └──────────────────────────────────────────┘

层次2：工作流验证
  ┌──────────────────────────────────────────┐
  │  验证 Agent 的多步工作流是否满足业务规则      │
  │  - 操作顺序约束（必须先登录再下单）            │
  │  - 资源访问约束（数据不可跨用户访问）          │
  │  - 终止性保证（工作流一定会结束）              │
  └──────────────────────────────────────────┘

层次3：决策逻辑验证（最具挑战性）
  ┌──────────────────────────────────────────┐
  │  验证 Agent 的决策是否符合预期策略           │
  │  - 策略一致性（相同的上下文得出相同结论）      │
  │  - 公平性（不基于敏感属性做歧视性决策）        │
  │  - 可解释性约束（决策必须有可理解的推理链）    │
  └──────────────────────────────────────────┘
```

## 二、形式化验证的核心技术

### 2.1 模型检测（Model Checking）

模型检测是最成熟的形式化验证技术。其核心思想是：**穷举搜索系统所有可能的状态，检查每个状态是否满足给定的属性规范**。

```
模型检测流程：

┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐
│ Agent行为 │   │ 建模      │   │ 规范     │   │ 验证器   │
│ 描述      │ → │ (Formal   │ → │ (Spec    │ → │ (Model   │ → 通过/反例
│ (代码/文档)│   │  Model)  │   │  Logic)  │   │ Checker) │
└──────────┘   └──────────┘   └──────────┘   └──────────┘
```

**Agent 行为的形式化建模示例**（使用 TLA+ 语言风格）：

```
---------------------------- MODULE AgentWorkflow ----------------------------
EXTENDS Integers, Sequences

(* 状态定义 *)
VARIABLES 
    step,           \* 当前步骤编号
    authenticated,  \* 是否已认证
    data_accessed,  \* 已访问的数据ID集合
    terminated      \* 是否已结束

(* 初始状态 *)
Init == 
    /\ step = 0
    /\ authenticated = FALSE
    /\ data_accessed = {}
    /\ terminated = FALSE

(* 步骤1: 认证 *)
Authenticate ==
    /\ step = 0
    /\ authenticated = FALSE
    /\ step' = 1
    /\ authenticated' = TRUE
    /\ UNCHANGED data_accessed

(* 步骤2: 查询数据 *)
QueryData ==
    /\ step = 1
    /\ authenticated = TRUE
    /\ step' = 2
    /\ data_accessed' = data_accessed \cup {CurrentDataId}
    /\ UNCHANGED authenticated

(* 步骤3: 结束 *)
Finish ==
    /\ step = 2
    /\ terminated' = TRUE
    /\ UNCHANGED <<step, authenticated, data_accessed>>

(* 完整的 Next 关系 *)
Next == Authenticate \/ QueryData \/ Finish

(* 要验证的属性 *)
(* 属性1: Agent 必须先认证才能访问数据 *)
SafetyProperty1 == 
    [](data_accessed /= {} => authenticated)

(* 属性2: Agent 最终一定会结束 *)
LivenessProperty == 
    <>(terminated = TRUE)

================================================================================
```

### 2.2 运行时验证（Runtime Verification）

对于无法静态建模的 Agent 系统，运行时验证在 Agent 实际执行过程中**实时监控**行为是否符合规范。

```python
class RuntimeMonitor:
    """
    Agent 运行时验证器。在 Agent 执行过程中实时检查操作合法性。
    """
    
    def __init__(self):
        self.state = AgentState()
        self.violations = []
    
    def before_action(self, action: Action):
        """
        在 Agent 执行操作前检查是否允许。
        如果检查不通过，可以阻止操作。
        """
        # 安全检查：操作对象是否有权限访问
        if not self._check_permission(action):
            raise PermissionError(f"Agent 无权执行此操作: {action}")
        
        # 顺序检查：操作顺序是否合法
        if not self._check_order(action):
            raise OrderViolationError(
                f"操作顺序违规: 当前状态 {self.state.step}, "
                f"不允许执行 {action.type}"
            )
        
        # 资源检查：是否超出资源限制
        if not self._check_resource(action):
            raise ResourceLimitError("操作超出资源限制")
    
    def after_action(self, action: Action, result: ActionResult):
        """
        操作后更新验证状态。
        """
        self.state = self._transition(self.state, action, result)
        
        # 检查后置条件
        for invariant in self.invariants:
            if not invariant.check(self.state):
                self.violations.append(
                    InvariantViolation(invariant, self.state)
                )
```

### 2.3 符号执行（Symbolic Execution）

符号执行不运行具体的输入值，而是用**符号变量**代替具体值，沿着所有可能的执行路径进行计算，最终得到每一条路径上的约束条件。

在 Agent 中的应用场景：

```python
# 假设 Agent 有一个退款决策函数
def refund_decision(order_value: float, days_since_purchase: int, 
                    is_vip: bool) -> str:
    """决定是否允许退款"""
    if days_since_purchase > 30:
        return "rejected"  # 超过30天拒绝退款
    
    if is_vip:
        return "approved"  # VIP 直接批准
    
    if order_value > 1000:
        return "manual_review"  # 大额订单人工审核
    
    return "approved"  # 正常批准

# 符号执行可以回答以下问题：
# 问题1：是否存在一个输入，使 Agent 同时返回 "approved" 和 "rejected"？
# → 符号执行证明：该函数是确定性的，没有歧义路径

# 问题2：是否存在一个 >30 天的 VIP 客户被批准的情况？
# → 符号执行发现：线路 days_since_purchase > 30 → "rejected" 
#   检查所有分支后，确认 VIP 状态不会覆盖 30 天规则
#   但需要确认这是否是预期行为
```

### 2.4 抽象解释（Abstract Interpretation）

对于状态空间过大的系统，抽象解释通过**抽象域**来近似计算程序行为。

在 Agent 中的示例：

```
抽象域：将具体值映射为抽象值

具体值域           抽象值域（抽象解释使用）
0, 1, 2, ...  →    Positive
-1, -2, ...   →    Negative
0             →    Zero

Agent 工具调用参数验证：
- 具体：page_size = 5000, offset = -1
- 抽象：page_size ∈ Positive, offset ∈ Negative
- 验证规则：offset 必须 ≥ 0
- 抽象检查：Negative ⊆ NonNegative ? → 否 → 发现错误！
```

## 三、形式化验证在 Agent 中的典型应用

### 3.1 工具调用约束验证

```python
class ToolInvocationVerifier:
    """
    验证 Agent 对工具的调用是否符合约束规范。
    使用形式化方法验证参数合法性。
    """
    
    # 工具调用的形式化规范
    SPECS = {
        "delete_user": {
            "precondition": "role == 'admin'",      # 只有管理员可以删除用户
            "param_constraints": [
                "user_id > 0",                       # 用户 ID 必须为正
                "user_id != current_user_id"         # 不能删除自己
            ],
            "postcondition": "user_exists(user_id) == False"
        },
        "transfer_money": {
            "precondition": "amount > 0",            # 金额必须为正
            "param_constraints": [
                "amount <= daily_limit",             # 不超过日限额
                "from_account != to_account"         # 不能转账给自己
            ],
            "postcondition": "balance(from_account) == old_balance - amount"
        }
    }
    
    def verify(self, tool_name: str, params: dict, context: Context) -> VerificationResult:
        spec = self.SPECS[tool_name]
        
        # 验证前置条件
        for precondition in spec["precondition"]:
            if not self._evaluate(precondition, context):
                return VerificationResult(
                    passed=False,
                    reason=f"前置条件不满足: {precondition}"
                )
        
        # 验证参数约束
        for constraint in spec["param_constraints"]:
            if not self._evaluate(constraint, params):
                return VerificationResult(
                    passed=False,
                    reason=f"参数约束不满足: {constraint}"
                )
        
        return VerificationResult(passed=True)
```

### 3.2 工作流终止性证明

"Agent 是否会陷入死循环？"——这是部署 Agent 时最令人担忧的问题之一。

```
终止性证明的常用方法：良基序（Well-Founded Order）

1. 为 Agent 状态定义一个"度量函数" f(state) → NaturalNumber
2. 证明 Agent 的每一步操作都会使 f 严格递减
3. 由于自然数不能无限递减，Agent 必然终止

Agent 工作流的终止性度量示例：

工作流：客服 Agent 处理退款
度量函数 f(state) = 
    待处理退款数量 × 100 +
    当前步骤序号（越往后越小）
    
证明：
- 每处理一个退款申请，待处理数量 -1
- 每进入下一步，步骤序号递减
- 由于两个分量都非负且每一步至少有一个递减
- f 严格递减 → Agent 必然终止
```

### 3.3 安全策略的形式化验证

```python
# 安全策略的线性时态逻辑（LTL）规范

# Safety: Agent 永远不能直接访问密码表
G(access("password_table") → False)

# Safety: 删除操作前必须有备份
G(delete(file) → O(backup(file)))
# 解释：Globally, 删除文件前必须先备份该文件

# Liveness: 所有提交的工单最终都会被处理
G(submitted(ticket) → F(processed(ticket)))
# 解释：Globally, 如果工单已提交，最终(Future)会被处理
```

## 四、工程实践中的挑战与取舍

### 4.1 状态爆炸问题

Agent 的状态空间通常非常庞大（连续变量、多 Agent 并发），直接模型检测不可行。

**应对策略**：

| 策略 | 描述 | 适用场景 |
|------|------|----------|
| **抽象（Abstraction）** | 忽略与验证属性无关的细节 | 工具调用参数验证 |
| **分解（Compositional）** | 将大系统拆分为小模块分别验证 | Multi-Agent 系统 |
| **有界验证（Bounded）** | 只验证 K 步内的所有路径 | 短周期工作流 |
| **统计验证（Statistical）** | 用采样代替穷举的近似验证 | 非安全关键路径 |

### 4.2 验证 vs 实际执行的差距

形式化建模必然是对真实系统的**简化**。模型验证通过不代表真实系统一定正确。

**弥合差距的方法**：
- **细化验证（Refinement Verification）**：逐步细化模型，使模型越来越接近真实实现。
- **运行时验证互补**：静态验证覆盖"设计时"错误，运行时验证覆盖"实现时"错误。

## 五、关键概念速查表

| 概念 | 英文 | 解释 |
|------|------|------|
| 形式化验证 | Formal Verification | 用数学方法证明系统正确性的技术 |
| 模型检测 | Model Checking | 穷举搜索系统状态空间检查属性是否满足 |
| 运行时验证 | Runtime Verification | 系统运行时实时监控行为是否符合规范 |
| 符号执行 | Symbolic Execution | 用符号变量代替具体值穷举执行路径 |
| 抽象解释 | Abstract Interpretation | 用抽象域近似计算程序行为的静态分析 |
| 线性时态逻辑 | LTL (Linear Temporal Logic) | 描述时间相关属性的逻辑语言 |
| 不变量 | Invariant | 在所有状态下都必须成立的属性 |
| 终止性证明 | Termination Proof | 证明程序在所有输入下都会结束 |
| 状态爆炸 | State Explosion | 系统状态数随组件数量指数增长的问题 |
| 细化验证 | Refinement Verification | 逐层细化形式模型使其逼近真实实现 |
