# 选型决策指南 —— 按复杂度 x 性能 x 合规 x 团队能力的四维评估矩阵

## 概述

选择合适的 Agent 框架是项目成功的关键决策。本章提供了一个系统化的决策框架，帮助团队根据 **业务复杂度、性能要求、合规约束** 和 **团队能力** 四个维度评估和选择最合适的框架。

六个核心框架/项目的定位总览：

| 框架 | 一句话定位 | 最佳场景 |
|---|---|---|
| **LangGraph** | 有状态图驱动的复杂工作流 | 状态密集型、审计关键、人工审批 |
| **CrewAI** | 角色扮演式多 Agent 协作 | 内容流水线、营销自动化、快速原型 |
| **MAF** | 企业级双语言 Agent 框架 | 微软栈、Copilot 集成、企业合规 |
| **AG2** | AutoGen 社区分支延续 | 存量 AutoGen 迁移、Actor 模型需求 |
| **Agno** | 轻量高性能的 Agent 核心 | 延迟敏感、Serverless、嵌入式 Agent |
| **Google ADK** | Google 原生 Agent 框架 | Gemini 生态、Google 服务集成 |

> **AutoGen 已不再推荐用于新项目**（2025 年 9 月进入维护模式），新项目应选用 **MAF**（微软栈）或 **AG2**（社区版）作为替代。详见 [4.3-AutoGen.md](./4.3-AutoGen.md)。关于 PydanticAI、DSPy、LangChain、LlamaIndex、Mastra、OpenAI Agents SDK 等框架的详细分析，请参见 [4.5-其他框架技术定位.md](./4.5-其他框架技术定位.md)。

## 四维评估矩阵

### 维度一：业务复杂度（Complexity）

评估 Agent 应用所需的 **工作流复杂度** 和 **Agent 协作深度**。

| 复杂度级别 | 特征 | 推荐框架 | 不推荐 |
|---|---|---|---|
| **L1 - 简单** | 单 Agent，单轮/多轮对话，无工具或少工具调用 | Agno, PydanticAI, OpenAI Agents SDK | LangGraph, MAF（过度设计） |
| **L2 - 中等** | 单 Agent + 工具调用 + RAG，流程线性 | CrewAI, Agno, Mastra | MAF（学习成本偏高） |
| **L3 - 复杂** | 多 Agent 协作，条件分支，人工介入 | LangGraph, CrewAI（层次模式） | Agno（多 Agent 支持弱） |
| **L4 - 极复杂** | 大规模多 Agent，分布式部署，异步通信 | LangGraph, MAF, AG2 | CrewAI（控制粒度不足） |

**关键问题清单**：
- Agent 数量：1 个 / 2-5 个 / 5+ 个
- 工作流模式：线性 / 条件分支 / 循环 / 图拓扑
- 是否需要人工介入审核环节？
- 是否需要 Agent 之间的实时通信？
- 是否需要分布式部署？

### 维度二：性能要求（Performance）

评估应用的 **延迟敏感度、吞吐量需求** 和 **资源约束**。

```python
# 性能评估基准代码示例
import time
import psutil

def benchmark_framework(framework_name, agent_factory):
    """评估框架的实例化性能"""
    # 实例化时间
    start = time.perf_counter()
    agent = agent_factory()
    instantiation_ms = (time.perf_counter() - start) * 1000
    
    # 内存占用
    memory_mb = psutil.Process().memory_info().rss / 1024 / 1024
    
    return {
        "framework": framework_name,
        "instantiation_ms": instantiation_ms,
        "memory_mb": memory_mb
    }
```

| 性能指标 | LangGraph | CrewAI | AG2 | Agno |
|---|---|---|---|---|---|
| **实例化耗时（单 Agent）** | ~5,290 ms | ~1,180 ms | ~120 ms | **~10 ms** |
| **内存占用（空闲 Agent）** | ~245 MB | ~189 MB | ~180 MB | **~32 MB** |
| **首 token 延迟（含 LLM）** | 中高（图编排开销） | 中 | 中 | **低** |
| **并发吞吐量** | 中（串行图） | 中 | **高**（Actor 并发） | 中高 |
| **镜像体积** | ~1.2 GB | ~890 MB | ~650 MB | **~180 MB** |
| **简单任务耗时** | **<5s (<900 tokens)** | 可能消耗 3x Token | - | 低 |
| **状态管理稳定性** | **100/100** | 80/100 | - | 90/100 |
| **开发效率（快速原型）** | 中（3-5天） | **高（2-4h）** | 中 | 高 |

**性能决策规则**：

```
Q: 是否需要亚秒级 Agent 实例化？
├── 是 → Agno（唯一选择）
└── 否 → 继续评估其他维度

Q: 是否对资源消耗敏感（内存/存储）？
├── 是 → Agno > AutoGen > CrewAI > LangGraph
└── 否 → 继续评估其他维度

Q: 是否需要高并发多 Agent 执行？
├── 是 → AG2（Actor 原生并发）或 MAF
└── 否 → 继续评估其他维度

Q: 是否需要稳定可靠的状态管理？
├── 是 → LangGraph（100/100 稳定性评分）
└── 否 → 继续评估其他维度

Q: 开发效率是否优先于运行效率？
├── 是 → CrewAI（2-4h 快速原型，但注意 3x Token 开销）
└── 否 → 继续评估其他维度
```

### 维度三：合规约束（Compliance）

评估 **数据安全、审计追踪、可解释性** 等方面的要求。

| 合规需求 | LangGraph | CrewAI | MAF | AG2 | Agno |
|---|---|---|---|---|
| **审计追踪** | 内置检查点+时间旅行 | 有限（日志级别） | Entra ID 审计 | 消息日志 | Session 记录 |
| **人工审批** | 一等公民（interrupt） | 有限 | 内置审批流 | 通过消息拦截 | 需自定义 |
| **数据隔离** | 检查点存储隔离 | Session 隔离 | 企业级租户隔离 | Actor 私有状态 | Session Memory |
| **可解释性** | 高（状态可回溯） | 中（角色定义） | 高（Azure 审计） | 中高（消息流） | 中（上下文透明） |
| **PBAC/访问控制** | 需自定义 | 企业版提供 | 原生 Entra ID | 需自定义 | 需自定义 |
| **数据本地化** | 支持（SQLite/PG） | 支持 | Azure 区域选择 | 支持（分布式） | 支持（多存储） |

**合规决策规则**：

```
Q: 是否需要完整的执行审计追踪？
├── 是 → LangGraph（检查点 + 时间旅行调试）
└── 否 → 继续评估

Q: 是否需要频繁的人工审批环节？
├── 是 → LangGraph（interrupt 原生支持）
├── 部分需要 → MAF（内置审批流）或 AG2（消息拦截模式）
└── 不需要 → 继续评估

Q: 是否有严格的数据隔离要求？
├── 是 → MAF（企业级租户隔离）或 AG2（Actor 私有状态）
│         或 Agno（Session Memory 隔离）
└── 否 → 继续评估其他维度

Q: 是否需要 Microsoft Entra ID / Azure AD 集成？
├── 是 → MAF（原生 Entra ID 认证）
└── 否 → 继续评估其他维度
```

### 维度四：团队能力（Team Capability）

评估 **团队的技术栈熟悉度、学习能力和工程实践水平**。

| 团队画像 | LangGraph | CrewAI | AutoGen | Agno |
|---|---|---|---|---|
| **Python 初级** | 不推荐（学习曲线陡） | **推荐**（直觉 API） | 不推荐 | 不推荐 | 推荐（API 简洁） |
| **Python 中级** | 推荐（可控学习） | 推荐 | 需要投入学习 | 需要投入学习 | **强烈推荐** |
| **Python 高级 + 异步经验** | 推荐 | 简单场景 | 推荐 | **强烈推荐** | 推荐 |
| **分布式系统经验** | 推荐 | 不推荐 | 推荐 | **强烈推荐** | 一般 |
| **微软技术栈团队** | 一般 | 一般 | **强烈推荐** | 一般 | 一般 |

**团队能力自评清单**（每个项目 1-5 分自评）：

1. **Python 类型系统掌握程度**（Pydantic、TypedDict 等）
2. **异步编程经验**（asyncio、消息队列、Actor 模型）
3. **分布式系统经验**（微服务、消息中间件、gRPC）
4. **LLM/Prompt 工程经验**（Chain-of-Thought、Function Calling）
5. **DevOps 能力**（Docker、K8s、CI/CD）

**得分与推荐框架**：
- 15-25 分（团队能力强）：可驾驭任何框架，推荐 LangGraph 或 MAF/AG2
- 10-14 分（团队能力中等）：推荐 LangGraph 或 CrewAI
- 5-9 分（团队能力基础）：推荐 Agno 或 CrewAI

## 场景化推荐

### 场景 1：企业内部知识库问答机器人

**需求分析**：
- 复杂度：L1-L2（单 Agent，RAG 查询，线性流程）
- 性能：中等（用户可接受 2-3 秒响应）
- 合规：高（必须审计查询历史和数据来源）
- 团队：Python 中级，无分布式经验

**推荐方案**：
```
首选：Agno + LlamaIndex
  - Agno：轻量、内置 Session Memory 记录查询历史
  - LlamaIndex：业界最强的 RAG 和数据索引能力
  - 合规：SQLite/Postgres 持久化，完整查詢日志

备选：LangGraph + LlamaIndex
  - 如果需要更复杂的多轮推理或多步 RAG 流程
```

### 场景 2：自动化营销内容流水线

**需求分析**：
- 复杂度：L2-L3（多 Agent 协作：调研 → 写作 → 审核 → 发布）
- 性能：低（批处理任务，数分钟完成可接受）
- 合规：低
- 团队：包含非技术人员参与 Agent 定义

**推荐方案**：
```
首选：CrewAI
  - 角色扮演范式直观，非技术人员可参与 Agent 定义
  - 层次执行模式适合内容审核流程
  - YAML 配置降低代码维护成本

备选：LangGraph
  - 如果需要在内容流水线中加入复杂条件分支和人工审批
```

### 场景 3：金融交易分析系统

**需求分析**：
- 复杂度：L4（多 Agent 协作，实时数据流，需人工干预）
- 性能：高（低延迟，高吞吐）
- 合规：极高（完整审计，SLA 保障，数据隔离）
- 团队：高级工程师，有分布式系统经验

**推荐方案**：
```
首选：LangGraph
  - 有状态图模型天然支持完整审计追踪和时间旅行调试
  - 检查点持久化提供 100/100 的状态管理稳定性
  - interrupt 机制原生支持人工审批环节

辅助：
  - PydanticAI 用于输出类型安全约束（参见 4.5）
  - LangSmith 用于可观测性（独立于 LangChain 使用）

备选：MAF（微软技术栈）或 AG2（Actor 模型需求）
  - MAF 提供企业级 Entra ID 认证和 Azure 审计
  - AG2 保留 Actor 模型的并发和数据隔离优势
```

### 场景 4：实时客服系统

**需求分析**：
- 复杂度：L1-L2（单 Agent，工具调用，知识库检索）
- 性能：极高（亚秒级响应）
- 合规：中（对话记录保存即可）
- 团队：Python 中高级

**推荐方案**：
```
首选：Agno
  - 极低的 Agent 实例化开销适合按需创建
  - Serverless 友好，可部署在边缘节点
  - 首 token 延迟最低

备选：Mastra（TypeScript 栈）或 AG2（Python 多 Agent）
  - Mastra 与前端 TypeScript 生态自然集成
  - AG2 支持多个垂直 Agent 协作（如：订单查询 Agent + 退款 Agent）
```

### 场景 5：研发团队的多 Agent 研究助手

**需求分析**：
- 复杂度：L4（多个 Agent 协作研究，工具调用，长上下文推理）
- 性能：中等（离线研究任务，分钟级可接受）
- 合规：中（记录研究过程即可）
- 团队：Python 高级，有 asyncio 经验

**推荐方案**：
```
首选：LangGraph 或 AG2
  - LangGraph：适合需要精细控制研究步骤的场景
  - AG2：适合需要大量 Agent 并行研究的场景（继承 AutoGen Actor 模型）

辅助：
  - DSPy 优化关键研究步骤的 Prompt（参见 4.5）
  - LlamaIndex 管理和检索研究资料
```

## 框架迁移路径

框架选型不是一劳永逸的。项目发展过程中，需求可能变化，团队能力可能提升。以下提供常见的迁移路径：

```
项目初期（MVP）                项目中期（增长）             项目成熟期（规模化）
─────────────────────────────────────────────────────────────────────────
Agno ──────────────────▶ LangGraph ──────────────────▶ LangGraph + MAF
（快速原型，单 Agent）      （复杂工作流，多 Agent）     （企业级合规与扩展）

Agno ──────────────────▶ CrewAI ─────────────────────▶ LangGraph
（快速原型）                （多 Agent 协作原型）         （精细化控制）

CrewAI ─────────────────▶ LangGraph ─────────────────▶ MAF / AG2
（快速上线）                （增加审计和状态管理）        （企业级/分布式扩展）

AutoGen(存量) ──────────▶ AG2 ───────────────────────▶ MAF
（维护模式代码）            （社区延续，最小改动）         （官方企业级方案）
```

迁移时的关键注意事项：

1. **保持接口兼容**：使用适配器模式（Adapter Pattern）封装 Agent 调用的统一接口
2. **数据迁移**：确保 Session/状态数据可以从旧框架导出并导入新框架
3. **渐进式迁移**：将非核心模块先迁移，核心模块最后迁移
4. **回滚机制**：保留旧框架的部署版本，确保能够快速回滚

```python
# 适配器模式示例：统一 Agent 接口
from abc import ABC, abstractmethod

class AgentPort(ABC):
    """统一的 Agent 接口，隔离框架依赖"""
    
    @abstractmethod
    async def run(self, task: str) -> str: ...
    
    @abstractmethod
    async def stream(self, task: str) -> AsyncIterator[str]: ...

# LangGraph 适配器
class LangGraphAdapter(AgentPort):
    def __init__(self):
        from langgraph.graph import StateGraph
        self.graph = self._build_graph()
    
    async def run(self, task: str) -> str:
        return await self.graph.ainvoke({"input": task})

# Agno 适配器
class AgnoAdapter(AgentPort):
    def __init__(self):
        from agno import Agent
        self.agent = Agent(model="gpt-4o")
    
    async def run(self, task: str) -> str:
        return await self.agent.arun(task)

# 切换框架只需更换适配器实现
agent: AgentPort = AgnoAdapter()  # MVP 阶段
# agent = LangGraphAdapter()      # 增长阶段
# agent = MAFAdapter()            # 企业级阶段
```

## 反模式：常见选型错误

### 错误 1：过早选择重型框架

**表现**：项目只有 1 个 Agent + 2 个工具，却选择了 LangGraph 或 MAF。

**后果**：
- 开发效率降低 3-5 倍
- 不必要的学习成本
- 部署和维护复杂度增加

**正确做法**：从 Agno 或直接调用 LLM API 开始，当工作流复杂度确实超出轻量框架能力时再迁移。

### 错误 2：忽略团队能力

**表现**：招了一个有 Actor 模型经验的架构师，就选择 AG2，但团队其他成员没有异步编程经验。

**后果**：
- 代码质量参差不齐
- 调试和维护困难
- 成为"一个人的框架"，其他成员无法参与

**正确做法**：评估整个团队的能力，而不是 1-2 个人的能力。必要时选择学习曲线较低的框架。

### 错误 3：性能基准误导

**表现**：因为 Agno "快 529 倍"的数据而选择它，但应用场景并不需要这种极致的性能。

**后果**：
- 失去了 LangGraph/MAF 的高级编排能力
- 过早优化（premature optimization）

**正确做法**：先确定功能需求，再评估性能。绝大多数业务应用在 P95 延迟 2-5 秒范围内都可接受。

### 错误 4：框架锁定的恐惧

**表现**：担心被框架锁定，试图自己"封装一层"来保持灵活性。

**后果**：
- 封装层本身就是一种"自定义框架锁定"
- 封装层的维护成本可能超过框架本身
- 失去了框架生态的优势（社区支持、更新、插件）

**正确做法**：接受一定程度的框架绑定，但保持核心业务逻辑与框架的松耦合（如上文的适配器模式）。

## 2026年行业趋势与框架生态展望

### 1. AutoGen 退场与生态分裂

AutoGen 于 2025 年 9 月进入维护模式，标志着第一代 Agent 框架的转折点。其技术遗产分裂为两个方向：
- **MAF（Microsoft Agent Framework）**：微软官方继任者，Python+C# 双语言，与 Microsoft 365 深度集成
- **AG2（ag2ai/ag2）**：社区维护分支，Apache 2.0 许可证，延续 AutoGen API 风格

**启示**：选择框架时需考虑厂商长期承诺和社区健康度。依赖单一厂商的开源项目存在风险。

### 2. Provider 原生 SDK 崛起

OpenAI（Agents SDK）、Google（ADK）、Anthropic（Claude API 原生工具调用）等模型提供商纷纷推出自己的 Agent SDK/框架。这些 SDK 的特点是：
- 与自家模型深度优化，开箱即用
- API 设计极简，学习成本低
- 但生态绑定强，切换模型成本高

**趋势**：Provider 原生 SDK 将蚕食通用框架的"简单场景"市场份额，通用框架需在复杂编排、多模型支持、企业级功能上持续差异化。

### 3. TypeScript 生态成熟

Mastra 等 TypeScript 原生 Agent 框架的崛起，使得 JavaScript/TypeScript 生态不再依赖 Python 框架的桥接。这对以下场景意义重大：
- 全栈开发团队无需跨语言切换
- 前端应用可直接集成 Agent 能力
- Serverless/Edge 运行时（Vercel Edge、Cloudflare Workers）的 Agent 部署

### 4. 评估体系标准化

2025-2026 年，Agent 评估体系逐步标准化：
- **OpenTelemetry GenAI semconv**：LLM 调用追踪的行业标准语义约定
- **Agent 基准测试**：GAIA、SWE-bench、AgentBench 等基准成为行业标配
- **框架原生可观测性**：LangSmith、LangFuse 等工具与框架深度集成

### 5. 选型范式的转变

2026 年 Agent 框架选型的核心问题从"哪个最流行"转向"**哪个架构最匹配预期的失败模式**"：

| 失败模式 | 最匹配的框架 |
|---|---|
| 状态丢失 / 流程中断 | LangGraph（检查点持久化 100/100） |
| 开发周期过长 | CrewAI（2-4h 快速原型） |
| Token 消耗过高 | LangGraph（简单任务 <900 tokens） |
| 合规审计不达标 | MAF / LangGraph（完整审计链） |
| 厂商锁定风险 | AG2 / Agno（开源中立） |
| 团队技术栈不匹配 | Mastra（TS）/ Agno（轻量 Python） |

## 关键概念速查

| 概念 | 解释 |
|---|---|
| **四维评估矩阵** | 从复杂度、性能、合规、团队能力四个维度评估框架适配度的方法 |
| **适配器模式** | 一种设计模式，通过统一接口隔离框架依赖，便于框架迁移 |
| **过早优化** | 在未明确性能需求时过度追求性能指标，导致不必要的架构复杂度 |
| **框架绑定** | 项目对特定框架的依赖程度，完全绑定意味着更换框架需要重写大量代码 |
| **首 token 延迟** | 从发起请求到收到 LLM 第一个输出 token 的时间，是用户体验的关键指标 |
| **P95 延迟** | 百分之九十五的请求在多少毫秒内完成，衡量系统性能的常用指标 |
| **MVP** | 最小可行产品，用最小的开发成本验证产品需求 |
| **渐进式迁移** | 逐步将系统从一个框架迁移到另一个框架的策略，每次迁移一个模块 |
| **失败模式匹配** | 2026 年框架选型的核心范式——选择最匹配项目预期失败模式的架构 |
| **Provider 原生 SDK** | 模型提供商（OpenAI/Google/Anthropic）推出的自有 Agent SDK |
| **OpenTelemetry GenAI semconv** | LLM 调用追踪的行业标准语义约定，推动 Agent 可观测性标准化 |
| **MAF** | Microsoft Agent Framework，AutoGen 官方继任者，双语言企业级框架 |
