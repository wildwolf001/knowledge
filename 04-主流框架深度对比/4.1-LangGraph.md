# LangGraph — 有状态图驱动的 Agent 框架

## 概述

LangGraph 是由 **LangChain Inc.** 开发并开源的有状态 Agent 编排框架。与 LangChain 的 "DAG-of-chains" 模型不同，LangGraph 将 Agent 建模为 **有状态的有向图**（stateful directed graph），其中节点（nodes）代表计算步骤，边（edges）代表状态转换。这种设计使其特别适合需要循环、分支和恢复的复杂多步骤工作流。

截至 2026 年 5 月，LangGraph 的 Python 库版本为 **langgraph 1.1.10**，配套 SDK（LangGraph Cloud/Platform）版本为 **0.3.14**，GitHub 星标超过 **31.4k**。LangGraph 已成为 LangChain 生态中 Agent 编排的核心引擎——**LangChain v1 的高层 Agent API（如 `create_react_agent`、`create_tool_calling_agent`）实际上也基于 LangGraph 构建**。

## 核心架构

### 图模型

LangGraph 的核心抽象是一个有向图，包含：

- **节点（Node）**：一个可调用的函数或 Runnable，接收整个 State 并返回对 State 的更新。
- **边（Edge）**：定义控制流，可以是确定性的（始终从 A 到 B）或条件性的（ConditionalEdge，根据 State 内容动态选择下一节点）。
- **StateGraph**：图的容器，管理节点注册、边拓扑和编译。
- **Command**：LangGraph v0.2+ 引入的动态路由原语，允许节点在运行时决定下一跳，而无需全局条件边定义。

### 状态管理

LangGraph 的状态管理是其区别于其他框架的核心特征：

- **显式 State 对象**：所有节点共享一个类型化的状态对象，通常使用 Pydantic BaseModel 或 TypedDict 定义。
- **Reducer 机制**：每个状态字段可以定义自己的 reducer 函数（如 `add`、`replace` 或自定义函数），控制多个节点输出如何合并到同一字段。
- **状态更新是增量式的**：节点返回的更新会通过 reducer 合并到全局状态，而非完全替换。

### 检查点与持久化

LangGraph 内置了自动断点续传能力（checkpointing）：

- 每个节点执行后，框架自动将完整状态持久化到检查点存储（内存、SQLite、PostgreSQL 等）。
- 支持 **时间旅行调试（time-travel debugging）**：可以从任意历史检查点重新执行，修改中间状态后继续。
- 使 **人工介入（human-in-the-loop）** 成为一等公民：可以在任意节点前后设置中断点，等待人工审核或修改状态后再继续执行。

### 流式支持

LangGraph 支持流式输出（streaming）的多种模式：
- `stream_mode="values"`：每次状态变更时输出完整 State。
- `stream_mode="updates"`：仅输出节点返回的增量更新。
- 流式 token：部分节点支持逐 token 输出。

## 关键原语

| 原语 | 作用 |
|---|---|
| `StateGraph` | 定义状态类型和图拓扑的容器 |
| `Node` | 封装一个计算步骤的函数 |
| `ConditionalEdge` | 根据 State 内容分支到不同节点 |
| `Command` | 节点内动态路由，替代全局条件边 |
| `checkpointer` | 持久化存储接口 |
| `interrupt` | 图中插入人工断点 |

## 生产部署

LangGraph 是目前在企业级生产环境中部署最广泛的 Agent 框架之一（GitHub ~31.4k stars），已报告的生产案例包括：

- **Klarna**（8500 万用户）：使用 LangGraph 驱动的 AI 客服系统处理大规模用户请求
- **Elastic**：在其 Elastic Assistant 中使用 LangGraph 构建多步骤推理工作流
- **Uber**：在其内部工具链中使用 LangGraph 编排 Agent
- **LinkedIn**：使用 LangGraph 构建招聘相关的 Agent 工作流

LangGraph Cloud 提供托管部署服务，包括持久化、监控、并发管理等生产所需的基础设施。

## 何时选择 LangGraph

### 适用场景

- **复杂多步骤工作流**：需要循环、分支、条件判断的流程，如多轮推理、自我修正循环。
- **审计需求**：需要完整的执行轨迹记录和可追溯性，每个决策步骤都能回溯。
- **可恢复性要求高**：长时间运行的工作流需要在中断后从检查点恢复。
- **人工审批流程**：需要在流程中嵌入人工审核环节，如金融交易、内容审核。
- **状态密集型应用**：多个节点共享和共同维护一个复杂状态对象。

### 不适用场景

- **简单线性流程**：对于简单的 LLM 调用链，LangGraph 的图模型是过度设计，LangChain 的 Chain 或简单的函数调用就足够。
- **团队缺乏 Python 深度**：LangGraph 的类型安全、reducer、条件路由等概念有一定学习曲线。
- **对延迟极端敏感**：图编排和状态持久化带来额外开销。
- **纯流式聊天应用**：不需要图编排能力，直接使用 LLM API 更高效。

## 与 LangChain 的关系

LangGraph 是 LangChain 生态的演进方向。LangChain 本身被许多开发者认为已变得臃肿（bloated），而 LangGraph 作为更专注于 Agent 工作流的框架正在逐步取代 LangChain 在 Agent 场景中的位置。**LangChain v1 的高层 Agent API（如 `create_react_agent`、`create_tool_calling_agent`）实际上也是基于 LangGraph 构建的**，进一步印证了 LangGraph 作为 LangChain 生态 Agent 编排核心的地位。LangChain 的抽象层（如 Runnable、LCEL）仍然作为 LangGraph 节点内的组件使用，但图的编排逻辑由 LangGraph 接管。
