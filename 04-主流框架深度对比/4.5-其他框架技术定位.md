# 其他框架技术定位 —— 生态全景：PydanticAI / DSPy / LangChain / LlamaIndex / Google ADK / MAF / Mastra / OpenAI Agents SDK

## 概述

除了前四节详细分析的 **LangGraph、CrewAI、AutoGen/MAF/AG2、Agno** 等主流 Agent 框架外，2026 年的 Agent 生态中还涌现了一批具有独特技术定位的框架和库。本章节将它们分为两类：

- **Mastra**：TypeScript 原生 Agent 框架，TS 生态首选

## PydanticAI —— 类型安全的 Agent 框架

### 技术定位

PydanticAI 是由 **Pydantic 团队**（Pydantic v2 的维护者）开发的 Agent 框架。其核心定位是：**利用 Pydantic 的类型系统，提供类型安全的 Agent 开发体验**。PydanticAI 是 Pydantic v2 生态的自然延伸，专为需要强类型约束和严格数据验证的生产环境设计。

### 核心架构

PydanticAI 的架构围绕 **类型安全的 Agent** 和 **结构化输出** 两个核心能力构建：

```python
from pydantic import BaseModel
from pydantic_ai import Agent

# 定义结构化输出模型
class StockAnalysis(BaseModel):
    ticker: str
    current_price: float
    recommendation: str
    confidence: float
    risk_factors: list[str]

# 类型安全的 Agent
agent = Agent(
    "openai:gpt-4o",
    result_type=StockAnalysis,  # 输出被强制转换为该类型
    system_prompt="你是股票分析师"
)

# 执行 Agent，result 自动是 StockAnalysis 类型
result = agent.run_sync("分析 NVDA 股票")
print(f"推荐: {result.recommendation}, 置信度: {result.confidence}")
# IDE 自动补全 result.ticker, result.current_price 等字段
```

关键特性：

1. **结果类型约束**：Agent 的输出被强制转换为指定的 Pydantic 模型，如果 LLM 输出不符合类型约束，框架自动重试
2. **依赖注入**（Dependency Injection）：支持通过函数签名注入外部依赖，使 Agent 组件可测试
3. **工具工具的强类型定义**：使用 Python 类型注解定义工具函数参数和返回值
4. **串联 Agent 模式**：多个 Agent 可以通过类型匹配串联工作

```python
from pydantic_ai import Agent, RunContext

# 依赖注入示例
class MyDeps(BaseModel):
    db_connection: str

agent = Agent(
    "openai:gpt-4o",
    deps_type=MyDeps,
)

@agent.system_prompt
async def get_db_schema(ctx: RunContext[MyDeps]) -> str:
    # 自动注入依赖
    schema = await fetch_schema(ctx.deps.db_connection)
    return f"Database schema: {schema}"
```

### 性能特点

- **优势**：类型安全在大型项目中极大地减少了运行时错误，Pydantic v2 的 Rust 核心保证了数据验证的高性能
- **劣势**：Agent 编排能力有限，仅支持简单的顺序执行和工具调用，不适合复杂多 Agent 工作流

### 适用场景

- **对数据质量要求极高的应用**：金融、医疗、法律等领域，需要确保 LLM 输出结构严格合规
- **团队使用 Python 类型系统深度**：已在项目中广泛使用 Pydantic 的团队
- **微服务中的 Agent 组件**：作为服务的一个模块，与其他类型安全的服务集成

## DSPy —— 声明式 LLM 程序自动优化

### 技术定位

DSPy 由 **Stanford NLP 团队**（Omar Khattab 等）开发，是一个从根本上重新思考 LLM 编程范式的框架。与传统框架"手动编写 Prompt → 调用 LLM"的模式不同，DSPy 提出 **"编程，而非提示"**（Programming, not Prompting）的理念：开发者用声明式的方式定义 LLM 程序的逻辑结构，DSPy 自动优化 Prompt 和参数。

### 核心架构

DSPy 的核心抽象是 **Signatures（签名）** 和 **Modules（模块）**：

```python
import dspy
from dspy import Signature, Module, ChainOfThought

# 1. 定义签名（输入/输出规范）
class GenerateAnswer(Signature):
    """回答问题并给出推理过程"""
    question: str = dspy.InputField()
    answer: str = dspy.OutputField()
    reasoning: str = dspy.OutputField()

# 2. 构建模块
class RAG(Module):
    def __init__(self):
        super().__init__()
        self.retrieve = dspy.Retrieve(k=3)
        self.generate_answer = ChainOfThought(GenerateAnswer)
    
    def forward(self, question):
        context = self.retrieve(question)
        return self.generate_answer(question=question, context=context)

# 3. 编译优化（自动调优）
from dspy.teleprompt import BootstrapFewShot
optimizer = BootstrapFewShot(metric=your_metric_function)
optimized_rag = optimizer.compile(RAG(), trainset=training_data)

# 4. 使用
result = optimized_rag(question="谁发明了望远镜？")
print(result.answer)
```

### 关键创新

**自动 Prompt 优化**：DSPy 会根据编译时提供的训练集和评估指标，自动：

1. 生成高质量的 few-shot 示例
2. 优化 Chain-of-Thought 的推理格式
3. 调整指令表述（instruction-tuning）
4. 选择最佳的 LLM 调用参数（temperature、top_p 等）

```python
# DSPy 与传统模式对比
# 传统：手动调 Prompt
prompt = f"""你是一个专家。请回答问题：{question}
请逐步推理。使用以下格式：
推理：...
答案：...
"""

# DSPy：声明式定义，自动优化
class QA(Signature):
    """回答问题"""
    question: str = dspy.InputField()
    answer: str = dspy.OutputField()

program = ChainOfThought(QA)
# DSPy 自动决定 Prompt 模板和优化策略
```

### 性能特点

- **优势**：在多个基准测试中，DSPy 优化后的程序性能优于手动设计的 Prompt；大幅减少 Prompt 工程的工作量
- **劣势**：需要标注好的训练数据；编译过程耗时（可能数小时）；调试困难（生成的 Prompt 不透明）

### 适用场景

- **需要持续优化的 LLM 应用**：同一个任务需要频繁迭代优化
- **研究性质的项目**：比较不同 Prompt 策略、模型、优化方法的效果
- **批处理流水线**：不需要实时响应，可以接受离线编译优化的场景
- **Prompt 工程疲劳**：传统 Prompt 工程无法达到满意效果的复杂任务

### 不适用场景

- **实时交互应用**：编译时间太长，不适合需要即时部署的场景
- **简单 LLM 调用**：对于"翻译一句话"这种简单任务，DSPy 是过度设计
- **需要完全控制 Prompt**：某些合规场景要求精确控制输入给 LLM 的每一句话

## LangChain —— 转型中的 LLM 应用元框架

### 技术定位

LangChain 是 LLM 应用开发中 **历史最悠久、生态最庞大** 的框架，由 Harrison Chase 于 2022 年底创建。它在 2024-2025 年间经历了重大转型：从"LLM 应用瑞士军刀"转向"Agent 生态的基础设施层"。

截至 2025 年底，LangChain 的技术定位是：
- **Agent 生态的底座**：LangGraph（图编排） + LangSmith（可观测性） + LangServe（部署）的母平台
- **连接器标准**：超过 700 个第三方集成（数据源、模型、工具），业界最大的 LLM 生态
- **历史负担**：早期的 DAG-of-chains 模型和 LCEL（LangChain Expression Language）被认为是过度抽象

### 核心架构

LangChain 当前的架构更接近于一个"生态平台"而非单一框架：

```
LangChain 生态体系
├── LangChain Core（基础抽象层）
│   ├── Runnable 接口（所有组件的统一接口）
│   ├── Message 类型系统
│   └── 回调机制（Callbacks）
├── LangChain Community（第三方集成）
│   ├── 模型提供商（100+）
│   ├── 向量数据库（30+）
│   └── 工具和 API 集成（500+）
├── LangGraph（Agent 编排层） ← 当前重点
├── LangSmith（可观测性平台）
└── LangServe（部署服务）
```

```python
# LangChain Core 的基础抽象：Runnable
from langchain_core.runnables import RunnablePassthrough
from langchain_core.output_parsers import StrOutputParser
from langchain_openai import ChatOpenAI
from langchain.prompts import ChatPromptTemplate

# LCEL 语法（过时但仍广泛使用）
chain = (
    {"context": retriever, "question": RunnablePassthrough()}
    | ChatPromptTemplate.from_template("基于上下文：{context} 回答问题：{question}")
    | ChatOpenAI(model="gpt-4o")
    | StrOutputParser()
)

# 当前推荐：使用 LangGraph 替代 LCEL
from langgraph.graph import StateGraph
# ...（参见 4.1-LangGraph.md）
```

### 争议与批评

LangChain 在社区中一直存在争议，主要批评包括：

1. **过度抽象**（Over-abstraction）：Runnable、LCEL 等抽象层增加了不必要的复杂度
2. **调试困难**：堆栈跟踪（stack trace）往往深达数十层，定位问题极为困难
3. **版本不兼容**：0.1 → 0.2 → 0.3 版本的 API 频繁变更
4. **性能开销**：相对于直接调用 API，LangChain 引入 10-50% 的额外延迟

### LangChain 的当前价值

尽管存在上述问题，LangChain 在以下方面仍然具有不可替代的价值：

- **生态连接器**：700+ 第三方集成，是目前连接各种 LLM 服务和数据源的最快捷方式
- **LangSmith 可观测性**：LLM 应用追踪和调试的行业标准工具
- **向 LangGraph 的迁移路径**：对于已有 LangChain 代码库的团队，迁移到 LangGraph 的成本较低

### 适用场景

- **已有 LangChain 代码库的项目**：逐步迁移到 LangGraph，而非完全重写
- **需要 LangSmith 可观测性的团队**：LangSmith 是业界最成熟的 LLM 可观测性平台
- **快速集成实验**：利用 700+ 集成快速验证想法

### 不适用场景

- **新项目（除非需要 LangSmith）**：新建项目建议直接使用 LangGraph 或其他轻量框架
- **性能敏感的应用**：LangChain 的抽象层会引入显著的性能开销
- **需要完全控制的场景**：当需要精确控制每个调用细节时，LangChain 的抽象会带来障碍

## LlamaIndex —— 数据索引与 RAG 的领先框架

### 技术定位

LlamaIndex（原名 GPT Index）由 Jerry Liu 创建，是 **数据索引和检索增强生成（RAG）** 领域的领先框架。与专注于 Agent 编排的 LangGraph 不同，LlamaIndex 的核心能力是 **连接企业数据与 LLM**。

### 核心架构

LlamaIndex 的架构围绕数据处理的完整流水线构建：

```python
from llama_index.core import VectorStoreIndex, SimpleDirectoryReader
from llama_index.core.ingestion import IngestionPipeline
from llama_index.core.node_parser import SentenceSplitter
from llama_index.embeddings.openai import OpenAIEmbedding

# 数据摄取流水线
pipeline = IngestionPipeline(
    transformations=[
        SentenceSplitter(chunk_size=1024, chunk_overlap=200),
        OpenAIEmbedding(),
    ]
)

# 索引构建
documents = SimpleDirectoryReader("./data").load_data()
nodes = pipeline.run(documents=documents)
index = VectorStoreIndex(nodes=nodes)

# 检索 + 生成
query_engine = index.as_query_engine(similarity_top_k=5)
response = query_engine.query("公司的年度收入是多少？")
```

### LlamaIndex 的关键组件

1. **数据连接器**（Data Connectors / Readers）：150+ 数据源适配器（文件、数据库、SaaS API 等）
2. **文档处理流水线**（Ingestion Pipeline）：文档解析、分块、嵌入的完整流水线
3. **索引结构**（Index Structures）：向量索引、关键词索引、知识图谱索引、混合索引
4. **检索器**（Retrievers）：向量检索、BM25 检索、混合检索、自动检索策略
5. **查询引擎**（Query Engines）：支持复杂查询策略（树查询、逐步查询、路由查询）

### LlamaIndex 的 Agent 能力

LlamaIndex 从 v0.10+ 开始增加了 Agent 能力，但并非其主要定位：

```python
from llama_index.core.agent import ReActAgent
from llama_index.core.tools import QueryEngineTool, ToolMetadata

# LlamaIndex Agent 示例
query_tool = QueryEngineTool(
    query_engine=index.as_query_engine(),
    metadata=ToolMetadata(
        name="financial_data",
        description="查询财务数据"
    )
)

agent = ReActAgent.from_tools(
    [query_tool],
    llm=OpenAI(model="gpt-4o"),
    verbose=True
)
agent.chat("分析过去三年的收入趋势")
```

### 性能特点

- **优势**：业界最完善的 RAG 能力、提供从数据摄取到查询的端到端方案、Agent 可以无缝集成 RAG 能力
- **劣势**：Agent 编排能力弱于专门框架（LangGraph/AutoGen）、学习曲线集中在数据而非 Agent、库的体积较大

### 适用场景

- **RAG 重度应用**：核心业务依赖检索增强生成的企业知识库、客服系统
- **企业数据集成**：需要连接多种异构数据源（数据库、文档、SaaS）的 LLM 应用
- **复杂检索策略**：需要混合检索、重排序、元数据过滤等高级 RAG 功能
- **数据治理和合规**：需要对文档级权限、数据来源、检索过程进行精细控制的场景

## Google ADK (Agent Development Kit) —— Google 生态的 Agent 原生框架

### 技术定位

Google ADK (Agent Development Kit) 是 Google 于 2025 年推出的官方 Agent 开发框架，**专为 Gemini 模型和 Google Cloud 生态优化**。ADK 的定位是 Google 技术栈中构建 Agent 应用的首选方案，与 Vertex AI、Gemini API 深度集成。

### 核心架构

ADK 围绕 **Agent 原生 (Agent-Native)** 的理念设计，强调 Agent 作为应用架构的一等公民：

```python
# Google ADK 示例（概念）
from google.adk import Agent, Tool
from google.genai import types

# 定义 Agent
research_agent = Agent(
    model="gemini-2.5-pro",
    name="research_agent",
    instruction="你是一个研究助手，使用 Google 搜索和数据分析工具",
    tools=[
        Tool.google_search(),
        Tool.code_execution(),
    ]
)

# 运行 Agent
response = research_agent.run("分析2026年全球AI投资趋势")
```

关键特性：

1. **Gemini 原生优化**：深度利用 Gemini 的多模态、长上下文（1M+ tokens）、函数调用能力
2. **Google 服务集成**：与 Google Search、Google Maps、BigQuery、Drive 等 200+ Google 服务原生集成
3. **Vertex AI 部署**：一键部署到 Vertex AI Agent Builder，享受 Google Cloud 的 SLA 和安全管理
4. **多 Agent 编排**：支持 Agent 之间的层级组织和消息传递

### 适用场景

- **Google Cloud 用户**：已使用 GCP、Vertex AI 的组织
- **Gemini 模型重度用户**：需要最大化利用 Gemini 的多模态和长上下文能力
- **需要 Google 服务集成的应用**：搜索、地图、数据分析等 Google 生态联动

### 不适用场景

- **非 Google 技术栈**：使用 AWS/Azure 且无 Google 服务依赖
- **需要模型中立性**：框架与 Gemini 深度绑定，切换模型成本高
- **TypeScript 优先项目**：Mastra 或 LangChain 在 TS 生态中更成熟

## Microsoft Agent Framework (MAF) —— 企业级双语言 Agent 框架

### 技术定位

Microsoft Agent Framework (MAF) 是 Microsoft 在 AutoGen 进入维护模式后推出的官方继任框架，采用 **Python + C# 双语言** 支持，与 Microsoft 365 和 Azure 生态深度集成。与 AutoGen 的 Actor Model 不同，MAF 采用更简洁的 **Kernel-Agent 架构**。

### 核心特性

- **双语言支持**：Python 和 C# 提供对等的 Agent 开发体验
- **Microsoft 365 集成**：与 SharePoint、Teams、Outlook 等原生集成
- **企业级安全**：基于 Microsoft Entra ID 的认证和权限管理
- **Azure AI 深度集成**：与 Azure AI Foundry、Azure OpenAI Service 无缝对接

> MAF 的详细技术分析请参见 [4.3-AutoGen.md](./4.3-AutoGen.md) 中的"Microsoft Agent Framework (MAF) —— 官方继任者"章节。

### 适用场景

- **微软技术栈企业**：已使用 Azure、Microsoft 365 的组织
- **.NET/C# 团队**：希望在 .NET 生态中构建 Agent
- **需要 Copilot 扩展**：扩展 Microsoft Copilot 的能力

## Mastra —— TypeScript 原生的 Agent 框架

### 技术定位

Mastra 是 2025-2026 年崛起的 **TypeScript 原生 Agent 框架**，专为 Node.js 和 TypeScript 生态设计。在 TypeScript Agent 框架生态中，Mastra 成为首选方案之一，填补了此前 JS/TS 生态中缺乏成熟 Agent 框架的空白。

### 核心架构

Mastra 的设计围绕 TypeScript 的类型系统和异步特性构建：

```typescript
// Mastra TypeScript 示例（概念）
import { Agent } from 'mastra';
import { z } from 'zod';

// 定义带类型安全的 Agent
const researchAgent = new Agent({
  name: 'research-agent',
  instructions: '你是一个研究助手',
  model: {
    provider: 'OPEN_AI',
    name: 'gpt-4o',
  },
  tools: {
    search: searchTool,
    analyze: analyzeTool,
  },
});

// 定义结构化输出
const result = await researchAgent.generate(
  '分析2026年AI趋势',
  {
    output: z.object({
      summary: z.string(),
      key_trends: z.array(z.string()),
      confidence: z.number(),
    }),
  }
);
```

关键特性：

1. **TypeScript 原生**：完整的类型定义和 IDE 支持，类型错误在编译期捕获
2. **Zod 集成**：使用 Zod schema 定义 Agent 输入输出，运行时验证
3. **多种模型支持**：支持 OpenAI、Anthropic、Google Gemini 等主流模型
4. **工作流引擎**：内置工作流定义能力，支持条件分支和循环
5. **记忆系统**：支持短期和长期记忆管理
6. **可观测性**：内置日志和追踪能力

### 适用场景

- **TypeScript/Node.js 项目**：前端、全栈或 Node.js 后端项目
- **初创公司快速原型**：TypeScript 生态的开发效率优势明显
- **需要类型安全的前端应用**：与 React/Next.js 等前端框架自然集成
- **全栈 Agent 应用**：前端和后端共享类型定义的应用

### 不适用场景

- **Python 生态项目**：数据科学、ML 研究等以 Python 为主的场景
- **复杂多 Agent 编排**：相比 LangGraph 的状态图，Mastra 的工作流能力仍在发展中
- **企业级生产环境**：相对于 LangGraph 和 CrewAI，生产案例和最佳实践积累较少

## OpenAI Agents SDK —— 轻量级生态原生 Agent 运行时

### 技术定位

OpenAI Agents SDK 是 OpenAI 官方推出的轻量级 Agent 开发工具包，与 OpenAI API 生态深度集成。它的设计哲学是 **极简、轻量、与 OpenAI API 无缝衔接**，适合快速构建基于 OpenAI 模型的单 Agent 应用。

### 核心架构

```python
# OpenAI Agents SDK 示例（概念）
from agents import Agent, Runner, function_tool

# 定义工具
@function_tool
def get_weather(city: str) -> str:
    """获取城市天气"""
    return f"{city}天气：晴朗，25°C"

# 定义 Agent
agent = Agent(
    name="weather_assistant",
    instructions="你是一个天气助手，帮助用户查询天气信息",
    tools=[get_weather],
    model="gpt-4o"  # 使用 OpenAI 模型
)

# 运行 Agent
result = Runner.run_sync(agent, "北京今天天气如何？")
print(result.final_output)
```

关键特性：

1. **OpenAI 原生**：与 Assistants API、Function Calling、Streaming 等 OpenAI 特性无缝集成
2. **极简设计**：核心库极小，无外部依赖，实例化开销极低
3. **工具系统**：基于 Python 装饰器的工具定义，与 OpenAI 的 function calling 直接映射
4. **Handoff 机制**：支持 Agent 之间的任务交接（handoff），实现简单的多 Agent 协作
5. **护栏系统 (Guardrails)**：内置输入/输出护栏，确保 Agent 行为可控

### 适用场景

- **OpenAI 生态深度用户**：项目已围绕 OpenAI API 构建
- **简单单 Agent 应用**：客服机器人、工具调用助手等场景
- **快速原型开发**：从 LLM API 调用快速过渡到 Agent 模式
- **教学和演示**：学习 Agent 概念的最简入门框架

### 不适用场景

- **多模型需求**：框架与 OpenAI 模型绑定，不适合需要多模型切换的场景
- **复杂多 Agent 编排**：Handoff 机制相对简单，不支持复杂图拓扑
- **生产级复杂工作流**：缺少状态持久化、时间旅行调试等高级特性

## 框架间协同使用

在实际项目中，这些框架经常被组合使用：

```
┌─────────────────────────────────────────────────┐

├─────────────────────────────────────────────────┤
│                                                   │
│  模式 1: LangGraph + LlamaIndex                   │
│  LangGraph 编排 Agent 工作流                      │
│  LlamaIndex 提供 RAG 和数据检索能力               │
│                                                   │
│  模式 2: PydanticAI + DSPy                        │
│  PydanticAI 提供类型安全的 Agent 运行时           │
│  DSPy 优化关键 Prompt 模板                        │
│                                                   │
│  模式 3: LangChain 生态 + 自定义 Agent            │
│  LangChain 提供 700+ 集成连接器                   │
│  自定义框架（如 Agno）提供 Agent 运行时           │
│                                                   │
│  模式 4: Google ADK + Vertex AI                   │
│  Google ADK 构建 Gemini Agent                     │
│  Vertex AI 提供部署、监控和企业级能力             │
│                                                   │
│  模式 5: Mastra + 任意 LLM SDK                    │
│  Mastra 提供 TS Agent 框架                        │

│                                                   │
└─────────────────────────────────────────────────┘
```

## 关键概念速查

| 概念 | 解释 |
|---|---|
| **PydanticAI Agent** | 类型安全的 Agent，输出被强制转换为 Pydantic 模型 |
| **DSPy Signature** | 定义 LLM 程序输入/输出规范的声明式语法 |
| **DSPy Compiler** | 自动优化 LLM 程序的编译器，生成 Prompt 和参数 |
| **LangChain LCEL** | LangChain Expression Language，声明式链式调用语法 |
| **LangChain Runnable** | LangChain 的统一组件接口，所有组件实现该接口 |
| **LlamaIndex IngestionPipeline** | 数据摄取流水线，包含解析、分块、嵌入等步骤 |
| **LlamaIndex QueryEngine** | 查询引擎，封装检索和生成的完整逻辑 |
| **ReAct Agent** | Reasoning + Acting 范式，Agent 交替推理和行动 |
| **Google ADK** | Google 官方的 Agent 开发工具包，与 Gemini 和 Vertex AI 深度集成 |
| **MAF** | Microsoft Agent Framework，AutoGen 的官方继任者，双语言企业级框架 |
| **Mastra** | TypeScript 原生的 Agent 框架，提供类型安全的工作流和工具定义 |
| **OpenAI Agents SDK** | OpenAI 官方轻量 Agent SDK，与 OpenAI API 无缝集成 |
| **Agent-Native** | 将 Agent 作为应用架构核心的设计理念，Google ADK 的核心哲学 |
| **Handoff** | Agent 之间的任务交接机制，OpenAI Agents SDK 的多 Agent 协作方式 |
| **Kernel-Agent 架构** | MAF 采用的运行时架构，通过 Kernel 容器管理 Agent 生命周期 |

> **交叉参考**：本章节介绍的经典框架（PydanticAI、DSPy、LangChain、LlamaIndex）在实际项目中常与主流 Agent 框架组合使用——LangGraph + LlamaIndex 的组合请参见 [4.1-LangGraph.md](./4.1-LangGraph.md)；MAF 的详细分析请参见 [4.3-AutoGen.md](./4.3-AutoGen.md) 中的相关内容；轻量替代方案可参见 [4.4-Agno.md](./4.4-Agno.md)。完整的 2026 年选型分析请参考 [4.6-选型决策指南.md](./4.6-选型决策指南.md)。
