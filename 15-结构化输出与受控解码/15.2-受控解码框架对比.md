# 15.2 受控解码框架对比 —— Outlines / XGrammar / LMFE / Guidance

> 受控解码框架是介于"LLM 输出"和"合法语法"之间的桥梁。Outlines 基于有限状态机提供了灵活性与性能的平衡；XGrammar 使用下推自动机实现了 100x 加速；LMFE 在零样本场景下达到最低幻觉率 8.9%。本章从速度、内存、精度、适用场景四个维度进行全面对比。

---

## 一、受控解码框架概述

受控解码框架的核心功能是将 **语法约束** 转化为 LLM 解码过程中的 **token 级别屏蔽规则**。每个框架选择了不同的技术路线：

| 框架 | 发布方 | 核心机制 | 语法支持 | 加速技术 |
|------|--------|---------|---------|---------|
| **Outlines** | 社区开源 | 有限状态机 (FSM) | JSON Schema, EBNF, Regex | 正则表达式编译优化 |
| **XGrammar** | 社区开源 | 下推自动机 (PDA) | JSON Schema, EBNF | 确定性下推自动机 + 预编译 |
| **LMFE** | 学术界 | 零样本重排序 | 隐式语法约束 | 候选序列重排序 |
| **Guidance** | Microsoft | 模板+正则混合 | Handlebars 模板, JSON | 角色标记 + 模板缓存 |

### 1.1 为什么需要专门的框架？

直接实现 Constrained Decoding（如 15.1 节描述的 Logit Masking）存在三个挑战：

1. **效率问题**：每步解码都需要运行语法检查，如果语法检查比模型推理还慢，整体性能会大幅下降
2. **嵌套处理**：JSON Schema 支持深层嵌套（对象包含数组包含对象），FSM 理论上无法处理无限层嵌套
3. **上下文敏感**：某些 token 是否合法依赖于之前的 token 序列，需要维护状态

这四个框架以不同的方式解决了这些问题，但各有侧重。

## 二、Outlines —— 基于 FSM 的灵活平衡

### 2.1 工作原理

Outlines 使用**有限状态机（Finite State Machine, FSM）**来表示语法约束。FSM 由一组状态和状态之间的转移规则组成。每个状态对应当前已生成的 token 序列在语法中的位置，转移规则定义了在当前状态下哪些 token 是合法的。

```
FSM 示例：强制生成 {"name": "..."}

状态 0 (初始): {  → 状态 1
状态 1: "name"  → 状态 2
状态 2: :  → 状态 3
状态 3: 引号开始  → 状态 4
状态 4: 任意字符  → 保持状态 4（字符串内部）
状态 4: 引号结束  → 状态 5
状态 5: }  → 状态 6（终止）
```

### 2.2 核心代码示例

```python
from outlines import generate, models
from pydantic import BaseModel, Field

# 定义 JSON Schema
class WeatherRequest(BaseModel):
    city: str = Field(description="城市名")
    date: str = Field(description="日期，格式 YYYY-MM-DD")
    include_humidity: bool = Field(default=False)

# 加载模型
model = models.Transformers("Qwen/Qwen2.5-7B-Instruct")

# 创建约束生成器
generator = generate.json(model, WeatherRequest)

# 生成结构化输出
result = generator("查询北京2026年6月1日的天气，需要湿度信息")
print(result)
# 输出: WeatherRequest(city='北京', date='2026-06-01', include_humidity=True)
```

### 2.3 性能特性

- **单步延迟**：每生成一个 token 增加约 1-5ms 的语法检查开销
- **内存占用**：约 50-200MB（取决于 Schema 复杂度），FSM 状态表预编译后常驻内存
- **加速比**：相比纯 logit masking 实现快约 5-10 倍
- **主要瓶颈**：FSM 状态表的构建和查询在高并发场景下成为瓶颈

### 2.4 适用场景

- 语法复杂度中等的场景
- 开发调试阶段，需要快速迭代 Schema
- 对框架兼容性要求高（支持多种后端：Transformers、vLLM、llama.cpp）

## 三、XGrammar —— 下推自动机的 100x 加速

### 3.1 工作原理

XGrammar 使用**下推自动机（Pushdown Automaton, PDA）**替代 FSM。PDA 在 FSM 的基础上增加了一个**栈结构**，用于跟踪嵌套深度和上下文。

关键区别在于：

```
FSM 处理嵌套 JSON：
{"a": {"b": {"c": 1}}} 
→ FSM 需要为每层嵌套创建新的状态
→ 嵌套深度 = K 时，状态数量 N^K（指数增长）

PDA 处理嵌套 JSON：
{"a": {"b": {"c": 1}}}
→ PDA 使用栈跟踪嵌套深度
→ 每进入一层 obj { → 压栈
→ 每离开一层 obj } → 弹栈
→ 状态数量不随嵌套深度增长（线性增长）
```

### 3.2 核心优势

**确定性下推自动机（DPDA）** 是 XGrammar 的核心创新。DPDA 保证每一步只有唯一合法的转移路径，消除了回溯需求：

```python
# XGrammar 使用示例
from xgrammar import GrammarCompiler, TokenizerInfo

# 编译 JSON Schema 为 DPDA
compiler = GrammarCompiler(
    tokenizer_info=TokenizerInfo.from_huggingface("Qwen/Qwen2.5-7B-Instruct")
)
compiled_grammar = compiler.compile_json_schema('''
{
  "type": "object",
  "properties": {
    "actions": {
      "type": "array",
      "items": {
        "type": "object",
        "properties": {
          "type": {"type": "string"},
          "parameters": {"type": "object"}
        },
        "required": ["type"]
      }
    }
  }
}
''')

# 在解码中使用
def generate_with_xgrammar(model, prompt, compiled_grammar):
    input_ids = model.tokenizer.encode(prompt)
    state = compiled_grammar.init_state()
    
    for _ in range(max_tokens):
        logits = model.forward(input_ids)
        
        # XGrammar 获取合法 token 掩码
        allowed_mask = compiled_grammar.get_allowed_mask(state)
        masked_logits = logits.masked_fill(~allowed_mask, -inf)
        
        next_token = sample(masked_logits)
        input_ids.append(next_token)
        
        # 更新解析状态
        state = compiled_grammar.advance_state(state, next_token)
        
        if compiled_grammar.is_terminated(state):
            break
    
    return model.tokenizer.decode(input_ids)
```

### 3.3 100x 加速的来源

| 优化技术 | 说明 | 加速效果 |
|---------|------|---------|
| **预编译（Pre-compilation）** | Schema 在推理前编译为 DPDA，运行时只做矩阵运算 | 10-20x |
| **批量掩码（Batch Masking）** | 一次计算整个批次的合法 token 掩码，而非逐个 token | 2-3x |
| **缓存友好（Cache-friendly）** | DPDA 状态表使用紧凑数组存储，CPU 缓存命中率高 | 2-5x |
| **上下文无关栈操作** | 栈的 push/pop 操作是 O(1)，不随嵌套深度增加 | 3-10x |

综合加速比约为 **50-100x** 相比纯 logit masking 实现，**5-10x** 相比 Outlines。

### 3.4 性能特性

- **单步延迟**：约 0.1-0.5ms（比 Outlines 快 10 倍）
- **内存占用**：约 10-50MB（比 Outlines 少 3-4 倍，因为无需维护指数级状态表）
- **加速比**：相比纯 logit masking 可达 100x
- **冷启动时间**：Schema 编译时间约 1-5s（一次性开销）

### 3.5 适用场景

- 高吞吐量生产环境
- 需要处理深度嵌套 JSON 的场景
- 流式输出 + 语法约束的实时 Agent 系统
- 延迟敏感的应用（如语音对话 Agent）

## 四、LMFE —— 零样本最低幻觉率的独特路径

### 4.1 工作原理

LMFE（Language Model Formatting with Ensembles）不走"解码时约束"的路线，而是采用**生成后重排序**策略：

1. **多次生成**：对同一个输入，用自由解码生成 N 个候选输出（N 通常为 5-10）
2. **语法校验**：过滤掉不符合格式要求的候选
3. **质量排序**：使用一个轻量级评分模型对合法候选进行质量排序
4. **最优选择**：输出得分最高的候选

```
输入 → [生成候选1, 生成候选2, ..., 生成候选N]
         ↓
    语法过滤器（移除格式错误的候选）
         ↓
    质量评分器（为每个合法候选打分）
         ↓
    输出得分最高的候选
```

### 4.2 与 Outlines/XGrammar 的区别

LMFE 的关键区别在于它**不修改解码过程**，而是"生成后验证"。这使得它：

- 不会引入 14.6 节讨论的"约束解码导致推理质量下降"的问题
- 增加了推理成本（N 次生成 + 1 次重排序）
- 格式保证不如 Outlines/XGrammar 严格（如果所有候选都格式错误，LMFE 没有输出）

### 4.3 性能数据

根据 LMFE 论文报告的实验结果：

| 指标 | LMFE | Outlines | Prompt-Based | 自由解码 |
|------|------|---------|-------------|---------|
| **格式正确率** | 98.2% | 99.9% | 91.5% | 87.3% |
| **内容准确率** | 91.1% | 83.5% | 86.2% | 88.7% |
| **幻觉率** | **8.9%** | 16.5% | 13.8% | 11.3% |
| **延迟（相对）** | 5-10x | 1.1x | 1.0x | 1.0x |
| **内存开销** | 2-5x | 1.2x | 1.0x | 1.0x |

LMFE 的幻觉率 8.9% 是所有受控解码方法中最低的，但代价是 5-10 倍的延迟和 2-5 倍的内存。

### 4.4 适用场景

- 对内容准确率要求极高、对延迟不敏感的场景
- 离线批处理任务
- 作为 Outlines/XGrammar 的补充（用于验证和重排序）
- 不适合实时 Agent 系统（延迟太高）

## 五、Guidance —— Microsoft 的模板化路径

### 5.1 工作原理

Guidance 采用**模板+角色标记**的混合策略。它不像 Outlines/XGrammar 那样在 token 级别约束，而是在模型生成的文本中嵌入特殊标记来控制生成行为：

```python
import guidance

# 定义引导程序
@guidance
def extract_info(lm, text):
    lm += f"从以下文本提取信息：{text}\n"
    lm += "输出格式：\n"
    lm += "{\n"
    lm += f'  "name": "{guidance.gen("name", stop='"')}",\n'
    lm += f'  "age": {guidance.gen("age", pattern="\\d+")},\n'
    lm += f'  "city": "{guidance.gen("city", stop='"')}"\n'
    lm += "}\n"
    return lm

result = guidance(extract_info, text="张三，28岁，北京")
print(result["name"], result["age"], result["city"])
# 输出: 张三 28 北京
```

### 5.2 性能特性

- **单步延迟**：约 0.5-2ms（介于 Outlines 和 XGrammar 之间）
- **内存占用**：约 20-80MB（模板缓存 + 正则状态）
- **格式保证**：每个 `guidance.gen` 字段强制符合约束，字段间连接文本硬编码
- **扩展性**：支持条件、循环、变量绑定、角色切换

### 5.3 独特优势

Guidance 的最大优势是其对**角色扮演**和**对话控制**的原生支持：

```python
@guidance
def agent_conversation(lm):
    lm += "你是一个客服助手。\n"
    lm += f"用户：{user_input}\n"
    lm += '助手（思考）："' + guidance.gen("thought", stop='"') + '"\n'
    lm += "助手（行动）：\n"
    lm += "```json\n"
    lm += '{"action": "' + guidance.gen("action", stop='"') + '", '
    lm += '"params": ' + guidance.gen("params", pattern=r"\{[^}]+\}") + "\n"
    lm += "```\n"
    return lm
```

### 5.4 适用场景

- 需要精细控制对话流程的 Agent 系统
- 模板化的代码生成
- 小团队快速原型开发
- 对格式灵活性要求高的场景

## 六、四框架全方位对比

### 6.1 速度对比（以单 token 生成延迟，数值越小越好）

| 框架 | 简单 Schema | 中等 Schema | 复杂嵌套 | 冷启动编译 |
|------|-----------|-----------|---------|-----------|
| Outlines | 0.8ms | 2.1ms | 5.2ms | 0.1-0.5s |
| XGrammar | **0.1ms** | **0.2ms** | **0.5ms** | 1-5s |
| LMFE | N/A（后处理） | N/A | N/A | 0s（无编译） |
| Guidance | 0.3ms | 0.8ms | 1.5ms | 0.05s |

> 注：简单 Schema = 3-5 个顶层字段；中等 Schema = 包含嵌套对象和数组；复杂嵌套 = 3+ 层嵌套 + 多类型数组

### 6.2 内存对比

| 框架 | 基础开销 | 每 Schema 开销 | 峰值内存 |
|------|---------|--------------|---------|
| Outlines | 80MB | 20-100MB | 200-500MB |
| XGrammar | 30MB | 5-20MB | 50-100MB |
| LMFE | 200MB+ | 取决于 N | 500MB-2GB（N 次生成） |
| Guidance | 40MB | 10-30MB | 80-150MB |

### 6.3 精度对比（格式正确率 + 内容准确率）

| 框架 | 格式正确率 | 内容准确率 | 幻觉率 | 推理退化 |
|------|----------|----------|-------|---------|
| Outlines | 99.9% | 83.5% | 16.5% | 存在（中等） |
| XGrammar | 99.9% | 84.2% | 15.8% | 存在（中等） |
| LMFE | 98.2% | **91.1%** | **8.9%** | **不存在** |
| Guidance | 97.5% | 85.8% | 14.2% | 存在（轻度） |

> 注：内容准确率和幻觉率数据来自各框架论文/技术报告的标准化评测，实际效果因模型和任务而异。

### 6.4 功能对比

| 维度 | Outlines | XGrammar | LMFE | Guidance |
|------|---------|---------|------|---------|
| 语法类型 | JSON, EBNF, Regex | JSON, EBNF | 隐式 | 模板+Regex |
| 是否修改解码 | 是 | 是 | 否（后处理） | 是（角色标记） |
| 流式支持 | 是 | 是 | 否 | 是 |
| 批量支持 | 是 | 是 | 否 | 是 |
| 模型兼容性 | Transformers, vLLM, llama.cpp | Transformers, vLLM | 任意模型 | Transformers, llama.cpp |
| 社区活跃度 | 高 | 中 | 低 | 中 |
| 文档质量 | 好 | 良好 | 一般 | 好 |

## 七、框架选择决策树

```
你的首要关注是什么？
│
├── 速度（低延迟）
│   └── XGrammar（0.1-0.5ms/token）
│
├── 内容准确率（最低幻觉率）
│   └── LMFE（8.9% 幻觉率，但延迟高）
│
├── 开发体验（快速原型）
│   └── Guidance（模板直观，调试友好）
│
├── 平衡所有维度
│   └── Outlines（最成熟，社区最大）
│
└── 多框架组合（生产推荐）
    └── XGrammar（约束解码）+ LMFE（后验证）
    └── 速度与准确率的平衡方案
```

### 7.1 生产环境推荐组合

在真实的 Agent 生产系统中，推荐**多框架并用**：

```python
class ProductionConstrainedEngine:
    def __init__(self):
        self.primary = XGrammarEngine()  # 主解码引擎
        self.validator = LMFEValidator()  # 后验证引擎
    
    def generate(self, prompt, schema):
        # 第一层：XGrammar 快速约束解码
        result = self.primary.generate(prompt, schema)
        
        # 第二层：LMFE 轻量级验证
        quality_score = self.validator.score(prompt, result, schema)
        
        if quality_score < threshold:
            # 如果质量偏低，重生成
            result = self.retry_with_different_params(prompt, schema)
        
        return result
```

## 关键概念速查

| 术语 | 解释 |
|------|------|
| 有限状态机 (FSM) | 由有限数量的状态和状态间的转移规则组成的计算模型，用于描述合法 token 序列 |
| 下推自动机 (PDA) | FSM 的扩展，增加栈结构以处理嵌套语法，状态数不随嵌套深度指数增长 |
| 确定性下推自动机 (DPDA) | 每一步只有唯一合法转移路径的 PDA，消除回溯需求 |
| Logit Masking | 将非法 token 的 logit 值设为负无穷的技术，确保不会被采样到 |
| 预编译 (Pre-compilation) | 在解码开始前将 Schema 编译为高效数据结构的优化技术 |
| 重排序（Re-ranking） | 生成多个候选后按质量评分排序选择最优 |
| 角色标记 (Role Tagging) | Guidance 中用于控制模型生成行为的特殊标记 |
