# 15.1 两条路径 —— Prompt-Based vs Constrained Decoding

> 让 LLM 输出结构化的 JSON 是 Agent 工程的基础需求。但在实现路径上，存在两种完全不同的哲学：Prompt-Based（通过提示词引导，非确定性）和 Constrained Decoding（通过解码算法强制，确定性语法保证）。本章剖析两条路径的原理、优劣和适用场景。

---

## 一、为什么需要结构化输出？

在 Agent 系统中，LLM 的输出不再是"给人类看的一篇文章"，而是"给下游程序执行的指令"。这意味着输出必须满足：

- **可解析性**：下游程序（函数调用、数据库写入、API 请求）需要严格的格式
- **字段完备性**：不能缺少关键字段
- **类型正确性**：字符串不能出现在数字字段，嵌套对象结构必须正确

考虑一个典型的 Agent 调用：

```
用户：查询北京今日天气并设置提醒

期望输出（JSON）：
{
  "actions": [
    {"type": "query_weather", "city": "北京"},
    {"type": "set_reminder", "text": "带伞", "time": "08:00"}
  ]
}
```

如果 LLM 输出的是"好的，我来查询北京的天气并设置提醒"或者 JSON 缺少字段，下游程序就会崩溃。结构化输出不是锦上添花，而是 Agent 系统的基础保障。

---

## 二、路径一：Prompt-Based 提取（非确定性）

### 2.1 基本原理

Prompt-Based 方法依赖 LLM 本身的指令遵循能力来生成结构化输出。开发者通过提示词描述输出格式，并期望 LLM 按照格式输出。

```python
# Prompt-Based 结构化输出示例
prompt = """
请分析以下用户请求，以 JSON 格式输出：

用户请求：{user_input}

输出格式（请严格按照以下 JSON 格式）：
{
  "intent": "字符串，用户意图分类",
  "entities": {"key": "value", "提取的实体"},
  "confidence": 0.0-1.0的双精度浮点数
}

只输出 JSON，不要包含其他内容。
"""

response = llm.generate(prompt)
# 输出结果可能有效，也可能格式错误
```

### 2.2 优点

1. **零额外依赖**：不需要专门的解码库或 API 支持，任何 LLM 都能用
2. **无推理退化**：不存在 14.6 节讨论的"约束解码导致推理质量下降"问题，模型可以自由组织语言
3. **灵活性强**：可以通过提示词调整输出风格、详细程度，甚至让模型先思考再输出
4. **兼容性广**：开源模型、商业 API、本地部署都能使用

### 2.3 缺点

1. **格式不稳定**：即使有详细说明，LLM 仍可能漏掉字段、增加逗号、使用错误的引号
2. **解析失败率高**：在生产环境中，Prompt-Based 的 JSON 格式正确率通常在 85-95% 之间，对于复杂的嵌套结构可能更低
3. **难以调试**：格式错误可能是偶发的，且错误模式不固定，难以通过规则修复
4. **安全风险**：模型可能在 JSON 中注入意外字段（如 `"malicious": true`）

```python
# Prompt-Based 典型失败模式
# 预期输出：
{"name": "张三", "age": 28, "city": "北京"}

# 实际可能输出的各种变体：
{"name": "张三", "age": "二十八岁", "city": "北京"}  # 类型错误
{"name": "张三", "age": 28}  # 缺少字段
{"name": "张三", "age": 28, "city": 北京}  # 语法错误（缺少引号）
{
  "name": "张三",
  "age": 28,
  "city": "北京",
}  # 多余的尾部逗号（JSON 标准语法不允许）
```

## 三、路径二：Constrained Decoding（确定性语法保证）

### 3.1 基本原理

Constrained Decoding（受控解码，也称为约束解码）在解码阶段干预 token 的生成过程。每一步不是从整个词表中选择 token，而是先通过语法检查屏蔽非法 token，再在剩余合法 token 中采样。

### 3.2 工作流程

```
标准解码：
词表 [token_1, token_2, ..., token_V] → Softmax → 概率分布 → 采样 → 输出

约束解码：
词表 [token_1, token_2, ..., token_V]
          ↓
语法检查：当前 token 是否可能构成合法输出？
          ↓
          ↓ 合法 ←→ 保留
          ↓ 非法 → 屏蔽（概率设为 0）
          ↓
保留的合法 token → Softmax 重归一化 → 采样 → 输出
```

### 3.3 实现方式

**方式一：Logit Masking（logit 掩码）**

这是最常见的实现方式。在 LLM 输出的 logits（未归一化的分数）上直接应用掩码：

```python
import torch

def constrained_decode(logits, grammar_mask):
    """
    logits: [batch_size, vocab_size] 模型输出的原始分数
    grammar_mask: [vocab_size] 布尔掩码，True 表示该 token 合法
    """
    # 将非法 token 的 logit 设为负无穷
    masked_logits = logits.masked_fill(~grammar_mask, float('-inf'))
    # 在合法 token 上计算概率分布
    probs = torch.softmax(masked_logits, dim=-1)
    # 采样
    next_token = torch.multinomial(probs, num_samples=1)
    return next_token
```

**方式二：Token 级别的 FSM（有限状态机）**

使用 FSM 跟踪当前已生成的 token 序列处于语法中的什么状态，以及在当前状态下哪些 token 是合法的：

```python
# 伪代码：Outlines 框架的核心逻辑
class FSMConstraint:
    def __init__(self, json_schema):
        self.fsm = build_fsm_from_schema(json_schema)
        self.state = self.fsm.initial_state
    
    def get_allowed_tokens(self):
        """返回当前状态下合法的 token ID 列表"""
        return self.fsm.get_valid_tokens(self.state)
    
    def step(self, token_id):
        """根据生成的 token 推进状态"""
        self.state = self.fsm.transition(self.state, token_id)
    
    def is_finished(self):
        return self.fsm.is_terminal(self.state)
```

**方式三：下推自动机（Pushdown Automaton）**

对于嵌套结构（如 JSON 中的对象包含数组包含对象），FSM 的能力不足。下推自动机通过栈来跟踪嵌套深度，能够处理任意深度的嵌套结构。XGrammar 框架使用此方法。

### 3.4 优点

1. **100% 格式保证**：只要解码完成，输出一定符合语法约束
2. **类型安全**：可以强制字段类型（字符串、数字、布尔、数组、嵌套对象）
3. **可预测性**：开发者和测试者可以确信输出是可解析的
4. **安全性**：可以屏蔽包含敏感内容或代码注入的 token

### 3.5 缺点

1. **推理退化风险**：如 14.6 节所述，约束解码可能导致指令微调模型的推理质量下降
2. **额外计算开销**：每一步都需要进行语法检查和掩码操作
3. **限制表达能力**：过于严格的约束可能阻止模型输出合理的"我不确定"或"信息不足"
4. **框架依赖性**：需要专门的解码框架（Outlines、XGrammar 等）支持

## 四、两条路径的深度对比

| 维度 | Prompt-Based | Constrained Decoding |
|------|-------------|---------------------|
| **格式保证** | 85-95%（随复杂度下降） | 99.9%+（语法保证） |
| **解码速度** | 无额外开销 | 每步增加 0.1-5ms 开销 |
| **推理质量** | 无影响 | 可能下降 3-12%（见 14.6） |
| **实现复杂度** | 低（只需提示词） | 高（需要解码框架） |
| **调试难度** | 高（偶发失败） | 低（失败可复现） |
| **模型兼容性** | 所有模型 | 需要框架支持 |
| **安全性** | 低（模型可能偏离） | 高（语法边界内） |
| **适用场景** | 低风险、灵活输出 | 高风险、严格格式 |

### 4.1 核心权衡

两条路径的本质是 **可靠性 vs 灵活性** 的权衡：

- Prompt-Based 让模型自由发挥，通过提示词"引导"而非"强制"，格式正确依赖模型的指令遵循能力
- Constrained Decoding 牺牲部分灵活性，获得格式的绝对保障

### 4.2 组合策略："宽松 Prompt + 硬约束解码"

生产中推荐的做法是将两者结合：

```python
def combined_extraction(user_input, schema):
    """
    组合策略：宽松 Prompt 让模型理解任务，硬约束保证格式
    """
    # 步骤1：自由度较高的推理 Prompt
    reasoning_prompt = f"""
    分析以下请求，提取关键信息。
    要求：使用 {schema} 格式输出。
    
    请求：{user_input}
    
    请先思考用户的意图，然后用 JSON 格式输出结果。
    """
    
    # 步骤2：约束解码强制 JSON 格式
    # 使用 XGrammar 或 Outlines 进行约束解码
    with ConstraintEngine(schema) as engine:
        output = engine.generate(reasoning_prompt)
    
    return output
```

这种策略的好处是：
- 模型在推理过程中不受约束干扰（见 14.6 节的两阶段策略）
- 最终输出被约束框架"矫正"为合法格式
- 兼具 Prompt-Based 的推理自由度和 Constrained Decoding 的格式保证

## 五、如何选择？

### 5.1 决策流程

```
你的输出需要下游程序解析吗？
├── 否 → 自由文本即可，不需要结构化输出
└── 是 → 
    ├── 格式错误会导致严重后果吗（系统崩溃/数据损坏/安全漏洞）？
    │   ├── 是 → 必须使用 Constrained Decoding
    │   └── 否 → Prompt-Based 可能足够
    ├── 你的模型支持约束解码框架吗？
    │   ├── 否 → 只能使用 Prompt-Based
    │   └── 是 → 考虑约束解码
    ├── 你对推理质量要求极高吗（医疗/法律/金融分析）？
    │   ├── 是 → 两阶段策略：自由推理 + 约束提取
    │   └── 否 → 直接约束解码即可
    └── 你的输出结构复杂吗（深层嵌套/多种类型）？
        ├── 是 → 推荐 XGrammar 或 Outlines 框架
        └── 否 → OpenAI Structured Outputs 或 Prompt-Based
```

### 5.2 场景推荐

| 场景 | 推荐路径 | 理由 |
|------|---------|------|
| 简单实体提取（姓名、日期、地点） | Prompt-Based | 结构简单，格式错误率低 |
| 工具/函数调用 | Constrained Decoding | 格式错误会导致调用失败 |
| 多步 Agent 推理 | 两阶段（自由+约束） | 保证推理质量同时确保格式 |
| 流式输出（Streaming） | Constrained Decoding | 语法保证 + 逐 token 校验 |
| 原型验证阶段 | Prompt-Based | 快速迭代，无需额外基础设施 |
| 生产环境 API | Constrained Decoding | 稳定性和可靠性要求 |

### 5.3 混合部署策略

在实际的 Agent 产品中，最优方案往往是两者混合：

```yaml
# 混合部署配置示例
pipeline:
  # 阶段1：意图识别（对推理要求低，可直接约束解码）
  intent_classification:
    method: constrained_decoding
    schema: intent_schema
  
  # 阶段2：参数提取（复杂推理，使用两阶段）
  parameter_extraction:
    method: two_stage
    reasoning: free_text
    extraction: constrained_decoding
    
  # 阶段3：输出格式化（纯格式要求）
  output_formatting:
    method: constrained_decoding
    schema: output_schema
    
  # 阶段4：错误处理
  fallback:
    # 如果约束解码失败，降级到 Prompt-Based
    method: prompt_based
```

## 关键概念速查

| 术语 | 解释 |
|------|------|
| Prompt-Based | 通过提示词引导 LLM 生成结构化输出，无语法保证 |
| Constrained Decoding | 在解码阶段通过算法强制输出符合语法约束 |
| Logit Masking | 将非法 token 的 logit 设为负无穷，使其不会被选中 |
| 有限状态机 (FSM) | 通过状态和转移规则描述合法 token 序列的数学模型 |
| 下推自动机 (PDA) | 在 FSM 基础上增加栈结构，可处理嵌套语法 |
| 两阶段策略 | 自由推理 + 约束提取，平衡推理质量和格式正确性 |
