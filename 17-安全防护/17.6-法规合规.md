# 17.6 法规合规

> **法规合规**（Regulatory Compliance）是指 Agent 系统的设计、部署和运营必须遵守适用的法律法规要求。对于 Agent 系统，最重要的法规是欧盟的 **EU AI Act**（欧盟人工智能法案）——全球第一部全面的 AI 监管法律。此外，GDPR、中国《个人信息保护法》（PIPL）、《数据安全法》以及各行业的特定法规也对 Agent 部署有直接影响。

---

## 一、EU AI Act 对 Agent 系统的影响

### 1.1 EU AI Act 的风险分级框架

EU AI Act 将 AI 系统分为四个风险等级，Agent 系统根据其能力和应用场景落入不同的等级：

```
EU AI Act 风险金字塔

                  ┌──────────┐
                  │  不可接受   │  ← 禁止（Prohibited）
                  │  的风险    │     如社会信用评分、实时生物特征监控
                  └─────┬────┘
                        │
                  ┌─────▼────┐
                  │  高风险    │  ← 严格监管（High-Risk）
                  │  (High)   │     如医疗诊断 Agent、司法辅助 Agent
                  └─────┬────┘
                        │
                  ┌─────▼────┐
                  │  有限风险   │  ← 透明度义务（Limited Risk）
                  │ (Limited) │     如客服 Chatbot（需告知用户在与 AI 对话）
                  └─────┬────┘
                        │
                  ┌─────▼────┐
                  │  最小风险   │  ← 无特定义务（Minimal Risk）
                  │ (Minimal) │     如 AI 驱动的电子游戏
                  └──────────┘
```

**Agent 系统落入各等级的判断标准**：

| 风险等级 | Agent 系统的判定条件 | 示例 |
|---------|-------------------|------|
| **高风险** | Agent 在以下领域做出影响个人权利的决策：就业、教育、信贷、司法、移民、关键基础设施 | HR 简历筛选 Agent、贷款审批 Agent、医疗诊断 Agent、法律咨询 Agent |
| **有限风险** | Agent 直接与人类交互，但不做"重大决策" | 客服 Agent、信息检索 Agent、内容生成 Agent |
| **最小风险** | Agent 在封闭环境中执行非关键任务 | 个人代码辅助 Agent、个人日程管理 Agent |

### 1.2 对高风险 Agent 的具体要求

EU AI Act 第 8-29 条规定了高风险 AI 系统的具体义务。对于 Agent 系统，以下是必须满足的关键条款：

```
EU AI Act 对高风险 Agent 的核心要求

┌────────────────────────────────────────────────────────┐
│ 1. 风险管理体系（第 9 条）                              │
│    - 建立覆盖 Agent 全生命周期的风险管理系统              │
│    - 持续识别和评估 Agent 操作的潜在风险                  │
│    - 在 Prompt Injection 等安全威胁中实施风险缓解措施      │
│    - 风险管理的文档化（Risk Management File）             │
├────────────────────────────────────────────────────────┤
│ 2. 数据治理（第 10 条）                                 │
│    - Agent 训练/微调数据的质量和代表性检查                 │
│    - 数据偏差检测与缓解措施                              │
│    - 训练数据中的 PII 必须脱敏                           │
│    - 数据来源的完整文档记录                              │
├────────────────────────────────────────────────────────┤
│ 3. 技术文档和透明度（第 11-12 条）                        │
│    - Agent 的能力边界文档化                              │
│    - 工具权限配置的文档化                                │
│    - Agent 决策逻辑的可解释性说明                         │
│    - 向用户明确告知正在与 AI 系统交互（第 50 条）          │
├────────────────────────────────────────────────────────┤
│ 4. 人工监督（第 14 条）                                 │
│    - Agent 必须设计为可以被人类操作员实时停止              │
│    - 高风险决策必须有人类审核环节                         │
│    - Kill Switch 必须可由人类操作员触发                    │
│    - 在 Agent 不确定性超过阈值时转交人类处理               │
├────────────────────────────────────────────────────────┤
│ 5. 准确性和鲁棒性（第 15 条）                            │
│    - Agent 必须达到预定义的准确度指标                      │
│    - 对 Prompt Injection 等对抗性攻击有鲁棒性              │
│    - 对错误输入的优雅降级                                 │
│    - Agent 操作的审计日志可追溯性要求                      │
└────────────────────────────────────────────────────────┘
```

### 1.3 EU AI Act 对 Agent 部署的实际影响

以在企业中部署一个 HR 面试辅助 Agent 为例，展示 EU AI Act 的实际影响：

```
场景：跨国企业在欧盟地区部署"候选人面试辅助 Agent"

Agent 功能：
  - 读取候选人简历（RAG 检索）
  - 生成面试问题
  - 评估候选人回答的质量
  - 输出面试评估报告

EU AI Act 的触发条件：
  ✅ Agent 在"就业"领域做决策（候选人的面试评估）
  ✅ Agent 处理欧盟公民的个人数据
  ✅ Agent 的结果影响个体的雇佣机会
  → 被判定为高风险 AI 系统

合规要求映射：

1. 风险管理（第 9 条）
   - 评估"Agent 错误评估候选人"的风险
   - 评估"Agent 因 Prompt Injection 被操纵"的风险（见 17.1）
   - 实施"人类复核"环节：Agent 的评估结果必须由面试官审核

2. 透明度（第 50 条）
   - 候选人必须被告知"面试评估部分由 AI 辅助完成"
   - Agent 生成的评估报告必须标注为"AI 辅助生成"

3. 人工监督（第 14 条）
   - 面试官可以随时修改或拒绝 Agent 的评估
   - Kill Switch 可以由面试官触发（见 17.4）

4. 审计追溯（第 15 条）
   - Agent 的每次评估操作必须记录（谁、什么时间、用了什么数据、输出了什么）
   - 记录必须保留至少 6 个月
   - 记录必须支持事后审查
```

### 1.4 EU AI Act 的合规时间线

```
EU AI Act 实施时间线（2024 年通过，逐步生效）：

2025 年 2 月：禁止的 AI 实践条款生效
2025 年 5 月：通用 AI 行为准则生效
2026 年 8 月：高风险 AI 系统的多数条款生效
         ↑  ← 注意：部分高风险 Agent 系统在此日期前需合规
2027 年 8 月：附件 III 中高风险系统的全面合规期限

企业现在就应该开始准备的行动：
  1. 盘点现有 Agent 系统，判断风险等级
  2. 对高风险 Agent 系统，建立风险管理体系
  3. 部署审计追踪和人工监督机制
  4. 文档化 Agent 的能力、权限和决策逻辑
```

## 二、数据本地化要求

### 2.1 各辖区数据本地化法规对比

| 辖区 | 核心法规 | 数据本地化要求 | 对 Agent 的影响 |
|------|---------|--------------|---------------|
| **欧盟** | GDPR + EU AI Act | 个人数据原则上不能出境，需"充分性认定"或标准合同条款（SCC） | Agent 处理欧盟用户数据时必须使用欧盟境内的 LLM 实例或签署 DPA |
| **中国** | PIPL + 数据安全法 | 重要数据出境需安全评估；关键信息基础设施运营者（CIIO）数据原则上本地存储 | 在中国运营的 Agent 可能需要在中国境内部署 LLM |
| **美国** | 联邦层面无统一法（州级有 CCPA 等） | 无强制本地化要求，但出口管制限制 AI 模型参数出境 | Agent 使用开源模型时需注意出口管制分类 |
| **日本** | 个人信息保护法 | 数据出境需本人同意或等效保护措施 | Agent 需提供数据跨境处理的知情同意 |
| **印度** | DPDP Act 2023 | 重要数据本地化存储，允许部分数据出境 | Agent 架构上需支持数据分区存储 |

### 2.2 Agent 系统的合规架构设计

为了同时满足多个辖区的合规要求，Agent 系统应采用**分区部署架构**：

```

                        │   全局控制平面            │

                        └──┬───────┬───────┬──────┘

              │            │       │       │            │

         │  EU 区   │   │ 中国区 │ │ 美国区 │ │ 其他区│    │
```

### 2.3 数据分区路由实现

```python
class CompliantRouter:
    """
    合规路由：根据用户所属辖区将请求路由到对应的 Agent 实例
    确保数据不跨境流动
    """
    
    # 区域配置
    REGION_CONFIG = {
        'eu': {
            'llm_endpoint': 'https://eu-internal.llm.company.com',
            'data_storage': 'eu-s3',
            'audit_log': 'eu-audit-log',
            'allowed_tools': ['read', 'write', 'shell'],  # 不允许 network 出站
            'compliance': ['gdpr', 'eu_ai_act'],
        },
        'cn': {
            'llm_endpoint': 'https://cn-internal.llm.company.com',
            'data_storage': 'cn-s3',
            'audit_log': 'cn-audit-log',
            'allowed_tools': ['read', 'write'],
            'compliance': ['pipl', 'dsl'],
        },
        'us': {
            'llm_endpoint': 'https://us-internal.llm.company.com',
            'data_storage': 'us-s3',
            'audit_log': 'us-audit-log',
            'allowed_tools': ['read', 'write', 'shell', 'network'],
            'compliance': ['ccpa'],
        },
        'default': {
            'llm_endpoint': 'https://global.llm.company.com',
            'data_storage': 'global-s3',
            'audit_log': 'global-audit-log',
            'allowed_tools': ['read'],
            'compliance': [],
        },
    }
    
    def __init__(self):
        self.region_resolver = self._build_region_resolver()
    
    def _build_region_resolver(self):
        """构建区域解析器"""
        # 实际实现中可以使用 GeoIP 数据库 + 用户 profile 中的 region 字段
        return {
            'EU': 'eu',
            'CN': 'cn',
            'US': 'us',
        }
    
    def route_request(self, user_id: str, user_ip: str, 
                       request_data: dict) -> dict:
        """
        根据用户区域路由请求
        """
        # 1. 确定用户所属区域
        # 优先级：用户设置 > IP 地理定位 > 默认
        region_code = self._resolve_region(user_id, user_ip)
        
        # 2. 获取该区域的配置
        config = self.REGION_CONFIG.get(
            region_code, 
            self.REGION_CONFIG['default']
        )
        
        # 3. 检查请求数据是否可以在此区域处理
        data_check = self._check_data_compliance(
            request_data, region_code, config
        )
        
        if not data_check['allowed']:
            return {
                'status': 'rejected',
                'reason': data_check['reason'],
                'region': region_code,
                'suggested_action': data_check['suggested_action']
            }
        
        # 4. 返回路由决策
        return {
            'status': 'routed',
            'region': region_code,
            'endpoint': config['llm_endpoint'],
            'storage': config['data_storage'],
            'allowed_tools': config['allowed_tools'],
            'compliance_requirements': config['compliance'],
            'audit_log_config': {
                'destination': config['audit_log'],
                'retention_days': 365 if region_code == 'eu' else 180,
            }
        }
    
    def _resolve_region(self, user_id: str, user_ip: str) -> str:
        """解析用户所在区域"""
        # 简化实现——生产环境应使用 GeoIP + 用户设置
        # 模拟：根据 IP 段判断区域
        if user_ip.startswith('10.') or user_ip.startswith('192.168.'):
            return 'eu'  # 假设内部 IP 来自 EU
        
        # 默认返回 EU（最保守的默认值）
        return 'eu'
    
    def _check_data_compliance(self, data: dict, region: str, 
                                config: dict) -> dict:
        """检查数据是否符合区域合规要求"""
        # 如果数据包含 EU 用户 PII 且尝试在非 EU 区域处理
        if data.get('contains_eu_pii') and region != 'eu':
            return {
                'allowed': False,
                'reason': 'EU PII data cannot be processed outside EU',
                'suggested_action': 'reroute_to_eu'
            }
        
        # 如果数据包含中国居民个人信息且尝试在非中国区域处理
        if data.get('contains_cn_pii') and region != 'cn':
            return {
                'allowed': False,
                'reason': 'Chinese resident PII data cannot be processed outside China',
                'suggested_action': 'reroute_to_cn'
            }
        
        return {'allowed': True, 'reason': 'ok'}
```

## 三、模型输出审计追溯

### 3.1 审计追溯的必要性

EU AI Act 第 15 条要求高风险 AI 系统的输出必须具有可追溯性。对于 Agent 系统，这意味着：

```
审计追溯要回答的问题：

1. WHAT —— Agent 做了什么？
   - 调用了什么工具？参数是什么？
   - 生成了什么输出？

2. WHY —— Agent 为什么这样做？
   - 基于什么推理路径？
   - 使用了什么上下文数据？

3. WHO —— 谁发起的？
   - 哪个用户？
   - 什么会话？
   - 哪个 Agent 实例？

4. WHEN —— 什么时候做的？
   - 精确到毫秒的时间戳

5. WHERE —— 数据处理在哪里完成？
   - 哪个区域？
   - 哪个模型实例？
```

### 3.2 审计链实现

```python
import time
import json
import hashlib
from typing import Any

class AuditChain:
    """
    审计链：记录 Agent 的每一步操作，形成不可篡改的审计链
    
    使用哈希链（Hash Chain）确保审计记录的完整性：
    每条记录包含上一条记录的哈希值，修改任何一条记录
    都会导致后续所有记录的哈希不匹配
    """
    
    def __init__(self, agent_id: str, session_id: str):
        self.agent_id = agent_id
        self.session_id = session_id
        self.chain: list[dict] = []
        self.previous_hash = "0" * 64  # 初始哈希（genesis）
        
        # 记录链的起始
        self._append_entry({
            'event_type': 'session_start',
            'agent_id': agent_id,
            'session_id': session_id,
        })
    
    def record_tool_call(self, 
                          tool_name: str,
                          params: dict,
                          reasoning: str,
                          result: Any,
                          context: dict = None) -> str:
        """
        记录一次工具调用的审计条
        
        返回该条记录的 ID
        """
        entry = {
            'event_type': 'tool_call',
            'timestamp': time.time(),
            'tool_name': tool_name,
            'params_snapshot': self._sanitize_params(params),
            'reasoning_summary': reasoning[:500] if reasoning else '',
            'result_summary': str(result)[:500] if result else '',
            'context': context or {},
        }
        
        return self._append_entry(entry)
    
    def record_decision(self, 
                         decision_type: str,
                         input_data: dict,
                         output_data: dict,
                         confidence: float = None) -> str:
        """
        记录 Agent 的决策节点
        """
        entry = {
            'event_type': 'decision',
            'timestamp': time.time(),
            'decision_type': decision_type,
            'input_summary': str(input_data)[:500],
            'output_summary': str(output_data)[:500],
            'confidence': confidence,
        }
        
        return self._append_entry(entry)
    
    def record_security_event(self,
                               event_type: str,
                               severity: str,
                               details: dict) -> str:
        """
        记录安全事件（注入检测、权限拒绝等）
        """
        entry = {
            'event_type': 'security_event',
            'timestamp': time.time(),
            'security_event_type': event_type,
            'severity': severity,
            'details': details,
        }
        
        return self._append_entry(entry)
    
    def _append_entry(self, entry: dict) -> str:
        """
        追加审计条目，计算哈希链
        """
        # 添加链信息
        entry['chain_index'] = len(self.chain)
        entry['previous_hash'] = self.previous_hash
        
        # 计算当前条目的哈希
        entry_json = json.dumps(entry, sort_keys=True, default=str)
        entry_hash = hashlib.sha256(entry_json.encode('utf-8')).hexdigest()
        entry['entry_hash'] = entry_hash
        
        # 存储
        self.chain.append(entry)
        self.previous_hash = entry_hash
        
        return entry_hash
    
    def verify_chain_integrity(self) -> tuple[bool, list[dict]]:
        """
        验证审计链的完整性
        返回 (是否完整, 不一致的记录列表)
        """
        violations = []
        
        for i, entry in enumerate(self.chain):
            # 验证哈希链
            if i > 0:
                prev_entry = self.chain[i - 1]
                if entry['previous_hash'] != prev_entry['entry_hash']:
                    violations.append({
                        'index': i,
                        'issue': 'hash_chain_broken',
                        'expected_previous_hash': prev_entry['entry_hash'],
                        'actual_previous_hash': entry['previous_hash']
                    })
            
            # 验证当前条目的哈希
            entry_copy = dict(entry)
            stored_hash = entry_copy.pop('entry_hash', '')
            entry_json = json.dumps(entry_copy, sort_keys=True, default=str)
            computed_hash = hashlib.sha256(entry_json.encode('utf-8')).hexdigest()
            
            if computed_hash != stored_hash:
                violations.append({
                    'index': i,
                    'issue': 'entry_tampered',
                    'stored_hash': stored_hash,
                    'computed_hash': computed_hash
                })
        
        return len(violations) == 0, violations
    
    def export_audit_report(self) -> dict:
        """
        导出完整的审计报告
        """
        verified, violations = self.verify_chain_integrity()
        
        return {
            'agent_id': self.agent_id,
            'session_id': self.session_id,
            'start_time': self.chain[0]['timestamp'] if self.chain else None,
            'end_time': self.chain[-1]['timestamp'] if self.chain else None,
            'total_entries': len(self.chain),
            'chain_integrity': verified,
            'violations': violations,
            'entries': self.chain,
            'export_time': time.time(),
        }
    
    def _sanitize_params(self, params: dict) -> dict:
        """脱敏参数中的敏感信息"""
        sensitive_keys = ['password', 'api_key', 'token', 'secret']
        sanitized = {}
        for k, v in params.items():
            if any(sk in k.lower() for sk in sensitive_keys):
                sanitized[k] = '[REDACTED]'
            else:
                sanitized[k] = str(v)[:200]
        return sanitized
```

### 3.3 合规审计报告模板

EU AI Act 要求高风险 AI 系统维护的技术文档应包含以下内容：

```yaml
# compliance/agent-technical-documentation.yaml
# EU AI Act Article 11 — Technical Documentation

agent:
  name: "HR Interview Assistant Agent"
  version: "2.3.1"
  risk_classification: "High-Risk (Annex III, Point 4)"
  
  # 能力描述
  capabilities:
```

## 关键概念速查

| 术语 | 解释 |
|------|------|
| EU AI Act | 欧盟人工智能法案——全球首部全面的 AI 监管法律 |
| 高风险 AI 系统 | EU AI Act 中定义的，在就业、信贷、司法等领域影响个人权利的 AI 系统 |
| 风险管理 | 识别、评估和缓解 AI 系统潜在风险的系统化过程 |
| 人工监督 | 高风险 AI 系统必须设计为可被人类操作员实时监督和干预 |
| 审计追溯 | 通过日志记录 AI 系统的操作，支持事后审查和监管检查 |
| 哈希链 | 通过将每条记录的哈希值链接到上一条记录，确保审计日志不可篡改 |
| 数据本地化 | 数据在其产生的地理区域内处理和存储的合规要求 |
| 分区部署 | 在不同区域部署独立的 Agent 实例以满足数据本地化要求 |
| PIPL | 中国《个人信息保护法》（Personal Information Protection Law） |
| 数据安全法 | 中国《数据安全法》，建立数据分类分级和重要数据保护制度 |
| SCC | 标准合同条款（Standard Contractual Clauses），GDPR 下的数据跨境传输机制 |
| CE 标志 | 欧盟市场准入标志，高风险 AI 系统需通过符合性评估后加贴 |
| DPA | 数据处理协议（Data Processing Agreement） |
