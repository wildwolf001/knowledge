# 24.5 元数据质量衰减 —— RAG 索引随时间腐化

> 现象：RAG 系统的检索质量随着时间推移缓慢下降，Agent 效果逐周变差，但没有人在意——因为"下降"是渐进的，每天只下降 0.1%，三个月后累计下降 10%。没有告警机制，团队只在用户投诉激增时才意识到出了问题。

---

## 一、症状描述

### 1.1 典型的衰减曲线

某知识库 QA Agent 上线后的表现：

```
周 1: 检索准确率 92%  → 团队庆祝上线 🎉
周 4: 检索准确率 89%  → 没人注意（"在误差范围内"）
周 8: 检索准确率 84%  → 产品经理说"感觉最近回答不太准"
周 12: 检索准确率 76%  → 用户投诉率 +40%，团队开始调查
```

每天 0.1% 的衰减在短时间窗口内完全不可见。常规的监控（日粒度）也无法捕捉这种缓慢的漂移。

### 1.2 多维度衰减

元数据质量衰减不是单一维度的，而是多个维度同时恶化：

**维度 1：文档覆盖率下降**

新文档不断加入，但旧文档可能已过时或被删除。RAG 索引中包含的文档与用户实际需求之间的"覆盖率差异"逐渐扩大：

```
初始状态：索引有 10,000 篇文档，覆盖 90% 的用户问题
3 个月后：索引有 15,000 篇文档，但覆盖率降到 75%
原因：新增 5,000 篇文档，但其中有 3,000 篇是过时的/重复的/低质量的
```

**维度 2：Embedding 质量漂移**

文档的 embedding 在索引时计算，但随着业务发展：

```
初始：所有文档用 text-embedding-ada-002 生成 embedding
3 个月后：新增文档用 text-embedding-3-large 生成 embedding
→ 两个版本的 embedding 分布不一致 → 跨版本检索质量下降
```

或者更隐蔽的：**同一 embedding 模型在更新版本后分布发生变化**。

**维度 3：元数据（Metadata）过期**

```json
// 6 个月前索引的文档元数据
{
  "title": "2024 年退款政策",
  "last_updated": "2024-06-15",  // ← 可能已更新多次
  "department": "客服部",          // ← 可能已重组
  "version": "v1.2",             // ← 已到 v3.0
  "tags": ["退款", "policy"],    // ← 标签体系已变更
  "is_active": true              // ← 文档已归档但未标记
}
```

**维度 4：用户查询分布漂移（Query Distribution Drift）**

用户问的问题类型在变化，但索引的文档分布没有跟上：

```
上线初期：用户主要问 "如何退款"、"如何改密码"（有大量文档覆盖）
3 个月后：用户主要问 "API 限流策略"、"Webhook 配置"（文档覆盖不足）
→ 不是索引变差了，是用户的问题变了，但索引没有随之调整
```

### 1.3 生产数据

根据 2024 年针对 30 个生产 RAG 系统的调研：

| 衰减维度 | 3 个月后平均衰减 | 6 个月后平均衰减 | 可检测性 |
|---------|-----------------|-----------------|---------|
| 检索准确率 | -6.5% | -12.3% | 需基准测试 |
| Top-5 召回率 | -4.2% | -8.7% | 需人工标注 |
| 答案准确率 | -5.1% | -10.5% | 间接信号 |
| 用户满意度 | -8% (NPS) | -15% (NPS) | 滞后指标 |

关键发现：**90% 的团队的 RAG 系统在 6 个月内经历了可测量的质量衰减，但只有 15% 的团队有检测机制**。

## 二、根因分析

### 2.1 元数据不是一次性的资产

最常见的误解：认为 RAG 索引构建是一次性工作——文档写入索引后就"完事了"。

实际上，RAG 索引是一种**易腐化资产（Perishable Asset）**：

```
RAG 索引的"保质期"取决于：
1. 文档的更新频率（文档多久更新一次？）
2. 用户的查询分布漂移速度（业务变化多快？）
3. 标注数据的时效性（测试集多久过期？）
4. embedding 模型的版本稳定性（模型是否在升级？）
```

### 2.2 缺乏质量基准和持续评测

大多数 RAG 系统在上线后没有持续的评测机制：

```
❌ 常见情况：
上线前：团队标注了 500 条测试数据 → 评测通过 → 上线
上线后：没有人再标注数据 → 不知道质量是否下降
发现问题时：用户投诉 → 客服反馈 → 产品经理转达 → 技术排查
         → 从问题出现到发现平均滞后 2-4 周
```

### 2.3 数据的"静默腐化"

文档本身不会报错。过时的文档看起来仍然是合法的文档：

```markdown
# 2024 年退款政策（2024-06 编写，2025 年仍被检索到）

用户在 2024 年 6 月 15 日之前购买的商品...
← 但现在是 2025 年 Q2，政策已更新 3 次
```

索引系统没有"文档过期"的概念，也没有"这个文档最近的检索频率"或"这个文档对回答质量的贡献"等反馈指标。

### 2.4 标注测试集的"概念漂移"

用于评测的测试数据集本身也会过期：

```
2024 年 6 月标注的测试集：
问题: "如何退款？" → 答案引用 2024 年退款政策文档

2025 年 1 月：退款政策已变更
旧测试集：Agent 回答引用旧文档 → 标注认为是"正确"（但实际已过时）
新测试集：应该引用新文档 → 但没标注 → 无法评测
```

**测试数据本身的时效性**是元数据质量衰减中最容易被忽视的问题。

## 三、检测方法

### 3.1 自动质量基准（Automated Benchmarking）

建立持续运行的自动评测管线：

```python
class MetadataQualityBenchmark:
    """
    自动运行的质量基准测试。
    每周运行一次，生成质量趋势报告。
    """
    def __init__(self, test_suite_path: str):
        self.test_suite = self._load_test_suite(test_suite_path)
    
    def run(self) -> dict:
        """运行完整基准测试"""
        results = {
            "retrieval_accuracy": self._test_retrieval_accuracy(),
            "top5_recall": self._test_top5_recall(),
            "metadata_completeness": self._test_metadata_fields(),
            "freshness_score": self._test_document_freshness(),
            "coverage_score": self._test_query_coverage(),
        }
        
        # 与上周结果对比
        deltas = self._compare_with_previous(results)
        
        # 检测趋势
        trends = self._detect_trends()
        
        return {
            "current": results,
            "deltas": deltas,
            "trends": trends,
            "overall_health": self._calculate_health(results, trends)
        }
    
    def _test_retrieval_accuracy(self) -> float:
        """测试检索准确率（Top-1 是否正确文档）"""
        correct = 0
        for query, expected_doc_id in self.test_suite.retrieval_tests:
            results = retriever.retrieve(query, top_k=1)
            if results[0].doc_id == expected_doc_id:
                correct += 1
        return correct / len(self.test_suite.retrieval_tests)
```

### 3.2 元数据年龄报告

追踪索引中元数据的时效性：

```python
def metadata_freshness_report(index_stats: dict) -> dict:
    """
    生成元数据新鲜度报告。
    """
    now = datetime.now()
    docs = index_stats["documents"]
    
    age_buckets = {
        "< 1 周": 0,
        "1 周 - 1 月": 0,
        "1 月 - 3 月": 0,
        "3 月 - 6 月": 0,
        "> 6 月": 0,
    }
    
    for doc in docs:
        age = now - doc["last_updated"]
        if age < timedelta(weeks=1):
            age_buckets["< 1 周"] += 1
        elif age < timedelta(days=30):
            age_buckets["1 周 - 1 月"] += 1
        elif age < timedelta(days=90):
            age_buckets["1 月 - 3 月"] += 1
        elif age < timedelta(days=180):
            age_buckets["3 月 - 6 月"] += 1
        else:
            age_buckets["> 6 月"] += 1
    
    total = sum(age_buckets.values())
    
    return {
        "distribution": {k: v/total for k, v in age_buckets.items()},
        "stale_ratio": age_buckets["> 6 月"] / total,
        "health": "GOOD" if (age_buckets["> 6 月"] / total) < 0.2
                  else "WARNING" if (age_buckets["> 6 月"] / total) < 0.4
                  else "CRITICAL"
    }
```

### 3.3 查询分布漂移检测

监控用户查询的内容变化：

```python
def detect_query_drift(recent_queries: list[str], 
                        historical_queries: list[str]) -> float:
    """
    检测查询分布漂移。
    
    使用 embedding 聚类比较近期查询和历史查询的分布差异。
    漂移值 > 0.2 表示可能需要更新索引。
    """
    # 对查询进行聚类
    recent_clusters = cluster_queries(recent_queries, n_clusters=10)
    historical_clusters = cluster_queries(historical_queries, n_clusters=10)
    
    # 计算分布差异（JS 散度）
    drift = js_divergence(recent_clusters, historical_clusters)
    
    return drift
```

**监控指标配置**：

```yaml
指标: index_retrieval_accuracy (gauge)
  频率: 每日
  告警: 周均值下降 > 2% → warning
        周均值下降 > 5% → critical

指标: index_stale_doc_ratio (gauge)
  定义: 超过 6 个月未更新的文档比例
  告警: > 20% → warning
        > 40% → critical

指标: index_query_drift (gauge)
  定义: 当前查询分布与基线的 JS 散度
  告警: > 0.2 → warning
        > 0.4 → critical
```

## 四、解决方案

### 4.1 文档生命周期管理

为每个文档设定生命周期，到期自动标记为"待审核"：

```python
class DocumentLifecycleManager:
    """
    文档生命周期管理器。
    每个文档进入索引时设定"新鲜期"和"过期时间"。
    """
    LIFECYCLE_POLICIES = {
        "政策文档": {
            "freshness_period": timedelta(days=30),  # 30 天后需要审核
            "max_age": timedelta(days=180),           # 180 天后强制下架
            "review_action": "auto_review"
        },
        "API 文档": {
            "freshness_period": timedelta(days=60),
            "max_age": timedelta(days=365),
            "review_action": "notify_owner"
        },
        "FAQ": {
            "freshness_period": timedelta(days=90),
            "max_age": timedelta(days=365),
            "review_action": "auto_archive_if_unused"
        },
        "用户指南": {
            "freshness_period": timedelta(days=180),
            "max_age": timedelta(days=730),
            "review_action": "notify_owner"
        }
    }
    
    def audit(self, index_snapshot: list[Document]) -> list[AuditResult]:
        """执行文档新鲜度审计"""
        results = []
        now = datetime.now()
        
        for doc in index_snapshot:
            age = now - doc.last_updated
            policy = self.LIFECYCLE_POLICIES.get(doc.doc_type, {})
            max_age = policy.get("max_age", timedelta(days=365))
            
            if age > max_age:
                results.append(AuditResult(
                    doc_id=doc.id,
                    action="MARK_FOR_REVIEW",
                    reason=f"文档已超过最大年龄 ({age.days} 天)"
                ))
            elif age > policy.get("freshness_period"):
                results.append(AuditResult(
                    doc_id=doc.id,
                    action="FLAG_FRESHNESS",
                    reason=f"文档超过新鲜期 ({age.days} 天)，建议审核"
                ))
        
        return results
```

### 4.2 自动审核 Pipeline

```python
class IndexQualityPipeline:
    """
    每周运行的索引质量审核 Pipeline。
    """
    def run_weekly(self):
        """执行每周质量审核"""
        report = {}
        
        # 1. 新鲜度审核
        report["freshness"] = self._check_freshness()
        
        # 2. 覆盖率分析
        report["coverage"] = self._analyze_coverage()
        
        # 3. 检索质量基准
        report["benchmark"] = self._run_benchmark()
        
        # 4. 冗余检测
        report["duplicates"] = self._detect_duplicates()
        
        # 5. 无引用文档
        report["unused"] = self._find_unused_docs()
        
        # 生成汇总
        self._generate_report(report)
        
        # 如果质量下降超过阈值，自动触发修复
        if report["benchmark"]["accuracy_drop"] > 0.05:
            self._trigger_auto_repair(report)
    
    def _detect_duplicates(self) -> list[str]:
        """检测内容高度相似的重复文档"""
        docs = self._get_all_docs()
        duplicates = []
        
        for i, doc1 in enumerate(docs):
            for doc2 in docs[i+1:]:
                sim = cosine_similarity(doc1.embedding, doc2.embedding)
                if sim > 0.95:
                    duplicates.append({
                        "doc_a": doc1.id,
                        "doc_b": doc2.id,
                        "similarity": sim,
                        "action": "MERGE_OR_REMOVE"
                    })
        
        return duplicates
    
    def _find_unused_docs(self) -> list[str]:
        """查找从未被检索到的文档"""
        retrieval_logs = self._get_retrieval_logs(days=30)
        retrieved_ids = set(log["doc_id"] for log in retrieval_logs)
        all_ids = set(doc.id for doc in self._get_all_docs())
        
        unused = all_ids - retrieved_ids
        return [
            {"doc_id": doc_id, "days_unused": 30}
            for doc_id in unused
        ]
```

### 4.3 Embedding 版本管理

追踪 embedding 版本并对齐：

```python
class EmbeddingVersionManager:
    """
    Embedding 版本管理。
    确保索引中的 embedding 使用一致的模型版本。
    """
    def __init__(self):
        self.embedding_registry = {}
    
    def index_document(self, doc: Document, model_version: str):
        """索引文档并记录 embedding 版本"""
        embedding = self._compute_embedding(doc.content, model_version)
        doc.embedding_version = model_version
        doc.embedding = embedding
        self.embedding_registry[doc.id] = {
            "version": model_version,
            "timestamp": datetime.now()
        }
    
    def reindex_if_needed(self, doc: Document, 
                          target_version: str) -> bool:
        """如果 embedding 版本不一致则重新索引"""
        current = self.embedding_registry.get(doc.id, {})
        if current.get("version") != target_version:
            self.index_document(doc, target_version)
            return True
        return False
    
    def check_version_consistency(self) -> dict:
        """检查索引中 embedding 版本的一致性"""
        versions = {}
        for doc_id, info in self.embedding_registry.items():
            v = info["version"]
            versions[v] = versions.get(v, 0) + 1
        
        total = sum(versions.values())
        return {
            "version_distribution": versions,
            "dominant_version": max(versions, key=versions.get),
            "consistency_score": max(versions.values()) / total
        }
```

### 5.2 持续测试集更新

将用户反馈转化为新的测试数据：

```python
class TestSetUpdater:
    """
    从用户反馈中持续生成新的测试数据。
    每周更新一次测试集。
    """
    def update_from_feedback(self, feedback_logs: list[dict]):
        """
        从用户反馈日志中提取新的测试案例。
        - 用户明确的"点赞" → 作为正例
        - 用户"点踩"或反馈"不准确" → 作为负例
        - 用户手动修改了回答 → 作为"正确答案"
        """
        new_tests = []
        
        for log in feedback_logs:
            if log["rating"] == "thumbs_down":
                new_tests.append({
                    "query": log["user_query"],
                    "expected_doc": log["correct_doc"],  # 人工修正后的文档
                    "type": "negative_regression"
                })
            elif log["rating"] == "thumbs_up":
                new_tests.append({
                    "query": log["user_query"],
                    "expected_doc": log["retrieved_doc"],
                    "type": "positive_regression"
                })
        
        self._add_to_test_suite(new_tests)
```

## 关键教训速查

| 教训 | 说明 |
|------|------|
| 元数据质量衰减是渐变而非突变 | 每天 0.1% 的下降在短时间窗口内不可见 |
| 没有告警是最危险的 | 大多数团队没有元数据质量监控机制 |
| 衰减是多维度的 | 检索准确率、覆盖率、新鲜度、查询漂移 |
| 测试集本身也会过期 | 需要用用户反馈持续更新测试数据 |
| 文档生命周期管理是基础 | 每个文档都要设定新鲜期和过期时间 |
| SLA 驱动质量维护 | 设定明确的质量指标和违规响应流程 |
