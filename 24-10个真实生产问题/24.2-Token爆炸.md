# 24.2 Token 爆炸 —— 50 步工作流吃掉 100 万+ token

> 现象：一个看起来只有 50 步的 Agent 工作流，Token 消耗超过 100 万。不是因为任务复杂度高，而是工具元数据、检索结果和历史记录的层层累积导致了指数级膨胀。

---

## 一、症状描述

### 1.1 典型的 Token 账单冲击

某 SaaS 公司的代码审查 Agent 上线后，团队收到 AWS Bedrock 账单时震惊了：

```
预计：50 步/对话 × 2,000 tokens/步 = 100,000 tokens/对话
实际：50 步/对话 × 22,000 tokens/步 = 1,100,000 tokens/对话
超出预期：11 倍
月成本：$4,500（vs 预期 $400）
```

更令人困惑的是——每个步骤的"逻辑复杂度"并没有变，Token 消耗却随步骤数非线性增长。

### 1.2 Token 增长的"锯齿"模式

监控单次对话的 Token 消耗曲线，典型的模式是：

```
Step 1:   2,100 tokens  ← 系统指令(1.5K) + 用户输入(0.6K)
Step 2:   4,500 tokens  ← + 工具1的完整 Schema(2K) + 工具1结果(1K)
Step 3:   7,200 tokens  ← + 工具2的完整 Schema(2K) + 工具2结果(1.5K)
Step 4:  10,100 tokens  ← + 工具3的完整 Schema(2K) + 工具3结果(1.5K)
...
Step 10: 28,000 tokens  ← 累积的工具结果开始占据大头
...
Step 50: 110,000 tokens ← 50个工具结果 + 50条 Schema + 对话历史
```

每步增加的 Token 不是"输入 token + 输出 token"，而是**把所有历史重新读一遍 + 新的输出**。在 50 步时，Agent 每次推理都需要处理 110K tokens 的上下文。

### 1.3 生产数据

根据 Anthropic 2024 年的客户调研数据，生产环境中 Agent 系统的 Token 消耗分布如下：

| 组件 | 占比（典型值） | 说明 |
|------|--------------|------|
| 系统指令 | 5-15% | 通常是固定的 |
| 工具元数据 | 15-30% | 随工具数量线性增长 |
| 工具执行结果 | 25-45% | 随步数线性增长，有时超线性 |
| 对话历史 | 10-25% | 随轮数线性增长 |
| 检索结果（RAG） | 10-30% | 每轮检索可能附带大量文档 |
| 中间推理 | 5-15% | Agent 的 CoT 推理内容 |

**工具执行结果**和**工具元数据**是最容易被忽视的 Token 消耗大户。

## 二、根因分析

### 2.1 工具元数据膨胀

这是最隐蔽的 Token 消耗来源。每个工具注册时开发者写入的元数据包括：

```json
{
  "name": "search_customer_by_email",
  "description": "通过邮箱地址搜索客户信息。输入完整的邮箱地址，返回匹配的客户记录。如果找到多条记录，返回所有匹配项。",
  "parameters": {
    "type": "object",
    "properties": {
      "email": {
        "type": "string",
        "description": "要搜索的客户邮箱地址，必须是完整的邮箱格式，例如 user@example.com"
      },
      "include_inactive": {
        "type": "boolean",
        "description": "是否包含已停用的客户账户，默认为 false"
      }
    },
    "required": ["email"]
  }
}
```

**单个工具 Schema 可能占用 200-500 tokens**。100 个工具 = 20,000-50,000 tokens。并且**每轮推理都会重新发送全部工具 Schema**（即使本轮只用到 1 个工具）。

**Token 膨胀的倍增效应**：

```
工具数量 → Token 消耗
   10   →   2,000-5,000  (可接受)
   50   →  10,000-25,000 (开始心疼)
  100   →  20,000-50,000 (不可忽视)
  200   →  40,000-100,000 (触发上下文截断)
```

### 2.2 工具结果累积

每步的工具调用结果被追加到上下文，这是最严重的 Token 消耗源：

```
步骤 1: get_user_info → 返回 800 tokens 的用户信息 JSON
步骤 2: get_orders   → 返回 1,200 tokens 的订单列表
步骤 3: search_ticket → 返回 600 tokens 的工单列表
...
步骤 50: 累计 50 个工具结果 = 40,000+ tokens

关键问题：这 50 个结果中，真正对当前步骤有用的可能只有 2-3 个。
但 Agent 每步仍然需要处理全部的 40K tokens。
```

### 2.3 系统指令过度设计

开发者倾向于在系统指令中"把所有可能性都说清楚"：

```
系统指令（过度设计版，~4,000 tokens）：
- 角色定义 (300 tokens)
- 通用行为规则 (800 tokens)  
- 20 条具体限制条件 (1,200 tokens)
- 输出格式要求 (500 tokens)
- 10 个示例对话 (1,200 tokens)
```

其中大部分内容是**一次性读取、永远不会用到的"安全网"**。

### 2.4 对话历史冗余

Agent 框架默认将"完整的思考链"追加到历史中：

```json
{
  "role": "assistant",
  "content": "让我分析一下。用户想查询账户余额，我需要调用 get_account_balance 工具。这个工具需要一个 user_id 参数。我已经从登录信息中获取了 user_id = U12345。好，现在让我调用它...（80 tokens 的内部独白）",
  "tool_calls": [...]
}
```

这些内部独白对下一步是有价值的，但**90% 的内容在下一步就失去了意义**。

### 2.5 MCP 工具元数据膨胀（2026 年新增案例）

2026 年，MCP（Model Context Protocol）在 AI 生产环境中大规模普及后，工具元数据膨胀达到了一个新的量级——一个此前完全被低估的 Token 消耗黑洞。

**真实案例**：某团队的 Agent 集成了 7 个 MCP Server（数据库、GitHub、Slack、Jira、邮件、监控、文档），每个 Server 暴露 5-15 个工具，共 82 个工具。每轮推理的 Token 消耗：

```
MCP Server 工具元数据 Token 占用明细：

Server          工具数   Schema Token    描述
────────────────────────────────────────────────────
DB Server         15      14,200   含所有表结构的 CRUD 操作
GitHub Server     12      11,800   含 Repo/PR/Issue/Workflow 全部端点
Slack Server      10       9,600   含消息/频道/用户/文件/搜索
Jira Server       8        8,400   含 Issue/Sprint/Board/Project
Mail Server       6        6,100   含 Send/Read/Search/Filter
Monitor Server    12       9,500   含 Alert/Metric/Log/Dashboard
Docs Server       7        7,400   含 CRUD + Search + Version
────────────────────────────────────────────────────
总计             82      67,000+   tokens（仅工具定义！）
```

**问题规模**：
- **7 个 MCP Server = 67K+ tokens** 仅用于工具定义
- 加上实际工具调用结果和对话历史，单轮推理很容易超过 100K tokens
- MCP 的标准化描述格式（每个工具都需要完整的 JSON Schema + description）进一步加剧了这个问题

**2026 年解决方案**：

**方案 1：Tool Search（Anthropic 官方方案）**

```python
# 2026 年 Anthropic 引入 Tool Search 功能
# 不再将全部工具定义发送到上下文，而是在推理时动态搜索相关工具

# 传统方式（发送所有工具）：
client.messages.create(
    model="claude-sonnet-4-20260514",
    tools=ALL_82_TOOLS,  # 67K tokens，每次全部发送
    messages=messages
)

# Tool Search 方式（只检索相关工具）：
client.messages.create(
    model="claude-sonnet-4-20260514",
    tools=ALL_82_TOOLS,
    tool_search={"mode": "auto", "max_results": 5},  # 只发送最相关的 5 个
    messages=messages
)
```

效果对比：
```
67K tokens (全部工具) → 5K tokens (Tool Search 检索后)
Token 节省: 92.5%
```

**方案 2：Programmatic Tool Calling（程序化工具调用）**

不依赖 LLM 自主选择工具，而是用程序逻辑（规则引擎或轻量分类器）先确定需要哪些工具，然后将工具定义注入上下文：

```python
class ProgrammaticToolSelector:
    """程序化工具选择：先确定工具，再调用 LLM"""
    
    def select_tools(self, user_input: str) -> list[str]:
        """用轻量规则/分类器确定需要的工具"""
        # 关键词匹配或使用 < 1K tokens 的小模型
        intent = self.lightweight_classifier(user_input)
        
        tool_mapping = {
            "customer_query": ["get_user", "get_orders", "search_tickets"],
            "code_review": ["get_pr", "get_diff", "get_checks"],
            "incident": ["get_alerts", "get_logs", "get_metrics"],
        }
        return tool_mapping.get(intent, ["fallback_tool"])
```

效果对比：
```
传统方式: LLM 从 82 个工具中选择 → 67K tokens 工具定义
Programmatic: 先分类再注入 → 平均 12K tokens 工具定义
Token 节省: ~82%

综合效果（Tool Search + Programmatic Calling）: ~37% 整体 Token 减少
```

**关键教训**：MCP 的普及使得"工具元数据膨胀"从一个边缘问题变为核心问题。2026 年，**任何集成了 5+ MCP Server 的 Agent 必须启用 Tool Search 或 Programmatic Tool Calling，否则 Token 账单会失控。**

## 三、检测方法

### 3.1 Token 消耗分解

在日志结构中增加 Token 消耗的细粒度拆分：

```python
class TokenBreakdown:
    """每次推理的 Token 消耗分解"""
    system_prompt: int     # 系统指令
    tool_definitions: int  # 工具定义
    tool_results: int      # 工具执行结果（按工具拆分）
    chat_history: int      # 对话历史
    retrieval_results: int # 检索结果
    user_input: int        # 用户输入
    output: int            # 模型输出
    
    @property
    def total(self) -> int:
        return (self.system_prompt + self.tool_definitions + 
                self.tool_results + self.chat_history +
                self.retrieval_results + self.user_input + self.output)
```

## 四、解决方案

### 4.1 工具懒加载（Lazy Tool Loading）

**核心思想**：不是所有工具都需要在每轮推理中可见。

```python
class LazyToolRegistry:
    """
    层级工具注册中心：根级只暴露少量分类，按需展开具体工具。
    与 9.2 节「工具注册中心」和 25.4 节「层级工具菜单」配合。
    """
    def __init__(self):
        self.categories = {
            "用户管理": {
                "description": "用户查询、创建、更新操作",
                "tools": ["get_user", "search_users", "update_profile", ...]
            },
            "订单处理": {
                "description": "订单查询、退款、物流跟踪",
                "tools": ["get_order", "refund_order", "track_delivery", ...]
            },
            "客服工单": {
                "description": "工单创建、分配、状态更新",
                "tools": ["create_ticket", "assign_ticket", ...]
            }
        }
    
    def get_relevant_tools(self, user_input: str) -> list[ToolDef]:
        """
        根据用户输入分类，只返回相关类别的工具。
        减少 60-80% 的工具元数据 token 消耗。
        """
        category = self._classify_intent(user_input)
        tool_names = self.categories[category]["tools"]
        return [self._get_tool_def(name) for name in tool_names]
    
    def _classify_intent(self, user_input: str) -> str:
        """用轻量分类器（如关键词匹配或小模型）判断意图"""
        keywords = {
            "用户管理": ["用户", "账户", "注册", "登录", "profile"],
            "订单处理": ["订单", "退款", "物流", "快递", "支付"],
            "客服工单": ["工单", "投诉", "反馈", "问题"]
        }
        for category, kws in keywords.items():
            if any(kw in user_input for kw in kws):
                return category
        return "通用"  # 无法分类时返回最小通用工具集
```

### 4.2 Micro 压缩：清除已使用的工具结果

**核心思想**：工具结果是"一次性的"，消费后即可丢弃。

```python
class MicroCompressor:
    """
    每轮清除已使用的工具结果。
    这是性价比最高的压缩策略：零 LLM 成本，减少 25-45% 的 token 消耗。
    
    详见 5.4 节「Micro 压缩」。
    """
    def compress(self, context: list[dict]) -> list[dict]:
        """
        清除已使用的工具结果，但保留其摘要（10% 的 token）。
        """
        compressed = []
        for msg in context:
            if msg["role"] == "tool":
                if self._was_already_used(msg):
                    # 替换为摘要版本
                    compressed.append(self._summarize_tool_result(msg))
                else:
                    compressed.append(msg)
            else:
                compressed.append(msg)
        return compressed
    
    def _summarize_tool_result(self, msg: dict) -> dict:
        """将工具结果压缩为摘要"""
        result = json.loads(msg["content"])
        return {
            "role": "tool",
            "content": json.dumps({
                "summary": "已处理，结果摘要: ...",
                "key_fields": self._extract_key_fields(result),
                "original_length": len(msg["content"])
            })
        }
```

### 4.3 Token Budget 强制执行

参考 5.2 节，为每一层设定硬性上限：

```python
class TokenBudget:
    """
    每层 Token 预算强制执行器。
    在每次推理前检查并裁剪超出预算的层。
    """
    BUDGETS = {
        "system_prompt": 2000,      # 系统指令上限
        "tool_definitions": 8000,    # 工具定义上限
        "tool_results": 10000,       # 工具结果上限
        "chat_history": 5000,        # 对话历史上限
        "retrieval_results": 4000,   # 检索结果上限
        "output": 2000,              # 输出上限
    }
    
    def enforce(self, context: Context) -> Context:
        for layer, budget in self.BUDGETS.items():
            actual = context.get_layer_tokens(layer)
            if actual > budget:
                context.crop_layer(layer, budget)
                logging.info(f"Layer {layer} cropped: {actual} → {budget} tokens")
        return context
```

### 4.4 输出 Capping

限制模型输出的最大长度，防止 Agent 生成过长的 CoT 推理：

```python
# OpenAI API
response = client.chat.completions.create(
    model="gpt-4",
    messages=messages,
    max_tokens=500,  # 限制输出长度
)

# Anthropic API
response = client.messages.create(
    model="claude-sonnet-4-20250514",
    max_tokens=500,
    messages=messages,
)
```

**输出 capping 能有效抑制 Token 消耗**——模型的输出 Token 虽然只占总量的 5-15%，但它会影响后续步骤的输入长度（因为输出被追加到历史中）。限制输出长度同时也能抑制 Agent "过度思考"的倾向。

## 五、预防措施

### 5.1 Token 预算审计（Pre-flight Check）

每次推理前做预算审计：

```
推理前检查：
1. 当前上下文中 system_prompt 是否超过预算？→ 是，裁剪
2. 当前上下文中 tool_definitions 是否超过预算？→ 是，启用懒加载
3. 当前上下文中 tool_results 是否超过预算？→ 是，启用 Micro 压缩
4. 输出 Token 是否设置了上限？→ 否，报错
```

### 5.2 工具 Schema 优化

减少工具元数据的 token 占用：

```python
# ❌ 过度描述
"description": "通过邮箱地址搜索客户信息。输入完整的邮箱地址，返回匹配的客户记录。如果找到多条记录，返回所有匹配项。"

# ✅ 精简描述  
"description": "按邮箱搜索客户"
```

**精简规则**：
1. Description 控制在 10-20 字以内
2. 参数描述控制在 10 字以内
3. 删除所有"如果/当/为了"等条件状语
4. 删除重复说明（类型和描述中已经包含的信息）

### 5.3 定期 Token 审计

每周自动生成 Token 消耗报告：

```
Token 消耗周报
========================
本周平均每步: 12,345 tokens
环比变化: +12%
最大消耗对话: conv_xyz (2.3M tokens)
 
Top 5 高消耗模式:
1. 多轮 RAG 查询 (avg 32K/步)
2. 工具结果未压缩 (avg 28K/步)
3. 全部工具暴露 (avg 18K/步)
4. 长 CoT 输出 (avg 8K/步)
5. 对话历史未摘要 (avg 6K/步)
```

## 关键教训速查

| 教训 | 说明 |
|------|------|
| Token 爆炸的元凶是工具元数据和结果累积 | 不是任务复杂度，而是工程结构导致的膨胀 |
| 工具 Schema 占 15-30% 的 Token | 懒加载可减少 60-80% |
| 工具结果占 25-45% 的 Token | Micro 压缩可减少 90% 的无用结果 |
| 输出 Capping 控制输出长度 | 防止 Agent 生成过长的 CoT 推理 |
| Token 预算审计应在每次推理前执行 | 防止超出窗口限制被隐式截断 |
| 定期 Token 审计发现退化趋势 | 效果缓慢下降通常源于 Token 预算失控 |
| MCP 工具元数据膨胀可达 67K+ tokens（7 个 Server） | Tool Search 或 Programmatic Calling 是 MCP 时代的必需品 |
