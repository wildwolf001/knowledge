# 24.1 测试通过、48h 后死循环 —— 可观测性黑洞

> 现象：Stage 环境完整测试通过，系统运行 48 小时后莫名其妙进入死循环，日志显示一切正常，trace 链路完整但无法定位根因，且无法在测试环境复现。

---

## 一、症状描述

### 1.1 典型场景

某金融客服 Agent 在 Stage 环境通过了全部 200 个回归测试案例，上线 48 小时后开始出现异常行为：

```
用户 23:14:22 → Agent: 查询账户余额
Agent 23:14:23 → Tool: get_account_balance(user_id="U12345")
Tool  23:14:24 → Agent: {balance: 12500.00, currency: "CNY"}
Agent 23:14:25 → Tool: get_account_balance(user_id="U12345")  ← 重复
Tool  23:14:26 → Agent: {balance: 12500.00, currency: "CNY"}
Agent 23:14:27 → Tool: get_account_balance(user_id="U12345")  ← 再次重复
...
（持续 37 次调用直到超时）
```

Agent 在获取余额后没有返回给用户，而是反复调用同一个工具。日志中没有报错，每个工具调用都返回了正常结果，Trace 链路显示每步的 latency 都在 200ms 以内。但 Agent 就是停不下来。

### 1.2 更隐蔽的变体

并非所有死循环都是简单的工具重复调用。更常见的隐蔽变体包括：

**变体 A —— 查询-写入振荡**：
```
Agent → search_ticket(query="订单异常")  →  结果为空
Agent → create_ticket(title="订单异常", ...)  →  ticket_id=456
Agent → search_ticket(query="订单异常")  →  返回刚创建的 ticket
Agent → 认为"找到了问题"，但检查后觉得"不对"，再次 search ...
```

Agent 不断重复"搜索 → 创建 → 搜索 → 发现已存在 → 不满意 → 再创建"的循环。

**变体 B —— 自我质疑循环**：
```
Agent: "我已获取了用户信息，但可能信息不完整，让我再查一次"
Agent: "这次的信息和上次一致，但可能有更新，让我再查一次确保准确"
Agent: "数据没有变化，但考虑到并发写入的可能，我需要再确认一次"
```

每次 Agent 都能为"为什么要再查一次"找到合理理由——而且这些理由从单个步骤看确实合理。

### 1.3 生产数据

根据 2024 年 Stanford 和 Berkeley 对 10 个生产级 Agent 系统的调研（"Agent Failure Modes in Production"），**约 23% 的生产事故与循环执行相关**，其中：

- 12% 是显式死循环（重复调用同一工具）
- 11% 是隐式循环（状态来回切换，不断跨越两个或多个状态）

这些事故的平均持续时间为 47 分钟，平均产生 3,782 次额外 API 调用，相当于额外消耗 150 万+ tokens 和 $30+ 的成本。

## 二、根因分析

### 2.1 核心根因：Agent 缺乏"尝试记忆"

死循环的根因本质上是 Agent **不记得自己已经做过什么**。标准 Agent 循环的结构是：

```
while True:
    thought = llm.think(context)     # 思考
    action = llm.decide_action(thought)  # 决策
    result = execute(action)          # 执行
    context.append(action, result)    # 记录
```

问题在于：**Agent 的"记忆"是追加到上下文窗口中的，但 Agent 并不具备对自身行为的元认知**。它能读到上下文中的历史记录，但无法有效判断"我是否已经尝试过这个方案"。

当上下文窗口长度超过一定阈值时，模型对早期内容的"注意力"急剧下降（详见 24.4 节）。Agent 在 500 步后"读不到"第 3 步已经做过的事情，于是自然地再次尝试同样的方案。

### 2.2 为什么测试环境无法复现

这是最令团队困惑的部分。原因有三：

**① 上下文窗口差异**：Stage 环境每个测试用例都是**独立对话**，上下文窗口从未累积到触发注意退化的长度。生产环境中连续运行 48 小时后，上下文已包含数百轮对话历史。

**② 状态累积差异**：测试用例的初始状态是确定的、干净的。生产环境中 Agent 经过数十次工具调用后，上下文中的"碎片化信息"（部分成功的操作、中间计算结果、截断的历史）累积到一定量后，模型在统计上更倾向于选择"看起来合理的"而非"正确的"下一步。

**③ 时间依赖**：某些 Agent 的行为依赖于系统时间（如"检查是否超时"），测试中 200 个用例在 5 分钟内跑完，不存在时间压力。生产环境中经过 48 小时，Agent 的内部状态可能包含"时间戳"类型的中间变量，这些变量在上下文截断后变得不完整。

### 2.3 可观测性黑洞

死循环是最典型的"可观测性黑洞"——从监控指标看一切正常：

```
监控面板显示：
- API成功率: 99.8%   ← 每个工具调用都成功了
- P99延迟: 350ms     ← 在正常范围内
- 错误率: 0.2%      ← 没有明显异常
- Token消耗: 平稳增长  ← 没有突变
```

为什么监控看不到异常？因为死循环中的每一步都是**合法**的——工具调用成功、返回值正常、延迟正常。没有"错误"可以报警。

只有在添加了"单次对话工具调用次数"和"重复调用检测"指标后，问题才暴露出来。

## 三、检测方法

### 3.1 循环检测指标

在生产监控中新增以下指标：

```python
# 指标 1：单次对话的工具调用次数分布
metric: agent_dialog_tool_call_count (histogram)
  告警规则：p99 > 20 次/对话  → Warning
            p99 > 50 次/对话  → Critical

# 指标 2：重复工具调用比例
metric: agent_repeated_tool_call_ratio (gauge)
  检测：连续 N 次调用同一工具且参数相似度 > 0.9
  告警规则：ratio > 0.3 → Warning

# 指标 3：工具调用结果的"变化率"
metric: agent_tool_result_entropy (gauge)
  计算：连续工具调用结果之间的编辑距离
  骤降 → 结果高度重复 → 大概率进入死循环
```

### 3.2 离线检测：Trace 分析

对已有 trace 数据做离线分析，检测循环模式：

```python
def detect_loop_pattern(trace_events: list[dict]) -> list[dict]:
    """
    检测 trace 中的循环模式。
    返回所有疑似循环的时间段。
    """
    loops = []
    window_size = 5  # 滑动窗口大小
    
    for i in range(len(trace_events) - window_size + 1):
        window = trace_events[i:i+window_size]
        tool_names = [e["tool_name"] for e in window]
        
        # 检测模式：A-A-A-A-A（同一工具重复）
        if len(set(tool_names)) == 1:
            loops.append({
                "start_time": window[0]["timestamp"],
                "end_time": window[-1]["timestamp"],
                "pattern": "SAME_TOOL_REPEAT",
                "tool": tool_names[0],
                "count": len(trace_events) - i  # 总重复次数
            })
            break
        
        # 检测模式：A-B-A-B-A（两个工具交替）
        if len(set(tool_names)) == 2 and tool_names[0] == tool_names[2] == tool_names[4]:
            loops.append({
                "start_time": window[0]["timestamp"],
                "end_time": window[-1]["timestamp"],
                "pattern": "TOGGLE",
                "tools": list(set(tool_names)),
            })
            break
    
    return loops
```

### 3.3 可观测性改进清单

要打破可观测性黑洞，需要采集以下"非标准"指标：

| 指标类别 | 具体指标 | 说明 |
|---------|---------|------|
| **步数指标** | 单对话工具调用次数 | 最简单的循环检测指标 |
| **重复指标** | 连续相同工具调用次数 | 检测显式死循环 |
| **熵指标** | 工具调用结果差异度 | 结果不变化 = 大概率循环 |
| **时间指标** | 单对话持续时间 | 超长对话通常是异常 |
| **路径指标** | 状态转移频率 | 状态频繁切换可能是隐式循环 |

## 四、解决方案

### 4.1 硬性上限：最大步数限制

最简单的第一道防线：

```python
class AgentLoop:
    def __init__(self, max_steps: int = 25):
        self.max_steps = max_steps
        self.step_count = 0
    
    def step(self, thought: str) -> ActionResult:
        self.step_count += 1
        
        if self.step_count > self.max_steps:
            # 触发降级：返回当前最佳结果，而非继续循环
            return ActionResult(
                status="DEGRADED",
                message=f"已达到最大步数限制({self.max_steps})，返回已收集的最佳结果",
                partial_result=self._get_best_result()
            )
        
        return self._execute_step(thought)
```

**重要**：超过阈值后不应报错（错误会被淹没在日志中），而是应该优雅降级。

### 4.2 显式"已尝试"跟踪

解决"Agent 不知道自己尝试过什么"的问题：

```python
class AttemptTracker:
    """
    跟踪 Agent 已经尝试过的操作，在上下文中显式注入。
    与 7.3 节「工作记忆」配合使用。
    """
    def __init__(self):
        self.attempts: list[dict] = []
    
    def record(self, tool_name: str, params: dict, result: Any):
        """记录一次尝试"""
        self.attempts.append({
            "tool": tool_name,
            "params_hash": self._hash_params(params),
            "result_hash": self._hash_result(result),
            "timestamp": time.time()
        })
    
    def is_already_tried(self, tool_name: str, params: dict) -> bool:
        """检查是否已经尝试过相同的操作"""
        params_hash = self._hash_params(params)
        for attempt in self.attempts:
            if attempt["tool"] == tool_name and \
               attempt["params_hash"] == params_hash:
                return True
        return False
    
    def to_context_prompt(self) -> str:
        """生成注入到 Agent 上下文的提示"""
        if not self.attempts:
            return ""
        
        summary = "【已尝试过的操作】\n"
        for i, att in enumerate(self.attempts[-10:], 1):  # 只保留最近10条
            summary += f"{i}. 工具: {att['tool']}, 参数: {att['params_hash'][:8]}...\n"
        summary += "\n⚠️ 不要重复以上操作。如果所有操作都已尝试过，请返回当前最佳结果。\n"
        return summary
    
    def _hash_params(self, params: dict) -> str:
        return hashlib.md5(json.dumps(params, sort_keys=True).encode()).hexdigest()
    
    def _hash_result(self, result: Any) -> str:
        return hashlib.md5(str(result).encode()).hexdigest()
```

关键设计决策：`to_context_prompt()` 的输出是**声明性**的（"这些已经做过了"），而不是**追加性**的（把完整历史堆进去）。这避免了为上下文增加过多 token。

### 4.3 多样性惩罚

当 Agent 选择与之前高度相似的操作时，在 logits 层面施加惩罚：

```python
class DiversityPenalty:
    """
    对已尝试过的操作施加 logit 偏置，降低其被选中的概率。
    这相当于在模型推理时动态调整工具选择概率。
    """
    def __init__(self, penalty: float = -1.5):
        self.penalty = penalty
        self.recent_actions: list[str] = []
    
    def apply(self, logits: dict[str, float], 
              available_tools: list[str]) -> dict[str, float]:
        """
        对已尝试过的工具名称施加 logit 惩罚。
        
        原理：在模型选择工具的 softmax 之前，
        降低已尝试工具的 logit 值，使其被选中的概率下降。
        """
        adjusted = logits.copy()
        for action in self.recent_actions[-5:]:
            if action in adjusted:
                adjusted[action] += self.penalty  # logit 空间中的惩罚
        return adjusted
    
    def record_action(self, tool_name: str):
        self.recent_actions.append(tool_name)
```

### 4.4 走神检测（Diverge Detection）

当检测到 Agent 开始"原地打转"时，触发救生筏策略：

```python
def diverge_detection(recent_steps: list[Step]) -> bool:
    """
    检测 Agent 是否进入走神/循环状态。
    综合使用三个信号：
    1. 工具重复率 > 阈值
    2. 结果相似度 > 阈值
    3. 思考模式的重复（如连续出现同样的关键词）
    """
    if len(recent_steps) < 6:
        return False
    
    # 信号 1：工具重复
    tools = [s.tool_name for s in recent_steps[-6:]]
    tool_repeat_ratio = max(tools.count(t) for t in set(tools)) / len(tools)
    
    # 信号 2：结果相似度
    results = [s.result for s in recent_steps[-6:]]
    result_similarities = [
            levenshtein_similarity(results[i], results[i+1])
            for i in range(len(results)-1)
    ]
    avg_similarity = sum(result_similarities) / len(result_similarities)
    
    # 信号 3：思考模式检测
    thoughts = [s.thought.lower() for s in recent_steps[-6:]]
    stuck_keywords = ["再确认", "再查一次", "确保", "maybe", "let me check again"]
    keyword_hits = sum(
        1 for t in thoughts if any(kw in t for kw in stuck_keywords)
    )
    
    # 综合判断
    score = (
        0.4 * (tool_repeat_ratio > 0.5) +
        0.3 * (avg_similarity > 0.85) +
        0.3 * (keyword_hits >= 3)
    )
    
    return score > 0.5
```

## 五、预防措施

### 5.1 架构级预防：无状态 Agent 设计

尽可能将 Agent 设计为无状态的——每个步骤的决策只依赖于当前上下文和最新工具结果，不依赖于隐含的内部状态。无状态 Agent 天然抗循环，因为"遗忘"不再是问题。

### 5.2 测试策略：长对话压力测试

在测试 pipeline 中加入：

- **长对话测试**：构造 50-100 轮的对话，验证 Agent 不会进入循环
- **重复输入测试**：连续输入相同的问题，验证 Agent 不会重复相同操作
- **空结果测试**：工具返回空结果时，验证 Agent 不会反复重试
- **超时恢复测试**：工具调用超时后，验证 Agent 会合理降级而非重试

### 5.3 监控告警配置

```yaml
# Prometheus 告警规则示例

```

### 5.4 救生筏（Lifeboat）模式

在生产系统中始终配置"救生筏"——当检测到循环时自动切换到一个**确定性路径**：

```python
class Lifeboat:
    """
    救生筏模式：当检测到 Agent 循环时，
    切换到预定义的确定性处理路径。
    """
    def activate(self, context: dict) -> Response:
        logging.warning(f"Lifeboat activated for dialog {context['dialog_id']}")
        
        # 收集当前已获得的最佳信息
        best_info = self._extract_best_info(context)
        
        # 使用确定性规则而非 LLM 来生成响应
        if "account_balance" in best_info:
            return Response(
                content=f"您的账户余额是 {best_info['balance']} 元。",
                metadata={"lifeboat": True, "reason": "loop_detected"}
            )
        else:
            return Response(
                content="抱歉，我目前无法完成您的请求，请稍后再试或联系人工客服。",
                metadata={"lifeboat": True, "reason": "loop_detected"}
            )
```

## 关键教训速查

| 教训 | 说明 |
|------|------|
| 死循环不会在标准指标中暴露 | 需要新增"步数""重复率""结果熵"等非标准指标 |
| 测试环境无法复现 | 上下文长度累积和时间因素导致测试覆盖不到 |
| 硬上限是第一道防线 | 最大步数限制是最简单的防循环手段 |
| "已尝试跟踪"解决元认知缺失 | 让 Agent 知道自己已经做过什么 |
| 救生筏是生产必备 | 检测到循环后自动切换到确定性路径 |
| 长对话压力测试不可少 | 常规测试覆盖不了 50+ 轮的长对话场景 |
