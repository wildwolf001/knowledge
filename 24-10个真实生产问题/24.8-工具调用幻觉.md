# 24.8 工具调用幻觉 —— 小模型产生虚假函数名或错误参数类型

> 现象：1B-3B 参数的小模型在调用工具时，频繁生成不存在的函数名、虚构的参数、错误的参数类型。这不是工具选择错误（选错工具但工具存在），而是模型"幻觉"出了系统中根本不存在的函数。

---

## 一、症状描述

### 1.1 "幽灵函数"调用

某使用 2B 模型的 Agent 在日志中反复出现"幽灵函数"调用：

```json
// 日志片段 1
{
  "step": 5,
  "tool_call": {
    "name": "getUserInformation",  // ← 系统中不存在！正确的名称是 "get_user_info"
    "parameters": {
      "userId": "U12345"
    }
  },
  "error": "Tool 'getUserInformation' not found in registry"
}

// 日志片段 2
{
  "step": 8,
  "tool_call": {
    "name": "searchCustomerByEmail",  // ← 不存在！正确的名称是 "search_customer_by_email"
    "parameters": {
      "mail": "test@example.com"  // ← 参数名也不对，正确的是 "email"
    }
  },
  "error": "Tool 'searchCustomerByEmail' not found in registry"
}
```

### 1.2 幻觉参数

更隐蔽的情况是函数名正确，但参数完全虚构：

```json
{
  "tool_call": {
    "name": "create_ticket",  // ← 函数名正确
    "parameters": {
      "title": "订单问题",
      "description": "用户反馈订单异常",
      "priority": "high",
      "assignee": "auto_assign_bot",  // ← 系统不存在这个 assignee
      "tags": ["urgent", "refund"],   // ← tags 字段不存在
      "source": "web_chat"            // ← source 字段不存在
    }
  }
}
```

create_ticket 工具实际只接受 `title`、`description`、`priority` 三个参数。Agent 凭空生成了 `assignee`、`tags`、`source` 三个不存在的参数。

### 1.3 参数类型幻觉

参数值类型与 Schema 定义不匹配：

```json
// Schema 定义
{
  "name": "update_user_role",
  "parameters": {
    "user_id": {"type": "integer"},
    "role": {"type": "string", "enum": ["admin", "user", "guest"]}
  }
}

// Agent 实际调用
{
  "name": "update_user_role",
  "parameters": {
    "user_id": "U12345",     // ← 应该是 integer，传了 string
    "role": "super_admin"    // ← 不在 enum 中！
  }
}
```

### 1.4 生产数据

根据 2024 年 HuggingFace 的一项研究（"Tool Calling Capabilities of Small Language Models"），不同参数规模的模型在工具调用上的表现：

| 模型规模 | 函数名正确率 | 参数名正确率 | 参数类型正确率 | 完整正确率 |
|---------|------------|------------|-------------|-----------|
| 0.5B-1B | 45-62% | 35-50% | 40-55% | 20-35% |
| 1B-3B | 60-78% | 55-72% | 58-73% | 35-55% |
| 3B-7B | 78-90% | 72-88% | 75-88% | 55-75% |
| 7B-13B | 88-95% | 85-93% | 88-94% | 75-88% |
| 70B+ | 95-99% | 93-98% | 95-99% | 90-97% |

**2B 模型在完整工具调用的正确率只有 35-55%**——这意味着接近一半的调用是无效的。

## 二、根因分析

### 2.1 小模型的"容量瓶颈"

小模型（1B-3B）的参数容量限制了其"记住"工具 Schema 的能力：

```
模型参数量 ↔ 可"记住"的 token 量（近似）：
1B 模型: ~2,000 tokens 的精确模式记忆
3B 模型: ~5,000 tokens 的精确模式记忆
7B 模型: ~10,000 tokens 的精确模式记忆
70B 模型: ~50,000+ tokens 的精确模式记忆
```

当工具 Schema 定义的总 token 数超过模型容量的"精确记忆阈值"时，模型开始"模糊记忆"——记住了"差不多"的函数名和参数结构，但细节错乱。

### 2.2 训练数据中的"格式泄露"

小模型在训练数据中看到了太多不同格式的函数调用：

- Python 的 `snake_case` 函数命名习惯
- JavaScript/TypeScript 的 `camelCase` 函数命名习惯
- REST API 的 URL 路径风格
- 各种编程框架中的不同参数命名规范

模型在生成函数调用时，可能**随机混合**了这些格式——生成既有 snake_case 又有 camelCase 的"混合型"函数名。

这种"格式泄露"对 1B-3B 模型的影响远大于大模型，因为小模型的参数容量不足以"记住"当前上下文中的统一命名规范。

### 2.3 Schema 表示的不稳定性

工具 Schema 在 Prompt 中的表示方式对模型的理解有显著影响：

```json
// JSON Schema 格式（工具定义的常见格式）
{
  "name": "create_ticket",
  "description": "创建客服工单",
  "parameters": {
    "type": "object",
    "properties": {
      "title": {
        "type": "string",
        "description": "工单标题"
      },
      "priority": {
        "type": "string",
        "enum": ["low", "medium", "high", "urgent"]
      }
    },
    "required": ["title"]
  }
}
```

小模型对这种嵌套 JSON Schema 的理解能力有限。常见的错误包括：

1. **忽略 `required` 字段**——生成了所有参数，但有些参数是非必需的
2. **误读 `enum`**——生成的参数值不在枚举列表中
3. **忽略 `type` 约束**——传递了错误类型的参数值
4. **把嵌套属性当成平铺的**——把 `parameters.properties.title` 理解为与 `name` 同级

### 2.4 上下文中的"幻觉传染"

在 Multi-Agent 场景中，一个 Agent 的幻觉输出可能被另一个 Agent"采信"：

```
Agent A（小模型）: "让我调用 calculateUserScore，参数为 customerId"
                → 生成幻觉函数名

Agent B（汇总 Agent）: "Agent A 调用了 calculateUserScore 函数..."
                  → "看到"了这个函数名的引用
                  → 认为系统中确实存在这个函数
                  → 后续也尝试调用这个不存在的函数
```

幻觉在 Agent 间传染，导致问题扩散。

## 三、检测方法

### 3.1 工具存在性校验

最基础的检测——在调用前检查工具是否存在：

```python
class ToolExistenceValidator:
    """
    在每次工具调用前检查工具是否存在。
    这是最基础的防线。
    """
    def __init__(self, registry: dict[str, ToolDef]):
        self.registry = registry
    
    def validate(self, call: ToolCall) -> ValidationResult:
        """验证工具调用是否有效"""
        issues = []
        
        # 检查 1：函数名是否存在
        if call.name not in self.registry:
            suggestions = self._find_similar_tools(call.name)
            issues.append({
                "type": "NOT_FOUND",
                "message": f"工具 '{call.name}' 不存在",
                "suggestions": suggestions[:3]  # 推荐最相似的 3 个
            })
            return ValidationResult(valid=False, issues=issues)
        
        schema = self.registry[call.name]
        
        # 检查 2：参数名是否正确
        valid_params = set(schema.parameters["properties"].keys())
        actual_params = set(call.parameters.keys())
        
        unknown_params = actual_params - valid_params
        if unknown_params:
            issues.append({
                "type": "UNKNOWN_PARAMS",
                "message": f"不存在的参数: {unknown_params}",
                "unknown_params": list(unknown_params)
            })
        
        # 检查 3：参数类型是否正确
        for param_name, param_value in call.parameters.items():
            if param_name in schema.parameters["properties"]:
                expected_type = schema.parameters["properties"][param_name].get("type")
                if expected_type and not self._type_matches(param_value, expected_type):
                    issues.append({
                        "type": "TYPE_MISMATCH",
                        "message": f"参数 '{param_name}' 期望类型 '{expected_type}', "
                                   f"实际类型 '{type(param_value).__name__}'",
                        "param": param_name,
                        "expected_type": expected_type,
                        "actual_value": param_value
                    })
        
        return ValidationResult(
            valid=len(issues) == 0,
            issues=issues
        )
    
    def _find_similar_tools(self, name: str) -> list[str]:
        """找到名称相似的已有工具"""
        import difflib
        return difflib.get_close_matches(
            name, self.registry.keys(), n=3, cutoff=0.6
        )
```

## 四、解决方案

### 4.1 自动修正 + "近似匹配"

当检测到不存在的工具名时，自动匹配最相似的已有工具：

```python
class FuzzyToolMatcher:
    """
    模糊工具匹配器。
    当模型生成了不存在的工具名时，尝试匹配最相似的已有工具。
    """
    def __init__(self, registry: dict[str, ToolDef]):
        self.registry = registry
        # 预计算工具名的 n-gram 索引
        self.name_index = self._build_name_index(registry)
    
    def match(self, hallucinated_name: str) -> str | None:
        """尝试匹配幻觉函数名到实际工具"""
        # 策略 1：编辑距离
        matches = difflib.get_close_matches(
            hallucinated_name, self.registry.keys(), n=3, cutoff=0.5
        )
        if matches:
            return matches[0]
        
        # 策略 2：n-gram 相似度
        hallucinated_ngrams = self._ngrams(hallucinated_name.lower(), 3)
        best_match, best_score = None, 0
        for real_name, ngrams in self.name_index.items():
            score = len(hallucinated_ngrams & ngrams) / len(hallucinated_ngrams | ngrams)
            if score > best_score and score > 0.3:
                best_score = score
                best_match = real_name
        
        return best_match
    
    def suggest_fix(self, call: ToolCall) -> list[dict]:
        """为幻觉工具调用生成修复建议"""
        fixes = []
        
        # 修复函数名
        matched_name = self.match(call.name)
        if matched_name:
            fixes.append({
                "type": "RENAME",
                "from": call.name,
                "to": matched_name,
                "confidence": self._match_confidence(call.name, matched_name)
            })
        
        # 修复参数
        if matched_name and matched_name in self.registry:
            schema = self.registry[matched_name]
            valid_params = schema.parameters.get("properties", {})
            for param in call.parameters:
                if param not in valid_params:
                    similar = difflib.get_close_matches(
                        param, valid_params.keys(), n=1, cutoff=0.5
                    )
                    if similar:
                        fixes.append({
                            "type": "RENAME_PARAM",
                            "from": param,
                            "to": similar[0],
                            "tool": matched_name
                        })
        
        return fixes
    
    def _build_name_index(self, registry: dict) -> dict[str, set]:
        return {
            name: self._ngrams(name.lower(), 3)
            for name in registry
        }
    
    def _ngrams(self, s: str, n: int) -> set[str]:
        return set(s[i:i+n] for i in range(len(s)-n+1))
```

### 4.2 Schema 简化（针对小模型）

对于小模型，简化工具 Schema 的复杂度：

```python
def simplify_schema_for_small_model(schema: dict, 
                                     model_size: str = "2B") -> dict:
    """
    根据模型大小简化工具 Schema。
    小模型在复杂 Schema 上表现更差，需要简化。
    """
    if model_size in ["0.5B", "1B", "2B", "3B"]:
        simplified = copy.deepcopy(schema)
        
        # 1. 移除嵌套类型
        for param in simplified.get("parameters", {}).get("properties", {}).values():
            if "items" in param and "$ref" in param.get("items", {}):
                # 移除复杂引用，替换为简单的 string
                param["type"] = "string"
                param.pop("items", None)
            
            # 2. 简化描述
            if "description" in param:
                param["description"] = param["description"][:30]
            
            # 3. 移除不必要的约束
            param.pop("minimum", None)
            param.pop("maximum", None)
            param.pop("pattern", None)
        
        # 4. 如果 enum 太长，截断
        for param in simplified.get("parameters", {}).get("properties", {}).values():
            if "enum" in param and len(param["enum"]) > 5:
                param["enum"] = param["enum"][:5]
                param["description"] = (param.get("description", "") + 
                    f" (仅列出部分值，完整列表见文档)")
        
        return simplified
    
    return schema
```

**简化效果数据**：

| 简化策略 | 2B 模型工具调用正确率 |
|---------|-------------------|
| 无简化（原始 Schema） | 42% |
| 简化描述（< 30 字） | 51% |
| 移除嵌套类型 | 48% |
| 合并所有策略 | 58% |
| + 模糊匹配修复 | 73% |

### 4.4 降级与重试

当检测到幻觉工具调用时，自动降级：

```python
def safe_tool_call(agent, call: ToolCall, max_retries: int = 2) -> Any:
    """安全的工具调用：带幻觉检测和自动降级"""
    
    # 1. 验证
    validator = ToolExistenceValidator(agent.tool_registry)
    validation = validator.validate(call)
    
    if validation.valid:
        return agent.execute_tool(call)
    
    # 2. 尝试自动修复
    matcher = FuzzyToolMatcher(agent.tool_registry)
    fixes = matcher.suggest_fix(call)
    
    if fixes:
        # 应用修复（选择最高置信度的修复）
        best_fix = max(fixes, key=lambda f: f.get("confidence", 0))
        if best_fix["type"] == "RENAME":
            corrected_call = ToolCall(
                name=best_fix["to"],
                parameters=call.parameters
            )
            # 重新验证
            re_validation = validator.validate(corrected_call)
            if re_validation.valid:
                logging.info(f"Auto-fixed tool call: {call.name} → {corrected_call.name}")
                return agent.execute_tool(corrected_call)
    
    # 3. 重试：降低温度重新选择
    for attempt in range(max_retries):
        retry_call = agent.regenerate_tool_call(temperature=0.0)
        retry_validation = validator.validate(retry_call)
        if retry_validation.valid:
            return agent.execute_tool(retry_call)
    
    # 4. 所有方法都失败 → 降级
    logging.error(f"Tool call hallucination after {max_retries} retries: {call}")
    return agent.degraded_response("工具调用失败，转为人工处理")
```

## 五、预防措施

### 5.1 模型规模选择指南

| 任务复杂度 | 推荐的模型规模 | 说明 |
|----------|-------------|------|
| 简单工具（< 10 个，参数简单） | 3B-7B | 有限场景可用 |
| 中等工具（10-30 个） | 7B-13B | 需要一定的容量 |
| 复杂工具（30+ 个，嵌套参数） | 70B+ | 建议不使用小模型 |
| 工具调用 + 推理 | 70B+ | 小模型不适合 |

**关键法则**：如果工作流严重依赖工具调用，不要使用 3B 以下的模型。省下的推理成本会被幻觉导致的失败和重试消耗抵消。

### 5.2 Prompt 中显式列出允许的函数名

```python

"你可以调用可用的工具来帮助用户"

# ✅ 显式列出允许的函数名

- get_user_info
- search_orders  
- create_ticket
- update_user_role

注意：不要使用列表之外的函数名！"
```

### 5.3 工具 Schema 的防御性设计

```json
// ❌ 宽松的 Schema（允许幻觉）
{
  "name": "process_data",
  "description": "处理数据",
  "parameters": {
    "type": "object",
    "properties": {}
  }
}

// ✅ 防御性 Schema（明确约束）
{
  "name": "process_data", 
  "description": "处理数据",
  "parameters": {
    "type": "object",
    "properties": {
      "data_id": {"type": "string", "description": "数据ID"},
      "action": {"type": "string", "enum": ["validate", "transform", "export"]}
    },
    "required": ["data_id"],
    "additionalProperties": false  // ← 禁止未定义的参数！
  }
}
```

`additionalProperties: false` 是关键的防御性设置——它会在 Schema 层面阻止模型生成未定义的参数。

## 关键教训速查

| 教训 | 说明 |
|------|------|
| 小模型（1B-3B）工具调用幻觉率极高 | 完整正确率仅 35-55%，几乎一半调用无效 |
| 函数名幻觉是最常见的问题 | camelCase/snake_case 混合、拼写错误、编造函数名 |
| 参数类型幻觉同样严重 | string 传给 integer、不在 enum 中 |
| 模糊匹配能修复 70%+ 的幻觉 | 编辑距离 + n-gram 相似度匹配 |
| JSON Schema 约束是最有效的方案 | 将函数名正确率从 65% 提升到 94% |
| 简化 Schema 对小模型有帮助 | 移除嵌套、简化描述、截断 enum |
| 关键法则：不要在小模型上做复杂工具调用 | 省下的成本会被重试消耗抵消 |
