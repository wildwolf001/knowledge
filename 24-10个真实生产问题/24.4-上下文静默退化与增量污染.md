# 24.4 上下文静默退化与增量污染

> 现象：上下文长度增长到 100K tokens 时，模型输出质量暴跌 50%+（2025 年论文验证）。不报错、没有告警，输出看起来仍然流畅，但事实准确度显著下降。旧上下文被截断后，后续决策基于不完整信息。

---

## 一、症状描述

### 1.1 "看起来正常"的退化

最可怕的是：**上下文退化没有显式信号**。

某客服 Agent 在运行 3 小时后开始出现事实错误：

```
对话前 30 分钟（上下文 5K tokens）：
Agent: "用户的订单 ORD-2025-001 已经发货，物流单号 SF1234567890"
→ 正确 ✅

对话 3 小时后（上下文 85K tokens）：
Agent: "用户的订单 ORD-2025-001 仍在处理中"
→ 错误 ❌（前面已经说过已发货，但 Agent 没有读取到）
```

日志显示：Agent 在 85K tokens 的上下文中，成功"看到"了系统指令和最近 3 轮对话，但**"丢失"了中间的关键信息**——订单状态的更新发生在 2.5 小时前的对话中，埋没在 50K tokens 深处。

### 1.2 退化模式

2025 年 Liu 等人发表在 ACL 上的论文 "Lost in the Middle: How Language Models Use Long Contexts" 进行了系统性研究。关键发现：

```
在 100K tokens 上下文中，模型在不同位置的信息召回率：

上下文位置         信息召回率
─────────────────────────────────────
开头 (0-10%)      ~85%    ← 系统指令和高频工具 Schema 在此
前 30%            ~75%
中间 (30-70%)     ~38%    ← ！！！严重退化！！！
后 30%            ~65%
末尾 (90-100%)    ~55%
```

**中间位置的召回率不到 40%**——这意味着上下文中段的大量信息对模型来说几乎是"不可见的"。

### 1.3 增量污染

增量污染是静默退化的"并发症"：Agent 的后续决策基于前一步的输出，但前一步的输出可能已经受到了退化上下文的误导：

```
步骤 10: Agent 读取到部分信息，做出决策 A
步骤 11: Agent 将决策 A 作为"已知信息"继续推理
步骤 12: Agent 基于"决策 A 是正确的"这个假设（但 A 是基于不完整信息）
步骤 13: Agent 叠加更多污染
...
```

每一步的"污染"被增量地传递到下一步，但没有任何一步会报错。最终的结果可能完全偏离事实——但追溯起来极其困难。

### 1.4 生产数据

根据 2025-2026 年的多项大规模研究（包括 Google Cloud Next 2026 公布的企业级数据）：

| 上下文长度 | 相对性能（= 1.0 为基线） | 事实错误率 |
|-----------|----------------------|-----------|
| < 4K tokens | 1.0 (基线) | 3% |
| 4K-16K | 0.92 | 5% |
| 16K-32K | 0.81 | 9% |
| 32K-64K | 0.68 | 15% |
| 64K-128K | 0.52 | 24% |
| > 128K | 0.41 | 33% |

在 64K-128K 范围内，模型性能约为基线的 50%，事实错误率达到 24%。值得警醒的是：**很少有团队针对这种退化设置监控告警**。

**Google Cloud Next 2026 关键数据**：

```
78% 的企业 AI 生产故障源于上下文管理不足
  ├── 其中 43% 是"中间塌陷"导致信息丢失
  ├── 22% 是截断策略不当导致关键上下文被丢弃
  └── 13% 是增量污染累积导致事实漂移

1M Token 上下文窗口的真相（2026 年行业共识）：
  标称窗口: 1,000,000 tokens（广告宣传）
  有效窗口（性能 > 90%）: ~35,000 tokens（实测）
  有效窗口（性能 > 80%）: ~80,000 tokens（实测）
  
  差距: 广告 vs 实际的差距高达 28 倍
```

**关键结论**：2026 年，模型厂商竞相宣传更大的上下文窗口（1M/2M/10M），但"有效窗口"和"标称窗口"之间的鸿沟不仅没有缩小，反而因为模型试图处理更长上下文而出现了新的退化模式。

## 二、根因分析

### 2.1 注意力机制的"中间塌陷"

Transformer 的注意力机制存在固有的位置偏差：

```
Attention Score Distribution in Long Context:

位置 0 (开头):  high attention  ← "primacy bias"
位置 1-10%:     moderate attention
位置 10-80%:    low attention    ← "middle collapse"
位置 80-100%:   moderate-high attention  ← "recency bias"
```

这种现象的原因：
1. **初始 token 的强锚定**：开头 token 的 key-value 在注意力计算中获得了不成比例的权重
2. **注意力稀疏性**：长序列中，模型学会了忽略"大部分中间内容"以维持计算效率
3. **位置编码衰减**：RoPE 等位置编码在长程依赖上存在信息衰减

### 2.2 上下文窗口的"软上限"

模型虽然有 200K 或 1M 的"硬"上下文窗口，但"有效"上下文窗口远小于标称值：

```
模型（2024-2025）    标称窗口    有效窗口（性能>90%）   有效窗口（性能>80%）
──────────────────────────────────────────────────────
GPT-4                128K       ~20K                  ~45K
Claude 3             200K       ~30K                  ~60K
Gemini 1.5           1M         ~50K                  ~120K

模型（2026 更新）    标称窗口    有效窗口（性能>90%）   有效窗口（性能>80%）
──────────────────────────────────────────────────────
GPT-5                2M         ~45K                  ~95K
Claude 4             1M         ~55K                  ~110K
Gemini 2.0           2M         ~65K                  ~140K
```

**关键趋势（2026）**：
1. 模型进步使有效窗口提升了约 20-30%，但远落后于标称窗口的增长速度
2. Gemini 2.0 的有效窗口表现最好（得益于更优的注意力机制），但 65K @ 90% 性能 vs 2M 标称窗口的差距仍然触目惊心
3. **广告中的"1M 上下文"和实际可用能力之间仍然存在 20-30 倍的差距**

**"支持 200K 上下文"和"200K 上下文中效果好"是两回事**——2026 年这句话仍然成立，并且随着标称窗口的疯狂增长，这句话变得更加重要。

### 2.3 截断策略不当

大多数 Agent 框架在处理超长上下文时使用"从中间截断"的策略：

```
# 简单截断（如 LangChain 的默认行为）：
truncated_context = context[:max_tokens]  # 保留开头，丢弃末尾

# 导致的问题：
1. 最近的工具执行结果被丢弃（在末尾）
2. Agent 正在执行的当前步骤的上下文丢失
3. 但旧的、已无用的信息被保留（在开头）
```

这种截断策略加剧了"增量污染"问题——Agent 基于被截断的历史做出决策，而这些决策被追加到上下文中，形成新的"事实污染"。

## 三、检测方法

### 3.1 分位召回率测试

在不同上下文位置注入测试信息，检测模型在各位置的召回率：

```python
def test_positional_recall(model, context_lengths: list[int]):
    """
    在不同上下文长度和位置测试信息召回率。
    
    方法：在上下文的特定位置插入一条"事实"（如"密码是 'hello123'")，
    然后问模型"密码是什么"，检查是否能正确回答。
    """
    results = []
    for length in context_lengths:
        for position_pct in [5, 15, 30, 50, 70, 85, 95]:
            fact = f"密码是 'fact_at_{position_pct}pct'"
            context = build_test_context(length, position_pct, fact)
            
            response = model.generate(context + "\n\n密码是什么？")
            correct = "fact_at_" in response
            
            results.append({
                "context_length": length,
                "position_pct": position_pct,
                "correct": correct
            })
    
    return results
```

将此测试加入每周回归测试。

### 3.2 上下文质量指标

在生产中持续追踪上下文质量：

```yaml
指标: context_positional_recall (gauge)
  标签: [position_range: "0-10%" / "10-30%" / "30-70%" / "70-90%" / "90-100%"]
  来源: 随机注入的探针事实（probe facts）
  告警: 任意分位召回率 < 50% → critical

指标: context_effective_length (gauge)
  定义: 模型性能保持在基线 80% 以上的最大上下文长度
  趋势: 随模型版本更新自动追踪
```

### 3.3 事实一致性检测

在 Agent 的整个对话过程中随机插入事实一致性检查：

```python
class FactConsistencyChecker:
    """
    在 Agent 对话中随机插入"探针"问题，
    检测 Agent 是否能一致地引用之前的信息。
    """
    def __init__(self, probe_interval: int = 10):
        self.probe_interval = probe_interval
        self.facts: list[dict] = []
    
    def inject_fact(self, fact: str, step: int):
        """注入已知事实（由测试框架调用）"""
        self.facts.append({"fact": fact, "step": step})
    
    def check_consistency(self, step: int, context: str) -> float:
        """在上下文中插入一致性检查"""
        if step % self.probe_interval != 0:
            return 1.0
        
        # 选择一个早期注入的事实来查询
        old_fact = next(
            (f for f in self.facts if f["step"] < step - self.probe_interval),
            None
        )
        if not old_fact:
            return 1.0
        
        # 查询该事实
        probe_prompt = f"{context}\n\n之前提到的：{old_fact['fact']}"
        response = model.generate(probe_prompt)
        
        # 检查是否一致（语义相似度）
        consistency = semantic_similarity(old_fact["fact"], response)
        
        if consistency < 0.6:
            logging.warning(
                f"Context degradation detected at step {step}: "
                f"consistency={consistency:.3f}"
            )
        
        return consistency
```

## 四、解决方案

### 4.1 结构化上下文布局

**核心思想**：将上下文分区，并确保关键信息始终放在"注意力黄金区"（开头 10%）：

```python
class StructuredContext:
    """
    结构化上下文：将上下文分区并优化信息放置位置。
    """
    SECTIONS = {
        "system": "critical",        # 开头 → 高注意力区域
        "user_request": "critical",  # 开头 → 高注意力区域
        "tool_definitions": "high",  # 紧随其后
        "action_history": "sliding", # 滑动窗口，只保留最近 N 条
        "intermediate_results": "compressed",  # 需要压缩
        "retrieved_docs": "pruned",  # 需要修剪
    }
    
    def build(self, state: AgentState) -> str:
        # Section 1: 关键信息（始终在开头）
        sections = [
            self._format_system_prompt(state),
            self._format_user_request(state),
        ]
        
        # Section 2: 工具定义（懒加载版本）
        sections.append(self._format_tool_definitions(state))
        
        # Section 3: 行动历史（滑动窗口，最近 N 条）
        sections.append(self._format_action_history(state, window=20))
        
        # Section 4: 已压缩的中间结果
        sections.append(self._format_compressed_results(state))
        
        return "\n\n".join(sections)
```

### 4.2 定期上下文刷新（Context Refresh）

在 Agent 运行过程中，定期重新构建上下文——将关键信息提取到开头：

```python
class ContextRefresher:
    """
    上下文刷新：定期提取关键信息并重建上下文。
    防止信息被"埋葬"在长上下文的中间区域。
    """
    def __init__(self, refresh_interval: int = 15):
        self.refresh_interval = refresh_interval
    
    def refresh(self, state: AgentState) -> AgentState:
        """在指定步数后刷新上下文"""
        if state.step_count % self.refresh_interval != 0:
            return state
        
        # 1. 从当前状态中提取"仍然关键"的信息
        critical_facts = self._extract_critical_facts(state)
        
        # 2. 重建上下文
        new_context = ContextBuilder() \
            .add_system_prompt(state.system_prompt) \
            .add_critical_facts(critical_facts) \
            .add_recent_history(state.recent_steps[-5:]) \
            .add_current_request(state.user_request) \
            .build()
        
        # 3. 替换状态中的上下文
        state.context = new_context
        state.last_refresh_step = state.step_count
        
        logging.info(f"Context refreshed at step {state.step_count}: "
                     f"{len(state.old_context)} → {len(new_context)} tokens")
        
        return state
    
    def _extract_critical_facts(self, state: AgentState) -> list[str]:
        """从对话中提取仍然关键的事实"""
        critical = []
        # 提取原则：
        # - 用户提供的明确信息（姓名、订单号、金额）
        # - Agent 已经验证过的事实（如"用户余额为 10000 元"）
        # - 涉及不可逆操作的状态（如"退款已发起"）
        for step in state.recent_steps:
            if step.contains_confirmed_fact:
                critical.append(step.critical_fact)
        return critical[-10:]  # 最多保留 10 条
```

### 4.3 智能截断：策略性信息保留

替代"截断中间"的简单策略：

```python
def intelligent_truncation(context: str, max_tokens: int) -> str:
    """
    智能截断策略，在达到 Token 上限时，
    优先保留：
    1. 系统指令（优先级：最高）
    2. 当前用户请求（优先级：最高）
    3. 最近的 N 轮对话（优先级：高）
    4. 已确认的事实摘要（优先级：中）
    5. 工具定义（优先级：低 → 使用懒加载版本）
    6. 原始检索结果（优先级：最低 → 可丢弃）
    """
    sections = parse_context_sections(context)
    
    # 操作系统指令和用户请求（必须保留）
    essential = sections["system"] + sections["user_request"]
    remaining_budget = max_tokens - len(essential)
    
    if remaining_budget <= 0:
        raise ValueError("Essential sections exceed token budget")
    
    # 按优先级选择保留的内容
    result = [essential]
    
    for section_name, priority in PRIORITY_ORDER:
        if remaining_budget <= 0:
            break
        section_content = sections[section_name]
        if len(section_content) <= remaining_budget:
            result.append(section_content)
            remaining_budget -= len(section_content)
        else:
            # 对长内容做摘要而不是截断
            summarized = summarize(section_content, remaining_budget)
            result.append(summarized)
            remaining_budget = 0
    
    return "\n\n".join(result)
```

### 4.4 上下文退化告警

当检测到上下文质量下降时主动告警，而不是等到产生错误结果：

```python
class ContextDegradationMonitor:
    """
    上下文退化监控器
    在 Agent 运行过程中持续评估上下文质量
    """
    def __init__(self):
        self.window = deque(maxlen=20)
        self.degradation_threshold = 0.15
    
    def evaluate(self, current_step: dict) -> dict:
        """评估当前步的上下文质量"""
        metrics = {
            "context_length": current_step["total_tokens"],
            "middle_ratio": current_step["middle_section_ratio"],
            "truncation_occurred": current_step.get("was_truncated", False),
            "fact_consistency": current_step.get("consistency_score", 1.0),
        }
        
        self.window.append(metrics)
        
        # 趋势检测
        if len(self.window) >= 10:
            recent = list(self.window)[-5:]
            older = list(self.window)[:5]
            
            avg_recent_consistency = np.mean([m["fact_consistency"] for m in recent])
            avg_older_consistency = np.mean([m["fact_consistency"] for m in older])
            
            degradation = avg_older_consistency - avg_recent_consistency
            
            if degradation > self.degradation_threshold:
                return {
                    "status": "DEGRADING",
                    "degradation": degradation,
                    "suggested_action": "TRIGGER_CONTEXT_REFRESH"
                }
        
        return {"status": "HEALTHY", "degradation": 0}
```

## 五、预防措施

### 5.1 上下文预算管理

结合 Ch05.2 的 Token Budget 策略，设定上下文的有效长度上限：

```yaml
上下文管理规则:
  # 硬上限（框架层面强制）
  max_context_tokens: 32000
  
  # 软上限（超过时触发告警但继续运行）
  warn_context_tokens: 24000
  
  # 刷新触发条件
  refresh_at_steps: 15
  refresh_at_tokens: 20000
  
  # 截断策略
  truncation: "intelligent"  # 而非 "simple_middle_cut"
```

### 5.2 定期上下文质量基准测试

每周运行上下文质量基准测试：

```
测试场景：
1. 100 条事实分布在 50K 上下文中
2. 每条事实在 10 步后查询
3. 统计各位置召回率

通过标准：
- 整体召回率 > 80%
- 中间段（30-70%）召回率 > 60%
- 新模型版本必须不低于旧版本
```

### 5.3 设计"上下文独立性"的 Agent 架构

在架构层面减少对长上下文的依赖：

```
❌ 依赖长上下文的架构:
  所有历史 → Agent 决策 → 新结果 → 追加到历史 → ...

✅ 上下文独立的架构:
  当前状态摘要 + 最近 N 步 → Agent 决策 → 新结果 → 更新状态摘要
```

状态摘要机制（详见第 7 章「记忆系统设计」）可以将对长上下文的依赖降低 80% 以上。

## 关键教训速查

| 教训 | 说明 |
|------|------|
| 中间塌陷是注意力机制的天性 | 上下文中段（30-70%）的召回率可能低于 40% |
| 标称窗口和有效窗口是两回事 | 200K 标称窗口的有效性能窗口可能只有 30K；1M 标称窗口的有效窗口约 35K（2026 年数据） |
| 78% 企业 AI 故障源于上下文管理不足 | Google Cloud Next 2026 报告核心发现 |
| 退化没有显式信号 | 需要主动注入探针来检测上下文质量 |
| 定期上下文刷新是有效手段 | 每隔 N 步重建上下文，把关键信息移到开头 |
| 智能截断优于简单截断 | 按信息优先级保留，而非从中间一刀切 |
| 上下文独立性架构是终极方案 | 减少对长上下文的依赖比优化长上下文更可靠 |
