# 24.7 非确定性输出 —— 相同输入不同结果

> 现象：相同的用户输入、相同的系统配置，Agent 每次返回不同的结果。原因包括检索顺序波动、模型温度设置、工具输出的格式变化——这些问题单独看起来轻微，但组合在一起导致 Agent 行为不可预测。

---

## 一、症状描述

### 1.1 最典型的场景：测试不稳定

QA 团队报告 CI Pipeline 中 30% 的测试"偶发失败"：

```
测试用例 #47: "查询用户订单状态"
运行 1: Agent 调用 get_orders → 返回 3 条订单 → 正确 ✅
运行 2: Agent 调用 search_orders → 返回 2 条订单（API 分页不同）→ "失败" ❌
运行 3: Agent 调用 get_orders → 返回 3 条订单 → 正确 ✅
运行 4: Agent 调用 get_recent_orders → 返回 2 条订单 → "失败" ❌

同一输入，4 次运行选择了 3 种不同的工具，返回了不同的结果。
```

QA 团队无法区分这是真正的非确定性还是代码 Bug，每次测试失败需要人工判断，消耗大量精力。

### 1.2 非确定性的三个层次

**层次 1：检索顺序波动**

```python
# RAG 检索结果每次可能不同，即使使用相同的 query：
retrieve("如何退款？", top_k=5)
# 运行 1: [doc_A, doc_B, doc_C, doc_D, doc_E]
# 运行 2: [doc_A, doc_C, doc_B, doc_D, doc_F]  ← 顺序和内容都不同！

# 原因：
# 1. embedding 计算的浮点精度差异（GPU vs CPU）
# 2. 近似最近邻（ANN）索引的随机性（HNSW、IVF）
# 3. 索引更新后的数据分布变化
```

**层次 2：模型温度**

生产环境中，很多 Agent 框架默认 temperature > 0：

```python
# ❌ 很多框架的默认配置
config = {
    "temperature": 0.7,  # OpenAI 默认
    "top_p": 0.9,
}
# 每次输出都不同！

# ✅ 生产环境的推荐配置（需要确定性时）
config = {
    "temperature": 0.0,  # 近似确定性（注意：并非绝对确定）
    "top_p": 1.0,
}
```

即使 temperature=0，模型推理仍然可能因为以下原因产生非确定输出：

- GPU 计算的非确定性（CUDA 的非确定性浮点运算）
- 批处理大小不同导致的 padding 差异
- 不同的 API 端点（如 A/B 测试路由到不同模型版本）

**层次 3：工具输出格式波动**

```python
# 工具 A 在某些情况下返回：
{"orders": [{"id": "ORD-001", "status": "shipped"}]}

# 同样的工具在另一些情况下返回：
[{"order_id": "ORD-001", "delivery_status": "shipped"}]

# 或者在某些极端情况下返回空数组、null、甚至报错！
```

Agent 的后续步骤依赖于工具输出的格式。格式变化导致参数提取步骤产生不同结果。

### 1.3 生产数据

根据 2024 年的一项研究（"Reproducibility in LLM-based Agent Systems"）：

| 非确定性来源 | 影响程度 | 发生频率 | 可控制性 |
|------------|---------|---------|---------|
| Temperature > 0 | 高 | 总是 | 容易（设为 0） |
| 检索顺序波动 | 中-高 | 经常 | 中等（seed 固定） |
| GPU 非确定性 | 低-中 | 有时 | 困难（硬件层面） |
| 工具输出格式变化 | 高 | 经常 | 中等（Schema 校验） |
| 模型版本差异 | 高 | 偶尔 | 容易（固定版本） |
| Prompt 模板渲染 | 低 | 有时 | 容易（确定性模板） |

生产环境中最常见的不稳定组合：**主动 Temperature + 被动检索波动 + 工具输出变化**。

## 二、根因分析

### 2.1 LLM 本身就是概率模型

这是最根本的原因。LLM 的核心机制是从概率分布中采样：

```python
# LLM 生成过程不是 y = f(x)，而是 y ~ P(y|x)
# 每次采样都可能得到不同的 y

# 即使 temperature=0，也只是选择概率最高的 token：
# 但多个 token 的概率可能非常接近（如 0.31 vs 0.30）
# 浮点精度的微小差异可能改变"最高概率"的归属
```

### 2.2 检索系统的内在随机性

生产级的向量检索系统（FAISS、Milvus、Pinecone）默认使用近似检索：

```
精确检索（brute force）：确定性的，但 O(n) 复杂度，大规模不可行
近似检索（ANN）：非确定性的，O(log n) 复杂度，但每次结果可能不同

ANN 的非确定性来源：
1. HNSW 图遍历的随机起点
2. IVF 聚类中心的搜索顺序
3. PQ 量化重建的精度损失
4. 并发写入导致的索引状态不一致
```

### 2.3 多步骤的"蝴蝶效应"

Agent 的每一步都建立在前一步的基础上——前一步的微小差异在后续步骤中被放大：

```
步骤 1: 工具选择  →  差异: get_orders vs search_orders
         ↓
步骤 2: 参数提取  →  差异: {"user_id": "123"} vs {"user_id": "123", "status": "all"}
         ↓
步骤 3: 结果处理  →  差异: 解析 3 条订单 vs 解析 2 条订单
         ↓
步骤 4: 回答生成  →  差异: "您有 3 条订单" vs "您有 2 条订单"
```

**初始的微小差异经过多步骤放大后，最终结果可能完全不同**。这与混沌理论中的"蝴蝶效应"如出一辙。

### 2.4 隐式状态依赖

Agent 的行为不仅依赖于输入，还依赖于"隐式状态"：

```
隐式状态包括：
1. 之前对话的轮数（影响上下文长度和注意力分布）
2. 之前工具调用的顺序（影响 Agent 对"哪些工具可用"的认知）
3. 系统当前负载（影响 API 响应时间，进而影响 Agent 的"等待"决策）
4. 缓存命中状态（命中缓存 vs 重新计算导致不同的中间结果）
```

这些隐式状态的变化使得同一输入产生不同输出。

## 三、检测方法

### 3.1 确定性测试（Repeatability Test）

```python
class DeterminismTest:
    """
    确定性测试：相同输入重复运行 N 次，检查输出的一致性。
    """
    def __init__(self, agent, n_runs: int = 5):
        self.agent = agent
        self.n_runs = n_runs
    
    def test(self, input_data: dict) -> dict:
        """运行 N 次，比较结果"""
        results = []
        
        for i in range(self.n_runs):
            result = self.agent.run(copy.deepcopy(input_data))
            results.append(result)
        
        # 检查是否完全一致
        all_identical = all(
            self._normalize(r) == self._normalize(results[0])
            for r in results
        )
        
        # 计算语义一致性（即使格式不同，语义是否一致）
        semantic_scores = []
        for i in range(len(results)):
            for j in range(i+1, len(results)):
                score = self._semantic_similarity(results[i], results[j])
                semantic_scores.append(score)
        
        return {
            "exact_match": all_identical,
            "semantic_consistency": np.mean(semantic_scores),
            "semantic_std": np.std(semantic_scores),
            "n_runs": self.n_runs,
            "details": results
        }
    
    def _normalize(self, result: Any) -> str:
        """标准化结果以便比较"""
        return json.dumps(result, sort_keys=True, default=str)
```

### 3.2 注册非确定性来源

在系统中注册所有已知的非确定性来源：

```python
class NonDeterminismRegistry:
    """
    注册和追踪系统中所有的非确定性来源。
    """
    def __init__(self):
        self.sources: list[dict] = []
    
    def register(self, name: str, source_type: str, 
                 impact: str, controllability: str):
        """注册一个非确定性来源"""
        self.sources.append({
            "name": name,
            "type": source_type,
            "impact": impact,
            "controllability": controllability,
            "registered_at": datetime.now()
        })
    
    def report(self) -> dict:
        """生成非确定性报告"""
        return {
            "total_sources": len(self.sources),
            "by_impact": {
                impact: len([s for s in self.sources if s["impact"] == impact])
                for impact in ["high", "medium", "low"]
            },
            "by_controllability": {
                ctrl: len([s for s in self.sources if s["controllability"] == ctrl])
                for ctrl in ["easy", "medium", "hard"]
            },
            "sources": self.sources
        }


# 在系统初始化时注册
registry = NonDeterminismRegistry()
registry.register("LLM temperature", "model", "high", "easy")
registry.register("ANN retrieval order", "retrieval", "medium", "medium")
registry.register("GPU float precision", "infrastructure", "low", "hard")
registry.register("Tool output format", "tool", "high", "medium")
```

## 四、解决方案

### 4.1 主动控制非确定性

```python
class DeterministicAgent:
    """
    尽可能提供确定性输出的 Agent 配置。
    """
    def __init__(self):
        self.config = {
            # LLM 配置
            "temperature": 0.0,
            "top_p": 1.0,
            "seed": 42,  # 仅部分模型支持
            "model_version": "claude-sonnet-4-20250514",  # 固定版本
            
            # 检索配置
            "retrieval": {
                "top_k": 5,
                "ef_search": 100,  # HNSW 确定性搜索（固定 ef）
                "ensure_deterministic": True,
            },
            
            # 工具配置
            "tool_output": {
                "normalize_schema": True,  # 统一工具输出格式
                "strict_validation": True,
            }
        }
    
    def run(self, input_data: dict) -> dict:
        """确定性执行"""
        # 1. 固定 seed（如果模型支持）
        if "seed" in self.config:
            input_data["_seed"] = self.config["seed"]
        
        # 2. 归一化检索结果
        retrieval_results = self._deterministic_retrieve(input_data)
        
        # 3. 固定输出格式
        result = self._llm_generate(input_data, retrieval_results)
        result = self._normalize_output(result)
        
        return result
    
    def _deterministic_retrieve(self, query: str) -> list[dict]:
        """使用确定性检索（精确检索或固定 seed 的 ANN）"""
        if self.config["retrieval"]["ensure_deterministic"]:
            # 使用精确检索（小数据集时）
            return self._exact_search(query)
        else:
            # 使用固定 seed 和参数的 ANN
            return self._deterministic_ann_search(query)
```

### 4.2 检索结果排序固化

消除检索系统的顺序波动：

```python
def stabilize_retrieval_order(results: list[dict]) -> list[dict]:
    """
    固化检索结果的排序和内容。
    
    策略：
    1. 分数降序排列
    2. 相同分数的按文档 ID 字典序排列
    3. 如果发现重复文档，只保留一个
    """
    # 排序：先按分数降序，再按文档 ID 升序
    sorted_results = sorted(
        results,
        key=lambda x: (-x.get("score", 0), x.get("doc_id", ""))
    )
    
    # 去重
    seen_ids = set()
    unique_results = []
    for r in sorted_results:
        doc_id = r.get("doc_id")
        if doc_id not in seen_ids:
            seen_ids.add(doc_id)
            unique_results.append(r)
    
    return unique_results
```

### 4.3 工具输出规范化

在 Agent 和工具之间加入输出规范化层：

```python
class ToolOutputNormalizer:
    """
    工具输出规范化层。
    将所有工具的输出统一为标准的 Schema 格式。
    """
    SCHEMAS = {
        "order_query": {
            "orders": [
                {
                    "order_id": str,
                    "status": str,
                    "amount": float,
                    "created_at": str
                }
            ]
        },
        "user_query": {
            "user_id": str,
            "name": str,
            "email": str
        }
    }
    
    def normalize(self, tool_name: str, raw_output: Any) -> dict:
        """将工具输出归一化为标准 Schema"""
        if tool_name not in self.SCHEMAS:
            # 没有定义 Schema 的工具，保持原始输出
            return {"raw": raw_output}
        
        schema = self.SCHEMAS[tool_name]
        
        # 处理各种可能的输出格式
        if isinstance(raw_output, list):
            return self._normalize_list(raw_output, schema)
        elif isinstance(raw_output, dict):
            return self._normalize_dict(raw_output, schema)
        elif raw_output is None:
            return self._normalize_none(schema)
        else:
            return {"raw": raw_output, "normalized": False}
    
    def _normalize_dict(self, output: dict, schema: dict) -> dict:
        """将字典归一化为 Schema"""
        normalized = {}
        for key, expected_type in schema.items():
            # 尝试多种可能的 key 名称
            possible_keys = [key, key.upper(), key.lower(), 
                           key.replace("_", ""), key.replace("_", "-")]
            value = None
            for pk in possible_keys:
                if pk in output:
                    value = output[pk]
                    break
            
            if value is not None:
                normalized[key] = value
            else:
                normalized[key] = None  # 显式标记缺失
        
        return normalized
```

### 4.4 语义等价测试

对于无法消除的非确定性，使用*语义等价*而非*精确匹配*来验证：

```python
def semantic_equivalence(output_a: str, output_b: str, 
                          threshold: float = 0.95) -> bool:
    """
    使用语义相似度判断两个输出是否等价。
    替代精确字符串比较。
    """
    # 方法 1：embedding 余弦相似度
    emb_a = embed(output_a)
    emb_b = embed(output_b)
    cosine_sim = cosine_similarity(emb_a, emb_b)
    
    # 方法 2：LLM 判断（更准确但更贵）
    prompt = f"""判断以下两个回答是否等价（含义相同）：
    
回答 A: {output_a}
回答 B: {output_b}

输出 YES 或 NO。"""
    
    judgement = llm_judge(prompt)
    
    return cosine_sim >= threshold and "YES" in judgement
```

## 五、预防措施

### 5.1 Temperature 管理策略

```yaml
temperature 策略:
  生产环境（需要确定性）: temperature = 0.0
  创意生成（需要多样性）: temperature = 0.7-1.0
  A/B 测试: 固定 seed 和 temperature
  
  核心原则:
  - 工具选择步骤: temperature = 0.0
  - 参数提取步骤: temperature = 0.0
  - 回答生成步骤: 可根据场景调整
  - 非必要时绝不使用 temperature > 0
```

### 5.2 检索系统确定性配置

```yaml
检索系统确定性配置:
  FAISS:
    - 使用 IndexFlatIP（精确检索）替代 IndexIVFFlat（近似检索）
    - 或固定 nprobe、ef_search 参数
  
  Milvus:
    - 设置 search_params. guarantee_timestamp = True
    - 使用一致性级别 Strong
  
  Pinecone:
    - 使用确定性索引类型
```

### 5.3 基础设施层面的确定性

```python
# 设置 PyTorch / CUDA 确定性模式（会降低性能）
import torch
torch.backends.cudnn.deterministic = True
torch.backends.cudnn.benchmark = False
torch.use_deterministic_algorithms(True)

# 设置随机种子
import random, numpy as np
random.seed(42)
np.random.seed(42)
```

注意：确定性模式会降低约 10-30% 的推理性能。只在需要严格确定性的场景启用。

### 5.4 测试策略调整

```yaml
测试策略:
  1. 精确匹配测试: 仅用于 temperature=0 且完全确定的路径
  2. 语义等价测试: 用于涉及检索的路径
  3. 统计测试: 多次运行取统计特征（平均值、分布），用于高度非确定的路径
  4. 黄金数据测试: 使用预定义的"黄金输出"做语义比较
```

## 关键教训速查

| 教训 | 说明 |
|------|------|
| LLM 本质是概率模型 | 非确定性是天赋属性，只能控制不能消除 |
| Temperature=0 并非绝对确定 | GPU 浮点精度和批处理差异仍会导致微小波动 |
| 检索排序是非确定性的主要来源 | ANN 索引的内在随机性需要主动控制 |
| 多步骤放大微小差异 | 初始的微小差异经过多步放大后输出完全不同 |
| 工具输出规范化是低投入高回报 | 确保工具输出格式一致能显著减少下游波动 |
| 测试中区分精确匹配和语义等价 | 不同场景需要不同的测试策略 |
| 注册并管理所有非确定性来源 | 明确哪些可控、哪些不可控 |
