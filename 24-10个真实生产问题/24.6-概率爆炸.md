# 24.6 概率爆炸 —— 多节点 Agent 工作流中的错误累积

> 现象：多步骤 Agent 工作流中，每一步的错误概率独立看起来很小（1%），但经过 6 步累积后，整体成功率从 99% 降到 94%。10 步后降到 90%，30 步后低于 75%——这就是概率爆炸（Probability Explosion）。

---

## 一、症状描述

### 1.1 概率的残酷数学

假设每个步骤的准确率为 p，N 个串行步骤的整体成功率：

```
P(整体成功) = p^N

当 p = 0.99:
N=1:  99.00%
N=6:  94.15%  ← 每 20 次执行就有 1 次失败
N=10: 90.44%  ← 每 10 次执行就有 1 次失败  
N=20: 81.79%  ← 每 5 次执行就有 1 次失败
N=50: 60.50%  ← 接近抛硬币
N=100: 36.6%  ← 成功概率比失败还低
```

这不是理论推演。某金融 Agent 在实际生产中：

```
步骤链：
1. classify_intent (99.5%) → 
2. extract_entities (98.5%) → 
3. call_tool_a (99.0%) → 
4. parse_result_a (97.0%) →
5. call_tool_b (98.5%) →
6. format_response (99.5%)

整体成功率：0.995 × 0.985 × 0.990 × 0.970 × 0.985 × 0.995 = 0.922
→ 7.8% 的请求会失败
→ 每 13 个用户请求就有 1 个得不到正确结果
```

### 1.2 生产中的实际表现

某电商 Agent 在双十一期间（日请求量 50 万）的表现：

```
工作流：理解查询 → 检索商品 → 查库存 → 查价格 → 生成推荐 → 格式化输出

单步平均准确率: 98.5%
理论整体成功率: 98.5%^6 = 91.3%
实际整体成功率: 87.5%

差距 (91.3% - 87.5% = 3.8%) 来自"相关性错误"——
前一歩的错误不仅导致该步失败，还"污染"了后续步骤的输入。
```

在高峰期：

```
日请求量: 500,000
日失败量: 62,500 (12.5%)
受影响用户: ~31,000 (假设每人 2 次请求)
```

### 1.3 概率爆炸 vs 级联失败

**概率爆炸**和**24.1 的级联失败**不同：

| | 概率爆炸 | 级联失败 |
|------|---------|---------|
| 本质 | 独立概率的乘积 | 前一步错误直接导致后续偏离 |
| 表现 | 随机失败，无明显模式 | 一旦某步错，后续全错 |
| 根因 | 步骤多、每步不够可靠 | 步骤间的强依赖 |
| 缓解 | 提高每步可靠性 + 冗余 | 检查点 + 回滚 + 重试 |

两者经常同时发生，但需要不同的应对策略。

## 二、根因分析

### 2.1 独立假设不成立

概率爆炸计算的理论基础是"每步错误相互独立"。但在实际 Agent 系统中，这个假设几乎从不成立：

```python
# 实际情况：错误是相关的！
P(步骤 N 失败 | 步骤 N-1 失败) >> P(步骤 N 失败)

# 原因：
# 1. 步骤 N-1 的输出质量下降导致步骤 N 的输入质量下降
# 2. 系统性偏差（如模型的温度设置过高）影响所有步骤
# 3. 上下文污染链式传递（24.4）
```

相关性错误使得实际成功率低于理论计算值。

### 2.2 多节点拓扑的复杂度

在 Multi-Agent 架构中（第 12 章），概率爆炸更严重：

```
串行 + 并行混合拓扑：

       ┌──→ Agent B ──→ ┐
Agent A ──→ Agent C ──→ ─→ Agent E
       └──→ Agent D ──→ ┘

P(成功) = P(A) × [1 - (1-P(B))×(1-P(C))×(1-P(D))] × P(E)

假设每步 p=0.98:
P(成功) = 0.98 × [1 - 0.02^3] × 0.98
       = 0.98 × 0.999992 × 0.98
       = 0.960
       
看起来不错？但如果有 10 个串行阶段：
P(成功) = 0.98^10 = 0.817
```

**系统越复杂，概率爆炸越严重**。

### 2.3 不可靠的单步

生产环境中 Agent 各步骤的真实可靠性：

| 步骤类型 | 典型准确率 | 失败模式 |
|---------|-----------|---------|
| 意图分类 | 95-99% | 模糊意图、多意图 |
| 实体提取 | 92-98% | 罕见实体、歧义 |
| 工具选择 | 85-97% | 工具数 > 50 时显著下降 |
| 参数提取 | 90-98% | 复杂嵌套参数 |
| 代码生成 | 80-95% | 复杂逻辑、边界条件 |
| 结构化输出 | 95-99% | 格式错误、Schema 不符 |
| 事实验证 | 85-95% | 开放域、长尾知识 |

大多数步骤的准确率远低于 99%。

## 三、检测方法

### 3.1 端到端成功率追踪

```python
class PipelineSuccessTracker:
    """
    追踪多步骤工作流的端到端成功率。
    按步骤分解，识别瓶颈。
    """
    def __init__(self):
        self.step_stats: dict[str, list[bool]] = {}
        self.pipeline_stats: list[bool] = []
    
    def record_step(self, step_name: str, success: bool):
        """记录单步结果"""
        if step_name not in self.step_stats:
            self.step_stats[step_name] = []
        self.step_stats[step_name].append(success)
    
    def record_pipeline(self, success: bool):
        """记录整体结果"""
        self.pipeline_stats.append(success)
    
    def report(self) -> dict:
        """生成可靠性报告"""
        report = {}
        
        # 整体成功率
        if self.pipeline_stats:
            report["overall_success_rate"] = (
                sum(self.pipeline_stats) / len(self.pipeline_stats)
            )
        
        # 单步成功率
        step_rates = {}
        for step_name, results in self.step_stats.items():
            rate = sum(results) / len(results)
            step_rates[step_name] = {
                "rate": rate,
                "failures": len(results) - sum(results),
                "total": len(results)
            }
        report["step_success_rates"] = step_rates
        
        # 瓶颈识别：成功率最低的步骤
        sorted_steps = sorted(
            step_rates.items(),
            key=lambda x: x[1]["rate"]
        )
        report["bottleneck_steps"] = sorted_steps[:3]
        
        # 理论 vs 实际成功率
        theoretical = 1.0
        for _, info in step_rates.items():
            theoretical *= info["rate"]
        report["theoretical_success_rate"] = theoretical
        
        return report
```

## 四、解决方案

### 4.1 检查点（Checkpoint）与重试

在关键步骤后设置检查点，失败时自动重试：

```python
class CheckpointedPipeline:
    """
    带检查点和自动重试的工作流。
    每个检查点保存中间状态，失败后回滚到最近的检查点。
    """
    def __init__(self, max_retries: int = 3):
        self.checkpoints: list[dict] = []
        self.max_retries = max_retries
    
    def run(self, pipeline: list[Step]) -> dict:
        """执行带检查点的 Pipeline"""
        checkpoint_index = len(self.checkpoints) - 1
        
        for step_index, step in enumerate(pipeline):
            retries = 0
            while retries <= self.max_retries:
                try:
                    result = step.execute(self._get_checkpoint_context())
                    self._save_checkpoint(step_index, result)
                    break  # 成功，继续下一步
                except Exception as e:
                    retries += 1
                    if retries > self.max_retries:
                        # 回滚到最近的检查点
                        logging.warning(
                            f"Step {step.name} failed after {self.max_retries} retries. "
                            f"Rolling back to checkpoint {checkpoint_index}."
                        )
                        self._rollback_to(checkpoint_index)
                        return {"status": "DEGRADED", 
                                "last_checkpoint": checkpoint_index}
                    
                    logging.info(f"Step {step.name} failed (attempt {retries}). Retrying...")
        
        return {"status": "SUCCESS", "result": self._get_final_result()}
    
    def _save_checkpoint(self, step_index: int, result: Any):
        self.checkpoints.append({
            "step_index": step_index,
            "result": result,
            "timestamp": time.time()
        })
    
    def _rollback_to(self, checkpoint_index: int):
        """回滚到指定检查点"""
        self.checkpoints = self.checkpoints[:checkpoint_index + 1]
```

### 4.2 冗余执行（投票机制）

对关键步骤使用"多个模型实例独立执行，投票决定结果"：

```python
class VotingExecutor:
    """
    冗余执行器：多个模型实例独立执行同一任务，投票决定最终结果。
    牺牲成本换取可靠性。
    
    3 个独立执行 → 3 选 2 投票 → 单步准确率从 95% 提升到 99.3%
    5 个独立执行 → 5 选 3 投票 → 单步准确率从 95% 提升到 99.9%
    """
    def __init__(self, num_executors: int = 3, strategy: str = "majority"):
        self.num_executors = num_executors
        self.strategy = strategy
    
    def execute(self, task: str, context: dict) -> tuple[Any, float]:
        """冗余执行并投票"""
        results = []
        
        for i in range(self.num_executors):
            result = self._single_execute(task, context, seed=i)
            results.append(result)
        
        # 投票决定最终结果
        if self.strategy == "majority":
            final_result = self._majority_vote(results)
            confidence = self._calculate_confidence(results)
        elif self.strategy == "weighted":
            final_result = self._weighted_vote(results)
            confidence = self._calculate_weighted_confidence(results)
        
        return final_result, confidence
    
    def _majority_vote(self, results: list[Any]) -> Any:
        """多数投票"""
        from collections import Counter
        counter = Counter(str(r) for r in results)
        most_common = counter.most_common(1)[0]
        return most_common[0]
```

**成本-收益分析**：

| 策略 | 单步准确率 | 成本倍数 | 适用场景 |
|------|-----------|---------|---------|
| 无冗余 | 95% | 1x | 低风险步骤 |
| 3 选 2 | 99.3% | 3x | 中等风险步骤 |
| 5 选 3 | 99.9% | 5x | 高风险步骤（如金融交易） |
| 自一致性（同模型多温度）| 97-99% | 2-3x | 事实性任务 |

### 4.3 降级路径设计

为关键工作流设计降级路径——当 A 方案失败时，自动切换到 B 方案：

```python
class DegradationPipeline:
    """
    带降级路径的工作流。
    Tier 1 失败后自动降级到 Tier 2，Tier 2 失败后降级到 Tier 3。
    """
    TIERS = {
        "tier_1": {  # 高质量模型 + 复杂流程
            "model": "claude-sonnet-4-20250514",
            "steps": ["classify", "extract", "search", "reason", "format"],
            "expected_accuracy": 0.98,
        },
        "tier_2": {  # 中质量模型 + 简化流程
            "model": "claude-haiku-4-20250514",
            "steps": ["classify", "search", "format"],
            "expected_accuracy": 0.92,
        },
        "tier_3": {  # 规则引擎回退
            "model": None,  # 无模型
            "steps": ["keyword_match", "template_response"],
            "expected_accuracy": 0.85,
        }
    }
    
    def execute(self, request: dict) -> Response:
        """执行带降级的工作流"""
        for tier_name, tier_config in self.TIERS.items():
            try:
                result = self._execute_tier(tier_config, request)
                if self._validate_result(result, tier_name):
                    return result
                logging.warning(f"Tier {tier_name} result failed validation")
            except Exception as e:
                logging.warning(f"Tier {tier_name} failed: {e}")
        
        # 所有 tier 都失败 → 返回保底响应
        return self._fallback_response()
```

## 五、预防措施

### 5.1 架构级预防：减少串行步骤数

**最根本的预防：从架构上减少串行步骤**。

```
❌ 过深的串行链（11 步）：
input → A → B → C → D → E → F → G → H → I → J → output

✅ 并行 + 合并（3 步）：
input → [A|B|C] → merge → [D|E|F] → output
```

将串行步骤数控制在 5 步以内，整体成功率可以维持在 95% 以上。

### 5.2 步骤可靠性基线

为每个步骤类型设定可靠性基线，持续监控：

```yaml
步骤可靠性基线:
  意图分类: ≥ 97%
  实体提取: ≥ 95%
  工具选择: ≥ 95%
  参数提取: ≥ 95%
  代码生成: ≥ 90%
  结构化输出: ≥ 97%
  
  低于基线 2%: warning（优先级低）
  低于基线 5%: critical（需要立即修复）
```

### 5.3 概率预算（Probability Budget）

类似 Token Budget，为工作流的"概率消耗"设定预算：

```
概率预算示例：
总成功率目标: ≥ 95%
允许的步骤数: ≤ 5 步
每步最低准确率: ≥ 99%
或者: ≤ 10 步，每步 ≥ 99.5%

概率预算 = -ln(目标成功率) / 步骤数

例子：
目标成功率 = 95%, 步骤数 = 5
概率预算 = -ln(0.95) / 5 = 0.0103
→ 每步允许的失败概率上限约为 1.03%
```

超过概率预算时，必须在"减少步骤"和"提高单步可靠性"之间做选择。

## 关键教训速查

| 教训 | 说明 |
|------|------|
| 概率爆炸是数学必然 | 串行步骤数超过 5 步时，成功率已开始显著下降 |
| 单步 99% 不代表系统可靠 | 30 步后成功率低于 75% |
| 检查点和重试是第一道防线 | 在关键步骤后保存状态，失败后回滚 |
| 冗余执行（投票）提升可靠性 | 3 选 2 将单步准确率从 95% 提升到 99.3% |
| 降级路径确保服务不中断 | 高质量模型失败后自动切换到低质量模型或规则引擎 |
| 减少串行步骤是最好的策略 | 架构设计上控制串行链长度 |
| 概率预算指导设计决策 | "总成功率 / 步骤数"量化每步可靠性要求 |
