## 一、动态发现与热加载

### 1.1 为什么需要动态发现？

在 10.1 节我们提到 `list_tools` 使 AI 应用能够动态感知工具的能力。但工程实践中，动态发现不仅仅是"启动时一次 list_tools"，还需要支持：

- **热加载**：在应用运行时新增/移除 Server，不中断正在进行的对话
- **状态感知**：Server 可以根据上下文动态返回不同的工具列表（如"用户未登录时不返回敏感工具"）
- **版本管理**：当 Server 更新后，Client 能感知到工具 Schema 的变化

### 1.2 动态发现架构

### 1.3 热加载实现

```python
"""
mcp_registry.py — MCP Server 注册表与热加载管理器
"""

import asyncio
import logging
from dataclasses import dataclass, field
from enum import Enum
from typing import Optional


class ServerStatus(Enum):
    OFFLINE = "offline"
    ONLINE = "online"
    ERROR = "error"


@dataclass
class MCServerConfig:
    """MCP Server 配置"""
    server_id: str
    command: str
    args: list[str]
    env: dict = field(default_factory=dict)
    auto_reconnect: bool = True
    health_check_interval: int = 30  # 秒


class MCPRegistry:
    """
    MCP Server 注册表
    
    职责：
    - 管理多个 MCP Server 的生命周期
    - 提供统一的工具发现接口
    - 支持运行时热添加/热移除 Server
    - 自动健康检查和重连
    """
    
    def __init__(self):
        self._servers: dict[str, 'MCPClient'] = {}
        self._configs: dict[str, MCServerConfig] = {}
        self._global_tools_cache: list[dict] | None = None
        self._lock = asyncio.Lock()
    
    async def register_server(self, config: MCServerConfig) -> None:
        """
        注册一个新的 MCP Server 并连接到它。
        
        Args:
            config: Server 配置
        """
        async with self._lock:
            if config.server_id in self._servers:
                logging.warning(f"Server {config.server_id} 已存在，将覆盖")
            
            # 创建新的 Client 连接
            client = MCPClient(config.command, config.args)
            try:
                await client.connect()
                self._servers[config.server_id] = client
                self._configs[config.server_id] = config
                # 清空全局缓存，触发重新发现
                self._global_tools_cache = None
                logging.info(f"Server {config.server_id} 注册成功")
                
                # 启动健康检查任务
                asyncio.create_task(
                    self._health_check_loop(config.server_id)
                )
            except Exception as e:
                logging.error(f"Server {config.server_id} 注册失败: {e}")
                # 配置保留，但标记为离线
                self._configs[config.server_id] = config
    
    async def unregister_server(self, server_id: str) -> None:
        """
        移除一个 MCP Server。
        
        Args:
            server_id: 要移除的 Server ID
        """
        async with self._lock:
            if server_id in self._servers:
                client = self._servers[server_id]
                await client.close()
                del self._servers[server_id]
                del self._configs[server_id]
                self._global_tools_cache = None
                logging.info(f"Server {server_id} 已移除")
    
    async def discover_all_tools(self, force_refresh: bool = False) -> list[dict]:
        """
        从所有在线的 Server 发现全部工具。
        
        使用缓存加速（默认 30 秒过期）。
        
        Args:
            force_refresh: 是否强制刷新缓存
            
        Returns:
            所有可用工具的列表
        """
        async with self._lock:
            if self._global_tools_cache and not force_refresh:
                return self._global_tools_cache
            
            all_tools = []
            
            for server_id, client in self._servers.items():
                try:
                    tools = await client.list_tools()
                    # 给每个工具标记来源 Server
                    for tool in tools:
                        tool["server_id"] = server_id
                    all_tools.extend(tools)
                except Exception as e:
                    logging.warning(
                        f"从 {server_id} 发现工具失败: {e}"
                    )
            
            self._global_tools_cache = all_tools
            logging.info(
                f"工具发现完成，共 {len(all_tools)} 个工具，"
                f"来自 {len(self._servers)} 个 Server"
            )
            return all_tools
    
    async def call_tool_on_server(
        self, server_id: str, tool_name: str, arguments: dict
    ) -> str:
        """
        在指定的 Server 上调用工具。
        
        Args:
            server_id: 目标 Server
            tool_name: 工具名称
            arguments: 工具参数
        """
        if server_id not in self._servers:
            raise ValueError(f"Server {server_id} 不在线")
        
        client = self._servers[server_id]
        return await client.call_tool(tool_name, arguments)
    
    async def _health_check_loop(self, server_id: str):
        """定期健康检查循环"""
        config = self._configs.get(server_id)
        if not config:
            return
        
        while server_id in self._servers:
            await asyncio.sleep(config.health_check_interval)
            
            try:
                client = self._servers[server_id]
                # 通过 list_tools 做健康检查
                await client.list_tools()
            except Exception:
                logging.warning(f"Server {server_id} 健康检查失败")
                
                if config.auto_reconnect:
                    await self._attempt_reconnect(server_id)
    
    async def _attempt_reconnect(self, server_id: str):
        """尝试重连"""
        config = self._configs.get(server_id)
        if not config:
            return
        
        # 移除旧连接
        if server_id in self._servers:
            await self._servers[server_id].close()
        
        # 尝试重连（最多 3 次）
        for attempt in range(3):
            try:
                client = MCPClient(config.command, config.args)
                await client.connect()
                self._servers[server_id] = client
                self._global_tools_cache = None
                logging.info(f"Server {server_id} 重连成功")
                return
            except Exception as e:
                logging.warning(
                    f"Server {server_id} 重连第 {attempt+1} 次失败: {e}"
                )
                await asyncio.sleep(2 ** attempt)  # 指数退避
        
        logging.error(f"Server {server_id} 重连失败，标记为离线")
```

## 二、缓存策略

### 2.1 缓存层级

MCP 系统中存在三个可缓存的层级：

```
层级 1: Tool Schema 缓存
  缓存内容：list_tools 返回的工具 Schema 列表
  缓存策略：TTL（默认 30 秒），可手动刷新
  命中率：高（工具 Schema 极少变化）
  失效代价：低（重新 list_tools 一次即可）

层级 2: Tool 调用结果缓存
  缓存内容：特定参数下的工具调用结果
  缓存策略：基于参数哈希的 LRU Cache
  命中率：中（同一参数的重复调用）
  失效代价：视工具而定

层级 3: Resource 内容缓存
  缓存内容：read_resource 读取的资源内容
  缓存策略：TTL + 事件驱动失效
  命中率：高（同一资源被多次读取）
  失效代价：可能读到过期数据
```

### 2.2 缓存实现

```python
"""
mcp_cache.py — MCP 缓存管理器
"""

import hashlib
import json
import time
from collections import OrderedDict
from typing import Any, Optional


class LRUCache:
    """
    最近最少使用（LRU）缓存
    
    特点：
    - 固定容量，自动淘汰最少使用的条目
    - 支持 TTL 过期
    - 线程安全（通过双端队列实现）
    """
    
    def __init__(self, capacity: int = 1000, ttl: int = 60):
        """
        Args:
            capacity: 最大缓存条目数
            ttl: 过期时间（秒）
        """
        self.capacity = capacity
        self.ttl = ttl
        self._cache = OrderedDict()  # key → (expire_time, value)
        self._stats = {"hits": 0, "misses": 0}
    
    def get(self, key: str) -> Optional[Any]:
        """获取缓存值，不存在或过期返回 None"""
        if key not in self._cache:
            self._stats["misses"] += 1
            return None
        
        expire_time, value = self._cache[key]
        
        if time.time() > expire_time:
            # 过期条目淘汰
            del self._cache[key]
            self._stats["misses"] += 1
            return None
        
        # 移动到末尾（最近使用）
        self._cache.move_to_end(key)
        self._stats["hits"] += 1
        return value
    
    def set(self, key: str, value: Any, ttl: Optional[int] = None):
        """设置缓存值"""
        expire_time = time.time() + (ttl or self.ttl)
        self._cache[key] = (expire_time, value)
        self._cache.move_to_end(key)
        
        # 淘汰最旧的条目
        while len(self._cache) > self.capacity:
            self._cache.popitem(last=False)
    
    def invalidate(self, key: str):
        """使指定缓存失效"""
        self._cache.pop(key, None)
    
    def clear(self):
        """清空所有缓存"""
        self._cache.clear()
        self._stats = {"hits": 0, "misses": 0}
    
    @property
    def hit_rate(self) -> float:
        """缓存命中率"""
        total = self._stats["hits"] + self._stats["misses"]
        if total == 0:
            return 0.0
        return self._stats["hits"] / total


class ToolResultCache:
    """
    工具调用结果缓存
    
    使用参数哈希作为缓存键，
    确保相同参数调用返回缓存结果。
    """
    
    def __init__(self, capacity: int = 500, default_ttl: int = 30):
        self._cache = LRUCache(capacity=capacity, ttl=default_ttl)
        self._default_ttl = default_ttl
    
    def _make_key(self, server_id: str, tool_name: str, arguments: dict) -> str:
        """生成缓存键（基于参数哈希）"""
        content = f"{server_id}:{tool_name}:{json.dumps(arguments, sort_keys=True)}"
        return hashlib.sha256(content.encode()).hexdigest()
    
    def get(self, server_id: str, tool_name: str, arguments: dict) -> Optional[str]:
        """获取缓存的工具调用结果"""
        key = self._make_key(server_id, tool_name, arguments)
        return self._cache.get(key)
    
    def set(
        self, 
        server_id: str, 
        tool_name: str, 
        arguments: dict, 
        result: str,
        ttl: Optional[int] = None
    ):
        """缓存工具调用结果"""
        key = self._make_key(server_id, tool_name, arguments)
        self._cache.set(key, result, ttl or self._default_ttl)
    
    def invalidate_tool(self, server_id: str, tool_name: str):
        """
        使某个工具的所有缓存失效。
        用于工具 Schema 变更后的缓存清理。
        """
        # 由于缓存键基于哈希，无法精确匹配
        # 这里简化为清空所有缓存
        # 生产环境可使用前缀匹配的缓存方案
        self._cache.clear()
    
    @property
    def hit_rate(self) -> float:
        return self._cache.hit_rate


# 使用示例
def demo_cache_usage():
    cache = ToolResultCache(capacity=100, default_ttl=60)
    
    # 第一次调用（未命中）
    result = cache.get("web-server", "search_web", {"query": "北京天气"})
    assert result is None
    
    # 缓存结果
    cache.set("web-server", "search_web", {"query": "北京天气"}, "晴天 25°C")
    
    # 第二次调用（命中）
    result = cache.get("web-server", "search_web", {"query": "北京天气"})
    assert result == "晴天 25°C"
```

### 2.3 缓存策略建议

| 工具类型 | 缓存策略 | TTL | 说明 |
|---------|---------|-----|------|
| 文件搜索 | 不缓存 | - | 文件系统变化频繁 |
| 天气查询 | TTL 缓存 | 30 分钟 | 天气变化缓慢 |
| 数据库查询 | TTL 缓存 | 1-60 秒 | 视数据更新频率 |
| API 调用 | TTL 缓存 | 取决于 API 限频 | 降低 API 调用成本 |
| Schema 信息 | 长期缓存 | 5-30 分钟 | 极少变化 |
| 系统信息 | 短暂缓存 | 5 秒 | CPU/内存变化快 |

## 三、多 MCP Server 协作模式

### 3.1 协作模式总览

一个成熟的 Agent 系统通常会运行多个 MCP Server，它们之间的协作存在几种经典模式：

```
模式 A：并行调用（Fan-out）
  一个任务需要多个工具并行执行
  例如：查询行程需要同时查天气、查航班、查酒店

模式 B：流水线调用（Pipeline）
  一个工具的输出是另一个工具的输入
  例如：搜索文件 → 读取文件内容 → 分析文件

模式 C：网关路由（Gateway/Router）
  一个中央 Server 根据请求内容路由到不同的后端 Server
  例如：统一的 "ask_agent" 工具，路由到不同的专业 Agent

模式 D：能力叠加（Capability Composition）
  多个 Server 提供互补能力，Agent 自动选择
  例如：文件系统 Server + 代码分析 Server + Git Server
```

### 3.2 并行调用（Fan-out）模式

```
用户请求："帮我计划明天去上海出差"

Agent 分解任务：
  任务1: 查询明天北京→上海的航班
  任务2: 查询上海的天气
  任务3: 查询明天上海的会议安排

并行执行：
  ┌────────────────────────────────────────────┐
  │               协调器 (Orchestrator)          │
  │                                             │
  │  ┌──────────┐  ┌──────────┐  ┌──────────┐ │
  │  │ 航班查询  │  │ 天气查询  │  │ 日历查询  │ │
  │  │ Server A  │  │ Server B  │  │ Server C  │ │
  │  └─────┬────┘  └─────┬────┘  └─────┬────┘ │
  │        │              │              │        │
  │        └──────────┬───┴──────────┬──┘        │
  │                   ▼                          │
  │           结果合并 + 生成回答                 │
  └────────────────────────────────────────────┘
```

```python
import asyncio

async def parallel_tool_calls(registry: MCPRegistry, tasks: list[dict]) -> list[str]:
    """
    并行调用多个工具。
    
    Args:
        registry: MCP Server 注册表
        tasks: 工具调用列表，每项包含 server_id, tool_name, arguments
        
    Returns:
        所有工具的执行结果列表（保持顺序）
    """
    async def single_call(task: dict) -> str:
        return await registry.call_tool_on_server(
            task["server_id"],
            task["tool_name"],
            task["arguments"]
        )
    
    # 所有任务并行执行
    results = await asyncio.gather(
        *[single_call(task) for task in tasks],
        return_exceptions=True  # 单个失败不影响其他
    )
    
    # 处理异常
    processed = []
    for i, result in enumerate(results):
        if isinstance(result, Exception):
            processed.append(f"[{tasks[i]['tool_name']}] 执行失败: {result}")
        else:
            processed.append(result)
    
    return processed
```

### 3.3 流水线（Pipeline）模式

```
任务：查找项目中所有未使用的 import 语句

步骤1: list_files(Server: 文件系统, pattern: "*.py")
  ↓ 返回文件列表 ["main.py", "utils.py", "api.py"]

步骤2: read_file(Server: 文件系统) → 对每个文件
  ↓ 返回文件内容

步骤3: analyze_imports(Server: 代码分析, files: [...])
  ↓ 返回未使用的 import 列表

步骤4: generate_report(Server: 工具, imports: [...])
  ↓ 返回修复建议
```

```python
async def pipeline_execution(registry: MCPRegistry, pipeline: list[dict]):
    """
    顺序执行流水线工具调用。
    每一步的输出作为下一步的输入之一。
    """
    context = {}
    
    for step in pipeline:
        # 支持模板参数（引用上一步的输出）
        resolved_args = {}
        for key, value in step.get("arguments", {}).items():
            if isinstance(value, str) and value.startswith("$"):
                # 从上下文中引用上一步的结果
                ref_key = value[1:]
                resolved_args[key] = context.get(ref_key, value)
            else:
                resolved_args[key] = value
        
        # 执行当前步骤
        result = await registry.call_tool_on_server(
            step["server_id"],
            step["tool_name"],
            resolved_args
        )
        
        # 将结果存入上下文
        if "output_key" in step:
            context[step["output_key"]] = result
    
    return context
```

### 3.4 网关路由（Gateway）模式

当存在大量 MCP Server 时，可以考虑引入一个"网关 Server"统一管理路由：

```
                          ┌──────────────────┐
                          │   MCP 网关 Server  │
                          │  (统一的入口点)    │
                          └────────┬─────────┘
                                   │
                   ┌───────────────┼───────────────┐
                   ▼               ▼               ▼
            ┌──────────┐   ┌──────────┐   ┌──────────┐
            │ Server A │   │ Server B │   │ Server C │
            │ (金融)    │   │ (医疗)    │   │ (法律)    │
            └──────────┘   └──────────┘   └──────────┘
```

网关 Server 的核心逻辑：

```python
class GatewayServer:
    """
    MCP 网关 Server
    
    职责：
    - 统一工具发现（聚合所有下游 Server 的工具）
    - 按能力路由（根据工具名称和参数路由到正确的 Server）
    - 负载均衡（多个同类型 Server 间的请求分发）
    - 访问控制（统一认证和授权）
    """
    
    def __init__(self):
        self.backend_servers: dict[str, MCPRegistry] = {}
        self.routing_table: dict[str, str] = {}  # tool_name → server_id
    
    async def discover_backends(self):
        """发现所有后端 Server 并构建路由表"""
        for server_id, client in self.backend_servers.items():
            tools = await client.list_tools()
            for tool in tools:
                self.routing_table[tool["name"]] = server_id
    
    async def route_call(self, tool_name: str, arguments: dict):
        """根据工具名称路由到正确的后端 Server"""
        server_id = self.routing_table.get(tool_name)
        if not server_id:
            raise ValueError(f"没有 Server 提供工具 {tool_name}")
        
        return await self.backend_servers[server_id].call_tool(
            tool_name, arguments
        )
```

## 四、MCP 与 A2A 协议的竞合关系

### 4.1 A2A 协议简介

A2A（Agent-to-Agent Protocol，Agent 间通信协议）是 Google 在 2025 年 4 月提出的开放协议，与 MCP 形成互补。两者的核心区别在于：

```
MCP：AI → Tool（AI 调用工具）
  AI Agent ←→ API / 数据库 / 文件系统 / ...

A2A：Agent → Agent（Agent 间通信）
  Agent A ←→ Agent B / Agent C / ...
```

关于 A2A 协议的详细技术分析，见第 26.3 节。本节从"与 MCP 的竞合关系"角度进行分析。

### 4.2 MCP vs A2A 对比

| 维度 | MCP | A2A |
|------|-----|-----|
| **全称** | Model Context Protocol | Agent-to-Agent Protocol |
| **提出者** | Anthropic（2025.12 捐赠给 Linux Foundation） | Google（后来也加入 Linux Foundation） |
| **通信方向** | Client → Server（单向） | Agent ↔ Agent（双向） |
| **核心原语** | Tools, Resources, Prompts | Skills, Cards, Artifacts |
| **传输协议** | JSON-RPC 2.0 (Stdio/SSE/HTTP) | HTTP (REST + SSE Stream) |
| **主要用途** | AI 应用接入工具/数据源 | Agent 之间协作通信 |
| **认证方式** | 进程隔离 + 用户授权 | OAuth 2.0 + JWT |
| **状态管理** | 无状态请求/响应 | 支持长时间运行任务 |
| **典型场景** | 文件操作、API 调用、数据库查询 | 跨 Agent 任务委派、协商 |

### 4.3 两者如何共存

MCP 和 A2A 不是竞争对手，而是解决不同问题的互补协议。2025 年 12 月 Anthropic 将 MCP 捐赠给 Linux Foundation 后，两类协议均在 Linux Foundation 的治理框架下发展，合作关系进一步明确：

```
                   ┌─────────────────────────┐
                   │      用户/人类用户         │
                   └────────────┬────────────┘
                                │
              ┌─────────────────▼─────────────────┐
              │        主 Agent（协调器）           │
              │  使用 A2A 与其他 Agent 通信         │
              └──────┬──────────────────┬─────────┘
                     │                  │
              ┌──────▼──────┐   ┌──────▼──────┐
              │  A2A 通信    │   │  MCP 通信    │
              │  Agent ↔ Agent│  │  AI → Tool   │
              └──────┬──────┘   └──────┬──────┘
                     │                  │
              ┌──────▼──────┐   ┌──────▼──────┐
              │ 专家 Agent A │   │  文件系统    │
              │ 专家 Agent B │   │  数据库      │
              │ 专家 Agent C │   │  API 网关    │
              └─────────────┘   └─────────────┘

主 Agent 的通信策略:
  - 与其他 Agent 协作 → A2A（Agent 间协商、任务委派）
  - 访问工具和数据源 → MCP（工具调用、资源读取）
```

### 4.4 工程中的融合使用

在一个实际的 Agent 系统中，MCP 和 A2A 可能同时存在：

```python
class HybridAgent:
    """
    同时支持 MCP（工具调用）和 A2A（Agent 通信）的 Agent
    """
    
    def __init__(self):
        # MCP: 工具和资源访问
        self.mcp_registry = MCPRegistry()
        
        # A2A: Agent 间通信
        self.a2a_client = A2AClient(
            agent_card="https://agent.example.com/.well-known/agent.json"
        )
    
    async def handle_task(self, task: str):
        """处理一个任务，可能涉及工具调用和 Agent 协作"""
        
        if self._needs_tools(task):
            # 通过 MCP 调用工具
            tools = await self.mcp_registry.discover_all_tools()
            result = await self.mcp_registry.call_tool_on_server(...)
            return result
        
        if self._needs_collaboration(task):
            # 通过 A2A 委派给专家 Agent
            a2a_result = await self.a2a_client.send_task({
                "agent_id": "expert-analysis-agent",
                "query": task,
                "metadata": {"priority": "high"}
            })
            return a2a_result
        
        # 混合模式：先 A2A 协作，再 MCP 执行
        plan = await self.a2a_client.negotiate_plan(task)
        for step in plan.steps:
            if step.type == "tool_call":
                await self.mcp_registry.call_tool_on_server(...)
            elif step.type == "agent_delegation":
                await self.a2a_client.send_task(step)
```

### 4.5 选择指南

```
你的场景是什么？
    │
    ├── AI 应用需要访问工具/数据源
    │   └── MCP（10.1-10.4 节）
    │
    ├── Agent 需要与其他 Agent 协作
    │   └── A2A（26.3 节）
    │
    ├── AI 应用需要工具访问 + Agent 协作
    │   └── MCP（对内工具）+ A2A（对外协作）
    │
    └── 不确定
        └── 先 MCP，再 A2A（工具接入是 Agent 的基础能力）
```

## 五、五大 Server 设计模式（2026 官方指南）

2026 年，MCP 官方发布了五种经过生产验证的 Server 设计模式，为不同场景提供架构参考：

### 5.1 Remote-only servers（纯远程部署）

适用于 Web 应用、移动端和云 Agent。Server 完全运行在远程，Client 通过 Streamable HTTP 或 MCP Tunnels 连接。

```
┌──────────────┐      Streamable HTTP      ┌──────────────┐
│  云 Agent    │───────────────────────────→│  远程 Server  │
│  (Claude)    │←───────────────────────────│  (SaaS API)  │
└──────────────┘                            └──────────────┘
```

**适用场景**：云端 AI 助手调用 SaaS 工具（Slack、Notion、GitHub）。

### 5.2 Intention-grouped tools（按意图分组工具）

不再按 API 端点镜像来组织工具，而是按用户意图分组。例如，一个 CRM Server 不应为每个 CRUD 操作暴露独立工具，而是按业务意图组织：

```json
// 不推荐：按 API 端点镜像（15+ 个工具）
"tools": ["create_contact", "read_contact", "update_contact", 
          "delete_contact", "create_lead", "read_lead", ...]

// 推荐：按意图分组（3-5 个工具）
"tools": [
  "search_crm"     // 智能搜索客户/线索/商机
  "update_crm"     // 智能更新（自动判断增/删/改）
  "analyze_crm"    // 数据分析与报表
]
```

**优势**：减少模型的选择负担，提高工具调用的准确率。配合 Tool Use Examples 效果更佳。

### 5.3 Code sandbox for large surfaces（少量工具覆盖大量端点）

当后端拥有大量 API 端点时（如 Cloudflare 的 2500+ 端点），不可能为每个端点创建独立的 MCP 工具。解决方案是使用少量高度灵活的"代理工具"：

```python
# Cloudflare 只用 2 个工具覆盖 2500+ API 端点
tools = [
    Tool(name="cf_api_call", description="调用任意 Cloudflare API 端点",
         inputSchema={
             "method": "string",    # GET/POST/PUT/DELETE
             "endpoint": "string",  # /client/v4/accounts/{id}/...
             "params": "object"
         }),
    Tool(name="cf_api_list", description="列举 Cloudflare 资源",
         inputSchema={
             "resource_type": "string",
             "filters": "object"
         })
]
```

**适用场景**：云平台管理（Cloudflare、AWS、GCP）、大型 SaaS 平台。

### 5.4 MCP Apps（返回交互式 UI）

传统的 MCP Server 返回纯文本响应，MCP Apps 模式允许 Server 返回交互式 UI：

```
工具调用 → Server 返回 UI 组件

{
  "content": [
    {
      "type": "ui",
      "ui_type": "form",
      "schema": {
        "fields": [
          {"name": "email", "type": "email", "label": "邮箱地址"},
          {"name": "template", "type": "select", "options": [...], "label": "选择模板"}
        ]
      }
    }
  ]
}
```

**适用场景**：表单填写、配置管理、审批流程。

### 5.5 Elicitation（引导式暂停）

Server 在执行过程中暂停，等待用户输入或 OAuth 授权后继续：

```
用户请求："帮我发一封邮件给张三"

1. Agent 调用"发送邮件"工具
2. MCP Server 暂停，等待用户确认邮件内容
3. 用户编辑并确认
4. MCP Server 继续执行，发送邮件
5. 返回发送结果
```

**适用场景**：发送消息前确认、OAuth 授权流程、敏感操作审批。

## 六、工程实践清单

### 5.1 生产环境部署检查表

```
□ MCP Server 进程管理
  □ 使用进程管理器（systemd / supervisord）管理 Server 生命周期
  □ 配置自动重启（崩溃后 3 秒自动拉起）
  □ 设置资源限制（内存、CPU、文件描述符）
  □ 配置日志轮转（按天或按大小）

□ 安全配置
  □ 每个 Server 配置最小权限原则
  □ 文件系统 Server 限定可访问的目录
  □ 网络 Server 限定可访问的域名
  □ 敏感操作（写/删）的用户确认机制
  □ STDIO Server 来源验证（防止 RCE 攻击）
  □ 考虑使用 MCP Tunnels 替代裸 STDIO（企业环境）
  □ 考虑 Self-Hosted Sandboxes 部署（数据主权要求）

□ 监控与告警
  □ 记录每个工具调用的延迟分布（P50/P95/P99）
  □ 记录工具调用成功率（按 Server 和工具名聚合）
  □ 配置告警：连续 5 次调用失败 → 通知
  □ 配置告警：P99 延迟超过 10 秒 → 通知
  □ 缓存命中率监控

□ 测试策略
  □ 单元测试：每个工具的输入/输出 Schema 验证
  □ 集成测试：Server 启动 → 连接 → 调用 → 断线重连
  □ 压力测试：模拟 100 个并发工具调用
  □ 安全测试：越界路径、超长输入、恶意参数
```

### 5.2 常见陷阱与解决方案

| 问题 | 症状 | 解决方案 |
|------|------|---------|
| Server 崩溃未恢复 | 工具调用返回 ConnectionError | 实现自动重连（见 1.3 节） |
| 缓存过期数据 | 工具返回旧结果 | 为不同工具设置不同的 TTL |
| 并发调用死锁 | 工具调用卡死 | 使用 asyncio.gather 并发控制 |
| 工具 Schema 不匹配 | 参数验证失败 | 调用前做 Schema 校验 |
| 内存泄漏 | Server 内存持续增长 | 限制工具输出大小，定期重启 Server |
| 参数量过大 | JSON-RPC 消息超过限制 | 对大参数做分片或压缩 |
| STDIO RCE 风险 | 恶意 Server 进程执行任意代码 | 验证 Server 来源，使用沙箱/Tunnels |

### 5.3 性能优化清单

```
□ 使用 LRU 缓存工具 Schema（减少 list_tools 调用）
□ 为幂等工具启用结果缓存（减少重复计算）
□ 大文件读取使用流式传输（避免内存 OOM）
□ 批量操作优先使用 Server 内部批处理（减少 IPC 次数）
□ 高频工具考虑合并到同一个 Server（减少进程数）
□ 使用压缩传输（对大数据量的 JSON-RPC 启用 gzip）
```

## 关键概念速查

| 术语 | 解释 |
|------|------|
| 动态发现 | 运行时通过 `list_tools` 获取可用工具，支持热加载 |
| 热加载 | 不中断服务的前提下添加/移除 MCP Server |
| Server 注册表 | 管理多个 MCP Server 的生命周期和状态的组件 |
| 工具结果缓存 | 对幂等工具的调用结果进行缓存，降低延迟和成本 |
| LRU Cache | 最近最少使用淘汰策略的缓存实现 |
| Fan-out 模式 | 多个工具并行调用的协作模式 |
| Pipeline 模式 | 一个工具输出是另一个工具输入的串行协作模式 |
| 网关模式 | 统一入口路由到多个后端 Server 的架构模式 |
| A2A (Agent-to-Agent) | Google 提出的 Agent 间通信协议，详见 26.3 节 |
| 健康检查 | 定期检测 MCP Server 是否正常运行的机制 |
| 指数退避 | 重连时等待时间指数增长，避免 Server 过载 |
| Remote-only servers | 纯远程部署 Server，适用于 Web/移动/云 Agent |
| Intention-grouped tools | 按用户意图而非 API 端点组织工具 |
| Code sandbox for large surfaces | 少量代理工具覆盖大量 API 端点 |
| MCP Apps | Server 返回交互式 UI 而非纯文本 |
| Elicitation | Server 暂停等待用户输入或 OAuth 授权 |
| Self-Hosted Sandboxes | 企业自有基础设施上的沙箱执行环境 |
| MCP Tunnels | 单向加密隧道，安全访问内网资源 |
