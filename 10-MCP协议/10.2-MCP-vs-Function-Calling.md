# 10.2 MCP vs Function Calling

> MCP 和 Function Calling 是 AI Agent 生态中两个常被混淆的概念。一个常见的面试问题是："MCP 是否取代了 Function Calling？" 答案是否定的——**MCP 是通信管道，Function Calling 是工具选择机制，两者在 Agent 系统中扮演不同层级的角色，相互补充而非替代**。

---

## 一、基本概念区分

### 1.1 Function Calling 是什么

Function Calling 是 LLM 模型在生成文本时识别出"需要调用外部函数"并输出结构化调用请求的能力。它不是模型的一个独立功能模块，而是模型在训练中习得的**输出格式能力**——模型学会了在特定上下文中输出特定格式的 JSON，表示"我需要调用这个函数，参数是这些"。

工作流程：
```
用户请求："北京明天会下雨吗？"

模型内部推理：
  - 用户需要一个实时信息（天气）
  - 我有一个 get_weather 工具可用
  - 应该用参数 location="北京", date="明天" 调用它

模型输出（Function Call）：
  {
    "function": "get_weather",
    "arguments": {
      "location": "北京",
      "date": "2026-06-02"
    }
  }

执行环境收到函数调用 → 执行函数 → 返回结果给模型 → 模型生成最终回答
```

Function Calling 的**本质**是模型的一种"意图识别+参数提取"能力，是**模型层面的能力**。

### 1.2 MCP 是什么

如 10.1 节所述，MCP 是 AI 应用与外部工具之间的**标准化通信协议**。它定义了：
- 工具如何被"发现"（list_tools）
- 工具如何被"调用"（call_tool）
- 资源如何被"读取"（read_resource）
- 错误如何被"报告"（标准错误码）

MCP 的**本质**是工具和 AI 应用之间的**集成标准**，是**基础设施层面的能力**。

### 1.3 两个概念的分层关系

```
┌──────────────────────────────────────────────────┐
│                     AI 应用                        │
│  ┌──────────────────────────────────────────────┐│
│  │          LLM（大语言模型）                      ││
│  │  ┌──────────────────────────────────────┐    ││
│  │  │  Function Calling（意图识别+参数提取） │    ││
│  │  │  模型说："我需要调用 get_weather"     │    ││
│  │  └──────────────┬───────────────────────┘    ││
│  └─────────────────┼───────────────────────────┘│
│                    │                              │
│  ┌─────────────────▼───────────────────────────┐│
│  │     MCP Client（协议层通信）                  ││
│  │     把函数调用变成 JSON-RPC 请求             ││
│  │     并通过 Stdio/SSE 发送给 Server           ││
│  └─────────────────┬───────────────────────────┘│
└────────────────────┼────────────────────────────┘
                     │
┌────────────────────▼────────────────────────────┐
│              MCP Server（执行层）                 │
│                get_weather 的具体实现             │
│                调用天气 API → 返回结果            │
└──────────────────────────────────────────────────┘

分层解读：
第一层（模型层）：Function Calling — 模型"想"调用什么
第二层（协议层）：MCP Client — 把"想法"标准化地传递出去
第三层（执行层）：MCP Server — 真正执行工具逻辑
```

### 1.4 2026 年的新变化：Advanced Tool Use Suite

2025 末至 2026 初，Anthropic 发布了 Advanced Tool Use Suite，在 Function Calling 和 MCP 之间引入了新的能力层：

```
传统流水线：
LLM Function Calling → MCP 执行

2026 年增强流水线：
LLM Function Calling 
  + Tool Search（工具懒加载，降低上下文占用）
  + Programmatic Tool Calling（PTC，Python 脚本编排）
  + Tool Use Examples（复杂参数示例）
→ MCP 执行
```

**Tool Search** 改变了工具发现的方式：不再一次性将所有工具的 Schema 注入模型上下文，而是通过语义搜索动态加载匹配的工具子集。这使得 Agent 可以管理数千个工具而无需担心上下文窗口限制。

**Programmatic Tool Calling（PTC）** 允许 Claude 编写 Python 脚本来自动编排复杂的工具调用链路，相比逐次 Function Calling 减少了 37% 的 token 消耗。

**Tool Use Examples** 允许开发者为工具参数提供调用示例，将复杂参数场景的准确率从 72% 提升至 90%。

## 二、详细对比

### 2.1 核心维度对比表

| 维度 | Function Calling | MCP |
|------|-----------------|-----|
| **层级** | 模型层（LLM 内部能力） | 基础设施层（通信协议） |
| **核心功能** | 意图识别 + 参数提取 | 工具发现 + 远程调用 + 资源访问 |
| **谁来定义** | AI 模型提供商（OpenAI、Anthropic、Google） | 社区协议（Anthropic 发起） |
| **工具来源** | 通过 API 参数传入（硬编码） | 通过 `list_tools` 动态发现 |
| **通信方式** | 模型输出 JSON → 宿主环境解析 | JSON-RPC 2.0 通过 Stdio/SSE |
| **调用延迟** | 极低（模型生成 JSON，< 1ms 额外开销） | 中（JSON-RPC 序列化 ≈ 1-10ms + IPC 延迟） |
| **集成复杂度** | 低（API 参数传工具定义即可） | 中（需要搭建 MCP Server/Client 基础设施） |
| **动态能力** | 差（工具列表预先传入，变更需重新请求） | 强（运行时发现新工具，热插拔） |
| **安全模型** | 依赖宿主环境实现 | 内置沙箱 + 用户授权 + 进程隔离 |
| **资源访问** | 不支持（只能调用函数） | 支持（Resource 原语读取数据） |
| **适用范围** | 单 Agent 内部 | 多 Agent + 多工具生态系统 |
| **标准化程度** | 每个模型提供商的格式不同 | 统一标准，跨平台互操作 |
| **生态规模** | 与模型绑定，工具数量受限 | 可扩展的 Server 生态（2026 Q1: 7000+ Server, ~30亿月下载量） |

### 2.2 适用场景对比

**更适用 Function Calling 的场景：**

1. **单 Agent、少量工具的简单场景**
   - 例如：一个只做天气查询的聊天机器人，只有 2-3 个工具
   - 不需要动态发现，工具列表在代码中写死即可

2. **对延迟极度敏感的场景**
   - 实时对话场景中，Function Calling 的额外延迟几乎为零
   - MCP 的 IPC 开销在毫秒级，但高频调用可能累积

3. **工具在模型内部进程中执行**
   - 当工具是纯计算型（数学计算、数据处理），不需要访问外部系统
   - 直接在 LLM 所在进程中执行，无需进程间通信

4. **团队没有基础设施维护能力**
   - 不需要搭建 MCP Server/Client
   - 直接用模型 SDK 的 Function Calling 功能

**更适用 MCP 的场景：**

1. **多工具、动态工具集**
   - Agent 需要根据任务场景动态加载不同的工具
   - 例如：代码开发 Agent 有时需要 Git 工具，有时需要数据库工具

2. **标准化工具生态**
   - 工具提供方希望一次开发被多个 AI 应用使用
   - 例如：数据库 MCP Server 可被 Claude Code、Cursor、VS Code AI 同时使用

3. **安全敏感的操作**
   - 文件系统访问、数据库写入、消息发送等需要沙箱和用户确认
   - MCP 的安全模型比自定义实现更成熟

4. **资源密集型访问**
   - 需要读取文件、查询数据库、获取网页内容
   - MCP 的 Resource 原语比 Function Calling 更适合数据获取

5. **企业级工具治理**
   - 需要统一管理、审计、监控所有工具的访问
   - MCP Server 可以集中部署、统一升级

### 2.3 延迟与性能对比

以一个典型的工具调用场景为例（"查询北京的天气"）：

```
Function Calling 路径：
┌────────┐    ┌──────────┐    ┌──────────┐
│  User  │───→│   LLM    │───→│ 执行环境  │───→ 天气 API
└────────┘    └──────────┘    └──────────┘
延迟：模型生成(500ms) + 函数调用(200ms)
总计：~700ms

MCP 路径：
┌────────┐    ┌──────────┐    ┌──────────────┐    ┌────────────┐
│  User  │───→│   LLM    │───→│ MCP Client   │───→│ MCP Server │───→ 天气 API
└────────┘    └──────────┘    └──────────────┘    └────────────┘
延迟：模型生成(500ms) + TCP/IP序列化(3ms) + MCP处理(2ms) + 工具调用(200ms)
总计：~705ms
差异：~5ms（在典型场景中差异可忽略）

高频调用场景（如文件搜索 + 代码阅读 + 代码修改 连续调用）：
- Function Calling: 多次调用在同一个进程内完成，上下文切换少
- MCP: 每次调用经过独立进程的序列化/反序列化，累积差异更明显
- 在连续 20 次工具调用时，MCP 额外开销约 60-100ms，占总时间的 < 5%
```

结论：在绝大多数场景中，MCP 的额外延迟（约 3-5ms 每次调用）对用户体验的影响可以忽略。当工具调用次数较少或单次工具执行时间较长（如查询数据库、调用 API）时，这个差异几乎不可感知。

## 三、互补关系：它们如何合作

### 3.1 典型合作流程

在现代 Agent 框架中，Function Calling 和 MCP 不是"二选一"，而是"先 Function Calling，后 MCP"的流水线关系：

```
1. 模型通过 Function Calling 输出调用意图
   └── 输出: {"function": "search_web", "arguments": {"query": "北京天气"}}
   
2. MCP Client 层接收函数调用请求
   └── 将请求转换为 JSON-RPC 格式
   
3. MCP Client 通过传输层发给对应的 MCP Server
   └── {"jsonrpc":"2.0","method":"call_tool","params":{"name":"search_web","arguments":{...}}}
   
4. MCP Server 执行具体的工具逻辑
   └── 调用搜索引擎 API → 获取结果
   
5. MCP Server 返回结果给 MCP Client
   └── {"result": {"content": [{"type": "text", "text": "北京天气..."}]}}
   
6. MCP Client 将结果注入到模型的上下文中
   └── 作为 Function Calling 的"执行结果"返回给模型
   
7. 模型基于结果生成最终回答
```

### 3.3 实际代码中的融合

以下是一个 MCP Client 如何将 Function Calling 与 MCP 结合使用的示例：

```python
import asyncio
from mcp import ClientSession, StdioServerParameters

class MCPFunctionCallingAdapter:
    """将 MCP 工具适配为 LLM 的 Function Calling 格式"""
    
    def __init__(self, server_params: StdioServerParameters):
        self.server_params = server_params
        self.session = None
        self.tools = []
    
    async def connect(self):
        """连接到 MCP Server 并获取工具列表"""
        # 创建 MCP 会话（详见 10.3 节）
        self.session = await ClientSession.create(self.server_params)
        
        # 动态发现工具（list_tools）
        tools_response = await self.session.list_tools()
        
        # 转换为 Function Calling 格式
        self.tools = []
        for tool in tools_response.tools:
            fc_tool = {
                "type": "function",
                "function": {
                    "name": tool.name,
                    "description": tool.description,
                    "parameters": tool.inputSchema  # JSON Schema
                }
            }
            self.tools.append(fc_tool)
        
        return self.tools
    
    async def execute(self, function_name: str, arguments: dict) -> str:
        """通过 MCP 执行工具调用"""
        result = await self.session.call_tool(function_name, arguments)
        return result.content[0].text

# 使用示例
async def main():
    # 初始化 MCP 适配器
    adapter = MCPFunctionCallingAdapter(
        StdioServerParameters(
            command="python",
            args=["mcp_server.py"]
        )
    )
    
    # 连接并获取工具列表
    tools = await adapter.connect()
    
    # 将工具列表传给 LLM（OpenAI Function Calling 格式）
    # import openai
    # response = openai.chat.completions.create(
    #     model="gpt-4",
    #     tools=tools,  # ← 通过 MCP 动态获取的工具列表
    #     messages=[...]
    # )
    
    # 当 LLM 返回 Function Call 时，通过 MCP 执行
```

## 四、什么时候选择什么？

### 4.1 决策流程图

```
开始：你的场景是？
    │
    ├── 需要工具在多个 AI 应用间复用？
    │   └── 是 → MCP
    │
    ├── 只有 1-3 个简单工具？
    │   └── 是 → Function Calling 更简单
    │
    ├── 工具需要动态变更（运行时增减）？
    │   └── 是 → MCP（list_tools 热更新）
    │
    ├── 需要读取各种数据源（文件、数据库、API）？
    │   └── 是 → MCP（Resource 原语）
    │
    ├── 对安全有严格要求（企业级）？
    │   └── 是 → MCP（内置沙箱 + 权限模型）
    │
    ├── 需要极低延迟（每轮 < 10ms）？
    │   └── 是 → Function Calling
    │
    └── 以上都不清楚？
        └── 建议：先用 Function Calling 快速验证
             再按需引入 MCP 做标准化
```

### 4.2 常见面试问题

**Q: MCP 会取代 Function Calling 吗？**
A: 不会。两者是不同层级的互补技术。Function Calling 解决"模型什么时候调用什么工具"的问题，MCP 解决"工具如何被发现和调用"的问题。就像网络协议中 HTTP 和 TCP 的关系——一个在上层，一个在下层，各自解决不同的问题。

**Q: 为什么 MCP 的出现让 Function Calling 变得更重要？**
A: 因为 MCP 让工具的**数量**和**种类**大幅增加。一旦大量工具通过 MCP 标准化接入，Agent 面临更多工具选择的场景，Function Calling 的"多工具选择能力"就变得更加关键。这与第 9 章（Function Calling）密切相关——MCP 大幅扩展了 Function Calling 的可用工具范围。

**Q: 可以用 MCP 完全不用 Function Calling 吗？**
A: 可以，但需要框架层做额外的逻辑。一些 MCP Client 直接让 LLM 的对话输出中包含工具调用意图（通过特定 Prompt 格式），而不依赖模型的 Function Calling 能力。但这样会失去模型原生训练的意图识别能力，通常不如两者配合使用效果好。

## 五、MCP + Function Calling 的最佳实践

### 5.1 推荐组合方案

```
生产环境的推荐方案（2026 版）：

┌──────────────────────────────────────────┐
│  基础层：Model Provider Function Calling    │
│  - 使用 OpenAI/Anthropic 原生的工具调用    │
│  - 获得最佳的工具选择准确率                 │
├──────────────────────────────────────────┤
│  增强层：Advanced Tool Use Suite             │
│  - Tool Search：懒加载工具 Schema          │
│  - PTC：Python 脚本编排复杂调用链路        │
│  - Tool Use Examples：复杂参数示例引导     │
├──────────────────────────────────────────┤
│  管道层：MCP Protocol                       │
│  - 动态发现工具（不是硬编码工具列表）       │
│  - 标准化工具执行（不是自己写执行逻辑）     │
│  - 安全沙箱（不用自己实现权限控制）         │
├──────────────────────────────────────────┤
│  增值层：MCP Server 生态                    │
│  - 通过 Registry 发现 7000+ 公共 Server   │
│  - 复用现有的工具实现，不重复造轮子         │
│  - Skills 集成：Server 直接分发程序性知识   │
└──────────────────────────────────────────┘
```

### 5.2 混合使用的模式

有两种主流的混合使用模式：

**模式一：MCP 作为 Function Calling 的"执行网关"**
```
LLM 输出 Function Call → MCP Client 作为网关执行 → 返回结果
```
- 优点：保留了模型的 Function Calling 能力（最佳工具选择准确性），同时获得 MCP 的动态发现和安全沙箱
- 缺点：两层间的适配需要额外的代码

**模式二：MCP 作为"工具源"，Function Calling 作为"选择器"**
```
MCP Server 提供工具 Schema → 转换为 Function Calling 格式 → 传入 LLM
```
- 优点：工具列表动态更新，无需修改 LLM 调用代码
- 缺点：首次连接时需要做格式转换
