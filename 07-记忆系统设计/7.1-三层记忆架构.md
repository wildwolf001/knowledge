# 7.1 三层记忆架构

> 人类的记忆并非单一存储——海马体负责短期记忆，皮层负责长期记忆，而工作记忆则是当前意识的焦点。Agent 的记忆系统同样需要分层设计：**Working Memory（工作记忆）** 对应上下文窗口，**Short-Term Memory（短期记忆）** 对应会话级缓存，**Long-Term Memory（长期记忆）** 对应持久化知识库。

---

## 一、为什么需要三层记忆？

### 1.1 LLM 的天然局限

大语言模型本身是无状态的。每次推理调用都是独立的概率计算，模型不"记得"上一轮对话说了什么。当前的解决方案主要有两种：

| 方案 | 做法 | 问题 |
|------|------|------|
| **全历史拼接** | 把完整对话历史放进 Prompt | Token 成本 O(n²)，达到上下文窗口上限后被截断 |
| **固定长度滑窗** | 只保留最近 K 轮对话 | 丢失早期关键信息，无法跨会话回忆 |

Agent 需要一种**有结构、有优先级、有生命周期**的记忆系统，而不只是"把所有文本塞进上下文"。

### 1.2 认知架构的启发

人类记忆的三层模型（Atkinson-Shiffrin 记忆模型）为 Agent 记忆设计提供了理论框架：

```
  外部信息                      注意力                     编码
  ────────→  感觉记忆 (Sensory) ───→ 短期记忆 (STM) ──────────→ 长期记忆 (LTM)
              (毫秒级)               (秒-分钟)                  (天-年)
                                        ↑                        │
                                        │       提取/回忆         │
                                        └────────────────────────┘

         Agent 记忆映射：
         感觉记忆  →  Raw Input Buffer (原始输入暂存)
         短期记忆  →  Short-Term Memory (Redis 会话缓存)
         长期记忆  →  Long-Term Memory (向量数据库)
         工作记忆  →  Working Memory (上下文窗口 + 注意力焦点)
```

## 二、Working Memory（工作记忆）

### 2.1 定义与范围

Working Memory 在 Agent 中对应 **当前 LLM 调用中可见的全部信息**。它直接占据 Token 消耗，因此是最昂贵的记忆层级。

```
┌─────────────────── Working Memory ───────────────────┐
│                                                      │
│  ┌──────────┐  ┌──────────┐  ┌──────────────────┐  │
│  │ System   │  │ Dialogue │  │ Retrieved         │  │
│  │ Prompt   │  │ History  │  │ Context (from DB) │  │
│  │ (恒定)   │  │ (滑窗)   │  │ (按需注入)        │  │
│  └──────────┘  └──────────┘  └──────────────────┘  │
│                                                      │
│  ┌────────────────────────────────────────────────┐  │
│  │    Token Budget 分配:                           │  │
│  │    Total = C (窗口上限, 如 128K tokens)         │  │
│  │    System Prompt = S (固定占用)                  │  │
│  │    Dialogue = D (动态调整)                      │  │
│  │    Retrieved = R (剩余配额)                     │  │
│  │    约束: S + D + R ≤ C                         │  │
│  └────────────────────────────────────────────────┘  │
└──────────────────────────────────────────────────────┘
```

### 2.2 注意力焦点与 Token Budget 管理

Working Memory 的核心管理策略是 **Token Budget 分配**。类似操作系统为进程分配内存，Agent 需要为不同类型的上下文分配 Token 配额：

```python
class WorkingMemoryManager:
    def __init__(self, max_tokens: int = 128000):
        self.max_tokens = max_tokens
        self.system_prompt_tokens = 0
        self.dialogue_history_tokens = 0
        self.retrieved_context_tokens = 0
        self.attention_focus = None  # 当前关注的记忆 ID

    def allocate_budget(self, dialogue: list, retrieved: list) -> dict:
        """动态分配 Token 预算"""
        # 系统 Prompt 固定占用
        system_tokens = self.system_prompt_tokens

        # 优先保留对话历史（最近 K 轮）
        max_dialogue_tokens = int(self.max_tokens * 0.3)  # 最多 30%
        dialogue_tokens = min(
            self._estimate_tokens(dialogue),
            max_dialogue_tokens
        )

        # 剩余给检索上下文
        remaining = self.max_tokens - system_tokens - dialogue_tokens
        retrieved_tokens = min(
            self._estimate_tokens(retrieved),
            remaining
        )

        return {
            "system": system_tokens,
            "dialogue": dialogue_tokens,
            "retrieved": retrieved_tokens,
        }
```

**关键约束**：Working Memory 中 D（对话历史）+ R（检索上下文）的和必须小于等于剩余窗口大小。当检索结果过多时，对话历史会被截断；反之亦然。

### 2.3 Working Memory 压缩策略

当内容超出窗口时，有以下压缩策略（由简到繁）：

| 策略 | 做法 | 信息损失 | 延迟开销 |
|------|------|----------|----------|
| **截断** | 丢弃最早的内容 | 高 | 无 |
| **滑动窗口** | 仅保留最近 N 轮 | 中 | 无 |
| **摘要压缩** | 用 LLM 对历史做摘要 | 中-低 | 1 次 LLM 调用 |
| **结构化压缩** | 提取关键实体 + 关系 | 低 | 1 次 LLM 调用 + 解析 |
| **选择性检索** | 只注入与当前 Query 最相关的内容 | 低 | 1 次向量检索 |

实践中，**选择性检索 + 滑动窗口**是最常见的组合：对话历史保持最近 10-20 轮，更早的信息通过向量检索按需注入。

## 三、Short-Term Memory（短期记忆）

### 3.1 定义与技术选型

Short-Term Memory 是**会话级别**的缓存，在 Agent 的多次推理调用之间保持状态。这是 Agent"记住刚才说了什么"的层级。

典型技术选型：

| 技术 | 优点 | 缺点 | 适用场景 |
|------|------|------|----------|
| **Redis** | 极快（<1ms），支持 TTL 自动过期，支持数据结构丰富 | 内存有限，需规划 eviction 策略 | 会话状态、对话上下文、实体缓存 |
| **Memcached** | 更简单的 KV 缓存 | 不支持持久化，数据结构有限 | 纯缓存场景 |
| **本地内存 dict** | 零网络开销 | Agent 重启即丢失，不跨进程 | 单进程原型 |

### 3.2 Redis 会话管理设计

```python
import redis
import json
import time
from typing import Optional

class ShortTermMemory:
    """
    短期记忆：基于 Redis 的会话管理
    - TTL: 30 分钟无活动自动过期
    - 数据结构: Hash (field = 记忆类型, value = JSON)
    """
    def __init__(self, redis_url: str = "redis://localhost:6379/0"):
        self.client = redis.from_url(redis_url)
        self.session_ttl = 1800  # 30 分钟
        self.max_sessions_per_user = 50

    def get_session(self, session_id: str) -> Optional[dict]:
        key = f"session:{session_id}"
        data = self.client.hgetall(key)
        if data:
            # 刷新 TTL
            self.client.expire(key, self.session_ttl)
            return {k.decode(): json.loads(v) for k, v in data.items()}
        return None

    def update_session(self, session_id: str, memory_type: str, data: dict):
        """更新会话中的某个记忆字段"""
        key = f"session:{session_id}"
        self.client.hset(
            key,
            memory_type,  # e.g., "dialogue_history", "entities", "state"
            json.dumps(data)
        )
        self.client.expire(key, self.session_ttl)

    def add_dialogue_turn(self, session_id: str, turn: dict):
        """追加对话轮次（使用 List 结构）"""
        key = f"dialogue:{session_id}"
        self.client.rpush(key, json.dumps(turn))
        self.client.ltrim(key, -100, -1)  # 最多保留 100 轮
        self.client.expire(key, self.session_ttl)
```

### 3.3 STM 的 Eviction 策略

Redis 虽然是内存级速度，但空间有限。短期记忆的淘汰（Eviction）策略：

- **TTL 过期**：30 分钟无交互自动清理。
- **数量上限**：每个用户最多 50 个活跃 Session，超限时淘汰最旧的。
- **重要性标记**：标记为"重要"的短期记忆（如用户明确说"记住这个"）获得更长的 TTL（24 小时）。

### 3.4 STM → LTM 的晋升阈值

短期记忆不会永远留在 STM 层级。当满足以下条件之一时，晋升为长期记忆：

```python
def should_promote_to_ltm(memory: dict) -> bool:
    """
    判断是否晋升短期记忆为长期记忆：
    1. 被用户明确要求记住
    2. 跨会话出现超过 N 次
    3. 重要性评分 > 阈值 (详见 7.5 节)
    """
    if memory.get("user_flagged"):          # 用户要求记住
        return True
    if memory.get("cross_session_count", 0) >= 3:  # 跨会话出现
        return True
    if memory.get("importance_score", 0) >= 0.7:   # 重要性阈值
        return True
    return False
```

## 四、Long-Term Memory（长期记忆）

### 4.1 定义与技术选型

Long-Term Memory 是 Agent 的**持久化知识库**，跨越会话边界，存储事实、用户画像、历史事件等需要长期保留的信息。

典型技术选型：

| 技术 | 核心能力 | 适用场景 |
|------|----------|----------|
| **向量数据库（Milvus/Qdrant/Pinecone）** | Embedding 语义检索 | 非结构化记忆（事件描述、事实文本） |
| **PostgreSQL + pgvector** | 结构化 + 向量混合查询 | 需要 SQL 过滤的用户画像 |
| **SQLite + sqlite-vec** | 轻量级嵌入 | 单机/边缘部署 |
| **Neo4j（图数据库）** | 关系推理 | 实体关系复杂的记忆网络 |

详细的向量数据库选型对比见 [第 3 章：向量数据库](../03-数据基础/)。

### 4.2 LTM 的存储结构

长期记忆的核心是 **(内容, 元数据, Embedding)** 三元组：

```python
class LongTermMemory:
    """
    长期记忆：基于向量数据库的持久化存储
    """
    def __init__(self, vector_db, embedding_model):
        self.db = vector_db
        self.embed = embedding_model

    def store(self, content: str, metadata: dict) -> str:
        """存储一条长期记忆"""
        embedding = self.embed.encode(content)
        memory_id = self.db.insert(
            vector=embedding,
            payload={
                "content": content,
                "metadata": metadata,
                "created_at": time.time(),
                "access_count": 0,
                "last_access": time.time(),
            }
        )
        return memory_id

    def retrieve(self, query: str, top_k: int = 5, filters: dict = None) -> list:
        """语义检索相关记忆"""
        query_embedding = self.embed.encode(query)
        results = self.db.search(
            vector=query_embedding,
            top_k=top_k,
            filters=filters
        )
        for r in results:
            r.payload["access_count"] += 1
            r.payload["last_access"] = time.time()
        return results
```

### 4.3 三级存储的完整交互流

```
用户消息
    │
    ▼
┌─────────────────────────────────────────────┐
│  1. Working Memory 拼接                      │
│     - System Prompt (固定)                   │
│     - 当前对话历史 (STM 提供)                │
│     - 检索到的长期记忆 (LTM 提供)            │
│     → 组装成最终 Prompt → LLM 推理           │
└─────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────┐
│  2. LLM 响应解析                             │
│     - 提取新实体/事实                        │
│     - 识别用户意图变更                       │
│     - 检测需要记忆的关键信息                 │
└─────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────┐
│  3. 记忆写入                                 │
│     ├─→ STM: 追加对话轮次到 Redis            │
│     ├─→ LTM: 重要的新事实写入向量 DB          │
│     └─→ WM:  更新 Token Budget 统计          │
└─────────────────────────────────────────────┘
```

## 五、三层记忆的对比

| 维度 | Working Memory | Short-Term Memory | Long-Term Memory |
|------|---------------|-------------------|------------------|
| **存储介质** | LLM 上下文窗口 | Redis / 内存缓存 | 向量数据库 / SQL |
| **容量** | 受限（4K-200K tokens） | 中等（GB 级） | 大（TB 级） |
| **持久性** | 无（每次重建） | TTL 过期 | 持久化 |
| **访问速度** | 随 Prompt 一起推理 | <1ms | 10-100ms（含 Embedding） |
| **成本** | 极高（按 token 计费） | 低 | 中（存储 + 检索） |
| **生命周期** | 单次推理 | 会话期间（分钟-小时） | 跨会话（天-月-年） |
| **数据结构** | Plain Text | JSON / 序列化对象 | 向量 + 结构化元数据 |

## 关键概念速查

| 术语 | 解释 |
|------|------|
| **Working Memory** | LLM 上下文窗口内的可见信息，使用 Token Budget 管理 |
| **Short-Term Memory** | 会话级 Redis 缓存，TTL 过期自动清理 |
| **Long-Term Memory** | 持久化向量数据库，跨会话检索 |
| **Token Budget** | 上下文窗口的各部分 Token 配额分配策略 |
| **STM → LTM 晋升** | 满足重要性/重复/用户标记条件时触发的记忆转存 |
| **Eviction** | 短期记忆空间不足时的淘汰机制 |
