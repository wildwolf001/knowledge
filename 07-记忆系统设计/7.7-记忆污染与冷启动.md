# 7.7 记忆污染与冷启动——Upsert 而非 Append、初始画像推断、垃圾记忆清理

> 记忆系统最危险的陷阱不是"记不住"，而是"记错了"。**记忆污染（Memory Pollution）** 是 Agent 记忆系统中的累积性错误——一条错误信息被写入后，会在后续对话中被反复检索、确认并强化，最终变成"事实"。与之对应的是**冷启动（Cold Start）**问题——当 Agent 第一次接触用户时，没有任何历史记忆可用，如何快速建立初始画像？

---

## 一、记忆污染：定义与成因

### 1.1 什么是记忆污染？

记忆污染是指 Agent 的长期记忆中包含了**错误、过时、矛盾或无关的信息**，导致其在后续对话中持续输出错误结果。

```
污染传播链：

第 1 轮: 用户说"我今年 35 岁" → Agent 存入 "用户年龄: 35"
第 2 轮: Agent 输出"根据您的年龄 35 岁..." → 用户未纠正
第 3 轮: LLM 幻觉产生 "用户出生在 1990 年" → 存入 LTM
第 4 轮: 检索找到 "出生在 1990" → Agent 用这个信息回答问题
第 5 轮: 两条矛盾记忆引起混乱 → Agent 采信了错误的那条（因为更新的）
                                          ↑ 污染固化！
```

**核心问题**：记忆系统没有区分"用户说的"、"Agent 推断的"、"LLM 幻觉的"。错误的源头可能是：
1. **LLM 幻觉**：Agent 在总结对话时编造了不存在的细节。
2. **用户错误**：用户提供了不准确的信息（有意或无意）。
3. **上下文污染**：检索到的其他错误记忆影响了当前推理（见 8.7 节 RAG 污染）。
4. **过期信息**：用户的信息已变化但旧记忆未被更新。

### 1.2 污染的类型

| 污染类型 | 描述 | 案例 |
|---------|------|------|
| **事实污染** | 存储了与客观事实不符的信息 | "地球是平的" |
| **过时污染** | 曾经正确但现在已变化的信息 | 用户电话号码已更换 |
| **矛盾污染** | 两条及以上相互矛盾的记忆 | 年龄同时记录为 35 和 40 |
| **噪声污染** | 无关/无意义的记忆占据空间 | "用户今天说了句'今天天气不错'" |
| **幻觉污染** | LLM 编造的信息被当作真实 | "用户曾在 Google 工作"（实际没有） |

## 二、Upsert 而非 Append

### 2.1 Append 的问题

大多数初学者设计的记忆系统是 **Append-only（只追加）** 的：

```python
# ❌ 错误示范：只追加不更新
def append_memory(memory_store, new_memory):
    """Append-only 模式：每次写入都追加一条新记录"""
    memory_store.insert(new_memory)
    # 问题：同一实体（如"用户所在公司"）每次提及都新增一行
    # 结果：10 次提及 → 10 条记录，可能互相矛盾
```

Append-only 的三个致命问题：

```
问题 1: 同一事实多条矛盾记录
  [{ "公司": "腾讯" }, { "公司": "阿里" }, { "公司": "腾讯" }]
  → Agent 应该用哪条？时间最新的？频次最高的？
  → 如果用户三次提了三家不同公司，且都是"当前公司"？

问题 2: 无法区分"新增"和"更新"
  Append 模式下，"用户换了新手机号"和"新增了备用手机号"
  在存储格式上完全无法区分

问题 3: 去重越来越难
  100 条记忆里可能有 30 条在说同一件事
  每次检索要先做去重聚合，浪费 Token 和时间
```

### 2.2 Upsert 的正确做法

**Upsert = Update + Insert**。对于同一实体/事实，不追加新记录，而是**更新已有记录**：

```python
class UpsertMemory:
    """
    Upsert 模式：更新或插入
    核心思想：每个实体/事实只有一条权威记录
    """
    def __init__(self, db):
        self.db = db

    def upsert_fact(self, entity: str, attribute: str, value: any,
                    source: str = "user", confidence: float = 1.0):
        """
        更新或插入一个事实。
        使用 (entity, attribute) 作为唯一键：
        - 如果已存在 → 更新 value, confidence, timestamp
        - 如果不存在 → 插入新记录
        """
        key = f"{entity}:{attribute}"
        existing = self.db.get(key)

        if existing:
            # 存在 → 更新（不是新增！）
            old_value = existing["value"]
            old_confidence = existing["confidence"]

            # 冲突检测
            if old_value != value:
                self._handle_conflict(
                    entity, attribute,
                    old_value, old_confidence,
                    value, confidence
                )
            else:
                # 相同值 → 增强置信度
                new_confidence = min(
                    old_confidence + confidence * 0.1,
                    1.0
                )
                self.db.update(key, {
                    "value": value,
                    "confidence": new_confidence,
                    "updated_at": time.time(),
                    "source": source,
                })
        else:
            # 不存在 → 插入
            self.db.insert({
                "_key": key,
                "entity": entity,
                "attribute": attribute,
                "value": value,
                "confidence": confidence,
                "source": source,
                "created_at": time.time(),
                "updated_at": time.time(),
                "version": 1,
            })

    def _handle_conflict(self, entity, attribute, old_val, old_conf,
                         new_val, new_conf):
        """
        冲突处理策略：
        默认是"新信息置信度 > 旧信息置信度 × 1.2 → 更新，否则保留"
        """
        if new_conf > old_conf * 1.2:
            # 新信息更可靠 → 更新
            self.db.update(f"{entity}:{attribute}", {
                "value": new_val,
                "confidence": new_conf,
                "updated_at": time.time(),
                "previous_value": old_val,  # 保留历史
                "version": self.db.get(f"{entity}:{attribute}")["version"] + 1,
            })
        else:
            # 旧信息仍更可靠 → 不更新，但记录有分歧
            # 可选：创建一条"低置信度候选记录"
            self.db.insert({
                "_key": f"{entity}:{attribute}:candidate",
                "entity": entity,
                "attribute": attribute,
                "value": new_val,
                "confidence": new_conf,
                "source": "conflicting",
                "status": "candidate",
            })
```

### 2.3 Append vs Upsert 对比

| 维度 | Append | Upsert |
|------|--------|--------|
| **存储方式** | 每次新的写入都追加一条 | 同一实体只保留一条权威记录 |
| **存储量** | 线性增长 | 趋于稳定 |
| **冲突处理** | 不处理（多条矛盾共存） | 有策略地合并或更新 |
| **信息更新** | 无法区分新增 vs 更新 | 显式支持版本和更新语义 |
| **检索难度** | 需要聚合去重 | 直接获取最新权威值 |
| **适合场景** | 不可变日志（如对话轮次） | 可变事实（如用户信息、偏好） |

### 2.4 什么时候应该 Append？

Upsert 并非万能。以下场景仍然应该 Append：

1. **对话轮次记录**（Episodic Memory）：每个对话轮次是不可变的事件日志，应该追加。
2. **操作审计日志**：每次 Agent 做了什么操作，需要保留完整历史。
3. **用户行为序列**：用户在不同时间点的行为，需要保留时间线。

**黄金法则**：
- **事实（Semantic Memory）→ Upsert**：每个事实只有一条权威记录
- **事件（Episodic Memory）→ Append**：每个事件是一条不可变日志
- **技能（Procedural Memory）→ Update**：技能模式随实践优化

## 三、垃圾记忆清理

### 3.1 清理策略

即使有了 Upsert，记忆系统仍会积累低质量记忆。需要定期清理：

```python
class MemoryJanitor:
    """
    记忆清理器：定期清理低质量记忆
    """
    def __init__(self, memory_store, scoring_system):
        self.memory_store = memory_store
        self.scoring = scoring_system
        self.cleanup_thresholds = {
            "min_confidence": 0.2,       # 置信度过低
            "max_age_days": 180,          # 半年以上未访问
            "max_noise_score": 0.3,       # 噪声评分过高
            "max_contradictions": 3,      # 被矛盾次数过多
        }

    def cleanup_cycle(self):
        """执行一轮清理"""
        all_memories = self.memory_store.get_all()
        cleaned_count = 0

        for mem_id, memory in all_memories.items():
            reasons = []

            # 检查置信度
            if memory.get("confidence", 1.0) < self.cleanup_thresholds["min_confidence"]:
                reasons.append("low_confidence")

            # 检查时效性
            age_days = (time.time() - memory.get("updated_at", 0)) / 86400
            if age_days > self.cleanup_thresholds["max_age_days"]:
                if memory.get("importance", 0.5) < 0.3:  # 除非很重要
                    reasons.append("too_old")

            # 综合评分下限
            score = self.scoring.compute_score(memory)
            if score < 0.1:
                reasons.append("below_decay_threshold")

            # 执行清理
            if reasons:
                self._handle_cleanup(mem_id, memory, reasons)
                cleaned_count += 1

        return cleaned_count

    def _handle_cleanup(self, mem_id, memory, reasons):
        """根据记忆类型和清理原因做不同处理"""
        memory_type = memory.get("type", "unknown")

        if memory_type == "temporal":
            # 时间敏感信息（如价格、活动日期）→ 直接删除
            self.memory_store.delete(mem_id)

        elif memory_type == "fact":
            # 事实信息 → 降级为候选（可恢复）
            self.memory_store.update(mem_id, {
                "status": "archived",
                "archive_reason": ",".join(reasons),
                "archived_at": time.time(),
            })

        else:
            # 一般信息 → 直接删除
            self.memory_store.delete(mem_id)
```

### 3.2 矛盾检测与修复

```python
def detect_contradictions(memory_store) -> list:
    """
    检测长期记忆中的矛盾
    返回需要人工审查的矛盾对
    """
    # 按实体分组
    entity_groups = memory_store.group_by_entity()

    contradictions = []
    for entity, facts in entity_groups.items():
        # 检查同一属性的不同值
        attr_values = {}
        for fact in facts:
            key = (entity, fact["attribute"])
            if key not in attr_values:
                attr_values[key] = []
            attr_values[key].append(fact)

        for (ent, attr), records in attr_values.items():
            values = set(r["value"] for r in records)
            if len(values) > 1:
                contradictions.append({
                    "entity": ent,
                    "attribute": attr,
                    "conflicting_values": [
                        {"value": r["value"], "confidence": r["confidence"],
                         "timestamp": r["updated_at"]}
                        for r in records
                    ]
                })

    return contradictions
```

## 四、冷启动（Cold Start）

### 4.1 冷启动问题

冷启动指 Agent 在第一次接触用户时，LTM 中没有任何该用户的记忆。这导致：
- Agent 无法个性化回答
- 需要大量对话才能建立基础画像
- 首次交互体验差

### 4.2 初始画像推断

**策略一：显式引导对话**

```python
class ColdStartHandler:
    """
    冷启动处理：快速建立用户初始画像
    """
    def __init__(self, llm, memory_system):
        self.llm = llm
        self.memory = memory_system

    def handle_first_interaction(self, user_message: str) -> dict:
        """
        第一次交互：提取初始画像
        """
        # 使用 LLM 从第一条消息中推断用户信息
        inference_prompt = f"""
        用户的第一条消息: "{user_message}"

        请从中推断以下信息（尽量推断，不确定的标记为 low_confidence）：
        1. user_name: 用户名（如果有）
        2. role: 角色（工程师/产品经理/学生...）
        3. domain: 领域（技术/金融/医疗...）
        4. intent: 用户的主要意图
        5. language: 使用的语言
        6. expertise_level: 专业水平（beginner/intermediate/expert）
        7. inferred_traits: 推断的性格特征（如 detail_oriented）

        格式：JSON
        """

        inferred_profile = self.llm.generate(inference_prompt)

        # 写入记忆系统（标记为 low_confidence）
        for key, value in inferred_profile.items():
            if value:  # 只存非空值
                self.memory.upsert_fact(
                    entity="user_inferred",
                    attribute=key,
                    value=value,
                    source="cold_start_inference",
                    confidence=0.3  # 低置信度
                )

        return inferred_profile
```

**策略二：主动提问策略**

当 LLM 推断的信息置信度过低时，Agent 应主动提问以填补关键空白：

```python
def generate_onboarding_questions(inferred_profile: dict, important_gaps: list) -> list:
    """
    生成引导性问题，填补用户画像的关键空白
    """
    questions = []

    if "role" not in inferred_profile or inferred_profile.get("confidence_role", 0) < 0.5:
        questions.append("为了更好地帮助您，可以告诉我您的角色或所在的行业吗？")

    if "domain" not in inferred_profile:
        # 根据用户消息判断领域
        questions.append("您主要关注哪个领域的问题？")

    # 最多 2 个问题，避免首次交互过度提问
    return questions[:2]
```

**策略三：从公开信息推断**

```python
def infer_from_email_domain(email: str) -> dict:
    """
    从邮箱域名推断组织信息
    """
    domain = email.split("@")[-1]
    inferences = {}

    # 企业邮箱模式
    enterprise_domains = {
        "acmecorp.com": {"company": "AcmeCorp", "industry": "technology"},
        "bankofexample.com": {"company": "BankOfExample", "industry": "finance"},
    }
    if domain in enterprise_domains:
        inferences.update(enterprise_domains[domain])
        inferences["confidence"] = 0.6  # 中等置信度
    else:
        # 通用推断
        if domain.endswith(".edu"):
            inferences["role"] = "academic"
            inferences["confidence"] = 0.4
        elif domain.endswith(".gov"):
            inferences["role"] = "government"
            inferences["confidence"] = 0.4

    return inferences
```

### 4.3 置信度驱动的画像更新

初始画像的置信度较低（通常 0.3-0.5），需要随着交互逐步完善：

```python
def update_profile_confidence(memory_system, entity: str, attribute: str,
                               user_corrected: bool = False):
    """
    用户确认或修正信息时，提升对应的置信度
    """
    if user_corrected:
        # 用户主动修正 → 大幅提升置信度
        memory_system.update_confidence(
            entity, attribute,
            delta=+0.4
        )
    else:
        # 信息被后续对话印证 → 小幅提升
        memory_system.update_confidence(
            entity, attribute,
            delta=+0.1
        )
```

## 五、最佳实践总结

### 5.1 写入原则

```
┌────────────────────────────────────────────────┐
│  记忆写入决策树                                 │
│                                                  │
│  新信息到达                                      │
│      │                                           │
│      ▼                                           │
│  是什么类型？                                     │
│      │                                           │
│   ├─ 事实（Semantic）→ Upsert（更新或插入）       │
│   │    ↓                                         │
│   │  冲突检查 → 置信度比较 → 更新或标记候选      │
│   │                                              │
│   ├─ 事件（Episodic）→ Append（追加）             │
│   │    ↓                                         │
│   │  重要性过滤 → 仅保留重要性 > 0.3 的事件      │
│   │                                              │
│   └─ 推断（LLM Generated）→ 标记为 low_confidence │
│        ↓                                         │
│      需要后续交互确认 → 用户修正后升级置信度     │
└──────────────────────────────────────────────────┘
```

### 5.2 关键参数配置

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `初始置信度` | 0.3 | LLM 推断的信息的初始置信度 |
| `用户确认提升` | +0.4 | 用户主动确认/修正时的置信度增量 |
| `印证提升` | +0.1 | 后续对话自然印证时的置信度增量 |
| `清理置信阈值` | 0.2 | 低于此值的记忆被清理 |
| `矛盾检测周期` | 24h | 全量矛盾检测的执行间隔 |
| `冷启动问题数` | ≤2 | 首次交互主动提问的上限 |

## 关键概念速查

| 术语 | 解释 |
|------|------|
| **记忆污染** | 长期记忆中的错误/过时/矛盾信息导致的系统性偏差 |
| **Upsert** | Update + Insert，同一实体只保留一条权威记录并更新 |
| **Append** | 只追加不更新，适合事件日志但不适合事实信息 |
| **冷启动** | Agent 首次接触用户时无历史记忆的状态 |
| **初始画像推断** | 从第一条用户消息中 LLM 提取用户特征的策略 |
| **置信度驱动** | 所有推断信息附带置信度，随交互逐步修正和提升 |
| **记忆清理** | 定期扫描并删除低置信度、过期、矛盾记忆的维护操作 |
| **污染固化** | 错误信息被反复检索使用后变得难以清除的过程 |

*下一节：08 — 检索增强生成（RAG）*
