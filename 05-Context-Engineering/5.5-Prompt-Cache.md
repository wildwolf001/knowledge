# 5.5 Prompt Cache

> Static/Dynamic 分离、工具 Schema 排序保证缓存键稳定、全局缓存作用域（跨用户共享）

## Prompt Cache 的核心原理

Prompt Cache 是一种**端侧缓存机制**，其核心思想是：LLM 推理过程中，输入 token 的 Transformer 计算（特别是自注意力机制中的 Key 和 Value 矩阵）在上下文的**前缀部分**是高度可复用的。如果上下文的开头部分在多次推理之间保持不变，那么这些前缀的 KV（Key-Value，键值）缓存可以跨推理请求复用，从而避免重复计算。

这不仅是"减少传输数据量"的网络优化，而是**直接跳过大部分 Transformer 计算**的结构性优化。其加速效果远高于常规的请求缓存。

### 工作原理可视化

```
无缓存: 每次请求全部计算
┌─────────────────────────────────────────────────┐
│ 请求 #1: [系统指令][工具][记忆][检索][用户输入]      │
│          │       │    │    │    │                │
│          ▼       ▼    ▼    ▼    ▼                │
│          ├───────┬────┬────┬────────────────►    │
│          全部计算 Transformer                         │
│                                                   │
│ 请求 #2: [系统指令][工具][记忆][检索][用户输入']     │
│          │       │    │    │    │                │
│          ▼       ▼    ▼    ▼    ▼                │
│          ├───────┬────┬────┬────────────────►    │
│          又全部计算 Transformer (浪费)               │
└─────────────────────────────────────────────────┘

有 Prompt Cache: 重复前缀跳过计算
┌─────────────────────────────────────────────────┐
│ 请求 #1: [系统指令][工具][记忆][检索][用户输入]      │
│          │       │    │    │                     │
│          └───┬───┴────┴────┘                     │
│              ▼                                   │
│          计算并缓存 KV ─────────►  Cache Pool    │
│              ├─────────────────►  Final Calc     │
│                                                   │
│ 请求 #2: [系统指令][工具][记忆][检索][用户输入']     │
│          │       │    │    │                     │
│          └───┬───┴────┴────┘                     │
│              ▼                                   │
│          [Cache Hit!] ──────────► 复用缓存 KV     │
│              ├─────────────────► 仅计算用户输入    │
│                                                   │
│ 加速比: 仅用户输入部分需要计算 (通常 80-95% 跳过)   │
└─────────────────────────────────────────────────┘
```

### 为什么这很重要

假设一个 Agent 系统每次推理发送 20,000 tokens（系统指令 + 工具定义 + 历史摘要），其中只有 500 tokens 是变化的用户输入。Prompt Cache 使得：

- **计算量**: 从处理 20,500 tokens 降至处理 500 tokens（节省 97.6%）
- **延迟**: 首 token 时间（Time to First Token, TTFT）从 ~1.5s 降至 ~0.1s
- **吞吐量**: 单节点可服务更多并发请求

## Static/Dynamic 分离

Static/Dynamic 分离是设计高效 Prompt Cache 的核心原则。

### Static 层

**定义**: 在多次推理之间不发生变化的上下文前缀。

**典型内容**:
- 系统指令（版本化、不常变更）
- 高频工具定义 Schema（名称、描述、参数结构）
- 固定的角色设定和行为规则
- 不基于用户或轮次变化的静态示例

**缓存策略**:

```
Static 层缓存管理
                                        
┌─────────────────────────────────────────────┐
│              Static Cache Pool              │
│                                             │
│  Cache Slot #1: system_v1                   │
│  Hash: a1b2c3d4e5                           │
│  Size: 3,200 tokens                         │
│  TTL: 24 hours / until invalidation         │
│  Hit Rate: 99.2%                            │
│                                             │
│  Cache Slot #2: tools_high_frequency        │
│  Hash: f6g7h8i9j0                           │
│  Size: 5,100 tokens                         │
│  TTL: 1 hour / on schema change             │
│  Hit Rate: 87.5%                            │
│                                             │
│  Cache Slot #3: behavior_rules              │
│  Hash: k1l2m3n4o5                           │
│  Size: 1,800 tokens                         │
│  TTL: 24 hours / on config change           │
│  Hit Rate: 98.1%                            │
└─────────────────────────────────────────────┘
```

### Dynamic 层

**定义**: 每次推理可能发生变化的上下文部分。

**典型内容**:
- 用户输入
- 当前轮次的对话历史（新增轮次）
- 实时检索的文档
- 记忆提取结果
- 当前步骤的工具调用结果

**缓存策略**: Dynamic 层通常**不缓存**或仅做**短时缓存**（秒级），但可以通过预计算加速。例如：用户输入的前缀部分如果固定（如模板化的查询格式），其 KV 计算也可以缓存。

```python
class PromptCacheManager:
    """
    Prompt Cache 管理器 - Static/Dynamic 分离
    
    核心逻辑:
    1. 将上下文编码为 (static_hash, dynamic_suffix)
    2. static_hash 用作 KV 缓存键
    3. 仅计算 dynamic_suffix 的注意力
    """
    
    def __init__(self, cache_ttl: int = 3600):
        self.cache = {}  # hash -> (kv_cache, timestamp)
        self.cache_ttl = cache_ttl  # 秒
        self.stats = {"hits": 0, "misses": 0}
    
    def build_cache_key(self, static_content: str) -> str:
        """
        生成静态内容的缓存键
        
        要求:
        - 确定性: 相同内容始终产生相同键
        - 对微小变化敏感: 任一字符变化 → 不同键
        """
        import hashlib
        return hashlib.sha256(static_content.encode("utf-8")).hexdigest()
    
    def split_context(self, context: str, 
                      dynamic_boundary: str = "=== USER INPUT ===") -> tuple:
        """
        将上下文分为 static 和 dynamic 两部分
        
        Args:
            context: 完整上下文
            dynamic_boundary: 静态和动态部分的分隔标记
            
        Returns:
            (static_part, dynamic_part)
        """
        if dynamic_boundary in context:
            parts = context.split(dynamic_boundary, 1)
            return (parts[0], dynamic_boundary + parts[1])
        return (context, "")
    
    def get_or_compute(self, cache_key: str) -> object:
        """获取缓存或返回 None（表示需要计算）"""
        if cache_key in self.cache:
            entry = self.cache[cache_key]
            if time.time() - entry["timestamp"] < self.cache_ttl:
                self.stats["hits"] += 1
                return entry["kv_cache"]
        
        self.stats["misses"] += 1
        return None
    
    def set_cache(self, cache_key: str, kv_cache: object):
        """存储 KV 缓存"""
        self.cache[cache_key] = {
            "kv_cache": kv_cache,
            "timestamp": time.time()
        }
    
    def invalidate(self, cache_key: str):
        """手动失效缓存"""
        if cache_key in self.cache:
            del self.cache[cache_key]
    
    def get_hit_rate(self) -> float:
        total = self.stats["hits"] + self.stats["misses"]
        return self.stats["hits"] / total if total > 0 else 0.0
```

## 工具 Schema 排序与缓存键稳定性

这是 Prompt Cache 实现中最隐蔽却最关键的技术细节。

### 问题描述

工具定义（Tool Schema）是 Agent 上下文的主要组成部分之一。当 Agent 拥有 20 个工具时，这些工具的 Schema 在上下文中占据约 15,000-20,000 tokens。理想情况下，工具 Schema 属于 Static 层，应该被缓存。

**但是**，如果工具 Schema 在每次推理中**以不同顺序**排列，其拼接后的字符串内容就会不同，导致缓存键（Cache Key）变化，缓存失效。

### 为什么顺序会变化

在未排序的情况下，工具 Schema 的排列顺序受多种不确定因素影响：

1. **工具注册顺序**: 不同环境可能以不同顺序加载工具
2. **并发请求**: 多线程环境下，工具列表的枚举顺序不确定
3. **懒加载顺序**: 前一步推理可能改变了工具的加载顺序
4. **Schema 变更时间**: 个别工具的 Schema 更新时间点不同

### 排序保证缓存键稳定的原理

```python
import json

# ❌ 不稳定: 每次可能以不同顺序序列化
tools_unsorted = {
    "search_tool": {"name": "search", "description": "搜索网络"},
    "calc_tool": {"name": "calculator", "description": "数学计算"},
    "weather_tool": {"name": "get_weather", "description": "查询天气"}
}
# 序列化结果可能为:
# '{"calc_tool": ..., "search_tool": ..., "weather_tool": ...}'
# 或
# '{"search_tool": ..., "weather_tool": ..., "calc_tool": ...}'
# 不同顺序 → 不同缓存键 → 缓存失效

# ✅ 稳定: 确定性排序
def stable_tool_hash(tools: dict) -> str:
    """
    生成稳定的工具 Schema 缓存键
    
    原理:
    1. 按工具名称字母排序
    2. 确保同一工具内容的表示方式完全一致
    3. 使用确定性哈希算法
    """
    # 1. 按名称排序（关键步骤）
    sorted_names = sorted(tools.keys())
    
    # 2. 按排序后的顺序构建有序列表
    sorted_tools = []
    for name in sorted_names:
        schema = tools[name]
        # 对每个工具的 Schema 内部也做键排序
        sorted_tools.append(json.dumps(schema, sort_keys=True))
    
    # 3. 合并为完整字符串
    canonical_str = "|||".join(sorted_tools)
    
    # 4. 哈希
    import hashlib
    return hashlib.sha256(canonical_str.encode()).hexdigest()

# 即使多次调用，只要工具内容不变，哈希值就一致
hash_1 = stable_tool_hash(tools_unsorted)
hash_2 = stable_tool_hash(tools_unsorted)
assert hash_1 == hash_2  # ✓ 始终通过
```

### 排序的"蝴蝶效应"

工具 Schema 排序不仅影响缓存键，还通过以下机制影响缓存命中率：

```
缓存命中链
                                        
工具 Schema 未排序:
  ┌──────────┐   ┌──────────┐   ┌──────────┐
  │ 请求 #1  │   │ 请求 #2  │   │ 请求 #3  │
  │ 序: A,B,C│   │ 序: B,A,C│   │ 序: A,C,B│
  └────┬─────┘   └────┬─────┘   └────┬─────┘
       │              │              │
       ▼              ▼              ▼
  hash(ABC)      hash(BAC)      hash(ACB)
       │              │              │
       └── MISS ──┬──┘              │
                  └────── MISS ─────┘
  命中率: 0% ── 每次请求都缓存未命中

工具 Schema 已排序:
  ┌──────────┐   ┌──────────┐   ┌──────────┐
  │ 请求 #1  │   │ 请求 #2  │   │ 请求 #3  │
  │ 序: A,B,C│   │ 序: A,B,C│   │ 序: A,B,C│
  └────┬─────┘   └────┬─────┘   └────┬─────┘
       │              │              │
       ▼              ▼              ▼
  hash(ABC) === hash(ABC) === hash(ABC)
       │              │              │
       └──── HIT ─────┼──── HIT ─────┘

```

## 全局缓存作用域

Prompt Cache 不仅可以缓存单个用户的重复前缀，还可以**跨用户共享**——因为 system prompt 和高频工具 Schema 对所有用户是一致的。

### 三级缓存作用域

```python
class CacheScope:
    """三级缓存作用域"""
    
    @staticmethod
    def global_scope():
        """
        全局缓存: 跨所有用户共享
        
        适用: 系统指令、全局工具定义、公共知识
        特点: 
        - 缓存键不含用户信息
        - TTL 最长（小时-天）
        - 缓存池最大
        """
        return {
            "scope": "global",
            "key_prefix": "",
            "ttl": 86400,  # 24小时
            "max_entries": 1000
        }
    
    @staticmethod
    def user_scope(user_id: str):
        """
        用户级缓存: 单用户内共享
        
        适用: 用户偏好、个性化工具配置
        特点:
        - 缓存键含用户 ID
        - TTL 中等（分钟-小时）
        - 缓存池中等
        """
        return {
            "scope": "user",
            "key_prefix": f"user:{user_id}",
            "ttl": 3600,  # 1小时
            "max_entries": 100
        }
    
    @staticmethod
    def session_scope(session_id: str):
        """
        会话级缓存: 单次会话内共享
        
        适用: 对话历史前缀、当前轮次状态
        特点:
        - 缓存键含会话 ID
        - TTL 短（秒-分钟）
        - 缓存池小
        """
        return {
            "scope": "session",
            "key_prefix": f"session:{session_id}",
            "ttl": 300,  # 5分钟
            "max_entries": 20
        }
```

全局缓存 ──> 用户缓存 ──> 会话缓存

## 缓存破裂检测

**缓存破裂（Cache Invalidation）**是指当静态内容发生变化时，需要使对应缓存失效的机制。Prompt Cache 中最危险的场景是：**缓存已过时但未失效，导致模型使用旧上下文生成回答**。

```python
class CacheInvalidationDetector:
    """
    缓存破裂检测器
    
    检测策略:
    1. 版本号对比
    2. 内容哈希对比
    3. 变更订阅通知
    """
    
    def __init__(self):
        # 已缓存内容的版本号
        self.cached_versions = {}
        # 最新版本号
        self.current_versions = {
            "system_prompt": "v2.1.3",
            "tool_schemas": "v1.0.5",
            "behavior_rules": "v3.0.0"
        }
    
    def is_cache_valid(self, cache_key: str, 
                       content_type: str) -> bool:
        """检查缓存是否有效"""
        if cache_key not in self.cached_versions:
            return False
        
        cached_version = self.cached_versions[cache_key]
        current_version = self.current_versions.get(content_type, "v0.0.0")
        
        return cached_version >= current_version  # 语义版本对比
    
    def on_content_change(self, content_type: str, 
                          new_version: str):
        """
        内容变更时主动通知
        
        调用场景:
        - 系统指令更新后
        - 工具 Schema 变更后
        - 行为规则修改后
        """
        self.current_versions[content_type] = new_version
        # 触发所有相关缓存的破裂
        invalid_count = 0
        for key, ver in self.cached_versions.items():
            if ver < new_version:
                invalid_count += 1
        
        return {"invalidated": invalid_count}
```

## Prompt Cache 的局限性

1. **前缀依赖性**: Prompt Cache 只对上下文**前缀**有效。如果变化发生在开头附近（如系统指令变化），后方的所有缓存都失效。
2. **内存消耗**: KV 缓存占用大量 GPU 显存。20,000 tokens 的 KV 缓存约占用 2-4 GB。
3. **缓存污染**: 低质量请求产生的 KV 缓存仍然占用空间。
4. **缓存一致性问题**: 全局缓存在大规模分布式部署中需要协调更新。

## 代码示例：完整 Prompt Cache 集成

```python
class AgentWithPromptCache:
    """
    集成了 Prompt Cache 的 Agent
    """
    
    def __init__(self, model="claude-4", tools=None):
        self.model = model
        self.tools = tools or {}
        self.static_system = self._build_system_prompt()
        self.cache_manager = PromptCacheManager()
        
        # 构建并缓存静态部分
        self._cache_static_prefix()
    
    def _build_system_prompt(self) -> str:
        """构建系统指令（Static 部分）"""
        return """
        你是一个 AI Agent 助手。你的行为规则:
        1. 始终用中文回答
        2. 在调用工具前说明理由
        3. 如果信息不足，询问用户
        """
    
    def _cache_static_prefix(self):
        """预先计算并缓存静态前缀"""
        # 对工具 Schema 排序
        sorted_tools = dict(sorted(self.tools.items()))
        static_content = self.static_system + json.dumps(sorted_tools, sort_keys=True)
        cache_key = self.cache_manager.build_cache_key(static_content)
        self.cache_key = cache_key
    
    def run(self, user_input: str, context: dict = None) -> str:
        """执行一次 Agent 推理"""
        # 构建完整上下文
        full_context = self._build_context(user_input, context)
        
        # 检查是否有缓存
        cached_kv = self.cache_manager.get_or_compute(self.cache_key)
        
        if cached_kv:
            # 缓存命中：仅计算动态部分
            result = self._inference_with_cache(
                cached_kv, 
                user_input, 
                context
            )
            print(f"[Cache HIT] 跳过静态内容计算")
        else:
            # 缓存未命中：全部计算
            result = self._inference_full(full_context)
            # 存储 KV 缓存
            self.cache_manager.set_cache(self.cache_key, self._extract_kv(full_context))
            print(f"[Cache MISS] 完整计算")
        
        return result
    
    def _build_context(self, user_input: str, context: dict) -> str:
        """构建完整上下文"""
        sorted_tools = dict(sorted(self.tools.items()))
        return (
            self.static_system 
            + json.dumps(sorted_tools, sort_keys=True) 
            + (context.get("memory", "") if context else "")
            + user_input
        )
    
    def _inference_full(self, context: str) -> str:
        """完整的模型推理"""
        # 实际调用 LLM API
        return f"处理上下文 ({len(context)} tokens)"
    
    def _inference_with_cache(self, kv_cache, user_input: str, context: dict) -> str:
        """利用缓存做增量推理"""
        # 仅处理动态部分
        dynamic_part = user_input + (context.get("memory", "") if context else "")
        return f"增量推理 ({len(dynamic_part)} tokens, 缓存跳过 {len(self.cache_key)} tokens)"
    
    def _extract_kv(self, context: str) -> object:
        """模拟提取 KV 缓存"""
        return {"prefix": context[:100], "kv": "..."}
```

## 六、2026年演进：从缓存静态内容到动态按需加载

### 6.1 MCP Tool Search：Prompt Cache思想在工具定义层的延伸

2026年兴起的MCP Tool Search技术，本质上是Prompt Cache思路在工具定义层的延伸。

**核心思想演进**：

```
传统Prompt Cache:
  缓存对象: 静态前缀（系统指令 + 工具Schema）
  缓存策略: 全部加载 → 缓存全部
  问题: 即使某些工具从不使用，其Schema仍占用缓存空间

MCP Tool Search (2026):
  缓存对象: 工具 Schema 索引（轻量摘要）
  缓存策略: 按需检索 → 动态加载
  优势: 仅缓存工具索引（约5K tokens），完整Schema按需加载
```

### 6.2 从缓存策略到加载策略的演进

| 阶段 | 时期 | 策略 | Token成本 | 命中率 |
|------|------|------|----------|--------|
| 静态缓存 | 2024 | 一次性缓存全部工具Schema | 50K-80K | 95%+ |
| 排序缓存 | 2025 | 排序保证缓存键稳定，选择性缓存高频工具 | 15K-30K | 85-96% |
| **动态按需** | **2026** | **仅缓存工具索引，完整Schema动态加载** | **5K-10K** | **按需100%** |

### 6.3 对Prompt Cache架构的影响

MCP Tool Search的出现改变了Prompt Cache的设计重心：

1. **从"缓存什么"到"缓存多少"**：重点不再是"哪些内容不变可以缓存"，而是"最少缓存多少内容可以保持系统可用"
2. **缓存与检索的融合**：Prompt Cache不再只是KV缓存，而是与检索（Retrieval）体系融合——先检索再缓存
3. **动态边界移动**：Static/Dynamic的边界不再是固定的。一个工具在当前推理中是"动态加载"的，但在连续使用中可能变为"静态缓存"

这一演进方向指向一个统一的趋势：**Prompt Cache正从"静态内容复用"走向"智能按需加载"**，两者之间的界限越来越模糊。
