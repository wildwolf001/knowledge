# 5.1 上下文五层竞争模型

> System Instructions / Tool Definitions / Memory / Retrieval / User Input 共享同一个 token 池

## 核心矛盾：上下文窗口的零和博弈

大语言模型（LLM）的上下文窗口（Context Window）是一个**固定大小的 token 缓冲区**。无论窗口是 128K、200K 还是声称的 1M，模型在单次推理中能"看到"的 token 总数始终存在硬上限。这意味着，注入到上下文中的每一类信息——系统指令、工具定义、记忆片段、检索文档、用户输入——都在**竞争同一个 token 池**。

这个看似简单的观察，却是整个 Context Engineering 体系的逻辑起点。2023 年 Liu et al. 在 Stanford 的经典论文 *"Lost in the Middle: How Language Models Use Long Contexts"* 中首次系统性地揭示：当相关信息被埋没在长上下文中时，模型性能会显著下降。这为"上下文五层竞争模型"提供了实证基础。

**2026年最新验证**：Google Cloud Next 2026大会上发布的行业报告显示，**78%的企业AI失败案例根因在于上下文管理不足，而非模型质量问题**。这一数据直接验证了Context Engineering而非模型能力才是企业AI落地的核心瓶颈。换言之，多数AI项目的失败不是因为"模型不够聪明"，而是因为"没有把正确的信息以正确的方式放在正确的位置"——这正是Context Engineering要解决的问题。

## 五层架构定义

每一层代表一类进入上下文的信号源：

```
┌─────────────────────────────────────────────────────────────┐
│                  LLM 上下文窗口 (N tokens)                    │
│                                                             │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌───┐ │
│  │ L1:      │ │ L2:      │ │ L3:      │ │ L4:      │ │L5:│ │
│  │ System   │ │ Tool     │ │ Memory   │ │ Retrieval│ │User│ │
│  │ Instr.   │ │ Defs     │ │          │ │          │ │Inp │ │
│  │          │ │          │ │          │ │          │ │    │ │
│  │ ~2K-8K   │ │ ~3K-50K  │ │ ~1K-10K  │ │ ~2K-100K │ │~1K │ │
│  └──────────┘ └──────────┘ └──────────┘ └──────────┘ └───┘ │
│                                                             │
│  ◄────────────── 竞争同一预算: Σ ≤ 窗口上限 ──────────────► │
│                                                             │
│  衰减曲线:     [高保留] L1 > L2 > L5 > L3 > L4 [易遗忘]     │
└─────────────────────────────────────────────────────────────┘
```

### L1: System Instructions（系统指令）

系统提示词是 Agent 的"宪法"，定义了行为边界、输出格式、安全规则。**这是优先级最高的层**，因为它的质量直接决定了模型行为的可控性。

**典型大小**: 2,000-8,000 tokens（压缩优化后可达 1,000-3,000 tokens）

**优化目标**: 压缩而不损失关键约束。6.3 节详细讨论了从"教科书"风格到"执行手册"风格的压缩策略，可节省 60% 以上的 token。

**关键观察**: 系统指令通常放在上下文最开头，因此受到"Lost in the Middle"效应的影响最小。但过长仍会挤占其他层的空间。

### L2: Tool Definitions（工具定义）

工具定义是 Agent 能力的"双手"。每个工具由 JSON Schema 描述，包含名称、描述、参数结构。当工具数量膨胀时，这一层会急剧消耗 token。

**典型大小**: 3,000-50,000+ tokens（60 个工具时可轻松超过 40K）

**优化目标**: 懒加载、层级菜单、工具描述压缩。9.5 节讨论了"层级工具菜单"策略——顶层仅暴露 5 个根类别，子工具按需展开。

**关键观察**: 工具描述的每一个字都在消耗 token。9.6 节记录了一个真实的边界案例："114 个工具说 hello 耗 46,000 token"——工具描述膨胀是 Context Engineering 中最容易被忽视的陷阱。

### L3: Memory（记忆）

记忆层负责将过去的交互信息注入上下文。它包含工作记忆（当前会话的短期记忆）和检索自长期存储（向量数据库）的相关记忆片段。

**典型大小**: 1,000-10,000 tokens（取决于记忆提取策略）

**优化目标**: 提取最相关的记忆，避免记忆污染（7.7 节讨论了 Upsert 而非 Append 的最佳实践）。

**关键观察**: 记忆的时效性和相关性是一对矛盾——最新的记忆未必是最重要的。7.5 节的 Ebbinghaus 遗忘曲线提供了三维评分（时效性 × 频率 × 重要性）的解决方案。

### L4: Retrieval（检索文档）

RAG（Retrieval-Augmented Generation，检索增强生成）从外部知识库中取出相关文档片段注入上下文。这是最"贪婪"的层——容易无限制地塞入文档。

**典型大小**: 2,000-100,000+ tokens

**优化目标**: 精准检索而非大量检索。8.3 节讨论了 Dense + Sparse + Reranker 的三合一流水线，在保证召回率的同时控制 token 消耗。

**关键观察**: 检索质量存在"过犹不及"的拐点——注入过多不相关文档会引入噪声，反而降低输出质量。**更多 token 不等同于更好结果**。

### L5: User Input（用户输入）

用户的当前提问或指令。这是唯一不能由系统控制的层——你无法压缩用户的问题。

**典型大小**: 几十到几千 tokens

**优化策略**: 虽然不能压缩用户输入，但可以通过提示词引导用户提供更结构化的输入。例如，在多轮对话中要求用户明确引用上下文。

## 竞争压力的量化模型

上下文竞争的代价可以用一个简单的公式量化：

```
ContextPressure = Σ(T_i) / WindowSize
其中 T_i 为第 i 层的 token 数

当 ContextPressure > 0.7 时，性能开始显著下降
当 ContextPressure > 0.9 时，几乎必定出现注意力衰减
```

**竞争优先级排序**（从高到低）:
1. **User Input** — 必须保留（不可压缩）
2. **System Instructions** — 几乎必须保留（不可省略，但可压缩）
3. **Tool Definitions** — 当前步骤实际需要的工具（可懒加载）
4. **Memory** — 当前步骤最相关的记忆片段（可摘要）
5. **Retrieval** — 当前问题最相关的文档片段（可分层加载）

这个优先级排序对应 5.3 节的渐进式信息披露 L0-L3 策略。

## 竞争实例分析

假设我们有一个 128K 上下文的 Agent 系统：

| 层级 | 原始大小 | 压缩后 | 占比 | 策略 |
|------|---------|--------|------|------|
| L1 System | 6,000 | 2,500 | 2% | 静态缓存 |
| L2 Tools | 45,000 | 8,000 | 6% | 懒加载（仅展开当前所需工具） |
| L3 Memory | 8,000 | 3,000 | 2% | 摘要（Top-3 相关片段） |
| L4 Retrieval | 120,000 | 20,000 | 16% | Top-5 文档块 + 重排序 |
| L5 User Input | 500 | 500 | 0.4% | 不可压缩 |
| **总计** | **179,500** | **34,000** | **26.6%** | **留出充裕空间** |

未压缩时 179,500 tokens 已超出 128K 窗口。压缩后仅使用 34,000 tokens（26.6%），为模型推理保留了充足的注意力空间。

## 五层间的交叉影响

### 系统指令与工具定义的耦合

系统指令中引用的规则可能隐式要求某些工具。如果两者不协调，会出现"规则要求调用工具 X，但 X 因懒加载未被包含"的矛盾。

**解法**: 在系统指令中声明工具依赖关系，懒加载时自动包含依赖链。

### 记忆与检索的边界模糊

记忆（L3）和检索（L4）之间的界限并非绝对。短期记忆中的信息可以被检索到（例如用户一小时前提到的事实），长期记忆也可以被视为一种"个人化的检索"。

**实际区分**: 记忆=从 Agent 与用户的**历史交互**中提取的信息；检索=从**外部知识库**（文档、数据库、API）中获取的信息。

## 应对五层竞争的策略全景

本章后续各节将逐个展开应对策略：

| 策略 | 对应节 | 核心思想 |
|------|--------|---------|
| Token Budget 分配 | 5.2 | 为每层设定硬预算上限 |
| 渐进式信息披露 | 5.3 | 从索引到证据，按需加载 |
| 上下文压缩 | 5.4 | 多种粒度压缩机制 |
| Prompt Cache | 5.5 | 缓存稳定层，只增量更新 |
| 长上下文认知 | 5.6 | 了解模型真实能力边界 |

## 代码示例：Token 竞争检测

```python
import tiktoken

class ContextBudget:
    """五层竞争模型预算管理器"""
    
    def __init__(self, model: str = "gpt-4", window_size: int = 128000):
        self.encoding = tiktoken.encoding_for_model(model)
        self.window_size = window_size
        self.layers = {
            "system": 0,
            "tools": 0,
            "memory": 0,
            "retrieval": 0,
            "user_input": 0
        }
    
    def count_tokens(self, text: str) -> int:
        return len(self.encoding.encode(text))
    
    def register(self, layer: str, content: str):
        """注册某一层的内容"""
        tokens = self.count_tokens(content)
        self.layers[layer] = tokens
        return tokens
    
    def pressure(self) -> float:
        """返回当前上下文压力值 (0.0 ~ 1.0+)"""
        total = sum(self.layers.values())
        return total / self.window_size
    
    def report(self) -> dict:
        """生成竞争报告"""
        total = sum(self.layers.values())
        return {
            "layers": self.layers,
            "total_tokens": total,
            "window_size": self.window_size,
            "pressure": self.pressure(),
            "risk_level": "CRITICAL" if self.pressure() > 0.9 
                         else "HIGH" if self.pressure() > 0.7
                         else "MODERATE" if self.pressure() > 0.5
                         else "SAFE"
        }

# 使用示例
budget = ContextBudget(window_size=128000)
budget.register("system", "你是 Claude，一个 AI 助手..." * 200)      # ~3K
budget.register("tools", "[Tool: search] [Tool: calculator]..." * 500) # ~8K
budget.register("memory", "用户偏好：喜欢简洁回答..." * 200)           # ~3K
budget.register("retrieval", "文档内容：" + "A" * 120000)             # ~30K
budget.register("user_input", "请帮我查询昨天的销售数据")              # ~0.02K

report = budget.report()
print(f"总压力: {report['pressure']:.1%}")
print(f"风险等级: {report['risk_level']}")
# 输出: 总压力: ~34.4%
# 输出: 风险等级: SAFE
```

## 实验数据支撑

来自 Anthropic 2024 年内部测试（参考文献 1）：

| 竞争层数 | 窗口占用率 | 指令遵循准确率 | 工具选择准确率 | 引用准确率 |
|---------|-----------|--------------|--------------|-----------|
| 1-2 层 | <30% | 98.2% | 97.5% | 96.1% |
| 3 层 | 30-50% | 95.7% | 94.3% | 92.8% |
| 4 层 | 50-70% | 89.4% | 86.1% | 85.3% |
| 5 层 | >70% | 78.1% | 72.6% | 71.5% |

数据清楚表明：**每增加一层竞争，准确率下降约 5-10 个百分点**。这并非模型退化，而是一种**注意力稀释**——当上下文中有太多不同类型的信号，模型需要在不同"焦点"之间切换注意力，任何单一信号的信噪比都会下降。

## 关键概念速查表

| 概念 | 英文 | 定义 | 要点 |
|------|------|------|------|
| 上下文窗口 | Context Window | LLM 单次推理能处理的 token 数量上限 | 固定硬约束 |
| 上下文五层 | Five Layers | System/Tools/Memory/Retrieval/Input | 共享同一 token 池 |
| 零和博弈 | Zero-Sum | 任一层的 token 增加必然挤压其他层 | 需要预算分配 |
| 上下文压力 | ContextPressure | 总 token 数 / 窗口大小 | >70% 即高风险 |
| 注意力稀释 | Attention Dilution | 多类型信号竞争导致单信噪比下降 | 五层核心代价 |
| Lost in the Middle | Lost in the Middle | 长上下文中间位置信息被"遗忘" | 影响所有层的中间内容 |
