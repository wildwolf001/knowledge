# 5.4 上下文压缩体系

> Micro（清旧工具结果）/ Auto（LLM 摘要）/ Reactive（API 报错触发）/ SessionMemory（零成本）

## 压缩：Context Engineering 的基石

上下文压缩（Context Compression）是在不丢失关键信息的前提下，减少 token 占用的技术集合。与 5.2 的 Token Budget 不同（预算关注"分配多少"），压缩关注"如何让相同的信息占用更少的 token"。

四类压缩机制从不同的触发条件和压缩粒度切入，构成了一个完整的压缩体系：

```
压缩体系总览
                                        
┌──────────────────────────────────────────────────────────────────────┐
│                      上下文压缩体系                                     │
│                                                                      │
│  ┌─────────────────┐  ┌─────────────────┐  ┌──────────────┐  ┌────┐ │
│  │   Micro         │  │   Auto          │  │  Reactive    │  │ SM │ │
│  │   (微观)        │  │   (自动)         │  │  (响应式)     │  │    │ │
│  │                 │  │                 │  │              │  │    │ │
│  │  触发: 每轮     │  │  触发: 间隔      │  │  触发: API   │  │零  │ │
│  │  操作: 清工具   │  │  操作: LLM 摘要  │  │  错误后      │  │成  │ │
│  │  结果           │  │  对话           │  │  操作: 裁剪  │  │本  │ │
│  │                 │  │                 │  │  上下文      │  │    │ │
│  │  成本: ~0 token │  │  成本: LLM 调用  │  │  成本: 可变  │  │    │ │
│  └─────────────────┘  └─────────────────┘  └──────────────┘  └────┘ │
│                                                                      │
│  频率: 每轮         频率: 每 N 轮        频率: 按需       持续激活   │
└──────────────────────────────────────────────────────────────────────┘
```

## Micro 压缩：清旧工具结果

**核心思想**: 工具执行结果（Tool Result）是**一次性使用**的。在完成当前推理后，上一步的工具结果对后续步骤没有任何价值——Agent 已经将其"消化"为新的推理状态。

**问题**: 许多框架（LangGraph、AutoGen）默认将工具执行结果追加到上下文，导致上下文随工具调用次数线性增长。10 次工具调用可能产生 10,000+ 无用的 tokens。

### 实现策略

```python
class MicroCompressor:
    """
    Micro 压缩器：每轮清除已使用的工具结果
    
    这是最简单但最高效（收益/成本比）的压缩策略
    """
    
    def __init__(self):
        self.executed_tools = []  # 已执行工具历史
    
    def compress_after_step(self, context: list) -> list:
        """
        在每步推理后压缩上下文
        
        策略:
        1. 保留最后 N 轮工具结果（用于连续调试）
        2. 移除更早的工具结果
        3. 将工具执行错误保留（用于错误分析）
        """
        compressed = []
        recent_tool_results = 0
        
        for msg in reversed(context):  # 逆序遍历
            if msg["role"] == "tool":
                if recent_tool_results < 2:  # 保留最近 2 个
                    compressed.append(msg)
                    recent_tool_results += 1
                # 其余工具结果丢弃
            else:
                compressed.append(msg)
        
        return list(reversed(compressed))
    
    def get_stats(self, before: int, after: int) -> dict:
        return {
            "before": before,
            "after": after,
            "saved": before - after,
            "saved_pct": (1 - after / before) * 100
        }
```

### 真实案例

一个调用 6 次工具的 Agent 流程：

| 阶段 | 原始上下文 | Micro 压缩后 | 节省 |
|------|-----------|------------|------|
| Step 1 | 12,500 | 12,500 | 0% |
| Step 2 | 16,800 | 14,200 | 15.5% |
| Step 3 | 21,200 | 15,800 | 25.5% |
| Step 4 | 25,900 | 17,100 | 34.0% |
| Step 5 | 30,100 | 18,300 | 39.2% |
| Step 6 | 34,500 | 19,500 | 43.5% |

**仅在 6 步之后，Micro 压缩就节省了 43.5% 的 token**。随着步骤增加，节省比例趋近于 50-60% 的渐进上限。

### 注意事项

- **不要清除错误结果**: 工具执行失败的信息可能对后续纠错有用（见 9.7 工具调用失败三层处理）
- **保留最近 1-2 个结果**: 在多步推理中，上一步的结果可能是当前步骤的输入
- **对用户可见的工具结果谨慎处理**: 如果工具结果需要展示给用户（如搜索摘要），需保留

## Auto 压缩：LLM 摘要

**核心思想**: 使用 LLM 将冗长的对话历史或工具结果压缩为精炼摘要。牺牲少量 LLM 调用成本，换取大幅度的 token 节省。

### 实现策略

```python
class AutoCompressor:
    """
    Auto 压缩器：间隔 N 轮使用 LLM 做摘要压缩
    
    阈值策略:
    - 当上下文占用 > 50% 窗口时触发自动摘要
    - 保持最近 3 轮完整内容
    - 更早内容全部摘要化
    """
    
    def __init__(self, llm_func, threshold: float = 0.5, 
                 keep_recent: int = 3):
        self.llm = llm_func
        self.threshold = threshold
        self.keep_recent = keep_recent
        self.summary = None  # 累积摘要
    
    def should_compress(self, current_usage: int, 
                        window_size: int) -> bool:
        """判断是否需要压缩"""
        return current_usage / window_size > self.threshold
    
    def compress(self, conversation: list) -> list:
        """
        执行压缩：摘要 + 保留最近轮次
        """
        # 分离近期和远期
        recent = conversation[-self.keep_recent * 2:]  # 用户+助手配对
        history = conversation[:-len(recent)]
        
        if not history:
            return conversation
        
        # 生成摘要
        history_text = self._format_history(history)
        new_summary = self._summarize(history_text)
        
        # 合并到既有摘要
        if self.summary:
            merged = self._merge_summaries(self.summary, new_summary)
        else:
            merged = new_summary
        
        self.summary = merged
        
        # 构建压缩后的上下文
        compressed = [{
            "role": "system",
            "content": f"[对话摘要]\n{self.summary}"
        }] + recent
        
        return compressed
    
    def _summarize(self, text: str) -> str:
        """调用 LLM 生成摘要"""
        prompt = f"""请将以下对话压缩为简洁摘要（保留关键事实、决策和用户偏好）:

{text[:4000]}  # 限制输入长度

摘要:"""
        return self.llm(prompt)
    
    def _merge_summaries(self, old: str, new: str) -> str:
        """合并新旧摘要"""
        prompt = f"""合并以下两份对话摘要为一个连贯摘要:

旧摘要: {old}
新内容: {new}

合并摘要:"""
        return self.llm(prompt)
    
    def _format_history(self, messages: list) -> str:
        """将消息列表格式化为文本"""
        parts = []
        for msg in messages:
            role = msg.get("role", "unknown")
            content = msg.get("content", "")
            parts.append(f"[{role}]: {content[:200]}")
        return "\n".join(parts)
```

### 压缩率与质量权衡

| 摘要策略 | 压缩率 | 信息保留率 | 额外 LLM 成本 |
|---------|--------|-----------|-------------|
| 关键词提取 | 90% | 40-50% | ~0 |
| 单轮摘要 | 80% | 70-80% | 1 次调用 |
| 分层摘要（先分段再合并） | 75% | 85-90% | 2-3 次调用 |
| 增量摘要 | 85% | 75-85% | 1 次调用（但需保留旧摘要） |

**推荐**: 增量摘要策略——每次只摘要"新的"内容，然后与旧摘要合并。在压缩率、质量和成本之间取得最佳平衡。

### 压缩时长上下文的分层摘要算法

对于极长上下文（>50,000 tokens），单次摘要会导致 LLM 遗漏中间细节。采用**分治策略**:

```python
def hierarchical_summarize(text: str, llm_func, 
                            chunk_size: int = 4000) -> str:
    """
    分层摘要算法
    
    1. 将长文本切分为块
    2. 逐块摘要
    3. 将各块摘要合并为最终摘要
    """
    # Step 1: 分块
    chunks = [text[i:i+chunk_size] 
              for i in range(0, len(text), chunk_size)]
    
    # Step 2: 逐块摘要
    chunk_summaries = []
    for chunk in chunks:
        summary = llm_func(f"摘要以下内容:\n{chunk}")
        chunk_summaries.append(summary)
    
    # Step 3: 合并摘要
    if len(chunk_summaries) == 1:
        return chunk_summaries[0]
    
    combined = "\n\n".join(chunk_summaries)
    final = llm_func(f"合并以下摘要为一个连贯摘要:\n{combined}")
    return final
```

## Reactive 压缩：API 报错触发

**核心思想**: 将**错误信号**作为触发压缩的"传感器"。当 API 返回 context_length_exceeded 或 token limit 错误时，即时执行激进压缩。

### 实现策略

```python
class ReactiveCompressor:
    """
    Reactive 压缩器：在捕获到上下文溢出错误时触发
    
    这是最后一道防线——当预算管理失败时的兜底策略
    """
    
    def __init__(self, llm_func):
        self.llm = llm_func
        self.compress_count = 0  # 统计触发次数
    
    def on_overflow_error(self, context: dict) -> dict:
        """
        处理上下文溢出错误
        
        压缩优先级（由低到高删除）:
        1. 最早的工具结果
        2. 非关键的历史轮次
        3. 检索文档的冗余部分
        4. 最后手段：删除非核心系统指令
        """
        self.compress_count += 1
        compressed = context.copy()
        
        # Phase 1: 清除最早的工具结果（Micro 策略）
        tool_results = [m for m in compressed["messages"] 
                       if m.get("role") == "tool"]
        if tool_results:
            # 仅保留最近 50%
            keep_count = max(1, len(tool_results) // 2)
            removable = tool_results[:-keep_count]
            compressed["messages"] = [
                m for m in compressed["messages"] 
                if m not in removable
            ]
        
        # Phase 2: 如果还不够，摘要对话历史（Auto 策略）
        if self._still_overflowing(compressed):
            auto = AutoCompressor(self.llm)
            compressed["messages"] = auto.compress(
                compressed["messages"]
            )
        
        # Phase 3: 如果还不够，裁剪检索文档
        if self._still_overflowing(compressed):
            for msg in compressed["messages"]:
                if msg.get("role") == "user" and len(msg.get("content","")) > 2000:
                    msg["content"] = msg["content"][:2000]
        
        # 记录压缩事件
        compressed["_compressed"] = True
        compressed["_compress_count"] = self.compress_count
        
        return compressed
    
    def _still_overflowing(self, context: dict) -> bool:
        """模拟检查是否仍然溢出"""
        # 实际实现需要调用 tokenizer 计数
        total = sum(len(m.get("content", "")) for m in context.get("messages", []))
        return total > 100000  # 假设 100K 阈值
    
    def get_compress_stats(self) -> dict:
        return {
            "total_compressions": self.compress_count,
            "avg_savings_per_compression": "15,000-30,000 tokens"
        }
```

### 压缩等级递进

| 等级 | 操作 | Token 节省 | 信息损失 | 延迟影响 |
|------|------|-----------|---------|---------|
| R1 | 清除旧工具结果 | 10,000-30,000 | 低（结果已使用） | 无 |
| R2 | 摘要对话历史 | 20,000-50,000 | 中（细节丢失） | +1 LLM 调用 |
| R3 | 裁剪检索文档 | 10,000-80,000 | 中-高（可能损失关键证据） | 无 |
| R4 | 截断系统指令 | 2,000-8,000 | 高（行为可能失控） | 无 |

**设计原则**: Reactive 压缩应始终从损失最低的等级开始，逐级升级。

## SessionMemory 压缩：零成本

**核心思想**: SessionMemory（会话内存）是 Agent 框架（如 Agno 框架，原名 Phidata）内置的一种轻量级机制——**不需要显式管理，框架自动处理上下文历史**。

### 工作原理

SessionMemory 将"对话轮次"作为一种有结构的记忆单元来管理，而不是简单地追加 token：

```
SessionMemory 内部结构
                                        
┌─────────────────────────────────────────────────────────┐
│  SessionMemory                                           │
│                                                          │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐     │
│  │ Round 1     │  │ Round 2     │  │ Round 3     │     │
│  │ user: "..." │  │ user: "..." │  │ user: "..." │     │
│  │ asst: "..." │  │ asst: "..." │  │ asst: "..." │     │
│  │ tools: [...]│  │ tools: [...]│  │ tools: [...]│     │
│  │ summary: "" │  │ summary: "" │  │ summary: "" │     │
│  └──────┬──────┘  └──────┬──────┘  └──────┬──────┘     │
│         │                │                │            │
│         └────────────────┴────────────────┘            │
│                      │                                  │
│                      ▼                                  │
│             当轮次超限时,自动合并                          │
│         Round 1-3 → 一条摘要记录                          │
└─────────────────────────────────────────────────────────┘
```

### 关键优势

1. **零额外编码成本**: 不需要开发者编写压缩逻辑——框架内置
2. **自动触发**: 基于预设的轮次上限或 token 阈值自动执行
3. **结构化保留**: 不是简单的文本拼接，而是保留角色、工具调用、摘要的结构化数据

### 框架对比

| 框架 | SessionMemory 支持 | 压缩策略 | 开发成本 |
|------|------------------|---------|---------|
| Agno (Phidata) | 内置 | 自动轮次合并 + 摘要 | ~0 |
| LangGraph | 需手动配置 | 需编写 reducer | 中 |
| CrewAI | 有限（依赖工具） | 需手动管理 | 中-高 |
| AutoGen | 需手动实现 | 需自定义 | 高 |

### 非框架环境的实现

如果未使用包含 SessionMemory 的框架，可自行实现一个轻量版本：

```python
class SessionMemory:
    """
    轻量级 SessionMemory 实现
    
    零成本压缩：仅通过结构化管理实现，不调用 LLM
    """
    
    def __init__(self, max_rounds: int = 10, 
                 max_tokens_per_round: int = 2000):
        self.rounds = []
        self.max_rounds = max_rounds
        self.max_tokens_per_round = max_tokens_per_round
    
    def add_round(self, user_msg: str, assistant_msg: str, 
                  tool_calls: list = None):
        """添加一轮对话"""
        self.rounds.append({
            "user": user_msg[:self.max_tokens_per_round],
            "assistant": assistant_msg[:self.max_tokens_per_round],
            "tools": (tool_calls or [])[:5],  # 仅保留最近 5 个工具调用
            "summary": None
        })
        
        # 自动压缩
        self._auto_compress()
    
    def _auto_compress(self):
        """当轮次超限时自动压缩"""
        if len(self.rounds) > self.max_rounds:
            # 将最早的 N/2 轮合并
            to_merge = self.rounds[:len(self.rounds) // 2]
            merged = {
                "user": f"[{len(to_merge)} 轮对话摘要]",
                "assistant": f"包含 {len(to_merge)} 轮对话的关键信息",
                "tools": [],
                "summary": self._merge_texts(to_merge)
            }
            self.rounds = [merged] + self.rounds[len(self.rounds) // 2:]
    
    def _merge_texts(self, rounds: list) -> str:
        """合并文本（无 LLM，仅拼接关键信息）"""
        summaries = []
        for r in rounds:
            if r.get("summary"):
                summaries.append(r["summary"])
            else:
                summaries.append(f"用户: {r['user'][:50]}...")
        return " | ".join(summaries)
    
    def get_context(self) -> list:
        """获取用于 LLM 调用的上下文"""
        messages = []
        for r in self.rounds:
            messages.append({"role": "user", "content": r["user"]})
            messages.append({"role": "assistant", "content": r["assistant"]})
        return messages
```

## 四类压缩对比总结

| 维度 | Micro | Auto | Reactive | SessionMemory |
|------|-------|------|----------|-------------|
| **触发条件** | 每轮自动 | 阈值触发（50% 窗口） | API 错误触发 | 轮次/容量超限 |
| **压缩粒度** | 移除/保留整条消息 | 文本摘要重写 | 多级递进 | 结构化合并 |
| **是否调用 LLM** | 否 | 是 | 条件性 | 否 |
| **信息损失** | 极低 | 中（依赖摘要质量） | 取决于等级 | 低（结构化） |
| **Token 节省** | 40-60% | 60-80% | 30-70% | 30-50% |
| **延迟影响** | 无 | +1-3 次 LLM 调用 | +0-2 次 LLM 调用 | 无 |
| **实现复杂度** | 低 | 中 | 中-高 | 低 |
| **适用范围** | 所有系统 | 长对话 | 预算管理不完善的系统 | 框架使用者 |

## 组合使用策略

在实践中，四类压缩应组合使用，形成一个多级防御体系：

```python
class CompressionPipeline:
    """四类压缩串联管道"""
    
    def __init__(self, llm_func, window_size: int = 128000):
        self.micro = MicroCompressor()
        self.auto = AutoCompressor(llm_func)
        self.reactive = ReactiveCompressor(llm_func)
        self.session = SessionMemory()
        self.window_size = window_size
    
    def step(self, context: dict) -> dict:
        """每步推理后执行的压缩管道"""
        # 1. Micro: 始终执行
        context = self.micro.compress_after_step(context)
        
        # 2. Auto: 检查是否需要压缩
        usage = self._estimate_tokens(context)
        if self.auto.should_compress(usage, self.window_size):
            context = self.auto.compress(context)
        
        return context
    
    def on_error(self, context: dict) -> dict:
        """错误时的 Reactive 压缩"""
        return self.reactive.on_overflow_error(context)
```

**生产建议**:
- **Micro** 和 **SessionMemory**: 始终启用（零成本、高收益）
- **Auto**: 在消费级/企业级应用中启用（摘要质量的关键在于 prompt 设计）
- **Reactive**: 必须始终启用（兜底安全网，防止"炸上下文"）

## 关键概念速查表

| 概念 | 英文 | 定义 | 要点 |
|------|------|------|------|
| Micro 压缩 | Micro Compression | 每轮清除已使用的工具结果 | 零成本，40-60% 节省 |
| Auto 压缩 | Auto Compression | LLM 自动摘要对话历史 | 60-80% 节省，有 LLM 成本 |
| Reactive 压缩 | Reactive Compression | API 错误触发的兜底压缩 | 最后防线，四级递进 |
| SessionMemory | Session Memory | 框架内置的上下文管理 | 零编码成本，结构化压缩 |
| 分层摘要 | Hierarchical Summarization | 分块→逐块摘要→合并 | 处理 50K+ 长文本 |
| 增量摘要 | Incremental Summarization | 仅摘要新增内容后与旧摘要合并 | 效率与质量的平衡 |
| 压缩率 | Compression Ratio | 压缩后/压缩前的 token 比 | 越低越好 |
| 信息保留率 | Information Retention | 压缩后保留的关键信息比例 | 越高越好 |
