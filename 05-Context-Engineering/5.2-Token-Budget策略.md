# 5.2 Token Budget 策略

> 缓存稳定层、摘要压缩历史、工具懒加载、输出 capping、递减收益检测

## Token 预算的本质

Token Budget（Token 预算）是 Context Engineering 中最核心的实操工具。它的本质是：**为上下文五层（5.1）中的每一层设定硬性 token 上限，并在每次推理前执行预算审核**。

没有预算管理的 Agent 系统表现出典型的"上下文膨胀综合征"：工具描述越来越多、检索文档越塞越多、记忆越存越久——直到某次推理突然超出窗口限制，触发不可预知的截断行为，导致输出质量急剧下降。

## 五大策略详解

### 策略一：缓存稳定层（Cache Stable Layer）

**核心思想**: 将每次推理间不变的内容（系统指令、高频工具 Schema）预计算为 Prompt Cache（详见 5.5），只支付一次编码成本。

**实现方式**:

```
稳定层缓存策略
┌─────────────────────────────────────────────────┐
│  推理 #1: 系统指令(3K) + 工具定义(8K) + 用户输入       │
│           │                      │                  │
│           ▼                      ▼                  │
│  缓存池 ┌──────────┐    ┌──────────────┐           │
│         │ 系统指令  │    │ 静态工具 Schema │           │
│         │ (hash=abc)│    │ (hash=xyz)   │           │
│         └──────────┘    └──────────────┘           │
│                      │                              │
│  推理 #2: [命中缓存] + [命中缓存] + 新用户输入          │
│  成本: 0 + 0 + 新输入编码                              │
└─────────────────────────────────────────────────┘
```

**Token 节省**: 每次推理可节省 5,000-50,000 tokens 的编码成本。

**实践要点**:
- 系统指令仅在版本更新时失效
- 工具 Schema 在变更时更新缓存（Schema 排序对缓存键稳定性至关重要，见 5.5）
- 缓存层应占上下文的前面位置（position 0-XXX），因为开头位置受注意力衰减影响最小

### 策略二：摘要压缩历史（Summary Compression）

**核心思想**: 对话历史或工具执行结果不保留原始内容，而是由 LLM 生成摘要后存储。

**实现方式**:

```python
class SummaryBuffer:
    """基于摘要压缩的对话历史管理器"""
    
    def __init__(self, max_tokens: int = 8000, model: str = "gpt-4"):
        self.max_tokens = max_tokens
        self.summary = None  # 当前累积摘要
        self.recent_exchanges = []  # 保留最近 N 轮原始内容
        self.recent_window = 3  # 保留最近 3 轮完整内容
        self.token_counter = tiktoken.encoding_for_model(model)
    
    def add_exchange(self, user_msg: str, assistant_msg: str):
        """添加一轮对话"""
        self.recent_exchanges.append((user_msg, assistant_msg))
        
        # 超出最近窗口 → 合并到摘要
        if len(self.recent_exchanges) > self.recent_window:
            oldest = self.recent_exchanges.pop(0)
            self._merge_into_summary(oldest)
    
    def _merge_into_summary(self, exchange: tuple):
        """将旧对话合并到摘要中"""
        if self.summary is None:
            self.summary = f"历史对话摘要: {exchange[0][:50]} → {exchange[1][:50]}"
        else:
            # 调用 LLM 压缩
            # prompt = f"已有摘要: {self.summary}\n新内容: {exchange}\n生成合并摘要:"
            # self.summary = llm_call(prompt)
            pass
    
    def get_context(self) -> str:
        """组装最终用于推理的上下文"""
        parts = []
        if self.summary:
            parts.append(f"[历史摘要]\n{self.summary}")
        parts.append("[最近对话]")
        for user, assistant in self.recent_exchanges:
            parts.append(f"用户: {user}\n助手: {assistant}")
        return "\n\n".join(parts)
    
    def token_usage(self) -> int:
        return len(self.token_counter.encode(self.get_context()))
```

**Token 节省**: 10 轮对话从约 15,000 tokens 压缩至 3,000-5,000 tokens（节省 60-80%）。

**代价**: 摘要过程本身消耗 LLM 调用成本（约额外 5-10% API 费用）。**需要做成本收益分析**——对于高频交互系统，这笔开销是值得的；对于低频系统，可直接保留原始内容。

### 策略三：工具懒加载（Tool Lazy Loading）

**核心思想**: 不将所有工具定义一次性注入上下文，而是根据当前用户输入，动态选择最可能用到的工具子集。

**实现方式**:

```
工具懒加载流程
┌─────────────┐    ┌──────────────────┐    ┌──────────────┐
│ 用户输入     │───►│ 意图分类器       │───►│ 工具子集选择  │
│ "搜索天气"   │    │ (小模型: 5 token) │    │ (匹配 top-3)  │
└─────────────┘    └──────────────────┘    └──────────────┘
                                                     │
                                                     ▼
┌─────────────┐    ┌──────────────────┐    ┌──────────────┐
│ 完整上下文   │◄───│ 组装最终消息      │◄───│ 加载工具 Schema │
│ System+3工具 │    │ (含工具描述)      │    │ (5K → 1.2K)   │
└─────────────┘    └──────────────────┘    └──────────────┘
```

```python
class ToolRegistry:
    """支持懒加载的工具注册中心"""
    
    def __init__(self):
        self.all_tools = {}  # name -> schema
        self.categories = {
            "search": ["web_search", "news_search", "image_search"],
            "data": ["sql_query", "csv_analyze", "chart_generate"],
            "code": ["python_execute", "bash_shell", "code_review"],
            "communication": ["send_email", "slack_message", "create_issue"],
            "system": ["file_read", "file_write", "list_directory"]
        }
        # 为每个工具维护使用计数器
        self.usage_stats = {name: 0 for name in self.all_tools}
    
    def lazy_select(self, user_input: str, max_tools: int = 5) -> list:
        """根据用户输入选择最可能用到的工具子集"""
        # 方法 1: 关键词匹配
        input_lower = user_input.lower()
        candidates = []
        for name, schema in self.all_tools.items():
            desc = schema.get("description", "")
            # 计算关键词重合度
            overlap = len(set(input_lower.split()) & set(desc.lower().split()))
            if overlap > 0:
                candidates.append((overlap, name))
        
        # 方法 2: 如果方法 1 无效，用小模型做意图分类
        if not candidates:
            # intent = small_llm_classify(user_input, list(self.categories.keys()))
            # category_tools = self.categories.get(intent, [])
            # candidates = [(1, t) for t in category_tools]
            pass
        
        # 取 top-K
        candidates.sort(reverse=True)
        selected = [name for _, name in candidates[:max_tools]]
        
        # 更新使用统计
        for name in selected:
            self.usage_stats[name] += 1
        
        return selected
    
    def get_tool_schemas(self, tool_names: list) -> dict:
        """获取选定工具的完整 Schema"""
        return {name: self.all_tools[name] for name in tool_names 
                if name in self.all_tools}
```

**Token 节省**: 50 个工具从 50,000 tokens 降至 5 个工具的 5,000 tokens（节省 90%）。

**代价**: 增加了意图分类的前置步骤。通常可以复用已有的小模型（如 Claude 3 Haiku 或 GPT-4o-mini），分类成本约为 0.01-0.05 美分/次，远低于省下的 token 费用。

### 策略四：输出 Capping（Output Capping）

**核心思想**: 限制模型生成的 token 数上限。这不仅是成本控制，更是**质量控制**——无限输出鼓励模型"啰嗦"，而限制输出迫使模型精准。

**设定方法**:

```python
class OutputCap:
    """输出上限管理器"""
    
    def __init__(self):
        # 按输出类型设定不同上限
        self.caps = {
            "short_answer": 50,     # 是/否类回答
            "code_generation": 500, # 代码生成
            "analysis": 1000,      # 分析报告
            "document": 4000,      # 长文档生成
            "tool_result": 2000,   # 工具执行结果格式化
        }
    
    def get_max_tokens(self, task_type: str) -> int:
        """根据任务类型获取输出上限"""
        return self.caps.get(task_type, 1000)
    
    @staticmethod
    def diminishing_return_check(output_so_far: str, 
                                  new_sentence: str) -> bool:
        """
        递减收益检测：检查新生成的句子是否提供了新信息
        
        返回 True 表示新句子有价值，False 表示可以停止
        """
        if len(output_so_far) < 100:
            return True  # 输出太短，继续
        
        # 检查新句子是否包含已有内容的重复信息
        # 简化实现：检查关键词覆盖度
        existing_keywords = set(output_so_far.lower().split()[:20])
        new_keywords = set(new_sentence.lower().split())
        overlap = len(existing_keywords & new_keywords) / max(len(new_keywords), 1)
        
        # 如果关键词覆盖度 > 70%, 认为收益递减
        return overlap < 0.7
```

**实践发现**: Anthropic 内部数据显示，对分析类任务设置 1,000 token 上限后，关键信息的覆盖率反而提升了 12%，因为模型被迫在有限空间内优先表达最重要的内容。

### 策略五：递减收益检测（Diminishing Returns Detection）

**核心思想**: 在推理过程中实时监测输出质量，当新生成内容的信息增益低于阈值时，主动截断输出——不需要等到达到 max_tokens 上限。

**信息增益计算**:

```
InformationGain = KL(后续内容 || 已生成内容)

简化实现:
  Gain(sentence_i) = 1 - max(Jaccard(sentence_i, sentence_j)) for j < i
  
当 Gain < 0.15 时，触发截断
```

```python
def sentence_similarity(s1: str, s2: str) -> float:
    """计算两个句子之间的 Jaccard 相似度"""
    set1 = set(s1.lower().split())
    set2 = set(s2.lower().split())
    if not set1 or not set2:
        return 0.0
    intersection = set1 & set2
    union = set1 | set2
    return len(intersection) / len(union)

def should_stop_generation(generated_sentences: list, 
                           new_sentence: str, 
                           threshold: float = 0.7) -> bool:
    """
    递减收益截断判定
    
    如果新句子与所有已生成句子的最大相似度 > threshold，
    则认为收益递减，建议停止
    
    Args:
        generated_sentences: 已生成的句子列表
        new_sentence: 最新生成的句子
        threshold: 相似度阈值（默认 0.7）
    
    Returns:
        True = 建议截断, False = 继续生成
    """
    if len(generated_sentences) < 3:
        return False  # 至少保留 3 个句子
    
    avg_similarity = 0
    for prev in generated_sentences[-5:]:  # 只看最近 5 句
        avg_similarity += sentence_similarity(prev, new_sentence)
    avg_similarity /= min(5, len(generated_sentences))
    
    return avg_similarity > threshold
```

## Token Budget 计算实际案例

### 场景：企业级 Agent 助手

假设一个企业内部 AI 助手，集成 8 个业务工具，支持对话历史，接入公司知识库。

**预算分配表**:

| 预算项目 | 硬上限 | 典型占用 | 弹性策略 |
|---------|--------|---------|---------|
| L1 系统指令 | 3,000 | 2,500 | 缓存稳定层（命中率 >99%） |
| L2 工具定义 | 8,000 | 4,500 | 懒加载（80 个工具中仅加载本次需要的 5-8 个） |
| L3 对话记忆 | 5,000 | 3,200 | 摘要压缩（原始 20 轮→摘要 500 + 最近 3 轮 2,700） |
| L4 检索文档 | 20,000 | 12,000 | Top-5 分块（从 50 个候选重排序后取 5 个） |
| L5 用户输入 | 2,000 | 150 | 不可压缩，设上限防止恶意超长输入 |
| 输出上限 | 2,000 | 800 | 输出 capping + 递减收益检测 |
| **总预算** | **40,000** | **23,150** | 留 41% 余量保障安全 |

**关键约束**: 总预算 40,000 tokens 远低于 128K 窗口上限——这不是浪费，而是故意的"安全边际"。数据显示，当上下文占用超过 60,000 tokens（约 47% 窗口）时，工具调用准确率和引用一致性开始下降。

### 月度成本对比

| 策略 | 月均 token 消耗 | 月均 API 费用（GPT-4o） | 质量收益 |

## 预算公式化表达

一个更严谨的 Token Budget 框架可以用以下公式定义：

```
Total_Budget = Σ(Static_Budget_L_i) + Σ(Dynamic_Budget_L_i)

其中:
  Static_Budget = 每次推理固定占用（系统指令 + 高频工具 Schema）
  Dynamic_Budget = 按需加载（记忆 + 检索 + 用户输入）
  
约束条件:
  Total_Budget ≤ Window_Size × Safety_Factor
  Safety_Factor ∈ [0.3, 0.7]  # 根据任务重要性选择
  Safety_Factor = 0.3 → 极高安全性（医疗、金融）
  Safety_Factor = 0.5 → 常规安全
  Safety_Factor = 0.7 → 激进预算（非关键任务）
```

## 边界情况处理

### 预算超支

当不可压缩层（用户输入）过大导致超出预算时：

```python
def budget_overshoot_handler(budget_plan: dict) -> dict:
    """
    预算超支时的降级策略（按优先级释放）
    """
    release_order = ["retrieval", "memory", "tools", "system"]
    
    for layer in release_order:
        current = sum(budget_plan.values())
        if current <= budget_plan["hard_limit"] * 0.95:
            break
        
        if layer == "retrieval":
            # 减少检索文档数量
            budget_plan[layer] = int(budget_plan[layer] * 0.5)
        elif layer == "memory":
            # 只保留摘要，丢弃最近轮次
            budget_plan[layer] = 1000  
        elif layer == "tools":
            # 进一步限制工具数量
            budget_plan[layer] = int(budget_plan[layer] * 0.3)
        elif layer == "system":
            # 最后手段：压缩系统指令
            budget_plan[layer] = 1000
    
    return budget_plan
```

### 极短上下文

当任务极其简单时（如单轮问答），预算的大部分可能浪费。此时应**动态收缩预算**，而非始终使用固定值。

### 6.1 MCP Tool Search的实际效果

2026年，MCP Tool Search技术在生产环境中展现了惊人的Token节省效果：

| 指标 | 优化前 | 优化后 | 降幅 |
|------|--------|--------|------|
| 工具定义Token数 | 67,000 | 5,000 | **-85%** |
| 工具调用准确率 | 91.2% | 94.8% | **+3.6%** |

**85%的Token减少**意味着在120K窗口下，光工具定义就从占据窗口的56%降到了4%。释放出的空间可以分配给检索文档或记忆，大幅提升整体输出质量。

### 6.2 Programmatic Tool Calling的Token收益

采用程序化工具调用（Programmatic Tool Calling）替代自然语言工具调用后：

- **Token消耗减少37%**：因为不需要在上下文中保留冗长的工具调用描述和自然语言解释
- **工具执行速度提升52%**：跳过了解析自然语言到程序调用的中间步骤
- **错误率降低28%**：减少了因自然语言歧义导致的误调用

### 6.3 Token Budget的优先级提升

截至2026年，Token Budget管理已从"推荐优化"升级为**"第一优先级可靠性问题"**：

```
Agent系统可靠性分级（2026）
                                        
┌────────────────────────────────────────────────────┐
│  P0 (停机级)   Token Budget管理                    │
│                 上下文窗口溢出 = 系统不可用          │
├────────────────────────────────────────────────────┤
│  P1 (严重)     Prompt Cache击穿                    │
│                 缓存失效 → 延迟飙升 → 用户体验下降   │
├────────────────────────────────────────────────────┤
│  P2 (一般)     工具选择准确率                      │
│                 受上下文压缩质量影响                 │
├────────────────────────────────────────────────────┤
│  P3 (轻微)     输出格式一致性                      │
│                 受系统指令截断影响                   │
└────────────────────────────────────────────────────┘
```

**核心原因**：当Token Budget失控导致上下文溢出时，模型的行为不再是"变差"而是"不可预测"——截断点之后的所有关键信息都会丢失，工具调用失败、安全规则失效、记忆被清零。这是任何生产系统都无法接受的可靠性风险。
