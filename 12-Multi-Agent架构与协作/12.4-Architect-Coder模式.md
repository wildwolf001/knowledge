# 12.4 Architect-Coder 模式

> Architect-Coder 模式将软件开发的"设计"和"实现"两个阶段分离为两个独立的 Agent：Architect Agent 负责规划和设计，Coder Agent 负责编码实现。这种关注点分离（Separation of Concerns）降低了每个 Agent 的认知负担，提高了代码质量和可验证性。

---

## 一、模式概述

### 1.1 核心思想

Architect-Coder 模式是**两阶段接力式协作**的典型代表：

```
[用户需求] → [Architect Agent] → [设计文档] → [Coder Agent] → [代码实现]
                设计阶段                       实现阶段
```

**关键原则**：
- **关注点分离**：Architect 关注"做什么"（What），Coder 关注"怎么做"（How）
- **接力式协作**：两个 Agent **串行**工作，不是同时执行
- **契约驱动**：Architect 的输出（设计文档）是 Coder 的输入契约（Contract），Coder 不需要再次理解原始需求

### 1.2 与 Orchestrator-Worker 的区别

| 维度 | Orchestrator-Worker（12.3） | Architect-Coder |
|------|---------------------------|----------------|
| 协作方式 | 并行分发 | 串行接力 |
| 任务特征 | 多任务可并行 | 强依赖的前后阶段 |
| Agent 关系 | 控制-被控制 | 平等接力 |
| 反馈循环 | Orchestrator 聚合 | Coder → Architect 反馈（迭代） |
| 适用场景 | 搜索-分析-生成流水线 | 代码生成、方案设计 |

## 二、架构设计

### 2.1 双 Agent 通信拓扑

```
阶段 1：设计（Design Phase）
                    ┌─────────────────────┐
                    │     Architect        │
                    │  LLM + Prompt 工程    │
                    └─────────┬───────────┘
                              │
                    ┌─────────▼───────────┐
                    │    设计文档           │
                    │  - 架构图（ASCII）    │
                    │  - 数据模型          │
                    │  - API 规范          │
                    │  - 技术选型          │
                    │  - 文件结构          │
                    └─────────────────────┘
                    
阶段 2：实现（Implementation Phase）
                    ┌─────────────────────┐
                    │     Coder            │
                    │  LLM + 文件系统工具   │
                    └─────────┬───────────┘
                              │
                    ┌─────────▼───────────┐
                    │    源代码            │
                    │  - 按规范实现        │
                    │  - 单元测试          │
                    │  - 文档注释          │
                    └─────────────────────┘

可选阶段 3：审查（Review Phase）
                    ┌─────────────────────┐
                    │     Reviewer         │
                    │  LLM + 代码分析工具   │
                    └─────────┬───────────┘
                              │
                    ┌─────────▼───────────┐
                    │    审查报告          │
                    │  → Coder 修复 /     │
                    │  → Architect 修改设计│
                    └─────────────────────┘
```

### 2.2 职责边界

| 决策项 | Architect 负责 | Coder 负责 |
|--------|---------------|-----------|
| 技术栈 | 选择（Python + FastAPI vs Go + Gin） | 遵循选择 |
| 数据模型 | 定义实体、字段、关系 | 实现 ORM 模型 |
| API 设计 | 定义端点、请求/响应格式 | 实现路由和 handler |
| 文件结构 | 规划目录组织 | 按约定创建文件 |
| 代码风格 | 指定规范（如 Google Python Style） | 遵守规范 |
| 测试策略 | 定义测试范围和方法 | 编写测试用例 |
| 错误处理 | 定义错误码和异常层次 | 实现异常处理 |
| 性能要求 | 定义性能目标 | 优化实现 |

## 三、完整实现代码

### 3.1 Architect Agent

Architect Agent 的核心工作是将用户需求转换为**结构化的设计文档**：

```python
from dataclasses import dataclass, field
from typing import List, Optional, Dict, Any
import json
import asyncio


@dataclass
class DataModel:
    """数据模型定义"""
    name: str
    fields: List[Dict[str, str]]  # [{"name": "id", "type": "int", "constraints": "PK"}]
    relationships: List[Dict[str, str]] = field(default_factory=list)


@dataclass
class APISpec:
    """API 规范"""
    endpoint: str
    method: str  # GET/POST/PUT/DELETE
    request_schema: Dict
    response_schema: Dict
    description: str


@dataclass
class FileStructure:
    """文件结构规划"""
    path: str
    type: str  # "file" | "directory"
    description: str
    children: List['FileStructure'] = field(default_factory=list)


@dataclass
class DesignDocument:
    """
    完整的架构设计文档。
    这是 Architect → Coder 的契约。
    """
    project_name: str
    description: str
    tech_stack: Dict[str, str]  # {"language": "Python", "framework": "FastAPI", ...}
    data_models: List[DataModel]
    api_specs: List[APISpec]
    file_structure: List[FileStructure]
    conventions: List[str]  # 编码规范
    constraints: List[str]  # 约束条件
    error_handling: str     # 错误处理策略
    testing_strategy: str   # 测试策略
    additional_notes: str   # 补充说明


class ArchitectAgent:
    """
    Architect Agent —— 需求分析 + 架构设计
    
    输入：用户自然语言需求
    输出：DesignDocument（结构化设计文档）
    """
    
    def __init__(self, llm: Any, model_name: str = "gpt-4"):
        """
        Architect Agent 通常使用能力更强的模型，
        因为它需要做架构决策和技术选型。
        """
        self.llm = llm
        self.model_name = model_name  # 建议使用能力最强的模型
    
    async def design(self, user_request: str, 
                     context: Optional[Dict] = None) -> DesignDocument:
        """
        根据用户需求生成架构设计。
        
        Args:
            user_request: 用户的自然语言需求描述
            context: 可选的上下文信息（现有代码库、技术限制等）
        
        Returns:
            DesignDocument: 结构化设计文档
        """
        context_str = ""
        if context:
            context_str = f"""
            上下文约束：
            - 现有技术栈：{context.get('tech_stack', '无限制')}
            - 必须兼容：{context.get('compatibility', '无要求')}
            - 特殊约束：{context.get('constraints', '无')}
            """
        
        design_prompt = f"""
        你是一名资深软件架构师（Architect）。请根据以下用户需求设计系统架构。
        
        用户需求：
        {user_request}
        
        {context_str}
        
        请输出 JSON 格式的设计文档，包含以下部分：
        
        1. tech_stack: 技术栈选择（语言、框架、数据库、第三方服务）
        2. data_models: 数据模型定义（实体、字段、关系）
        3. api_specs: API 规范（端點、方法、请求响应格式）
        4. file_structure: 文件/目录结构规划
        5. conventions: 编码规范和约定
        6. constraints: 设计约束和限制条件
        7. error_handling: 错误处理策略
        8. testing_strategy: 测试方案
        
        设计原则：
        - 保持简单，不过度设计
        - 遵循 SOLID 原则
        - 考虑可扩展性和可维护性
        - 清晰的关注点分离
        - 详细的类型定义
        
        注意：输出必须是合法 JSON，不要包含 JSON 之外的文字。
        """
        
        response = await self.llm.complete(
            design_prompt,
            model=self.model_name,
            response_format={"type": "json_object"}
        )
        
        return self._parse_design(response)
    
    def _parse_design(self, response: str) -> DesignDocument:
        """解析 LLM 返回的 JSON 为设计文档"""
        data = json.loads(response)
        
        # 将原始数据转换为结构化 DesignDocument
        return DesignDocument(
            project_name=data.get("project_name", "untitled"),
            description=data.get("description", ""),
            tech_stack=data.get("tech_stack", {}),
            data_models=[
                DataModel(**m) for m in data.get("data_models", [])
            ],
            api_specs=[
                APISpec(**a) for a in data.get("api_specs", [])
            ],
            file_structure=self._parse_file_structure(
                data.get("file_structure", [])
            ),
            conventions=data.get("conventions", []),
            constraints=data.get("constraints", []),
            error_handling=data.get("error_handling", ""),
            testing_strategy=data.get("testing_strategy", ""),
            additional_notes=data.get("additional_notes", "")
        )
    
    def _parse_file_structure(self, items: List[Dict]) -> List[FileStructure]:
        """递归解析文件结构"""
        result = []
        for item in items:
            children = item.pop("children", [])
            fs = FileStructure(**item)
            fs.children = self._parse_file_structure(children)
            result.append(fs)
        return result
```

### 3.2 Coder Agent

Coder Agent 根据设计文档实现代码：

```python
class CoderAgent:
    """
    Coder Agent —— 根据设计文档实现代码
    
    输入：DesignDocument（来自 Architect）
    输出：生成的源代码文件
    """
    
    def __init__(self, llm: Any, 
                 file_system_tool: Any,  # 文件写入工具
                 model_name: str = "gpt-4"):
        self.llm = llm
        self.file_system = file_system_tool
        self.model_name = model_name
    
    async def implement(self, design: DesignDocument,
                        target_dir: str) -> List[str]:
        """
        根据设计文档实现代码。
        
        Args:
            design: Architect 产出的设计文档
            target_dir: 代码生成的目标目录
        
        Returns:
            List[str]: 生成的文件路径列表
        """
        generated_files = []
        
        # Step 1: 创建目录结构
        await self._create_structure(design.file_structure, target_dir)
        
        # Step 2: 逐个文件生成
        for file_spec in self._flatten_files(design.file_structure):
            code = await self._generate_file(design, file_spec)
            file_path = f"{target_dir}/{file_spec.path}"
            await self.file_system.write(file_path, code)
            generated_files.append(file_path)
        
        # Step 3: 生成配置文件（requirements.txt, package.json 等）
        configs = await self._generate_configs(design)
        for config_path, content in configs.items():
            full_path = f"{target_dir}/{config_path}"
            await self.file_system.write(full_path, content)
            generated_files.append(full_path)
        
        return generated_files
    
    async def _generate_file(self, design: DesignDocument, 
                             file_spec: FileStructure) -> str:
        """生成单个文件的内容"""
        # 构建文件生成的上下文
        context = self._build_file_context(design, file_spec)
        
        implementation_prompt = f"""
        你是一名资深程序员（Coder）。请根据以下架构设计文档，实现指定的文件。
        
        ## 项目概览
        {design.description}
        
        ## 技术栈
        {json.dumps(design.tech_stack, indent=2)}
        
        ## 编码规范
        {chr(10).join(f"- {c}" for c in design.conventions)}
        
        ## 数据模型
        {json.dumps([vars(m) for m in design.data_models], indent=2, default=str)}
        
        ## API 规范
        {json.dumps([vars(a) for a in design.api_specs], indent=2, default=str)}
        
        ## 待生成的文件
        路径: {file_spec.path}
        描述: {file_spec.description}
        类型: {file_spec.type}
        
        ## 错误处理策略
        {design.error_handling}
        
        ## 额外约束
        {chr(10).join(f"- {c}" for c in design.constraints)}
        
        请只输出该文件的完整代码，不要输出解释或其他文件的内容。
        代码需要：
        1. 完整的 import 语句
        2. 完整的类型注解
        3. 完整的 docstring
        4. 遵循指定的编码规范
        5. 包含错误处理
        """
        
        return await self.llm.complete(
            implementation_prompt,
            model=self.model_name
        )
    
    def _build_file_context(self, design: DesignDocument, 
                           file_spec: FileStructure) -> str:
        """构建文件生成的上文信息"""
        # 确定该文件需要知道哪些其他文件的接口
        # 例如 model.py 需要知道 data_models 的定义
        context_parts = [f"Generating: {file_spec.path}"]
        
        if "model" in file_spec.path.lower():
            context_parts.append(
                f"Data models: {[m.name for m in design.data_models]}"
            )
        elif "api" in file_spec.path.lower() or "route" in file_spec.path.lower():
            context_parts.append(
                f"API specs: {[a.endpoint for a in design.api_specs]}"
            )
        
        return "\n".join(context_parts)
    
    async def _create_structure(self, structures: List[FileStructure], 
                                base_dir: str):
        """递归创建目录结构"""
        for item in structures:
            path = f"{base_dir}/{item.path}"
            if item.type == "directory":
                await self.file_system.mkdir(path)
                if item.children:
                    await self._create_structure(item.children, base_dir)
    
    def _flatten_files(self, structures: List[FileStructure]) -> List[FileStructure]:
        """展平文件树，只返回文件"""
        files = []
        for item in structures:
            if item.type == "file":
                files.append(item)
            if item.children:
                files.extend(self._flatten_files(item.children))
        return files
    
    async def _generate_configs(self, design: DesignDocument) -> Dict[str, str]:
        """生成项目配置文件"""
        configs = {}
        tech = design.tech_stack
        
        if "Python" in tech.get("language", ""):
            # 生成 requirements.txt
            deps = ["fastapi", "uvicorn", "pydantic"]
            if "sqlalchemy" in str(design.data_models):
                deps.append("sqlalchemy")
            configs["requirements.txt"] = "\n".join(deps)
        
        return configs
```

### 3.3 反馈与迭代

Coder 完成实现后，可以触发一个**审查循环**：

```python
class ReviewCycle:
    """
    Architect-Coder 的审查迭代循环。
    允许 Coder 向 Architect 反馈问题，或 Reviewer 审查代码质量。
    """
    
    MAX_ITERATIONS = 3  # 最大迭代次数
    
    async def run_with_review(self, user_request: str, 
                              architect: ArchitectAgent,
                              coder: CoderAgent,
                              reviewer: Optional['ReviewerAgent'] = None) -> Dict:
        """
        带审查的完整 Architect-Coder 流程。
        
        流程：
        1. Architect 设计
        2. Coder 实现
        3. (可选) Reviewer 审查
        4. 如果有问题，回到步骤 1 或 2
        """
        iteration = 0
        design = None
        files = []
        review_results = []
        
        while iteration < self.MAX_ITERATIONS:
            iteration += 1
            
            # Phase 1: Architect 设计/修改设计
            design = await architect.design(
                user_request, 
                context={"iteration": iteration, 
                         "previous_reviews": review_results}
            )
            
            # Phase 2: Coder 实现
            files = await coder.implement(design, target_dir="./generated")
            
            # Phase 3: 代码审查
            if reviewer:
                review = await reviewer.review(design, files)
                review_results.append(review)
                
                if review.approved:
                    break
                else:
                    # 将审查意见反馈给 Architect 和 Coder
                    architect.add_feedback(review.feedback)
                    coder.add_feedback(review.feedback)
            else:
                break  # 没有 Reviewer，一轮即止
        
        return {
            "design": design,
            "files": files,
            "iterations": iteration,
            "reviews": review_results,
            "final_approved": review_results[-1].approved if review_results else True
        }
```

## 四、实践要点

### 4.1 Model 分配策略

| Agent | 推荐模型 | 理由 |
|-------|---------|------|
| **Architect** | 最强模型（GPT-4 / Claude 3.5 Sonnet） | 架构决策需要深度推理和全局理解 |
| **Coder** | 能力较强的模型（GPT-4 / Claude 3 Haiku） | 需要代码生成能力，但对架构理解要求较低 |
| **Reviewer** | 中等模型 | 只需要检测明显的问题，不需要深层推理 |

**成本优化**：Architect 每个会话只调用 1-2 次，Coder 每个文件调用 1 次。总 token 消耗通常比直接让一个大模型做所有事情更低，因为每个 Agent 的上下文更短、更聚焦。

### 4.2 常见失败模式

```
失败模式 1：过度设计
  Architect 设计了一个"完美"但过于复杂的方案。
  → 解决：在设计 Prompt 中强调"保持简单"（KISS原则）

失败模式 2：设计-实现偏差
  Coder 实现的代码与 Architect 的设计不一致。
  → 解决：Reviewer 检查实现是否符合设计，增加设计验证步骤

失败模式 3：上下文丢失
  Coder 在生成长文件时"遗忘"了设计文档中的某些细节。
  → 解决：将设计文档的关键部分嵌入文件生成的 Prompt 中

失败模式 4：双向不匹配
  Architect 选择的框架/库 Coder 不熟悉，导致实现质量低。
  → 解决：在 Architect 的 Prompt 中指定"优先选择 Coder 熟悉的技术栈"
```

### 4.3 设计文档的最佳实践

好的设计文档应该像一份**技术 spec**，而非需求说明书：

```
✓ 好的设计文档：
  - 每个 API 端点有明确的输入/输出 Schema
  - 数据模型的字段有类型和约束
  - 文件结构有明确的职责描述
  - 技术选型有理由说明

✗ 差的设计文档：
  - "用合适的框架"（太模糊）
  - "根据需要添加字段"（不完整）
  - "代码应该要健壮"（无法执行）
  - "按照最佳实践"（没有具体说明）
```

## 五、Architect-Coder 的变体

### 5.1 带测试的扩展（Architect-Coder-Tester）

```
[Architect] → 设计文档
    ↓
[Coder] → 实现代码
    ↓
[Tester] → 编写测试并运行
    ↓
[结果] → 测试通过？完成 | 测试失败 → Coder 修复
```

Tester Agent 承担了 Reviewer 的部分职责，但更专注于测试覆盖率和验证。

### 5.2 多 Coder 并行（Architect + N × Coder）

```
              ┌── [Coder A: Models]
              │
[Architect] ──┼── [Coder B: APIs]
              │
              └── [Coder C: Tests]
```

当项目规模较大时，Architect 的设计文档可以分发给多个 Coder Agent 并行实现不同模块。这实际上变成了 12.3 节 Orchestrator-Worker 的一个特例。

### 5.3 自然语言优先（Natural Language First）

Architect 的输出不一定是 JSON 设计文档，也可以是一份**详细的技术方案文档**（Markdown），然后 Coder 从文档中提取需要实现的 spec。这种方式更灵活，但需要 Coder 有较强的文档理解能力。

## 关键概念速查

| 术语 | 解释 |
|------|------|
| 关注点分离（Separation of Concerns） | 不同 Agent 负责不同层面的决策 |
| 接力式协作 | Agent 串行工作，前一 Agent 的输出是后一 Agent 的输入 |
| 契约驱动（Contract-Driven） | 设计文档是 Architect 和 Coder 之间的正式契约 |
| 审查循环（Review Cycle） | Coder 实现后由 Reviewer 审查，反馈修正的迭代过程 |
| 技术 Spec | 包含具体类型定义和接口规范的技术设计文档 |
| 设计-实现偏差 | Coder 实现与 Architect 设计不一致的问题 |
