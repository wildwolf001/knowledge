# 12.1 Single vs Multi 的决策边界

> **一个 Agent 搞不定的时候怎么办？** 多 Agent 协作能解决更复杂的问题，但协调是有代价的。本节分析何时值得引入多个 Agent，何时一个 Agent 就足够。

---

## 一、问题的本质：Agent 系统的"规模拐点"

### 1.1 什么是"协调开销"

多 Agent 系统的核心代价是**协调开销（Coordination Overhead）**——让多个 Agent 之间保持共识、传递信息、解决冲突所消耗的计算资源、延迟和工程复杂度。

协调开销的来源：

```
单 Agent 系统：
  输入 → [Agent] → 输出
  延迟 = T_model
  复杂度 = 1 个 Agent

多 Agent 系统：
  输入 → [Agent A] ─→ [Agent B] ─→ [Agent C] → 输出
            │            │            │
            └────消息传递──┴────结果合并──┘
  延迟 = T_model × N + T_comm × C(N)
  复杂度 = N 个 Agent + 通信拓扑 + 分歧解决
```

其中：
- `N` = Agent 数量
- `T_model` = 单个 Agent 推理时间
- `T_comm` = 一次 Agent 间通信延迟
- `C(N)` = 通信次数，与拓扑结构相关（广播为 O(N²)，Hub-Spoke 为 O(N)）

**关键洞察**：多 Agent 的收益并非线性增长，而是存在一个"规模拐点"——超过这个拐点，增加更多 Agent 带来的协调开销超过了能力增益。

### 1.2 什么时候一个 Agent 就够了？

以下场景中，多 Agent 引入的复杂度不可证伪（即："能用单 Agent 解决的问题，用多 Agent 不会更好"）：

| 场景 | 特征 | 示例 |
|------|------|------|
| **封闭域问答** | 输入/输出边界清晰，不需要多步推理 | "法国的首都是什么？" |
| **单一工具调用** | 只用一个 API 或工具就能完成 | "翻译这段文字到中文" |
| **确定性转换** | 输入到输出是确定的映射关系 | "把 CSV 转为 JSON" |
| **短上下文处理** | 上下文在一个模型窗口内，不需要分工 | "总结这篇 200 字的文章" |
| **顺序依赖链** | 步骤 A→B→C 严格串行，无并行空间 | "注册用户→发送邮件→返回结果" |

**单 Agent 的优势**：

```
单 Agent                         多 Agent
────────                          ────────
✓ 架构简单，无协调开销           ✗ 需要消息路由、序列化、状态管理
✓ 延迟可预测（单次推理）         ✗ 延迟 = 最慢的 Agent + 通信时间
✓ 调试容易（单一日志流）         ✗ 追踪跨 Agent 的调用链困难
✓ 无一致性问题                   ✗ 需要分歧解决机制
✓ 部署运维成本低                 ✗ N 倍的部署和监控开销
```

### 1.3 什么时候必须用多 Agent？

| 场景 | 特征 | 示例 |
|------|------|------|
| **异构能力需求** | 不同步骤需要不同专业能力 | 规划→编码→测试→审查 各需要不同专长 |
| **并行独立任务** | 多个子任务互不依赖，可并行 | 同时搜索 5 个不同数据源 |
| **信息不对称** | 不同 Agent 有不同知识/上下文 | 数据库 Agent vs Web 搜索 Agent |
| **安全隔离** | 需要权限分离 | 只读 Agent vs 可写 Agent |
| **长流程容错** | 需要隔离故障、部分失败处理 | 10 个步骤中某个失败不影响其他步骤 |

## 二、决策框架：何时引入多 Agent

### 2.1 三维度评估模型

将一个任务分解为三个维度来评估是否需要多 Agent：

```
               任务复杂度（高）
                     │
                     │  需要多 Agent
                     │  ●───────────●
                     │ /             \
               低 ←──●───────────────●──→ 专业隔离需求（高）
                     │                 \
                     │   单 Agent 也 OK  ● 绝对需要多 Agent
                     │                     （安全/权限原因）
                     │
                （低）
                协调容忍度（高）
```

**维度一：任务复杂度**
- 任务是否需要多个不同领域的专业知识？
- 任务是否需要在多个数据源中并行搜索？
- 任务的步骤数是否超过 5 步？

**维度二：专业隔离需求**
- 不同步骤是否需要不同的权限（读 vs 写）？
- 是否需要隔离"可能产生幻觉的部分"不影响核心逻辑？
- 是否需要让不同模型处理不同类型的信息（敏感 vs 公开）？

**维度三：协调容忍度**
- 任务对延迟的容忍度如何？
- 协调失败（Agent 间意见不一致）的代价有多大？
- 工程团队能否承担多 Agent 的运维复杂度？

### 2.2 决策矩阵

| 任务复杂度 | 专业隔离需求 | 协调容忍度 | 推荐方案 |
|-----------|------------|-----------|---------|
| 低 | 低 | 高 | **单 Agent** |
| 低 | 高 | 高 | **单 Agent + Guardrails**（第 14.2 节） |
| 中 | 低 | 中 | **单 Agent + 工具调用** |
| 中 | 中 | 高 | **2-3 个轻量 Agent**（如 Architect-Coder 模式，见 12.4 节） |
| 高 | 低 | 中 | **Orchestrator-Worker 模式**（见 12.3 节） |
| 高 | 高 | 高 | **完整多 Agent 架构**（Orchestrator + 多个 Worker） |
| 高 | 高 | 低 | **简化设计**：降低协调开销，或考虑人工工作流 |

### 2.3 成本收益分析

引入多 Agent 前，先做以下量化估算：

```
收益因子：
- Coverage Gain: 多 Agent 能覆盖单 Agent 无法处理的输入比例
- Quality Gain: 多 Agent 协作提升的准确率/完成率
- Resilience Gain: 单 Agent 失败时，多 Agent 的成功概率提升

代价因子：
- Latency Penalty: 额外增加的延迟（通常 2x-5x）
- Cost Penalty: 额外 token 消耗（通常 2x-10x）
- Complexity Penalty: 工程复杂度（部署、调试、维护）

决策公式（简化版）：
  引入多 Agent 的条件：
  ∑(Coverage + Quality + Resilience) > ∑(Latency + Cost + Complexity)
```

**经验法则**：

1. **2 倍原则**：如果单 Agent + 更好的 Prompt 工程能达到多 Agent 80% 的效果，就先用单 Agent。多 Agent 至少要有 2 倍以上的提升才值得引入。

2. **3 Agent 上限**：大多数团队在早期阶段，将 Agent 数量控制在 3 个以内是最优的。超过 3 个 Agent 后，协调复杂度呈指数级增长。

3. **渐进式引入**：不要一开始就设计 10 个 Agent 的系统。从单 Agent 开始 → 扩展到 2-3 个 → 按需增加。

## 三、单 Agent 的局限与多 Agent 的适配

### 3.1 单 Agent 的典型失败模式

```
失败模式 1：遗忘（Forgetting）
  长流程中，Agent 在步骤 7 忘记了步骤 1 已经完成的任务
  → 多 Agent 中，每个 Agent 只负责一个子问题，上下文更集中

失败模式 2：任务混淆（Task Confusion）
  Agent 在同一个上下文中处理"写代码"和"写测试"，切换代价高
  → 多 Agent 中，Coder Agent 只写代码，Tester Agent 只写测试

失败模式 3：幻觉级联（Hallucination Cascade）
  步骤 3 的一个错误被步骤 4-10 放大
  → 多 Agent 中，分歧解决机制（第 12.6 节）可以打断级联
```

### 3.2 多 Agent 的引入成本

| 成本项 | 单 Agent | 多 Agent（2-3个） | 多 Agent（>5个） |
|-------|---------|-----------------|-----------------|
| 推理 Token 消耗 | 1x | 2-3x | 5-10x |
| 端到端延迟 | 1x | 2-4x | 5-15x |
| 代码复杂度 | 低 | 中 | 高 |
| Agent 间通信代码 | 无 | 100-500 行 | 1000+ 行 |
| 测试用例数量 | 10-20 | 50-100 | 200+ |
| 调试难度 | 低 | 中 | 高 |

## 四、从单 Agent 到多 Agent 的迁移路径

### 4.1 推荐的渐进式路径

```
Step 1: 单 Agent（基线）
  ┌──────────────────────────────────┐
  │ [Agent] → 调用工具 → 输出结果      │
  │ 使用最好的 Prompt + Guardrails    │
  └──────────────────────────────────┘

Step 2: 单 Agent + 专业化工具
  ┌──────────────────────────────────┐
  │ [Agent] → 调用工具 A / B / C     │
  │ 工具本身就是"专业化 Agent"的雏形  │
  └──────────────────────────────────┘

Step 3: 2-Agent 架构（如 Architect-Coder，见 12.4）
  ┌──────────────────────────────────┐
  │ [Agent A: 规划] → [Agent B: 执行] │
  │ 最简洁的多 Agent 入门模式        │
  └──────────────────────────────────┘

Step 4: Orchestrator + N Workers（见 12.3）
  ┌──────────────────────────────────┐
  │ [Orchestrator]                   │
  │    ├── [Worker A: 搜索]          │
  │    ├── [Worker B: 分析]          │
  │    └── [Worker C: 生成]          │
  └──────────────────────────────────┘
```

### 4.2 经验证的反模式

```
✗ "让两个 Agent 做同样的事情然后对比结果"
  → 这几乎总是浪费 token。用 14.5 节的置信度评分更有效。

✗ "给我所有 Agent 都配上 GPT-4"
  → 90% 的 Agent 工作可以用小模型完成。大模型只给 Orchestrator 或需要推理的 Agent 用。

✗ "先设计 8 个 Agent 的架构图再编码"
  → 从 2 个 Agent 开始验证可行性，再逐步扩展。

✗ "My Agent can talk to your Agent"
  → 避免让 Agent 之间自由对话。总是通过结构化的通信协议交换消息。
```

## 五、边界案例讨论

### 5.1 模糊地带：可能单 Agent 也可能多 Agent

一个典型的例子是代码生成任务：

```
场景：生成一个带数据库操作的 REST API

单 Agent 方案：
  [Agent] 分析需求 → 设计架构 → 写代码 → 生成测试
  优势：上下文连贯，Agent 对整个代码库有全局理解
  劣势：提示词太长，可能遗漏某些细节

多 Agent 方案（Architect-Coder，见 12.4）：
  [Architect Agent] 设计 API 规范和数据模型
  [Coder Agent] 根据规范实现代码
  优势：关注点分离，每个 Agent 的上下文更精简
  劣势：Architect 可能设计出 Coder 难以实现的方案
```

**决策建议**：对于代码生成，如果业务逻辑复杂度低于 5 个实体类型，用单 Agent；超过则用 Architect-Coder。这是实践中积累的"经验阈值"。

### 5.2 动态决策：运行时判断

高级架构可以在运行时动态判断是否启动多 Agent：

```python
def should_use_multi_agent(task: Task) -> bool:
    """运行时判断是否启用多 Agent"""
    # 条件 1：任务复杂度
    if len(task.subtasks) > 3:
        return True
    
    # 条件 2：需要异构能力
    required_skills = analyze_required_skills(task)
    if len(required_skills) > 2:
        return True
    
    # 条件 3：单 Agent 先尝试，置信度低则升级
    if task.criticality > CRITICAL_HIGH:
        return True  # 关键任务默认用多 Agent 提高可靠性
    
    return False  # 默认单 Agent
```

这种模式结合了两种方案的优点：简单任务走快速路径，复杂任务自动升级为多 Agent。

## 关键概念速查

| 术语 | 解释 |
|------|------|
| 协调开销（Coordination Overhead） | 多 Agent 间通信、同步、解决冲突的资源消耗 |
| 规模拐点 | 超过该点后增加 Agent 的协调代价超过能力增益 |
| 异构能力 | 不同 Agent 拥有不同的专业知识和工具 |
| 专业隔离 | 因权限/安全需求将不同职责分配给不同 Agent |
| 渐进式迁移 | 从单 Agent 开始逐步引入更多 Agent 的工程策略 |
| 运行时判断 | 根据任务特征在运行时动态决定是否使用多 Agent |
