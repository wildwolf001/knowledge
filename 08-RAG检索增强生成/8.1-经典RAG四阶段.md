# 8.1 经典 RAG 四阶段：Index → Retrieve → Augment → Generate

> RAG（Retrieval-Augmented Generation，检索增强生成）是当前 Agent 工程中最重要的架构范式之一。它将外部知识检索与 LLM 的生成能力相结合，以解决大模型知识过时、幻觉和领域适配等问题。经典 RAG 流水线由四个阶段构成：**Index（索引）→ Retrieve（检索）→ Augment（增强）→ Generate（生成）**，每个阶段都有独特的工程挑战。

---

## 一、RAG 架构总览

### 1.1 为什么需要 RAG？

LLM 本身存在三个难以克服的局限：

| 局限 | 描述 | RAG 的解决方式 |
|------|------|----------------|
| **知识截止** | 训练数据有截止日期，无法获知最新信息 | 实时检索最新文档 |
| **领域盲区** | 对私有/专业领域知识缺乏了解 | 注入企业知识库 |
| **事实幻觉** | 模型可能编造看起来合理但错误的内容 | 提供事实依据，约束生成 |

**核心洞察**：RAG 不是在"教"模型新知识，而是在**推理时向模型提供相关上下文**，让模型做一个"开卷考试"而非"闭卷考试"。

### 1.2 四阶段流水线架构

```
                           ┌─────────────────────────────┐
                           │       原始文档集合            │
                           │  (PDF/HTML/DB/Confluence...) │
                           └──────────┬──────────────────┘
                                      │
                          ┌───────────▼───────────┐
          阶段 1: Index    │   文档预处理与索引构建    │
                          │ • 文档解析 (Parser)      │
                          │ • 分块 (Chunking)        │
                          │ • Embedding 向量化       │
                          │ • 构建倒排索引 + 向量索引  │
                          └───────────┬───────────┘
                                      │ 索引存储
                          ┌───────────▼───────────┐
          阶段 2: Retrieve │     检索阶段            │
                          │ • Query Embedding      │
                          │ • 向量检索 (ANN)        │
                          │ • 关键词检索 (BM25)     │
                          │ • 混合检索 + Rerank     │
                          └───────────┬───────────┘
                                      │ Top-K 文档块
                          ┌───────────▼───────────┐
          阶段 3: Augment  │     增强阶段            │
                          │ • 构建 Prompt 上下文    │

                                      │ 增强后的 Prompt
                          ┌───────────▼───────────┐
          阶段 4: Generate │     生成阶段            │
                          │ • LLM 推理             │
                          │ • Token 流式输出        │
                          │ • 后处理与格式校验        │
                          │ • 引用验证              │
                          └───────────┬───────────┘
                                      │
                                 最终回答
```

## 二、阶段 1：Index（索引构建）

索引阶段的目标是将非结构化的原始文档转化为可高效检索的结构化索引。这是整个 RAG 系统的**地基**——索引质量直接决定了检索上限。

### 2.1 文档解析

原始文档格式多样，需要针对不同格式设计解析器：

| 格式 | 解析工具 | 常见问题 |
|------|---------|----------|
| PDF | PyMuPDF, pdfplumber, marker | 表格错乱、多栏布局、OCR 识别错误 |
| HTML | BeautifulSoup, trafilatura | 导航栏/广告噪声、动态渲染内容 |
| Markdown | 正则解析 | 代码块和表格的边界识别 |
| Word/DOCX | python-docx | 样式信息丢失、嵌入式对象 |
| 图片/扫描件 | OCR (Tesseract, Azure Form Recognizer) | 识别准确率不足、版面分析 |

```python
# 示例：PDF 解析与清洗
import pdfplumber

def parse_pdf(file_path: str) -> list[dict]:
    """解析 PDF 文档，返回按页划分的文本块"""
    pages = []
    with pdfplumber.open(file_path) as pdf:
        for i, page in enumerate(pdf.pages):
            text = page.extract_text()
            # 清洗：移除多余空白、修复断行
            text = clean_text(text)
            pages.append({
                "page_num": i + 1,
                "text": text,
                "metadata": {
                    "source": file_path,
                    "page": i + 1
                }
            })
    return pages

def clean_text(text: str) -> str:
    """基础文本清洗"""
    import re
    # 合并断行（英文中连字符断行）
    text = re.sub(r'(\w)-\n(\w)', r'\1\2', text)
    # 移除多余空白行
    text = re.sub(r'\n{3,}', '\n\n', text)
    return text.strip()
```

### 2.2 分块（Chunking）

分块策略直接影响检索的粒度与召回率。详见第 8.2 节，这里简要列出分块在 Index 阶段的关键决策点：

- **块大小**：通常在 256-1024 tokens 之间，取决于 Embedding 模型的最大输入长度和检索任务的需求
- **块重叠（Overlap）**：相邻块之间保留 10-20% 的重叠内容，防止语义被截断
- **分块策略选择**：固定大小分块简单但召回率低；语义分块效果好但计算成本高

### 2.3 Embedding 向量化

将文本块转换为稠密向量（Dense Vector），详见第 3.1 节。

```python
from sentence_transformers import SentenceTransformer

# 加载 Embedding 模型（常用选择）
# - BAAI/bge-large-zh-v1.5: 中文场景首选
# - intfloat/multilingual-e5-large: 多语言场景
# - text-embedding-3-large: OpenAI 方案
model = SentenceTransformer("BAAI/bge-large-zh-v1.5")

def embed_chunks(chunks: list[dict]) -> list[dict]:
    """对分块结果进行向量化"""
    texts = [chunk["text"] for chunk in chunks]
    embeddings = model.encode(
        texts,
        normalize_embeddings=True,  # 归一化后可直接用点积计算相似度
        show_progress_bar=True,
        batch_size=64
    )
    for chunk, emb in zip(chunks, embeddings):
        chunk["embedding"] = emb.tolist()
    return chunks
```

### 2.4 索引存储

向量化后的数据需要存入专门的存储系统：

| 存储方案 | 适用场景 | 优缺点 |
|----------|---------|--------|
| FAISS (Facebook AI Similarity Search) | 本地/单机 | 检索极快，但不支持实时更新 |
| Milvus | 大规模生产 | 分布式，支持 CRUD，运维复杂 |
| Chroma | 快速原型 | 简单易用，性能一般 |
| Elasticsearch | 已有 ES 基础设施 | 支持向量+关键词混合检索 |
| PGVector (PostgreSQL) | 需要关系查询 | 与业务数据关联方便，性能受限于 PG |

```python
# 示例：FAISS 索引构建
import faiss
import numpy as np

def build_faiss_index(embeddings: list[list[float]], dimension: int = 768):
    """构建 FAISS 索引"""
    index = faiss.IndexFlatIP(dimension)  # 内积索引（归一化后等价于余弦相似度）
    embeddings_np = np.array(embeddings).astype('float32')
    index.add(embeddings_np)
    return index
```

### 2.5 阶段 1 的工程挑战

**挑战 1：分块边界破坏语义**
当一个完整的语义单元（如一段代码、一个表格）被分到两个不同的块中，检索时两个块都无法完整表达该语义。解决方案：使用语义分块（详见 8.2 节）。

**挑战 2：Embedding 维度选择的权衡**
- 低维度（256-384）：检索快，但语义表达能力有限
- 高维度（1024+）：语义表达好，但存储成本和检索延迟显著上升

**挑战 3：索引更新策略**
- 实时更新：每次文档变更都重建索引，保证新鲜度，但计算成本高
- 批量更新：定时重建全量索引，成本低但有时延
- 增量更新：只更新变更部分，需要支持删除和插入的索引结构

## 三、阶段 2：Retrieve（检索）

检索阶段的目标是从海量索引中找到与用户查询最相关的 K 个文档块。

### 3.1 检索流程

```
用户查询 "2024年AI芯片市场占比"
         │
         ▼
┌─────────────────────┐
│ 查询预处理            │

│ • 去除停用词          │

└─────────┬───────────┘

│  ┌──────────────┐   │
│  │ 向量检索       │   │  ← Dense Retrieval (cosine sim)

│  └──────┬───────┘   │
│         │           │
```

### 3.2 向量检索（Dense Retrieval）

将查询文本用同样的 Embedding 模型编码，然后在向量空间中进行近似最近邻搜索（ANN, Approximate Nearest Neighbor）：

```python
def dense_retrieve(query: str, index, chunks: list[dict], top_k: int = 10):
    """向量检索"""
    query_emb = model.encode([query], normalize_embeddings=True)
    scores, indices = index.search(np.array(query_emb).astype('float32'), top_k)
    results = []
    for score, idx in zip(scores[0], indices[0]):
        results.append({
            "chunk": chunks[idx],
            "score": float(score),
            "method": "dense"
        })
    return results
```

### 3.3 关键词检索（Sparse Retrieval）

使用 BM25 算法，基于词频和逆文档频率计算相关性：

```python
from rank_bm25 import BM25Okapi

def build_bm25_index(chunks: list[dict]):
    """构建 BM25 索引"""
    tokenized_chunks = [chunk["text"].split() for chunk in chunks]
    bm25 = BM25Okapi(tokenized_chunks)
    return bm25

def sparse_retrieve(query: str, bm25, chunks: list[dict], top_k: int = 10):
    """BM25 检索"""
    tokenized_query = query.split()
    scores = bm25.get_scores(tokenized_query)
    top_indices = scores.argsort()[-top_k:][::-1]
    results = []
    for idx in top_indices:
        results.append({
            "chunk": chunks[idx],
            "score": float(scores[idx]),
            "method": "sparse"
        })
    return results
```

### 3.4 阶段 2 的工程挑战

**挑战 1：检索噪声**
Top-K 结果中总有一些不相关的"噪声"文档，会误导 LLM 生成错误的回答（详见 8.7 节）。

**挑战 2：语义鸿沟（Semantic Gap）**
用户的查询表述和文档的表述方式之间存在词法差异。例如用户问"怎么治感冒"，但文档写的是"上呼吸道感染的临床处理"。解决方案：查询扩展（Query Expansion）和混合检索。

**挑战 3：检索延迟与覆盖率的权衡**
- 召回更多的候选（增加 K 值）提高召回率但降低精确率和增加 LLM 推理的 token 消耗
- 实践中 K 通常在 3-10 之间

## 四、阶段 3：Augment（增强）

增强阶段的核心任务是将检索到的文档块与原始问题组织成 LLM 的输入，让 LLM 在"有上下文参考"的条件下生成回答。

### 4.1 Prompt 模板设计

```python
AUGMENT_PROMPT_TEMPLATE = """你是一位专业的 AI 助手。请基于以下提供的参考文档来回答用户的问题。

## 回答要求
1. 如果参考文档包含足够信息，请给出准确回答并标注引用来源 [来源编号]
2. 如果参考文档信息不足，请明确告知"根据提供的资料无法完整回答"
3. 不要编造事实或使用参考文档之外的信息
4. 如果参考文档之间存在矛盾，请指出矛盾点

## 参考文档
{% for doc in documents %}
[来源 {{ doc.id }}]
{{ doc.text }}
{% endfor %}

## 用户问题
{{ query }}

## 请给出你的回答："""
```

### 4.2 增强策略的演进

| 策略 | 描述 | 适用场景 |
|------|------|----------|
| **简单拼接** | 直接将 Top-K 文档拼接到 Prompt 中 | 原型验证 |
| **重排序剪枝** | Rerank 后只保留高置信度的文档 | 提高精确率 |
| **摘要压缩** | 用 LLM 对检索结果做摘要后再输入 | 减少 token 消耗 |
| **分步检索** | 先生成中间推理，再检索所需信息 | 复杂推理问题 |

### 4.3 上下文窗口管理

LLM 的上下文窗口是有限的（通常 8K-128K tokens），这带来了几个工程问题：

1. **窗口溢出**：当检索的文档过长时，需要截断或压缩
2. **"中间迷失"问题**：研究发现 LLM 对长上下文中间部分的信息利用效果最差

```python
def build_context(documents: list[dict], max_tokens: int = 4000):
    """构建受限上下文，按相关性从高到低排列"""
    # 按相关性分数降序排列
    sorted_docs = sorted(documents, key=lambda x: x.get("score", 0), reverse=True)
    
    context_parts = []
    total_tokens = 0
    
    for doc in sorted_docs:
        doc_tokens = estimate_tokens(doc["text"])
        if total_tokens + doc_tokens > max_tokens:
            # 截断最后一个文档
            remaining = max_tokens - total_tokens
            truncated = truncate_text(doc["text"], remaining)
            context_parts.append(truncated)
            break
        context_parts.append(doc["text"])
        total_tokens += doc_tokens
    
    return "\n\n".join(context_parts)
```

### 4.4 阶段 3 的工程挑战

**挑战 1：提示注入（Prompt Injection）**
恶意的检索文档可能包含提示注入攻击，操控 LLM 的行为。需要在 Augment 阶段进行输入清洗和分隔符转义。

**挑战 2：信息冗余**
多个检索文档可能包含重叠的信息，既浪费 token 又可能引入矛盾。需要去重（Deduplication）。

**挑战 3：引用标注的准确性**
LLM 可能错误地引用来源——引用了文档 A 但实际内容来自文档 B，或者编造不存在的内容来源。这是 14.4 节讨论的核心问题。

## 五、阶段 4：Generate（生成）

生成阶段是 LLM 基于增强后的 Prompt 产生最终回答的过程。

### 5.1 生成控制参数

```python
def generate_with_rag(
    prompt: str,
    model="gpt-4o",
    temperature=0.3,     # 低温度 → 更确定性，降低幻觉
    top_p=0.9,
    max_tokens=2048,
    stream=True
):
    """RAG 生成阶段，使用低温度提高事实准确性"""
    response = openai.chat.completions.create(
        model=model,
        messages=[
            {"role": "system", "content": "你是一个基于检索文档回答问题的助手。"},
            {"role": "user", "content": prompt}
        ],
        temperature=temperature,
        top_p=top_p,
        max_tokens=max_tokens,
        stream=stream
    )
    return response
```

### 5.2 引用输出格式

好的 RAG 系统应该在输出中包含引用标记，让用户能追溯信息来源：

```python
# 带引用的输出格式示例
{
  "answer": "2024年全球AI芯片市场规模达到580亿美元[1]，其中NVIDIA占据约80%的市场份额[1][2]。",
  "citations": [
    {"id": "1", "source": "2024 AI Industry Report.pdf", "page": 12},
    {"id": "2", "source": "Market Analysis Q4 2024.docx", "page": 5}
  ]
}
```

### 5.3 阶段 4 的工程挑战

**挑战 1：引用幻觉**
模型可能在输出中添加看起来可信但实际上不存在的引用索引。这也是 14.4 节中提到的引用溯源问题。

**挑战 2：忠实性（Faithfulness）**
模型是否真的基于检索内容生成，还是忽略检索内容继续"自由发挥"？

**挑战 3：输出格式控制**
需要保证输出格式的一致性（JSON、Markdown 等），以便下游系统解析。

## 六、工程实践：端到端 RAG 流水线

```python
class BasicRAGPipeline:
    """经典 RAG 四阶段流水线"""
    
    def __init__(self, embedding_model: str = "BAAI/bge-large-zh-v1.5"):
        self.embedder = SentenceTransformer(embedding_model)
        self.index = None
        self.chunks = []
        self.bm25 = None
    
    def stage1_index(self, documents: list[dict]):
        """阶段 1: 索引构建"""
        print("[Stage 1] Indexing documents...")
        parsed = [parse_pdf(doc["path"]) for doc in documents]
        self.chunks = [chunk for pages in parsed for chunk in pages]
        embeddings = self.embedder.encode(
            [c["text"] for c in self.chunks], normalize_embeddings=True
        )
        dim = embeddings.shape[1]
        self.index = faiss.IndexFlatIP(dim)
        self.index.add(np.array(embeddings).astype('float32'))
        self.bm25 = build_bm25_index(self.chunks)
        print(f"  Indexed {len(self.chunks)} chunks")
    
    def stage2_retrieve(self, query: str, top_k: int = 5):
        """阶段 2: 检索"""
        print("[Stage 2] Retrieving...")
        dense_results = dense_retrieve(query, self.index, self.chunks, top_k * 2)
        sparse_results = sparse_retrieve(query, self.bm25, self.chunks, top_k * 2)
        # RRF 融合
        combined = self._rrf_fuse(dense_results, sparse_results)
        return combined[:top_k]
    
    def _rrf_fuse(self, results1, results2, k=60):
        """Reciprocal Rank Fusion"""
        scores = {}
        for rank, r in enumerate(results1):
            chunk_id = id(r["chunk"])
            scores[chunk_id] = scores.get(chunk_id, 0) + 1 / (k + rank + 1)
        for rank, r in enumerate(results2):
            chunk_id = id(r["chunk"])
            scores[chunk_id] = scores.get(chunk_id, 0) + 1 / (k + rank + 1)
        sorted_ids = sorted(scores, key=scores.get, reverse=True)
        seen = set()
        fused = []
        for cid in sorted_ids:
            if cid not in seen:
                seen.add(cid)
                fused.append({"chunk": next(r["chunk"] for r in results1 + results2 if id(r["chunk"]) == cid), "score": scores[cid]})
        return fused
    
    def stage3_augment(self, query: str, documents: list[dict]):
        """阶段 3: 增强"""
        print("[Stage 3] Augmenting...")
        return AUGMENT_PROMPT_TEMPLATE.render(
            query=query,
            documents=documents
        )
    
    def stage4_generate(self, prompt: str):
        """阶段 4: 生成"""
        print("[Stage 4] Generating...")
        response = openai.chat.completions.create(
            model="gpt-4o",
            messages=[
                {"role": "system", "content": "你是一个严谨的 AI 助手，严格依据参考文档回答问题。"},
                {"role": "user", "content": prompt}
            ],
            temperature=0.3,
            max_tokens=2048
        )
        return response.choices[0].message.content
    
    def query(self, user_query: str):
        """端到端 RAG 查询"""
        retrieved = self.stage2_retrieve(user_query)
        augmented_prompt = self.stage3_augment(user_query, retrieved)
        answer = self.stage4_generate(augmented_prompt)
        return answer
```

## 七、四阶段的核心权衡矩阵

| 阶段 | 核心指标 | 主要瓶颈 | 优化方向 |
|------|----------|----------|----------|
| Index | 召回率上限（Oracle Recall） | 分块策略、Embedding 质量 | 语义分块、领域微调 Embedding |
| Retrieve | Hit Rate / MRR | 检索延迟、语义鸿沟 | 混合检索、Query 重写 |
| Augment | 上下文利用率 | token 预算、信息冗余 | 摘要压缩、动态筛选 |
| Generate | Faithfulness / 引用准确率 | 模型能力、指令遵循 | 引用验证、低温度采样 |

## 本章小结

经典 RAG 的四阶段架构（Index → Retrieve → Augment → Generate）虽然看起来简单直接，但每个阶段都充满了工程上的权衡和挑战：

1. **Index 阶段**决定了检索能力的上限——低质量的索引意味着无论检索算法多好都无法找到正确的信息
2. **Retrieve 阶段**需要在召回率、精确率和延迟之间取得平衡——混合检索是当前最优解
3. **Augment 阶段**是连接检索和生成的桥梁，Prompt 工程在此发挥重要作用
4. **Generate 阶段**的最终质量取决于前三阶段的质量和 LLM 本身的指令遵循能力

理解这四个阶段的内在联系和工程挑战，是构建可靠 RAG 系统的基础。后续章节将深入探讨分块策略（8.2）、混合检索（8.3）、Agentic RAG（8.4）、GraphRAG（8.5）、RAG 评估（8.6）和生产陷阱（8.7）。
