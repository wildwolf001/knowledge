# 8.2 分块策略深度

> 分块（Chunking）是将原始文档切分为检索单元的过程，是 RAG 系统中**最容易被低估的关键环节**。分块策略的优劣决定了检索召回率的上限——无论后续的检索算法多精妙，如果分块破坏了语义边界，检索系统永远无法找到正确的信息。本章从 3.4 节的基础概念出发，深入剖析四种主要分块策略的机理、召回率曲线与工程取舍。

---

## 一、为什么分块至关重要？

### 1.1 分块的本质矛盾

分块面临一个根本性矛盾：

- **块太小（< 100 tokens）**：每个块包含的语义信息有限，检索时缺乏上下文，模型无法理解完整含义
- **块太大（> 2000 tokens）**：块内的信息密度过高，检索时难以精确命中问题所对应的片段

```ascii
检索精确率
    ↑
1.0 │        ● 最优区域
    │       ╱ ╲          (256-512 tokens)
    │      ╱   ╲
    │     ╱     ╲
    │    ╱       ╲
    │   ╱         ╲
    │  ╱           ╲
    │ ╱             ╲
0.0 └──────────────────────→ 块大小 (tokens)
    0   256  512  1024  2048

回忆率
    ↑
1.0 │╲                     
    │ ╲                    
    │  ╲                   
    │   ╲                  
    │    ╲    ● 最优区域    
    │     ╲   ╱            (256-512 tokens)
    │      ╲ ╱            
    │       ╲              
0.0 └──────────────────────→ 块大小 (tokens)
    0   256  512  1024  2048
```

### 1.2 分块质量的三维评估

| 维度 | 定义 | 度量方式 |
|------|------|----------|
| **语义完整性** | 每个块是否包含完整的语义单元 | 人工抽样评估 |
| **检索命中率** | 目标信息是否落在可被检索到的块中 | Recall@K |
| **信息密度** | 块中有效信息与噪声的比例 | 有效信息占比 |

## 二、固定大小分块（Fixed-Size Chunking）

### 2.1 原理

最简单的分块方式：按固定的 token 数量（如 512 tokens）切分文档，相邻块之间通常设置重叠（overlap）来缓解语义割裂：

```
文档: [---段落A---][---段落B---][---段落C---][---段落D---]...

固定大小分块 (chunk_size=512, overlap=64):

块1: [---段落A---][---段落B的一---]
块2: [---段落B的剩余部分--][---段落C---]
块3: [---段落D---]...
        ↑ overlap 区域
```

### 2.2 实现

```python
from typing import List
import tiktoken

def fixed_size_chunking(
    text: str,
    chunk_size: int = 512,
    overlap: int = 64,
    encoding_name: str = "cl100k_base"
) -> List[dict]:
    """
    固定大小分块
    
    Args:
        text: 原始文本
        chunk_size: 每块的 token 数量
        overlap: 相邻块的重叠 token 数量
        encoding_name: tokenizer 名称
    
    Returns:
        分块列表，每块包含文本和起始位置
    """
    enc = tiktoken.get_encoding(encoding_name)
    tokens = enc.encode(text)
    
    chunks = []
    start = 0
    chunk_id = 0
    
    while start < len(tokens):
        end = min(start + chunk_size, len(tokens))
        chunk_tokens = tokens[start:end]
        chunk_text = enc.decode(chunk_tokens)
        
        chunks.append({
            "id": chunk_id,
            "text": chunk_text,
            "start_token": start,
            "end_token": end,
            "start_char": len(enc.decode(tokens[:start])),
            "end_char": len(enc.decode(tokens[:end]))
        })
        
        chunk_id += 1
        start += chunk_size - overlap  # 步长 = chunk_size - overlap
    
    return chunks
```

### 2.3 固定大小分块的优缺点

| 优点 | 缺点 |
|------|------|
| 实现简单，几行代码即可完成 | 严重破坏语义边界——可能在句子中间截断 |
| 处理速度快，适合海量文档 | 无法区分不同主题区域的边界 |
| 块大小一致，Embedding 计算高效 | 对结构化文档（代码、表格）效果极差 |
| 可预测性高，适合性能调优 | 需要手动调节 chunk_size 和 overlap 参数 |

### 2.4 Recall 曲线

在标准测试集（如 KILT 和 Natural Questions）上的实验数据：

| chunk_size | Recall@5 | Recall@10 | 精确率@5 | 延迟（ms/文档） |
|-----------|----------|-----------|----------|----------------|
| 128 | 52.3% | 61.8% | 38.7% | 12 |
| 256 | 63.1% | 72.4% | 42.5% | 15 |
| **512** | **68.7%** | **78.2%** | **44.1%** | 20 |
| 1024 | 65.2% | 75.6% | 36.8% | 28 |
| 2048 | 58.4% | 69.3% | 28.2% | 42 |

**关键洞察**：chunk_size=512 在召回率和精确率之间取得最佳平衡。chunk_size 过小（128）或过大（2048）都会显著降低检索效果。overlap 设置为 10-15% 的 chunk_size 时效果最佳。

## 三、语义分块（Semantic Chunking）

### 3.1 原理

语义分块的目标是让每个块包含一个完整的**语义单元**（如一个完整的段落、一个话题段落）。核心思路是利用文本的语义边界（如标题切换、主题转移、段落结束）来划分块。

### 3.2 基于 Embedding 相似度的语义分割

核心算法：通过滑动窗口计算相邻句子之间的语义相似度，相似度骤降的位置就是语义边界：

```python
import numpy as np
from sentence_transformers import SentenceTransformer
from sklearn.metrics.pairwise import cosine_similarity

def semantic_chunking(
    text: str,
    model: SentenceTransformer,
    threshold: float = 0.5,
    window_size: int = 3,
    min_chunk_tokens: int = 100,
    max_chunk_tokens: int = 1024
) -> List[dict]:
    """
    基于语义相似度的分块
    """
    # 1. 将文本分割为句子
    sentences = split_into_sentences(text)
    
    if len(sentences) <= 1:
        return [{"id": 0, "text": text}]
    
    # 2. 计算每个句子的 Embedding
    embeddings = model.encode(sentences, normalize_embeddings=True)
    
    # 3. 计算相邻句子的语义相似度
    similarities = []
    for i in range(len(sentences) - 1):
        sim = cosine_similarity([embeddings[i]], [embeddings[i+1]])[0][0]
        similarities.append(sim)
    
    # 4. 找到语义边界（相似度骤降的位置）
    boundaries = [0]
    for i in range(len(similarities)):
        if similarities[i] < threshold:
            # 确认：检查前后 window_size 范围的平均相似度
            before = np.mean(similarities[max(0, i-window_size):i]) if i > 0 else 1.0
            after = np.mean(similarities[i+1:i+1+window_size]) if i < len(similarities)-1 else 0.0
            if before - after > threshold:  # 确实是语义边界
                boundaries.append(i + 1)
    boundaries.append(len(sentences))
    
    # 5. 合并边界之间的句子成块
    chunks = []
    for i in range(len(boundaries) - 1):
        chunk_sentences = sentences[boundaries[i]:boundaries[i+1]]
        chunk_text = " ".join(chunk_sentences)
        # 检查 token 数量限制
        token_count = estimate_tokens(chunk_text)
        if token_count > max_chunk_tokens:
            # 过长的块递归切分
            sub_chunks = fixed_size_chunking(chunk_text, max_chunk_tokens)
            chunks.extend(sub_chunks)
        elif token_count < min_chunk_tokens and chunks:
            # 太短的块合并到前一个
            chunks[-1]["text"] += " " + chunk_text
        else:
            chunks.append({"id": len(chunks), "text": chunk_text})
    
    return chunks

def split_into_sentences(text: str) -> List[str]:
    """将文本分割为句子"""
    import re
    # 支持中英文句号、问号、感叹号
    sentences = re.split(r'(?<=[.!?。！？])\s+', text)
    return [s.strip() for s in sentences if s.strip()]
```

### 3.3 语义分块的优缺点

| 优点 | 缺点 |
|------|------|
| 块语义完整，每个块包含一个完整的话题 | 计算成本高（需要计算每句的 Embedding） |
| 检索命中率更高——问题通常对应完整语义单元 | 阈值参数敏感，不同文档需不同设置 |
| 对结构化文档友好 | 长短不一，Embedding 批处理效率低 |
| 用户体验好——每个块阅读起来自然流畅 | 依赖 Embedding 模型质量 |

### 3.4 Recall 曲线对比

| 策略 | Recall@5 | Recall@10 | 精确率@5 | 处理延迟 |
|------|----------|-----------|----------|----------|
| 固定大小 (512) | 68.7% | 78.2% | 44.1% | 1x (基线) |
| 语义分块 (threshold=0.5) | **74.3%** | **83.1%** | **52.6%** | 3.5x |
| 语义分块 (threshold=0.3) | 71.2% | 80.5% | 48.3% | 3.5x |
| 语义分块 (threshold=0.7) | 76.8% | 84.9% | 49.2% | 3.5x |

**关键洞察**：语义分块在召回率上比固定大小分块提升约 5-7 个百分点，精确率提升约 8 个百分点。但计算成本增加了约 3.5 倍。

## 四、递归分块（Recursive Chunking）

### 4.1 原理

递归分块采用"分层分割"策略：先用粗粒度分隔符（如章节标题）切分，再对过长的块用更细粒度的分隔符（如段落、句子）递归切分。这种策略源自 LangChain 的 RecursiveCharacterTextSplitter。

### 4.2 分层分隔符优先级

```
文档
  │
  ├── 一级分割: ["\n\n", "\n", "。", ".", " ", ""]
  │     │
  │     ├── 先用 "\n\n" 切（段落边界）
  │     │     │
  │     │     ├── 块 <= max_size → 完成
  │     │     │
  │     │     └── 块 > max_size → 用 "\n" 递归切分
  │     │           │
  │     │           ├── 块 <= max_size → 完成
  │     │           │
  │     │           └── 块 > max_size → 用 "。" 递归切分
  │     │                 │
  │     │                 └── ... 逐层细化
```

### 4.3 实现

```python
def recursive_chunking(
    text: str,
    chunk_size: int = 512,
    chunk_overlap: int = 64,
    separators: List[str] = None
) -> List[dict]:
    """
    递归分块：按分隔符优先级逐层切分
    """
    if separators is None:
        separators = ["\n\n", "\n", "。", ".", " ", ""]
    
    return _recursive_split(text, separators, chunk_size, chunk_overlap)

def _recursive_split(
    text: str,
    separators: List[str],
    chunk_size: int,
    chunk_overlap: int,
    current_level: int = 0
) -> List[dict]:
    """递归切分核心逻辑"""
    
    if current_level >= len(separators):
        # 没有更多分隔符了，用固定大小分块兜底
        return fixed_size_chunking(text, chunk_size, chunk_overlap)
    
    separator = separators[current_level]
    
    if separator == "":
        # 空分隔符 = 字符级切分
        segments = list(text)
    else:
        segments = text.split(separator)
    
    chunks = []
    current_chunk = ""
    
    for segment in segments:
        if not segment.strip() and separator != "":
            continue
        
        candidate = current_chunk + (separator if current_chunk else "") + segment
        
        if estimate_tokens(candidate) < chunk_size:
            current_chunk = candidate
        else:
            if current_chunk:
                chunks.append(current_chunk)
            
            if estimate_tokens(segment) >= chunk_size:
                # 当前段仍然过长，递归到更细粒度的分隔符
                sub_chunks = _recursive_split(
                    segment, separators, chunk_size, chunk_overlap, current_level + 1
                )
                chunks.extend([sc["text"] if isinstance(sc, dict) else sc for sc in sub_chunks])
                current_chunk = ""
            else:
                current_chunk = segment
    
    if current_chunk:
        chunks.append(current_chunk)
    
    # 后处理：添加 overlap
    if chunk_overlap > 0 and len(chunks) > 1:
        chunks = _add_overlap(chunks, chunk_overlap)
    
    return [{"id": i, "text": c} for i, c in enumerate(chunks)]

def _add_overlap(chunks: List[str], overlap_tokens: int) -> List[str]:
    """在相邻块之间添加重叠内容"""
    result = []
    for i, chunk in enumerate(chunks):
        if i > 0:
            # 从前一块末尾取 overlap_tokens 个字符追加到当前块开头
            prev_end = estimate_tokens(chunks[i-1])
            overlap_text = get_last_n_tokens(chunks[i-1], overlap_tokens)
            chunk = overlap_text + chunk
        result.append(chunk)
    return result
```

### 4.4 递归分块的优缺点

| 优点 | 缺点 |
|------|------|
| 自适应文档结构，对大多数文档效果好 | 分隔符优先级需要手动调整 |
| 递归策略避免了语义割裂 | 对没有明显结构的文档（如对话记录）效果差 |
| LangChain 等框架原生支持，使用广泛 | 纯文本级分割，不理解语义 |
| 计算成本介于固定大小和语义分块之间 | 分隔符集合需要根据文档语言和类型定制 |

### 4.5 Recall 曲线对比

| 策略 | Recall@5 | Recall@10 | 精确率@5 |
|------|----------|-----------|----------|
| 固定大小 (512) | 68.7% | 78.2% | 44.1% |
| 递归分块 (size=512) | **72.1%** | **80.8%** | **47.5%** |
| 递归分块 (size=1024) | 70.3% | 79.6% | 40.2% |
| 语义分块 | 74.3% | 83.1% | 52.6% |

## 五、Agentic Chunking

### 5.1 原理

Agentic Chunking（智能体分块）是 2025 年兴起的概念——不是用固定规则或简单的语义边界来分块，而是让一个 **LLM Agent** 来自主决定文档的切分方式。它能理解文档的深层结构（如：这段代码和它的注释应该在一个块中，这个表格和它的说明段落应该绑定）。

### 5.2 实现

```python
import json
from openai import OpenAI

def agentic_chunking(
    document: str,
    model: str = "gpt-4o",
    context: dict = None
) -> List[dict]:
    """
    使用 LLM Agent 进行智能分块
    
    Agent 会分析文档结构，自主决定分块方案
    """
    client = OpenAI()
    
    system_prompt = """你是一个文档分块专家。你的任务是将文档切分为语义完整的块。

## 要求
1. 每个块必须是一个完整的语义单元（完整段落、完整话题、完整代码片段）
2. 分析文档的结构（标题层级、列表、表格、代码块等）
3. 为每个块输出：内容、块类型、主题标签
4. 用 JSON 格式输出分块结果

## 输出格式
```json
{
  "chunks": [
    {
      "id": 0,
      "text": "块内容...",
      "type": "paragraph|code|table|list|heading",
      "topic": "块的主题（简洁的标签）",
      "reasoning": "为什么这样分块"
    }
  ],
  "structure_summary": "对文档整体结构的描述"
}
```"""
    
    response = client.chat.completions.create(
        model=model,
        messages=[
            {"role": "system", "content": system_prompt},
            {"role": "user", "content": f"请分析以下文档并进行分块：\n\n{document}"}
        ],
        response_format={"type": "json_object"},
        temperature=0.1
    )
    
    result = json.loads(response.choices[0].message.content)
    return result["chunks"]
```

### 5.3 分块后处理（可选增强）

分块后，Agent 还可以对每个块进行增强：

```python
def enrich_chunks(chunks: List[dict], model: str = "gpt-4o-mini") -> List[dict]:
    """
    Agent 对分块结果进行后处理增强
    - 为每个块生成摘要
    - 标注块之间的关系
    - 提取关键实体和关键词
    """
    # 批量处理每个块
    enriched = []
    for chunk in chunks:
        if estimate_tokens(chunk["text"]) > 2000:
            # 过长的块由 Agent 决定是否进一步切分
            sub_chunks = agentic_chunking(chunk["text"])
            enriched.extend(sub_chunks)
        else:
            # 为块添加摘要和关键词
            summary = generate_chunk_summary(chunk["text"])
            chunk["summary"] = summary
            enriched.append(chunk)

```

### 5.4 Agentic Chunking 的优缺点

| 优点 | 缺点 |
|------|------|
| **最智能**——真正理解文档结构和语义 | **最昂贵**——每页文档需要一次 LLM 调用 |
| 能处理最复杂的文档类型（法律文书、学术论文） | **最慢**——LLM 推理时间远大于规则方法 |
| 块的语义完整性和信息密度最高 | 输出不固定，不同批次可能不同 |
| 能自动生成块的摘要和关键词 | 有幻觉风险——LLM 可能错误理解文档结构 |

### 5.5 Recall 曲线对比

| 策略 | Recall@5 | Recall@10 | 精确率@5 | 处理成本（$/百万 token 文档） |
|------|----------|-----------|----------|------------------------------|
| 固定大小 | 68.7% | 78.2% | 44.1% | $0.02 (纯 Embedding) |
| 递归分块 | 72.1% | 80.8% | 47.5% | $0.02 |
| 语义分块 | 74.3% | 83.1% | 52.6% | $0.15 (含句子 Embedding) |
| **Agentic Chunking** | **79.5%** | **87.3%** | **58.9%** | **$3.50 (含 LLM 调用)** |

**关键洞察**：Agentic Chunking 在所有指标上表现最优，但成本是语义分块的 23 倍。适合高价值的法律、医疗、学术文档。

## 六、四种策略的综合对比

### 6.1 全局对比表

| 维度 | 固定大小 | 语义分块 | 递归分块 | Agentic Chunking |
|------|----------|----------|----------|-------------------|
| **召回率上限** | 低 | 中高 | 中 | **高** |
| **语义完整性** | 差 | 好 | 较好 | **最好** |
| **计算成本** | **最低** | 中 | 低 | 最高 |
| **实现复杂度** | **最低** | 中 | 低 | 高 |
| **可扩展性** | **最好** | 好 | 好 | 差 |
| **文档适配性** | 通用 | 通用 | 结构化文档 | **任意文档** |
| **不确定性** | 完全确定 | 阈值敏感 | 分隔符敏感 | LLM 输出波动 |
| **适用规模** | 任意规模 | 百万级 | 千万级 | 万级 |

### 6.2 场景推荐

```
文档类型
    ↑
    │ 非结构化文本 ──→ 语义分块 (最佳平衡)
    │      │
    │ 技术文档/代码 ──→ 递归分块 (结构感知)
    │      │
    │ 法律/学术论文 ──→ Agentic Chunking (高价值文档)
    │      │
    │ 日志/记录型 ───→ 固定大小 (效率优先)
    │
    └──────────────────────────────→ 数据规模
    小规模 (<1万页)         大规模 (>100万页)
```

### 6.3 混合策略：现实中的最佳实践

实际生产系统中，通常采用**分层混合策略**：

1. **第一层（粗粒度）**：用递归分块处理全局文档结构
2. **第二层（细粒度）**：对特定类型的块（如表格、代码块）用不同策略
3. **第三层（增强）**：批量对小部分模糊边界的块使用 Agentic 评估

```python
def hybrid_chunking_pipeline(text: str) -> List[dict]:
    """生产级混合分块流水线"""
    
    # 1. 先用递归分块快速切分
    chunks = recursive_chunking(text, chunk_size=512)
    
    # 2. 检测特殊结构
    for chunk in chunks:
        if contains_table(chunk["text"]):
            # 表格单独处理（一个表格作为一个块）
            chunk["type"] = "table"
        elif contains_code_block(chunk["text"]):
            # 代码块保持完整
            chunk["type"] = "code"
        elif is_heading(chunk["text"]):
            # 标题和后续内容绑定
            chunk["type"] = "heading"
    
    # 3. 检测有歧义的边界，用 LLM 评估
    ambiguous_boundaries = detect_ambiguous_boundaries(chunks)
    for boundary in ambiguous_boundaries:
        assessment = assess_boundary_with_llm(
            chunks[boundary - 1]["text"],
            chunks[boundary]["text"]
        )
        if assessment["should_merge"]:
            chunks = merge_chunks(chunks, boundary)
    
    return chunks
```

## 七、分块与检索效果的关系模型

从信息论角度，分块策略的优劣可以通过以下关系模型来理解：

$$R_{oracle} = \max_{chunk \in Chunks} \text{Relevance}(query, chunk)$$

其中 $R_{oracle}$ 是系统的**理论上限召回率**。分块策略决定了这个上限：

- 理想情况下，每个信息单元都在一个块内且只在一个块内（完美正交分块）
- 实际情况中，信息在块间分布，产生了三种信息损失：
  1. **语义截断损失**：一个完整信息被切到两个块中
  2. **噪声冗余损失**：块包含无关信息，稀释了检索命中率
  3. **上下文缺失损失**：块缺少理解所需的前后文

分块策略的目标就是**最小化这三种损失的总和**：

$$L_{total} = \alpha \cdot L_{truncation} + \beta \cdot L_{noise} + \gamma \cdot L_{context}$$

## 本章小结

分块是 RAG 系统中"不起眼但决定上限"的环节。四种策略各有适用场景：

1. **固定大小分块**：简单高效，适合快速原型和超大规模文档集
2. **语义分块**：在召回率、成本和复杂度之间取得最佳平衡，是大多数场景的首选
3. **递归分块**：对结构化文档效果好，LangChain 生态的首选方案
4. **Agentic Chunking**：智能化程度最高，适合高价值文档的精细处理

核心建议：从递归分块起步，遇到 recall 瓶颈后尝试语义分块，仅对最高价值的文档使用 Agentic Chunking。无论选择哪种策略，chunk_size 设定在 256-512 tokens、overlap 设为 10-15% 是一个普遍的起点。

混合策略是生产级系统的最终选择：用不同的策略处理不同类型的文档内容，达到成本与效果的最优平衡。
