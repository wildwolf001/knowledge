# 8.5 GraphRAG

> GraphRAG（图检索增强生成）是 RAG 与知识图谱（Knowledge Graph）的深度融合——它不仅在文本向量空间中检索，还利用实体之间的结构化关系来增强信息检索和推理能力。GraphRAG 的核心价值在于：**当答案需要跨越多个实体和关系进行推理时，纯向量检索会失败，而图结构可以精确地沿着关系路径找到答案**。

---

## 一、GraphRAG 与经典 RAG 的本质区别

### 1.1 信息组织方式的根本不同

```
经典 RAG (Flat/平面):
┌──────────────────────────────────────┐
│                                     │
│  [文档1]  [文档2]  [文档3]  [文档4]  │
│     │        │        │        │     │
│  [向量]   [向量]   [向量]   [向量]   │
│                                     │
│  信息以独立的"文档块"存在              │
│  块之间没有显式的关系连接               │
└──────────────────────────────────────┘

GraphRAG (Graph/图):
┌──────────────────────────────────────┐
│          ┌─────┐                     │
│   ┌─────→│实体A │←──────┐           │
│   │      └─────┘       │            │
│   │         │          │            │
│   │      [关系]        │            │
│   │         │          │            │
│   ▼      ┌─────┐       ▼            │
│ ┌─────┐  │实体B │  ┌─────┐          │
│ │文档1 │  └─────┘  │文档3 │          │
│ └─────┘     │      └─────┘          │
│             │                       │
│          [关系]                      │
│             │                       │
│          ┌─────┐                    │
│          │实体C │←───[关系]───[文档4]│
│          └─────┘                    │
│                                     │
│  信息以"实体-关系-实体"三元组存在      │
│  块之间通过关系路径连接               │
└──────────────────────────────────────┘
```

### 1.2 核心差异对比表

| 维度 | 经典 RAG | GraphRAG |
|------|----------|----------|
| **基本单元** | 文档块（Chunks） | 实体（Entities）+ 关系（Relations） |
| **检索方法** | 向量相似度搜索（ANN） | 图遍历 + 向量检索混合 |
| **关系利用** | 隐式（语义向量中的统计关联） | 显式（定义明确的谓词关系） |
| **多跳推理** | 困难——需要 Agent 多次向量检索 | 自然——沿图路径遍历即可 |
| **聚合查询** | 困难——需要总结大量块 | 自然——可以从图结构中聚合统计 |
| **事实一致性** | 容易矛盾——不同文档可能冲突 | 高——关系约束保证一致性 |
| **构建成本** | 低——只需分块+Embedding | 高——需要实体抽取+关系抽取 |
| **维护成本** | 低——增删改简单 | 高——图结构更新复杂 |

### 1.3 一个具体的对比示例

查询："Apple 收购了哪些 AI 初创公司？它们的核心技术分别是什么？"

```
经典 RAG 的处理方式：
1. 将查询编码为向量
2. 在向量空间中搜索相似的文档块
3. 可能匹配到：
   - "Apple 收购了 X 公司，X 专注于..."（但可能不完整）
   - "AI 初创公司 Y 被大型科技公司收购"（提及 Apple 但没明确关联）
4. 需要 LLM 从多个块中推理关系

GraphRAG 的处理方式：
1. 提取查询实体："Apple"、"AI初创公司"
2. 在知识图谱中查找：
   ┌───────┐        ┌──────────┐
   │ Apple │──收购──→│ X公司   │──核心技术→ [AI芯片设计]
   │       │──收购──→│ Y公司   │──核心技术→ [NLP引擎]
   │       │──收购──→│ Z公司   │──核心技术→ [计算机视觉]
   └───────┘        └──────────┘
3. 直接沿"收购"关系路径遍历，精确返回所有被 Apple 收购的公司
4. 再沿"核心技术"关系获取每个公司的技术
```

**本质区别**：经典 RAG 不知道"Apple"和"X公司"之间有"收购"关系——它只在语义空间中找"相似"的文本。而 GraphRAG 显式存储了这个关系，可以精确检索。

## 二、GraphRAG 的架构设计

### 2.1 整体架构

```
原始文档
    │
    ▼
┌─────────────────────────────┐
│   知识图谱构建阶段            │
│                              │
│  ① 实体抽取 (NER)            │
│    识别文档中的人名、公司、     │
│    地点、产品等命名实体        │
│                              │
│  ② 关系抽取 (RE)              │
│    识别实体之间的语义关系      │
│    (收购、任职于、生产、位于等) │
│                              │
│  ③ 实体链接 (Entity Linking)  │
│    将同一实体的不同指代对齐     │
│    ("Apple" = "苹果公司")     │
│                              │
│  ④ 图存储                    │
│    存入 Neo4j / Nebula 等    │
└───────────┬─────────────────┘
            │
            ▼
┌─────────────────────────────┐
│   双引擎检索阶段              │
│                              │
│  ┌──────────────────┐       │
│  │ 向量检索引擎       │       │
│  │ (用于语义匹配)     │       │
│  └──────┬───────────┘       │
│         │                    │
│  ┌──────────────────┐       │
│  │ 图检索引擎         │       │
│  │ (用于关系遍历)     │       │
│  └──────┬───────────┘       │
└───────────┬─────────────────┘
            │
            ▼
┌─────────────────────────────┐
│   结果融合与生成阶段          │
│                              │
│  结构信息 + 文本信息 → LLM   │
│                              │
│  最终回答                    │
└─────────────────────────────┘
```

### 2.2 知识图谱构建（离线阶段）

```python
import spacy
from typing import List, Tuple

class KnowledgeGraphBuilder:
    """从文档构建知识图谱"""
    
    def __init__(self, llm_model: str = "gpt-4o-mini"):
        self.nlp = spacy.load("zh_core_web_sm")  # 中文 NER
        self.client = OpenAI()
        self.model = llm_model
        self.graph = {
            "entities": {},   # entity_id -> {name, type, description}
            "relations": []   # [(subject_id, predicate, object_id, confidence)]
        }
    
    def extract_entities_relations(self, text: str) -> dict:
        """从文本中提取实体和关系"""
        prompt = f"""从以下文本中提取所有实体和它们之间的关系。

文本: {text}

## 实体类型
- PERSON: 人物
- ORG: 组织/公司
- PRODUCT: 产品
- LOCATION: 地点
- EVENT: 事件
- CONCEPT: 概念/技术

## 关系类型
- acquire: 收购
- founded_by: 创立于
- located_in: 位于
- develop: 开发
- compete_with: 竞争
- partner_of: 合作
- employ: 雇佣
- produce: 生产

输出 JSON:
{{
  "entities": [
    {{"name": "实体名", "type": "ORG", "description": "描述"}}
  ],
  "relations": [
    {{"subject": "实体A", "predicate": "acquire", "object": "实体B"}}
  ]
}}"""
        
        response = self.client.chat.completions.create(
            model=self.model,
            messages=[
                {"role": "system", "content": "你是一个知识图谱构建专家，精确提取实体和关系。"},
                {"role": "user", "content": prompt}
            ],
            response_format={"type": "json_object"},
            temperature=0.1
        )
        
        result = json.loads(response.choices[0].message.content)
        return result
    
    def build_from_documents(self, documents: list[dict]):
        """从文档集构建知识图谱"""
        
        for doc in documents:
            extraction = self.extract_entities_relations(doc["text"])
            
            # 添加实体
            for entity in extraction.get("entities", []):
                entity_key = entity["name"]
                if entity_key not in self.graph["entities"]:
                    self.graph["entities"][entity_key] = entity
                else:
                    # 合并信息（保留更详细的描述）
                    existing = self.graph["entities"][entity_key]
                    if len(entity.get("description", "")) > len(existing.get("description", "")):
                        existing["description"] = entity["description"]
            
            # 添加关系去重
            for rel in extraction.get("relations", []):
                rel_tuple = (rel["subject"], rel["predicate"], rel["object"])
                if rel_tuple not in self.graph["relations"]:
                    self.graph["relations"].append(rel_tuple)
        
        print(f"构建完成: {len(self.graph['entities'])} 实体, {len(self.graph['relations'])} 关系")
        return self.graph
    
    def query_graph(self, start_entities: list[str], relation_types: list[str], max_depth: int = 2) -> dict:
        """图查询：从起始实体出发，沿指定关系类型遍历"""
        results = {"nodes": [], "edges": []}
        visited = set()
        
        def traverse(entity_name, depth):
            if depth > max_depth or entity_name in visited:
                return
            visited.add(entity_name)
            
            if entity_name in self.graph["entities"]:
                results["nodes"].append(self.graph["entities"][entity_name])
            
            for rel in self.graph["relations"]:
                sub, pred, obj = rel
                if sub == entity_name and pred in relation_types:
                    results["edges"].append({"from": sub, "relation": pred, "to": obj})
                    traverse(obj, depth + 1)
        
        for entity in start_entities:
            traverse(entity, 0)
        
        return results
```

## 三、图检索与向量检索的双引擎

### 3.1 双引擎检索策略

GraphRAG 不是用图替换向量检索，而是**两者互补**：

```python
class GraphRAGRetriever:
    """图 + 向量双引擎检索器"""
    
    def __init__(self, vector_retriever, graph_builder):
        self.vector_retriever = vector_retriever
        self.graph = graph_builder
    
    def hybrid_search(self, query: str, top_k: int = 10) -> list[dict]:
        """双引擎检索"""
        
        # Step 1: 向量检索（获取相关文档块）
        vector_results = self.vector_retriever.search(query, top_k=top_k)
        
        # Step 2: 从查询中提取实体
        extraction = self.graph.extract_entities_relations(query)
        query_entities = [e["name"] for e in extraction.get("entities", [])]
        
        # Step 3: 图检索（沿关系路径扩展）
        graph_context = []
        if query_entities:
            graph_data = self.graph.query_graph(
                query_entities,
                relation_types=["acquire", "develop", "compete_with", "partner_of", "produce", "founded_by"],
                max_depth=2
            )
            
            # 将图结构转为文本用于 Prompt
            for node in graph_data["nodes"]:
                graph_context.append(f"[实体] {node['name']} ({node.get('type', '')}): {node.get('description', '')}")
            
            for edge in graph_data["edges"]:
                graph_context.append(f"[关系] {edge['from']} --{edge['relation']}→ {edge['to']}")
        
        # Step 4: 融合结果
        return {
            "vector_context": vector_results,
            "graph_context": graph_context,
            "entities_found": query_entities
        }
```

### 3.2 Microsoft GraphRAG 方案

2024 年 Microsoft 提出的 GraphRAG 方案采用了不同的思路——不是构建完整的知识图谱，而是对文档做**层次化摘要**：

```
原始文档
    │
    ▼
┌──────────────────────┐
│  文本分块              │
└──────────┬───────────┘
           │
           ▼
┌──────────────────────┐
│  实体/关系提取          │
│  (每个块独立提取)       │
└──────────┬───────────┘
           │
           ▼
┌──────────────────────┐
│  社区检测 (Leiden)     │
│  将相关实体聚为社区    │
└──────────┬───────────┘
           │
           ▼
┌──────────────────────┐
│  社区摘要              │
│  为每个社区生成自然语言   │
│  的摘要描述             │
└──────────┬───────────┘
           │
           ▼
┌──────────────────────┐
│  检索时:               │
│  1. 向量匹配找到相关社区 │
│  2. 返回社区摘要+原文   │
│  3. LLM 综合生成答案    │
└─────────────────────────┘
```

Microsoft GraphRAG 的核心创新点是**社区摘要**机制，使得 GraphRAG 能回答"文档集中有哪些主要趋势"这类需要全局理解的聚合性问题——这是经典 RAG 难以做到的。

### 3.3 图遍历 vs 向量检索的互补

```python
class GraphRAGQueryEngine:
    """完整的 GraphRAG 查询引擎"""
    
    def query(self, query: str, retriever, graph_builder) -> str:
        """处理查询"""
        
        # 1. 判断查询类型
        query_type = self._classify_query(query)
        
        if query_type == "factual":
            # 事实性查询 → 优先向量检索
            print("[Strategy] 事实性查询 → 向量检索优先")
            context = retriever.search(query, top_k=5)
            
        elif query_type == "relational":
            # 关系型查询 → 优先图检索
            print("[Strategy] 关系型查询 → 图检索优先")
            extraction = graph_builder.extract_entities_relations(query)
            entities = [e["name"] for e in extraction.get("entities", [])]
            graph_data = graph_builder.query_graph(entities, max_depth=2)
            context = self._graph_to_text(graph_data)
            
        elif query_type == "aggregate":
            # 聚合型查询 → 图结构+全局摘要
            print("[Strategy] 聚合型查询 → 社区摘要")
            context = self._get_community_summaries(query, graph_builder)
        
        else:  # "hybrid"
            # 混合型查询 → 双引擎联合
            print("[Strategy] 混合型查询 → 双引擎联合")
            hybrid = retriever.hybrid_search(query)
            context = self._merge_contexts(hybrid)
        
        # 2. 生成
        return self._generate(query, context)
    
    def _classify_query(self, query: str) -> str:
        """对查询进行分类"""
        prompt = f"""判断以下查询属于哪种类型：

- "factual": 事实性（单一事实，如"XX公司的CEO是谁？"）
- "relational": 关系性（涉及实体间关系，如"A公司收购了哪些公司？"）
- "aggregate": 聚合性（需要全局总结，如"文档集讨论的主要话题有哪些？"）
- "hybrid": 混合性（综合以上）

查询: {query}

只需输出类型名称:"""
        
        response = self.client.chat.completions.create(
            model="gpt-4o-mini",
            messages=[{"role": "user", "content": prompt}],
            temperature=0.1,
            max_tokens=10
        )
        
        return response.choices[0].message.content.strip()
```

## 四、GraphRAG 的关键技术

### 4.1 实体对齐（Entity Alignment）

同一实体在不同文档中可能有不同表述，需要对齐：

| 原始表述 | 归一化后 | 对齐方法 |
|----------|----------|----------|
| "Apple"、"苹果公司"、"AAPL" | "Apple" | 同义词表 + 上下文识别 |
| "GPT-4"、"GPT4"、"Generative Pre-trained Transformer 4" | "GPT-4" | 正则匹配 + 别名映射 |
| "李宏毅"、"Hung-yi Lee" | "李宏毅" | 中英文名映射 |
| "2024年12月"、"2024-12"、"last Dec" | "2024-12" | 时间归一化 |

### 4.2 图增强的检索策略

```python
def graph_expanded_retrieval(query: str, retriever, graph, hop: int = 1) -> list[dict]:
    """
    图扩展检索：在向量检索的基础上，通过图关系扩展上下文
    """
    # 初始向量检索
    initial_results = retriever.search(query, top_k=5)
    
    # 从检索结果中提取实体
    entities_from_results = extract_entities([r["text"] for r in initial_results])
    
    # 图扩展：获取这些实体的邻接实体
    expanded_entities = set(entities_from_results)
    for entity in entities_from_results:
        neighbors = graph.get_neighbors(entity, max_hop=hop)
        expanded_entities.update(neighbors)
    
    # 获取扩展实体的文档块
    expanded_chunks = []
    for entity in expanded_entities:
        chunks = graph.get_entity_chunks(entity)
        expanded_chunks.extend(chunks)
    
    # 融合去重
    all_chunks = initial_results + expanded_chunks
    seen = set()
    unique = []
    for c in all_chunks:
        if c["text"] not in seen:
            seen.add(c["text"])
            unique.append(c)
    
    return unique
```

### 5.1 不同查询类型的效果对比

在标准测试集上的实验数据：

| 查询类型 | 经典 RAG (Recall@10) | GraphRAG (Recall@10) | 提升 |
|----------|---------------------|---------------------|------|
| **简单事实** | 85.2% | 86.1% | +1% |
| **单跳关系** | 72.3% | 83.5% | +16% |
| **多跳关系（2跳）** | 51.8% | 74.2% | +43% |
| **多跳关系（3跳）** | 34.6% | 61.8% | +79% |
| **聚合/总结** | 45.2% | 68.3% | +51% |
| **比较分析** | 58.7% | 76.4% | +30% |

**关键洞察**：图结构在**多跳推理**和**聚合分析**场景下优势最为显著。对于简单事实查询，图结构没有明显收益——甚至因为增加了检索延迟而有微量负面影响。

## 六、GraphRAG vs Agentic RAG

GraphRAG 和 Agentic RAG（8.4 节）是两种不同的增强路径，它们不是互斥的——可以融合使用：

| 维度 | Agentic RAG | GraphRAG | 两者融合 |
|------|-------------|----------|----------|
| **核心机制** | Agent 多步推理循环 | 图结构关系检索 | Agent 利用图结构辅助推理 |
| **检索方式** | 多次向量检索 | 图遍历 + 向量检索 | Agent 决定何时用图、何时用向量 |
| **推理能力** | 强（Agent 自主） | 中（图结构辅助） | 最强 |
| **构建成本** | 低 | 高（需要构建图谱） | 最高 |
| **适用场景** | 复杂问题分解 | 多跳关系、聚合分析 | 最复杂的推理任务 |

```python
# GraphAgenticRAG: 融合两者的方案
class GraphAgenticRAG:
    """Agentic RAG + GraphRAG 融合"""
    
    def run(self, question: str) -> str:
        # Agent 决定检索策略
        plan = self.plan_retrieval(question)
        
        context = []
        for step in plan:
            if step["method"] == "vector":
                result = self.vector_retriever.search(step["query"])
            elif step["method"] == "graph":
                result = self.graph_retriever.traverse(
                    step["start_entities"],
                    step["relations"]
                )
            elif step["method"] == "both":
                result = self.hybrid_retriever.search(step["query"])
            
            context.append(result)
        
        return self.generate(question, context)
```

## 七、生产部署注意事项

### 7.1 图数据库选型

| 数据库 | 适用场景 | 优势 | 劣势 |
|--------|----------|------|------|
| **Neo4j** | 企业级知识图谱 | 生态成熟，Cypher 查询灵活 | 部署运维重 |
| **NebulaGraph** | 超大规模图 | 分布式原生图，水平扩展 | 学习曲线陡 |
| **NetworkX** | 原型验证 | Python 原生，无需部署 | 全内存，不适合大规模 |
| **KuzuDB** | 嵌入式/分析型 | 列式存储，分析查询快 | OLTP 能力弱 |
| **RDFLib** | 语义网/本体 | W3C 标准兼容 | 性能差 |

### 7.2 图更新的工程挑战

```
更新场景         挑战                    解决方案
──────────────────────────────────────────────────────
新文档加入      →  新实体可能和已有实体冲突   → 实体对齐校验
关系修改        →  影响已有图查询的结果      → 版本化图快照
实体删除        →  级联影响相关关系         → 软删除（标记失效）
大规模更新      →  重建图谱成本高           → 增量更新策略
```

## 八、2026 年前沿：自进化的 Agentic GraphRAG

> 2026 年，GraphRAG 经历了从"静态图谱"到"自进化、RL 优化的 Agentic GraphRAG"的范式跃迁。以下四个工作代表了这一方向的前沿突破。

### 8.1 EvoGraph-R1（CVPR 2026）—— 知识图谱作为动态环境

**核心思想**：将知识图谱本身视为一个**动态环境**，Agent 在图谱中自主探索和交互，并通过交互结果驱动图谱自我进化。

```
传统 GraphRAG:
  文档 → 静态知识图谱 → 查询时只读检索 → 回答

EvoGraph-R1:
  文档 → 初始知识图谱 → Agent 在图谱中探索/交互
       → 发现缺失实体/关系 → 自动补充新节点/边
       → 图谱自我进化 → 下一次查询时图已更新
```

**关键创新**：
- 图谱不再是"构建一次、只读使用"，而是**持续演化的活系统**
- Agent 在回答复杂查询时发现图谱盲区，自动触发实体抽取和关系补充
- CVPR 2026 实验显示：经过 5 轮自我进化后，图谱覆盖率提升 34%，多跳推理准确率提升 22%

### 8.2 HyperGraphPro —— 超图检索 + 强化学习

**核心思想**：将传统知识图谱扩展为**超图**（Hypergraph，一条边可连接多个节点），并用强化学习进行结构感知的检索策略优化。

```
传统图:  实体A ──关系──→ 实体B（二元关系）
超图:    [实体A, 实体B, 实体C] ──共同参与──→ [事件X]（多元关系）
```

**关键创新**：
- **超图结构**：一条边可以连接多个实体，更自然地表达复杂事件（如"甲、乙、丙共同参与了项目X"）
- **进度驱动策略优化（Progress-driven Policy Optimization）**：强化学习 agent 在检索过程中不仅关注当前步的奖励，还跟踪整体推理进度，动态调整下一步的检索策略
- 在多个多跳问答基准上相比传统 GraphRAG 提升 15-28%

### 8.3 YouTu-GraphRAG（ICLR 2026）—— 垂直统一 Agent 范式

**核心思想**：提出"垂直统一"（Vertical Unified）的 Agent 范式——将图构建、图检索、图推理整合到**同一个 Agent 框架**中，而非传统的流水线（pipeline）架构。

| 维度 | 传统流水线 GraphRAG | YouTu-GraphRAG (垂直统一) |
|------|-------------------|------------------------|
| **架构** | 独立模块串行执行 | 单一 Agent 端到端管理 |
| **实体抽取** | 离线批处理 | Agent 在推理过程中按需抽取 |
| **图检索** | 固定查询→遍历 | Agent 动态决定何时检索、沿哪条路径 |
| **成本** | 高（全量离线构建） | 低 33.6%（按需构建） |
| **准确率** | 基线 | +16.62% |

**关键成果**：
- 33.6% 的成本节省（按需构建 vs 全量离线构建）
- 16.62% 的准确率提升（Agent 动态决策优于固定 pipeline）
- ICLR 2026 Spotlight 论文

### 8.4 ProGraph-R1 —— 用 GRPO 做 GraphRAG 的 RL 训练

**核心思想**：将 GRPO（Group Relative Policy Optimization，组相对策略优化）引入 GraphRAG 的检索器训练中。

```
传统 GraphRAG 检索器训练:
  人工标注 → 监督学习 → 固定检索策略

ProGraph-R1 检索器训练:
  Agent 在图谱上探索 → 多组检索路径对比
  → GRPO 评估各路径的最终答案质量
  → 奖励高质量路径，惩罚低质量路径
  → 检索策略持续自优化
```

**关键创新**：
- 无需人工标注检索路径，用**最终答案质量**作为奖励信号
- GRPO 在组级别做相对比较，避免绝对评分的不稳定性
- 在 3 个公开基准上，经过 RL 训练的检索策略相比固定策略提升 12-19%

### 8.5 关键趋势总结：从静态到自进化

```
2024             2025              2026
──────────────────────────────────────────────
静态 GraphRAG → 半自动 GraphRAG → 自进化 Agentic GraphRAG
                               │
                    ┌──────────┼──────────┐
                    ▼          ▼          ▼
               EvoGraph-R1  HyperGraphPro  YouTu-GraphRAG
               (自进化)     (超图+RL)      (垂直统一Agent)

核心趋势:
1. 图谱从静态 → 动态自进化（EvoGraph-R1）
2. 检索从固定策略 → RL 优化策略（HyperGraphPro, ProGraph-R1）
3. 架构从流水线 → 垂直统一 Agent（YouTu-GraphRAG）
4. 成本从全量离线 → 按需动态构建（YouTu-GraphRAG）
```

## 本章小结

GraphRAG 的本质区别在于：**经典 RAG 只"理解"文档的语义相似性，而 GraphRAG 还"理解"文档中实体之间的关系。**

1. **信息组织方式不同**：经典 RAG 是扁平化的文档块索引，GraphRAG 是网络化的实体-关系图
2. **检索方式不同**：经典 RAG 做向量相似度搜索，GraphRAG 做图遍历+向量检索双引擎
3. **推理能力不同**：在多跳关系推理场景下，GraphRAG 比经典 RAG 召回率提升 40-80%
4. **构建成本不同**：GraphRAG 需要额外的实体抽取和关系抽取阶段，成本显著更高

GraphRAG 的**最佳应用场景**：
- 强关系型查询："A 公司和 B 公司有什么关系？"
- 多跳推理："A 公司的竞争对手的供应商有哪些？"
- 聚合分析："文档集中讨论了哪些主题？变化趋势是什么？"

不建议使用 GraphRAG 的场景：简单事实问答、对延迟极度敏感、文档间没有明显关系。

实践中，GraphRAG 和 Agentic RAG 并非二选一——可以构建"Graph-Agentic RAG"融合架构，让 Agent 在推理过程中根据问题类型动态选择向量检索或图检索路径。
